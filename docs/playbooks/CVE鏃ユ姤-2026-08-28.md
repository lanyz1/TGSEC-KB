```text

   login_type=0-0&email=<a>@x.tld&max_repo_creation=-1&active=on&admin=on&allow_git_hook=on
```

# Gitea diffpatch RCE — CVE-2026-60004

## 实战实况（2026-09 一台 1Panel + Docker 源站，Gitea :3003 直出公网）

**入口**：普通账号 → diffpatch 写 hook → **Gitea 容器内命令执行**。

- ★ **同一个 hook 必须 apply 两次才会跑**：第一次只入库/落文件，第二次才真正触发执行。
  只发一次就下结论「没打通」是本类目最常见的误判（与 §路 C 的 Gogs hook 不同，那条 push 即触发）。
- 拿到的是 **容器内**权限，不是宿主机：实测镜像底座是 **s6 + `su-exec`**（入口由 s6 监督、切用户降权），
  **换 `git`/`sh` 二进制也提不到容器 root** —— 别在这上面耗时间，直接做 `container-security-testing`
  三点五节的天花板判定，能出就出，出不去就按「容器权限」结案。
- 版本口径以 `/api/v1/version` 实测为准（报告目标是 2026 年的 Gitea 26.x，与卡内 `<1.27.1` 判据同一前提：
  **未打 diffpatch 补丁即阳性**）。
- 收尾（用户要求清库/锁定场景）：`gitea` 库里把账号 `prohibit_login=1`、只留一个自控号、关注册与 OpenID，
  再 `DROP DATABASE gitea_<实例>`。
- **同机常有并列的第二条 DB 路**：Gitea 只是入口之一，同源站公网开放 5432 且应用账号是 superuser 时，
