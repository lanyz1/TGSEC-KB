# 公告全文补抓 + 阶段修复轮（2026-10 上线）

## 一句话
「项目看不到/归错组」类 bug 有四层真因：**时间格式、判据短路、公告解析、排序键**；只修一层不够。

## 四条硬结论（判据）
1. **索引时间字段整片空 ⇒ 先查 `master/merge.py::_fmt_ts`**：它按**位数**分流（≥14 位 / 8 位 / 12 位），12 位 `YYYYMMDDHHMM` 漏一个分支就整片空。索引**每轮全量重算 stage** ⇒ 修完下一轮自动回填，**不要手改数据**。
2. **「报名截止」抠不到 ⇒ 查 `_parse_reg_end` 的格式矩阵**：公告原文是 `2026年09月27日 17时00分`（中文年月日 + 时/分），只认 dashed-19 的正则 **100% 失败**。修法 = 「键 × 格式矩阵」，保留 dashed-19 兜底。
3. **判据链会短路**：`sell` 空 + `status=19` 直接判「报名中」⇒ 目标永远埋在 🟢。加兜底必须同时**收紧**（12 位时间与竞价窗口都未到才算）。
4. **列表零排序 = 目标埋没**：🟢/🟡 组此前无排序（338 项里目标在第 240 位）。排序键取不到要退 `projCode`，且行渲染要带时间（`⏰ MM-DD HH:MM`）才看得出来。

## 上线生效判定（最容易踩）
- **合库是短进程循环**：`v6m_daemon.sh`（读 `/opt/v6/merge_sleep`，默认 120s）+ crontab `orch` 每 5 分钟 —— **每轮新起 python，进程启动时才解析 `current`**。⇒ `--activate` 后**自然吃新码，合库侧无需重启**；但**启动早于激活时刻的那一轮仍跑老码**（实测：20:02:23 激活 ⇒ 20:03 那轮仍老码、20:06 启动的那轮才生效）。
- **只有常驻进程要手重启**（bot / priv）。bot 停起**必须串行**（同 token 只允许一个 `getUpdates` 消费者）。
- 判生效：`ps -eo pid,lstart` 看新进程启动时刻**晚于**激活时刻；日志锚 `grep -n 按钮层已接线 | tail -1`；锚点后 `Traceback|ROUTE-ERR` 计数须 0。

## 探针纪律（本轮踩坑）
- **别臆造源码标记串**：用 `[0:12]` / `%Y年%m月%d日` 去 grep 补丁，在新老两棵树上都 0 命中 ⇒ 差点误判「补丁没进包」。**标记串必须从源码原文抄**（如 `len(digits) == 12`、`(\d{4})年(\d{1,2})月`）。
- **差分实验要自校验**：老树（现役）结果必须复现线上已观测值，否则 harness 作废。本轮老树 `derive_stage` = 「报名中」与线上一致 ⇒ PASS 后才采信新树输出。
- **伪 self 直调方法**：`Merger(conf)` 要真 conf 对象（传路径报 `'str' object has no attribute 'get_str'`）⇒ 用 `types.SimpleNamespace(pool=..., tz_off=..., open_status=..., ended_status=..., fallback_days=...)` 并把类里所有 `_` 前缀函数绑到伪对象上，即可**无副作用**直调 `_parse_reg_end` / `derive_stage`。
- **`ssh -n` 与 `bash -s < 脚本` 冲突**：`-n` 把 stdin 指向 /dev/null ⇒ 远端 bash 读不到脚本、**静默零输出**（exit 0 骗人）。投脚本时去掉 `-n`。
