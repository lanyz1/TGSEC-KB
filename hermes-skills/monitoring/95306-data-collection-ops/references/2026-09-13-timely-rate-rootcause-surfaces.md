# 「及时拦截度为什么这么低」根因解剖 —— 报名期曝光面 vs 采集管道(2026-09-13 定论)

姊妹篇:`daily-report-intercept-rate.md`(口径/复算/汇报格式)、`intercept-coverage-measurement.md`、`2026-09-11-miss-forensics-playbook.md`。
本篇 = 用户追问「59% 为什么这么低」时的完整证据链与数据面模型。

## 一、结论(先背这个)

59% = 结构底(双盲 ~15%) + 增量失血: **报名期新登记进入我方 coll 的主通道本就很窄**(依赖票/会话类窄通道),09-10 起票源断供(TQ 断 / priv 池干 / 审计票停)→ >4h 缺口"复活通道"停工 → 存量积压(1-3天 148 家 / 3-7天 72 家,占缺口 ~85%)。
竞价前 85.8% ≈ 历史基线 83–85%:到截止/竞价阶段数据面打开 + 补采合拢 → 恢复正常。**"即时低落、终局健康"= 差的就是报名期实时通道。**

## 二、数据面模型(各视图对报名期新登记的曝光)

|---|---|---|---|
| `bid_package_bidder_business23`(b580 家族) | 竞价阶段语义 | **否**(竞价阶段表) | 2026-09 切片 zgrep 正博嘉/潺通/铁恒/兴胜 **全 0** |

⇒ 采集机若只扫竞价阶段表,报名期新登记根本扫不到;真正接住靠 ①名册家族扫增量 ②票/会话通道。**票荒 = 失血直接原因。**

## 三、单条 miss 五步取证 recipe(可复跑)

1. `plat_enroll_map`:是否在册 + `报名时刻`(判断年龄/批次)
2. roster 切片:`zgrep -c '<企业名>' /data_raw/95306_full/roster_2026-09.jsonl.gz` → 公开可得性
3. b580 切片:`zgrep -c ... b580_2026-09.jsonl.gz` → 预期 0(报名期)→ **不得**以此判"平台没有"
4. 采集机 raw:`grep -rl '<企业名>' /data_raw/<机器>/` → 采集侧是否接过
5. pack_map:`grep -l '<企业名>' /data_pool/*/pack_map.json` → 其他旧批次偶现 = 历史采到过、本批次没接住

实例(大秦22次 OV002026083108391684):①在册(09-09 21:59,与 21次/11次同夜批量报名)②roster=13 ③b580=0 ④raw 零命中 ⑤旧大秦批次 pack_map 有它;其 pack_map 冻结时长 ≠ 故障(其他 1088 个 pack_map 同期在刷,merger 健康——无新数据可合而已)。

## 四、⚠️ 窗口语义坑(两次误判实踩)

各视图 start/end 过滤的**不是同一个日期字段**:b23 ≈ buy_time;biddingandsellingsupplier = 公告日(公告 08-31 的项目,在 09-08~09-13 窗口拉不到它的登记行!)。**"拉不到" ≠ "不存在"**:下 absent 结论前先拉**阳性对照**(某条确知当日/该窗登记的记录)验证窗口命中,或直接 30 天宽窗复拉。

## 五、修复方向(方案已出,待拍板)

1. roster 家族增量接进实时环 → **缺口驱动补采**(发现缺口 → 走带明细通道细查回填)。
2. ⛔ **禁止直接拿名单回填 coll**:指标虚高、业务价值为零(联系人/包件明细才是实物)。
3. 票源复活:priv_loop 已换血重启;TQ 轨恢复后 stale 开始收敛(日志 `ROWS>0` 即实锤)。

## 六、汇报模板(用户问"为什么低/多少")

- 数字:R1/R2 + 明细(c/a,项目数) + 漏采昨→今 + 分层(≤4h / >4h)
- 归因:结构底 + 票荒存量 + (若有)当日事故,各给一句证据
- 一句预期:竞价前回归 83–85%;stale 随票源恢复收敛
