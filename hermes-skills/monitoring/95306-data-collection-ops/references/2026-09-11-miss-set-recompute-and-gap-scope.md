# 待补名单复算(名册−已采)与缺口口径补充(2026-09-11)

## 权威待补集 = 复算法(不依赖用户给单)
- 逻辑 = orch8b 的 miss 计算:对 index 内目标 stage 项目(报名中 / 待竞价 / 竞价中当天 / 已结束≤30天),取 `plat_enroll_map.projs[projCode].企业`(名册企业),减去该项目 pack_map 已采企业(`_norm` 归一:去空格、全半角括号后比对),即每项目 miss。
- 实现要点:直接复用 orch8b.py 的 `_norm` 与数据读取路径(照抄其路径约定最稳);产物落 `/data_pool/miss_current.json` = `{records, uniq, proj_miss, miss_all}`。
- 2026-09-11 实测:**202 项目 / 809 条 / 416 家**(与 orch8b 日志自报 "416" 完全对齐)。stage 分布(项目数):已结束 106 / 报名中 55 / 待竞价 36 / 竞价中 5;条数:577 / 149 / 69 / 14。
- 用户提供的"待补企业清单"通常是平台侧可见子集(项目用平台短名、库内为长名,同一批事实的两个视角)→ **先复算全量、再 overlay 用户名单,勿等完整清单**。

## 口径与误诊防治
- `gaps.json` 的"企业报名缺口" = merger.py:1000 的**窄口径**(审计报名账号 × pack_map,只覆盖被审计到的跳转式报名账号)→ **空 ≠ 无缺口**;全量缺口以上面复算为准。
- "ST放弃"告警 240 条**全部集中在 2026-09-09 单日**(连续失败弃票风暴),v9.12 冷却退避复活后零新增 → 历史事件,勿当现行病灶。
- 没采集**三层归因**(对用户解释的标准框架):
  1. 票源覆盖:跳转式报名→审计 ST≈25% 可覆盖;**直报/批量报名=双盲盲区**;TQ=增强认证事件(非全登录);
  2. 行可见延迟 vs 票 TTL(见 `2026-09-11-tq-delayed-visibility-verdict.md`);
  3. 窗口:报名中 / 已结束≤30天(超窗不可回溯)。
