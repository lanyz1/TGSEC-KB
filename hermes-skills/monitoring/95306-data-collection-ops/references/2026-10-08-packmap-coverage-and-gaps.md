## ⭐ 一、必记坑位：`acct_map.json` 必须用 `map` 反查

```python
am = json.load(open('/opt/v6/acct_map.json'))
# 错误写法（我第一次就踩了，得到"0 命中"的假结论）：
#   acct in am              ← 顶层只有 5 个元数据键，永远 False
# 正确写法：
rev = {str(a): str(e) for e, a in am['map'].items()}   # 账号 -> 企业名
e = rev.get(账号)
```

`acct_map.json` 结构：`{ts, ent_full:7398, size:1648, pack_map:53134, map:{企业名→账号×1648}}`
⇒ `ent_full` = **已知企业总数**；`len(map)` = **有账号的企业数** ⇒ 两者之差 = **映射缺口**。
⇒ ⇒ **任何"映射覆盖率/可补条数"的结论，必须先确认自己查对了层级**，否则会给用户报"0 可补"的假答案。

## ⭐ 二、缺口的四类语义（`/data_pool/gaps.json`）

| 键 | 含义 | 行动 |
|---|---|---|
| `项目包件缺口` | `{proj_id, 缺, pack_ids}` 某项目缺 N 个包件 | 需平台侧复核 |
| `企业报名缺口` | 企业报名维表缺口（常为 0） | 有值才动手 |
| `待确认缺口` | `{notice_id, 账号, 时间}` 有账号但单位归属未知 | **可用 `acct_map` 反查补全** |
| `疑似仅打开页面` | `{proj_id, 账号, 时间, 单位}` 企业点开页面但未落成报名 | **真信号**，追是否漏抓 |
| `采集机告警` | `{giveup:[{acct,tries,tm,at}], overflow, 机器}` | 注意认时间戳，可能是陈旧未清 |

## ⭐ 三、缺口归因法：先分清「平台侧取值」还是「我方产物」

判一个缺口是不是真漏采，**必须找到平台侧独立口径**：

- ✅ `/data_pool/index.json`（53954 项目权威索引）每项带
  `{projName, projCode, status, stage, enterpriseCount, packCount, bidStarttime, live}`
  ⇒ **`enterpriseCount=0` 就是平台说"无人报名"** ⇒ 无 `pack_map` 属**必然**，不是漏采（本案 14 个项目）。
- ⚠️ **循环论证陷阱**：`stage`/`packCount` 也可能是**我方采集产物**（如 `项目包件缺口` 154 条里
  `packCount=0` 是历史项目）⇒ **不能只用我方产物自证"平台没有"**，要拿活票回平台独立查一次才算定论。

⇒ 一句话：**分母取平台侧，分子取我方产物，才算覆盖率**。

## ⭐⭐⭐ 七、补全结果（2026-10-08 执行「补全123」）

### 7.1 `pack_map.json` 完整三键结构（**判缺口前必须知道**）

```json
{
  "targetProj": "<projId 字符串>",
  "enterprises": { "账号或企业名": {
      "单位": "...", "账号": "...", "包件": [...], "时间": "...",
      "来源": "01三态+映射链|8515链接|backfill8|公示包成交人|8515项目级",
      "报名时间_平台": "...", "用户": "联系人", "统一社会信用代码": "...",
      "ST": "...", "_obs": ..., "记录": ... } },
  "包件结果": { "<packId>": {
      "状态": "已决标|竞价中", "码": "22=已决标(中标)|01=竞价中",
      "成交价": "", "审核时间": "...", "报名时间": "..." } }
}
```

⇒ ★ **`enterprises` 的 value 里本身就带 `账号` 字段** ⇒ 建「账号→企业」映射**不必按 key 形态猜**，直接取 `v['账号']` + `v['单位']`。

### 7.2 ★★ 最大坑位：**判包件缺口必须看 `包件结果`，不能只看 `enterprises`**

`gaps.json` 的 `项目包件缺口` **154 条 / 缺 391 包件**经复核 **全部是假缺口**：
`enterprises` 为空 ⇒ 统计脚本判"缺 N 个包件"，但 `包件结果` **154/154 非空且包件数精确吻合**（缺 19 ⇒ 结果 19 条，缺 33 ⇒ 33 条）。
⇒ **只看 `enterprises` 会凭空造出上百条假缺口。**

### 7.3 `index.json` 的 `enterpriseCount` 已验证可靠

逐项比对 `index.enterpriseCount` 与 `pack_map` 实际企业数：**9=9 / 17=17 / 30=30 / 0=0**（`enterpriseCount=0` 的项目 pack_map 里确实 0 家）。
⇒ 用它判「无人报名 ⇒ 无 pack_map 属必然」**成立**（本案 14 个在网项目）。
⚠️ 但 `packCount`（**包件总数**）与 `包件结果`（**已出结果的包件**）**语义不同** —— 在网项目未开标，`包件结果` 为空是正常，**不是缺失**。

### 7.4 「账号→企业」映射可离线全量重建（无需票）

遍历 `53135` 个 `pack_map.json`（**仅 2.5 秒**）⇒ 得 **账号→企业 4953**、企业→账号 3902、信用代码→企业 3489、联系人 771。
覆盖率 **22.3% → 67.0%**（分母 = `acct_map.ent_full` 7398）。
⚠️ **同一企业可有多个账号**（`lk_2b8796d116a2` 与 `lyng123456` 同为河南崇锐贸易）⇒ 别假设"企业→唯一账号"。
⇒ 余下 2445 家无映射的属性同下条：**从未报过名**（`pack_map` 只记"报名参与"的企业）。

### 7.5 `疑似仅打开页面` / `待确认缺口` 的定性

- 44 条空单位账号在**新旧映射表中全部查不到** ⇒ 它们**从未成功报名任何项目** ⇒ 「仅打开页面」= **看了没报**，**没单位是必然，不是漏采**。
- 172 条 `待确认缺口` 中 **49 条可用映射表补出企业**（28.5%），余 123 条同为"从未报名"。
