## 行数 ≠ 家数（「池内 19 / 平台 12」类对不上的总根因）

**判据/显示口径一律用 `pool.ent_unit_count(pid, info)`；`len(ents)` 与 `enterpriseCount` 是记录行数。**

- **机制**：backfill 补录按**账号 key** 落一条（`来源: backfill8`），原始采集按**单位全名 key** 再落一条（无来源），同账号/同包件/同时间 ⇒ 纯重复。实例：7 个账号各多一条 ⇒ `19 = 12 + 7`，按账号去重 = **12 = 平台名册 12**（完全一致）。
- **别名**：同一账号两种单位写法（简称 + 全称）⇒ 只按单位名去重并不到底；实体口径 = 规范化单位名 + **同账号 union-find 合并**，账号为空才退回单位名。
- **影响面**（实测）：在办 425 项里 219 项（51.5%）有此重复，合计虚高 865 行（+44%）；判据 `src=='平台' and plat and 家数>=plat` 因行数天然 ≥ 家数而**偏宽**，容易误报「采全了」。
- **修后同快照复算（旧树 vs 新树各跑同一探针）**：`groups()` 分组逐项一致、✅ 采集完成条数与明细（1/1、4/4）不变 ⇒ 虚高不是 ✅ 的来源；变的只是虚高格本身（19 → 12，卡片 `🏢 企业: 12/12`）。
- **消费点四处**：项目卡「企业」行、采集完成判定、分类列表行 `🏢N/M家`、详情页已采数。
- **已治本并已上线（`v6rel_20261005ah`，2026-10-05 09:40 UTC activate；回滚点 = `ag`）**：口径的**唯一实现**搬到 `collector/entcount.py`（`count_units` / `dedup_units`，纯函数零依赖，bot 与 master 共 import）；**写入侧** `master/merge.py`：`build_index` 写「实体家数」+ 并库循环按实体归并（同账号双记账）+ `rows_of` 出表先去重 ⇒ 读索引的**汇总求和 / 18 列导出 / 判据**全部自动同口径、零额外读盘。
  - ★**18 列 CSV 根本没有「企业数」列**：它的虚高是**同一个企业出重复行** ⇒ 靠 `rows_of` 归并解决；别去找那个不存在的列（找错方向会白改一轮）。
  - ★**归并比计数严**（故意不对称）：`dedup_units` 只并「同账号（非空）」或「都无账号且规范化单位名相同」；**同单位不同账号 = 两笔真报名，绝不并**（并了会丢包件归属）。纯函数反例断言已冻结在闸门里。
  - ★**已知边界**：单位写法不同 + 账号不同 ⇒ 仍算 2 家（归一化只去空白/标点，**不剥公司后缀**——剥了会把「甲厂/甲公司」误并）。跨写法合并靠**账号**那条边。
  - 真池只读预演（未割接新树 `V6_TREE=` 跑）：全池 7,875 项 **72,515 行 → 70,388 家**（虚高 2.9%）；会归并 **520 项 / 2,124 条**；在办 424 项 **2,823 行 → 1,955 家**（虚高 868 / 30.7%，归并 219 项 865 条）；「归并不丢数据」全池校验 **孤儿 0 / 丢包 0**（每个被并键的账号或单位必仍在存活记录里 + 包件 packId 集合不减）。
- **上线记录**：`v6rel_20261005ag`（2026-10-05 09:26 UTC，record `activate.20261005_092601.json`）已上线 `pool.ent_unit_count()`，四处消费点统一；回滚点 `af`。线上终检：用户那条 **19 行 → 12 家 = 平台 12**、卡片 `🏢 企业: 12/12`；在办 424~425 项 **2823 行 → 1955 家**（消虚高 868）；同快照旧/新对照 `groups()` 一致、✅ 仍 2；计时 `ui_home 0.34s / groups 0.47s` 无回归。**数字变小是变准，不是数据丢了**（客户会问，先说明）。

## 上线后终检与两个残留（2026-10-05 `ah` 割接实测）

**生效时机铁律**：`--activate` 只切 `current` 链接、**不重启合库 daemon**（启动日志 `skipped_already_running`）。合库 daemon 每 120s 拉一个**全新子进程** `python3 /opt/v6/v6m.py merge`（子进程启动时才解析 `current`），所以 **activate 那一刻正在跑的那一轮仍用旧码** ⇒ 判效果必须等**第一个在 activate 之后启动的周期**跑完（onset ≈ activate + ≤120s + 单轮 3–4 分钟）。踩过：按 activate 后 2 分钟内池文件的写入误判「补丁没生效」⇒ 已撤回。
判据（只读）：`grep -ac "实体归并" /tmp/v6_merge_daemon.log` 由 0 → 数千，即证新码在跑；再查池文件行数/索引 `enterpriseCount`。

**终检数值（首轮新码，与上线前只读预演完全一致）**：
- 主控索引：在办 424 项 `enterpriseCount` 合计 **2,823 → 1,955**；全池 53,940 项合计 **72,515 → 70,388**。
- 池内：7,875 个项目文件 记录 70,391 行 / 实体 70,388 家（在办 1,958 行 / 1,955 家）。
- 样例 `OC002026091617321254`：**19 行 → 12 行 = 12 家**，索引 `enterpriseCount=12`；18 列实物（`/data_pool/汇总/实时项目汇总_18列.csv`）该项目 36 行 / 12 企业 / 12 账号（12×3 包件）。
- 新 bot pid 556720（flock 单实例、ROUTE-ERR 0、启动后 0 错误行）。

**残留一（口径正确、非 bug）「同名企业多账号」**：同项目下**账号不同、单位名规范化相同** ⇒ `count_units` 计 **1 家**（平台名册口径），但 `dedup_units`/出表**保留每条账号记录** ⇒ 行数可 > 家数。实测在办 3 行（`武汉希澎智创` xpzc1412/whxpzc123456、`广州飞动` deng5188/deng51881、`武汉鑫盛康泉` XSKQ123_8/LJY0122）。⇒ **不许把「行数 == 家数」当验收条件**。

**残留二（真重复）已结束/历史项目的 `包件` 数组自带同 packId 重复条目**：单条记录的 `包件` 里同一 packId 被 append 最多 **54 次**。实测汇总 18 列 CSV：310,389 行 / 真重复组 5,254（同项目+企业+**同账号**+同包件）/ 多余行 **38,035**，分布 **已结束 5,238 组、历史 15 组、在办 1 组**（`四川和记鑫城…` ×2）。

- **双根因（只修一半必漏）**：① **读侧** `collector/entcount.dedup_units` 对单条记录原样保留（`out[k] = dict(ev)`），`_merge_rec` 只在**两条记录归并**时才按 packId 并集 ⇒ 单条自带的 54 份直通出表；② **写侧** `master/writer.merge_ent` / `apply_named` 只保证「**不再新增**重复」（按 packId 建 `have` 表防新增），**从不清理 `old` 里已有的** ⇒ 历史重复永久留存，与分布（已结束 5,238 / 在办 1）**完全吻合**。
- **治本三处（缺一处都算没修）**：`entcount` 加纯函数 `norm_packs`/`norm_units`（同 packId 多份快照**只留最新**）+ `_merge_rec` 的并集改走它 + `dedup_units` 对**每条记录**都归一化；`writer` 两个归并函数**归并前先自愈** `old["包件"]`；池内历史残留另跑一次性清扫（默认 **dry-run**，`--apply` 才写）。
- ★**自愈必须放在 `have` 建表之前**：归一化产出的是 `dict` **副本**，若先建 `have` 再换列表，`have` 里抓的引用会与列表**脱钩** ⇒ 之后 `fill_only` 的字段补写落不进列表（静默丢更新）。
- **同一 packId 多份快照的取舍序**：时间字段最大 → 字段更全 → 列表更靠后；缺字段由其余快照补，**但空值绝不覆盖非空值**（所以「新快照审核状态=未审批」不会把旧的「通过」抹掉 —— 与写入侧既有铁律同源）。**旧口径「更长者胜」已废**：它会让陈旧的驳回原因顶掉新状态。
- **不许并的边界（与家数口径同源）**：不同 packId 绝不并；只有**同 packId 的多份快照**才收敛成一份（收敛的是「同一份包件的多次抓取」，不是「同一个包件的多次报名」）。
- **清扫会改已结束项目的历史导出行数（≈38k 行，客户已交付过的数据）** ⇒ 与发布**分开**、单独点头；探针与清扫一律先 dry-run，报「会掉多少行 + 样例若干」再谈 apply。
- 定性/预演沿用上面的 **18 列重复行定性法**（`tools/_probe_csv18c.py`），别另起口径。

**18 列重复行定性法（只读探针范式，脚本已落地 `tools/_probe_csv18c.py`）**：`csv.DictReader` 两轮计数 —— ① 按 `(项目ID, 企业全称, 登录账号, 包件编号)` 计数 ⇒ >1 = **真重复**；② 按 `(项目ID, 企业全称, 包件编号)` 计数 ⇒ >1 = 多账号合法多行。再拿 `index.json` 的 `stage` 归类，分开「在办」（客户实时看，须干净）与「已结束/历史」（出表尾巴）。汇总 CSV 119 MB ⇒ 解析约 1–2 分钟，探针输出**落文件再读**（直读 stdout 会被管道/后台吞）。
