# 端到端时延测量 + "第一次登录/报名→采集"定论(实测)

> 回答用户核心问题:"从监控到上线,到采集需要多长时间"。答过几轮理论,本次终于有实测。

## 1. 定论(稳态,2026-09-10 实测)

**企业操作(登录/报名点击)→ 采集完成:1-5 分钟;→ bot 可见:3-7 分钟。**

依据:沪4 `journalctl -u v6collector` 实证——WXB8523366 09:16:11 点击"公告报名按钮"
(redirectEnrollUrl 行)→ 09:17 沪4 轮询抓到 → 09:19/09:21 三次处理完成(连点 3 次全捕获)
= 5.5 分钟内采集完成;+ 全链路参数。

## 2. 链路分段(稳态)

| 段 | 耗时 | 机制 |
|---|---|---|
| ① 平台审计行可见 | **秒级**(顶行 lag 7-15s 实测) | 平台日志实时落库,**无写入延迟** |
| ② 审计轮询抓取 | 0-90s(均 ~40s) | 12 台错峰,70-90s/轮 |
| ③ 抓后处理(验活+拉包件+落本地) | 20-60s | 2-3 请求+节流 |
| ④ rsync 回传 | 0-2min(均 60s) | merger daemon 120s 循环 |
| ⑤ 合并入池 + bot | 秒级 / 订阅 ≤60s | 即查即有 |

瓶颈结论(已给用户):已近工程下限,瓶颈=轮询周期(70-90s,12 台错峰=预算/覆盖平衡);
压到 35s 需请求翻倍(预算+风控风险,不值得)。真正不可控=盲区通道(批量静默报名零审计)。

## 3. 测量方法(可复用的三个探针)

### 3a. _lat.json 打点(collector 审计段,v9.16 已内置)
- new_t 处逐条记录:{acct, proj, audit_time=行 operation_time(北京时), proc_time=UTC+8, lag_s, op, m(SHARD)}
- 写 `/tmp/targets/_lat.json`(滚动 300 条)→ rsync 自动回传(根级文件,非项目目录,merger 不 merge)
- 12 台各自独立 seen → 同一 ST 会被多台重复记录 → **真实端到端 = 按 (acct, audit_time) 去重取 min(proc_time)**
  (多台冗余中最快发现者才是系统的真实时延)

### 3b. 顶部行固有延迟探针(查平台侧是否延迟落库)
采集机执行:`python3 -c "import sys; sys.path.insert(0,'/opt/v6'); import collector; ..."`
拉 auditlog 页1(pageSize 100)→ 最新行 operation_time vs now(UTC+8)。实测 7-15s = 平台无延迟。
(审计行字段:operation_time/operation_account/operation_details(含 serviceTicket)/operation_url/
operation_username/operation_ip/operation_status… **无"入库时间"字段**)

### 3c. 日志时间线核对(journalctl)
`journalctl -u v6collector --since "…" | grep -E "账户|审计 ST"` → 每轮 "审计 ST ~50, 新 2-7";
处理行为(冷却计数、拉包件)可精确定位某账户的首次处理时刻——**判定慢样本真伪的唯一可靠手段**。

## 4. ⚠️ 核心坑:seen_st 无序截断 → 重启重放伪影(勿把慢样本当真实时延!)

- 根因:`state["seen_st"] = list(seen)[-2000:]` —— set 无插入序,list(set) 是哈希序稳定但任意的
  2000 条;重启/新台首启后,审计窗内(~30-60min)历史行被当"新 ST"**重放**。
- 症状:_lat.json 出现 19-33min 甚至 30-60min 的"慢样本",12 台全有,新机(蒙10)和刚重启的台最重。
- **本次差点误判为"平台延迟落库"**:顶部行探针(7-15s)+ journalctl 核对(沪4 早就处理过)双双证伪。
- 判据流程:**慢样本 → 先查该账户在该台 journalctl 的首次处理时间 → 已处理过=伪影,勿归因平台/轮询**。
- 重放本身无害(多拉一次包件,幂等),但:①污染打点统计 ②白耗 business 预算。
- 修复方向(当时未做):seen 保存改为按时间序截断 / 保 5000 条,消除重启重放。

## 5. 方法论沉淀

- 测时延先分清三段:**平台可见延迟 / 我们的轮询延迟 / 传输展示延迟**——分开测,别混算。
- 12 台冗余体系里,"首次发现时间"必须跨台取 min,单台数据会高估。
- 部署/重启后的首批打点数据永远有伪影,评估稳态要等至少 30-60min(或对照日志人工剔除)。
- 打点工具上线本身会重启服务 → 会制造它要测的那种伪影;先知道这一点,别绕圈子。
