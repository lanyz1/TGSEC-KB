# 2026-09-12 审核详情缺口口径(用户"有中标为何审核不全"标准答法)

## 案例: 西安79次废钢铁 OY002026083116162635 (pid 3a5a0784-7bd6-4ce5-a855-dc56c23026fe)
- bot 报名总表含 3 条中标(宏达宇×2/恒丰盛达×1), 但 19家×8包件=192格中审核状态仅 67 格有值(35%), 空=null(非"未审批"码)。
- 用户推论"有中标=平台权威已披露, 审核详情为何不全" → 以下五查定论。

## 定论
1. **审核状态/审核码 = 快照字段**: 值 = 该企业【最近一次被捕会话】的拉取结果; 空 = 快照停在报名当天(早于审核动作), 之后无新会话。
2. **中标来源**: 结果发布后仍被抓到会话的企业(快照含 22=中标), 非公告解析。
3. **公告面**: queryBusinessNoticeList 按项目名搜全部 noticeType → 许多项目仅有 1 条项目公告, 无独立结果公告。
4. **8515 匿名通道非全覆盖**(此项目 4 日期窗 1840 行扫描=0); 行身份字段全 null(bidder_name/id/phone), 不支持 condition 过滤(proj_id/bidder_name/proj_name like 试遍均空)。
5. **审核明细非公开面**: 逐企业 通过/未审批 = 过程数据, 仅【企业自身】与【采购方工作台(员工功能)】可见; 公开面=名册+包件+结果。
=> 标准答句: "不是抓丢了——缺的是'有权限看明细的会话'。" 补全公式 = 任意一家企业任意一次可捕登录 × 刷新链 = 自动回填。

## 诊断流程(同类质询复用)
1. 读 CSV 定缺口形态(空 vs 未审批); 2. 主服 pack_map 统计 fill 率 + sample filled/empty;
3. grep 8515 库看覆盖; 4. 收割池(jwt/st32)/机器 enroll_st 找该企业新鲜会话;
5. notices_map 反查公告数; 6. 输出: 快照语义+公开面边界+自动化现状+加速选项。

## 自动化与盲点
- 审核刷新队列(非终态企业)会话触达即重拉; **注意: 刷新 pull 用 ev["ST"] 存量票**——旧票已死则无效, 真正触发 = 新捕获事件/缺票定向补拉。
- audit_harvest.py(10min) 实时收割登录/操作票; 企业看结果那一刻即被抓。
- 加速选项: 给任一企业账号密码=秒补; 或挂"专项盯守"(名单内任意账户出现在收割流→自动回填+推送)。

## 附: 入口细节
- queryBusinessNoticeList 需有效会话(无鉴权=HTTP401; 用收割池最新 st32 可"操作成功"; 旧票碰壁正常, 轮试最新数张)。
