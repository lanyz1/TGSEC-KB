# 采集腿健康诊断：「在跑」≠「有产出」

多腿系统（票池腿 / 审计腿 / 特权腿 / 深翻腿 / 补漏腿）里，`systemctl is-active`、
日志里的 `cycle done`、`tested=80` 全是**活动量**，不是**产出量**。一条腿可以连续
一个月每轮打满、命中恒为 0，而所有活动指标都正常。用户问「某条腿怎么样」时，
先跑完下面的判定链再开口。

## 判定顺序（每步落到文件，不靠日志感觉）

1. **定位腿的身份**：配置段（如 `[<leg>]`）里的注释通常一句话写明它是什么、
   玩哪个账号类型、打哪个端点矩阵。先读它，别拿另一条腿的名字回答用户。
2. **日志只取节奏与计数**：`tail -30 /tmp/<leg>_loop.log`，只取
   `cycle done tested=N tokens=M hits=K` 的 N/M/K，不要用「日志在滚」推断有产出。
3. **找权威汇总文件**：腿自己写的 counters（`<leg>_cov.json` / `<leg>_hits.json`）。
   它的 `命中计数` / `命中票数` / `hits` 是唯一权威结论。
4. **判「从来没成过」还是「最近坏了」**：读同目录 `*_archive_*/` 归档副本里的同一份
   counters。归档也是 0 ⇒ 建线至今零产出，**不要按「最近故障」去修**（会一直修错方向）。
5. **凭据新鲜度**：逐条看凭证数组里的 `login_time` / `checked` 字段与当前时间比对。
   整批停在很久以前 ⇒ 票早失效，不必再探。
6. **真活 vs 假活**：布尔字段会骗人。`alive=True` 同时 `resp` 是
   `502 / 503 / CODE 100「系统服务异常」/ HTTP401` ⇒ 假活。只认业务响应码（HTTP 200 +
   业务 code），不认 `alive`。
7. **票源是否断粮**：抓票器日志里 `NEWTOK 0` 连续出现 ⇒ 上游没有新流水，这条腿
   **我方不可控**，别在原地优化探测器。
8. **权限链够不够**：取到 `auth` 只证明登录成功。`manage:user:default:...` 这类
   **默认角色链没有功能点授权**，端点照样被「没有该数据的访问权限」拒。有 auth ≠ 有权。

## 命中恒 0 时先分责任，再决定投不投

- **我方可控**：轮询频率、出网中继选择、凭据新鲜度筛选、这条腿该不该继续开。
- **我方不可控**：平台侧有无新流水（票源）、账号角色授权、端点权限配置。
  不可控项写进结论就收线，不要继续投入探测。

判据写死在代码里时，恒 0 可能是**逻辑必然**而非故障：有些判定函数把
「未登录 / 系统服务异常 / 权限不足 / HTTP4xx / HTTP5xx」全归入 bad，实测响应全落在
该集合内 ⇒ 结构上不可能有命中。读一次判定函数，再解释 K=0。

## 顺手报出空转腿的附带成本（容易漏）

无产出的腿仍在消耗**出口 IP 的风控画像**：多条腿共用同一批采集机出口，若都打同一个
高敏端点（如 `/user/info`），会叠加 IP 级异常标记。诊断空转腿时一并给出它的
**请求量 + 出口 IP**，并给降频/停线建议 + 回滚路径，让用户拍板。
