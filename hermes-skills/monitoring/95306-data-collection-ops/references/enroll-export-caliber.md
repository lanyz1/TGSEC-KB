# 报名总表导出：三口径对账、联系方式缺口与「平台外」机制

用户投诉「平台 N / 采集 N / 表格 N 三个数不符」或「部分企业没有联系方式」时，按本文件走。
**核心纪律：先按口径验算，再谈 bug。三个数能互相推得出来就不是丢数据。**

## 一、三个数字分别是什么（口径基线）

| 口径 | 定义 | 落位 |
|---|---|---|
| 平台 N | 平台侧的报名企业名单（按项目） | `/data_pool/plat_enroll_map.json` → `projs[projCode]` = `{企业数, 企业:[全称…], 公告日, 报名时刻:{全称:时刻}}` |
| 采集 N | 池内采到的报名账号数 | `/data_pool/<池目录>/pack_map.json` → `enterprises`（**键 = 登录账号**） |
| 表格 N | 导出表的企业并集 | `bot/regcsv.py` 三档行：`✅已采` / `⏳待补` / `🔹平台外` |

必须验算的三条恒等式（对不上才继续查）：

- 平台 = 已采(命中平台名单) + 待补
- 池内账号数 = 命中 + 平台外
- 表格企业数 = 已采 + 待补 + 平台外
- 行数 = 已采家×每家包件数 + 待补家×1 + 平台外家×包件数

平台名单的产出：`/opt/v6/sync_plat_enroll.py`，来源平台接口 `findList?funcId=biddingandsellingsupplier`（供应商报名列表），按 `bidder_name` 聚合、按 `proj_code` 归集，30 天滑动窗；出网走采集中继（`relay_post_http`），主服不直连平台。

## 二、池内数据结构与字段语义（对账必读）

`/data_pool/<池目录>/pack_map.json` = `{targetProj, enterprises, 包件结果}`

`enterprises[账号]` = `{ST, _obs, 包件, 单位, 用户, 账号, 时间, 报名时间_平台, 来源}`

- **键 = 登录账号**；**企业名在 `单位`**；`用户` 是注册人姓名，或该账号在平台登记的**公司名**
- `报名时间_平台` 有值 = 这条在平台报名列表里有对应行；**为空 ⇒ 平台报名列表里没有它**（零平台请求的 oracle，判「平台外」成因时第一个看它）
- `_obs` = 观测时间戳（同批采集时间相同）；`来源` 有值表示由某条补采链路写入
- 项目目录里另有 `企业包件表_18列_<projCode>.csv`（**不含联系方式列**）、`项目信息.json`（projId / projCode / projName）、`包件清单.json`

导出表（用户下载件）：13 列 = 数据状态 / 报名时间 / **企业全称(idx2)** / 登录账号 / 联系人 / 法人 / 手机号 / 包件编号 / 包件名称 / 竞卖保证金 / 审核状态 / 报价模式 / 物资条数；BOM + CRLF。

## 三、三个省时间的坑

1. `/data_pool/*/pack_map.json` 是**每个池目录一份**（1.4 万+ 份，每份百 KB 级）。**绝不要 glob 全量打印**——回包能到 5 万字符被截断。直读目标目录那一份。
2. **池目录名 = projId（UUID），不是 projCode**。用 projCode 拼 `/data_pool/<projCode>` 必然全部落空；全域扫描要先建索引：遍历 `*/项目信息.json` 取 `projCode` → 目录。
3. 拿 `enterprises` 的**键**去和平台企业名比对 ⇒ 得到「池内∖平台 = 全部条数」这种全错结论。**必须取 `单位` 字段比对**（这是「拿错维度」的复发点）。

## 四、联系方式（联系人 / 法人 / 手机号）缺口

取值链：`bot/regcsv.py::sup_profile(pool_dir, kw)`

- **`pool_dir` 传的是全局池根 `/data_pool`，不是项目目录**（项目目录下**没有** `企业档案/`、`供应商/` 子目录；直接查项目目录会得出「联系方式全取不到」的错误结论）
- 匹配方式：`企业档案/`(~7.7K) 与 `供应商/`(~37 万) 里按**文件名包含关键字**（`kw = norm_ent_name(单位)` 或平台全称）
- 合并规则：**只在源字段为真值时覆盖**（空串不覆盖）

缺失只有两类根因，先查源、别改代码：

1. **档案库两侧都没有这家企业** ⇒ 取不到。档案库是历史全量采集的产物，新树与老正本里**都只有读取方、没有写入方** ⇒ 靠重跑采集长不出来
2. **有档案，但源字段本身就是空串**（`供应商/<全称>.json` 的 `手机号 = ""`，`企业档案` 那份三项 null）⇒ 不覆盖 ⇒ 表里留空。这类表现为「只有手机号缺、联系人/法人有值」

判缺口类别时逐家比一次「企业档案 + 供应商」两侧，不要只看导出表。

## 五、「平台外」是什么（判定 + 分型）

判定：`bot/render.py::plat_alias_match(单位, 平台名单)` 返回空 ⇒ 归入 extra ⇒ 表里标 `🔹平台外`。

含义：池里有**真**报名记录（账号真、包件真、报名时间真），但这名字在**该项目的平台报名名单里匹配不到** ⇒ 既不能算「已采到位」（跟平台对不上），也不能算「待补」（数据已采到），单列一类如实呈现。

全域实测（387 个有池目录的平台项目）：平台外共 37 条；分布 **352 项目 0 家 / 33 个 1 家 / 2 个 2 家（≈9% 项目会出现）** ⇒ 常态现象，不是数据错误。

三类成因（按此向用户解释）：

1. **同账号两套名字**（最常见）：平台登记名 = 池内 `用户` 字段，池内 `单位` 是另一个名字（简称 / 关联公司）⇒ 匹配不上。典型：`单位` = 石家庄城森回收公司、`用户` = 河北铁景铁路工程有限公司，平台名单里只有后者，且**9 个项目一一对应** ⇒ 同主体跨项目反复呈现同一形态
2. **账号形态或自填简称**：`单位` 字段填成账号（如 `cqjincai`）或简称，平台名单里根本没有这名字
3. **完整全称但该项目的名单没返回它**：该企业在平台存在（其他项目的名单里有），本项目没有 ⇒ 项目级名单缺失，不是企业不存在

可落地改进（改前先问用户）：对判为平台外的记录，再用 **`用户` 字段**去平台名单二次匹配，能救回第 1 类；剩下的标注改细（`🔹平台外·个人自填`）。仅动 `plat_alias_match` 兜底 + `regcsv.py` 标注，不影响「平台 / 已采 / 待补」三个数。

判成因的三件套（零平台请求）：

- `报名时间_平台` 是否有值（空 = 平台报名列表里没这行）
- 全库平台名单 grep 名字片段（含账号、注册人姓名）：命中 0 = 该名字从未进入平台名单体系
- 同一账号跨项目是否反复出现同一形态（一贯形态 vs 一次性异常）

## 六、判断「是不是新版回归」

`/data_pool/汇总/报名总表_<projCode>.csv` 是历史导出（无 `(n)` 后缀）。与用户下载件逐项比：行数 / 唯一企业数 / 三档分布 / 缺联系方式企业名单。一致 ⇒ **既有状态**，不是本次改动引入，别去改代码。

## 七、只读探针套路

- 分析用户附件：`write_file` 落到 scratch 目录再 `python <脚本>.py` 跑（不要内联巨脚本；脚本里注意企业全称在**第 3 列**）
- 远程只读：`write_file` 落本地 → `scp` 到主控 → `ssh python3` 跑 → 输出一律 `| head -N` 截断，避免回包被压缩截断
- 以上定性**全程不需要任何平台请求**（池内字段 + 全库名称 grep + 档案库文件名匹配已足够）；确需平台侧行级证据时才考虑一次只读 GET
