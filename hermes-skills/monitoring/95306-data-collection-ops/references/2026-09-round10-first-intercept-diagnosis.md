## 审计抓票链路丢票点(collector_v9 结构,修前必读)


### 三个确定性丢票缺陷(2026-09-06 定位,修复方案待用户拍板)

1. **enroll 票分片单点**(主因):L1185 `if not _my_ticket(st0): continue` — enroll(报名跳转)补拉队列只由 hash 归属台消费;归属台故障/积压 → tries≥3(5min 间隔×3)删除,其余 7 台看到票却跳过 → 报名企业初次拦截失败。北京局13次欧锦 8:39/德裕隆 9:29/恒铁 9:32 即此。
   修复:enroll_st 消费去掉 _my_ticket 分片(8 台都补拉,幂等,报名量小可接受)。
2. **滚雪球反查 noticeId 盲区**:缺口定向反查(L967)condition like `projId[:8]`,但**报名跳转行只带 noticeId**(redirectEnrollUrl?noticeId=xxx,无 projId)→ 搜不到报名行 → 找回机制失效,只能等企业再登录。修复:反查加 like noticeId[:8](从 notices_map.json 取映射),双条件。
3. **静默丢票**:proc 每轮 ≤15 且排序偏新票 → 积压时 30min 候选窗口滑出的老票**不进 retry**(只有"处理失败"才进 retry)→ 无声放弃;审计溢出(recent_60s≥100)只记录不缓解。修复:proc 上限 15→25+老票年龄保底排序;审计翻页 5→10 页。

另注意:主 proc `seen.add(st)` 在 buyed 拉取**之前**(L1031)→ buyed 失败仍 seen=该企业本次登录白抓;enroll 补拉 got_any=False 时只加 tries 不 seen(该路径 OK)。
