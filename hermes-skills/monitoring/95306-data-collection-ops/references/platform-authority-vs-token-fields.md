# 平台公开面 vs 企业 token 面：字段边界与取数路径

本卡回答一个问题：**某个字段到底能从平台公开面拿，还是必须靠企业活票？** 搞错会白跑一整天。

## 一、平台公开面 = `dataplatform/api/findList`（报名记录）

```
POST https://cg.95306.cn/proxy/dataplatform/api/findList
     {"funcId":"biddingandsellingsupplier", "appId":"system", "pageNum":N, "pageSize":500,
      "params":[{"key":"startDate","value":"YYYY-MM-DD HH:MM:SS"},
                 {"key":"endDate",  "value":"YYYY-MM-DD HH:MM:SS"}]}
```

- 走主控的 relay（`sync_plat_enroll.py` 里的 `relay_post_http`），**主控直连无效**；脚本已在 cron 里跑，
  需要原始返回时直接 `import sync_plat_enroll` 复用它，别自己重写请求。
- **只认时间窗参数**：`params` 里塞 `proj_code` 实测 `rows=0` ⇒ 想取某项目必须窗扫后按 `proj_code` 过滤。
- **该 funcId 家族只有报名一个功能**：13 个兄弟候选
  （`…package/…result/…detail/…notice/…proj/…win/…deal/…bid` 等）实测全部
  `code=-1 不存在的功能` ⇒ **不要再花时间猜 funcId 拿包件**。
- **分页会返回重复行**：同一 (项目, 企业) 出现两条、`buy_time` 只差几十秒
  （实测 16:15:57 / 16:15:34）⇒ 去重必须按 `bidder_name` 取最新 `buy_time`。

### 行字段（实测就这 9 个）
```
bidder_name  bulletin_reldate  buy_time  proj_business_type  proj_business_type_name
proj_code    proj_name         proj_type un_social_cr_code
```
⇒ **无登录账号、无包件、无审核状态**。

## 二、字段归属表（照这张表决定走哪条路）

| 字段 | 来源 | 说明 |
|------|------|------|
| 企业全称 / 统一社会信用代码 | **平台公开面** | `bidder_name` / `un_social_cr_code` ⇒ 缺企业名单可直接补全、无需 token |
| 平台报名时刻 | **平台公开面** | `buy_time`（要买标书就得登录 ⇒ **= 一次必然发生的登录**） |
| 登录账号 | 我方历史采集表 | 项目表 `企业包件表_18列_*.csv` 的 `登录账号` 列 |
| 包件号 / 物资条数 / **审核状态** / 审核时间 / 报名时间 | **企业 token 面** | 18 列表的这几列只能由活票采集 |

⇒ 用户要的「完成项目每企业通过/驳回包件矩阵」**天然被 token 闸门锁死**，平台公开面没有这条路；
所以采网的全部杠杆 = **排序优先级（rank=0）+ 轮次频率 ÷ token 寿命**。

## 三、`buy_time` 与会话时长的用法（关键推理）

- `buy_time`（平台报名）由**购买标书**触发 ⇒ 那一刻该企业一定在 rail 里留下登录记录。
- 我方表的 `报名时间` = **包件提交时刻**。实测：`buy_time 10-02 15:18` → `报名时间 10-02 15:56`，
  差 **38 分钟** ⇒ 该企业在**同一次登录会话内**完成「报名 + 提交包件」
  ⇒ **接住它的登录，同一会话就能把包件 + 审核状态一次拿全**；不必等第二次登录。
- 推论：缺口家的 `buy_time` 若已是几小时/几天前（如 10-08 报名、次日才补采）⇒ 那批票 token 早死，
  **只能等其下一次登录**；而「竞价开始」前它们必须再登录 ⇒ **竞价窗口就是收网窗口**。

## 四、交付形态：平台权威名单对账表

用户需求「活跃项目企业报名采集 + 平台权威名单验证完整度」的标准交付是**一行一企业**的对账表：

```
企业全称,统一信用代码,平台报名时刻,我方登录账号,我方包件行数
```

取数 = 窗扫平台报名接口（覆盖到最早报名日）→ 按 `proj_code` 过滤并按 `bidder_name` 去重
→ 与我方项目表 join（用 `登录账号` 列 + `企业全称`）。
对账表落桌面（CSV，带 UTF-8 BOM 免得 Excel 乱码），完整度 = 「有包件行数>0 的家数 / 平台家数」。

## 五、18 列表的列定义（判断"矩阵字段"是否齐）

```
企业全称,统一信用代码,登录账号,项目ID,项目名称,包件号,包件名称,物资条数,
审核状态,审核时间,报名时间,竞价开始,竞价结束,数据更新时间,…
```

- `竞价开始/竞价结束`（实测 `2026-10-14 09:00` / `10:24`）= 该项目的**必然登录窗**，缺口家会在此时集中登录。
- `审核状态`（`未审批` / 通过 / 驳回）就是需求②的矩阵主体。
