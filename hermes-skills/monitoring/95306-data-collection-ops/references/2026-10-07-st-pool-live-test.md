# 2026-10-07 「ST 池化」构想的现场实测（12 台机队 + 平台接口）

> 用户构想：把已抓到的 ST 汇成池子轮询，把该 ST 名下所有项目详情/包件采齐，避免已结束项目被 skip；
> 缺某企业包件时回池取该企业存活 ST 直接补。测法：只读探针（约 78 个请求，4s 间隔，未走 guard 记账）。

## 一、票寿命（硬数据，推翻「可以长期存票」）

| 样本 | 票龄 | 结果 |
|---|---|---|
| 池内票（19:07–19:48 BJ 登录） | ≤1h | ✅ `/user/info` 正常返企业名 |
| pack_map 老票（今日 00:00 写入） | ~20h | ❌ HTTP 401 未登录 |
| pack_map 老票（09-27 写入） | ~10d | ❌ HTTP 401 |
| 历史实证（前序 ref） | 3.5h+ | ✅ 仍活 |

**结论：票有效窗口 = 小时级（观察到活 ≲3.5h，20h 实测已死）。池化只能利用「票还活着的 1–3 小时」，不能当长期资产。**

## 二、`getSupplierPackageList?statusGroup=` 只剩一个合法值

- `buyed` = 唯一合法；`all/finished/ended/history/win/空` ⇒ `100 系统服务异常`（空值 ⇒ `参数statusGroup不能为空`）。
- **`buyed` 只返回「在网」项目**：实测 4/4 行 `status=19`，池内阶段=报名中/待竞价；某账号名下 8 个**已结束**项目，`buyed` 一个都不返回。
⇒ 「用 ST 枚举该账号名下全部项目（含已结束）」**做不到**，必须自建「账号×项目」索引（`ent_coverage.json` 现成：1702 账号 × 67073 条，含 `end` 标记）。
- 行的项目标识：`id` == `key` == 36 位 UUID == 池内 projId；**`projId` 字段恒为 None** ⇒ 取 `r.get("projId") or r.get("id")`（`targets.py:206` 已如此，非 bug）。

## 三、活票能不能补「已结束」项目（构想核心）✅

- 参与者活票（40min 龄）+ 3 个**已结束**项目 ⇒ **全部 HTTP 200 操作成功**，包件 11/30/1 条完整（乌鲁木齐72次/75次、北京局5次）。
- 非参与者活票 ⇒ `您没有该数据的访问权限`。
⇒ **「回池取该企业存活 ST 直接补采」成立（含已结束项目），但只限「该票主自己参与过的项目」。**

## 四、平台权限边界（决定池化价值上限）

- `/bidProject/getProjInfo?projId=` **无权限校验**：任意活票（连项目无关账号）都能读项目基本信息（projCode/projName/purId/dwdz/dwhz）。
- `/bidMonitor/getSupplier`（项目全部企业）、`packTable`、`getSignInNum`、`bidPackageBidder/packCheckList`、`reqCheckProject/initCheckProject` ⇒ **500「您没有该功能的操作权限」**（普通企业票）。
- 独立复核现役特权环：`priv_loop.py` 每 ~12min 一轮，连续 7 轮 `tested=80 tokens=206 hits=0`，`priv_hits.json` = `{}`。
⇒ **「一张票看全项目所有企业」不成立**（已扫穿归零）。池化价值边界 = 补票主自己的视角。

## 五、响应判读修正（覆盖 2026-09-11 ref 的初版字典）

| 报文 | 真义 |
|---|---|
| HTTP 401 `您未登录或已退出登录` | **死票**（最硬判据，验活必看它） |
| `100 系统服务异常` | 通用错：可能是**死票**，也可能是**参数非法**（如 statusGroup 取值错 / projId=None）⇒ 不能单凭它判死 |
| `您没有该数据的访问权限` | 活票，但缺该项目的数据权限（非参与者） |
| `您没有该功能的操作权限`（HTTP 500 包装） | 活票，缺功能权限（普通企业票对监控/审核端点） |
| `参数statusGroup不能为空` | 参数校验层（证明票活着） |

## 六、票池现状（零请求实测）

- 12 台 `rail_pool` 去重 **241–243 张**活票；`ttl_min=45` 是 **`_evict` 淘汰线**（删 45min 前登录的票），非去重冷却。
- **票池 ∩ 真参与过项目的账号 = 8/241（3.3%）**；96.7% 是「登录过但没参与 02 业务域」的账号 ⇒ 池子大但命中稀疏。

## 七、对「已结束被 skip」的对齐

- v9.21（09-10）已把**已结束 ≤30 天**纳入补漏（`orch8b.py` `elif stg == "已结束"` + bidStarttime≤30d），该项目（108 次，结束 09-29）本在窗内。
- 那 2 家补不上的真因 = **双盲类用户（审计流无痕）⇒ 唯一通道是登录流 token，而他们此后没再登录**（没人登录就没票）。⇒ 「已结束被 skip」是误判，真因是「没票」。

## 八、据实测可定的最小改造（3 处，须过发布点头闸）

1. `rail.ttl_min` 45 → 验活驱动（或 ≤120）：现役 45min 淘汰线比实测寿命短 60–80%，池子被浪费。
2. 把 `ent_coverage`（账号×项目，含已结束）接进 `gapgen` 缺口名册 ⇒ 账号一出现在池里，就把它名下**所有**存量缺口一次性配对补齐（而非只补当前那轮目标项目）。这是该构想的正确实现形态。
3. 补采排队优先「名下含已结束项目存量缺口的账号」（一票可连补多个历史项目）。
