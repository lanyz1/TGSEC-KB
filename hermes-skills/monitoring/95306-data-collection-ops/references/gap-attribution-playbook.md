# 「漏采」归因 playbook（2026-10-08 全池实证）

用户说「采集漏采 / 初次采集漏采 / 这家漏采什么原因」时按本卡走。**先别当 bug 修，先分类。**

## 一、三层机制（记住这三条，八成问题不用跑脚本）

1. **采集粒度 = 「账号 × 项目」**，不是「项目」。包件明细（报了几个包件/保证金/审核状态）**只在该企业自己的登录态里可见** ⇒ 必须有该企业的**票**。
2. **票只来自平台登录流水**（`collector/api.py`：`tokenrailquery` = 票的主来源；`auditlog` = 审计流水）。收割：`collector/tickets.py harvest_p1` —— 每 360s 拉最近 20 分钟流水、6 页 × 500 条，按 `shards.my_account(uid)` 分片认领进 `rail_pool{uid: token}`。
3. **票有效期实测 ≈ 6 小时**（池内按**登录时间** >180min 淘汰；45min 只是 stale 阈值）。
   ⇒ **任何「过 6 小时再回头看」的设计都必然漏票**。补采器 `collector/gapfill.py`：拿票 → `user/info` 探活读企业名 → **匹配缺口名单** → 拉包件 → 回写 pack_map。
   ⇒ **票的唯一用途是「补缺口」**：若企业登录的 6h 窗口内该项目的**名录/缺口 ctx 还没就绪**，票就在池里空转过期 ⇒ **永久漏**（只能等它再登录）。

## 二、三分类（必须分开说，用户看到的「漏」是混在一起的）

| 类 | 判据 | 量（2026-10-08 全池） | 处置 |
|---|---|---|---|
| **A 真漏·票窗口** | 名录有该企业、池内无数据，且无同名/别名匹配 | **352 家次 / 70 项目** | 机制天花板；提升 ctx 时效与捡票密度，其余等企业再登录 |
| **B 假漏·名称口径** | 同一项目**同时**出现「⏳待补」+「🔸已采·未入名录」= 同一家拆两行 | **63 家次 / 36 项目**（含纯口径项目 15） | ✅ `alias_mine.py --apply` + `alias_add.py`（`/data_pool/ent_aliases.json`，热读免重启） |
| **C 首采天然低** | 56 项目部分覆盖、27 项目零明细；部分覆盖项目**首采覆盖率中位 50%、最低 8.3%** | — | 非 bug，靠 gapfill 收敛 |

全池基线：名录家次 **2845** / 池内 **2556** / 归一命中 **2493** = 覆盖 **87.6%**。

## 三、单项目归因顺序（判据链，前一条能定论就停）

| 序 | 查什么 | 位置 | 定论 |
|---|---|---|---|
| 1 | 平台名录家数 | `/data_pool/plat_enroll_map.json` → `projs[code].企业`（**纯名字数组，无账号字段**） | 权威全集 |
| 2 | 池内已采家数 | `/data_pool/<uuid>/pack_map.json` → `enterprises{账号:{单位,包件[],时间}}`（**键是账号**） | 实采 |
| 3 | projCode→uuid | 扫 `/data_pool/*/项目信息.json` 的 `projCode`（**目录名是 uuid，不是平台编号**） | 定位 |
| 4 | 企业是否在册 | `/data_pool/ent_registry.json` → `{信用代码:{企业:{first,last,n}}}` | `first` |
| 5 | `first` vs 项目首采时刻 | `pack_map` 里最早 `时间` | **first > 首采 ⇒ 名录后增长（非漏）；first ≤ 首采 ⇒ 真漏** |
| 6 | `last` 是否停在项目发布日 | 同上 | 停在发布日 = 那天有票没用上（窗口问题）；一直不更新 = 该企业再没登录 |
| 7 | 账号名册 | `/opt/v6/acct_map.json` → `map{企业名:账号}`（**只有账号名，没有密码**） | 有账号 ≠ 有票 |
| 8 | 票池比对 | `/opt/v6/bid2_tokens.json`（`{jwt,st32}`）、`/opt/v6/priv_tokens.json` | **票池是当日滚动池、用完即弃** ⇒ 查不到不代表当时没票，别当判据 |

## 四、坑（都实测踩过）

- **票池比对无用**：滚动池 + TTL 淘汰 ⇒ 已采项目的账号同样「查不到票」。**别用「现在票池里有没有」判当年漏采。**
- **`ent_coverage.json` 不含全部项目**（673 个 uuid 里可能没有目标项目）⇒ 拿它判「本项目采过没采过」会误判。
- **`acct_map.json` 的 `map` 是企业→账号名册**（1648 家），**曾被误当成「票源」**；它只证明「有账号」，不证明「有票」。
- **CSV 导出是快照**：判「漏没漏」前先看文件 mtime。实例：18:34 导出的表里 hncxhy 是「待补」，19:03 池内已被采到 ⇒ **导出后 29 分钟自动补上**。
- **别把「假待补」当漏采**：改名无共同字时同一家会拆两行（池内「西安恒鑫」/ 名录「西安建安实业有限公司(原西安恒鑫)」）。
- **`alias_mine.py` 没有 `__main__` 入口**（`-m` 跑无输出），要 `python3 -c "import sys;sys.argv=['x'];from tools import alias_mine as m;m.main()"`；dry-run 不落盘（跑完 `md5sum /data_pool/ent_aliases.json` 自证未写）。
- 池侧别乱写：**探针只读，导出只写 `/opt/v6/exports`**，`/data_pool` 零写。

## 五、改善项（按收益）

1. **缩短「名录 → 缺口 ctx」时延**（决定报名那批票能不能用上）★★★
2. **报名高峰放开深翻**（`rail` 固定 6 页 × 500 / 20min 窗口，高峰易被翻页截断；`audit` deep 档 181 页但只放偶数分片）★★
3. **别名表扩量**（`alias_mine.py --apply`，写 `/data_pool` 前须用户点头）★
4. **天花板**：无企业账号密码 ⇒ 不能主动登录催票 ⇒ A 类只能等企业再登录。

## 六、探针（scratch 可复用）

`oy_diag.py`~`oy_diag6.py`（单项目逐层下钻）、`gap_quant.py`（全池名录vs已采+首采覆盖率分档）、`gap_first.py`（`first` vs 首采 定性）、`gap_two.py`（真漏/假漏两分类+项目榜）。
