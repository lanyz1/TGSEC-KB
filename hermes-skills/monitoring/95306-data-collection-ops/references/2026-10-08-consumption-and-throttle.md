# 95306 采集端「消化」与风控熔断 —— 实测结论（2026-10-08）

## 铁律速查

1. **`inject_max` 是死键**：`collector/tickets.py:48` 定义了它，但 `self.inject_max` 全库 **0 个消费点**。改它没有任何效果。
   - 对照（**别搞混**）：`[gapfill] probe_limit` **不是**死键 —— 它是真限流点，`main_parts.py:19-24` 用它同时决定候选池（`probe_limit × 3`）与实探数。详见 `2026-10-08-collection-rate-levers.md`。
   `_rail.json` 里 `new` 恰好 = 8 是**分片抓取速率巧合**，不是被 `inject_max` 限制。
2. **真正的消化上限**（按优先级）：
   - `[gapfill] probe_limit = 24`（每轮每台最多验活 24 张，≈4s/张）
   - `[backfill] check_limit = 1500`（深翻腿每轮验活上限，`rail_pages = 30`×500）
   - `main.py:92` `budget/max_biz_per_round = 620`（每轮业务请求总预算）
   ⇒ 三者都**远未打满**（实测 14~17 业务请求/轮 = 预算 2.7%）。
3. **真瓶颈 = `/user/info` 的平台风控熔断**：日志形如
   `⏸ 平台风控：进入冷却 5 分钟（触发点 /user/info，累计 35 次）` →
   `冷却中（剩 21s），本轮补采跳过` → `第 N 轮结束: 请求 45（业务 0 / 数据 45）`。
   ⇒ 每累计 **~35 次**风控响应就冷却 **5 分钟**，该轮 `probed=0`、**秒退**。

## 判断「某台是空转还是冷却」的判别法

看 `master_state.json` 的 `汇总.分片.<名>`：

| 现象 | 含义 |
|---|---|
| `候选 72 / probed 0 / 秒 0` | **冷却整轮跳过**（秒退）。不是分时轮转 —— 轮转会 `候选=0` |
| `候选 72 / probed 18~24 / 秒 65~100` | 真在跑，≈3.8s/张 |
| `probed=24` | 打满 `probe_limit` |

`summary` 里 `probed` 的权威来源是 `master_state` 的 `汇总.验票`（旧文档写的"验票字段"= probed）。

## conf 定位法（改参数前必做）

- `collector.py`：`conf = $V6_CONF` 或 `<tree>/conf/collector.ini`；`<tree>` 由 `find_tree()`（= `/opt/v6/current` 软链）决定。
- 采集机上 **`V6_CONF` 未设置**（service 只设 `Environment=V6_SHARD=n`）。
- 验证改动是否长期有效的**唯一铁证**是启动日志：
  `[boot] tree=/opt/v6/lib/v6rel_XXXX tree_hash=... conf=/opt/v6/lib/.../conf/collector.ini shard_env=0`
- **陷阱**：`/opt/v6/current` 会被主控切到新树，而**新树可能没有 `conf/`**（推送只带代码）。
  所以：改完必须回读 `[boot]` 日志确认 `conf=` 指向你改的那一份，别假设 `current` 一定带 conf。
- `readlink` 验证要在**采集机**上跑：经主控嵌套 ssh 时，`$(readlink ...)` 有可能被中间 shell 提前展开，得出错误路径
  （本次就出现过假报 `v6rel_202610081757`，实际是 `v6rel_202610080354`）。

## 票池 / 上限语义

- `tickets.py:49` `pool_max = 2000` **硬编码**；`_evict`（129–145 行）= **砍最老的**，不会丢新票 ⇒
  "卡 2000 会漏新票"是**伪命题**。单台实测池仅 323~381 张，根本没触顶。
- `[shard] window_min = 30` × 12 台 = **6 小时** ⇒ 设计意图就是"覆盖票寿命"。
  所以 `[rail] ttl_max_min` 应设 **360**（原 180 = 3h 与 6h 设计不自洽）。
- **票龄实测口径（别把票龄当票寿命）**：池内票中位票龄 ≈155 分钟、最大 ≈214 分钟（≈3.5h）。
  这是**当前保留窗口下的观察值**，不是票的自然寿命。`[backfill] seen_ttl_h = 6` 与 `window_min`×12
  三处应保持一致（=6h）。
- **验证保留窗口改动是否生效**：统计票龄 > 旧窗口 的票数（如 `OVER180 > 0`）。
  旧窗口下早该被淘汰的票还在池里 ⇒ 改动已生效；`OVER360 = 0` 只说明还没攒到，**不能**用来否定生效。

## 只读普查套路（12 台）

主控 `jumpers.json` 的 `collectors[].{shard,ip,port,name}` 生成 IP 列表，逐台
`ssh -n -i /root/.ssh/id_ed25519 -o BatchMode=yes -P <port> root@<ip>`。

**坑**：
- while 循环里 ssh **不加 `-n` 会吞掉 stdin**，循环只跑第 1 台（exit 0 却不报错）。
- 嵌套 `ssh "bash -s" <<EOF` **stdin 传不进去**（输出为空）⇒ 改把脚本 scp 过去再执行。
- 先 `head -N` 截断管道会让 while 循环 SIGPIPE 提前退出。
- 远程内联 `python3 -c "…"` 经**多层 shell / 双跳 ssh**时引号与反斜杠会被吃掉（症状：`SyntaxError`、
  `unclosed group`、`else` 后为空）⇒ **一律本地写 `.py`/`.sh` → scp → 直接执行**，不要靠叠加转义层级取胜。

## ★ 定量回答「N 台全开能不能无遗漏消化高峰」

不看感觉，按四步出数，最后一步才下结论。

1. **消化上限（理论）** = 台数 × `[gapfill] probe_limit` × (60 ÷ 轮间隔分钟)。例：12 × 24 × 10 = 2880 张/h。
2. **实测消化** = **当轮真在跑**的台数 × 同一公式（冷却/秒退的台不计）。实测常只有理论的 50%
   ⇒ 两个数都要报，只报理论值会把客户带进错误预期。
3. **反推输入速率**：票池是稳态有界队列 ⇒ **池规模 ≈ 输入速率 × 保留窗口**。
   用 `池总量 ÷ TTL 小时` 反推（例：12 台合计 4351 张 ÷ 3h ≈ 1450 张/h）。
4. **找真高峰**：逐小时统计进池量（`_cstats` 或 rail 的 hourly 计数），**不要拿当下时刻当高峰**
   —— 实测峰值落在工作日 17 点，20 点只剩峰值的 1/15。用「峰值小时」当被除数。

三档一起给：现况（实测拆分台数）/ 满负荷（理论）/ 改动后预期。
**「会积压」≠「永久遗漏」**：票在保留窗口内 ⇒ 高峰积压可在低峰回补。
判据 = `高峰持续时长 + (积压量 ÷ 低峰富余) ≤ TTL`；成立即可说「能补完」，不成立才叫遗漏。

**补漏的真实边界（别把消化当主因）**：`rail_pool` = `{账号: {token, name(姓名), at(进池时刻)}}`
—— 键是**目标账号**，票由该账号自己登录产生，我方只是采集者。缺口名册里 `缺口账号数: 0`
⇒ **我方手里没有这些账号**，既不能替它登录也无法造票。
⇒ 高峰期的真正价值不是「消化快」，而是**目标账号登录概率最高**（票最可能出现）。
答题必须把「消化能力够不够」与「票进不进池」**分开说**，否则会把不可控的票源问题包装成「我们机器不够」。

## ★ 风控熔断参数的去敏改动纪律

`[cool] streak` / `streak_window` 与 conf 自注常互相打架（注释承认「单票返回 100 是正常的（票不适配业务域）」，
却用「窗口内 N 张返回 100 就冷却 5 分钟」当熔断线；配 `[http] gap_business = 4.0` 时
单轮 N 张 × 4s 全落在同一个窗口内 ⇒ **参数自己触发自己**）。对症改法 = 抬高 `streak`（3 → 6）。

- **先 2 台灰度、不盲改全队**：改 → 重启服务 → 逐台回读 `OLD/OLD→NEW` 确认，观察至少一轮后再推剩余台。
- **每台留 `.bak_<用途>` 备份**，改动只动目标行（同文件里其他已调参数不能被顺手覆盖）。
- **效果判据用「秒退台数」而不是日志里冷却行数**：重启会清空冷却计数，窗口内的冷却行数分不出改前改后；
  `st_obs.jsonl` 的「干活台数 / 秒退台数」才是跨改动的可比量（实测首轮告成：probed 167→285、秒退 6→4）。
- **`master_state` 是 30 分钟粒度覆盖写** ⇒ 五分钟采样会把同一条快照重复落三次；判效果必须等到下一个刷新点。
- 无产出的腿（如特权探测线）也在打同一个高敏端点（`/user/info`）⇒ 改熔断参数时一并评估它的
  **请求量 + 出口 IP**，给降频/停线建议 + 回滚路径，让用户拍板。
