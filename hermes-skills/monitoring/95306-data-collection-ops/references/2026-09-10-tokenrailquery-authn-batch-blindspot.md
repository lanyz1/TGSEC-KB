# 2026-09-10 v9.13 前后:tokenrailquery 本质定性 + 批量报名盲区定稿 + 平台侦察法

## tokenrailquery = 增强认证(非密码)事件日志 —— 机制本质定性(推翻"全登录日志"假设)

- login_mode 分布实测(2h 窗 2000 行):仅 **证书登录(265)/随机码登录(151)/手机号登录(84)**,**普通账号密码登录 0 记录**
- 语义:它记录"敏感操作/增强认证事件"(证书/手机/随机码验证),不是每次登录
- 推论链:竞价日进场=强制二次验证 → 有行 → orch 能补(西安 38→54);日常报名(密码会话内普通操作)→ 无验证事件 → 永不记录 → orch 翻不到
- **orch 通道的本质 = 监听"企业做增强认证"事件**,不是"监听登录"

## 入口模型第三类修正:平台官方"批量报名"功能(不是三方自动化工具)

用户截图纠正(9/9):供应商工作台"企业报名"里有 **批量上传/批量报名**(平台自带功能,中大型回收商常用,一次勾选多项目提交)。
批量报名用户操作链 = 密码登录(SSO)→ 工作台批量接口 → **全程无增强认证 + 审计无逐条跳转行** → 双票源同时空。

实测证据:
- 崇锐 9/7 两次批量报名(09:47-09:50 南昌3项 / 11:05-11:09 乌鲁木齐4项,间隔 1-5 秒)=平台批量功能形态
- 批量特征不再是"自动化嫌疑",是平台正常功能;缺口归因别再定性为异常行为

## 长命 token/ST 假说否决(日龄存活实验 = 廉价判定法)

用户质疑"今天报名可能是前几天登录的票还在用" → 实验:
- 采样 8/20、8/24、8/28、9/1、9/4、9/7 各 1h 窗的 03 活票 50 张,现在(9/10)逐个 user/info 验证
- **六档全部 0% 存活**(连 9/7 的票都活不到 3 天后)→ token/ST 无跨天长命形态
- TTL 实测汇总:审计跳转 ST ≥30-40min(泽盛 23:20 报名票→上海 23:52 仍成功);tokenrailquery token 2-4h(58-78min 全活,4h 全死)
- **方法论:判断"是否要扩搜索窗/重扫历史票"前,先跑日龄存活实验**(6 档 × 50 票 ≈ 2min),全死=扩窗无意义(扫死票浪费预算),orch 4h 窗保持

## cooldown 实测时长 ~30min 限流窗(12 台同抢一票现象)

- ZSTLPJ 9/8 23:20 报名 → 12 台同时处理同票:广州 23:23 成功(第一枪)→ 其余台触发"同 ST 高频查询限流"
- 上海持续失败 29min → 23:52 成功 = 冷却窗 ~30min,不是用户记忆的"隔天冻结"
