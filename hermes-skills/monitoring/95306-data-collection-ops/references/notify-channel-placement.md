# 新增推送事件的落点判据(订阅式 vs 无条件)

适用:给数据池/采集链路的 bot 加一类新通知。

## 一、动码前先回答三问
1. **这件事该谁收到?** 只有订阅了该对象的人才关心 → 订阅式;全体授权用户/运维都该知道(数据面变化、采集侧回写) → 无条件。
   判据错的两端都糟:运维级变化做成订阅式 ⇒ 没人订阅就永远静默;海量业务变化做成无条件 ⇒ 刷屏。
2. **候选挂载点的守卫是什么?** 把函数**从头读一遍**,抄下第一段早退条件(`if not subs: return 0` / `if not watch_list` / `if not conf`)。
   挂在早退之后的代码,守卫为假时**永不执行** —— "写好了"和"会触发"是两回事。
3. **项目集从哪拿?** 复用既有的"在网/活跃项目"取数函数(它通常已过完业务过滤闸,别再自己实现一遍)。**绝不遍历全池** —— 五万级项目每轮读文件是不可接受成本。

## 二、诊断「某推送从未发生」(按序查,先别怀疑业务)
1. 状态文件 mtime + 条目数:`ls -l <state>.json` + 加载后数 key。
   **mtime 停在很久以前且只有 1 条 ⇒ 该函数从未被调用过**(早退/线程没起/异常被宽 except 吞掉),不是"事件没发生"。
2. 订阅/名单文件是否为空:名单为空 ⇒ 订阅式通道整条死,先判这个再改码。
3. 启动日志的线程清单里有没有这个线程名。
4. 上面三样都正常,再去查数据面。

## 三、无条件通知的降噪三律(缺一条就刷屏或被当故障)
1. **首轮只建基线不播**:首次运行把存量全部登记进去重文件、推送 0 条。存量(十万级历史条目)当"新增"播出去就是一次事故。
2. **按业务主键永久去重**:键 = 主体 + 对象 + 对象内唯一 id,登记到 `<x>_seen.json`;同一事件永久只推一次。
   不要用"与上轮快照比对"的方案 —— 进程重启/状态丢失后会重播存量。
3. **扫描 cap**:`<x>_scan_cap` 上限(默认取"在网量级",如 200),成本可预测;超量推**汇总一条**而非逐条。

## 四、参考实现骨架
```python
def check_x_news(self):
    cap = conf.get_int(SEG, "x_scan_cap", 200)
    f = conf.get_str(SEG, "x_seen", "<生产绝对路径>")
    st = self._load(f, {}) or {}
    seen = st.get("seen") or {}
    first = "base" not in st                 # 首轮只建基线
    n = 0
    for pid, _info in list(self.pool.live_projects().items())[:cap]:
        d = self.pool.proj_detail(pid)
        n += self._x_hit(项目名, pid, 对象, seen, first)   # 单条比对抽 helper,守住 函数≤50 行
    st["seen"], st["base"] = seen, 1
    self._dump(f, st)
    return n
```
`_x_hit` 顺序固定:算 key → 命中 seen 直接 `return 0` → **先登记** `seen[key]` → `first` 为真则 `return 0`(只登记不播) → 否则 broadcast 一条摘要。

## 四·五、上线后真环境验收锚点(2026-10-08 「📦 新增包件」实例)

无条件通道落地后,**离线夹具全绿不够**,必须回读这 4 样才算「真生效」:
1. 去重状态文件**已生成**且含基线:`/opt/v6/pack_seen.json`(实测 515KB / `seen` 4619 条 /
   `base`=1) —— 没有 `base` 键 = 还在首轮之前,再等一个周期。
2. **启动日志的线程清单里出现新线程名**(`[bot] 线程启动：sub/health/gaps/data/watch/packnew`)。
   线程名不在 = `start_threads` 没注册(或注册在早退分支后),别去查业务。
3. 该线程注册周期在源码里的**行号与秒数**(`bot/main.py` 300s)+ 进程 pid 两次采样稳定。
4. 自启动块起 `grep -c -e Traceback -e Error <日志>` = **0**。

**发布链本身的坑**:`master_deploy.py --activate` **不会重启常驻进程**(判据「已在跑就不重复起」)
⇒ 换树后 bot 仍持旧代码,必须**手工两步**重启(kill 与 start 分两个 exec,方括号 pkill + 核残留 0 +
lock 释放后再起)。fleet 侧同理:**包若在改动之前就打出来了,必须重打一轮再 stage/activate**
(本轮第一版包即因早于改动被打出而作废,白跑一整轮割接)。

## 五、配套改动清单(漏一个就白跑一轮发布)
- [ ] 配置键**同时写进 conf 模板 ini 的对应段**:离线夹具用 `patch_ini` 按段改**模板里的键**,模板缺键会直接报「段里没有键」——代码里带默认值**不算**。
- [ ] 注册成独立 daemon 线程 + 周期键(`x_sec`,默认与同类通道对齐)。
- [ ] 离线夹具:去重文件路径指向 **tmp**(绝不能落到生产绝对路径),并覆盖降噪三律三条断言 —— 首轮 0 条 / 补一条后恰好 1 条且文案命中 / 再跑一次 0 条。
- [ ] 无条件通道**不要**同时挂进订阅函数,否则两处重复推。
- [ ] 夹具顶破结构硬限时(文件 ≤400 行 / 函数 ≤50 行)按既有 `*_parts.py` 模式**外移**分段,且 import 的 **try 与 except 两个分支都要改**(只改一个 ⇒ NameError)。
