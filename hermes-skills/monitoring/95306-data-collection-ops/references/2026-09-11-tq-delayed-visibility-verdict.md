# TQ 行可见性"延迟"判定(2026-09-11 复测;修正"停更"定性)

> 修正 `2026-09-11-tq-outage-sentinels-ammo.md` 的"停更"表述:数据未停,是**延迟到达**且**延迟行票已死**。补扫弹药设计仍有效,但哨兵判据应从"行数>0"升级为"票鲜度"。

## 判别实验(可复用三件套)
1. **同窗跨时刻复测**:09-10 23:00-24:00 窗当晚查询=0;09-11 上午同窗=243 行 → 延迟到达实锤(非停更、非查询故障)。
2. **历史窗复测**:09-10 21:00-22:00 窗在 09-11 查询仍返回 500 行(页帽) → 平台保留数据,可回溯查。
3. **抽票验活**:从 23:00 窗(243 行)与 00:00-01:00 窗(140 行)各抽 03 票调 user/info → **全 DEAD**(code=100"系统服务异常") → 延迟行 token 已过期。
   反例:09-11 07:59-08:59 窗(4 行)抽 3 票 → **2 活**(窗龄 2-3h,在 TTL 内)→ 延迟 < TTL 时仍可采。

## 实测时间线(2026-09-10/11)
- 09-10 21:00 窗:当晚约 1h 内即可见(381 行)→ 当夜延迟 ≤1h。
- 09-10 23:00 窗:当晚查=0,次日上午=243 行 → 延迟升至数小时+。
- 09-11 00:00-01:00=140 行、01:00-02:00=15 行(夜间正常衰减后断档);02:00-08:00≈全空(至 11:00 仍不可见);08:00-09:00 清晨查=0,近 11:00 在 07:59 边界窗见 4 行且带活票。
- 结论:当前为**"稀疏到达 + 延迟数小时 + 部分窗带活票"的混合形态**;边界精度待 30min 级复扫细化。

## 接口(探针用,均无鉴权)
- 行查询:POST https://cg.95306.cn/proxy/dataplatform/api/findList body `{funcId:"tokenrailquery", appId:"system", pageNum:1, pageSize:500, params:[{key:"startDate",value:"YYYY-MM-DD HH:MM:SS"},{key:"endDate",...}]}`;页帽 500。
- 票验活:GET https://cg.95306.cn/business-proxy/business/user/info,Header `Authorization: <token>`;有效=code 为 null 且 success=true;失效=code 100。
- worker 拉取:GET /business-proxy/business/supplierPackage/getBuyPackageList?projId=`<pid>`。

## 已部署
- `/opt/v6/tq_liveness.py`(主服):从 now-2h 起每 1h 往前找**最新有行窗** → 抽 5 个 03 票验活 → 单行 JSON `{ts,frontier,rows,probe,alive,verdict}`;verdict ∈ ALIVE|STALE|NO_DATA。
- 用法:每小时经主服执行;verdict=ALIVE → 报"捕获取暖"并立即全窗密集补扫(行含活票即可回填);STALE → 静默观察。

## 影响与待办
- 补采有效性 = "行可见延迟 < 票 TTL(2-4h)"。延迟 >TTL 的窗:行可见时票已死 → 该段捕获真空**不可回溯**(只能等该批企业在后续窗口再留票)。
- 待办:①30min 级边界复扫定形态;②orch 扫描窗加"延迟补偿"(把 4-10h 前窗并入复扫,含活票即可采);③09-11 当天 8 场竞价(沈阳93/上海124/北京18/成都34/西安79/乌鲁木齐64/西南汽车/贵阳14)在降级状态下进行,持续观察审计通道兜底与后续收敛。
