# 缺口名册修复：实测增益 + 采集端日志口径铁律（2026-10-09）

## 一、日志口径铁律（先看这个，否则所有数字都会错）

采集端日志：`第 N 轮结束: 请求 X（业务 Y / 数据 Z）预算剩 B`

**X/Y/Z 是进程生命周期累计值**（重启归零、单调递增）。实测证据（shard4 上海2 连续 8 轮）：
`请求 2256→2358→2460→2564→2666→2768→2873→2970`，每轮增量 业务 **+55~61** / 数据 +40。

⇒ **唯一正确用法 = 相邻轮差分 Δ业务**（跨重启/异常间隔的相邻两条必须丢弃，否则会出现负跳变）。

### ★ 三个被实测推翻的错误口径（勿再犯）
| 错误做法 | 后果 |
|---|---|
| 用 `max_biz_per_round(620) − 预算剩` 当业务量 | **比值不稳**：实测与 Δ业务 各台 1:1.65 ~ 1:3 ⇒ 不可作代理（历史上报过的「业务/台/轮 24~35」全是这个口径，只能同口径内部相对比较） |
| 把累计值跨轮求平均 | 本轮曾得出「−15.1%」，纯是把凌晨早期低值与大值混在一起，**作废** |
| `journalctl --since -90min \| grep '名单 N / 账号 M' \| tail -1` 判名册到位 | 名册是周期重生成的，**刷新时点晚于窗口的台会被误判成「漏台」**（武汉 shard9 实测：窗口内显示账号 0，直接读文件 = 188/29 与主控一致） |

判名册是否到位**只认直接读文件**：`python3 tools/ctx_fleet_check.py`（逐台 base64 回读）。
注意 ctx 文件内含 `gen_time`/`gen_ts`，**各台 md5 必然不同**，判一致性要用解析后的 `names`/`accts`。

## 二、名册下发机制（补推=覆盖文件，免重启）
主控 `master/orch.py:112` 用 ssh `cat > /tmp/bk8_ctx.json` 推到采集机；
采集端 `collector/main.py:206` **每轮**读该文件并打 `缺口 ctx: 名单 N / 账号 M（生成于 …）`。
同名同内容重推**幂等**（仅动 mtime），不需重启采集机，不影响在跑的轮次。

**12 台合计 48 轮 68.5 → 77 轮 73.4 = +7.2%**

读法（诚实归因）：
- `缺口命中` 列 3h 内 **15 次**（广州 8 / 成都 3 / 上海2 3 / 宁波 1；修前恒 0）= 名册被采集端消费的直接证据。
- 台级 −5%~+40%，领涨台（深圳/上海/成都）与「有缺口目标可采」一致；其余波动在噪声内。
- 窗口跨越 12 台滚动重启（00:14–00:16）与 bot 重启（01:01:55）⇒ **不是单一变量**；
  只能说「名册修复后观测到 +7.2%」，不能说「名册带来 +7.2%」。
- 与 `probe_limit=48` 旧结论自洽：**真杠杆=候选池/名册，不是抬上限**。
- 名册的**主要价值在覆盖缺口企业（完整性），不在抬业务量**（名册仅 188 名/29 账号，量级本就小）。
