## 2. 菜单消息静态性(用户困惑高频源)

菜单消息=发送时的静态文本,状态流转后**旧消息不会自动更新**。用户贴旧截图说"怎么还是报名中/还是 0 个"时:重开菜单(/start)或实测分组函数,通常流转早已生效。同理推送只推变化,不推"已归位"。

## 3. 诊断类提问:先答原因,再等拍板修复

用户问"是什么情况/怎么归0了/为什么不动"类问题,**先给证据链结论,不要边查边改**——本会话用户两次打断("先回答我原因,不要直接做修复")。查证(只读脚本)可以先行,代码修改必须等用户确认方向。

## 5. 静默失败排查套路(按钮点击无响应)

- TG sendMessage 单条上限 **4096 字符**,超出 → API 400 错误被静默吞 → 观感="点按钮没反应"(沈阳99次 18包长名项目 4688 字符实测案例)
- 修复:send_msg 通用超长保护(text>4000 按行切段,每段 ≤3800 分多条,键盘只挂最后一段;edit 不分段)——通用修复后所有长列表/长推送受益
- 排查链:日志 CB 时间线确认回调到达 → 独立进程实测渲染函数(排除逻辑错误,注意输出 len)→ 发现超长 → 修 send_msg 而非业务函数
- 同模式其他源:callback 未 answer_cb(TG 按钮一直转圈)、异常被 try/except 吞无日志

## 6. pack_map 冗余键统计口径(审核数"倒退"假波动)

- pack_map.enterprises 可能**账号键(规范)与历史中文单位键(冗余)并存**(同企业两份);遍历全部键计数=重复计数,冗余键随写入者(补采/合并)重写时有时无 → 统计数 9↔7 抖,3min 监控当"审核回退"推(十堰案例)
- 铁律:**任何 pack_map 企业/审核统计先 `merge_ents_by_unit(enterprises)`(同单位合并、包件 packId 去重、账号键优先)再数**;check_status_summary 一处修复,菜单列表与监控共用函数全局生效
- 监控推送口径只应反映真实业务变化(新报名/审核真变),统计去重先行
