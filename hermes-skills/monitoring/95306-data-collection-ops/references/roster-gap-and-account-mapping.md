# 报名名单缺口 / 账号→企业映射 / 缺口回填驱动(面级参考)

适用:用户问「平台名单 N 家,池里差 K 家,怎么还没补全」/ 竞价日当天仍未补全 / 要定位某企业账号。
与 `miss-audit-and-targeted-backfill.md`(漏采三层判定)互补:本文件只管**名单口径差 + 缺票 + 账号映射**这一面。

## 1. 判读顺序(先口径,后能力)

1. 取分母:`plat_enroll_map.projs[<projCode>]`(**权威**;`biddingandsellingsupplier` 必须带 `startDate/endDate`,无参返 0)。
2. 取分子:`/data_pool/<pid>/pack_map.json` → `enterprises` 键数(**账号键**;`单位` 在同层)。
3. 逐名对差集,先分成三类:**简称未归一 / 我方多采 / 真缺**。
   - 简称类:**改池即可收敛**,但 merger `_pick_fresh` 只取较新一份 ⇒ 必须一次性回填存量(逐个备份 + 原子写 + 计数核验)。
   - 真缺类:进入 §2(票寿命)与 §3(账号映射)。
4. 报给用户的形态:**真缺几家 + 每家缺的原因(没有可用票 / 从未登录 / 无账号线索) + 已布下的抓捕手段**;不要把"口径差"写成"漏采",也不要把"抓不到"写成"在补"。

## 2. 票寿命 = 结构性边界(最重要的机理)

- ST 寿命 **~6h**;collector 侧源码注释即 **"实测ST寿命≥6h,截断6h"** ⇒ 审计扫描窗 = 最近 6h 的登录票。
- `user/info` 语义:**`code=100` = 冷却/暂时退避(不是死票)**;**`404` = 终局(票已死,无法回溯)**。
  ⇒ 单批票全返回 `code=100` 时,**先判"票老了/被限流",不要判"端点或调用形状错"**;要判形状对错另取新鲜票或与采集机在跑的调用对照。
- 推论:企业只在**登录后 6h 内**才可能被识别入库;**报名后不再登录 ⇒ 结构上永远进不了池**。竞价日当天也不保证——报名与竞价是两条动作,线下/一次性报价都可能不登录。
- 因此**唯一可靠的抓捕手段 = 覆盖面**:多台并行 worker 反复覆盖 `[now-4h, now]` 的时间窗,按 `user/info` 的 `dwhz`(单位名)匹配缺口名单;命中即刻拉 `getBuyPackageList`。窗口数学要按"每台负责一个窗"分配,单机只覆盖 30min 会漏全天(见 `bk_fill_multi.py` 型实现)。

## 3. `gap_projects.json` 契约与账号缺口为何填不上

位置 **`/opt/v6/gap_projects.json`**(不是 `/data_pool/`);生成器 `gen_gap_projects.py` cron `8,18,…,58`,产出后**推送 12/12 台**;采集机 collector 消费其中的 `accounts` 索引(命中即优先处理)。

```
projects : { projId: { noticeId, 账号s: {acct: <任意标记>} } }
accounts : { acct: { 项目s: [projId, …] } }      # 采集机"审计命中即优先处理"
notices  / name_gaps
```

- **`_plat_diff_ent_gaps`(平台名单差集→账号缺口)**:`amap` = 池内 `单位→账号`(大写去空格精确匹配);只在**已采到过该企业账号(在其他项目)**时能转账号。**它整段依赖 `plat_enroll_map` 里该项目的键 —— 报名期一结束键会消失 ⇒ 这条支路对本项目永久空转**。
- **`_name_gaps`(持久 roster gz)**:只登记 `names`,**不写 `账号s`** ⇒ 采集机知道缺谁、却不知道该盯哪个账号。
- **修法**:name-gap 分支补一句 `acct = amap.get(name)`,把命中的账号写进 `账号s`(以及 `accounts[acct]["项目s"]`)。改动极小、立即生效、不改采集主逻辑。
- 判"gap 管道活着":看该文件的 mtime 与 `time` 字段(分钟级)、生成器日志里的推送台数(应 12/12)、以及 collector 侧是否有读 `accounts` 的代码路径。

## 4. 企业→账号映射的产地与挖法

| 产地 | 形态 | 说明 |
|---|---|---|
| 池内 pack_map | `单位\|账号\|pk N/M` | **最省**,一账号常跨多项目出现 ⇒ `grep -rl <账号> /data_pool/*/pack_map.json` 量级秒级 |
| `_ent_full` 转储 | `/data_raw/*/_ent_full_<ts>_<账号>.json`,内容 `{"企业","账号","时间","项目"}` | 映射产出的持久库;**产出通道一断就不再新增**,更新时间即通道存活证据 |
| 审计 rail 行 | `operation_account`(登录账号)、`operation_obj_account`(公告 id)、`first_function`(动作名)、`token=<REDACTED> | 一个项目的全量审计行只有 20 个账号而池里 49 家 ⇒ **审计只覆盖跳转式报名 ~25%,不能用它证明"没报名"** |
| 官方供应商库 / matrix CSV | 全称 + 信用代码 + 法人,**无账号**;matrix 有投标主体 `uuid` | 只能证明企业存在与投标主体,拿不到账号 |

- 池里还能见到 **"全称 + 空账号"** 的名字条目 ⇒ 存在按企业名(非账号)落包件的通道;但别指望它补当前项目的缺。
- 拿不到账号时,补救方向 = **按企业名匹配**(见 §2 的 `dwhz` 匹配 + `accounts` 索引),而不是继续找账号。

## 5. 8515 活轨的匿名性 + 阳性对照探针配方

- `bid_package_bidder_business23`(活轨,**矩阵 CSV 的来源**):字段有 `proj_id/pack_id/uuid/buy_time/status/check_time/current_price/hereor_time/memo/ratinglevel`,**而 `bidder_name`/`bidder_id`/`dwcode` 恒为 null** ⇒ **按企业名 `like` 查必 0 行**;按 `proj_code`/`proj_id` 过滤也不保证可用。
- 名字只存在于**周期性 bulk 导出**(b580 系列 → matrix CSV);该导出会停更 ⇒ **要看"最新"的企业名/投标名单时不能用它**。
- **★ 阳性对照探针(批量查询 0 行时的定层法)**:0 行有三种成因,顺序排除:
  1. **轨道活着吗** —— 无条件下、只给时间窗(带 `params:[{start_time},{end_time}]`)拉几行,有行 = 活;
  2. **参数形状对吗** —— 拿第 1 步样本行里真实的 `pack_id` 重跑**同形状的过滤查询**,应能命中该行;
  3. 两者都通过,**才轮到**"目标确实没有数据"。
  - 实测坑:带 `condition` 但**省略时间窗** ⇒ 0 行(看着像"没数据");该轨字段恒空时按该字段过滤 ⇒ 0 行(看着像"项目没人报名")。
  - 结论口径:先把"这轨给不出我要的维度"讲清楚(附阳性对照证据),再谈补数路径。

## 6. 汇报口径(用户只看结论)

- 一句话给**为什么没补全**(结构性原因),再给**已布下的抓捕手段与其边界**(窗口、台数、按名字匹配),最后给**还不能做的部分**(无账号线索者只能等其登录)与**待决策项**。
- 任何"待你点头"的改动(补采上 cron、主控死通道搬到采集机)**单独列出**,不擅自上线。
