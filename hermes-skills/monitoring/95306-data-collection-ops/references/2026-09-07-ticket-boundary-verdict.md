## 终局结论(坐实,勿再追查)

自动化直调报名企业(识别:同分钟/秒级间隔跨局连报多项目,如崇锐 09:47-09:50 南昌 3 项 + 11:05-11:09 乌鲁木齐 4 项,信用代码 91410311MAD3W90R38)的登录在 tokenrailquery **任何时段、任何 status、任何登录方式下都不存在**(累计 ~1.2 万+ 03 行 user/info 全查 0 命中)。

→ 报名期对这类企业**无票可翻是物理边界**。收敛路径只剩:竞价日 cg 入口进场(留票→orch 补)或弃权僵尸 ⚠️。预测承诺必须分两口径(报名期即时 ~57% 天花板 vs 竞价日终局 90%+),拒绝笼统"85-90%"。

## 附带运维沉淀(同日)

- **orch worker CHECK_LIMIT 饥饿**:竞价日单窗 30min 活票 03 可达 900-1900(远超 400),每轮只吃前 N 个导致老票饿死滑出 4h 窗。400→800 消化翻倍;诊断看 worker 日志"候选/已查"是否撞上限。稳态请求量≈候选量(seen 排除后),不是 上限×轮数,预算看板盯 cool 熔断即可
- **rsync 失败告警降噪**:merger `_rsync_fail` 维护连续 count(≤5min 相邻叠加),成功 `_rsync_ok` 清零;bot 侧 count≥3 才推(单次抖动自愈不打扰)。旧记录无 count 按 1 不误报
- **推送企业数口径**:pack_map 键含账号键+中文单位键冗余 → 推送/详情必须 merge_ents_by_unit 去重(曾 54 键显示 50/64,真实去重 44/64);平台名册侧 sync 名单本身无重复
- **手工 orch 轮与 cron 撞轮**:单实例锁保护,撞轮=自动退出。修复后让 cron 自动轮跑即可,手动连跑无增量;验证"进程数"用 ps 详情(ps -ef | grep 会把 bash -c 包装行算进去,勿用 wc -l 数)
- **状态机边界 patch 教训**:orch8b/gen_gap 曾同款 bug(竞价中项目被踢出补采 + 待竞价时间已过误杀 continue),注释与代码一度写反——patch 状态过滤后必须构造该状态实例实测/grep 逻辑,不能只看注释
