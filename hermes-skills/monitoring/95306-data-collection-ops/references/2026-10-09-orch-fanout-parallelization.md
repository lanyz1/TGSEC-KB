# orch 扇出并行化：补采轮次 ≈7.4 倍（2026-10-09 落地）

## 一句话

`master/orch.py` 的 `run()` 是**纯串行**（一台跑完才派下一台）。实测每台 `gap_once` 一轮 ≈**3 分 20 秒** ⇒ 12 台串行 ≈**40 分钟/轮**，`rounds=12` 时一次调用跑 **8 小时**，`flock -n /tmp/v6_orch.lock` 全程霸占 ⇒ **cron 每 5 分钟的触发几乎全部被挡掉空转**。
改成「先全 12 台派发、再各自等结果」后：一轮 **5 分 54 秒**（第 1 轮 5 分 23 秒，稳态 5 分 55/53 秒）⇒ **≈6.8 倍**，且 cron 周期终于真能跑。

> ★ 别把理论值当收益：并行下限 = 单台最慢 4.4 分钟 + 派发 61s + `wait_done` 30s 轮询粒度，三项都要串在一轮里，所以是 **6.8 倍而非 11 倍**。

## 三个曾把方向带偏的误判（都靠实测推翻）

1. **「一轮 6 小时」错** —— 只看了 `for i in BOXES` + `window_min=30` 就推断固定等 30 分钟。
   实际 `wait_done()` 是 **30s 轮询 `/tmp/bk_stats_<i>.json`，文件一出现立刻返回**（早退）。真耗时是 Σ(每台实际)。
2. **「`rounds=12` 是为覆盖票寿命的刻意设计，不能并行」错** —— 每个采集机**用自己的票池**（票不跨机共享）⇒ 并发不增加单账号风控暴露；12 台出口 IP 各异 ⇒ 单 IP 暴露也不变，只有聚合量上升。
3. **「并行会把 12 台的风险叠加到平台」错** —— 采集机本来就各自 360s 自轮询（独立并发），`gap_once` 只是被主控**触发一次**，不新增新通道。

## 补丁（主控侧，零进程重启即生效）

- `master/orch.py`：`run()` 只做轮循环与分发；新增 `_round()`（fanout 分支）+ `_take()`（取一台结果、超时只记账）。
  md5 `65fd799bca7f → a9a07f840789`，267→297 行；`struct_check` 0 新增违规。
- `conf/master.ini` `[shard]` 加 `fanout = 1`（**默认 0 = 旧串行**，改回一行即回滚）。
- 备份：`…/v6rel_202610081757/master/orch.py.bak_20261009_fanout`、`…/conf/master.ini.bak_20261009_fanout`。
- **生效机制**：`v6m.py orch` 每 5 分钟由 cron 重新起进程 ⇒ **改文件即生效，不需要重启任何常驻进程**。

```python
# _round() 关键分支
if not self.conf.get_int("shard", "fanout", 0):        # 旧串行：逐台 D→W→C
    for i, box in enumerate(self.boxes): ...
    return
start = time.time()                                     # 扇出：先全派发
live = [(i, b) for i, b in enumerate(self.boxes) if self.dispatch(i, b)]
for i, box in live:                                     # 再各自等（窗口从本轮起算）
    self._take(agg, i, box, pool, dry, start + self.window_min * 60)
```

## 坑（都是现场踩出来的）

1. **cron 用 `>` 重定向 ⇒ 日志每 5 分钟被“被挡掉的 tick”截断一次**：`grep -c 扇出 /tmp/orch8b_cron.log` 会时有时无。权威聚合看 `/opt/v6/master_state.json`（`摘要.轮/触发/命中/落库/验票/超时`）。
2. **`/tmp/bk_stats_<i>.json` 在 gap_once 开工时被清掉**（防编排读到上一轮残留）⇒ 轮在跑时该文件**不存在**，别把“文件不存在”当失败。
3. **`wait_done` 粒度 30s** ⇒ 收官时间戳最多晚 30s×台序，判断并行程度要看各台 log 首尾时间，不要只看收官时间。
4. **别用 `master_state` 的 `轮` 数判断是否卡死**：它每轮落盘，正在跑时显示的是“已完成轮数”。
5. 回滚一条命令：`cp …/orch.py.bak_20261009_fanout …/orch.py`（配置改 `fanout = 0`），下一个 cron tick 生效。

| 每轮工作量 | 48/台 | 48/台（验票 1728 累计/3轮 ⇒ 576/轮） | 无退化 ✓ |

- **工作量没退化**：12 台 `probed` 均 41~48（满额 48），各台自跑 235~294s，与改前同强度；`超时 0 台`、异常扫描 0 条。
- **`落库 0` 不是扇出打坏的**：每台自己的 `written` 字段当轮就是 0，判定逻辑一字未动 ⇒ 当轮真无新料。
