日期:2026-09-04。本轮三大块:①榨干机制 yield 报告调查 ②ent_coverage(死数据差集)从空壳修复为 3405 企业 ③"平台外"标记实证打脸(平台数据其实最全)。

## 1. ent_coverage 空壳根因与修复(主服 gen_gap_projects.py)

**症状**:主服+8台 ent_coverage.json 只有 1 企业 1 条(基线近乎空)→ collector 对已覆盖的已结束项目全部重复榨干。

**三层根因**:
1. **主服系统时区 = UTC**,平台时间全为北京时 → 脚本里 `datetime.now()` 直接与 bidStarttime/regEndtime 比较错位 8 小时。修复:文件头加 `_bjnow()` = `datetime.now(timezone(timedelta(hours=8))).replace(tzinfo=None)`,所有平台时间比较用 _bjnow()。**普适坑:任何跑在主服/海外机上的调度脚本做平台时间比较前先 date 确认时区。**
2. **safe 判定过严**:pack_map 企业记录的"时间"= 企业首次被抓登录时间(多在报名期),要求 `tm >= bidStarttime` 几乎全挡(6,122 个已结束项目覆盖全被拒)。修复规则:
   - 项目竞价结束 >48h → 平台数据定稿,存量真实包件即终稿,认可可跳过
   - 原 `tm>=bst` 保留(刚结束项目)
3. **榨干文件证据可放宽**:/data_raw/*/_ent_full_*.json 的 **mtime = 实际拉取时刻**(文件内 bidStarttime 字段常为空,须从 index 取)。拉取时刻 >= 竞价开始 → 审核已定稿(平台竞价开始后审核不再变化)→ 认可,无需项目已结束。进行中未开标项目 fts<pb 自动排除;采购项目无 bst 自动排除;活数据永不跳过铁律不受影响。

**验证**:基线 1 企业/1 条 → **3,405 企业/51,502 条可跳过**(只剩 ~176 真实缺口重拉)。8台推送后验证命令:`python3 -c "import json; d=json.load(open('/opt/v6/ent_coverage.json')); print(len(d), sum(len(v) for v in d.values()))"` 每台应输出 3405 51502,文件 ~4.5MB。

**推送机制**:gen_gap main() 每轮只推 gap_projects.json;**ent_coverage 每 6h(cov_ts)才重新生成并推 8 台**。手动推送注意:主服→8台 paramiko 顺序 sftp 推送遇某台慢会整体卡;先前台卡死的 exec 进程不会随 SSH 断开消失 → 多进程并发推送互相挤(阿里云 SSH 并发限制)→ 推送慢=正常,验证靠探测采集机文件而非等推送日志。

## 3. 已结束项目数据通道(纠正"结束即断供"错误认知)

- 竞价结束项目退出平台在网列表(collector 发现/orch8b/gen_gap 不再覆盖)——但这**不等于断供**:
- **榨干队列是已结束项目补强线**:采集机拦到某企业有效 ST → 该企业 buyed 全部项目(含已结束/采购)入队 → getBuyPackageList 用其 ST 拉包件,**平台对终态项目照样返回数据**。每轮 ≤3 企业×10 项目,ent_coverage 跳过已覆盖(修复后真正生效),活数据永不跳过。
- 数据池 20,719 个已结束项目、6,122 个带 pack_map,主要靠此线 + 竞价期间最后一次榨干。
- 物理边界不变:从没被拦到 token 的报名企业(never-login)= 平台无免鉴权全量报名明细接口 → 永久黑洞,进 🏁 标 ⚠️部分数据。竞价当天企业必登录 = 最后补采窗口。

## 4. "平台外"标记 = 我方匹配 bug,不是平台数据不全(实证打脸)

用户质疑:"不应该是平台侧的数据是最全的吗" —— 对,平台全量永远最全。实证:全库唯一含"平台外"的 CSV(漯阜A ON002026082716462849,15待补/54已采/6平台外),其"平台外"企业长葛市博涛金属(账号 cgsbt111)**在平台名册 25 家名单第 19 位**!

**机制**:报名总表 CSV 生成(pix_bot_server.py ~L709-741):平台名册为基底循环,`got.pop(norm名)` 匹配我方已采 → pop 不中 → 平台位置写 ⏳待补(空行);未 pop 出的数据留在 got → 表尾附加 🔹平台外(带包件行)→ **同一企业两行**。名册名与 pack_map 单位名 norm 后不等(全半角/空格/抬头差异待 repr 对比确认)。

**教训(方法论)**:展示层出现"权威源之外多了数据"时,先验证是不是两边同实体匹配失败(名称规范化孤儿),不要直接信代码注释的语义推测——本会话第一轮照注释答"平台名单漏了、兜底抓到"是错的,第二轮实证才纠正。修复方向:norm_ent_name 增强或 pop 失败后二次宽松匹配(去特殊字符/互相包含)。

## 5. 漯阜双公告案例(平台同批物资拆两条公告)

- 用户给名"漯阜铁路有限责任公司 2026年报废机车公开竞价处置项目" ≠ 平台公告名"2026年第3次废移动设备物资处置项目(报废韶山6B型电力机车、报废东风4型内燃机车、报废金鹰重型轨道车…)" → 查项目先按关键词族(漯阜/机车/报废)扫 index,不要死磕用户给的完整名。
- 同一"第3次"拆两公告:A 批 8/27(ON002026082716462849,6包,报名截止9/2,竞价9/10,名册25家)与 B 批 8/25(ON002026082508284281,7包,报名截止8/31,竞价9/8)。两批物资组合不同(销售编号 ZXCZ-JW-20260800340 vs 00421)→ 两个独立项目,不是重复公告。
- **biddingandsellingsupplier 对 B 批返回 0 报名行(仅公告行 bidder_name=null)**——接口行=报名动作流水;项目在窗口内(公告8/25⊂14天)却无报名行 = 平台侧该项目报名数据真空/走其他通道。带 proj_code 参数会被接口忽略(500行全 null 的坑:未知参数不报错,直接返回全量汇总列)。
