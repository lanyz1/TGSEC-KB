# 2026-09 round9: 批次幽灵条目(平台同批双 code 重发残留)识别与菜单过滤

日期:2026-09-05。round8 窗口修复后扫残余"在途但权威 0"项目,发现 14 个;其中 9 个是沈阳铁道 OT 系 → 揭出**平台对同一批次发过两个 code**(旧公告作废但 index 残留),旧 code 条目权威必然 0。

## 1. 现象

沈阳铁道 96/97/98/93/94 次等在 index 里有**两个 code 的同名项目**:
```
OT002026082609594636 | 报名中 | 竞价09-11 09:30 | ✅权威 平台21·采18   ← 活(接口认)
OT002026082610108782 | 报名中 | 竞价09-11 08:30 | ❌权威0 平台0·采0    ← 幽灵(接口无行)
```
接口只认新版 code(竞价常比旧版晚 1h,如 09:30 vs 08:30);旧 code 不在名册快照 → 菜单"平台权威 0"。

## 2. 识别方法(全库扫描)

按 projName 分组(完全相同),组内 ≥2 条且在途(stage∈报名中/待竞价/竞价中):
- 接口快照(plat_enroll_map projs keys)里有 = 活条目;没有 = 疑幽灵
- 同组对照:公告日/竞价时间差(≤1h 同场重发 vs 差天=重拍)、平台权威数、采集数
- 沈阳铁道系重发规律:同 projName + 同公告日 + 竞价差 1h(08:30 vs 09:30)+ 旧 code 接口无行

**非幽灵对照组(勿误杀)**:
- 兰州 OJ 双 code **都在接口**(双权威 1/11)→ 平台认两个,都活 → 都显示
- 广州 4次报废机车双 code 都权威 0(接口有行但 0 企业)→ 无法判定,保留显示
- 跨年同名(2025月饼 vs 2026月饼)= 假双 code,正常
- 真重拍(沈阳铁道 90次 8/17 + 9/2"第二次竞卖")= 两批都活

## 3. 修复:菜单层 _ghost_filter(bot blockable_projects 候选前)

藏规则(同 projName 组内,满足其一即藏):
1. **code 不在名册快照,但组内有在快照的兄弟** → 作废公告(沈阳铁道型)
2. **在快照但平台权威=0 且采集=0,组内有数据兄弟** → 作废残留(北京局11次型:8/27版权威0采0 vs 8/28版权威12采6,竞价同为 9/9 08:00)

只藏确定作废的;兰州式双活/广州式双权威0 无法判定 → 保留(不误杀)。实现要点:采集数=pack_map enterprises 长度,权威数=load_plat_enroll()。12 个幽灵过滤后:88 未开始/152 报名中/74 待竞价,抽查 5 个幽灵 code 残留=无。

## 4. 为什么不做数据层清理

- 幽灵 pid 的目录/pack_map(如有早期采集)不删:数据留存可查
- index stage 不强制"已结束":merger 每轮按采集回传重算 stage,会复活 → **菜单展示层去重,不动 index**

## 5. 类级规则

- **"在途但平台权威 0"≠ 采集漏,先查三层**:①快照窗口切掉(round8,看公告日 vs start)②快照回退(round7)③**批次双 code 幽灵**(本 round:同 projName 双条目,接口只认新版)。第③层特征最显眼:沈阳铁道系高频,发现同 projName 双 code 直接对接口。
- 平台发过废/重发公告后旧 code 长期残留在"在途"(stage 不流转,因竞价时间在未来)→ 菜单全显示时代(round4 起)会成排出现"权威 0"。
- 处理优先级:先全库扫分组(projName 相同)再逐组判定,不要单个项目救火。
