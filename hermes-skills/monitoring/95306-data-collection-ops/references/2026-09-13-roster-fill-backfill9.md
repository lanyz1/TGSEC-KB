## 是什么 / 放哪

- `/opt/v6/roster_fill.py`(主服),cron `*/15`,日志 `/tmp/roster_fill.log`,支持 `--dry` 干跑。
- 补上"报名期新登记 → 我方 coll"的最后一环:消费 plat_enroll_map(每 10 分钟刷新,已换中继)里**已登记、而 pack_map 未见**的企业 → 以真实名册记录写入 pool pack_map。
- 触发词语境:用户说"及时拦截度为什么这么低 / 全部修复完"→ 本脚本即该修复的落地物。

## 设计要点(改动前必读)

- 只处理 stage ∈ 报名中/待竞价/竞价中 的项目;其余不动。
- 缺口判据 `matched()`:**全名相等** 或 **双向子串互含(len≥2)** → 视为已有(治"简名 dwhz≠全名"假缺口,如 coll 存"兴豪" vs 平台"河南省兴豪物资回收有限公司")。
- 写入条目:`key = rs_<md5(单位)[:10]>`,`{账号:key, 单位, 时间:报名时刻, 来源:"roster_fill", 待明细:1, 包件:[]}`。
- **只增不改**(既有 key 一律不碰)+ 原子写(tmp + `os.replace`)+ 幂等(rs_ key 去重)。
- **merger 语义兼容(实证 merger.py L384-416)**:pack_map 合并=保留历史(8515/手动)、采集数据仅同 key 覆盖 → `rs_*` 合成 key 永不与采集 key 碰撞 ⇒ 永续保留。
- 同构先例:系统既有 `来源:"backfill8"` 条目(鑫鑫/星轩等)——本批即 **backfill9 代**。

## 口径与披露义务(重要)

- 本批 = **名册级**记录(单位+报名时刻);**明细(账号/包件/联系人)仍为空**,`待明细:1`。
- 明细由既有审计通道续接:`gaps.json 企业报名缺口` → orch8b/8515 → pack_map。
- **战报口径定义 = "是否持有该企业报名记录"**(名册级即计入);向用户汇报/被问拦截率时**必须区分"名册级 vs 明细级"**,必要时可另算"明细完整版"口径。
- 回滚 = 删掉全部 `来源=="roster_fill"` 条目(一次 python 遍历可完成)。
