# 限速维度判定与爆破可行性算术

## 判定流程

1. 对端点连打到出现 429，记录第几次开始 429（= 窗口内配额）。
2. 换一个从未用过的伪造 IP 头（`X-Forwarded-For: 10.x.y.z`）单发一次：
   - 401/正常业务响应 → 限速**按 IP** 记，头可信 → 可轮换绕过。
   - 仍 429 → 按**账号/挑战/全局**记，或后端取真实 IP。
3. 再用 Tor 换真实出口 IP 单发一次：
   - 恢复 → 纯 IP 维度，可用代理池/Tor 轮换。
   - 仍 429 → 存在全局计数器，轮换无效，立刻停手等冷却。
4. 换不同 body 键（email / challenge / account）测是否有**二级限速**按对象记。

## 判定表

| 现象 | 结论 | 动作 |
|---|---|---|
| XFF 轮换即恢复 | 按 IP | 代理池轮换可继续 |
| XFF 无效、Tor 恢复 | 按真实 IP | 需大量出口 IP |
| Tor 也 429 | 全局/账号计数 | 停，等冷却，换攻击面 |
| 同一 challenge 前 n 次 401、第 n+1 次起 429 | 按挑战限次 | 换挑战才有新配额 |
| 换邮箱仍 429 | 按邮箱/店铺记 | 换对象 |

## 可行性算术

OTP 6 位 = 1,000,000。

- 每挑战 5 次、10 分钟窗口 → 单挑战命中率 0.0005%，换挑战还要重新发码（有发送冷却）→ **不可行**。
- 每挑战不限次但 IP 维度 8 次/分钟 → 10 分钟最多 80 次/IP；覆盖 1e6 需 12,500 个出口 IP → **不可行**。
- 结论线：`需要的出口数 = 密钥空间 / (每IP每窗口次数 × 窗口数)`；>1000 就当死路。

SSH：先跑 60 秒看 hydra 的 `tries/min`。

- 字典条数 ÷ tries/min = 分钟数；>120 分钟就换小字典或放弃。
- 每次尝试 4 秒 = 服务端 `pam_faildelay` 或 MaxStartups 限流，加并发上不去。
- 只开 password 认证、无 publickey 的 OpenSSH：说明管理员用密码登录，值得试站点定制密码，但不值得上 5 万条通用字典。

## 何时转向源码

出现以下任一，停止应用层爆破，转源码审计/服务器侧：

- 服务端用 `crypto/rand` / `secrets.token_*` 生成验证码或 token。
- 有每挑战 attempts 上限 + 常量时间比较。
- token 形式是 `HMAC(secret, ...)`（说明存在服务端密钥，拿到即全破）。
- 有 TOTP 防重放表（`last_step` 单调递增）。

## 探测时的自我约束

- 每轮探测之间 sleep 到窗口结束再继续，别在 429 里连续试探，会延长全局锁定。
- 限速探测本身要记日志（第几次 429、用了什么 IP 头、换 IP 后状态码），否则无法区分「按 IP」和「全局」。
