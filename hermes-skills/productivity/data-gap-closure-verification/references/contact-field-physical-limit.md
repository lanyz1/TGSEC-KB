# 客户说「联系人不全/某列不齐」时的核验流程(联系方式类字段)

## 铁律一:词命中 ≠ 联系方式命中
宽松正则(只匹配「微信」两字)会把「私信我」「微信登录」「平台内部标识」全部计为命中。
**交付前必做加严校验**:手机号要号段+长度校验(`1[3-9]\d{9}`,剥 `+86/86`);微信号要 `[A-Za-z][A-Za-z0-9_-]{4,24}` 或有明确前缀(`vx:`/`微信号:`)。
本次实测:宽松口径报「1,215 条任务含联系方式」,加严后真实值只有 **16 条** —— 交付宽松口径会被客户直接打回。

## 铁律二:扫原始全量 JSON,别扫派生 CSV
派生 CSV 常按需只保留部分列(本次 `tasks.csv` 15 列,丢了 `merchant.desc` 等关键字段)。
⇒ 用 `json.JSONDecoder().raw_decode` 逐条流式解析原始大 JSON(1GB/43k 条 ≈ 140s,内存恒定),对**所有**字符串字段跑正则。
**特别检查「开关型」字段**:`display_contact_info: 1` 不是联系方式文本,而是「是否对外展示」开关 ⇒ 它控制的是**这条记录有没有填值/是否放出**,**不是「该字段是否被序列化下发」**。判定字段存不存在要按响应里的**键**判,绝不能因为开关为 0 就断言该字段平台不下发(见铁律七:承载端点常在另一个对象的口上)。

## 铁律三:真名/名称类字段必须找对位置
同一个商家名可能在多个产物里:接口 A(`merchants.json`)该字段为空,接口 B(任务内嵌 `merchant.desc`)才有值 ⇒ **一处取不到就换数据源再取**,别用昵称(fallback)充当名字,否则交付表整列是错的。

## 铁律四:测「越权读手机号」前先验响应身份
请求 `/api/user?id=<他人id>` 返回 200 且带 `binded_phone` 时,**先比对响应里的 id 是否等于请求的 id**:
本次实测 3 个他人 id 全部返回 `id=<自己>` ⇒ 该端点**忽略参数、只返回本人** ⇒ 不是漏洞,别写成越权。
(反过来,路径形态 `/api/user/<他人id>` 真返回他人数据但字段少 = 另一种情况,要分别下结论。)

## 铁律五:身份比联系方式更能触达
平台不给联系方式时,**把身份给全就是交付**:
- 公司/店铺真名(本次 4,602 家,如「东莞市狼鸣智能科技有限公司」)
- 品牌名(9,037 家)
- 官网/ICP 备案(从真名可外部反查)
客户拿到真名/品牌即可自行触达;绝对不要因为「电话字段拿不到」就交一张空表。

## 铁律六:穷尽后要给「路 + 代价」而不是含糊结论
核验完必须输出:①公开面的物理极限(数字);②平台为何不给(设计证据);③还有哪几条路可补、每条路的**代价与风险**(外部反查不碰目标 / 建立业务关系会暴露客户手机号 / 外部爬第三方站点不在授权范围)。

## 铁律七:宣布「结构性缺口 / 该字段 API 从不下发」前,必须先做承载端点反查

结论的边界只能写到**「在我已穷尽的那组端点内不下发」**。把「某个端点不下发该字段」升级成「平台不下发」是最贵的一类误判:它让整条链停在错误结论上并写进交付
(实测:父对象详情口确实不含联系方式字段 ⇒ 一度定性为结构性缺口,而它实际由另一个口下发)。

反查三步(纯只读,成本极低):
1. **字段名反查承载端点**:把目标字段名在高权端/另一端 bundle 与**全部落盘 chunk** 上 grep,命中件的**调用点**就是承载该字段的端点。
2. **优先看「子对象的详情/聚合端点」,而不是该对象自己的详情端点**:序列化器常把父对象整块内嵌进子对象响应
   (实测子对象快照口 `GET /signup/{id}/snapshot` 的 `data = {signup_detail, task_detail}`,父口被剥掉的联系方式就在 `task_detail` 块里)。
   机理:这类子端点语义是「申请人看自己的记录」⇒ **常缺归属校验,拿到任意合法子对象 id 即可读**,比攻父端点便宜一个量级。
3. **子对象 id 不必枚举**:导出表几乎总带显式 `xx_id` 列(实测 2.15GB 导出 CSV 的第 2 列就是报名 id)⇒ 全量映射,零枚举成本。

判定纪律:
- **字段「是否被序列化」看响应里的键**,不看业务开关。
- 键在、值为空 ⇒ 结论是「该条记录未填/未放出」,下一步是**抽样统计填充率**,而不是回头改写成「不下发」。
- 反查跑完之前,不要输出「物理极限」「只能建立业务关系才拿得到」这类结论句。

## 铁律八:「能不能拿全」要按通道分别核算,并用**并集 + 增量**给覆盖率

「XX 的联系方式能拿全吗」要的是一条**覆盖率会计**,不是一句能/不能。口径固定四步:
1. **分母** = 该角色**真实存在过的实体数**(有记录的账号/企业去重数),**不是任务数/记录数**——用记录数当分母会把覆盖率算假低,
   用某张表的行数当分子会把覆盖率算假高。
2. **逐源非空** = 每个数据源各自的「唯一值数 / 覆盖实体数」,一源一行,写清源表名。
3. **并集去重** = 跨源合并后的唯一值数与唯一实体数(按实体 id 去重,不按记录去重)。
4. **增量** = 「仅 A 无 B」的实体数(如「仅微信、无手机号」)——它才是换通道换来的**真实增益**,是回答「还要不要继续挖」的依据。

实测形状:手机号覆盖 46%(1,205/2,606)→ 加微信号与可点链接 67.8% → 再加「扫码可加」的二维码
⇒ **可触达 99.7%(2,597/2,606),纯零联系方式只有 9 个**。
⇒ 结论句写成「手机号拿不全(天花板 N 个号码 / M 个实体);微信通道覆盖 M2;合并 X/Y = Z%」,
**绝不能用单一通道的缺口否定整体可触达性**——那会把一份 99.7% 的交付说成失败。

## 铁律九:联系二维码解出来是**社交通道**,不是手机号;按链接域分类并归属到实体

图片集解码(纯本地 `cv2`,不外发)后拿到的永远是社交链接。实测 1,861 张 → 554 张可解 → **含手机号 0**:
`work.weixin.qq.com` = 企业微信;`weixin.qq.com/g/…` = 微信群(有有效期);`u.wechat.com` = 个人名片。
- **必须归类后再归属到实体**:用 `task_id → creator_id` 映射把链接挂到人,否则链接无法并进某人的联系方式行。
- 二维码线对手机号**零增益**,但对「可触达」是**独立通道**(实测 220 个实体只有二维码、号/手机都没有)⇒ 两条结论分开写,
  别因为「解不出手机号」就把这条线判成无用。
- 剩余解不出的图多是名片/微信号截图,别当失败项;报「可解率 + 解出内容分布」。

## 铁律十:交叉字段里冒出来的「手机号」先与已有并集求差,再宣布增量

同一实体常把手机号填进**微信列 / 昵称 / 署名 / 开票信息**里(实测 934 条)。这不是新源:
抽出号码后**必须与已有手机号并集做差集**,只报差集里的新值。本次 908 个去重值**全部已在并集内** ⇒ 天花板不上浮。
⇒ 任何「又找到一个源」的结论,先求差再写数,否则就是虚报增量。

## 铁律十一:列名像数据、值域是标志位的列,用前先验值域

准备当值域用的列,先打印 **distinct 值集 + 长度分布**:
- 值集 ⊆ {是,否,Y,N,1,0}(或长度恒为 1)⇒ 是**布尔/开关列,不是数据**;
- 长度分布单峰且极短 ⇒ 先怀疑是标志位或枚举,不是 ID/号码。

实测一列名叫 `微信登录账号`,12,268 行值全是「是」⇒ 若按「微信号」并入,
交付表会被塞进 12,268 条垃圾、且整表每一列的覆盖率都虚高。**列名不可信,值域才可信。**

## 铁律十二:免票/无鉴权端点的状态会漂移,用前复测;规划管线前先看对象 schema

- 同一个端点**换个日期就可能被厂商补上鉴权**(实测某查询口此前 200 可直读,复测已是全 401)。
  ⇒ 依赖某条端点的数据线,**每次用前跑一次只读复测并记下状态码**;宣布「这条线死了」必须附复测证据,不能凭印象。
- **门开着也不等于有你要的字段**:实测那个支付流水口有 16 万余条、内嵌 user 对象**只有 17 个键,本来就没有联系方式**。
  ⇒ 规划脱字段前**先打印对象 `keys` 看 schema**,否则整条管线做完才发现目标字段根本不在里面。
  (顺序:先看 schema 再看鉴权——成本一样,收益更大。)

## 铁律十三:并集类交付的产物形状与自检(含合并脚本变量遮蔽坑)

产物固定「两表 + 一份统计」:
- **长表**(一行一通道:值 / 通道类型 / 实体id / 署名 / 真名 / 品牌 / 是否付费 / 付费额 / 来源,链接类附所属二维码 URL)
  = 对方可直接照着逐个加好友;
- **宽表**(一行一实体:手机号(全部)/ 微信号(全部)/ 企业微信·群·名片链接 / 二维码URL / 可触达通道数 / 付费额)
  = 用于盘点与分级;
- **统计**:逐源数字 + 并集 + 仅X无Y + **付费子集单列**(付费实体才是那批值钱的,要单独报个数与金额)。

纪律:
- **合并脚本的循环变量不能遮蔽身份字典**:`for uid, d in byuid.items()` 会把上文 `d = ident[...]` 覆盖成通道字典,
  于是所有归属列都写成 `[]`。⇒ 用 `ch`/`info` 等不同名。
- **生成后必做健全性自检**:逐列非空计数是否落在合理区间 + 扫单元格里有没有 `[`/`{`/`None`/`defaultdict`。
  Python 容器被 `str()` 写进 CSV 会**伪装成「有值」**(空列表 → `"[]"`),让每一列覆盖率都看着是 100%
  ——最容易发生的形态是「某一列居然每行都有值」,看到这种就该停下来查值域而不是直接交付。
- **PII 值不入对话**:回传只给「非空数 / 覆盖率 / 结论」,实值只落文件;抽样核验也掩码(如 `***` + 后 4 位)。
- 交付表命名带口径(如 `…_联系方式总表_手机+微信.csv`),并在回复里写清「哪张是主表、哪张能直接照着做」。
