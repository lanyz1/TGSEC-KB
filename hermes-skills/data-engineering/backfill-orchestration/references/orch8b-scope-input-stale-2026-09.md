# 补漏范围扩展 + 编排输入断链检测(2026-09 实录)

## 1. 补漏范围:报名中 + 竞价开始前的待竞价

原实现只补 `stage=="报名中"` 的项目。报名截止后项目转"待竞价",orch8b 立即放弃 → 截止前几小时扎堆报名产生的漏采(当时 30min 轮 + 2h 凭证窗口来不及)永久遗留,采集完整度停摆。

修复(orch8b targets 过滤):
```python
if stg not in ("报名中", "待竞价"):
    continue
if stg == "待竞价":
    bst = str(info.get("bidStarttime") or "")[:16]
    if bst and bst < 平台时间系now:   # UTC+8,勿用服务器UTC直比
        continue   # 竞价已开始,不再补
```
理由:报名截止后权威名册不再增长——补一个少一个,应补到竞价开始为止;竞价开始后(或平台已切终态)才停止。

配套(菜单分组"采集完成"分类):报名结束未竞价阶段的项目按 平台名册差集 拆成"待补中/采集完成"两组,采集完成的单独归档;补漏写回后项目自动从"待补"挪到"完成"(纯状态驱动,无手工)。判定:平台名册非空 且 差集=0 → 完成;平台无名册 → 无法判定,归待补。

## 2. 编排输入断链检测(产物陈旧 = 链路断)

案例:缺口清单 gap_projects.json mtime 停在 28 小时前,而 8 台采集机的"审计命中即补拉"机制依赖它(每 60s 重读)。根因两层:
1. 生成方 `gen_gap_projects.py` **不在 cron**(只有 sync_plat_enroll + orch8b 两条)→ 产物停滞;
2. 生成方输入 gaps.json 的"企业报名缺口"由已停摆的 merger 填充 → 即使跑也只有项目级缺口,企业级缺口为空。

排障顺序(可复用):
1. 产物 mtime vs 期望周期 → 停更?
2. 生成方在不在 cron/常驻进程?(注意:主进程可能 subprocess 内部调度——别只看 crontab)
3. 生成方输入是否断供?(缺口源由退休组件填充 = 断供)
4. 修复 = 在生成方内**自算差集**(plat_enroll 权威名册 vs pack_map),不再依赖退休组件输入;补注册 cron。
5. 效果验证:产物内容从"0 项目/29 账号"变"58 项目/70 账号",8 台推送 8/8。

## 3. 企业名→账号 的映射来源

差集按企业名计算,但执行机补拉要账号/token:从数据池"进行中项目 pack_map"里收集 企业名(norm 后)→ 账号 映射(同一企业报名多个项目,其它项目里采到过账号即命中)。映射不到的纯新人 = 物理边界(报名后从未在任何项目被审计/采集见过)→ 只能靠凭证轨迹窗口等它下次登录,如实标注"待补"。
