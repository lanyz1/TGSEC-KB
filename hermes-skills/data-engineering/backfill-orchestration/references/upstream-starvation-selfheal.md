# 补漏链上游断供与静默停摆(自检与自愈方法论)

2026-09-03 95306 实战案例:缺口清单(gap_projects.json)停更 28h,采集机审计联动通道静默失效,期间 orch8b 通道照常跑、零告警。完整案例见 `tg-bot-operations/references/95306-v740-gap-chain-coverage-fusion.md`。

## 链式结构 = 链式风险

补漏链是多层串行:`权威名单 sync(30min)→ 缺口清单生成器(差集)→ 清单分发(8台)→ 执行机审计联动`。**任何一环停摆,下游继续消费旧产物,整链静默失效**——上游不报错、下游不告警,只有"缺口迟迟不收敛"这种弱信号。

本案例两根断点叠加:
1. 清单生成器(gen_gap_projects.py)**从未注册进 cron**(产物停留在 28h 前);
2. 其输入 gaps.json"企业报名缺口"由已退役组件(merger)生成 → 断供后该字段恒为 0,即使生成器恢复也只有半份清单。

## 自检方法(可操作)

- **产物文件 mtime 新鲜度**:清单/快照文件修改时间 > 2× 声明周期即告警。与 `crontab -l` 逐条对照:缺注册、路径错、静默崩都能抓到。不要只确认"执行机在跑"。
- **退役/停用任何组件前,先 grep 谁读它的输出**;同理,改造生成器前确认它的每个输入字段还有生产者。
- **看差集是否收敛**:连续 N 轮缺口数不降反升(报名窗口内可能正常上涨,窗口关闭后仍不降=通道疑停),配合 mtime 检查定位。

## 修复模式:消费端自算差集

不修中间层,让最终消费者直接读两个权威源(名单 vs 数据池)现场算缺口,消除中间文件依赖:

- 差集匹配用规范化名(norm:去空格/全角括号统一/大写),与既有工具同口径;
- 缺口是实体名级、而联动清单要凭证级时:从数据池内**同实体其他记录**反查映射(如该企业在别项目被采到过账号);映射不到的(纯新人)= 物理边界,如实标注留给其他通道,不要伪造凭证;
- 覆盖范围=业务有意义窗口(报名中 + 竞价未开始的待竞价),不是全量。

## cron 排布与部署纪律

- 错峰:上游权威 sync 整点 0/30 → 下游清单生成 15/45(避开重型任务 5/35);分发/生成时长计入节奏。
- 执行机端清单 TTL 短重读(60s 级):文件一更新立即生效,无需重启采集机。
- **生成函数与分发 main 分离**:验证只调生成函数看输出;确认无误再跑含分发 main(首次跑会触发 6h 节流的全库基线生成,需后台+观察日志,勿当卡死)。
- 推送结果必须回读:分发函数报 `8/8 台` 后,抽查一台的收文 mtime/内容,别只信主服侧日志。
