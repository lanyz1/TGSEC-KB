# 多机并行数据补漏编排(Backfill Orchestration)

适用:发现「权威名单」与「实际采集数据」存在差集(漏采/缺口)→ 用多台执行机并行补齐 → 写回共享数据池 → cron 常态化看守的场景。

## 架构模式

```
主服(编排):
  1. 读权威名单 + 数据池 → 算差集(漏采清单: 实体名 → 目标ID列表)
  2. ctx.json = {miss_names, miss_map, rounds} → sftp 分发到 N 台执行机
  3. worker 各跑 1 个时间窗分片(并行) → 结果写 /tmp/bk_result_<shard>.json
  4. 轮询 ps/DONE → 收集合并 → 写回共享 pack_map/数据文件
  5. cron 每 30min + 单实例锁(pid 文件 + os.kill(pid,0) 探测)
```

worker(执行机)单轮:
```
拉凭证/候选(按时间窗) → 逐个识别实体身份(如 user/info 返回名称)
→ 命中漏采名单? → 拉详情(按目标ID) → 结果 JSON 落盘
```

## 关键设计(踩坑换来的)

1. **写共享 JSON 前先对齐消费者 schema**。本次教训:补漏 worker 写 pack_map 用 `packs`(dict+审核),而既有生态(采集器/bot 展示)读 `包件`(list+审核状态)→ 79 家企业补了但 bot 读不到,白补一轮。规则:**先 grep 现有读者代码确认字段结构,再写**;数据契约优先于个人喜好。
2. **网络出口必须选目标平台认可的网络**。海外/异地服务器 IP 可能被目标平台 WAF 针对性拦截(业务接口全 code=100/401),同 token 换国内执行机立即成功。先小样验证再大规模分发。
3. **增量 seen 持久化**:`{token: 登录时间}` dict,加载时裁剪 >6h 过期项;旧 list 格式自动识别丢弃。避免 seen 无限膨胀 + 每轮只查新凭证。
4. **时间窗分片**:凭证 TTL 决定窗口长度;N 台各跑不同窗(错峰)覆盖更长时段;窗口太老的机命中 0 属正常(凭证过期),不要当故障。
5. **单实例锁**:pid 文件 + `os.kill(pid, 0)` 检查存活,防 cron 重入;进程异常退出后锁文件残留时 `ProcessLookupError → pass → 重写` 自愈。
6. **验证以最终业务状态为准**:worker 日志 "DONE" 不算成功——必须确认写回的文件被真实消费者(bot/菜单)能读到(schema 兼容验证)。
7. **多副本合并:判"谁更新"用来源产物 mtime(观测时间),不用记录里的逻辑时间字段**。N 台副本由同一批凭证产生时,逻辑时间(如凭证登录时间)几乎全同 ⇒ `>=` 判定会让"最后被扫到的陈旧副本"赢,共享池状态每轮来回翻转、报表与推送相位相反。mtime 才是"这份数据何时被观测到"的真信号;合并时把它写进记录(如 `_obs`)留给下轮比较。同一观测时间**严格保留池内已有值**(用 `>` 而非 `>=`),否则同窗重复合并也会互相覆盖。
8. **合并必须幂等,且用变更计数当信号**:只有真发生变化才写回(`if hits: write`),否则每轮空转刷 mtime,"这份数据有没有更新"再也没法判(池目录 mtime 不是新鲜度代理)。自测把幂等写成断言:同一批数据再并一次必须报 **0 更新**。
9. **并集式合并的两条硬规则**:① **空值不许覆盖非空值**(某台这轮没采到 ≠ 之前采到的作废,否则会抹掉报名截止/审核时间类字段并导致错误分期)② **回填/保留字段集必须与既有数据的键名逐字一致** —— 少一个键,那个字段的历史值就在并库时被静默丢掉。先 grep 消费方 + 从存量数据抽一遍真实键名,再定字段集;同样地,归集键要用消费方读取的那个键(如账号),不是人类可读的名字。
10. **手搓/重写版上线前必须做 parity 对拍**:把新实现与旧实现并行打开,逐条核「分片口径 / 时间窗与 TTL / 字段键名与回填集 / 写库路径唯一性」,而不是只比“跑不跑得通”。差异产出交两份清单:对拍发现的旧口径差异 vs 自测发现的自身 bug。
11. **缺口生成器必须能从「权威名单」独立产出缺项，不能只遍历「已有映射」**：「遍历现映射里的每个实体、找它缺的目标」这类实现有个致命盲区 —— **映射里完全没有的实体（最严重的情形）永远不会产出缺口**；判据写成 `if not ents: continue`（该实体在映射里一条都没有）就是把最该补的整条跳过。⇒ 以**权威名单为左边**做差集（名单在册 ∧ 映射缺该实体/整体空 ⇒ 单独一类缺口），并**拿「全池缺口 0 条」当告警信号**：一片真空通常不是「真没缺口」，而是判据把路走窄了。
  - ★ **修的时候要取「所有腿的补集」，不能只补你看到的那一条腿**：多通路缺口生成器常有 A 腿「遍历已有映射」+
    B 腿「遍历另类来源」，各自带 `continue` 守卫 —— **两条守卫的交集就是死区**（实测：「映射里缺该实体 → continue」
    与「在网对象交 B 腿 → continue」叠加 ⇒「在网 ∧ 映射整空」谁都不管；单看任一腿的判据都「逻辑正确」）。
    先逐条列出每条腿的守卫条件，把 `not(守卫A) ∧ not(守卫B)` 单独成一类，再动手写补丁。
  - **修复的验收三件套**：① 计数从 0 变到 N（治理前对整空对象**恒 0**，跑一轮即可对比）
    ② 已知受害人对象在产出清单里**逐条在位**（不是「总数变大了」就算）
    ③ **喂给下游 worker 的那份交接文件**(ctx/名单)里同样在位。只有 ①②③ 同时成立才算治本，否则是「数字好看了但没接上」。
  - **缺口生成器不许顺手写数据**：它只产「待补清单」。比对件要**复用展示层同一套匹配函数**
    （懒加载、失败即 fail-closed 返回空，绝不猜），否则清单口径与展示口径不一致，又制造出新的假差集。
12. **先分清「机制边界」还是「管道故障」，再动手修**：目标对象的明细/详情类数据常常是**驱动型**的（凭据不在编排机侧、只能等同侧登录产生的短 TTL 票）⇒ 名单有、明细恒空可能是机制边界，不是采集坏了。判据三件套：①**产物落盘时间 vs 最近一次发布/配置变更时间**（排除「是不是我们在更新」）②**池内凭证的有效期**（全部过期 ⇒ 上游断供，不是采集端故障）③**权威日志/快照里该对象的命中数**（0 命中 ⇒ 它压根没出现过，不是采不到）。三条一起看才定性；先看产物时间戳能省掉一整轮自查。

## Pitfalls(通用远程执行坑)

- **pkill -f 自杀**:`bash -c "pkill -f 'xxx'; ...; python3 xxx.py &"` 中 pkill 正则匹配 bash 自身命令行(含后续启动串)→ 自杀,后续命令全不执行(命令"看起来没效果")。修复:kill 与 start 分两次独立 exec;或 pkill 模式避开命令行其余部分。
- **paramiko exec_command 后必须 read**:fire-and-forget(不 read 直接 close)命令可能根本没发出。read 即使超时(PipeTimeout)也说明命令已投递。
- **接口返回结构多变**:同一接口 data 可能是裸 list 也可能是 `{result: []}`;解析用 `d if isinstance(d, list) else d.get("result", [])` 兼容。
- **属性回填技巧**:实体无关的属性(如 packCode 是包件属性不是企业属性)可从同目标其他记录/汇总 CSV 按 ID 匹配回填,不必重新拉取。
- **并发分发**:ThreadPoolExecutor(4 workers)比串行快 4-8 倍;注意 lambda 闭包陷阱(解包元组长度)。
- **先手动单台打通,再并发放大**:单台跑通全流程(识别→写回→消费者可读)是并行的前置条件。
