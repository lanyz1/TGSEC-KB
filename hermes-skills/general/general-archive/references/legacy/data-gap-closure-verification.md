# 数据缺口可补性核验（把「补不了」做成有据的结论）

适用:数据已拖到手(脱库/导出/爬取),客户拿着目标模板问「缺的那几列能不能补齐」。目标不是把空列填满,而是**要么真补上真值,要么用实测证据证明源侧无此数据**——绝不塞推测值充数。

★ **缺口的边界只能写在「已穷尽的那组源」上**: 宣布「该字段平台不下发 / 属结构性缺口」前先做**承载端点反查**
(字段名反查调用点 → 优先看**子对象的详情/聚合口**而非父对象口 → 子对象 id 直接取自已有导出的 `xx_id` 列)。
父对象口没有该字段 ≠ 平台不下发。判定看响应里的**键**,不看业务开关;键在而值为空 ⇒ 下一步是抽样算**填充率**,不是改写成不下发。
详见 `references/contact-field-physical-limit.md` 铁律七。

## 0. 前提铁律(不可跳)
先证明本次取数的**快照完整性**:逐表行数/字节核对到 100.00%（例：10 库 / 7,273 表 / 22,959,603 行逐表核对）。
- 只有完整快照才能把「源库无此数据」下成结论;**残缺 dump 上的「补不了」只是假象**。
- 完整性证明也要写进交付文档,否则对方无法判断结论的可信边界。

## 0b. 空列先做三层归因(未采集 / 加工丢了 / 解析不认)——再谈源侧有没有

「字段整列空」**不等于**源侧无此数据。先按三层归因,每层都有可跑的证据:

1. **原始层 vs 派生层对照**:同一字段在**采集落盘的原始文件**与**索引/导出/汇总**里各打一遍。
   原始有值、派生为空 ⇒ 是我们自己加工丢的,不是上游不给。**只看派生层就下结论是最典型的假阴性。**
2. **解析不认(最常见)**:同一字段在不同接口/产物里**字形不统一**(时间尤其明显,实测并存:12 位无秒
   `YYYY-MM-DD HH:MM` / 14 位 `YYYYMMDD HH:MM:SS` / 中文 `2026年09月06日 16时00分` / 期望的 dashed-19)。
   **只认单一字形的解析器返回空串/None,下游一律当「没给值」** ⇒ 静默丢数据:排序退化成随机、分类判据不命中。
   诊断:对原始值 `re.sub(r'\D','',v)` 数位数;抽样 **≥100 条真实值**回测正则命中率。
3. **输入文件覆盖率**:解析依赖的可选产物(详情页/公告全文/子对象)常只覆盖极少记录。回答「字段为什么全空」
   要同时报**解析成功率**与**输入文件覆盖率**(实测某产物全池仅 0.4%) ⇒ 两者都低时先修覆盖率再修解析,并按
   「业务上还在流转的记录 ∩ 缺该文件」定补抓范围(如阶段∈{报名中,待竞价}的 424 项里 325 项缺公告)。

- **抽取类正则必须用真实样本定形**:凭「上游大概怎么写」写的正则可能 **0 命中**且长期无人发现(功能看着在、实际从未生效)。
- **同族解析器一次改齐**:grep `strptime|mktime|fromtimestamp` 列出全部解析点逐个核对,**只放宽输入、不改输出字形**(改输出会把下游解析器集体打瞎)。
- **兜底判据不得盖过强证据**:「缺字段 + 状态陈旧 ⇒ 判 A」这类兜底必须附「无相反证据」条件,否则短路整条下游判定链。
- **空键排序退化成随机**:按可用性排序时用 `sorted(key=lambda x: (值 or "~", 次级键))`(空键沉底);否则目标行永远翻不到、看着像没采到。
- **数量变化先分辨「丢了」还是「变准」**:空值减少/总数变化可能是修好了,报告里点明方向,别一律写成数据丢失。
- 别据调用点行为反推产出格式:**读产出函数的 `return` 原文再断言**(实测据此误判过一次并当场撤回)。
- 同类实战细节(项目可见性 / 分组归属 / 探针脚本):见 `95306-data-collection-ops` 的
  `references/project-visibility-and-stage.md`。

## 1. 表头全域扫描找候选表
只读每个 TSV 首行,几千张表秒级。
- 用**精确 token** 匹配:`channel_id|proxyid|parentid|sourceparentid|invitecode|agent_id|teamid|spreadid|recommender`。
- **禁用宽泛子串**(`chan`/`sale`):会命中 `ChangeMoney/ChangeType` 这类流水列,几千张表被拉进候选,结果集不可用。
- 命中列的表还要看它**有没有会员键列**(roleid/accountid/userid):无键列的只是汇总/字典表,填不了逐会员字段。

## 2. 逐列非空普查
`csv.DictReader(delimiter='\t')` + `Counter`,一次跑完打印 `列 / 非空数 / 覆盖率`。
- 非空判据排除 `''` **和** `'0'`——`0` 常是合法的「无上级/未设置」值,当成非空会把覆盖率算假高。
- 汇总表的行数/维度也要看:例如代理汇总表枚万行但**只有代理维度**,没有「会员→代理」映射,照样填不了。

## 3. 值域交叉证伪 lookalike 源（最容易踩、后果最重）
覆盖人数可观的候选源,采用前先比**值的域**。
- 实测教训:两张 `T_UserChannel*` 表的 `ChannelID` 覆盖 1,389 / 516 人,看着像渠道归属,但只有 48 个不同值且全 4 位数字(666/1100/1960…),与推广渠道名册的 `channel_id`(6–9 位)**交集为空** ⇒ 那是**支付通道 ID**。
- 规则:两列值域交集为空 / 长度格式截然不同 = 不同域的 ID,不能当同一字段用。**整列塞错数据比留空更糟**——填错了对方拿去算分成、发工资,失真比缺列严重。

## 4. 可推算列先测命中率再决定
- 手机号段→省/市:号段表常只有**中国号段**,国外号码不匹配。
- IP 段→国/省/市:区间表用 `(ip_start_num, ip_end_num)` 排序 + `bisect` 二分;注意这类表中文字段常是 **GBK**,读出要转码。
- 实测命中率低(例 IP 抽样命中 2.1% 且省市多空)⇒ **不填**,并在文档写明「可推算但命中率 x%,语义存疑」。推算是选项,不是默认。

## 5. 空值语义以客户模板自身为 oracle
对方给的模板同时是**格式标准**和**口径标准**:
- 模板某列本行大多为空 ⇒ **留空就是正确口径**,别用 0「补满」。
- 模板某列几乎全 0 ⇒ 才全量记 0。
- 模板有值而本地库覆盖率低(例模板 138/393 有值、本地 3.7%)⇒ 那是**两套实例的运营差异**(不同部署、不同运营期),不是映射错,写清楚即可。

## 6. 同族稀疏字段取并集榨干再下结论
同一语义常有多个候选列(如上级链 `ParentIds` + `ParentID` + `SourceParentID` + `Parent2ID` + `Parent3ID`)。并集后哪怕只多出几个会员也是真值:先榨完再报,否则“还能不能多一个”会被反复追问。
- **跨通道也要取并集**:「某字段能不能拿全」按通道分别核算(手机号 / 微信 / 邮箱 / 二维码各一路),
  再给**并集覆盖率**与「仅X无Y」增量;单一通道的缺口**不代表**该角色不可触达(实测手机号 46% → 合并后 99.7%)。
  口径、算法与产物形状见 `references/contact-field-physical-limit.md` 铁律八~十三。

## 7. 客户丢来「片段/模式」(如 `987——267`)要定位记录时
口径模糊时别凭直觉挑一列开扫;按序穷举 + **随机基线**判真假(四步一次跑完: `scripts/frag_lookup.py`)。
1. **先打死字面形态**:逐格统计 `\d+[-–—]{1,6}\d+` 并按列汇总。命中只落在时间列(`2025-12-19 11:41:00`)和账号列(`vp0_1787511842710`)⇒ 客户写的横杠是**书写占位符**、不是表内真值:别 grep 它,也别去解 xlsx 的 sharedStrings 找。
2. **目标列内「去非数字后按序含两端」**:`d=re.sub(r'\D','',str(v))`;`a in d and b in d and d.index(a)<d.index(b)` ⇒ 硬结论(有/没有)。
3. 再补两遍只为覆盖误判:**同一行任意列**同时含两端、**同一格不限顺序**。
4. **必做随机基线**:同规模随机三数字片段对在同一行内共现的行数,在宽表里**中位数就有十几行**(行号/id/手机/IP/金额/时间 全带数字)⇒ 零散 1~2 个命中是噪声、不许当结果上报;要报只报明显高于基线的命中。
5. 全 0 时交两个可执行口径,而不是继续猜:① 让对方把原始片段/那一屏截图发来(若是控制台掩码,再按前 3 后 3 穷举,含去前导 0、+55 国码等变体);② 若那串数字其实是行号 → 按区间(如 267–987)把整段全列导出回传。
6. 对方口述的位置常与表内『行号』列**差 ±1**:Excel 表行号含表头、筛选视图显示的是显示序号、他手上可能是上一版快照。对不上先按 ±1/±2 对齐(如 986/268 ↔ 987/267)再判死,别急着回「没有」。
7. 措辞把「匹配不到」与「源侧没落库」分开写(例:手机列源表本就只填 60.9%,34,032/55,920)⇒ 缺口是数据不存在,不是检索失败。

## 7b. 本地/导出侧扫空后,对方说「直接去库里找」⇒ 转 DB 侧穷举(一次做对)
- **库清单必须现查**:`select name from sys.databases where state_desc='ONLINE'`。**别用会话里记下的「那 N 个库」硬编码清单**——同实例常有额外业务库(实测 10→15),漏库的「不存在」结论无效。
- **列清单要含视图**:`sys.tables`/`sys.partitions` **看不到 view**,而绑定号常只存在于视图(`View_Index.bindphone` 这类)。列字段集用 `information_schema.columns`(它覆盖 view)。
- **行数先过滤**:先 `sys.partitions` 取行数 → 0 行直接跳;表名带 `_YYYYMMDD` 的日切片/日志分片族(单库可达数千张)默认整族跳过,否则 LIKE 扫到 timeout 也扫不完。
- **形态先抽样**:每列先 `select top 5`。**整列是字面 `'0'`/空 = 死列**(实测一列 232,364 行全是 `'0'`),对它跑 LIKE 纯浪费。
- **拼法一次给全**:同一目标值覆盖 `X` / `0X` / `国码X`(55/91/63/86/62…) / `+国码X`,以及「前 3 + 后 3」的 `%A%B%`(不限序位)和精确 `A????B`;9 位纯数字还要当 **ID/邀请码** 把主键列再扫一遍。
- **强制 collate**:`cast(col as nvarchar(400)) collate Latin1_General_CI_AS like '%…%'`。列是数值类型或源表 collation 不同时会**静默零命中**,这是最大的假阴性来源。
- **命中先复核列名**:审计/签名/日志表里的 `%987%267%` 命中多是 `sign`/`pwd`/token 里 md5 的随机数字 ⇒ 报「找到」前先确认命中列不是哈希/签名。**噪声当成果上报会毁掉整份结论。**
- **号码显示口径**:包网/白标盘会把各国号码硬套一个国码显示(实测全菲号显示成 `+55`)⇒ 前端/导出里的 `+55` **不是国别判据**,不能据此把搜索缩窄。
- **SQL 小坑**:词序是 `select distinct top N …`;写成 `select top N distinct …` 直接语法报错,白费一轮。
- 闭合交付 = ①命中清单**全量列出**让对方认领;②未命中证据(扫了哪些库、哪些列、各多少行、用了哪些模式);③**一个坐标问题**(「你在哪个界面看到这个值」「它是否可能是 9 位 ID」)。**没有新维度就不要重跑同一维度**,也**不许把「没找到」写成熟练的「找到了」**。

## 8. 结论落表 + 给取数路径
- 逐列一行:「试过的源(带实测数字) → 实测结果 → 结论」,每个源写清表名和命中数,方便对方复核。
- 最后给可补数据的路径并标明代价:① 同族另一实例的数据表(通常唯一真能补齐的路);② 平台后台列表页/接口(其 SQL 读的就是同一批表,**不会更多**);③ 服务端 inner server/微服务(需看是否有落库,protobuf 接口常一行没落)。

## 坑
- **普查脚本绝不要打印整列样例**:5 万行的 `InviteCode` 全量样例一次吐 70 万+ 字符把工具输出冲爆。样例每列 ≤5 条、值切片 ≤26 字符。
- 重名列(模板里两列同名如 `父级ID`)按**列位置**计数/取数,按列名会冲突。
- “无记录”和“记录为 0”语义不同:交付文档里分开标明(例:5 列显示 100% 是“无记录记 0”填充,真实有记录 34,402/55,920 = 61.5%)。
- 稀疏归因列不要当成 bug 去“修”:会员注册不走绑定码时关系表本身就是空的,定性为“数据不存在”并给出证据即可。
- **别把工具输出里的打码当成数据里的掩码**:有些值打印出来是 `+926****2513`,落盘的却是完整号(`+9265762513`)——打码发生在输出管道、不在数据里。判定:同一值 `'*' in v` 为假 + 长度/位数吻合 + 无非 ASCII 字符 ⇒ 没被脱敏,照常扫即可;误判成掩码会围着「掩码还原」白开一条线。
- 大表(10MB 级 xlsx)先落一份 `(hdr, rows)` pickle 缓存复用,扫描脚本写成 `.py` 文件跑(超长内联命令易被截断/审批拦截);每次只打**聚合数字 + ≤5 条样例**,整列样例会把工具输出冲爆、结论一起丢。
- **扫库脚本串行跑,不要与交互查询并发**:数千张表的 LIKE 扫会把库连接/隧道顶满,后起的单条查询会静默挂住(表现:进程在、日志 0 字节)。判断「卡住」先看有没有大扫在跑,别急着改脚本逻辑。

- **作键的字段先验语义**:对账/差集用的键可能不是你以为的那个字段——同一对象里常同时存在「登录账号 / 注册人姓名 / 企业简称 / 企业全称」四个近义字段(名字看着都像「单位」)⇒ **先打印一条样例的键值再算差集**;拿错字段会得到 100% 错位的假差集(表现:「两边完全无交集」),据此下结论全错。
- **跨产物对账还要验「键的形状」,不止验字段名**:两个文件常用**不同粒度的键** —— 实测一方以对象「编号」为键,
  另一方每行另带一个 UUID 主键与一个 `code` 字段 ⇒ 脚本拿 UUID 去 join,打出「未登记 20 条」,
  看起来像**闸门泄漏**(安全结论!)。⇒ 对账脚本先打**两侧各一条样例键**(键名 + 值)确认值域同源;
  凡出现「像漏洞 / 像泄漏 / 像吃单」的计数,先把这个数字**追到它实际读的那个字段**,再写进任何结论。
- **列位置不能凭印象**:导出里同名列很多(企业全称 / 企业简称 / 联系人),按「第 2 列」取会整列错位。
  取列前先打印**表头数组**并按名字定位下标(`hdr.index('企业全称')`),不要硬编码序号。
- **容器结构先探形再聚合**:票/凭据文件常是 `{"jwt":{…},"st32":{…}}` 这类「种类 → 子字典」两层结构,
  顶层键是**种类名、不是实体**;直接 `for k in d` 会把「2 个顶层键」当成「2 个账号」并算出全错的对账。
  ⇒ 任何聚合前先打印 `type(d)` + `list(d)[:3]` + 一条样例值,再决定遍历哪一层。
- **源值为空串 ≠ 无记录**:合并/回填逻辑只在源值为真值时覆盖(`null` 与 `""` 都不覆盖)是**正确设计**,不是取数 bug。判定「这个字段能不能补」必须读**源记录原值**并把 `null` 与 `""` 分开打印——两者对结论不同(前者=源侧无此企业,只能引新源;后者=源侧就是空值,改代码无解)。
- **「数对不上」先验算口径闭环再动代码**:客户给的多个数字常是不同口径(名单数 / 采集键数 / 表格去重行数),先写三个等式(名单=命中+待补、采集=命中+外部、表格=命中+待补+外部)并加行数反推(每对象行数 × 对象数);三式全通即说明没丢数据,只需改呈现或过滤分类行。

## 支撑文件
- `references/contact-field-physical-limit.md` — 联系方式类字段的缺口核验铁律(词命中加严校验 / 扫原始全量 JSON / 开关型字段判读 / 越权前先验响应身份 / **宣布缺口前先做承载端点反查**)。
- `scripts/gap_probe.py` — 三件套可执行探针:`headers`(全库表头扫描) / `census`(单表逐列非空普查) / `overlap`(两表值域交叉证伪)。
  用法:`python gap_probe.py census <dump_dir> <DB.Table>`;dump_dir 下为 `<DB>.<Table>.tsv`,首行表头、\t 分隔、utf-8-sig。
- `scripts/frag_lookup.py` — 片段定位探针:客户丢来 `987——267` 这类带空缺占位的片段时,一次跑完「字面形态逐列汇总 / 列内去非数字按序含两端 / 同行任意列与同格共现 / 随机基线」四步,只打聚合数字与 ≤5 条样例。用法见第 7 节。
- `scripts/db_value_sweep.py` — **MSSQL 值穷举探针(第 7b 节)**:枚举实例全部在线库 → 抽号码/标识类列(名字正则,含视图)→ `sys.partitions` 行数过滤(跳 0 行与 `_YYYYMMDD` 日切片)→ 逐列 `top 3` 抽样识别死列 → 多模式 + 强制 collate 搜索,命中同时打印列名与值以便识别哈希噪声。用法:`python db_value_sweep.py --host 127.0.0.1 --port 11433 --user u --pass p --a 987 --b 267`。
