# 工装拒拆时：手工拆 + 外移到新模块

AST 工装只能切**顶层语句边界**。下列条目它必须拒拆，只能手工做：单条语句自身超过段上限、
段内 `return` 跨多行、拆出的段自身仍 >上限、带装饰器的函数、类内没有 `self/cls` 的方法、整函数只有一条顶层语句。

## 手工拆的两条硬约束
1. **不许把主文件撑大**：棘轮对**文件**行数同样只看「新增/变大」⇒ 在贴着上限的文件里就地加 helper
   （每个 `def` 行 + 空行 ≈ +3 行）会把文件顶穿，等于拿一条新违规换一条旧违规。
2. **调用点不许改**：调用方遍布全树时，改调用点 = 引入看不见的回归。

## 配方：方法体原样搬进新模块（首参仍叫 `self`）
- 新建**只依赖标准库**的兄弟模块，把长方法里的各小节整体搬进去，**首参仍命名为 `self`** ——
  它**就是**原方法的 self，于是函数体除整体反缩进 4 空格外**一个字都不用改**（`self.pool` / `self.raw` 照旧可用）。
- 原文件只留调度：前置守卫 + 每小节一行调用 + 原有的落盘/日志/return。
- 小节顺序 = 执行顺序，不可调换；有返回值的按 `x = f(self, …)` / `a, b, c = f(self, …)` 接回。
- 通用的无状态助手（`log` / `read_json` / `write_json` / `_d` / `_int` 这类）**另起一个 `util` 模块**，
  原文件用 `from <pkg>.util import …` 引回 ⇒ 其余模块里的 `from <原模块> import log` 照旧有效（名字仍在原命名空间）。
- 原模块保留 re-export（`from <pkg>.<新模块> import <节名>, …`），对外函数名/签名不变。

## 为什么新模块必须只依赖标准库
`原模块 ⇄ 新模块` 互相 import 时，原模块先被导入、在**定义那些助手之前**就执行到
`from <新模块> import …` ⇒ 新模块回读原模块拿到**半初始化的模块对象** ⇒ `ImportError` / `AttributeError`。
把助手下沉到 stdlib-only 的 `util` 模块、两边都从它 import，就根本不成环。

## 宿主也需要 parts 里的 helper：`bind()` 注入（反向依赖也不成环）

上面那条「parts 只依赖标准库」在 **parts 必须调用宿主函数**时不成立（宿主函数用的是宿主的模块常量、
连接池、路径根，抄一份就分叉）。此时**不要互相 import，改成注入**：

- 宿主 import 段：`import _x_parts as _P`；宿主文件末（所有 `def` 之后、`if __name__ == "__main__":` 之前）：
  `_P.bind(sys.modules[__name__])`。⇒ 必须用 `sys.modules[__name__]`，**不要**写 `import _x` 或
  `sys.modules.get("_x")`：脚本模式下模块名是 `__main__`，这两种写法会把整个文件**再执行一遍**成第二个模块对象。
- parts 侧：模块级占位 `fill_entry = None`（绑定审计看得见它「有绑定」）+ `def bind(mod): global fill_entry; fill_entry = mod.fill_entry`。
  这样 parts 里的调用点保持**原文**（`fill_entry(ev, pm)`），不必逐处改写成 `mod.fill_entry(...)` ⇒ 机械对账的缺口最小。
- `bind` 捕获的是**函数对象**（绑定那一刻的快照）⇒ 冒烟里 `mod.scan = stub` 之后必须**再 `bind(mod)` 一次**，
  否则 parts 内部仍调原函数（症状：桩像没生效、真函数被跑）。
- 宿主瘦身方向：新拆出的 helper 全进 `<name>_parts`，宿主只剩 import + `main` ⇒ 文件行数从
  「head + 全部 helper」降到「head + main」，行数上限才过得去；`main` 里逐行写 `_P.<helper>(…)` 即可。

## 验尸与验收
- 手工拆完逐级验：`py_compile` → **该树自测桩** → 最终**全量门禁**（结构闸 + 全部桩）。
- 工装尝试留下的 `TypeError: 'NoneType' object is not iterable` 一类症状，先按 `state-passing-model.md`
  的三类静默破坏排查，再决定「修工装」还是「手工」—— **能修就修（修完整树重拆）**，不要用手工拆去掩盖工装缺陷。

## 安全装配纪律（手工拆 = 自己在内存里拼新源码，落盘前过四关）

1. **自检前置，且用 `compile()`**：`compile(cand, path, "exec")` 过得了才落盘（同目录 tmp + `os.replace`）；
   不过就把候选另存 `<file>.cand` 后退出，**一个字节都不写**。顺序反了（先改源、后自检）＝自检失败也留残骸：
   半条语句被删、装饰器悬空，比不动更糟，还得从备份复位。
   `ast.parse` 挡不住「`continue` 不在循环里」「`return` 在函数外」—— 它不做 symtable 检查，必须 `compile()`。
2. **控制流改写白名单 + 「原文一行不丢」机械证明**：块搬进新函数后，循环出口语句（`continue`/`break`）失效，
   只能改写成 `return <默认值>`；计数语句也要改成 `return 1` 交回调用方。把这些**有意改写逐条列成白名单**，
   再机械对账 `Counter(原文去空行strip) ⊆ Counter(新文) + 白名单`，差额非空即拒写盘。
   一条 `compile()` 只报第一处失效的 `continue`，白名单对账才能一次抓全。
3. **反缩进按「层差」精确算**：数出块在原文的嵌套层数、目标函数体层数，逐层 4 格地减 —— 是数出来的，不是感觉出来的。
   拿不准就先把候选写到 `.cand` 用 `compile()` 验，再回填正式文件。
4. **巨型字面量语句按条目边界切片**：合并壳 `{**a, **b, **c}` 依赖「同键后者覆盖」，
   所以**合并壳里各片顺序必须与原文一致**（否则键的迭代序变了，依赖顺序的派发/前缀匹配会错）。
   拆完对账 **key 集合**：`set(原文键) == set(合并后键)`、条数相等、无改名 —— 行数对不上不是证据，键集合才是。

## 配额与对账
- **零件模块的配额要留接线余量**：搬运器每搬一个方法多写 ~2 行（别名 import、类体别名赋值/dunder 双写），
  按「方法数 × 上限」切出来的模块会超限 ⇒ 配额留 ~20% 余量，并加「零件模块自身超限即拒收并只回滚本批」守卫。
- **行数增量对不上就 diff 拆前备份**，别推理：差额可能来自工装行为，也可能来自被截断/压缩后误读的输出。
- **批量驱动的失败判因用确定性逐名判定**，不用二分探针（同参数两次 `rc` 不一致 ⇒ 报空坏名集，把真因盖住）；
  失败处理 = 「只回滚本批 + 打印完整错误」，不要整文件回滚。
