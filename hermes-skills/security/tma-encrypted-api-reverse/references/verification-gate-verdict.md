# 验证闸门判决方法学（受控三态实验矩阵）

**用途**：面对「开包/领奖/下单」等**多段验证码 + 会话态**的闸门，判定「服务端是否强制完成全部验证」。

## 铁律：绝不用「部分日志」推断绕过

**症状**：某账号意外到账，而其会话日志只见到 1/N 段 `verify` 通过 ⇒ 极容易误判为「部分验证即放行」的绕过缺陷。
**为什么错**：日志会被下一轮覆盖（`run.log` 常被 `rm -f` 重建）⇒ 「只见到 1 段」只说明**你读日志的时刻**落后于链路实际进度，不说明链路停在那里。时间戳能自证：到账时刻若落在 `open` 后的 TTL 内（而非超时后），则**只可能**是合法的完整验证 claim。
**正确做法**：造**受控三态矩阵**，同一出口、同一脚本、同一次运行内对照。

## 三态矩阵（必做）

| # | 已验证段 | claim 时机 | 期望读法 |
|---|---|---|---|
| ① | 全段 `completed=True` | 紧接末段 | `200 + amount` = 正常通道（**阳性对照，必须先跑**）|
| ② | **1/N 段** | `open` 后 5~10 s（**远在 TTL 内**）| 若 `400 + 「请先完成验证」` ⇒ **闸门健全**；若 `200 + amount` ⇒ **真绕过** |
| ③ | **0 段** | 紧接 `open` | 同上 |
| ④ | 任意 | `open` 后 > TTL | `「会话已失效」` ⇒ 该码**与验证无关**，勿混入结论 |

**要点**：② 必须在 TTL 内触发，否则会与 ④ 混淆（本库实战：`40705 会话已失效` 常被误读成验证失败）。TTL 需实测，本项目 TMA 为 60~73 s，`initData` 为 ~12 min。

## 如何在脚本里造「只过前 k 段」

给远端模板加**判据开关**（不要改判据本身），经既有 JSON 注入通道传参，**并在发往服务端前 `pop` 掉**，避免污染报文：

```python
_fs_from = ob.pop("_force_skip_from", None)      # 第 n 段起强制跳过
if idx is not None and not (_fs or (_fs_from is not None and i >= _fs_from)):
    val = str(idx)                                 # 正常用求解器结果
# 否则 val 留 None ⇒ 落回「等人工答案」分支 ⇒ 推 <i> SKIP 即触发 break
```

**坑**：强制跳过会让求解器结果失效、模板落入「等答案文件」分支，必须**同时**补推 `SKIP`，否则会静默空等满 `WAIT_S` 才超时（表现为「没有任何 claim 相位」，极易误读成实验没跑）。

## 结论措辞模板

- 0 段与 1 段均被拒 ⇒ 「**验证绕过不成立（正面结论）**；闸门强度 = 验证码强度」。
- 全自动求解 3/3 且到账 ⇒ 唯一真实风险 = **可脚本化抢包**（前提：持有 token），建议「提高验证码强度 / 会话内提交风控 / `claim` 绑定领取者身份 / token 一次性短时效」。
- 任何自纠结论**必须留痕归档**（「已证伪假设」单列一节），避免后人引用旧推断。

## 载体/前缀词典（Telegram Mini App 常见分词法）

同一 base64 载荷按**前缀**分语义，前缀猜错会得到「无效链接」类错误码（本项目 `40671`）：

| 前缀 | 语义 |
|---|---|
| 裸 24 字符 | 包/对象 token（`detail`/`open` 请求体）|
| `rp_` | 发送（inline query / 卡片）|
| `rpu_` | **解锁**（发包人）|
| `rpl_` | 列表 |
| `startapp=<裸>` | MiniApp 深链 |

**做法**：先在**只读** dump 里枚举卡片全部按钮（含 `data`/URL），**照抄**其 `start_param` 前缀，不要凭语义猜。

补充（同一产品实测新增）：`/transfer <32 字符 base64url>` = **支付命令**（消息层命令，非回调）；`?start=recv_<24 hex>` = **收款深链**。一个产品可能同时有「发送/解锁/收款/支付」四套前缀，而**都是同一份随机载荷的不同封装**。

# 判「能不能脱离 Telegram 调用」——入口地图四步取证

用户问「只能从 bot 调吗」时不要凭架构推断，四步拿硬证：

1. **爬页面**：`/`、`/rp/detail`、`/mch`、`/console`、`/robots.txt`、`/asset-manifest.json` 各发 GET。全部回同一份小 HTML（实测 728 B）= SPA fallback；`/assets/` 应回 403；`/console` 可能另有诱饵页（其体积会随版本变化，实测 2,276 → 5,882 B）。
2. **抓 bundle**：从该 HTML 提 `<script src="/assets/index-<hash>.js">` 直接下载（实测 740 KB 可整下）。`.js.map` 多数回落 404/SPA ⇒ 无 sourcemap，只能做 minified 分析。
3. **定词表**：在 bundle 里正则抽 `/(?:api|app-api)/...` 得 API 前缀，再抽全部 `` `${Rr}/xxx` `` 调用点 ⇒ **调用点集合应与黑盒 oracle 命中集合 1:1 对应**（本目标两侧均为 5 条）——这是最强的双向印证，也是"路由面穷尽"的独立证据。
4. **判面分裂**：抽中文文案 `[\u4e00-\u9fa5]{2,12}` 做 Counter，再数资金类词（提币/提现/转账/充值/收款/闪兑/余额宝/星币 + withdraw/recharge/balance/swap）命中数。**全 0 ⇒ 前端不承载资金功能** ⇒ 资金逻辑只在 bot 服务端状态机 ⇒ 不存在可伪造的客户端资金 API（这是产品唯一的架构级防护）。

## 判据分级：别把「连上了」当成「能用了」

- 页面 GET 200 ≠ 可调用：它自己引 `telegram-web-app.js`，真数据接口还要 `X-Telegram-Init-Data`。
- API 被 curl 打到 401/`40701` = **端点存在**，别报「未授权访问」。
- 无 initData ⇒ 401；伪 initData ⇒ 签名失败；复用旧 initData ⇒ `40704`；过期 ⇒ `expires_in=900`。**四件都测过才能说"身份不可绕"。**
- 前端读载体常见回落链 `initDataUnsafe.start_param → ?startapp= → ?token=` ⇒ 「URL 直接打开」是**设计支持**，不是配置失误，别写成漏洞。

## 顺手产物

bundle 里能直接读到协议常量与开关：HKDF salt、请求头名（`X-Session-Id`/`X-Timestamp`/`X-Nonce`/`X-Signature`）、`apiBaseURL`、`isDev/isProd`、`antiDebugEnabled`、`devInitData` ⇒ 把"猜测的协议"升级成"引代码的协议"；`antiDebugEnabled:true` 是值得另开一项实测的新情报。
