## bot 侧(= "Web 之外的管理端")实测手法
- ★ **`/start <param>` 命名空间枚举**:逐前缀发 `/start <prefix><32hex>`,**判别式 = 响应是否非主菜单**(未知前缀一律静默回落主菜单 ⇒ 不是错误页)。实测活前缀极少(某站仅 `recv_` 收款、`rpl_` 红包解锁)⇒ **20 个前缀跑一轮即可断言「无 admin/merchant/panel 深链」**,零成本关闭该面。
- ★ **bot 与 API 是两条独立授权面,不可互相当证据**:同一解锁 token,API 回 `40671 解锁链接无效`,而 bot `/start rpl_<token>` **无需 initData** 完整渲染包详情(中奖名单 + 金额 + `tg://user?id=`)。⇒ ① **用 bot 路径复核 token 活性**,别拿 API 的拒绝码断定「对象无效/包已死」(极易造成假阴性误判);② 该渲染面本身即**隐私泄露**(任何泄露 token 都能读到全名单)。
- ★ **零资金读「收款/支付」协议**:走 bot「收款 → 任意金额」(金额由付款方填写)可在**不提交任何金额**下拿到 `/transfer <base64(hex id)>` 与 `t.me/<bot>?start=recv_<hex>` 协议、编码规律(base64(hex))与有效期语义;并据此判定该币种通道**是否暴露第三方支付网关域名**(判定新资产线)。
- ★ **建群/加群类打法先做账号预检**:先用 `@SpamBot` 发 `/start` 查账号状态。被 `spamreported` 的账号**禁建群/禁加群/禁给非联系人发消息**,但**回话与驱动 bot 仍正常** ⇒ 群模式(群主后台)路线整条不可达,别浪费在 `CreateChannelRequest` 报错上。
- ★ **找运营方运营群的正规入口 = `GetFullChannelRequest` 的 `linked_chat_id`**:一次拿 about/participants/linked_chat_id/pinned;`admins` 枚举常被拒(`Chat admin privileges are required`)⇒ 拿不到运营账号时别硬耗。
- ★ **管理端的闸门必须拿「实测原文」,不凭文案推断**:自助入口实测路径 `商户 → 创建商户 → 输入商户名称`,提交后回 **「⚠️ 钱包余额不足，暂无法自助开通商户。」** ⇒ 闸门 = **钱包余额**(非先前猜测的 `≥1 USDT`/支付密码)。探法:提交 **1 个无害可识别名称串**看响应,**资金类词一律不点**;响应一含 费率/押金/确认/开通 即停手 dump。**被拒 = 零残留**,但仍须:回读确认未建 + **删掉那条测试消息** + 按「取消」退出表单复位(用户偏好恢复原状)。
- ★ **bot 控制台 = 管理端常见形态,但闸门是资金/PIN**:`商户`/`安全设置`/`备用账户` 等菜单**可达且规格可读**,而**创建/绑定动作一律被「余额不足」或「🔒 需要支付密码」拦下** ⇒ 这类 fail-open 假设必须**实测证伪后才写报告**,不能凭文案推断。
