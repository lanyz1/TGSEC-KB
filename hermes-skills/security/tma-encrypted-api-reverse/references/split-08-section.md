## 收尾
路由测绘用错误码判别式(未授权码=路由存在,404=不存在),把「只有一个前缀、只有 N 个接口」**证明成闭环**。
- ★★ **AES-GCM 响应体禁止用 md5 判定同异**:密文带随机 IV,**同一明文每次 md5 都不同**(实测 `/rp/detail` 六个变体 md5 全不一样、解密后明文完全相同)⇒ **必须先解密再比明文**,否则会把「同一个拒绝」误读成「六种不同行为」,进而编造出不存在的差异。
- ★★ **已鉴权路由测绘(拿到 session 后才做得了的那一面)**:用**有效会话**扫候选路径(业务语义词 + 同族管理端路由双份词表),**判别式 = 非 Go-404**(真实业务路由会回业务错误码如 `40671`,天然充当阳性对照)。实测某站 app base **仅 4 条真实路由**(`POST handshake`、`GET rp/detail`、`POST rp/claim`、`POST rp/open`)⇒ **带合法会话仍扫不出 admin/merchant/banker/console ⇒ 这是对「公网无管理端」的最强证伪**(比未鉴权视角硬得多),管理端只可能在**另一下载面**:bot 侧菜单(闸门=余额/PIN/PIN 前置)或需自有群(群主后台)。
- ★ **只读纪律下也能做资金面侦察**:先只调 `handshake` + `GET` 类端点;`open/claim` 等写入端点**留待有明确授权后**再动,report 里标明「未开发面」而非省略。
- ★ **前端 bundle 是 API 面的穷尽证据**:数 bundle 里发起请求的函数(每个 `get/post(\`${base}/x\`)` 算一个),**函数个数 = 真实端点数**。看到 5 个函数即可断言「无 config/pay/user 未发现端点」,不必盲扫万级探针。
- ★★ **bundle 字面量提取必须纳入反引号模板串**:只抓 `"`/`'` 会把结论做废(实测同一 bundle:仅 `"`/`'` = **137 条**;纳入反引号 = **5,354 条 / 唯一 2,236**,该 bundle 的路由与文案**全在反引号里**)⇒ 「无管理端 chunk」曾被误降级为不可判定,根因即此。**提取后先跑正控**(搜必然存在的 `handshake`/`rp/detail`/`X-Signature`),正控命中才允许下「无 X」的否定结论。
- ★ **客户端 config 对象是白送的线上事实**:`{encryptionEnabled,requestSigningEnabled,antiDebugEnabled,apiBaseURL}` 常以明文对象出现 ⇒ `apiBaseURL:""` = **同源单基址**,`antiDebugEnabled:true` = SPA 自带反调试;指纹库名(`ThumbMarkJS`)也能一眼读出 ⇒ **别猜「FingerprintJS Pro」之类,读出来**。
- ★ **兄弟 API 基址要在【已鉴权】视角再扫一遍**:未鉴权时非注册基址全 404、无区分度;带合法会话扫 `26 基址 × 7 叶子 = 182 探针`,**non_404 = 0** 才可断言「管理端不在别的 base」(实测第 11 次归零)。
- ★ **可用账号先做存活预检,别把号库当富矿**:farm 号库实测 **14 个全为死号**(`get_me() is None`)⇒ 建群/群主后台整条路线不可达。先 `get_me()` 筛一轮再谈 `CreateChannelRequest`;存活率与「号库里有会话文件」无关。
- ★ **子域 / Mini App 短名 oracle 要打两轮**:首轮泛枚举 0 命中后,用**业务语义词**(merchant / agent / panel / console / ops / daili)跑第二轮;两轮全空才可断言「只有这一个 App / 主机名」。
- ★ **DNS 结论必须带通配检测**:随机 12 位子域 `NXDOMAIN` 才证明无通配记录、爆破结果有效;否则「只解析出 N 个名」是假结论。
- ★ **纯蜜罐主机判别式**:某主机**只有一条非 404 路由**、响应体仅客户端 IP(或空)⇒ 整机诱饵(如商户域名 `mch.*`),立即停止投入。
