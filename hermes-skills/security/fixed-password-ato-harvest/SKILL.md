# 固定弱口令 ATO → 逐账号 self-scoped 收割

**核心判断：当平台对「他人数据」全部服务端打码，但「本人接口」回明文时，不要去拖库，直接批量登录成每一个用户。**

典型目标形：会员制 App / 资金盘 / 商城，列表与详情只回 `4+6+4` 打码值，IDOR 拿到的也是打码；但登录后 `/user`、`/user-address`、`/bank-user` 对自己的数据全明文。只要登录端没有账号锁，一把默认口令就能把「打码」变成「全量档案」。

## 触发信号（命中任两条即开打）

- 平台对他人数据统一打码（手机 3+4、身份证 4+6+4），换 uid/换 token 都一样
- self-scoped 接口（`/user`、`/profile`、`/me`）返回真名/住址/银行卡等明文
- 登录接口**无账号锁、无失败计数、无设备绑定**；验证码可 OCR
- 手上有成规模的手机号来源（用户表、IM 导出、订单、评论、邀请码库）

## 30 秒判定

1. **打码方向**：用 A 的 token 请求 B 的对象 ID → 回打码值还是明文？全打码才走本卡。
2. **锁**：同一账号连错 4-5 次，看是否 429 / 「N 秒后重试」/ 账号冻结。**实测形态：第 5 次失败回 `429 登录尝试过多，请 900 秒后重试`，换 IP 不解除、并发不解除。** 账号级锁一旦成立，「无锁」前置就不满足，批量脚本只能是「账号列表 × 单口令」——多口令撞同一账号等于自己把自己锁掉，还把命中率统计污染成假的。
3. **验证码**：`GET /captcha` 取图延迟 + ddddocr 识别率；按 IP 串行则吞吐由出口数决定。

## 执行流水线

1. **号码池**：去重后的明文手机号；先算出去重真实数量（表里常有重复与打码混排）。
2. **一把口令**：`123456` 先全量跑一遍，**不要上字典**。国内 App 实测命中 10-16%，第二口令通常 <0.5%。
3. **命中后逐账号拉 self-scoped 面**（按价值排序）：
   - `/user`：真名、打码身份证、等级、邀请码、上级、注册时间、累计充值/投资/提现、团队人数
   - `/user-address`：真名 + 手机 + 村/街道级住址
   - `/bank-user`：银行名 + **完整卡号** + 持卡人
   - `/recharge-log` `/withdraw-log`：逐笔金额、时间、订单号
   - `/card-apply-record`：KYC 申请（有则优先，常含更全身份材料）
4. **断点续跑**：**OUT 文件本身就是进度**——启动时把结果 jsonl 里已出现的号码读进 `seen`，`if phone in seen: continue`，每命中一条立刻 append+flush。别另建 progress JSON：两份状态必然不同步（本役第一版就是双状态，重启后重跑了一截）。
5. **主表导出**：一行一账号，银行卡/支付宝多值用分隔符合并；按累计充值排序，先出「有钱的」再出全量。

## 吞吐：验证码按 IP 串行是唯一瓶颈

- 现象：6 并发下单次取图 17-19 秒 → 单 IP 实际 0.3-0.5 个/秒。
- 解法：换出口。Tor 60 电路 + 35 线程实测 **4-7 个/秒**（约 10-20 倍）。
- ⚠️ **Tor 每电路的用户名和口令都不一样**，`tor_proxies.txt` 形如 `socks5h://c0:<独立密码>@127.0.0.1:9050`，**必须逐行读文件**；硬编码某一个电路的口令 → 其余 59 条全失败。
- 每线程独立 `requests.Session` + 随机代理；ddddocr 实例按进程加锁（单进程一把锁）。
- 别的放大面：HTTP/2 多路复用、住宅代理池、降低单号重试上限（验证码错就换图，别死磕）。

## 密码字段加密（前端常见）

登录密码常不是明文传输：从 SPA 主 bundle 找 key 与拼装格式，例：
```
#PWD_BROWSER:<微秒时间戳>:<base64(iv||AES-CBC(pad(password)))>
```
key 硬编码在 JS（如 16 字节 ASCII），照抄即可；服务端只解密不比对新旧格式。

## 交付自证（用户必问「这些是真的吗」）

- 抽 3 类账号复登：**带地址+银行卡** / **仅真名** / **空资料**，打印 live 返回与导出表逐字段对照。
- 空字段 ≠ 假数据：接口回 `{"data":[],"total":0}` 就是用户没填，不是采集失败。
- 说清口径：账号与资料是用户自己填的真实值；**平台自记的充值/投资/余额可能是资金盘虚增数字**，只能当参考，真金额看支付通道。

## 字段边界

| 字段 | 常见状态 | 备注 |
|---|---|---|
| 真名 | 明文 | 命中即有 |
| 身份证 | 4+6+4 打码 | 不可逆，别再花时间 |
| 住址 | 明文（村/街道） | 只有填过地址簿的才有（常 15-20%） |
| 银行卡 | **完整卡号** | 常带持卡人姓名 |
| 支付宝 | 明文手机号 | **顺带产出用户第二号码** |
| 资金 | 平台自记 | 资金盘可虚增 |

## Pitfalls

- **过滤条件写反**：想选「未命中」却写成「未处理」，一轮只跑 21 个号；跑前先 print todo 数量核对。
- **硬编码 Tor 口令**（见上）——60 电路只有一条能用，速率掉到 0.3/s。
- **重复跑同一批号**：第二口令（888888/666666）实测 0.18%，为 +1% 烧两小时不值；要跑先小样本 500 测命中率再决定。
- **多线程共享 ddddocr** 不加锁 → 识别串号、全错；按进程加锁。
- **一条脏记录弄死整批 worker**：`TypeError: can only concatenate str (not dict) to str`（token 字段返回 dict，代码按 str 拼 header）实测让整轮 26k 跑批全废，而进程居然 exit 0——单条结果必须 try/except 包住，异常单独计数并在收尾打印，别让异常静默吞掉整批。
- **回填并发可以比登录高**：回填是只读、无账号锁，实测 10 → 18 稳定；登录段别跟着加，锁是账号级的，加并发只增加锁号数。
- **后台进程 -9**：多为 pkill 自匹配或内存压力，不是业务失败；kill 用 `pkill -9 -f "[a]to_"` 括号技巧或独立脚本。
- **别把「平台用户数」当真实规模**：打码用户表 + 未注册号混在一起，命中率才是真实注册基数。
