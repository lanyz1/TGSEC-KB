# 验证码 / 人机闸门分诊:先判能不能免浏览器打穿

拿到一个带验证码的登录/注册面时,**第一动作不是起浏览器滑滑块**,而是取一次验证码初始化响应,
判服务端是「在线校验」还是「离线/降级校验」。有些站点走离线校验,一个 md5 就过,
省掉整条有头浏览器 + 轨迹拟合的路线。

## 1. 先取初始化响应(必须带 Referer)

```bash
curl -sk 'https://<目标>/<captcha-act>' \
  -H 'Referer: https://<目标>/<登录页>' \
  -H 'X-Requested-With: XMLHttpRequest'
```

- **不带 Referer 的 403 / 恒定报错不是「本站没有验证码」**,是闸门本身。判死端点前先补 Referer 重测一次。
- 回包通常含 `success` / `gt` / `challenge` / `new_captcha`。

## 1.5 ★ 先判「墙」的类型:验证码墙 vs 邮箱后缀白名单墙(打法完全不同)

| 墙 | 判据 | 打法 |
|---|---|---|
| 验证码/人机墙 | 登录/注册前有 captcha 初始化响应 | §2–§4 破码,或换 OAuth/OTP 路径 |
| **邮箱后缀白名单墙** | 公开设置/注册页出现域列表(`registration_email_suffix_whitelist`、「允许的邮箱域名」类) | **破码毫无意义**:码过了照样被后缀拒 ⇒ 走下面 |

**邮箱后缀白名单墙五步:**
1. **产品开源就直接读 policy 源码,数校验函数的调用点** —— 调用点数量 = 被保护的路径数;顺带确认 OAuth 注册路径是否同过这堵墙(同过 = 无 OAuth 旁路)。
2. **第三方登录开关用活体探针判,不看开关名/按钮**:逐个打 `GET /api/v1/auth/oauth/<provider>/start` —— 启用回 302 到供应商 authorize(带 `client_id`/`scope`/`state`),未启用回 `OAUTH_DISABLED` 类文案。
3. **解析歧义排查清单**(逐条实测,现代实现多数已封):
   - `<EMAIL-REDACTED>@attacker.com` 双 `@`:实现用 `strings.Cut(email,"@")`(切第一个)再拒「域内含 @」⇒ **封死**;用 `LastIndex`/取最后一段 ⇒ 可绕。**读实现,别猜**。
   - 大小写/尾点/空白归一化(`ToLower` + `TrimRight(".")`)基本是标准动作 ⇒ 无隙。
   - `*.` 只通配子域、前缀为精确匹配 ⇒ punycode/homoglyph 无效(且域名还必须能被对方 MTA 投递)。
4. 结论:白名单域墙通常**硬**。时间花在「搞到白名单域真邮箱」上,别在解析上钻牛角尖。
5. **搞邮箱前先算账**:若进门的唯一收益是一个普通账号,而目标价值面(管理端/RCE 原语)还要另一层提权,先把账算清再投入注册马拉松。

## 2. 模式判定表

| 初始化响应 | 模式 | 打法 |
|---|---|---|
| `success:0`,且 `gt=e10adc3949ba59abbe56e057f20f883e`(= `md5("123456")`,厂商官方公共测试 ID) | **离线/降级校验** | 提交 `geetest_validate = md5(challenge)` 即过,免浏览器 |
| `success:1`,gt 为真实 32hex 且非上值 | 在线校验 | md5 无效,走有头浏览器 + 真实鼠标事件路线 |

`gt = md5("123456")` 这类**测试凭据是离线模式的强指纹**:厂商 demo 用公开 ID ⇒ 配套私钥也是公开的
⇒ 服务端只能做本地可算的校验。

## 2.5 自研图形码（非第三方）：先判「码语义 + 签名」，再谈读图

站点不是 geetest/腾讯滑块，而是自画 4 位字母数字图 + 一个提交签名时，按此判：
- **先看提交体要不要签名**。自研站常在 `captchaCheck` 里要一个前端不明写的 `sign`：
  grep 前端 bundle/源码里的**短盐常量**（产品名拼音/缩写）与 `sign`/`md5` 邻接；
  典型式 `sign = MD5( MD5(code + ip) + '<盐>' )`，`ip` 是**取图响应里回显的服务端所见出口 IP**（不是本机 IP）。
  缺 sign 或 IP 错配的表现是**永远「验证码不正确」** —— 会误导你反复重读图。走代理/跳板时先核对出网 IP 是否与取图接口看到的一致。
- **会话 key 语义（最贵的一课）**：同一 cookie jar 里**连续取多张图，只有最后一张的 key 有效**，前几张的 key 立即作废。
  要提吞吐必须**每张图一个独立会话/cookie jar**；在同一 jar 里连取多张再逐张提交 = 除最后一张外全部白刷。
  单图单提交（1 图 1 票）是默认打法。
- **读图增强（不写 OCR）**：真字符是**深且高饱和**像素、干扰字符**浅/低饱和** ⇒ 按「亮度<阈值 且 饱和度>阈值」掩码二值化，
  干扰整体消失；再把每个字符槽放大 10x 横拼成一条读；同时用原色 6x 整图交叉验证，只取两图一致的字符，其余进候选兜底。
  字符**对角错位(staggered)排版**时直接放弃 ddddocr(字符基线错位 = 训练分布外，读出乱码且预处理救不回)——只走放大视觉直读，按正常阅读顺序逐字符读，对错用报错文案自校验。
- **ticket/一次性语义**：命中后给的 ticket 常**一查即焚**（第二次回「人机验证失败」）；
  但**被 WAF 拦掉的请求不算消费**（票还在）—— 别因一次 WAF 拦截就重取图。

### 2.5.1 SPA/Next.js 站取图流: id 取证 + 视觉直读 + 两图时序(实测)

- **先取证 id 生成器再复刻**: 取图请求形如 `/api/auth/captcha?purpose=X&id={13位ms}_{hex}`。id **长度/字符集错**时服务端回的是 `image unavailable` 类文案(非「格式非法」) ⇒ 极易误判端点损坏、转头去啃前端加载路径。取证: chunk 里 `rg -o '.{260}getRandomValues.{200}'` 找 `new Uint8Array(N)`(hex 位数 = N×2;实测 N=18 ⇒ **36 位**,34 位被拒); `Date.now()` 给时间戳位数。
- **判「最新一张」语义的省事法**: 拿图后**只提交验证码值、不带 id**;能过 ⇒ 服务端按会话最近一张校验(与本节会话 key 同族) ⇒ 全链 `GET 图 → 读码 → 立即提交`,中间不插入其它取图;每个 captcha 门控 POST 前一刻重取最新一张即可,不必追踪 id。
- **读图走「放大直读」(不写 OCR 代码)**: 表单 HTML 的 `pattern=`(如 `[2346789A-Za-z]{5}`)先给长度与字符集;PNG 落盘 → `PIL resize((w*8,h*8), LANCZOS)` → **多模态视觉直接读**;读错用服务端报错文案自校验(「验证码错误」→ 重拿重读)。一次性流程用直读(实测 3/3 全对);批量高频再上 §2.1 式 OCR 管道。
- **注册链两图时序(实测)**: send-code 会消费第一张 ⇒ **提交前重取第二张**;邮箱码用临时邮箱(temp-mail.io 这类,**~10 分钟寿命**)⇒ 全链脚本先预演、再一口气跑。**成功判据别只看提交响应**——注册/Server Action 失败常静默重渲染原页(200 也可能是失败),用登录后页面二次验证;未过先查时序(captcha 是否最新、邮箱码是否过期),再怀疑格式。
- **★ 号建成与否只能活体验证(乐观凭据文件坑)**: 自动化注册脚本 **exit 0 + 本地写出凭据文件 ≠ 账号存在**——常在最后一步(人机验证/手机号/软错误页)失败而脚本照样写盘,凭据文件只是乐观写入。**未验证的邮箱一旦被当作白名单/收码前提,下游整个计划都是空中楼阁**(会白啃一轮才发现号没建成)。验证纪律:①对邮箱 Web 面**真实登录一次**(报「找不到帐户」= 号不存在,不是密码错);②做一次 IMAP 认证;两者都不通才换方案。**必须用与注册相同的出口复验**,出口风控不同会给出误导结论。
- **邮件通道的实测边界**: **Outlook/Hotmail 个人号 IMAP 基础认证已被禁用** ⇒ 脚本 IMAP 收信不可行,只能浏览器 Webmail(CDP 载具)或 OAuth2/Graph;未登录访问 webmail 常被重定向到营销页,**登录入口走账号域(`login.live.com`)而非邮箱域**。mail.com 类 IMAP 认证失败 = 号没建成,不是代理配置问题。**IMAP 走 socks**:`imaplib.IMAP4_SSL(host=None)` + 手工 socket 会 `getaddrinfo(None)` 报错,重写 `_create_socket` 让连出走代理即可(SMTP/POP3 同理)。
- 免费邮箱注册被**手机号闸门**挡时(API 报 `mobileNumber must not be null` 类):先试 UI 流有无「跳过/无手机号」分支,再考虑接码,别直接判死。

## 2.6 ★ 判「校验后端自己坏了」——两个端点全败就停，别再调 OCR

**症状**：站点自绘图码，读图已**独立证准**（原图放大肉眼比对一致、OCR 也对）、**签名/出口 IP 绑定也已对齐**，
但提交后**永远**回「验证码不正确」，换新会话、换新图、加长重试全无效。

**判据（三步，做完再决定投不投入）**：

1. **换端点复测**：同一站点再找**另一个也要验证码的入口**（商户端 / 买家端 / 注册 / 发码），
   用同样的「取图 + 提交」方法打一发。
2. **两端都「验证码不正确」⇒ 结论是站点侧人机校验组件失效/被关，不是参数名或 OCR 的问题。**
   这与运维状态常吻合：站点同时在广播「系统升级维护中/遭受攻击」之类公告时，几乎必然如此。
3. 此时**立刻停手**，不要再调读图、参数名、大小写、会话复用 —— 那是把时间烧在一个服务端已不做校验的闸门上。

**两个误导源**：

- **「验证码接口返回得很有内容」≠ 它在做校验** —— 返回体往往是**取图时**生成的，提交路径根本没进校验逻辑。
- 允许为参数名试错，但**两三个参数形态 + 一个对照端点**仍全败，就该定性为服务端问题并如实交付，
  而不是换第四个参数名。

**收线口径**：写「该站人机校验当前不可用（与维护公告一致）」并列出因此断掉的路径（依赖人机 ticket 的列表/下单接口等）；
**不要写成「验证码识别失败」**——那是错误归因，会让下一轮又从头调 OCR。

## 3. 提交矩阵与成功 oracle

- `validate` 字段**只放 `md5(challenge)`**;`|jordan` 是 `seccode` 的格式,拼进 `validate` 必失败。
  矩阵要**同时**含「带 `|jordan`」与「不带」两条,逐条比对结果差异。
- **成功不能看验证码接口自己的返回**,要看**下一层业务错误文案的变化**:
  登录从「验证失败，请重新验证」变成「用户名或密码不正确」;注册/发码从「验证加载失败」变成字段级报错。
  这是唯一可靠的 oracle。
- 命中后**重复 5 次**(每次重取 challenge 重算)确认稳定可复用,再据此做凭据尝试。

## 4. 多域名实例逐个比对,别在一个站上判死整族

同一套源码 OEM 成多个品牌域名时,验证码开关常逐站不同:一族里可能 A 站是在线模式(真 gt,硬墙)、
B 站是离线模式(测试 gt,一打就穿)。**把每个域名都取一遍初始化响应**,先打配置最弱的那台。

## 5. 收线与纪律

- 凭据尝试只用**靶向小列表**(少量账号 × 少量常见口令);大字典先问,并限速、可随时中断。
- ★ **过码 ≠ 限速豁免:锁定常按「端点/IP」记账(与用户名无关)** —— 提交失败照记服务端计数,用户名枚举与差分探测**共用同一预算**(建议 ≤20 发);出现带未来时间的锁定文案(「失败次数过多,请 N 分钟后再试」)= **硬停整个登录面** —— 换用户名/换大小写/空转等待都是同一计数(实测:一轮 ~50 发即锁,后续窗口作废)。换**正交端点**继续(安装向导 `test_connection` oracle / 找回密码面 / 未授权 API 面);目标带「机器验证/封卡」等价风控时按**触发代价**预算。
- ★ **「剩余 N 次尝试机会」型计数器常按会话记账(新建会话即满额重置)** —— 与上条的 IP/端点硬锁是两种制度：批量枚举时**每候选独立会话**(会话内取图+提交必须配对)，不在同一会话连打；「用户名不存在(剩余 N 次)」这类明确差分 = **用户名枚举 oracle**，先用几乎必不存在的用户名校准基线文案，仍低频单发、文案一变即停。
- 通过验证码 ≠ 登录成功:闸门破了只说明可以正常尝试;失败文案要如实区分「密码错」与「账号不存在」。
- 真在线模式 + challenge 一次性失效时纯自动化可能打不动 ⇒ **如实交付信息泄露面成果,不要在滑块里无限循环**。
- ★ **一次性码的时效与「工具往返」冲突（最贵的隐形杀手）**：取图 → 读图 → 提交若跨了多次工具调用（分钟级），码常已过期，表现是**恒回「验证码错误或已过期」而你看不到任何凭据层信息**。
  - 既定形态 = **把「取图 + 放大落盘」压进一次调用**；读图后**紧接着下一次调用就提交，中间不插任何请求**（尤其**不要为了「刷新」再取一次登录页**——那会换掉会话里那一张/作废前一票）。
  - ★ **失败先按文案归因，再决定改什么**：「验证码错误 / 已过期」= **门禁层** ⇒ 凭据尝试**零进展**，不要据此换口令、不要怀疑账号被锁、不要重跑凭据矩阵；只有文案切到「密码错误 / 账号不存在」才算摸到凭据层。把门禁层失败误归因成凭据层，是本类现场最常见的整轮白耗。
  - 判据：同一凭据、同一码值短时间内重复提交两次，**第二次回「已过期/已使用」与第一次回「错误」不同** ⇒ 码是一次性的且你的提交确实到达了校验逻辑（问题在时效，不在识别）。
