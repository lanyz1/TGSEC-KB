# Credential Attack Engineering

口令面攻击的**工程纪律**：怎么做出一个能被信任的「扫了 N 条 / 命中 0」结论，以及怎么不把自己和目标一起拖死。
本技能不授权开喷 —— 它保证的是「一旦决定喷，喷得对、结论可信、资源不被自己浪费掉」。

## 0. 先判定该不该喷（门优先于本技能）

默认**不开喷**。只在用户点名凭据面，或非凭据格子（未授权 / IDOR / 逻辑 / JS API / 会话 / 旁端口 / 注入）测满仍无路之后，用**定向少量主题词**。
完整门与本用户口径（「别他妈爆破了」「我要的是数据泄露/接管/资金」）见 `pentest-execution` 的 NO-SPRAY 与 2c 节 —— 与本技能冲突时以那里为准。

**枚举出用户名/邮箱 + 实测零限速零锁定，同样不是开喷许可证。** 这三个信号合起来只是把「定向爆破可行」写成一条发现
（PoC = 30 次连续失败全 401、秒级完成、无 429 无锁定），不是行动许可。交付口径：「目标可枚举 + 无限速 = 口令是唯一门锁」，
把决定权交回用户，不要喷到中为止。

## 1. 先认领产品身份，再决定要不要找源码（≤30 分钟）

多租户 / 代理后台 / 克隆机器人 / 发卡代理这类形态出现时：

1. 先锁**产品身份**：厂商频道、卖家客服号、自助开号 bot、`openapi` 里的默认联系人字段（克隆类后台的 `clone_contact` 默认值往往直接是运营者本人号）。
2. 最快的身份链是 Telegram 公开预览：`https://t.me/s/<channel_or_botname>` 带浏览器 UA，能直接扒出产品介绍、卖家联系方式、代理/克隆商业模式与教程帖。
3. 接受一个结论：**商业白标产品的源码与默认口令在卖家手里**。匿名可达的是 repo 搜索，代码级搜索需要认证。把「搜源码 / 搜默认口令」压到 30 分钟硬上限，搜不到就撤 —— 卖家明码标价卖可二开版本时，这是**购买问题不是技术问题**，不许耗掉整轮。
4. 随即切两条主线：① 运营者的**其它软资产做口令复用**（同一套密码走天下是这类运营者的常态；副实例、旁车服务、SSH、VPN 控制面全是复制点）；② 面板自身的 API 行为面（未授权 / IDOR / 会话 / 签名）。
5. 产品指纹写进同类专项 reference，不要每个目标新建一次性文件。

**反向情形：产品本身就是公开 OSS（Dujiao-Next、BEpusdt、Evolution API、RuoYi …）→ 立刻读上游源码，别在活站上瞎扫。** 直接 `curl -sL raw.githubusercontent.com/<org>/<repo>/main/<path>` 抓 `routes_*.go` / `urls.py` / 鉴权中间件 / 凭据生成服务，一趟拿到**全路由表 + 每组挂的鉴权中间件 + 凭据格式**，比在活站上猜路径快一个量级。凭据格式直接决定喷不喷：`crypto/rand` 出的 32/64 字节 hex（例：Dujiao-Next 商城渠道 API 的 `Dujiao-Next-Channel-Key`）= **不可爆破，字典立刻收回**；生成函数带默认值 / 短前缀 / 可预测序列才是入口。同一趟还能确认哪些端点**本该免鉴权**（登录、公开目录、身份 resolve），把火力集中过去。

**开源仓库不只给路由，还给默认凭据。** 翻 `migrations/*seed*.sql`、`*seed_admin_users*`、`config.yml.example`、`docker-compose*.yml`、示例 `.env`：里面的 bcrypt/md5 哈希**离线破**（种子账号生产部署常照抄，`admin` + 常见口令秒出），比对着登录口喷快一个量级。

破了默认凭据后的**第一个问题是「它部署在哪」，不是再试一次登录**：先把实例指纹（登录接口路径与响应形状、静态资源路径、特有请求头）铺到全部已知 host / 端口 / vhost 上做匹配，命中实例再花那一次宝贵尝试。在已知 host 上反复用同一凭据试、把命中率低的登录口当唯一入口，是本技能最常见的浪费。

## 2. 开工前三次判定（省掉整轮浪费）

- **账号名从哪来？先枚举，不要猜。** 两个向量按噪声从小到大：
  1. **注册接口的重复错误** —— `POST /api/users/register` 带一个猜测邮箱，若回 `"该邮箱已注册"`（而非笼统「注册失败」）
     就是**显式枚举**：零噪声、不消耗任何限速配额，比时序硬得多。任何目标先打这一枪。
  2. **登录时序** —— 存在账号跑一次 bcrypt（~40ms+）vs 不存在直接返回（~20ms）。判据同 §2c：候选与基线**交替**测量、
     ≥5 轮取中位数、**两簇零重叠**才可判存在；单发或顺序采样会把网络抖动误判成「存在」。
  同一手法遍历 `/api/admin/login` 的候选用户名即可定出管理员用户名（通常只命中一个）。拿到名字后**停手**，见 §0。
  3. **登录页自己的预检接口（最干净的一条：零噪声、零限速消耗）** —— 登录框 `blur`/`change` 时前端常先打一个预检请求，决定要不要显示验证码/2FA 框（`/user/beforeLogin`、`/checkAccount`、`/loginPolicy`、`/getLoginConfig` 之类）。这类接口**绝大多数不挂鉴权**，一次 GET 就回「账号是否存在 + 2FA 开关」，有的连 `isProxy`/`role` 一起给。用法：
     - 从登录页 JS 抠 URL（搜 `blur`/`focusout` + `account` 的 ajax）；
     - 拿它枚举账号名，与注册接口回显交叉验证；
     - **用它判「这道门后面还有几把锁」**：`googleAuthEnabled:false` 的账号登录只要口令，是整批账号里唯一值得投字典的子集；
     - 有的实现在「待绑定」态会把 **2FA secret 和二维码一起回给你**（拿来自算 TOTP，见 2FA 预言机）；
     - **管理端账号与客户端账号常是两张表**（管理端账号打客户端接口会回「用户不存在」），据此确认该枚举哪一侧、以及你的低权 token 可能在哪一侧不被认。
- **限流键是什么？** 10 发随机 `X-Forwarded-For` / `X-Real-IP` 的突发即可判定按 IP 还是按用户名/账号桶。按用户名 = 换用户名继续，不需要代理；XFF 伪造在 Gin/Node `ClientIP`（trusted proxies）或 nginx 覆写/追加 XFF 时是死杠杆，别把字典耗在上面。
- **有没有副本？** 同产品的第二个部署（换端口的副本、无前置限流的实例）= 免费爆破预言机。副本上打穿，同口令回打有前置限流的正主。一次爆破，两扇门。
- **限流在前端还是应用层？** nginx 429 = HTML；应用层 429 = JSON（如 `{"detail":"too many login attempts"}`）。应用层 token-bucket 常每窗口只放 2-5 发，XFF 绕不过，只能**配速**：一个窗口一发高价值口令，别开并发烧窗口。
- **密码面到底开没开？** 开工前用一行预检，别把整轮投在一个关着的门上：SSH 用 `ssh -o PreferredAuthentications=none -o BatchMode=yes -o StrictHostKeyChecking=no user@host`，返回的 `Permission denied (publickey,password)` 里列出的就是服务端**实际提供**的认证方式（只有 `publickey` = 别喷），同一次还会打印 banner 版本，据此判断是否落在已修复的 regreSSHion 一类版本上。RDP / WinRM / SMB 同理先看 `nmap -sV` 的服务与认证提示。nmap 的 `ssh-auth-methods` 脚本容易超时，用 ssh 自带技巧更稳。

## 2b. 验证码后台的口令攻击（判据先行）

验证码后台往往是唯一还开着的口令面，但前提是**两级判据写对**，否则整轮结论都不可信：

- **分开计数两类响应**：`{"code":0,"msg":"验证码输入有误"}` = 验证码没认对，**口令根本没被评估、不消耗尝试次数** → 换新图立刻重试；`{"status":1,"msg":"用户名或密码有误"}` = 真失败，计入限速/锁定。把前者当失败会以为「字典跑完了」，把后者当成功更糟。
- **成功判据只匹配显式成功标志**（`"status":0` / `登录成功` + 返回的跳转 url），**永远不要用通用 `code:0`**：验证码错误响应里同样带 `code:0`，用它判成功会对着验证码错误循环喊「登录成功 / RCE 成功」（本机真实翻车）。
- **OCR 多方案投票再提交**：同图跑 (放大倍数 × 二值化阈值) × `--psm 7/8/6` 的组合取众数；单阈值单 psm 会把大量尝试浪费在同一个字符上。小 JPEG 验证码优先 `ddddocr`，tesseract 只是备选。**OCR 不确定就刷新重取，绝不拿不确定结果去撞口令**（那才真在消耗配额）。
- **验证码每次请求新图，并与会话 cookie 绑定**；图与会话错配 = 必错。
- 登录成功后**先存 `PHPSESSID`/token，并立刻拉一个受保护接口验证会话有效**，再宣布拿到后台。

## 2d. 「口令明明是对的却登不进去」的归因顺序

已知口令 + 按前端 JS 逐字复刻的算法仍然失败时，按序排除，别先把脚本重写一遍：

1. **公钥是不是另一把。** 前端 bundle 里常自带 RSA 公钥常量（如 `crypto-util.js` 的 `publicKey`），可能与后端那把（`rsa_pub.pem`）不同。抠出来比对模数，再下结论。
2. **用错误码自证加密链路。** 密文块解不开 ⇒ 服务端 `500 系统异常`；解得开但口令不匹配 ⇒ 业务码（`2001`/`1001` 「账号或密码不正确」）。能分清这两种，就说明你的 RSA+Base64 与公钥都对，剩下的只能是口令本身。
3. **同一目标上「明文口令 → 500」与「密文口令 → 业务码」的差异本身就是账号存在性预言机**（服务端先查账号、查到才走解密），顺手收下这个 oracle。
4. 以上都排掉 ⇒ **口令已被运营方改掉**（主动反制），不是你的流程坏了。运营方可以同时删内置 admin、换 2FA 种子、给接口补鉴权、重置你的账号口令 —— 归因要看全局信号，不要单点怀疑自己实现。

## 2c. 锁定机制 = 判定在前、自增在后 → 竞态可整批绕过

账号锁定几乎总是「先 GET 计数判定，bcrypt 之后再 INCR」，判定与自增不原子。**一个栅栏同步的并发突发能让整批请求都在第一次自增落地前通过判定** —— 逐发第 6 发就锁的账号，同刻并发可整波通过（实测顺序 5 发即锁，并发 50 / 1000 / 1500 全部通过）。

- **先量化策略再决定用不用**：把 `invalid username or password`（真失败，计数 +1）与 `locked`（已被锁）**分开计数**。顺序打 5–8 发读出阈值；锁上后按分钟粒度打探出 `locked` 转回 `invalid` 的时刻 = TTL（常见 10–15 分钟）。阈值和 TTL 是读出来的，不是猜的。
- **波次形态**：TCP 握手提前做完，再把预构造好的请求字节同刻 `sendall` + 栅栏释放。窗口只有「首个请求 bcrypt」那段（约 60–100ms），握手慢 30 秒不影响结果 —— 但别把握手耗时算进波次耗时，否则会误判成被限流。
- **波次大小到顶就停，别越调越大**：有效通过数在 ~1300–1600 处饱和（实测 1000 / 1500 / 2500 / 4000 并发），再大只是多出 500 与连接错误。按「每窗口有效条数」调参；整波塌陷（<500）时先降到 1500 重跑一波，不要加码。
- **只有真失败才推进字典**：`locked` / 连接错误 / 500 一律留在剩余字典里下波重试，把 `invalid` 与命中当唯一进度，否则进度条是假的（见 §4）。
- **锁桶按账号精确匹配**：XFF 伪造、换源 IP、大小写 / 尾随空白变体都不换桶；按账号计数的锁定对 IP 轮换完全免疫（§3 只解决按 IP 封）。
- **副作用：锁定响应就是用户名存在性预言机** —— 计数器只在真实账号的失败路径上创建，不存在的用户名永远不会 `locked`。比时序可靠：WAN 抖动下同一候选的响应时间与基线可互差 2 倍，单发时序结论不可信；非要用时序就把候选与基线**交替**测量、多轮取中位数。
- **波次里出现既非 `invalid` 也非 `locked` 的响应立刻看**：那可能是「密码正确但需 2FA / 首次改密 / 临时凭据」的第二道门。
- 深度配方（测量脚本、栅栏爆破器、原始 socket 变体、波次实测数据、这个技巧解决不了什么）见 `references/login-lockout-race.md`。

## 3. 多源 IP 轮换（按 IP 封禁的唯一正解）

```python
sock = socket.socket(); sock.bind((src_ip, 0)); sock.connect((host, port))
```

- 一机多个公网源 IP = 多份独立配额（本机 eth0 绑有 4 个公网 IP）；这类封禁通常 1-2 分钟自解，轮换即可续命。
- 轮换 IP 只解决「按 IP 封」，解决不了「按用户名桶」。两者分开判、分开绕。**把 429 计数当调参信号**：轮换下 429 恒为 0 = 配额还有余量，可缩短间隔提速；一出现 429 立刻退半步加间隔，别把新 IP 也一起送进封禁。
- **被封的判据**：连接 accept 后立刻 RST / 连 banner 都没交换（如 `kex_exchange_identification: read: Connection reset by peer`）= fail2ban / allowlist 已封；只有 `Permission denied` 才是真的在比口令。被封就停手改慢节奏，继续试只会把封禁越刷越长。

## 4. 假阴性控制（本技能最重要的一条）

**「扫了 N 条、命中 0」只有在失败计数里没有混进 unknown 时才成立。**

- 明确失败（`AuthenticationException` / 401 / 统一「账号或密码错误」）= 真失败。
- 连接被丢 / 超时 / `Error reading SSH protocol banner` = **不确定**，绝不许计入失败。
- 不确定率实测常在 5-10%：真口令落在洞里就是假阴性。做法：worker 内先重试 2-3 次，主循环跑完再对全部不确定结果**补测一整遍**。
- 交付时必须能说出四个数：总尝试、明确失败、不确定、补测后剩余不确定。说「0 命中」时这四个数就是证据。

### 字典自己先自证加载过了（假的「不中」最常见的来源）

- 脚本第一件事：打印字典的 `path` / `len(lines)` / `lines[0]`。条目数对不上预期（预期 14M 实读 0）就**立刻停手修读入**，不要继续跑第二轮「确认」。
- **不要相信扩展名。** 名为 `rockyou.txt.gz` 的文件实测可能是**未压缩明文**：按 gzip 读 ⇒ 0 条 ⇒ 得出「14M 字典全不中」的假结论。先 `file <dict>` 或读前 4 字节魔数（`1f 8b` 才是 gzip）再决定要不要解压。
- 命中/不中的日志形状必须不同（命中写独立 `hit.txt` 并立刻打印），否则「跑完了」和「读到 0 条就跑完了」在你的终端里长得一模一样。

### 批量扫描的「全否」要对着源清单断言覆盖

- 从源码/JS 抠端点后**打印去重计数**，与现成清单（页面 JS、Swagger、接口表文件）对账：抠出 30 个而全集是 412 个，那「全部 401」是建立在 7% 覆盖上的结论，等于没测。
- **循环里禁止早 `break`。** 一轮只试第一个后端就退出的「重放/枚举脚本」，会把「一个实例否」写成「全部实例否」。收尾用三态计数 `0 命中 / N 被拒 / M 报错 / 共 T`；数量对不上 T 就是脚本自己的问题，不是目标加固。
- **matcher 拿已知正样本校准**：任何报「0 命中」的提取脚本，先跑一遍你刚拿到的那条已知会命中的数据，确认正则真的会命中。0 命中通常意味着正则写错。

## 5. 资源互斥（同一台机只留一条吃 CPU 的主线）

- bcrypt 类高开销喷密会把**目标宿主机** CPU 吃满，同机其它攻击面一起塌：实测把并发的 SSH 爆破从 455 次/分砸到 26 次/分。
- 要打同机的另一条向量，就**主动暂停**吃 CPU 的那条给它腾资源；命中值远高于并行度。单向量吞吐 > 多向量并行。
- 暂停用精确 PID（见 §6），并把「为什么暂停」写进状态文件，别让下一轮以为自己忘了。

## 6. 工具陷阱（每条都真实烧过时间）

- **`pkill -f` / `pgrep -f` 的模式串会匹配到你自己正在执行的命令行**：当前命令被 SIGTERM（`exit -15`、无回显），要杀的进程反而变孤儿。**两处都要中括号技巧**：`pkill -f "[b]rute_multi"`、`pgrep -f "[b]rute_multi" | xargs -r kill` —— `pgrep -f` 同样自匹配，`pgrep -f race_brute6 | xargs -r kill` 实测把发起它的 shell 一起杀了。最稳：`ps -eo pid,args | grep "[r]ace_brute" | awk '{print $1}' | xargs -r kill`，杀完再 `ps` 复核一次。
- **hydra 输出别接 `| tail`**：管道缓冲吞掉 `STATUS ... tries/min` 行，只剩尾部 = 丢掉唯一进度信号。写 `> log 2>&1` / `tee log` 再读 tail。
- **`hydra -R`** 从 CWD 的 `./hydra.restore` 续跑 —— 中途别换工作目录。
- **paramiko 装独立 venv**（系统 python 可能 PEP 668 只读）：`python3 -m venv /tmp/v1 && /tmp/v1/bin/pip install paramiko`。
- 长任务一律 `tee` 落日志，命中写独立 `hit.txt`；不要只靠 stdout（终端通知只带回尾部片段）。

## 7. 输出节奏（这个用户）

- 用户回「？」/「？？」= 上一轮**没有可见动作或没有可执行结论**（长篇推演、只报计划、结论含糊）。立刻停掉推演，直接调工具打出下一个具体动作；不要用更长的解释回应问号。
- 每条输出落到「已经打到什么 / 下一步打哪个面」。
- 命中：先给「有 / 无 + 账号密码」，再补证据。未命中：直接说未命中，不要把不确定当失败，也不要把预言机清单充数。
- 用户喊停（停 / 取消 / 停止）→ 立刻 kill 全部 spray 进程，报告「已测 X 未命中 + 按你要求停止」，不再输出攻击进度。
