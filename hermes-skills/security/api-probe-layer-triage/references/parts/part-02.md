## 302 的三种成因:差分组实验才敢下结论

同一条 `302 → /login` 可以来自三件完全不同的事,**只看一次响应无法区分**:

| 成因 | 触发条件 | 判别方法 |
|---|---|---|
| ① **未认证访问受限路径**(登录墙) | 无票 / 会话失效 | 带上有效会话复测 ⇒ 变 200 |
| ② **账号级(×端点)风控** | 该账号在此端点上的失败次数超阈值 | ★**固定端点+载体+参数,只换用户名**,同一批内:被风控账号 302 / 未触碰账号 200 业务 JSON |
| ③ **该路径不在白名单前缀内** | 匿名访问非白名单前缀 | 用**同前缀已知不存在路径**做对照:同为 302 ⇒ 该前缀整族在墙后,此响应**不携带存在性信息** |

**实战翻车**:一批探针测得"149/149 出口的 `/pfv3/resetLoginPwd` 全 302",据此写了"permitAll 被收回(约 20 分钟窗口)";20 分钟后**同一端点换另一个用户名**发一发就回 `200 otp_wrong` ⇒ 真因是该账号先前被连打 27 次错验证码、进了**账号×端点风控**,路径从来没关过。

四条必守:
1. **"放行被收回"这类结论必须做跨账号同批对照**才允许写 —— 单账号的 302 只有成因 ①②③ 三种可能,证据力为零。
2. **"仍开放 / 已关闭"必须带时间戳**(UTC + 目标时区双标),因为窗口期与风控状态都会变。
3. **攻击次数实验会污染后续判读**:做 N 次错值实验的账号**立即进风控**,此后该账号在同端点的一切响应(含"存在性 oracle")全部失真。⇒ 次数实验前后都要用**没被实验碰过的账号**重测基线。
4. 次数实验本身就是**风控存在性的量测**:错值 N 次后由业务 JSON 转为 302 ⇒ 得到"有账号级尝试计数"的正面证据,这是**给 ATO 链收口的关键结论**,比"未爆破成功"强得多。
5. **★参数差分(IDOR/越权判据)必须把 302/0B/000 归入"不可用",绝不记成"差异"**。实测事故:一批参数级 IDOR 差分共出 **75 行"差异"标记,100% 是 `code=302 len=0`** —— 基线在批内健康段测到 `200/2832B`,随后会话被风控顶掉,所有变体全 302;若按字面读就会写出"加 userId 触发差异 ⇒ 存在越权"。
   ⇒ 判据必须是:
   ```python
   USABLE = (200, 500)          # 业务 JSON 才算可用样本
   if base_code in USABLE and var_code in USABLE:
       diff = (var_len != base_len) or (var_body != base_body)   # 真差分
   else:
       void += 1                # 302/0B/000/405 = 不可用,不计入差异
   ```
   且**先验条件**:变体命中必须在**同一会话生命周期内**(基线与本组变体都非 302);作废样本数必须报出来(与命中数并列),"差异 0 条"只有在**有效样本数达标**时才能当阴性。

## 认证态批量探测的会话卫生(轮换型出口池)

用轮换型代理池(同一 `IP:port` 每次请求可能换真实出口)做**认证态**批量探测时:同一会话内交替使用多个出口 ⇒ 会话不可用 ⇒ **整批全是 302/登录墙**,极易被误读成"站点故障/鉴权收紧"。

- 实测:34 个动作同一批全 302,而同出口**重新登录后立刻**读同一端点 ⇒ `200 / 5394B`。
- 规则:**一个出口一个会话** —— 登录与全部请求走同一出口,不要在批内切出口重试认证请求(切出口只用于解 CF 挑战/匿名探测)。
- 每批开头先请求一个**已知-good 的受保护端点**自证会话;它若不是 200 ⇒ 整批作废重来,不得写"目标变了"。
- **★单设备登录(请求体 `getSystemSetting` 常带 `singleDeviceLoginFlag`)**:同一账号第二次登录会**顶掉**第一个会话(实测:脚本首版写"两次登录做兜底",第二次登录后整批 302)⇒ **一批只登录一次**,禁止并行用同一账号跑多个脚本。
- **★账号级 24 小时限流(风控原因明文写在 body)**:连续 302 时**回读登录响应体**,实测 `HTTP 200` + `{"code":500,"msg":"Request is limited, please try again after 24 hours"}` ⇒ 是**账号被风控**,不是目标变更、不是站点故障。触发量级参考:单账号 ~5 分钟内连开 4 批(百余请求)即触发,代价是 24h 内该账号全废 ⇒ **认证态探测按"账号预算"排期**:优先复用一条长会话,把"新登录次数"与"请求总数"当配额管理。
- **★风控只作用在账号×端点,不改变路径结论**:同一时刻另一个未被实验触碰的账号在同端点照回业务 JSON ⇒ 凡"仍开放/已关闭"结论都要附**账号 + 时间戳**,单账号状态≠全站状态。
- **★票与出口绑定(与“会话不绑 IP”相反的那一半)**:WAF/挑战类 token、一次性 ticket **常绑定铸它的那个出口 IP** ⇒ 铸票与回放**必须同出口**(把出口用环境变量固定进每次运行,如 `XVIP_SOCKS=host:port python probe.py`),跨出口回放会整批 401,极易误判成「票失效/权限不足」。同族的**页面域与接口域可能各自只有不同出口可达**(实测:页面源域仅经本机代理出口可达,接口域经跳板出口可达) ⇒ 为「页面源」与「接口」**分别固定出口并分别验证**。

## 判层三铁律(实战代价换来)

1. **永远读 body,不要读 HTTP 码**。大量 Java/RuoYi 系目标把 HTTP 码固定 200,把真实状态放在 body 的 `code`/`msg`;用 `%{http_code}` 判层会把 405(存在+放行)归进 200 组,白丢正向证据。
2. **命名空间决定 0B 的含义**。同一目标上 `/sys/**`、`/mer/**` 与 `/login`、`/common/**` 可能走**不同应用/上游**:前者无注册路由回 `200+0B`,后者无 handler 也回 401 JSON ⇒ 先用“真路径 + 同前缀假路径”两组对照确定该命名空间内 0B 是否可判阴性,再统一判读。**判读颗粒度是"具体路径",而"有没有 oracle"是前缀级的**:同主机上有的前缀真路径 401 / 假路径 0B(有区分度),有的前缀(认证中心 catch-all)连**绝不存在路径**也回同款 401(零区分度 ⇒ 该前缀内存在性不可判)⇒ 每批必须跑**该前缀自己的**假路径对照,不跨前缀套用。
3. **后端可能比前端契约小**。前端 bundle 编出的路径可能含**已下线/未部署**的死链;命中“同前缀假路径 = 0B”的族应判为**未注册**,不能计入攻击面(报告里不得把死链写成“69 个导出接口”这类可打面)。

## 401 零区分度时:用三态测绘白名单边界

当目标对**任意路径**都回同一个 401(含绝不存在路径)⇒ 401 组内部**零区分度**,该批端点存在性**不可判定、整批作废**(实测:103 个候选中 82 个零字节 + 19 个 401,对照组 `/zzz_no_such_ep_9x7` 回同款)。补救办法是找**能穿透过滤器层**的响应形态:

| 响应 | 含义 |
|---|---|
| `401` + 业务 JSON | **该前缀被认证中心 catch-all 接管** ⇒ 端点是否存在**判不出**,不写阳性 |
| `404` + **框架 JSON 错误体**(如 Spring Boot `{"timestamp":…,"status":404,"error":"Not Found","path":…}`) | **白名单内但资源不存在** ⇒ 与 401 可分,用来反推白名单前缀覆盖范围 |
| **`200`/`500` + 业务 JSON 文案**(如 `{"msg":"当前系统没有开启注册功能！","code":500}`、`{"msg":"Request method 'GET' not supported","code":500}`) | ★**白名单(permitAll)内且路由存在** ⇒ **无票能进业务层就是放行**;这是最强的**白名单发现 oracle** |
| `200` 真内容 / `405` / `302` | 白名单内且端点存在 |

**用这个 oracle 主动找白名单**(不是只用来判读已知端点):把契约全路径**无票 GET** 跑一遍,凡返**业务层文案**(非 401/0B/404)的即 permitAll 路径。实测据此翻出此前未知的 `/register` —— 路由在白名单内、注册开关由服务端关闭(`当前系统没有开启注册功能！`),但**开关是配置项**:换环境/换租户可能开着,必须写进报告而不是"功能已关闭"一笔带过。

- 实战:后端把**文档组件的静态资源**放进了 permitAll(`/swagger-ui/index.html` → 200 / 3,129B),而**数据源端点 `/v3/api-docs`、`/v2/api-docs`、`/swagger-resources` 全部 401** ⇒ 结论只能写"装了 API 文档组件但文档端点未放行",**不能**写"存在 Swagger 未授权"。
- 同理 `/swagger-ui/swagger-initializer.js` 回 `404 框架 JSON` ⇒ 证明放行的是**部分路径**而非该目录整片;别由静态资源可读推断文档可读,**逐路径测**。
- **白名单候选的产地(按命中率排序)**:①**登录/注册/落地页的页面内 JS**(见 `references/unauth-endpoint-harvest.md`)②动作名自带 `NotLogin`/`WithoutLogin` 的 ③页面 onLoad 阶段以**空体** `{}` 调用的。这三类是业务上"设计成登录前可调"的口,命中未认证面的概率远高于枚举。

## 代理池/出口:协议用错会伪装成"池子全坏"

- 条目形如 `IP:port:user:pass` 的池子**协议不定**:`http://` 全 `000` 时先换 **`socks5h://`** 再判池子死活(实测同一池:`http://` 全超时 → 换 `socks5h://` 后 4 个出口可用)。**`socks5h`(h=远端解析)**,别用 `socks5`。
- 池子可用性必须以**真实业务 API** 作对照(根路径通 ≠ 能打 API)。
- 换出口是解 CF 挑战的正解:同一站点、同一时刻,某些出口稳定拿真响应,另一些拿挑战页。

## 站点级 CDN 挑战页 = 第三态,先排除"是不是我方问题"

- 整批返回 Cloudflare 挑战页(数千字节 HTML、`Attention Required` / `Just a moment` / `cf-error`)⇒ **不得记阴性、不得记不存在**,该批归"未知"。
- 判定方法:**换多个口径的独立出口复测同一 URL**(本机直连 + 不同机房跳板机 + 代理池);**全部被挑战 ⇒ 站点级策略**(非我方出口问题),标未知并换通道;**只有部分出口被挑战 ⇒ 出口信誉问题**,换出口重跑。
- **每批必须带控制组端点**(已知会返回真数据的那个):控制组拿挑战页 ⇒ 该批全废;控制组 200 ⇒ 出口有效,后续样本才可信。

## 三态对照:证明"本该受保护"(最强论证)

只证"不带凭据 → 200"会被反驳成"这接口本来就公开"。补一发**非空无效凭据**:

| 请求 | 结果 | 推论 |
|---|---|---|
| 不带凭据头 | **200** | 放过 |
| 无效凭据(`token: 1` / `token: null`) | **401**(如"请重新登录" / "not authed") | 服务端明确要求身份 |

两条并存 ⇒ 这是**"只在凭据存在时才校验"的装饰器缺陷**,不是公开设计。这条比裸的"未授权 200"高一个数量级,必须写进报告。

注意:`token: ""` 常等同于"缺失"(拿不到 401)—— 对照必须用**非空无效值**。

## 服务端自报字段名,别急着跑候选词表

Python 栈的 422 响应体**逐字列出缺失字段名**:

| 栈 | 响应体 | 字段名 |
|---|---|---|
| marshmallow/Flask | `{"code":422,"msg":{"json":{"phone_number":["Missing data for required field."]}}}` | `phone_number` |
| FastAPI/Pydantic | `{"detail":[{"loc":["body","phone_number"],"type":"missing"}]}` | `phone_number` |
| 值域越界 | `{"msg":"Invalid value."}` | 参数已被识别且值域有限 ⇒ 用它二分值域 |

**字段名逐端点**:同族 `send_sms_code` 收 `phone`,`phone_login` 却收 `phone_number`。套错 schema 会让整批探针停在 422,得不出任何鉴权结论。

**Java/RuoYi 栈用 `500` 自报字段名,同一手法的另一形态**:写类端点缺必填时回 `500` + 文案逐字给出绑定名(实测一批 7 个 `500` 里 6 个是这类:`bankShortName`、`amountType`、`authId`、`apiType`、`receivingFlag`,第 7 个是伪动作的 `no such api`)。这批 **不是"疑似报错",是服务端亲手交付的参数名清单**:

- **★把这些自报名当作参数级 IDOR/越权差分的首选候选,而不是盲猜 `userId`/`accId`/`agentId`**。实测对 7 个资金端点做差分,盲猜名(含 `userNo`/`agentId` 共 7 个 × 2 值)在变体上零效果;而自报名里 `authId`/`apiType`/`receivingFlag` 本身就是**主体标识**,命中越权的概率高一个量级。
- **差分时保留一组盲猜名做对照**,否则无法区分"该端点无越权"与"我测错了参数名"。
- 报错**顺序 = 服务端校验顺序**(先校参数 → 再查库 → 才落盘),能直接读出前置条件链;`UNKNOW ERROR` 表示该端点有非参数前置条件(缺前置状态),不是参数名问题。
- 同一批里 `no such api`(伪动作)与 `cannot be null`(真动作)**必须分栏计数**:前者是存在性阴性,后者是"真实动作 + 参数名泄露"的正向情报,合并计数会把情报一起丢掉。

## 登录门的第二道参数:验证码/TOTP 字段名与锁定口径(零消耗真实账号)

口令对的账号仍会卡在门禁(图形码/短信码/TOTP/GA)。**门禁字段名与锁定策略都能只用不存在的用户名测出来**:

- **字段名 oracle 两步法**:① 只发 `{用户名, 口令}`;回「验证码不能为空 / 谷歌验证码不能为空」⇒
  门禁存在,且**校验跑在口令之前**(口令错也先报门禁)⇒ 该口的字段名探测**不必过口令**。
  ② 逐个候选字段名 + **错值**:唯一让文案翻到「验证码错误 / 谷歌验证错误」的那个就是真绑定名,
  其余候选恒回「不能为空」。⇒ **猜错名 ⇒ 文案不变;猜对名 + 错值 ⇒ 文案变**。
  把「文案没变」读成「该字段不参与校验」是这里最常见的错(与本卡「报错文案会骗人」同型;只发猜错名永远测不出字段名)。
- **免门禁账号判别器**:同一字段名 + 错值,回「验证码错误」= 该账号绑了门禁;回「用户名或密码错误」
  = 门禁被跳过。⇒ 用它挑**免门禁账号**,这是"口令对但缺动态码"的正路,而不是去猜动态码。
  三条判据全用**不存在的用户名**即可完成,真实账号的尝试计数零消耗。
- **锁定口径先测再打**:先分清锁定是**账号级还是 IP 级**、阈值多少,再决定发几发。**作用域有三种,第三种最容易漏**:
  ①账号级（键=用户名）②出口级（键=真实 IP）③**端点/站点级全局封锁**（换用户名 + 换出口 + 换会话仍回同一拒绝）。
  判法 = **单变量对照,一发一个变量**:固定出口换用户名 → 固定用户名换出口 → 两者同时换。命中 ③ ⇒ **立即停手**
  （换 IP、换账号、换 UA 全无用）,记下时间点,等自愈窗口（分钟~小时级）后**单发复测**再谈续打。
  ★**拒绝体形态突变本身就是信号**:应用正常错误体之外的**裸码响应**（如 `{"code":403}`,HTTP 200、无 `msg`、
  无业务字段）通常是**网关/风控闸门**回的,不是账号校验失败 —— 别把它读成「口令错」继续烧次数。
  ★**拿同宿主的非登录端点做对照**（首页/静态资源/另一业务口）:它正常返回 ⇒ 服务活着、只有登录被闸 ⇒ 印证全局封锁,
  同时排除「站点挂了」这一误判。
  ★**尝试预算**:作用域未判明前 **≤4 发**;连喷 6+ 发常把可自愈的窗口锁升级成硬封锁,并把仅有的高价值账号窗口一起烧掉。
  RuoYi 系实测形态:**仅 IP 级 / 阈值 ~3 / 连不存在的用户名也计数** ⇒ ①候选名枚举会
  **自己把出口 IP 打成 30 分钟封禁**(必须换出口 + 候选名串行);②「六位动态码爆破」可**数学排除**
  (10^6 × 阈值 / 出口数);③「只按 IP 记账」本身单列一条报告项(可被代理池 / XFF 绕过,与本卡限流绕过同源)。
  ★**同产品另一实例的相反形态(必须现场标定,不得套用上式)**:实测另一台 RuoYi 二开主机是**账号级**计数 ——
  用**不存在的用户名 + 非空错码**打一发**不消耗任何计数**(文案推进到门禁),而对**真实存在的账号**每试一次真实扣减,
  且响应体直接回显**剩余次数**(`谷歌验证码错误，还剩N次机会`)⇒ 该实例把配额读数白送给你。
  标定三步固定:①不存在的用户名 + 空门禁值 ⇒ 只回「不能为空」(零鉴别力,但确认了门禁先于口令);
  ②不存在的用户名 + **非空错码** ⇒ 文案推进到门禁计数 = **账号级**;若怕 IP 也被记账,用两个出口各发一发看谁被扣;
  ③把回显的剩余次数**当预算**用。
- ★★ **门禁计数是别人的真实资源,试错即扣减,可能短暂锁掉运营账号 —— 收手纪律**:对**存在的账号**每发一次错码都真实扣减其配额,
  ⇒ 只对**候选小列表**一次一测,对 admin / 超管 / 运营类账号**绝不反复打**;需要多测时优先拿**自己注册的账号**当主体(命中只锁自己);
  实测把两台主机的 `admin` 配额打到剩 1~3 次后**立即停手**,并把"打了什么、剩多少"向用户如实披露 ——
  这类副作用不进漏洞台账,但必须进汇报(用户会拿它当"要不要继续"的输入)。
  锁定随窗口自恢复,但**别去验证"它恢没恢复"** —— 验证动作本身就再扣一次。
  ★与"三条判据对真实账号零消耗"不矛盾:零消耗的前提是**名字不存在**;名字存在就会扣它的配额。
- **串行纪律**:换候选名、换账号名、换出口三个变量一次只动一个,否则分不清哪一行算命中。
- **★闸门之间有顺序,先读一次再动手**:同一端点用空参 / 错参名各发一次,若**先报角色/授权**(`用户不存在或角色错误`、`无权限`、
  `xxx 不存在`)**再**报门禁(验证码),则门禁**不是当前瓶颈** —— 是我方身份不够,再怎么试动态码也不会推进。
  判据:文案里出现「角色 / 权限 / 不存在该用户」这类词 = **授权层**,不是门禁层也不是参数名层。
  把"角色不足"误读成"只差一个验证码"会让整轮工作烧在门禁上。
- **★门禁/动态码类端点常"每调一次就轮换一次密钥"**:`create`/`bind` 型端点(GA/TOTP 绑定)每次调用都签发新 secret,
  旧的全部失效 ⇒ **连调 N 次后只有最后一次有效**,而中间任意一次失败**不能**证明"密钥不对"。
  纪律:调一次 ⇒ 立刻用它算码并当回写完绑定,别攒着批量试(否则每次试的都是已作废的 secret)。

### 前置闸门短路口令时:「账密有效」必须有错密码对照撑着

认证链上任何**前置闸门**(IP 白名单 / 人机验证 / TOTP / 租户匹配 / 设备指纹)都会**短路掉**口令校验,
⇒ 同一个文案会同时出现在「账密正确」与「账密错误」两种请求上。**从这种响应里读「账号存在 / 账密有效 /
只差 TOTP」是假的** —— 实测据此把「某默认号已过账密、只差白名单」写进案卷,直到补发对照才推翻。

- **铁律**:宣布「凭据有效 / 只差门禁 / 白名单是唯一障碍」之前,对**同一个账号**补发一发
  **错密码对照**(口令换随机串,其余字段不动)。**文案不变 ⇒ 该闸门在口令之前 ⇒ 凭据真伪未知**;
  只有文案切成「密码错误」才证明口令校验真被执行过。
- **配额归属跟着顺序走**:`还剩 N 次` / `账号已锁定 M 分钟` 是**前置闸门的配额**,不是口令错误次数;
  顺序未定就拿它做爆破预算 ⇒ 次数算错、号被锁。
- **两档文案完全不同,别混**:`ip不在白名单范围内:<IP>` = 真做了范围比对,**可伪造越过**;
  `白名单未配置` = 库侧该租户名单为空,**硬配置死路**(换任何 IP 都不动)⇒ 立刻换账号/换实例,
  别在这个号上继续换头烧轮次。
- **★IP 回显 = 白名单与头信任的免费 oracle**:错误文案里出回显 IP 时,把候选值(`1.2.3.4`)分别塞进
  各候选头,**回显变成该值 ⇒ 这个头就是被信任的**;成员候选用 `127.0.0.1`/`::1`/`192.168.0.1`/
  `10.0.0.1`/`172.17.0.1`(**白名单常含环回 + 内网段**,别只试 `127.0.0.1` 就收工),
  文案从「不在白名单」进阶到下一阶段即命中。让脚本按「回显 == 预期」自动判,别人工读。
- **按 IP 记账的封禁跟着伪造值走**:锁定文案点名 IP ⇒ 配额记在**那个头值**上 ⇒ 换一个新 XFF 值即得
  全新配额桶(实测按 IP 封 30 分钟,换值后立刻恢复);反面是篡改 IP 会一并重置限流与锁定状态,
  读到的锁定态不可归因于真实出口。
- **数值字段类型 oracle(Java/Jackson)**:给疑似数值字段发非数字串 ⇒ 回
  `Cannot deserialize value of type int from String` ⇒ 该字段是数值型,`"000000"` 实际以 **`0`** 参与比对
  (前导零丢失)、`1.5` 被截断、溢出/布尔/数组各有独立报错 ⇒ 先定类型再拼 payload,
  别把带前导零的串当敏感字符串用。

## 同一 handler 挂多套路径时:测一套推不出另一套

鉴权常在**路径前缀**上配白名单。同一 handler 常同时挂在带前缀与裸路径两套 URL(`/pc/<family>/**` 与 `/<family>/**`、`/api/<mod>/*` 与 `/pc/api/<mod>/*`)⇒ **只有一套在名单里,另一套整族匿名**。

- 把契约全 path 按**一级前缀聚类**,找出共享后缀段的孪生对,**两套各自单独测**。
- **带前缀那套 401 推不出裸路径那套也受保护** —— 这条推论是错的,而它会把真面判成"已排除"。
- 网关闭前缀名字也要穷举(`/dev-api`、`/prod-api`、`/stage-api`、裸路径)× 多个 `Host`,逐组合测。
- **不是整片开关**:同一前缀下,框架自带管理面可能仍 401,而同前缀下的自定义控制器全匿名 ⇒ **逐控制器族测**,用契约枚举自定义控制器,别按框架默认路径猜。

## 业务规则层 = 漏检证据

同一族端点里,某口返 `403 "请先开通会员"` / `"额度不足"` / `"未实名"`,而列表/详情口**没有这道检查** ⇒ 服务端**自证**该功能需受保护,而另一口漏检。这是可报告的对照,不是噪音。

## 限速要发送侧与校验侧分开探

同一功能两端的限速**通常不对称**,必须分开测,否则严重度会判错:

- 发送侧带 `每60秒一次` ⇒ 轰炸类严重度**下调**
- 校验侧连续错误码**无锁定/无失效/无递增延迟** ⇒ 暴力破解类严重度**上调**

判据:同一请求连发 N 次(如 12 次),观察是否出现锁定、验证码失效、封禁、递增延迟。

## 整面低价值的识别(及时收手)

拿到一堆端点后先判断"这整面是不是业务面":

- 消息/字段命名是 `appId` / `os` / `step` / `time` / `user` / `platform` 这类 ⇒ **客户端行为埋点 / analytics SDK**,不是业务 API。其 403/404 是**正常来源校验**,不是漏洞 —— 记一笔定性结论即可收手,别在签名上耗轮次。
- **前端 config 里的角色/类型开关**(`USERTYPE`、`role`、`isAdmin` 之类)先 grep 它在 bundle 里的**命中数**:命中 0 ⇒ **死配置**,前端从不读取 ⇒ 别为"篡改它提权"耗轮次(角色由服务端按账号判定)。
- **同族多端可能是同一份构建**:判据是**比 bundle 字节数 + 比 config 读取函数的解构字段**;同尺寸且读取模式逐字相同 ⇒ 单一构建多部署,差异只在 `_app.config.js` ⇒ 多端只审一份,别重复逆向。
