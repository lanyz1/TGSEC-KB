# 边缘拦截分层判定：404 / 封禁码 / 验证码是谁发的？

## 触发
某条 URL 关键字（`admin`、`think`、`invokefunction`、`../`、`union select`）被拒，但同站其它路由正常；或同一参数换个前缀就 404。此时**不能**直接下「该模块不存在 / 已打补丁」的结论——先确定 404 是哪一层发的。

## 流程

1. **基线探活**：拿一个确定存在的路由（首页、已知 API）请求，记录 `status / body 字节数 / Server 头`。
   - 应用在跑（如 ThinkPHP 的 `s=/index/index` 返 500）⇒ 后面的 404 是**选择性拦截**，不是整站挂。
2. **被拦路径**：同一入口、换成被拦关键字。对比三点：
   - `146B` 左右、`<center>nginx</center>`、`\r\n` 行尾 ⇒ **nginx 自己发的**（`if` 规则/`location` deny）。
   - 框架自己的 404 页/JSON（ThinkPHP「页面错误」、Spring Whitelabel、Express 默认页）⇒ 请求到了应用，是**路由/控制器不存在**。
   - 403 + `cloudflare` / `Server: cloudflare` ⇒ 边缘 WAF 规则，先找源站直连。
3. **编码变形验证**：只对「nginx 层」有意义，且**大概率无效**（见下）。对框架层 404，编码变形无意义。
4. **换通道**：URL 参数被过滤 ≠ body 被过滤。把载荷从 query 挪到 POST body / header / cookie 再试。
5. **结果确认**：body 通道打出去的请求，**必须拿到侧信道证据**（命令输出回显、DNS/HTTP 回连、写入后读回）才算成功。通用 500 错误页只说明应用抛异常（`app_debug=false`），**不是**执行成功。

## 关键机制（实测结论）

- **编码变形的成败取决于规则匹配的是哪份字符串，不是「nginx 一定解码」**：
  - 规则匹配 `$uri` / `$arg_`（已解码归一化）时，字母百分号编码**无效**——`%61dmin`、`%74hink` 解码后仍是 `admin`/`think`，`%5C`、`%2e%2e`、`//`、`;` 也会被 normalize。
  - 规则匹配 `$request_uri`（原始串），或上游网关按原始路径做 IP/路径前缀白名单时，**一个字符的编码就能穿过**：`/platform/auth/%6Cogin` 命中 `.. auth/login`，裸路径同一时刻仍返回封禁码。
  - 判据只有一条：**裸路径被封、同路径编码后出现应用层业务错误（校验文案 + `traceId`）** ⇒ 命中的是原始串规则；两者响应一致 ⇒ 该层解码后再匹配，别再换编码。
- **`if ($arg_s ~ ...)` 只看 query**，所以 `POST` body 里的 `_method=__construct&filter[]=...` 类载荷能穿过 WAF——但控制器仍要真实路由得上，否则只是另一个 500。
- 前缀白名单很常见：`s=/index/*`、`s=/api/*` 放行，`s=/admin/*`、`s=/foo` 一律 404。**这时 `admin` 模块可能真实存在只是入口不可达**，报告里必须写「被边缘过滤，未验证」，不能写「不存在」。

## 判读矩阵

| 观察 | 结论 |
|---|---|
| 被拦路径 146B nginx 404，基线 500/200 | 边缘 `$arg_` 或 `location` 过滤 |
| 被拦路径返回框架 404 页/JSON | 应用层路由不存在（可信） |
| 带反斜杠与不带反斜杠响应**完全一致** | 命名空间逃逸被规范化/修补 |
| body 载荷返回通用 500 | 未证实执行，换侧信道验证 |
| 同一端点所有参数名/格式/取值**逐字相同**的错误体 | 不是参数错，是**空数据集**（dev 库/白板），停手 |

## 硬封禁码 ≠ IP 白名单（先证伪再换 IP）

登录口返回「当前IP因异常访问已被永久封禁」这类硬封禁码时，**不要**直接判定网络层白名单/整段 IP 封杀。反爬规则对「缺浏览器头」和「IP 真被封」可以返回同一句话，判定顺序：

1. **默认 UA 本身常常就是触发器。** 同一条路径、同一个 IP：`curl/x.y` UA 一发即 `40000 永久封禁`（随后整站 403），换完整 Chrome UA 则返回 `401` 或业务错误、IP 继续可用十几发。所以**受保护前缀的第一次请求就必须带全套头**——「先用裸 curl 探一下」的代价是整条出口，而这正是最容易犯的一步。
2. 头部补齐后**响应文案变化**（封禁码 → 业务错误，如「登录账号不能为空」「账号不存在」「账号已被禁用」）= 之前命中的是**头部/反爬规则**，不是 IP 白名单。
3. 响应不变 = 才继续怀疑出口信誉；换一个从未用过的干净出口复测——旧的被封出口无法区分这两者。
4. 成对证据的落点取决于封禁是否永久：**永久封禁时同一出口做不出对照**（第二次请求只会拿到 403），必须用**两条全新出口**、除头部外逐字节相同的请求（一条裸 UA、一条全头）来配对；只有封禁可自解/临时限流时，同出口「无头 vs 有头」才是更强的证据。别把「同出口成对」当成默认做法——它在你最想证明的这一类封禁上根本跑不出来。
5. 头部模板直接抄：真实 Chrome UA（`Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/<ver>.0.0.0 Safari/537.36`）+ `Accept: application/json, text/plain, */*` + `Accept-Language: zh-CN,zh;q=0.9` + `Origin`/`Referer` 指向同站真实页面 + `Sec-Fetch-Site: same-site`、`Sec-Fetch-Mode: cors`、`Sec-Fetch-Dest: empty` + `X-Requested-With: XMLHttpRequest` + 业务 `Content-Type`。缺 `Origin`/`Referer` 会单独触发另一套反爬规则。
6. **静态首页干净 ≠ API 干净。** 反爬规则按路径分组，首页 200/135B 只能证明静态层没封；判断某条业务前缀是否可用，必须用带全套头的那条前缀请求本身（空 body 即可）去读业务错误码。这一条同时消掉了「先花一发探活、再花一发真打」的浪费——探活与首攻合并成同一发。

推论：一个出口跑挂之后，别把「所有出口都 40000」当成全局结论——封禁是**逐出口累积**的，先确认该出口是干净出口。

## 验证码门：真风控 vs 部署事故

后端要 `captchaKey/captchaCode` 时，先分清三种情况再决定要不要上 OCR：

1. **前端能取图** → 真验证码，走 OCR/打码。
2. **前端取码是写死的桩**（`function Qa(){return Promise.reject(Error("...验证码接口尚未接入"))}`）→ 后端开了开关、前端没接，**所有用户注册全挂**。这是 P1 可用性事故，不是你要绕的墙。
3. **字段名对不上**（`captcha` / `captcha_code` / `captchaCode`）→ 报「验证码错误/已过期」，问题在参数名。

判定证据链：
- 伪 key → `验证码已过期`：校验链在线，缺的是**合法 key 来源**，不是参数错。
- 把 `/captcha`、`/verify/captcha`、`/public/verify/captcha`、`/<realm>/auth/captcha` 扫一遍全 401/不存在 → 没有签发口。
- 换 3 个不同 ASN（Tor / 云代理 / 本机直连）结果一致 → 全局配置，不是你被针对。
- 同一端点一小时前还裸奔、现在要验证码 → 配置漂移，不是补丁。
- 顺手看对称性：注册要验证码≠登录要验证码，存量账号往往还能登，别把「注册挂了」写成「站点进不去」。

汇报口径：写成「注册功能 100% 不可用（P1）」并附前后对比，不写「验证码把我挡住了」。

## 现代 Spring Security：别在路径穿越上耗时间

`permitAll` 前缀（如 `/platform/auth/**`）看着可以用路径混淆劫持，实测全部在 Tomcat 层被 `StrictHttpFirewall` 砍掉：

- `..;/`、`%2e%2e`、`..%2f..%2f`、`..%252f..%252f` 全部 `400 Bad Request`，且响应里回显 `path`。
- 因此「安全链按前缀放行、MVC 归一化到别的路由」这条路在现代 Spring Boot 上不成立，**一次 400 就收手**，不要换十种编码重试。

分层指纹（同一 host 上按响应体认层）：

| 响应 | 层 |
|---|---|
| `{"code":30000,"message":"Full authentication is required..."}` | Spring Security，需要 token |
| `400` + `{"status":400,"path":"..."}` | StrictHttpFirewall |
| `{"code":40000,"message":"当前IP...永久封禁"}` | 应用自定义反爬/封禁 |
| `405 Not Allowed` + `Server: nginx` | **打错 vhost**（该 vhost 只做静态 SPA，POST 不转发） |
| `502` + `Server: openresty` | vhost 存在，上游服务死了 |

## vhost 发现：000 / 502 / 200 的三层语义

同一 IP 上所有 `*.domain` 常被 A 记录指过来，用 `curl --resolve <host>:443:<IP>` 逐个试 SNI：

- `000` + 连接失败 = **TLS 层拒绝**（`ssl_reject_handshake` / 无该 vhost）⇒ 这个子域在边缘不存在，别记成「服务挂了」。
- `502` = vhost 配好了、**上游死了**。这是「待复活入口」不是死路：记下 host，隔一段时间复测；CI/管理面板复活即等于新入口。
- `200/401/403` = 活的，正常继续。

**每批必须带一个已知活的 vhost 作对照**（同一个 `--interface`、同一批）。全部 `000` 时：对照也 000 ⇒ 隧道/出口坏了（传输层），不是全部子域不存在；对照正常 ⇒ 这批否定结论才可信。

## 汇报口径

先一句结论（「被边缘拦截，未打通」/「应用层不存在」），再给三层证据（基线、被拦、body 通道）。不要用「下一步我去试 X」收尾，也不要把 nginx 404 写成模块缺失。
