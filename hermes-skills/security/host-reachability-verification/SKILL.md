# 主机可达性与探针可信度验证

判定「这个 IP / 端口还活着吗 / 能不能通」时，**最大的风险不是测不到，而是采信了假阳性**。
本技能给出一条固定判定链：**先直连 → 再分类 → 最后才上多出口**，以及每一层的可信度陷阱。

## 何时用

- 「这个 IP/域名还活着吗」「这个端口开着吗」
- 经代理 / CDN / 中间层探测目标，结果看着可疑或与预期矛盾
- 要写探测、健康检查、监控报警类脚本
- 报告里要写「目标已下线 / 端口关闭 / 被墙」这类结论之前

## 核心纪律（永远适用）

1. **简单测试先做。** 能直连就不要先搭多出口 / 代理基础设施。
2. **`有响应` ≠ 目标可达。** 中间层可能拿自己的页面冒充目标。
3. **探测无效 ≠ 目标否定。** 得不出结论就明说，不要二选一硬判。
4. **没验证过会响的报警器等于没有报警器。**

## 一、判定顺序：先直连

秒级出结论，先用这个：

```bash
nping --tcp -p <port> -c 4 --delay 500ms <IP>   # 发4收0=被DROP；收到RST=closed
nmap -sS -Pn -p <port>,80 --reason -T4 <IP>      # --reason 打 no-response / reset
nc -zvw3 <IP> <port>                             # 超时 vs 秒拒，两者结论完全不同
```

**只有在直连结论不足以回答那个具体问题时**，才上多出口 / 代理。

**多出口只能回答一个问题：「是不是只封了我这个源 IP？」**
它**回答不了**「这个端口上有没有服务」。而且多出口结论**比直连更不可信**（见第三节）。

> 先搭多出口再回头补直连，会白烧大量时间，而且中间层的假阳性会污染结论。

## 二、端口状态三分类（别把 filtered 当 closed）

| nmap 状态 | 含义 | 能推出什么 |
|---|---|---|
| `open` | 有服务监听 | 端口开 |
| `closed` | 回了 **RST** | **主机活着**，但该端口无监听 |
| `filtered` | **零响应** | 包被防火墙 / 安全组静默 DROP |

**`closed` 是「主机活着」的铁证** —— 死主机的 TCP 栈不可能回 RST。
判「IP 死活」时，扫一个大概率无服务的端口（80/443）拿 RST，**比 ping 可靠**
（ICMP 常被策略性丢弃，ping 不通 ≠ 主机死）。

### 云上安全组画像（对比同主机多端口反推规则）

云厂商默认 DENY（AWS 安全组 / 阿里云 ECS 安全组）。所以：

- 端口 `closed` → 安全组**放行**了（包到了主机，只是没人监听）→ 存在对应 allow 规则
- 端口 `filtered` → 安全组**没放行**，或规则限定了**源 IP 白名单**

**推论**：「某端口 filtered」通常是「**没有 allow 规则**」或「白名单不含我」，
**不是**「服务下线了」。报告里别把 filtered 写成「服务已关闭」。

## 三、探针可能撒谎（最危险的一类假阳性）

### 症状

经代理 / 中间层探测时，中间层可能**压根没连目标**，而是把自己的页面当成目标响应返回。
实测形态：对目标的 `80(closed)` / `443(closed)` / `<目标端口>` / **`9999`（根本不存在的端口）**
**全部返回「有数据」**，内容里 `Server: squid/...`、`REMOTE_ADDR` 恒等于**中间层自己的 IP**。

### 铁律

**`CONNECT 200` / 「有响应」≠ 目标可达。**
中间层对**任何**端口（含不存在的端口）都回 200 时，它给出的**全部结论作废**。

### 对照组（必做，成本极低）

拿同一个中间层去连**已知必然不可达的端口**（目标的 80，或不存在的 9999）：

- 「死端口」也返回数据 → **中间层撒谎，本次全部结论作废**
- 死端口无数据、目标端口有数据 → 中间层诚实，数据可信

> **响应内容 md5 有微小差异不构成证据。** 差异常只来自 `REQUEST_URI` 里带的端口号；
> 关键字段（Server / REMOTE_ADDR / 服务 banner）完全一致就是撒谎的铁证。

### 响应归属校验

拿到响应后必须校验「这是谁回的」：

- 响应里的 `REMOTE_ADDR` / `SERVER_ADDR` / 主机名等于**中间层自己的地址** → 假响应
- 多个不同出口的响应**互相矛盾** → 至少一个假的，全部降级，**不可择优采信**
- 拿不准就以**本机直连**为基准，**不以中间层为准**

现成脚本：`scripts/probe_control_test.py`（多中间层 × 多端口交叉对照，自动判谎）。

## 四、写探针 / 监控工具时的正确性纪律

### 1. 失败路径绝不能返回成功码

写协议探测工具时，**每个分支都要有独立的哨兵码**。
反面案例：SOCKS5 探测里「代理不会说 SOCKS5」的认证失败分支被写成返回 `code=0`，
而 `0` 在 SOCKS5 协议里正是「连接成功」—— 于是「这代理是 HTTP 代理、根本不是 SOCKS5」
被统计成了「目标端口开放」，直接产出错误结论。

**规则**：结果至少分三类，**永不混用** —— `成功` / `目标否定` / `探测无效`。
`探测无效` 必须自成一类，且**不得计入成功**。

### 2. 报警器必须验证它会响

写完报警逻辑后，注入一个**必然触发**的假输入，验证三件事：

1. 第一次不报（防抖阈值正确压制）
2. 第二次报（阈值正确突破）
3. 持续处于报警态时输出**仍然稳定**（不会每轮重复骚扰）

### 3. 防抖：连续失败 N 次才判定

免费 / 不稳定资源经常瞬时失败（502 / 521 / 超时）。
单次失败即报警 = 狼来了，几次之后报警就被无视。
用**连续计数（strikes）**判死，并把计数**持久化到状态文件**。

### 4. 门控型监控要求确定性输出

若监控脚本用于「输出未变则跳过后续处理」的门控模式，
输出必须**严格确定性**：不带时间戳、不带会波动的计数。
否则每轮都被判定为「变了」，门控完全失效。

## 五、原始 socket 抓包的两个噪音源

1. **ICMP 必须校验回包源 IP。** 原始 socket 会收到主机上**所有** ICMP 流量，
   拿到的第一个回包未必来自目标。实测踩过：目标零响应，却收到一个来自**完全无关 IP**
   的 ICMP 回包 —— 不校验源地址就会误判「目标存活」。**校验通过才算证据。**
2. **非常规 header 名会被 HTTP 客户端丢弃。** 某些设备把型号放在**响应头名**上
   （形如 `PDVR M800: 1`）—— 这是非法 header 名，`requests`/urllib3 会直接**丢弃**，
   只用 `r.headers` 永远匹配不到。必须用**原始 socket 读响应头块**才能命中。

## 六、结论怎么写（诚实形态）

- 探测无效 ≠ 目标否定。**得不出结论时明确说「得不出结论」**。
- 跨出口结论不可信时，如实写「中间层撒谎，此路结论作废」，**不要挑一个顺眼的结果报**。
- 「filtered」写「**被防火墙静默丢弃（无 allow 规则 / 白名单不含我）**」，
  不写「服务已下线」。
- `closed` 可以拿来反证主机存活，写进结论时把「主机活着」和「端口没开」分开表述。

## 缺失 bind / 声明式端口不能证死（2026-10）
- 只看 TCP 连通不够：服务监听声明里 `bind` 缺失只代表没绑定到该地址，不代表服务不在
- 多协议端口（如 8081 同时 HTTP/WS）要用 HTTP 与 WS 两种方式各验一次
- `api=000` + `web=200` = 中间层只放行网页面，别写“接口不存在”
- 结论层级：TCP 连通 < 应用层响应 < 业务数据回包；只有第三层能写“确认可用”
