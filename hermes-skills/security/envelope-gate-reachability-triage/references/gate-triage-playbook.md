# 闸门判定表 · 抓包配方 · 分栈矩阵

## 1. 「恒定响应」实测判定表（典型形态，换成你的目标同样成立）

```
不带加密/签名头   POST /<real>.js      → 200 {code:401 认证失败}     ← 闸门被跳过，已到框架鉴权层
带加密/签名头     POST /<real>.js      → 400 Invalid encrypted request
带加密/签名头     POST /<real>;x=.js   → 400 同字（字段/时间窗/签名头试遍均同字）
带加密/签名头     POST <平台自身新鲜信封> → 400 同字                    ← ★决定性：平台自己也解不开
无加密头          GET/POST 真路径      → 恒 400（该路径强制加密）
```

⇒ 当**平台自身产物**与**乱码**同字，该 400 与「信封正确性」无关，任何继续调参都是零信息量。
⇒ 不要以「400 vs 401 的差异」推断信封对错：这两个响应往往分属「闸门层」与「鉴权层」，与密码学正确性无关。

## 2. 抓「平台自己的产物」配方

1. CDP `Network.enable`（**不要** `Fetch.enable`）。
2. 让前端自己发请求：伪造它依赖的宿主环境（宿主对象 + URL 参数）通常在页面挂载时即发请求；
   若前端有「非宿主环境不发」的分支，就补全宿主特征对象，而不是手写签名。
3. 收 `Network.requestWillBeSent`，按目标 API 主机过滤，落盘 `url / method / headers / postData`。
4. 客户端报错（挑战页 / CORS）**不影响抓包**，产物照样到手；注意可能会看到「带令牌重试」的第二、三轮——那是 WAF 注入的令牌被复用到同一请求上。
5. 投递时与乱码对照同发；**分钟级内**完成，避免与时间窗混淆。

## 3. 姊妹应用分栈矩阵（同平台多环境）

| 形态 | 指纹 | 带 body 的 POST 响应 | 打点 |
|---|---|---|---|
| 老应用 | JSP/JFinal；根路径 `My JSP 'index.jsp' starting page` + `<base href>` | **原生 404**（框架 404 页，长度随路径变） | **无闸门 ⇒ 静态后缀形态可直接带 body 打真接口** |
| 新应用 | Spring Boot / 权限框架；根路径 JSON 401 | `400 Invalid encrypted request` | 先过闸门才有得谈 |

⇒ 摸到任一主机的闸门后，**必须把姊妹主机逐个用带 body 的 POST 探一遍**，不要假设全平台同构。
⇒ 姊妹主机的 context-path 常从默认页 `<base href>` 或 404 页里直接读出。

## 4. 收线判据（别再耗轮次）

同时满足即判外部不可达，收线换面：① 网关对一切带 body 的真路径请求挑战（唯一过法是静态后缀形态，而静态形态又被闸门当静态资源处理）；② 闸门连平台自身新鲜产物都恒定拒绝。

换面顺序：同平台姊妹主机/环境 → 移动端/APK（拿完整 API 面）→ 开放平台/回调面 → TG bot/客户端面。

## 5. 交付纪律（本用户偏好）

- 判死后**立即说清结论 + 证据**再换面，不要在同一堵墙上默默多跑几轮；长时作业要主动报进度（已完成/进行中/下一步）。
- 每个结论附可复现的最小命令与「原始字节/状态码/长度」，不写无证据的推测。
- 资产面（CT 日志 + DNS 小字典）先摊开再动手；只翻出三五个子域就别再爆破了。
