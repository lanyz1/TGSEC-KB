# 枚举 / 爆破 harness 运维铁律

面向「确认名单 × 口令表」的定向爆破，以及大字典枚举。都是被配额和限速教训出来的形状。

## 1. 限速记账键 = X-Forwarded-For，逐发轮换

- 不带 XFF：2400 组合中约 95% 返回「操作频繁请10分钟后重试」，只有 78 发真正到达应用层。
- 逐请求注入随机 XFF（`11-210.1-254.1-254.1-254`）：频繁=0，有效率达 94%+。
- 结论：逐请求随机 XFF 是必备，不是优化。
- ★ **例外：登录端点本身绝不可带 XFF**（会被路由进 vhost/令牌中间件，整轮零覆盖）；同理 `X-Forwarded-Host` 只用于非登录的管理端点。改一个头之前，先确认影响的是限速记账还是路由。

## 2. 出口清单因主机而异，不要跨主机套用端口表

- 同一台跳板机的 SOCKS 端口表不能套到另一台：端口不存在时每请求卡满超时，整批跑数小时不出结果。
- 纪律：先逐出口健康探测（单请求打一个轻量端点，8s 超时，判 200/000），**只喂活出口**；脚本一律带 `--connect-timeout 4 -m 12`。
- 同一主机同一时刻**只跑一个投递任务**，并发多个会互相冲突（日志全空、任务不动）。

## 3. 响应三态判读（000 / 502 / 空）—— 决定结果可信度

- `000`（连接失败/超时）= 该出口死或被烧穿 ⇒ 换口。
- `502 Bad Gateway`（CDN 页）= **目标在限流，不是我方失败** ⇒ 组合未验证，必须重试，绝不能计入「口令错」。
- 空响应 = 同上，走重试。
- 判据：同出口 `https://www.gstatic.com/generate_204` 得 204 + 目标 502 ⇒ 目标限流；两者皆失败 ⇒ 出口坏。
- 定量：并发升到 4 口 × 8 线程后，502 计数从 28 涨到 113/口，四口同时被限。

## 4. 带重试的 harness 形状

- 共享 `collections.deque` + `threading.Lock` 做工作队列，元素为 `(账号, 口令, 已重试次数)`。
- 命中判据写死（如响应含 `merchant_token` / `"code":1`）→ 命中行 append 到远端 `<tag>_hits.jsonl`。
- 明确失败（含「不正确」等）→ 计为真失败。
- 其余（502/空/未知）→ `retry<2` 则重新入队交给别的 worker；否则记 OTH 留人工复核。
- 心跳线程每 25s 追加 `剩余/命中/失败/重试/OTH` 到远端 log：投递器只在进程结束时回吐 stdout，进度只能靠 log 读。
- 组合排序用**口令外层、账号内层**（`[(u,p) for p in PW for u in SHOPS]`）：最高概率的口令先过全部账号，命中来得最早；已到手的账号从表里剔除，别浪费配额复验。

## 5. 跳板机投递陷阱

- 投递器只上传显式指定的文件；脚本要「上传+后台拉起」就写成自分离模式（`script.py bg <args...>` → 内部 `setsid nohup` 重启）。
- ★ 自分离必须带全参数：`tool host sw.py bg <port> <shard> <nshard>`；写成 `bg` 后面不带参数，重启实例零参数启动 → `IndexError`，脚本在真正开打前就退出（看起来「已启动」其实什么都没跑）。
- 脚本内把进度同时 append 到远端 `/tmp/<tag>.log`，再用第二次独立调用 tail 读；清理用远端 `pkill -f <脚本名>`。
