## Next.js dev 运维（非代码 bug）
- **Jest worker 崩溃**：首次编译新路由 → 500/页面卡死/端口占用无响应。**2026-08-05/06 实测确认：改组件/CSS 触发重编译同样会崩**（本周已 9+ 次：S4 详情页编译 1106 modules、S5 物流页、AppleSelect/LanguageSync 修改、删 17TRACK 提示句、资金中心验证、用户访问 funds 时都崩过，日志 `[Error: Jest worker encountered 2 child process exceptions, exceeding retry limit]` + `write EPIPE` uncaughtException → dev exit -15）——**tsc EXIT 0 不代表 dev 不崩**（类型没错误但 Next dev 在 Windows 上重编译会挂）。表现：browser 打开页面显示 Next.js Runtime Error 对话框；或进程从 process list 消失（`process(action='list')` 空）但端口残留。**用户 2026-08-06 拍板：继续 dev 模式，崩了自动重启（勿主动建议换 pnpm build+start 生产模式）**。恢复：杀 3000/3001 残留 PID → 重启 `pnpm dev`（background + watch Local/EADDRINUSE）→ sleep 18 + curl 200 验证 → 重新登录导航。杀端口重启即恢复，不是代码问题。**用户说"页面进不去了/dev噶了"时：先 `process(action='list')` 查进程是否存活（可能已崩）→ 崩了按上述流程重启 → 用浏览器登录复测（curl 无 cookie 只会 307 到 login，不是页面 bug）**
- **端口冲突 3001**：旧 dev 进程僵死但仍占 3000 时，新 `pnpm dev` 会静默跑 **3001**——此时 3000 上的旧进程给 500/空页，且新进程日志显示 `Port 3000 is in use, using 3001`。必须先杀干净 3000 的监听进程（`netstat -ano | grep :3000` → `taskkill /F /PID`）再重启 dev，否则验证全部打到坏端口上
- **dev 进程被杀后端口残留（2026-08-05 "没更新到dev吗"根因）**：dev 进程可能被静默 kill（`process(action='poll')` 显示 `status: exited` / `termination_source: process.kill`），但旧监听进程还占着 3000/3001——页面照常返回 200（能打开）却**跑的是旧代码**，用户看到"没更新"。诊断三步：① `process poll` 看 status 是否 exited ② `netstat -ano | grep -E ":300[01].*LISTEN"` 看残留 PID ③ **两个端口都杀**（`taskkill /F /PID`）→ 重启 dev → curl 验证。**用户说"没更新到 dev"先查 dev 进程死活，别假设是热更新/浏览器缓存问题**
- **⚠️ watch_patterns \"Error\" 误报（2026-08-06 实测）**：dev 后台进程配 `watch_patterns: [\"Error\"]` 会匹配**编译中间态**——改文件瞬间 Fast Refresh 触发 SWC 报错（如 `Expected '</', got 'data'`）或临时 500（`GET /xxx 500`），**几秒后自动编译成功恢复**（日志随后全 200）。此时**不要杀进程重启**——先 `process(action='log')` 看最新请求是否已恢复 200，恢复了就是中间态误报。watch_patterns 的 Error 匹配对 dev 模式太敏感，只在真正连续失败（首页 000/进程消失）才走杀端口重启流程。**用户报\"页面进不去/404\"时先看 dev 日志里的真实 URL**：`GET /seller/<EMAIL-REDACTED>%EF%BC%89 404`（%EF%BC%88=全角括号）说明是**用户手动把邮箱拼进 URL**（`/seller/account（email）`），非代码 bug——正确地址不带邮箱，直接告知正确 URL 即可，别去改代码
- **tronscan 401**：本地无 TRONGRID_API_KEY 时 fallback Tronscan 公开接口被 401；生产配了 key 走 TronGrid 不受影响。本地可忽略
- **⚠️⚠️ Prisma dev/prod 双 schema（2026-08-06 df7baad 重大基建，改 schema 前必读）**：schema.prisma provider=**postgresql**（生产真源，2026-08-01 迁移），但本地 `prisma/dev.db` 是 **sqlite**。**dev 运行中 `prisma generate` 必 EPERM**（query_engine DLL 被 dev 进程占用，node_modules/.pnpm/...rename 失败）——所以迁移后 dev 一直用**旧 sqlite client** 跑 dev.db，generate 从未成功过。**一旦杀掉 dev 再 generate 成功 → client 变 postgresql provider → dev.db 连不上（\"URL must start with postgresql://\"，node 直查 PrismaClient 也报错）**。**方案（已落地）**：`scripts/make-dev-schema.mjs` 从主 schema 复制 + `provider=\"postgresql\"`→`\"sqlite\"` 生成 `prisma/schema.dev.prisma`（模型自动同步）；package.json 加 `db:gen:dev`（make + generate --schema dev 版）/ `db:push:dev`（make + db push --schema dev 版）。**流程**：改 schema.prisma（加模型/字段）→ **必须停 dev**（kill + 杀 3000 端口）→ `pnpm db:gen:dev && pnpm db:push:dev`（生成 sqlite client + 同步 dev.db）→ 重启 dev → `node -e`/mjs 直查新表确认存在。**生产部署前必须 `npx prisma generate`（主 schema postgresql）再 build——两个 client 不能混**。**验证 schema 改动后 client 正常**：`node` 跑 `new PrismaClient()` 查 store.count()（postgresql client 连 file: URL 会报 P1012，sqlite client 正常）
