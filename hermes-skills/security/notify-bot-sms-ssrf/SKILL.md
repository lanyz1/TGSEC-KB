# 通知机器人「验证码查询」SSRF

商城/告警类 Telegram 机器人的接码查询（`/phone`、`号码----链接`、回复“验证码监控中”）通常由后端**定时轮询用户提交的 URL** 抓短信码。若对 URL 限制不严，就是服务端全回显 SSRF，请求源 IP 即目标服务器本身。

## 识别与确认

- 机器人回复形如：`用法: /phone 号码----查询链接` / `或直接发送: 号码----https://...`
- 发金丝雀 URL（自己可控的日志端点或写入型 API），看是否回源；轮询间隔常见 15s，持续数分钟，可反复触发。
- 在自己的 access.log 里确认来源 IP = 目标服务器，即坐实。

## 校验绕过（302 跳转）

- 常见校验只查**初始 URL**：`file://`、`http://127.0.0.1/`、内网 IP 直连被拒（“仅支持公网 http/https”）。
- 绕过：自己公网服务器加跳转端点（nginx）：
  ```nginx
  location = /r { return 302 $arg_u; }
  ```
  请求 `http://<own-ip>/r?u=http://127.0.0.1:<port>/<path>` —— 初始 URL 合法，客户端默认跟随 302 进内网。
- 内网探测：有回显 = 端口有 HTTP；只有“验证码监控中”无后续 = 连接失败 / 非 HTTP 服务。
- 请求从 127.0.0.1 发出，天然绕过**只按来源 IP 封禁**的 WAF（数据中心/Tor 段常被 403 拦，住宅出口才过）。

## 回显限制

- 消息长度截断（实测 ~4KB）：超长响应直接不转发。小文件/小响应可读，20KB+ 的应用动态页读不到——需要大文件时找分段或小响应面。
- 回显内容可能被当成“验证码”原样发出，先用小响应（如 404 页）校准回显行为，再读目标。

## 命中验证纪律（通用，防代理缓存假阳性）

- 经代理/缓存拿到的“200 命中”必须先复测：`Cache-Control: no-cache, no-store` + 唯一 `?r=<random>`，要求 body 长度/哈希与已知页面不同。
- squid 类缓存代理会把缓存过的登录页回给任意路径，一次爆破可伪造出几十个“短前缀命中”（同长度 body + `Server: nginx`），复测时全部变回真实 404。
- 每个命中至少经 2 个独立出口、无缓存复测一致后才写入 hits 文件。
