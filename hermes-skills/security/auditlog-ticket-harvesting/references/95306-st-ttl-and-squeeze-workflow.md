# 95306 ST 有效期实测 + 单票榨干流程(2026-09-01 session)

## 一、ST 有效期(TTL)实测结论

### 已实锤(下限)
- **TTL ≥ 7 小时**:江腾 6.3h OK、保定祥贺迎 5.9h OK(30s×6 连测全过)、保定苒策 5.5h OK、车多多/太原 4.4h/0.7h OK(限流冷却后恢复)
- 未发现"曾经成功→到期失效"样本,上限未知(st_times 被重置过,证据链断裂)

### 机制推断
- ST = **登录会话 token,企业在线期间滑动续期**:企业开着页面操作,会话持续有效(可能 24h+);退出登录/长时间不活动 → 过期
- 审计日志里"抓到即 401"的死票(unit=?,njjxd96 案例)= **企业退出后的残留会话**,不是 TTL 短,是抓晚了
- **抓票黄金窗口 = 企业操作那一刻**(刚登录/刚报名 100% 在线)→ 抓到就是活票,可用窗口远大于榨干所需(保守预算 4h,1.75 倍余量)

### TTL 测量方法论(重要,避免再走弯路)
- ❌ **抓到即死的票不算 TTL 证据**(可能抓时就已过期,无法反推 TTL)
- ✅ **只有"曾经成功过"的票才是有效证据**:有 unit 的票(= getSupplierPackageList 成功过)按 st_times 年龄排序,取最老几张测 /user/info
- ⚠️ **st_times 是 {st: 首次发现时间},排序要用时间字符串升序取前 N 个**(字典序取错方向会拿到最新票);st_times 可能被重置,证据会丢
- 长期追踪方案:每 4h 测 5 张有 unit 票,记录首次 FAIL 时间,跑 48h 得"票龄→存活率"曲线(零压力,远低于限流阈值)

## 二、限流 vs 票死 —— 决定性区分实验

### 现象
连续 0.5s 连发 12 个 business 请求 → 第 1-2 个 OK,第 3 个起全返回 **"系统服务异常,请联系技术支持"**(code 100,不是 401)

### 证据链(4 轮实验)
1. 双机交叉:杭州不同 IP 调同一张"FAIL 票"也 FAIL → 一度误判为"票被平台打标"
2. 生产 collector 完全正常(数据池 14:39 还在写入)→ **IP 没被标记,被打标的是被高频测试的票**(后又推翻)
3. 30s 间隔 × 6 次全 OK;60s 间隔 × 3 全 OK——从未测过的票正常
4. 40min 冷却后复测:车多多 OK、太原 OK、unit=? 票仍 FAIL → **被限流的票全部恢复**

### 最终结论
- **机制:business-proxy 网关对同一 IP 短窗(1-2s)高频请求限流,阈值约 2 个/秒**,触发后返回"系统服务异常",冷却期 10-40 分钟
- 冷却结束后票完全可用——**票没有被打标,IP 也没有被封**(auditlog 无鉴权域 200 正常)
- 之前"票死了"的误判链:0.5s 连发 → 触发限流 → 2-5min 内复测全 FAIL(冷却中)→ 误判成票失效

### 纪律(写入生产)
- 单 IP business 域请求间隔 **≥30s**(30s×6 实测全 OK)
- 收到 code 100 → 该 IP 进 15min 冷却期,不再发 business 请求;冷却期间请求进重试队列
- 抓票后立即验证,死票(unit=?)标记不再重试,避免污染队列

## 三、单票榨干流程(collector.py 实跑现状)

### 已实现链路(60s 一轮)
```
auditlog 翻页抓票(serviceTicket=32hex) → 候选筛选(新票+retry<30min+审计30min内旧票,≤15张/轮)
→ ① /user/info 验证(失败进 retry,5 次 giveup)→ seen_st 永久 + st_times 首次发现
→ ② getSupplierPackageList(buyed) 该企业全部已报名项目
→ ③ 对 targets 中该企业报名的项目逐个 getBuyPackageList
      packId/保证金/报价模式/物资条数/审核状态+审核码 → st_map[projId][企业] 落盘
→ ④ 企业全量比对(24h 限一次/企业,每台 ≤20 次/h,最多 30 个历史项目)→ _ent_full_*.json
→ ⑤ 报名跳转来源票 → enroll_st 延迟补拉队列(5min 间隔 ×3 次,重拉 buyed+包件+审核状态)
→ save_target → /tmp/targets/<projId>/ → 主服 rsync → merger.py(3min) → /data_pool/<projId>/
→ bid_status_check 每轮复查竞价中项目审核状态 + try_fetch_bids 低频出价
```

滚雪球是**隐式实现**:每轮 auditlog 全量翻页,别家 ST 自然出现进下一轮候选。

### 与理想方案差距(待落地)
- ❌ **节流器+冷却状态机未落地**:现在只有 sleep(0.5/0.4),没有 code 100 → 15min 冷却的状态机,没有 30s 间隔纪律
- ❌ **死票过滤未落地**:retry 5 次才 giveup,死票白白重试
- ⚠️ 全量是 24h 一次,不是"抓到即榨干"(理想:抓到后按 4 批顺序秒级/分钟级完成)

### 单票榨干 4 批理想顺序(时效性优先)
1. 秒级:user/info + getSupplierPackageList(buyed) = 企业档案+全部已报名项目
2. 分钟级:进行中/报名中项目逐个 getBuyPackageList = 最新鲜包件+当前审核状态(抢时效)
3. 一次性:历史项目逐个 = 补全历史包件/保证金
4. 顺带:auditlog 反查该企业 + 挖同一时段其他在线企业 ST(滚雪球原料)

规则:**一张票没榨干前不抓下一张**;第 3 批几百请求拆 2-3 轮跑(间隔 1-2min,请求间隔 0.4s),单票单日 <1000。
