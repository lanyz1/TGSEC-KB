# 95306 数据采集链路限制与补全(2026-08-29 会话实录)

## 核心限制:ST TTL 30 分钟 → 历史报名企业拉不到包件明细
- getBuyPackageList(projId, st) 返回的是**该 ST 企业在该项目的报名包件**——自己的视角,不是全量。
- 审计日志里的 ST = 操作时刻的(30min TTL):**只有"当天活跃报名企业"的 ST 有效**。
- 报名截止早的项目(如 8/19 截止的武汉局69次)企业 ST 全过期 → 实时接口拉不到任何企业 → 项目企业数 0。
- 解释"同一项目时有时无/像幻觉":不同时间点审计出现不同企业 ST,能否拉到取决于当天谁在操作。

## 数据源分层(补全决策表)
| 数据源 | 粒度 | 范围 | 用途 |
|---|---|---|---|
| getBuyPackageList(实时) | 企业→packId | 仅当天活跃企业 | 实时报名+包件明细+审核 |
| 8515 快照(官方导出) | 项目级(企业名/信用代码/时间) | 8/28 时刻全量,26,977 条 | 补进行中项目企业名单(无包件明细!) |
| 08文件(615,267 条) | 企业→packId→审核(19列) | **只含已结束项目** | 历史全量 |
| 审计票证 | ST | 最近操作 | 换票后拉包件 |

- 8515 部分项目**只有公告行无企业**(无企业报名记录/项目新发)→ 该批项目企业数 0 是数据事实,不是 bug。
- 同名重复公告陷阱:同编号不同公告 → 两个 projId(沈阳82次 08:30 有 15 家企业 vs 09:30 企业 0)——按 projId 精确验证,别按名称。

## 多 ST 池化(提升实时覆盖)
单 ST 只能拉自己报名的项目 → 每轮从审计最新 100 条取 N 个不同企业 ST(常规 15 个),逐个拉全部目标项目;ST 池滚动,多轮累积(merger 侧合并保留) → 覆盖当天所有活跃报名企业。请求率注意 WAF(每轮 ~15×29 请求,0.4s 间隔)。

## 补采机制
- `collect_one.py --pid <projId>`:指定项目直接拉公告包件清单(先按项目名 notTitle 搜公告匹配 projId,翻 3 页兜底,readNoticeInfo 解析包件)→ 解决"采集没采到包件层面"。
- bot 项目详情"🔄 补采包件"按钮 + 管理员 `/repackall` 批量(扫描缺包件清单的 live 项目)。
- 8515 全量补导:按 proj_code→projId 把 8515 企业记录写入 pack_map(项目级,packId=PROJ_LEVEL),merger 合并保留 + `_enterprise_count()` 从 pack_map 统计防覆盖回 0。

## 企业名 dwhz 字段
user/info 返回 dwhz=企业注册自填名(简称/全称/空"?"),同账号不同时刻返回不同(ZZHJHB 曾 "?" 与全称并存)→ 归一化链见 tg-bot-operations references/pix-bot-v8-mobile-dataquality.md。
