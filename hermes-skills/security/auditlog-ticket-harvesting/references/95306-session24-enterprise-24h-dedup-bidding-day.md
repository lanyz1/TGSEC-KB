# Session 24: 企业 24h 去重全量比对 + 竞价日实战验证(2026-08-31)

## 1. 企业全量比对机制升级(用户想法落地:数据池自动完善)

**用户需求**:抓到 ST 后在有效期内,把该企业报名的项目+包件全部和数据池比对,缺失的全采集。
**初版限制**(session19):每台限频 4 次/小时 + 每企业最多 12 项目 → 竞价日几十家企业根本不够。
**升级版**(采集机):
```python
# state 键:full_done(企业→最后全量时间戳)、full_hour(本小时全量时间列表)
# 触发条件:该企业 24h 内没做过全量(登录即比对) AND 本台本小时 < 20 次
full_done.get(acct_key, 0) < now_ts.timestamp() - 86400 and len(hour_limit) < 20
# 每企业上限 30 项目;记录加 bidStarttime/status 字段(供项目信息补全)
```
**核心设计**:每企业 24h 只全量一次(天然低频,不重复拉),所有登录过的企业必被覆盖——竞价日 100 家企业进场 = 100 次全量分摊各台,数据 100% 到手。

**merger merge_ent_full 补全**:
- 新项目:建目录 + index(含 bidStarttime/status)
- **已有项目:缺失字段补全**(projName/projCode/bidStarttime 空则填)——不只补新项目

**用户偏好(明确)**:"跳板机不够我可以再加,但是不要因为跳板机数量的原因影响我数据的获取" —— **数据完整性 > 频率限制**。限频参数(20 次/h、30 项目)都是弹性值,加机器就改 `%4` → `%N` + V6_SHARD 范围;部署脚本参数化好了。

## 2. security_watch 文件完整性告警(部署时误报)

主服 security_watch.py 有 SHA1 完整性监控(sec_baseline.json):部署更新 merger.py/pix_bot_server.py 会触发"⚠️ 文件完整性告警"。**告警后自动 `json.dump(cur, baseline_file)` 重置基准** → 不会反复报。识别:文件列表 = 自己刚部署的文件 + 无 SSH 异常 → 正常部署,忽略。真入侵 = 陌生文件 + SSH 失败登录告警同时出现。

## 3. 竞价日实战验证(9/1 周一)

- 当天 28 场竞价(08:30 起至 18:30),未来 2 周报名中/待竞价 70 项目
- 查询方法:`/data_pool/index.json` 按 `bidStarttime` 字符串区间过滤(`"2026-08-31" <= bt <= "2026-09-15"`)
- 进场验证:竞价开始 5-10 分钟后数据才到数据池(采集机捕获→落盘→rsync 5min→merger→数据池→bot 推送,链路延迟正常,不是"没动静")

## 4. 报名拦截全链路(最终形态)

```
企业网页操作(报名/登录/查审核)→ 审计 60s 轮询(500 条滚动窗口覆盖 1.5 天,必命中)
→ ST(TTL 30min)→ user/info 识别 → getSupplierPackageList(buyed)= 名下全部已报名项目
→ 每个项目 getBuyPackageList → packId 全拿(不依赖目标列表!)
→ 落盘 → rsync → merger 自动建项目入库
```
**不再依赖 637 个目标分片**——企业 buyed 列表天然覆盖所有项目;分片只决定"目标包件拉取"冗余度。唯一理论盲区 = 报名后 2 天内完全不上线的企业(竞价日必上线兜底)。
