# 95306 Session15: ST 死票诊断 + 采集管道静默丢数据修复(2026-08-30)

## 背景
v6 监控系统(4 采集机 + 主服 merger + TG bot)运行中,用户质疑:"朋友在 bot 搭建后登录过,为何包件编号没被拉回?" 排查发现两类问题:① 采集机审计过滤把查看操作全漏掉;② 审计里的 ST 全是历史死票,过期无法利用。

## ST 生命周期事实(实测)
- ST TTL ≈ 30 分钟(bfwz 会话),审计记录里存的 ST 是"操作时刻"的
- 审计记录长期保留(几天),但 ST 过期后拉 `/user/info`、`/supplierPackage/getBuyPackageList` 全部失败
- **审计 = 历史登记簿,不能重建会话**;要拿业务数据必须:用户现在登录(60s 内采集机捕获)或提供账号密码走官方登录链(拉完即弃)
- bot 搭建至今 4 台采集机 seen_st 各 43(审计同源,全局 ≈ 43),100% 尝试利用,成功仅 2 家新企业(pldwsw 合肥日航、XR112233 黑龙江旭荣,10:04-10:05 审计放开后捕获的活票)

## "审计 ST N, 新 0" 的诊断含义
- N = 审计窗口(pageNum×pageSize)内 dedupe 后的票数;新 0 = 全部已在 seen(处理过)
- 持续"新 0" = **系统没有新操作发生**(不是采集挂了)
- 判断依据:seen_st 数量稳定 + state.json 里 last_st 哈希不变
- 采集机 state 文件:`/tmp/v6_state.json`(STATE_FILE),含 seen_st/last_st/targets

## 采集管道"静默丢数据"检查清单(10 项,本次全修复)
1. **审计过滤条件**:`like %redirectEnrollUrl%` 只抓报名操作 → 改为 `like %` 全量(查看/审核的票也要)
2. **审计翻页**:pageNum 1..2 × pageSize 100,满页继续,否则窗口内活跃票覆盖不足
3. **ST 提取正则**:只认 allProject?projName=...&serviceTicket= 格式 → 通用 `serviceTicket=([0-9a-f]{32})`
4. **目标发现翻页**:公告列表只查第 1 页 50 条 → pageSize 100 × 翻 2 页,48h 窗口项目不漏(41→43 目标)
5. **包件解析正则兼容**:`竞卖保证金:人民币([\d.]+)元` → `[竞竞]卖保证金[:：]?(?:人民币)?\s*([\d,]+(?:\.\d+)?)\s*元`(全角冒号/千分位/变体文案)
6. **包件去重策略**:按 packCode 先到先得(缺字段版本覆盖全字段)→ 字段更全优先(保证金/时间非空者胜出)
7. **路径错误**:sub_checker 读 `/data_pool/bid_status.json`(根目录不存在)→ 应为 `POOL/<pid>/bid_status.json`——竞价状态推送因此从未触发
8. **首推抑制**:`if old_st and st and st != old_st` 空→通过不推 → `if st and st != old_st`(审核首次结果也推)
9. **排序反转**:`sort(key=(0 if live else 1,...), reverse=True)` 把 live 排最后 → key=(1 if live else 0)
10. **搜索拆词**:纯子串匹配 "沈阳82"/"武汉局69次" 0 命中 → `re.findall(r'[\u4e00-\u9fa5]+|\d+', k)` 拆词 AND 匹配(名称+编号+pid 拼接 haystack)

## 通用原则
"静默丢数据"三大类:① 过滤/正则太窄(放开+翻页+兼容)② 路径/排序/条件错误(修正)③ 去重/推送策略缺陷(字段完整优先+状态变更即推)。修复后必须用真实数据验证(搜索实测命中数、目标数变化、日志 ST 数变化)。
