## 1. 等保 2.0（GB/T 22239-2019）

现行族谱（**需核对**是否已被新版替代）：GB/T 22239-2019 基本要求（现行）、GB/T 22240-2019 定级指南、GB/T 28448-2019 测评要求、GB/T 25070-2019 安全设计技术要求、GB/T 25058 实施指南。等级 1-5 级（自主/指导/监督/强制/专控保护），三级即"监督保护"。

**十个分类**（技术 5 + 管理 5），另有扩展要求（云计算 / 移动互联 / 物联网 / 工业控制）按对象适用：
- 技术：安全物理环境、安全通信网络、安全区域边界、安全计算环境、安全管理中心
- 管理：安全管理制度、安全管理机构、安全管理人员、安全建设管理、安全运维管理

**测评流程**：定级备案 → 调研与方案编制 → 现场测评（技术+管理，访谈/核查/测试）→ 分析与报告（打分制，含高风险项）→ 整改 → 复测确认。控制点编号形如 `8.x.y.z`，**编号随级别与扩展要求变化，报告里引用前必须在标准原文核对**。

**技术检查清单（安全计算环境控制项，可勾选）**
- [ ] 身份鉴别：两种以上鉴别技术组合，其中一种为密码技术；登录失败处理；远程管理鉴别信息加密传输
- [ ] 访问控制：主体-客体授权、最小权限、权限分离、默认账户改名、无多余账户
- [ ] 安全审计：覆盖每个用户、记录关键操作与结果、审计记录受保护（不可删改覆盖）、留存满足《网络安全法》要求（六个月，《网络安全法》2025 修订版为第二十三条第（三）项）
- [ ] 入侵防范：最小安装、关闭非必要端口/服务、漏洞修补、入侵行为检测与告警
- [ ] 恶意代码防范、可信验证（按级别要求）
- [ ] 数据完整性：重要数据传输/存储的校验或密码技术
- [ ] 数据保密性：重要数据存储保密性（加密）
- [ ] 数据备份恢复：本地备份 + 异地/热备 + 恢复演练
- [ ] 剩余信息保护：鉴别信息/敏感数据所在存储空间释放或清零
- [ ] 个人信息保护：仅采集必要的，禁止未授权访问和非法使用
- 通信网络/区域边界：区域划分、边界访问控制、通信加密(SSL/TLS)、带宽保障、入侵防范、安全审计、恶意代码过滤

**管理检查清单**：制度（策略/制度/规程/审批变更）· 机构（岗位设置、授权审批、合作方管理）· 人员（录用/离岗/考核/安全意识培训/外部人员）· 建设（定级备案、安全方案、产品采购、开发、工程实施、测试验收、交付、服务商）· 运维（环境管理、资产管理、介质、设备维护、漏洞和风险管理、配置管理、密码管理、变更、备份恢复、安全事件处置、应急预案演练、外包运维）。

**现场可执行的核查命令**（来自上游配置安全审计卡，真实命令）

## 4. GDPR / 个保法 关键流程

**ROPA（处理活动记录，GDPR 第 30 条）字段骨架**：处理活动名称｜控制者/处理者与联系人｜处理目的｜数据主体类别｜个人信息类别（含是否敏感）｜接收方/受托方与所在国｜跨境传输机制｜保存期限与删除方式｜技术与组织措施｜对应系统与数据流。

**DSAR（数据主体权利响应）**：权利集合——GDPR 第 15 访问、16 更正、17 删除、18 限制、20 可携、21 反对、22 自动化决策；个保法第四章（知情/决定/查阅复制/更正/删除/解释说明/可携带，死者近亲属权利）。SOP 骨架：受理与身份核验 → 定位数据（含备份、日志、第三方共享副本）→ 导出/更正/删除 → 回复与留证。时限请按现行文本与监管口径确认（GDPR 为 1 个月，可延长 2 个月；个保法未在法条中给出统一天数，**需核对**配套规定与客户承诺）。

**跨境传输（先判断有没有，再判断合法路径）**
- GDPR：充分性决定（第 45 条）→ 适当保障（第 46 条，SCC/BCR）→ 特定情形例外（第 49 条）；配合传输影响评估（TIA）。
- 个保法：第 38 条三条路径——国家网信部门安全评估、专业机构个人信息保护认证、标准合同；第 39 条跨境须告知并取得**单独同意**；第 36 条国家机关处理的个人信息应当境内存储（确需出境须做安全评估）；《网络数据安全管理条例》有进一步要求（**需核对**）。
- 现场核查点：数据流向外（CDN、SaaS、云区域、境外子公司运维账号）；合同里是否夹带"可向关联方共享"；远程运维跳板是否落到境外。

**PIA / DPIA 触发条件与报告骨架**
- GDPR 第 35 条：系统性大规模评估/评分、大规模特殊类别数据、大规模公共区域监控等"高风险处理"须在事前做 DPIA。
- 个保法第 55 条（已核对）：①处理敏感个人信息 ②利用个人信息进行自动化决策 ③委托处理、向其他处理者提供、公开个人信息 ④向境外提供 ⑤其他对个人权益有重大影响的活动——**事前**做个人信息保护影响评估并记录。
- 第 56 条（已核对）评估内容：合法性/正当性/必要性；对个人权益的影响与安全风险；保护措施是否合法有效且与风险相适应。**报告与记录至少保存三年**。
- 报告目录骨架：①处理活动描述与数据流 ②必要性/合法性依据（同意或第 13 条其他依据）③影响与风险（对个人权益 + 安全风险）④已采取措施与残余风险 ⑤结论与审批记录 ⑥复评触发条件（新增字段/新接收方/跨境变化）。
- 泄露通知模板要素：个保法第 57 条（已核对）——信息种类、原因、可能危害、已采取补救措施、个人可采取的减轻措施、联系方式、发生或可能发生的时间；GDPR 第 33 条为 72 小时内通知监管机构、第 34 条高风险时通知个人。事件记录本应保留（便于举证"及时"）。

## 5. CVSS v3.1 / v4.0 + EPSS 优先级与 SLA

**CVSS v3.1**（基准分，来自上游实现，公式与 FIRST 一致）：
`Exploitability = 8.22 × AV × AC × PR × UI`；`Impact = 1 − (1−C)(1−I)(1−A)`；`S:U → min(E+I,10)`；`S:C → min(1.08×(E+I),10)`。分级：9.0–10.0 Critical / 7.0–8.9 High / 4.0–6.9 Medium / 0.1–3.9 Low。用官方库而不是手写：
```bash
pip install cvss
python3 -c "from cvss import CVSS3;c=CVSS3('CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H');print(c.base_score,c.severity())"   # 9.8 CRITICAL
python3 -c "from cvss import CVSS4;c=CVSS4('CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N');print(c.base_score,c.severity())"
```
- v4.0 变化要点：取消 Scope，改用脆弱/后续系统两组 (VC/VI/VA + SC/SI/SA)，新增 AT 攻击要求与补充指标（Safety、Automatable、Recovery、Value Density、Provider Urgency）。**同一漏洞 v3.1 与 v4.0 分数不同**，报告中必须写明所用版本，否则客户无法对齐。

**EPSS**（利用概率，0–1）
```bash
curl -s "https://api.first.org/data/v1/epss?cve=CVE-2023-44487" | jq '.data[0] | {cve,epss,percentile,date}'
curl -s "https://api.first.org/data/v1/epss?cve=CVE-1,CVE-2,CVE-3" | jq -r '.data[]|"\(.cve) \(.epss)"'
```
经验区间（上游分级）：≥0.5 极高 / ≥0.1 高 / ≥0.01 中 / ≥0.001 低；实践中以"是否进 CISA KEV""是否有公开 PoC"为更强信号。

**优先级计算（上游公式，简化但可用）**
- 复合分：`priority = cvss/10 × (1+epss) × (1+asset_weight)`
- 业务风险 0–100：`技术分 = cvss/10×40 + epss×20`；`业务分 = 资产关键性×20 + 数据敏感度×10 + 暴露面×10`
  资产关键性示例：核心支付/资金 1.0、客户 PII 库 0.95、生产 API 0.9、内部 CRM 0.7、测试环境 0.1；数据敏感度：PII/金融 1.0、认证凭据 0.9、内部文档 0.5、公开 0.1；暴露面：互联网 1.0、DMZ 0.8、内网 0.5、隔离区 0.2。

**SLA 与升级（建议值，最终以客户制度为准）**

| 级别 | 条件 | SLA | 动作 |
|:--|:--|:--|:--|
| P0 | CVSS≥9.0 且 EPSS>0.5 且互联网暴露；或进 KEV；或蠕虫型 | 24h | 通知安全负责人→隔离→紧急修复 |
| P1 | CVSS≥7.0 且（EPSS>0.3 或涉敏感数据） | 72h | 紧急工单+责任人+缓解措施 |
| P2 | CVSS≥4.0 且 EPSS>0.1 | 30d | 纳入迭代/常规窗口 |
| P3 | 其他已验证漏洞 | 90d | 批量维护周期 |
| P4 | 误报/不可利用/无业务影响 | 不修 | 标记+定期复查 |

升级规则：有公开 PoC +1 档；进 CISA KEV → P0；资产为域控/堡垒机/核心数据库 +2 档；存在蠕虫传播风险 → P0 并启动应急。
度量 KPI（上游）：P0/P1 SLA 达成率>95%、MTTR P0<24h / P1<72h、积压<100、修复验证率>90%、误报率<20%、重开率<5%。

## Pitfalls

- 条款号是最容易出错的地方：网络安全法 2025 年修订（2026-01-01 施行）导致条文序号后移，老资料里的"第二十一条"已非现行编号；对外交付统一写"标准/法律全名 + 版本 + 条款号（需核对现行文本）"。
- 等保控制点编号 `8.x.y.z` 随级别、扩展要求变化，不要凭记忆写编号；写控制项**名称**永远安全。
- SOC 2 报告是"某时间窗内的控制有效性"，不是漏洞清单；PCI DSS 关注持卡人数据环境范围（CDE），把整站拉进来会误导客户。
- CVSS 高 ≠ 该修：没有 EPSS/KEV/暴露面加权的排序会把客户带偏；反之低分但拿 PII 的漏洞常被漏掉。
- 映射表是"同一控制点"的对应关系，不是"通过一个框架即满足另一个"；客户拿等保三级报告去主张 ISO 27001 合规时，要明确说清差异。
