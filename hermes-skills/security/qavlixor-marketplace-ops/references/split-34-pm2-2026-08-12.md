## PM2 多实例进程内缓存不同步 → "改了刷新不变"(2026-08-12 实测,重大)
**症状**:卖家端改库存(行内/批量)或改价,PATCH 返回 ok 且前端提示成功,刷新/重进页面仍显示旧值。**本地单实例 dev 复现正常,生产必现/概率复现**——用户报"改了不变/还是不对"先看本节再怀疑代码。
**根因**:生产 PM2 fork **4 实例**(端口 3000-3003,nginx 轮询),`lib/product-repository.ts` 的 `catalogCache`(60s TTL)+`catalogInflight` 是**模块级进程内变量,每实例独立一份**;`invalidateProductCatalog()` 只清**当前进程**缓存。PATCH 命中实例 A(更新 DB+清 A 缓存)→ 前端 router.refresh()/后续请求轮询到 B/C/D → B/C/D 在 60s TTL 内返回旧 catalog → 显示旧库存(如 19998=9999×2 双 SKU 商品)。
**排查顺序(先证真源再疑缓存)**:① paramiko 直查生产 DB 该商品 variants.stockQuantity 是否已变(变了=写入成功,问题在缓存层);② 本地端到端 PATCH 复现(见 `references/stock-change-multi-instance-cache-2026-08-12.md`);③ `pm2 jlist` 确认 fork 多实例 + grep catalogCache 确认进程内缓存;④ 生产 `$transaction`+末尾 throw 回滚模拟 syncProductToPrisma 的 upsert,验证 DB 层写入不报错(零副作用)。
**修复(已实施 ✅ commit edb07f3,2026-08-12,用户拍板方案 A 版本号广播)**:① schema 加 `CatalogVersion` 表(固定单行 id=1,`version Int` 递增);② `invalidateProductCatalog()` 改 async:清本地缓存 + `bumpCatalogVersion()`(`upsert where id=1, version increment 1`——所有实例共享同一 DB,写后全实例感知);③ `loadPrismaCatalogCached()` 读时比对 DB 版本:变了即使 TTL 未到也重建;**版本读失败返回 null → 降级纯 TTL 判断**(防 prisma 抖动时每次请求全表重建雪崩);④ **调用点必须 `await`**(PATCH/DELETE/POST 路由 + lib 内部 syncProductToPrisma/deleteProductFromPrisma 全改)——不 await 则响应先返回、前端 refresh 到达时版本还没递增,问题依旧。**验证(本地模拟多实例)**:外部 node 进程直接 UPDATE 变体库存 + bump 版本号 → 60s TTL 窗口内立即 GET 页面必须读到新值;无变更时连续 GET 缓存仍命中(不退化)。副作用:sync 内部+路由各 bump 一次版本跳 2(无害,Int 上限 21 亿)。部署时 deploy.py 自动 db push 建表。生产 27 个 19998 库存商品为拓竹铺货正常数据(9999×2),无需改数据。完整实录/复现配方见 `references/stock-change-multi-instance-cache-2026-08-12.md`。
**⚠️ 版本号广播上线后暴露的第二个坑:写路径禁全量 catalog(2026-08-12,commit a101ee3)**——批量改库存/改价(55 项)点应用后按钮变灰 5-10 分钟"卡死":每个 PATCH 结尾 bump 版本 → 下一个 PATCH 开头 `getProductCatalog()` 发现版本变 → **全量重建 7086 商品 catalog(实测 4.4s/次)** × 55 个串行 = 卡死。修复 = 新增 `getProductRowById(id)`(prisma findUnique 单商品 + operationMetric,实测 ~40ms/次),PATCH/DELETE 路由改用它校验商品存在/归属,写路径不再碰全量 catalog;读路径(买家页/列表页)仍走缓存。**教训:写操作路由永远用单商品查询,别用全量 catalog(哪怕有 60s TTL 缓存,批量写场景每写一次重建一次 = O(n²))**。批量 PATCH 后本地实测 3 连 PATCH 从 0.96s/0.14s/0.11s,生产验证 chunk 时间戳=本次构建。
**⚠️ 第三个坑:下单扣库存/取消回补库存漏广播 → "库存乱跳"(2026-08-12,commit 88eb093)**。症状:**买家端/店铺商品库存一会正常一会缺货,刷新来回跳**。根因:库存写路径不止卖家 PATCH——**`reserveProductStock`(下单扣库存,productVariant.updateMany decrement)和 `releaseProductStock`(取消/退款回补,increment)两个高频写路径漏调 `invalidateProductCatalog()`** → DB 库存变了但 4 实例缓存不知道(版本号没递增) → 有的请求命中缓存(旧库存=有货)、有的 TTL 过期重建(新库存=扣后/缺货)、交替显示。**规则:所有改库存的写路径(卖家 PATCH/批量改/下单扣/取消回补/销量增减)结尾都必须 `await invalidateProductCatalog()`——漏任何一条 = 多实例缓存不一致**。排查顺序:先 paramiko 直查 DB variants.stockQuantity 是否已变(变了=缓存层问题)→ 全局 grep 所有 `stockQuantity: { decrement|increment }` 写点逐个核对是否带广播。验证(本地):tsx 直调 `reserveProductStock`/`releaseProductStock` → 断言 CatalogVersion 递增(14→15→16)+ 库存数值正确回补。

**⚠️ 第四个坑:批量改库存 PATCH 传空/不全 skuItems → syncProductToPrisma 删光商品全部变体(2026-08-12 深夜,数据事故)**。症状:**店铺商品库存全 0/缺货,但 DB 变体表还有别的商品正常**——用户报"库存那会不是都改成999了,怎么现在全是0"。**证据链**:① nginx access.log 定位事故时刻的批量 PATCH(14:23 一串 Chrome 151 referer=/seller/products 的 PATCH)→ ② 查商品变体:`variants: 0`(44/47 个商品变体被删光,只剩我后来补铺的 3 个)→ ③ **ProductOperationMetric.skuItemsJson 数据完好**(含 SKU/价格/库存,是恢复源)→ ④ metric.updatedAt 与 PATCH 时刻一致。**根因**:`syncProductToPrisma` 里 `prisma.productVariant.deleteMany({ where: { productId, sku: { notIn: skuItems.map(sku) } } })`——批量改库存 PATCH 的 skuItems 只要与商品原变体集合不一致(空数组/只含 fallback 默认款),`notIn` 就把原变体全删。**⚠️ 排查期自踩的坑(全在 references/variant-deletion-incident-2026-08-12.md)**:① **Prisma Json 字段(skuItemsJson)返回已是对象,别再 JSON.parse——parse 对象抛错被 catch 后 items=[] 误判"数据空了"**,第一次检查得出错误结论;② Product 模型无 inventory 字段(库存只在 ProductVariant.stockQuantity);③ ProductOperationMetric 无反向 relation(不能 include,单独 findMany + Object.fromEntries 拼 map);④ groupBy by 必须用真实字段名;⑤ `variants: { none: {} }` 是查无变体商品的标准写法。**最终恢复(2026-08-12 完成,commit 65d6cdb + 数据脚本)**:① 用户拍板库存统一 9999(选 B,不是保持 metric 现值);② 恢复脚本 = 先 `deleteMany({ where: { productId: { in: ids } } })` 清空该店全部变体(防残留/跨商品 sku 冲突)→ 从 metric.skuItemsJson 逐商品重建(optionValues=[name], price, stockQuantity=9999)→ **同步更新 metric.skuItemsJson 里 stock 为 9999(防下次读 metric 显示旧 0)** → bump CatalogVersion;③ **⚠️ 恢复期新坑:sku 全局唯一冲突——被其他店铺(如 Nexora 用同模板新铺的 PD26081216* 商品)占用同 sku → create 报 Unique constraint failed on sku**,脚本先 `findUnique({ where: { sku } })` 查占用者,非本商品则 sku 加 `-lv` 后缀;④ **代码防御(commit 65d6cdb,最终版)**:deleteMany 改为**只在"现有变体数 > skuItems 数"时才删多余项**(`existingVariants.length > skuItems.length && skuItems.length > 0`),其余情况靠 upsert 对齐——**教训:任何"skuItems 与变体集不一致就删除"的逻辑都是高危,批量操作传空/兜底 skuItems 会静默删光变体**。恢复后验证:`variants: { none: {} }` 计数 0、0 库存变体 0、总库存=变体数×9999。**⚠️ 用户拍板点:恢复时 stock 保持 0(真实扣减语义)还是全 9999——必须问用户,别自己定**(本次用户选 B 全 9999)。恢复脚本模式/证据链完整版见 `references/variant-deletion-incident-2026-08-12.md`。**⚠️ 恢复脚本里 bash heredoc + 复杂正则(`/Unique[^\n]*/` 之类)会被 shell 转义破坏,node 脚本输出标志用简单 ASCII 标记(CROSS-OK/DUP-BLOCKED/CLEANED)再 grep,别用字符类正则**。\n\n**⚠️ 第五个坑(用户前瞻提问\"100个店铺全上架同样商品\"):sku 全局唯一 @unique 是定时炸弹 → 迁移为商品内唯一(2026-08-12,commit 7295798)**。**业务事实**:桌面模板 sku 固定(如 `petg-translucent-01`),schema `sku String @unique` 是**全库唯一** → 第 1 个店占住 sku,第 2~100 个店用同模板上架**全部创建失败**(本次已实测:Nexora 新铺 PETG Translucent 与 Livvy 旧商品 sku 冲突)。**修复 = @@unique([productId, sku])**(sku 只在同一商品内唯一,不同店铺同 sku 完全合法,这是业务正解——订单存 skuSnapshot、买家端按 productId+sku 组合查找,全局唯一无任何必要依赖)。**迁移四步**:① 全库查脏数据 `SELECT productId, sku, COUNT(*) FROM ProductVariant GROUP BY productId, sku HAVING COUNT(*) > 1`(0 组才能迁移);② schema `sku @unique` → `sku String` + 表尾 `@@unique([productId, sku])`;③ **代码里唯一依赖全局唯一的地方 = `productVariant.upsert({ where: { sku: item.sku } })` → 改 `where: { productId_sku: { productId, sku } }`**(组合唯一自动生成 productId_sku 查找键;**改完必须 `prisma generate` 重新生成 client,否则 tsc 报 `productId_sku does not exist`**);④ 生产迁移:**⚠️ deploy.py 的 db push 不带 `--accept-data-loss`——改唯一约束(删旧索引建新索引)Prisma 提示可能丢数据直接失败,但 deploy.py 不检查 db push 结果继续跑完部署(代码已上新、schema 没迁!)** → **必须手动补跑 `npx prisma db push --accept-data-loss`**(已确认无脏数据,实际零丢失)+ `pm2 restart` 加载新 client。**验证(生产脚本,标志输出)**:跨店铺(Livvy+Nexora)同 sku 各建变体 → 都成功(CROSS-OK);同商品重复 sku → 被拦(DUP-BLOCKED);测试数据清理(CLEANED)。**规则:① 凡导入/铺货场景(多店铺同模板)sku 必须商品内唯一,全局唯一是过度约束;② deploy.py db push 失败会静默(代码部署照跑)——改 schema 约束类变更后必须验证生产 DB 索引真的变了(查 `prisma db push` 输出或直接插测试数据)**。
