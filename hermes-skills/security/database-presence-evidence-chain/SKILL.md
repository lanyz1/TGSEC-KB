# 无 DB 直连时证明「记录已在库里」

老板常下这种口令：**「先注册一个号，然后拿到数据库，验证号在不在数据库里」**。
这是两件事，而且难度差一个数量级：**「号在不在库里」是确定可证的**（用应用自己的读写接口当探针）；
**「拿到数据库」是另一条线**（后台/导出/注入/存储），大多数会员盘会被强鉴权挡住。
本卡只管第一件的**证据标准**，以及第二件卡住时**怎么诚实交代**。

## 何时用

- 需要证明「我注册的这个号 / 我下的这单 / 我发的那条消息」确实落进了目标数据库
- 报告里要写「已入库」，但不能只凭「接口回 200」
- 目标是资金盘/会员盘/白牌 App，没有 3306/5432 暴露、没有源码、没有备份
- 老板追问「你怎么知道进去了」，需要能扛复核的证据链

## 核心原则

**接口回 200 ≠ 落库。** 前端可以假成功、可以只写缓存、可以异步落库后失败。
要证明落库，必须拿到**只有真实持久化才可能产生的旁证**：自增主键、唯一索引冲突、
服务端时间戳回读、跨会话仍存在、状态机变更（版本号/计数）。

## 五层差分证据链（按成本从低到高，全做一遍）

| # | 探针 | 期望回包 | 它证明了什么 |
|---|------|----------|--------------|
| 1 | 注册返回体 | `userId=<N>`（自增整数） | 得到表主键 = 真的插入了一行，不是内存态 |
| 2 | **同参数重注册**（同一手机号/邮箱） | `该手机号已被注册` / `duplicate` | 命中 `phone`/`email` **唯一索引** —— 索引只在持久层 |
| 3 | **对照组**：换一个新号重注册 | 成功，`userId=N+1` | 证明第 2 步的拦截来自**库**，不是前端/风控/我的请求格式错 |
| 4 | 重新登录，回读档案 | `createdAt`（服务端时间）、`lastLoginAt`、邀请码、初始余额/积分 | 只有 `SELECT` 命中该行才会回这些字段；`createdAt` 是服务端生成 |
| 5 | 触发一次**状态写**（改密/改昵称/领奖）后复用旧凭证 | 旧 token 立刻失效 / 版本号递增 / 余额变化 | `UPDATE` 真的落盘了；tokenVersion 类字段是最硬的一条 |

补充规模感（免费）：注册返回的自增 `userId` 水位 ≈ 全站用户量级；站内消息/订单的自增 id 水位 ≈ 业务量级。
写报告时给区间不给精确值。

### 第 2+3 步必须成对做

只做第 2 步是**无效证据**：任何前端校验、IP 风控、参数规范化都能造出「已被注册」。
只有**「同号被拒 + 新号通过」**这组对照，才能把原因收敛到库的唯一索引。
这一步只要 30 秒，但漏了整条链就是自说自话。

### 第 5 步的副作用要预判

改密类探针会**吊销自己所有会话**（`tokenVersion`/`sessionVersion` 递增）。
后果：手里别的脚本、别的 shell 的 token 全失效，看起来像「被踢了/被封了」。
做法：改密前先落盘新密码，改完立刻重登刷新 token，别在改密后紧接着跑依赖旧 token 的矩阵。

## 什么时候这五层**不**成立

- 第 1 步拿不到自增 id（用 UUID/雪花）→ 不妨碍，第 2/3/4/5 照样成立
- 第 2 步回的是**通用失败**（`参数错误`/`操作失败`）→ 分不清是唯一索引还是别的校验，**不能当证据**，改走第 4/5 步
- 第 4 步字段全是静态常量（同期多个账号 `createdAt` 完全相同）→ 可能是模板填充，别当 SELECT 证据
- 号是**只读影子库**（注册进 A 库、查询打 B 库）→ 现象：注册成功但立刻登录失败，等一段时间才通；第 4 步要延时重试

## 第二件事：全库可达性怎么判（卡住时怎么写）

「拿到数据库」在会员盘上的现实路径只有四条，按 ROI 排：

1. **后台导出面**（`user/export`、`kyc/export`、`withdraw/export`、`finance/flow/export`）—— 一条即全库，但需要**一个有效后台 token**
2. **签名层是否要密钥** —— 若是 `SHA256(token+method+path+ts+nonce+body)` 这类**无 secret** 的设计，签名不是门槛，**token 才是**；攻法从「猜口令」改成「搞到任意一个 token」（XSS/heapdump/日志/客户端 token 复用）
3. **注入面** —— 排序字段、导出筛选、搜索 LIKE；现代 Java/Go 后台多为参数化，别在这里沉没成本
4. **存储面** —— 备份桶、上传目录、CDN 后面的对象存储（见 `cloud-storage-bucket-recon`）

**判阴性前必须先把「挡住你的是什么」写成一句话**，例如：
「后台可达，但 2 发/账号/30 分钟账号级锁定 + 参数化查询 + 无密钥签名仍需 token ⇒ 口令线吞吐 < 30 次/小时，无实用价值」。
这比「后台打不进去」有用一百倍，也是老板唯一能拿去决策的东西。

## 报告纪律

- **「号在库里」和「拿到数据库」必须在报告里分成两节**，各自给结论。做到一半写成做到，是这类任务最常见的翻车。
- 证据链按上表逐条列，**每条附原始回包片段**（`userId=35148`、「该手机号已被注册」、`createdAt=...`）。
- 没拿到的部分写「未完成 + 卡在哪 + 还差什么」，不写「暂无漏洞」。
- 顺手拿到的 PII 类风险（实名证件匿名可读、桶名/APPID 泄露）单独列，它们**不需要后台权限**就成立，是报告里最硬的部分。

## Pitfalls

- **别把「该号已存在」当成「我拿到了数据库」。** 前者是单条记录的存在性，后者是全表读取，中间隔着鉴权。
- **别用「重复注册被拒」单条下结论** —— 必须配对照组（新号能成功），否则无法排除前端/风控拦截。
- **改密探针会吊销自己的 token**（`tokenVersion` 递增），且改密后旧密码立即失效；改前先落盘新密码并准备重登脚本。
- **探测锁定状态本身消耗尝试预算并可能重置计时器** —— 参见 `password-spray-lockout-bypass` 的「锁窗倒计时不可信」与「排程纪律」两节。
- **自增 id 水位会泄露规模**：`userId` 水位、消息 id 水位都写进报告前先想一遍会不会夸大（水位 ≠ 活跃用户数）。
- 证件/实名类文件存在**公共读**对象存储时，验证方式是「用无登录态 curl 回读自己上传的 URL」，`200` + 正常字节数即成立 —— 但**只测自己上传的那份**，不要去翻别人目录。
