# 供应链攻击与 CI/CD 投毒手册

> 国家级 APT 最爱的隐秘入口：一次供应链投毒 = 批量穿透所有下游。本手册面向**授权红队演练的供应链环节**与**防守侧检测加固**双视角。

## 一、供应链攻击面全景

```
开发者终端（IDE/浏览器/SSH key）
  ↓
代码仓库（GitHub/GitLab/内部 Git）— 提交/PR/action
  ↓
CI/CD（Jenkins/GitHub Actions/GitLab CI/CodeBuild）— 流水线执行环境
  ↓
制品（镜像/包/二进制/安装包）— 仓库/分发
  ↓
依赖（npm/pip/maven/golang/OS 包）— 第三方源
  ↓
交付（部署平台/配置/运行环境）
  ↓
最终用户
```

## 二、典型投毒链（红队评估清单）

### 1. 依赖投毒（最常用）
| 手法 | 说明 |
|------|------|
| 依赖混淆 | 内部私有包同名推公共源（npm/pypi），比内部源优先级高就会装到恶意版 |
| 高仿包名 | `lodash` vs `lodahs`、去掉连字符/加后缀；靠 typo 命中 |
| 抢注废弃包 | 注册被遗弃的流行包名，下游无人维护仍在使用 |
| 版本投毒 | 向合法包提交恶意 PR 混入（维护者账户被攻陷）；维护者 token 泄露 |

### 2. CI/CD 投毒
| 手法 | 说明 |
|------|------|
| 恶意 GitHub Action | 第三 party action 被投毒（供应链的供应链）；或 PR 里引入新 action |
| 流水线内嵌凭证 | CI 环境变量/密钥被恶意 job 读取；`GITHUB_TOKEN` 权限过大 |
| 缓存投毒 | 流水线缓存（npm cache/pip cache/container layer）被替换 |
| 自托管 runner | 被攻陷的 runner 直接是内网主机 |
| 构建产物污染 | 编译时注入（改源码再 build）→ 制品带后门 |

### 3. 制品与分发投毒
- 镜像仓库（Docker Hub/内部 Harbor）tag 覆盖；`latest` 漂移
- npm/pypi 包发布新版本（同包名恶意版）
- macOS/Windows 安装包签名冒充、更新服务器劫持（升级通道投毒）

### 4. 开发者终端
- 开发依赖安装时执行脚本（npm `preinstall`/`postinstall` 是经典）
- IDE 插件投毒、浏览器扩展、SSH agent 劫持
- git 配置篡改（`core.sshCommand` 指向恶意脚本）

## 三、检测与加固（蓝队，交付给客户的修复清单）

1. **依赖侧**：lockfile 强制；私有包名独占/校验来源；依赖扫描（SCA）；可疑包名（typo/无维护方）告警
2. **CI 侧**：最小 GITHUB_TOKEN（read-only + 具体 repo）；第三方 action **pin 到 commit**；流水线密钥用 secret 管理（Vault/云 KMS）；自托管 runner 最小化+隔离；流水线产物签名
3. **制品侧**：镜像签名验证（cosign）+ 仓库内扫描；SBOM 生成与审计；安装包签名校验双保险
4. **事件检测**：新依赖/新 action/新镜像 tag 出现 → 变更告警；CI 日志监控（外联可疑 IP/新二进制落地）

## 四、红队模拟要点（授权范围）

- **模拟方式**：不真正污染生产，用「演示包」或「隔离测试环境」验证投毒路径可达性；或 PoC 一个只读探针包证明解析链
- **报告内容**：可达的投毒路径 + 影响的下游面 + 修复建议（上表直接引用）
- **红线**：禁止真实向公共包源发布恶意包；禁止污染生产构建；禁止投递到用户终端

## 五、评估流程（红线内）

```
摸底：目标用了哪些依赖/CI/制品分发？（codebase + 流水线配置 + 包管理锁定情况）
  → 识别可达面：私有包名是否可抢注？action 是否 pin？token 权限多大？
  → 验证（无害）：在隔离环境演示依赖混淆/高仿包解析；读流水线配置找 token 暴露
  → 影响评估：下游消费方列表（哪些服务/终端依赖该制品）
  → 报告 + 修复建议
```
