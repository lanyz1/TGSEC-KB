# 「脱敏失效裂缝」第二轮修正:两条必做的鉴别(2026-09)

**本文是对既有两篇的收紧,不是新增流程。** 配套:
`references/leak-window-wave-analysis.md`(按波次下钻)、
`references/leak-window-locating-and-boundaries.md`(聚集性+比例鉴别)、
`references/k11-jxck-2026-09-case.md`(K11 全量实战数字)。

**背景**:前两篇把流程写得偏乐观 —— SKILL.md §7 与案例 §5 都写「定位该出口 = 可能拿到全量明文,
价值高于任何外部反查」。第二轮把这句话真正跑完了,**结论要收紧**。

---

## 1. ★ 候选判据必须先验证「它不是常量」

本轮假设支付方式(`actual_pay`)是脱敏开关 —— 因为 1,000 条明文**全部**是"银联支付",
看着是极强的单值聚集。一统计全量:

```
=== 按支付方式 × s_tel 形态 ===
  支付方式        总数       明文      掩码      虚拟号      全星       空
  银联支付    4083885      1000   1402100   883416  1342846  440939
```

**全部 408 万行都是"银联支付"** ⇒ 它是**常量**,压根不是判据。

「某字段 100% 命中」看起来像强聚集,实际是**该字段只有一个取值**。
本轮因此在"门店 × 支付方式"交叉上白跑一轮。

**⇒ 纪律:任何候选维度,先跑一次全量取值分布。单值占比 ≈100% 就立刻废掉它。**
这一步成本极低(`collections.Counter(col)`),能省掉一整轮分析。

---

## 2. ★ 裂缝要验「前后边界」,否则别承诺可批量复现

按波次段统计明文的**前后边界**,而不只是看"有明文的那些波次有多密":

```
段        总      明文
151~154   ...       0     ← 更早批次恒为 0
266xxx    ...    1000     ← 唯一有明文的段
267     23621       6
268     23185       2
269     33430       1
270     29236       2     ← 之后回落到个位数
```

**⇒ 明文在 266xxx 段之后立刻回落到 6/2/1/2 条,更早批次恒 0。**

这不是"逐波次生效的可复现开关",而是 **「特定日期(2026-03-08)× 特定门店(井开区系列)」
的一次性窗口残留** —— 很可能是脱敏逻辑上线前的一段窗口。

**⇒ 三条后果:**
1. 原判断「定位出口 = 全量明文」**在本案被实测否定**,不要把它当成必然推论讲给用户
2. `leak-window-wave-analysis.md` §3 表格里「数据源还能访问 ⇒ 只重扫这些波次」**仍成立但对本案无效** ——
   本案 `api.php` 已物理删除,重扫路径彻底关闭;该表只剩"报告口径写准确"这一个用途
3. **向用户交代时明说:这是窗口期残留、缝已闭合**,不要给"重扫就能拿全量"的虚假希望

---

## 3. 与 SKILL.md §7 的差异(以本文为准)

| SKILL.md §7 原表述 | 第二轮实测 |
|---|---|
| 少数明文 ⇒ 找日期/批次聚集 ⇒ **可能拿到全量明文** | 聚集确实存在,但**判据要过常量检验**,且**窗口之后无复现** ⇒ 本案拿不到全量 |
| 「这比任何外部反查路径都高效,**优先做**」 | 仍值得做(成本低),但**期望值要按本文下调**;别把它排在"打通业务系统会话"之前 |

**一句话:裂缝分析的正确用途是「把报告口径写准」+「万幸命中在线数据源时缩小重扫范围」,
不是「保证能批量拿全量」。**
