## 1. 先判闸类型(一次请求定路线)
| 响应 | 含义 | 立刻做 |
|---|---|---|
| `101020 未获得签名，拒绝处理` / `验签参数不可为空` | 只查字段存在性 | JSON body 或表单加 `sign=1` 即进业务层 |
| `101010 验签失败` | **真值校验** | 转第 3、4 节,不打字典 |
| `缺少参数，名称：X，类型：Y`(常 `code 100011`) | 参数预言机 | 逐参喂,见第 2 节 |
| `{com.<厂>.<模块>.validation.<字段>.NotBlank.message}`(常 `code 300400`) | Bean Validation 预言机,**泄全限定字段名** | 逐参喂,比 swagger 权威 |
| `211057 token不存在!` / `未登录` / `登录已过期` | 闸已过,**只剩会话** | 停手扩面,转第 5 节的值枚举 |

**铸票类闸(JWT 自签)先做三发差分,判「验不验签 + 有没有登记簿」**(省下一整轮无效爆破):
- A=结构完备 claims+真钥;B=同 claims+错钥;C=空/残缺 claims —— 同一端点各一发。
- A、B 回同一句话(如都回 `token已失效`)而 C 回另一句(如 `解析失败`)⇒ 签名根本不验,闸门 = claims 结构 + 服务端**有状态登记簿** ⇒ **该主体**自铸票必败(掌握密钥也无用),爆破/还原签名密钥是纯无效功;方向改:找**登记在册的真实 (主体id, secret) 对**(刷新流 / 配置载体 / 泄漏库)或借活票(审计日志 / 浏览器会话)。
- A、B 文案不同 ⇒ 签名真在验,再走密钥路线 —— **但「验签 + 有登记簿」不等于伪造路已死:登记簿比对常被特权身份短路**(见下条)。
- **★★ 已验出「验签 + 在册登记簿」时,改判据为「换身份」而不是「换密钥」**:同一把**已验证正确**的签名钥,签**普通主体**被登记簿挡(「不在册」档,如 `TokenNotExistError`),签**特权主体**却直接放行(实测 `errCode:0`)。⇒ **「自铸票必败」只对普通主体成立,严禁写成「该服务不可伪造」**;把结论降级为「非特权主体不可伪造」,下一步是拿**出厂默认特权名的小列表**(如 `imAdmin` / `admin` / `chatAdmin`,**不是大字典**)逐个试签,一个命中即完全接管。机制:特权判定写在在册比对**之前**。
  **★ 错误码阶梯就是校验顺序剖面**:`signature is invalid`(钥错)→ `TokenNotExistError`(验签过、票不在册)→ `… is not admin userID`(真票、非特权)。**码停在「不在册」而特权名返成功 ⇒ 特权判定在在册比对之前**;看清这条顺序,比再爆一轮密钥便宜一个数量级。
- **★ 扫描命中判定严禁用「响应里不含已知错误串」**:该写法把**每一档不同错误**都计成命中(实测一次「80 命中」里绝大多数是 `TokenNotExistError`,真命中仅 1 条,整轮判读作废)。正确做法 = 先**枚举该服务的完整错误码阶梯**(含成功码,如 `errCode:0`),命中只认**成功码或明确的下一档业务码**,其余按档归位并**分档计数** —— 分档计数本身就是闸门结构的证据。
- **★ 判「签名覆盖 payload 还是只覆盖固定串」必须用『保签名改载荷』,不能用『换错密钥』**:错密钥在任何实现下都失败,证明不了验签存在。正确的一对 = (i) **改 payload 里某个 claim、原样保留 signature** + (ii) **保留 payload、改 signature 一个字符**;外加 (iii) `alg:none`/算法降级。三发都拒且错码同档 ⇒ 签名真在验且**覆盖 payload**(伪造票路线关闭,只剩取真票或取签发密钥);只有 (ii) 拒而 (i) 放行 ⇒ 签名只覆盖 header/固定串 ⇒ **载荷可自由改 = 越权面**。
- **★ 闸门文案在目标二进制里 0 命中 ⇒ 该文案来自 DB/i18n 配置,不是漏挖**:先确认是否为原生串(邻域是 TLS/crypto/MySQL 模板即噪音),0 命中就停止在 strings 里找产出者,改搜**判定键名**(`minVersion` / `xxxDisabled` 这类配置键)并回线上实测。**「文案不在二进制」≠「判定逻辑不在二进制」**,两者要分开找。
- 文案分档:`解析失败`=结构层、`已失效/不存在`=状态层、`签名验证失败`=签名层;**同族错误的后缀数字(-1/-2)变化 = 到了不同校验档位**,作为分层信号采集,别当同一错误忽略。
- 有服务端二进制(如未剥离 Go 服务)时,把分层从文案猜测升级为**分支级证据**:错误串 xref 找到发射函数、反汇编读分支条件与中间件调用图(中间件含 Redis/DAO 调用 = 有状态登记簿),配方见 `go-service-binary-dissection`。

**同主机多路由的中间件排序不一致——用「全路由 × 三档凭据」矩阵扫「签名在前」的口**:
- 同一 host 上并存:有的路由先查签名(无签名回 `签名验证失败-N`),有的直接查 token(回 `token解析失败-N`)。
- **仅凭 App/平台级签名即返业务数据(ErrCode:0 且带字段)的路由 = 最高价值裂缝**:高级别凭据可能替代用户凭据直入业务层 ⇒ 逐参数试用户标识(uid / userId / memberId / 第三方 uid 等),并用响应字段核对拿到的是谁的数据。
- 签名在前且报「必填参数缺失」= 闸已过(错误从『签名失败 / 裸 403』推进到『业务字段错』就是进业务层的最强正证据,别再回头怀疑签名),补参即入;按报错字段名迭代,方法见 `api-param-name-discovery`。
- **403 墙判「端点族级」还是「App 级」必须带对照路由**:同一套有效凭据再打一条墙外的普通业务路由——它进业务逻辑(回字段校验错)⇒ `access denied` 只是**那一个端点族**(如第三方集成族)的授权墙,不是 App/IP 级;全部路由同 403 才是 App 级。无对照就写「IP 白名单」=凭空假设,会让整轮烧在换源 IP 上。
- **X-Api-Key 类应用凭据的两种拒态分读**(先在同 harness 拿「已知可用 key vs 乱造 key」对照再采信):`签名验证失败` = 服务端查不到该 key 对应 secret(app 认不出,换 key 才有意义);`access denied`/仅单端点族 403 = app 已认出但无该族授权(换 key 是无效功,换端点族或趁该 app 有权限的面)。
