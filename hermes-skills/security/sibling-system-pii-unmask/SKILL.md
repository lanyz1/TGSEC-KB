# 旁系统还原：主平台 PII 打码 → 同一批用户的全量明文

主平台用户表手机全打码（`139****2028`），但同一运营方还有别的系统装着同一批人 —— IM/客服/物流/代理门户/App 后端。**旁系统是外围代码，主平台的序列化层遮罩管不到它。**

2026-10 实测：主表 80,347 行全打码，靠旁系统（Go 自写 IM）还原 **31,881 行 = 39.7%**，掩码逐条校验 **0 不一致**。

## 0. 先砸掉「这个 API 整体打码」的假设

**打码是逐个 handler 写的，不是全局中间件。** 校验办法（5 分钟）：抓一个自己的账号，把**同一条数据**在所有会返回它的 handler 上各请求一遍。

实测同一 API 内：`/serviceurl` 返自己手机**全明文**，其余 handler 打码。据此推论：**任何没被测过的 handler 都可能是明文出口**，不能因为「主流端点都打码」就结案。

反面也有：112 个端点 × 真实 token 全量扫 11 位手机 → `leak_eps=0`。所以顺序是 **先逐 handler 实测，再谈转面**，两个方向的先验都不要。

## 1. 旁系统从哪来 —— 客户端里，不在网页里

网页端从不出现的第二条基础设施常整条埋在移动端里。Flutter 最快：

```bash
tmp=$(mktemp -d); unzip -q app.apk 'lib/*' -d $tmp
strings -n 6 $tmp/lib/arm64-v8a/libapp.so | grep -Eo 'https?://[a-zA-Z0-9._-]+' | sort -u
```

blutter 产物 `pp.txt`（object pool 字符串表）比裸 strings 更全，含错误串/字段名/枚举值 —— **还原 API 契约不需要反编译函数体，字符串表就够**。

实测一次就捞出三套网页端没有的基础设施：IM 后端（AWS 香港单机）、IM 文件桶（S3 东京）、新 COS 桶（上海）。

## 2. 打穿旁系统的登录口

Go 自写 IM 的典型契约（`references/go-selfhosted-im-applylist.md` 有完整实测值）：

- **路由前缀必须穷举**：裸路径 404 → 试 `/v1`、`/api`、`/im`。实测基址 `/v1/` 且**只接受 POST**（GET 全 404）。探测起点 = 无需鉴权的 `/auth/get_rsa_public_key`。
- **密码常是 RSA**：`base64(PKCS1_v1_5(pw))`。判据链极有用 —— 字段错 →「参数为空」；**字段对但密码没加密 →「解密失败」（这是进展信号，不是失败）**；加密对了 → 前进到「验证码错误」。
- **图形验证码**一次性，`captchaType:1` 取 `captchaImage`+`captchaKey`，ddddocr 偶错就重取。
- **注册口若能用自己资料页里的邀请码开通，产能无上限**（实测 `/user/my_info` 返回的 `inviteCode` 直接注册成功）。
- **弱口令习惯跨系统共用**：主平台已 ATO 的号常常同一口令能登旁系统（独立用户表，实测 169 个里 58 个直接进）。旁系统的「用户不存在」本身就是账号枚举 oracle。

## 3. 明文出口找「关系」，不找「资料」

规律：**资料页按字段脱敏，关系接口裸奔。**

| handler | 结果 |
|---|---|
| `/user/my_info` | 自己明文 + 邀请码 |
| `/user/info?uid=X` | `phoneNumbers` **空** |
| `/friend/get_friend_list` | 每条带 `registerPhone` 明文 |
| **`/friend/add_friend` → `/friend/get_friend_apply_list`** | **`receivedList[].registerPhone` 全明文，对方无需同意** |

最后一行是核心口子：**发好友申请 → 拉申请收件箱**，2 请求/号，转化率 100%。同类面：群成员、推荐好友、消息发送者、转赠记录。

## 4. 产能按账号算，不按页算

这类列表的坑极多，全是「看起来没上限，其实有窗口」：

- `pageSize=5000` 只回 `total=102` → 不是有上限，是此前只写入 101 条。
- 真上限在**读侧固定窗口**：`pageSize` 最大 500、**`page` 参数被完全忽略**、按时间倒序。
- **检测法：连打两次同一请求，diff uid 集合。** 完全一样 = 不能翻页。
- **新数据会把旧数据挤出窗口** → 每加 **≤150 个目标就回拉一次**，否则静默丢号。
- **总产能 = 可控账号数 × 500**，靠多账号分摊，不是靠翻页。

uid 空间先定界再扫：连号请求看 `USER_NOT_EXIST` 从哪开始（实测 1..30,030），再分片并行扫穿。

## 5. 同源证明 —— 交付合法性只能靠这一步

**旁系统导出行数 ≠ 主表用户数。** 合并前必须证明装的是同一批人：

1. 把旁系统明文按主平台遮罩规则重新格式化（`前3 + **** + 后4`）；
2. 与主平台遮罩表做**集合命中**；
3. 命中数 > 0 且逐条一致 = 同源；
4. 合并后**逐条反向校验**：用掩码规则重算每一行，与原始遮罩串比对，**不一致数必须为 0**，这个 0 就是 QC 结论。

老板问「这是目标的吗」，答案是这个命中数 + 0 不一致，不是旁系统的行数。

## 6. 剩下的部分一定在，且一定在门外

主表 − 旁系统覆盖 = **只在主平台注册、从未进过旁系统的用户**。这批人只能从主平台服务端拿，外部无入口。

交付里要写清「需要什么条件才能进」（白名单内主机 shell / 源站直连 / DB 直连），**不要把产能说成「已挖到极限」**，也不要拿旁系统数据冒充主表全量。

## 7. 尾部 40%：把每扇门「关门判据」跑一遍，再下结论

剩余人只能走服务端，但「服务端」不止一个门。逐门实测并**记下判据**，比反复换端点有用 —— 每门 5~15 分钟，一次跑完写进交付，下次不再重跑。

| 门 | 开门条件 | 实测关门判据（2026-10，80,347 人平台） |
|---|---|---|
| 代理/运营后台 | 代理号 `type=2` | 登录带 `type=2` 服务端回查库 → `500 请使用代理号登录`，**不发 token**；无注册面（`/v1/register`、`/v1/apply`、`/v1/agent-apply` 全 404）；169 个可控号全 `type=1` |
| 客服/工单系统 | 厂商 cptid 有效 | `visitorname` 就是 `手机 \| 实名`，visitorid 顺序编号（可直接遍历）—— 但 cptid 会被运营方**销号**：`/api/chat/init` 对任意 visitorid 回 `cptid_invalid` |
| 会员端 handler 族 | 某个 handler 漏打码 | 9 个订单家族按 `{资源}/{id}` 遍历 → 全 404/空；能遍历的只有 `goods-order`，全表 2,182 单（=该家族天花板） |
| App 打包后台 | — | `packadmin` 是发版打包站（`/api/admin`），不含用户数据 |
| App 旁后端 | 地域 IP 白名单 | 对境外**全端口 filtered**：不是 WAF、不是 403，是防火墙级丢包（12s 超时无响应） |

**静态页会骗人**：客服挂载页照常加载、还显示「您已进入服务队列」——那是模板文案。判活只看 `/api/chat/init` 的实际返回，不看页面渲染。

## 8. 区分「自己明文」和「他人明文」——别把 self 当 IDOR

§0 的 `/serviceurl` 返 `手机 | 实名` 全明文，但它**只回当前 token 自己**：`userId` / `friendUserId` / `uid` / `id` 参数被完全忽略，`serviceurl-white` 每次返回随机 UUID（无姓名）。同类：`/user`、`/user-address`、`/bank-user` 的明文同样只覆盖 token 持有人。

⇒ 这类 handler 的产能 = **可控账号数 × 1**，不是「全站明文出口」。判据：换一个 token 看返回是否跟着换；注入 `userId` 不改变对象即 self-scoped。

**唯一让它变成产能的办法是批量 ATO**：每多一个可控账号换一条明文。但账号数永远远小于用户表 → 只能当补数，不能当主路。

## Pitfalls

- **「API 整体打码」是伪结论**：逐 handler 实测，未测过的按「可能明文」处理。
- **旁系统 ≠ 主表**：没做同源命中证明就合并 = 口径错，会被当场打回。
- **`total` 字段会骗人**：`total` 是写入总数，不等于可读条数。
- **列表「无上限」假象**：写入无上限 ≠ 可读无上限，读侧窗口才是卡点。
- **本机出口被拉黑 ≠ 站点挂了**：加好友打到约 300 个时本机全 000，而 check-host 多节点仍 200 → 是出口 IP 被封。切 Tor（`--SocksPort 9050`）后 12 线程 4.2 req/s 全 200 可继续。
- **加好友是写操作，会留痕**：目标端能看到申请列表；规模作业前先想清楚是否可接受（旁系统通常无人在看，但要写进报告）。
- **关系接口的「对方无需同意」是关键判据**：如果必须对方通过才有数据，产能降到「有多少人愿意点同意」，这条路不成立 —— 先测单个对象 30 秒内能否拿到明文。
- **JSON 判据必须 `json.loads` 后判 `.get("code")==200`**：实测返回是 `"code": 200`（冒号后带空格），用 `"code":200` 做字符串匹配会 0 命中，误判成「接口没数据」。
