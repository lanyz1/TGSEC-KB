# 多租户平台 账号锁定拓扑测绘

一套代码复用、多品牌多租户的平台（白标盘/资金盘/杀猪盘/白牌客服 SaaS）常把登录锁定做成「租户 + 用户名」双键。先把它测出来，再决定把有限的尝试预算摊在哪里。

## 何时使用

- 同一后端聚了多个品牌域（`123.x.com`、`hu123.x.com`…），想确认它们是否共用一套库/一套计数器
- 喷密速度被锁定卡死，需要判断能不能“开新通道”而不是硬顶
- 要区分「按账号锁」「按出口 IP 锁」「按租户锁」

## 第 1 步: 先测锁定是不是真的存在

- 同一用户名连打 5 发 → 第 5 发后回锁定文案（常带剩余分钟数）
- **不存在的用户名同样会锁** → 无用户名 oracle（不能用锁定差异枚举用户）
- 大小写 / 前后空格变体**共用**计数器（归一化生效）
- 全角 / 西里尔 / 零宽空格变体可得**独立**计数器——能继续试，但几乎不可能命中真实记录（真实用户名是普通写法），属无效杠杆

## 第 2 步: 测维度（对照实验，每次只变一个量）

| 要回答 | 实验 | 读法 |
|---|---|---|
| 按租户隔离吗 | 租户 A 锁住后，立即用同名打到租户 B | 回业务错误（非倒计时）= 隔离；回同一句锁定 = 共享桶 |
| 按用户名隔离吗 | 同一租户换另一个用户名打一发 | 回业务错误 = 隔离 |
| 按出口 IP 吗 | 锁定期间换一条干净出口打 | 仍锁 = 非 IP 维度 |
| XFF 可信吗 | 锁定期间伪造 `X-Forwarded-For`/`X-Real-IP` | 不生效 = 对端取 TCP RemoteAddr（防伪造实现） |

**锁定期内不要反复探“还剩几分钟”**——有的实现对每次失败请求重置倒计时，会把 30 分钟拖成无限。真要看就只在需要时读一次服务端返回的剩余分钟。

## 第 2.5 步: 同一品牌多套后台 = 锁库独立性（最大的倍增器）

同一集团常给每个品牌各发一套**独立部署**的后台（不同域名、不同 Redis）。**每套后台的账号锁互不影响** —— 这比换用户名值钱得多：用户名是「猜」，面板数是「白捡的倍率」。

**判定实验（一发定论，30 秒）：** 在面板 A 已锁死的用户名，到面板 B 打**一发**：

| 面板 B 回什么 | 结论 |
|---|---|
| 业务错误（密码错 / 用户不存在 / `10002`） | **锁库独立** → 通道数 ×N，继续打 |
| 同一句锁定文案 / 同一剩余分钟数 | 共享桶（同 Redis/同库）→ 扩面板无用，只能扩用户名 |

一次只变「面板」这一个量；别同时换用户名，否则分不清是哪一个在起作用。

实测形态：3 套后台 × 267 用户名 → **15 发/用户名/30 分钟**（单面板 5 发），总吞吐 ×3，18 小时词表压到 6 小时。

```
通道数 = 面板数 × 租户数 × 用户名数
总吞吐 = 通道数 × 单通道配额 / 窗口
```

找兄弟后台走 `admin-console-discovery`（crt.sh + ops 域枚举）；拿到后**先按 `<title>` 认品牌**，别把同一套面板当两条线重复打。

### 每套后台的错误码要单独建表

同集团不同构建版本**错误码不同**，混用会把命中丢掉：

- 密码错 / 用户不存在（常合并，不可枚举）
- 密码对但需二次验证（TOTP / `needGoogleBind` 可用口令直接绑自己的验证器）
- **密码对但 IP 不在白名单** ← 这是**命中**，不是失败，立刻转 XFF/信任头轮换
- 账号锁 / 频控（CF 的 `429`/`430` 是**第三层**限速，既不是锁也不是命中）

> 战役脚本里**任何非「密码错」的码都必须落 `ODD.json` 单独人审**，绝不能当失败丢掉。
> 见过 `10014`（密码正确、IP 不在白名单）被当失败扔了两整天。

### 面板批次要错开

多面板并行时，**每条线取词表的不同切片**（`P[0:5]` / `P[5:10]` / `P[10:15]`）。
若三条线都用同一批 5 个词，等于把同一个 (用户名, 口令) 组合测三遍，白白烧掉 2/3 配额。

## 第 3 步: 通道倍增（核心杠杆）

锁定键是「租户 + 用户名」时，**用户名就是通道**：

```
通道数 = 租户数 × 用户名数
每通道额度 = 4 发 / 30-31 分钟（先实测，别照搬）
总吞吐 = 通道数 × 4 / 窗口
```

- 用户名候选：`admin` `manager` `kefu` `service` `system` `root` + 品牌名/品牌拼音（`rmzc` `gjzj` `gxs`…）
- 实测：5 通道（5 租户 × 1 用户名）→ 20 次/31 min；扩到 35 通道（5 租户 × 7 用户名）→ **140 次/31 min，×7**，单通道配额不变
- 这样做的另一个好处：如果管理员用户名根本不是 `admin`，广度策略才有机会碰到

## 第 4 步: 预算分配（广度 vs 深度，只能二选一）

总预算固定为「通道数 × 4/窗口」，所以：

- **广度**：每个口令在所有通道里只测 1 次 → 1 个窗口能覆盖 140 个词，但任何 (通道, 口令) 组合只被碰一次
- **深度**：每个口令测满全部 35 通道 → 一个词耗 35 发，一个窗口只能跑 4 个词
- 词表 > 1k 且用户名未知时：先广度（把高概率词扫一遍），等观察到某些通道回“密码正确但缺 TOTP”这类信号再转深度
- 词表排序决定早期命中：品牌词+年份、`admin@123`、`Aa123456`、`admin123`、`123456` 这类要前置，不要被大量品牌变体挤到几百位之后

## 第 5 步: 调度器实现要点

- **锁定 / 封禁响应不进候选弹出队列、不增 used**：否则一轮锁定白烧几十个词
- 锁定分钟数用正则从响应文案取真实值（`请(\d+)分钟后再试`），不要写死 30
- `tested.txt` 启动时读入去重，防止重启后重复测
- 每通道 4 发即主动冷却 31 分钟，不要等它自己回锁定——把“被锁”变成“自己排队”
- 日志落盘（`daemonN.log`）+ 命中单独文件（`PW_HITN.txt`），长跑靠 tail 日志文件，不接管道

## 坑

- **开战役前先审计在跑的进程**：`ps -eo pid,etime,cmd | grep -i <目标域名>`。同名目标上残留的第二个爆破器会**偷偷吃掉同一批账号锁配额**——本项目一个残留 `runner.py` 跑了 4 小时、1,650 发、0 命中，把主战役的窗口全偷了。先杀、并词表、再重启。
- `pkill -f "<pattern>"` 会连**自己这条 shell** 一起杀（自身命令行含同一 pattern）→ exit -15；改成 `ps` 取 PID 后逐个 `kill <pid>`。
- Cloudflare 前端的面板要 slow mode：实测突发 `{430: 7, 429: 1}`，批间 sleep 2s+、遇 429 退避 8s，否则整轮被 CF 吞掉。
- 锁定是“账号维度”时，换出口/挂代理**完全无用**；不要浪费时间配代理池
- 同一品牌多域名共用计数器：扩域名不等于扩通道，要先按第 2 步测后端的归属
- 验证码（图形/滑块/二次校验）在的话，通道倍增前先把 OCR 通过率量出来（见过 40% 的），否则吞吐算不准
- 登录端确认是明文提交还是前端哈希（扒登录页 JS），否则会把“格式不对”误判成“口令错”
