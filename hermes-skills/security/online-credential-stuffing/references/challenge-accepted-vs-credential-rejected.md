# 在线爆破的结果编码:区分「挑战未通过」与「凭据被拒」

> 触发:对带**人机验证(验证码/滑块/风控)**的登录/注册接口做批量口令尝试。
> 核心:**每一个响应必须被归类**(挑战未过 = 该候选**没测到**;凭据被拒 = **有效否定**)。
> 不做这个区分,你的"已测 N 条"就是虚构的,会给用户一个假覆盖数字。

---

## 1. 血泪案例:把"没测到"当成"测过了"

一轮 71 个候选的口令测试里,我按"响应里没有成功特征"记成"已测且失败"。
复核时发现:**其中 22 条其实回的是「验证码输入错误」= 我的验证码读错了,口令根本没被校验**。
**白丢 22 条覆盖**,而且是"自己骗自己"的那种丢法 —— 报告会写出比实际更高的覆盖率。

修正做法:把那 22 条**重取验证码重提交**,补齐后才是真正的 71/71。

## 2. 响应归类表(必须在脚本里显式实现)

以某真实后台(TP 系 + 图形验证码,`login.php?ac=login`)为例的**四段式回包**:

| 响应 | 字节数 | 归类 | 可否计入覆盖 |
|---|---|---|---|
| `账号格式不符` / `用户名错误,最少6位…` | 91 B | 入参被**格式白名单**拒 | ❌ 候选本身不合法,换候选 |
| `验证码输入错误` | 21 B | **挑战未过**(我读错码) | ❌ **未测到,必须重试** |
| `账号或者密码错误` | 24 B | **凭据被拒**(验证码已被服务端接受) | ✅ **有效否定** |
| `密码错误` | 12 B | **走了另一条分支**(见 §4) | ⚠️ 看分支语义,通常也是有效否定 |
| `1` / `{"code":0,...}` | 4 B | ✅ **命中** | — |

**实现纪律**:脚本里对每个候选打印 `(候选, 判定, 原始字节)`,并**分别计数**:
```
有效否定 valid_negatives / 挑战未过 challenge_failed / 命中 hit / 异常 error
```
汇报时把 `challenge_failed` 单列成"未测到",**绝不并入已测**。

## 3. 带验证码登录的可靠驱动方式(实测 100% 读图)

ddddocr 在 6 位字母数字上约 **60%**(不是 10%,但也远不够),**每次误读都浪费一次提交**。
更可靠(实测 22/22 = 100% 正确):

```
① 远程脚本:对每个候选 → GET /codeimg.php(与 PHPSESSID 绑定)
   → 输出 `CAP <序号> <完整cookie> <base64 PNG>`
② 拉回本机 → 解码 → PIL 拼「带 #编号」的网格大图(放大 6-8 倍, NEAREST)
③ 视觉一次读整张网格, 输出 `#n=xxxxxx`(验证码固定 6 位就强制 6 位)
④ 生成提交脚本:把 (cookie, 口令, 我读的码) 三元组**内联进脚本** → sftp → 批量 POST
```
要点:
- **会话(cookie)必须在取图与提交之间保持一致** —— 跨会话提交必失败
- 用 ddddocr 时**必须加长度校验**(`if len(code)!=6: 重新取图重读`),否则误读率显著抬升
- 批量提交时把 `code` 一起打印出来,便于事后抽查是"读错"还是"真拒"

## 4. ★ 先查有没有"跳过挑战"的前置分支

遇到"验证码挡死"**先别死磕识别**,怀疑实现里有**按参数形态分支**的逻辑。
真实案例(同族两套系统同一写法):
```php
if(!preg_match('/^[0-9a-zA-Z_\-]{6,}$/', $name)) die('账号格式不符');
if(strlen($pass) >= 6){                       // ★ 门闸:只有长口令才校验验证码
    if($code != session('verify')) die('验证码输入错误');
}else{
    die('密码错误');                           // ← 短口令/数组走这里, 根本不查验证码
}
```
⇒ 把参数做**形态变体**逐个试,常见手法:
`pass` 长度 < 阈值 / `pass[]` 数组(触发 `md5(array)=null`) / 字段缺失 / 换 content-type / HPP 重复参数 /
`code` 传空传数组。**观察哪一种变体让"验证码错误"消失** ⇒ 就找到了绕过挑战的分支。
(注意:该分支可能同时是"直接拒绝",那就只是发现了一条语义分支,不等于绕过 —— 用 §2 的表判断。)

## 5. 验证码的两条机制性事实(实测)

| 事实 | 影响 |
|---|---|
| 验证码与**会话 ID 强绑定** | 取图会话 ≠ 提交会话 ⇒ 必失败;批量时逐个候选配对 cookie |
| **一次性失效**:校验通过一次后同会话再提交同一码立即报错 | **1 次解图 = 1 次尝试**,码不可复用 ⇒ 无法"解一次跑一千发" |

第 2 条决定了效率上限:**每条候选都要重新取图 + 读图**。因此字典要**按概率排序**(先跑最可能命中的),让"跑不完"只损失尾部。

## 6. 无 oracle 时的止损判断

**没有账号存在性 oracle**(每个 ≥N 位输入都回同一句通用错误)时:
- 你无法先枚举出有效账号 ⇒ (账号 × 口令) 二维搜索不可行
- 只能**假定一个已知/疑似账号**,拿字典打它的口令
- **判定止损**:品牌/上下文弱口令(几十条)+ 真实员工手机号(几百条)打不出 ⇒
  **该账号口令很强或账号名本身不对**,继续扩字典的边际收益极低 ⇒ 建议向用户说明并换路线,
  而不是无限扩大字典假装还在推进。
