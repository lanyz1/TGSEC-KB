## Procedure

1. **Pull the spec** (rule 1) and list every path + method. If no spec: enumerate from the front-end JS bundles (`import()`/chunk maps reveal the API base and the exact `JSON.stringify({...})` field names) before fuzzing paths. **Then re-mine and diff — the endpoint list is not static.** Grep every JS/HTML fragment you hold for `/ns/endpoint` string literals, dedupe, and diff against your recorded list; sweep only the additions with a valid low-privilege token. A device/SIM control namespace that several earlier sweeps of the old list had missed surfaced exactly this way.
2. **Enforcement matrix** — probe all endpoints unauthenticated (rule 2), in one batched script, printing `status | first 200 bytes`. Batch, don't one-call-per-endpoint.
3. **Craft real bodies for the unenforced writers** using the spec schemas; include the signature/token fields with garbage, and the identity fields with a real target identity (rule 3).
4. **Chain the unchecked writes** — an import/bind that accepts an arbitrary identity usually upgrades another endpoint from "needs a session" to "needs nothing": re-run the token-consumption audit after each successful bind.
5. **Sibling-host sweep** — the gateway's neighbours on the same origin are part of the engagement: enumerate vhosts with the `Host:` header against the origin IP (DNS usually hides them), and look for the paired admin panel, uploader, ad server, or SSO app. An origin discovered through one service is the platform, not a single app. **On a white-label platform the sweep extends past the origin to every brand's backend:** harvest the brand list from two places — a leaked config value that spells out the mapping (`*_proxy_relation` / `*_user_relation` / encryption-domain keys read as `domain_<ids>|<ids>|<ids>`), and each brand's *own* front-end (`var server = "https://..."` in its page JS or `app-config-*.js`, which names the API host that brand actually talks to). Then run the **same** login/enforcement oracle against every backend found, because they typically share one account table but not one account *roster*: an account cleaned up on the backend you started with may still be live on a sibling (and vice versa), so a "dead credential" verdict from one host does not cover the family — and the deltas you collect are themselves a map of what the operator has already cleaned up. Record the family tree; it is a report finding in its own right.
6. **Report** — per finding: endpoint, credential used (none), the exact body, the response proving it, and the capability actually demonstrated. Separate "state changed" from "funds/permissions obtained".

## Pitfalls

- **200 with SPA HTML is not an API hit.** SPA fallbacks answer 200 + index.html for any unknown path; check `Content-Length`/`Content-Type` before scoring a hit.
- **Wrong content type, not wrong credentials.** FastAPI/Spring form-login endpoints return `422 Field required` for JSON bodies — try `application/x-www-form-urlencoded` before concluding the credentials failed.
- **Empty-body success** (`{}`) from a nonce/status endpoint means the endpoint answered, not that the record exists; do not build a chain on it without a second signal.
- **No-schema response is not no-endpoint.** A `404` with a JSON detail means the route exists and the record does not; a `404` with an HTML body means the route is absent.
- **A different 404 body on the same host is a different application.** When `{"scode":404}`-style errors suddenly become a framework default (`{"timestamp":…,"status":404,"error":"Not Found"}`), you have crossed into another process behind the same front-end proxy — its own middleware, path prefixes and default credentials. Enumerate that namespace from scratch instead of concluding the routes vanished; a 200 there with a fresh `requestId` is an unauthenticated write surface, not a read.
- **Don't stop at the first bypass.** The same missing check usually appears on every sibling endpoint (import/ad/bind/claim) — sweep them all before reporting.
- **A client-supplied scope field is a decoy until proven honored.** Sending `userId`/`proxyUserId`/`account` alongside a valid session and getting your own rows back proves only that *that* endpoint re-applies token scope — it says nothing about the sibling that takes a bare object ID. Test the object-ID endpoint on its own before recording "scoped" and moving on.
- **Report reach, not just the flaw.** When an IDOR returns other tenants' records, quantify what is recoverable (distinct owners, distinct subjects/recipients, record count, time span) and hand the extracted corpus over as files. One parameter that reads the whole platform's operational data is the headline finding, not a footnote.
- **A reflective CORS header is only as dangerous as where the session lives.** `Access-Control-Allow-Origin: <any reflected>` together with `Access-Control-Allow-Credentials: true` reads like instant cross-origin session theft, but the browser only auto-attaches credentials the site itself stores in a **cookie**. If the app keeps its session in `localStorage` (typical keys: `token` / `tokenExpires` / `csrfToken`), a cross-origin request carries nothing and SOP blocks reading the response — the reflection is inert on its own, and the chain has to go back through a **same-origin** XSS. Read the app's own login JS to see the credential store **before** promoting CORS reflection to a main line; only a cookie-backed session makes it a direct finding.
- **A generic "anything-but-401" bucket in your matrix script manufactures findings.** If the classifier scores `400 不支持的请求方式` / SPA `200` alongside real bypasses, block-level hits get reported as authz gaps; re-verify every hit with the correct verb and minimal params before it enters the report, or you will retract one mid-engagement (an admin-2FA `unbind` that looked bypassable returned `401` the moment the right method was used). Method-error responses state only "route exists + correct verb" — never a finding.
