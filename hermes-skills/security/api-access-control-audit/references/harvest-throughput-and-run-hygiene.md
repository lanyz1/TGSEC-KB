# 枚举收割的吞吐与运行卫生（把一次“能拿”变成“全量拿完”）

对一个已验证的 IDOR/枚举神谕做全量收割时，**失败模式几乎从不是“接口不通”，而是压速、越界号段白烧、看守进程误判完成、以及重启时把自己的 shell 杀掉**。

## 1. 吞吐：翻倍爬坡，别继承一个“限速”信念

CDN/网关的限速桶按 **(TCP 对端 IP, 主机名)** 分。同一后端常有多个兄弟域名（从 H5/App 的 JS 里 grep API base 得到），
每个 (源IP, 主机名) 组合是一个独立桶；**App API 主机往往比 H5/后台主机宽容得多**。

做法：固定 8-10 组 (源IP × 主机名) 并发，然后**把线程数翻倍**再测，每一步同时记 `命中率 + 实测 req/s`：

| 线程 | req/s | 命中率 |
|---|---|---|
| 20 | 33 | ~100% |
| 40 | 66 | 100% |
| 80 | 131 | 98.7% |
| 160 | **242** | 99.98% |

判据：**命中率不塌就继续翻倍；一塌（例如 73%→8%）立刻回退并记 Deadend**。
反面教训：一条“CDN 按源 IP 限速 ~1req/s、超即黑洞”的旧笔记源于**单个主机名**的观察，被当成全局天花板，
结果 40 分钟能跑完的全段被压成十几个小时。报告里把这条阶梯写上——持续吞吐本身就是对目标的结论。

## 2. 号段边界：先探再排队列

- 用步进/二分探出**真实 ID 下限与上限**（命中一个低值、高一档为空即封顶），再据此切队列。
- **不要相信平台自报的用户数**：资金盘/白标前台显示的“会员总数”常年是虚数（实测自称 468,157，真实可用 uid 段只有 31.8 万）。
- **队列别排序错**：把“已知真空区”（旧库/历史号段）排在真实号段前面 = 白烧成千请求（本役连踩两次）。
  越界的号段直接不排，或 miss 后立刻回写 done 文件。
- 命中率突变先怀疑自己的号段而不是服务端：先在**已知存在**的 ID 上验一发，再下结论。

## 3. 长任务运行卫生（每条都実际噎过）

- **日志无缓冲**：`python3 -u script.py 2>&1 | tee run.log`。被后台化 + 重定向时 Python 块缓冲，进程被杀 = 进度全丢。
- **断点续传靠文件，不靠内存**：done 文件按 ID 记录（miss 也记）；NDJSON 只追加写 + 线程锁；
  每轮打印 `done/ok/miss/rate/eta` 一行。重启不丢进度。
- **“跑完自动建库/打包”的看守进程不能只看主进程存活。** 为了加并发而 kill + 重启收割机时，
  看守看到“进程没了”就会按残缺数据建库打包。改法：判据换成**“进度文件 N 分钟无增长”**，或
  **重启收割机时同步重启看守**。同理，主进程被人停掉时先决定本轮产物是否作废。
- **清理进程禁用 `pkill -f <脚本名>` / `kill -9 $(ps|grep <脚本名>)`**：你**自己的 shell 命令行里就带这个脚本名**
  （同一条命令里既 kill 又 `nohup python3 <脚本名>` 时必然自 match），会把自己 SIGTERM/SIGKILL。
  `grep '<脚本名[3]>'` 的方括号花招**只在同一命令行里没有别处出现该名字时才成立**。唯一稳的写法：
  `ps -eo pid,args | awk '$2=="python3" && $3 ~ /脚本名/' | xargs -r kill -9`。
- **停一个面就把源 IP 让给另一个面**：同一批源 IP 上并行多个收割任务时，低价值任务（旧号段、已作废口径）
  及时停掉，把并发让给主线。

## 4. 收尾

用**算法级校验器**证明数据真实（身份证 mod 11-2 校验位、手机号号段），报通过率与唯一值数。
