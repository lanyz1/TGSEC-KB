# Always-on rules（续：第 10–15 条）

> 从 `SKILL.md` 拆出；主卡保留第 1–9 条。

10. **Role-prefixed realms on one API host are separate credential tables — map them, then prove non-escalation.** One host routinely serves the client, reseller/proxy and admin consoles under path prefixes (`/user/*`, `/proxyUser/*`, `/admin/*`) behind the same session cookie name and even the same RSA login key. Two things to test rather than assume: (a) each realm has its own account table and its own failure code — a valid client credential that fails `/proxyUser/login` with a realm-specific code (not the client's wrong-password code) means the account simply does not exist there, so success on one realm never authorizes another; (b) replay your session token against every realm's identity endpoint and record the exact rejection. An endpoint that only checks token *presence* (a `checkLoginStatus` that returns success) does not prove the token was accepted as that role, and a `logout` answering success may be a no-op. Write "cross-realm token rejected (code N)" down explicitly — that is the difference between a closed door and an untested one.
    - **Calibrate token liveness on a known-open path before recording "session dead".** One endpoint answering a realm/role denial (`scode:2`) while another answers success (`scode:0`) to the *same* token proves the session is alive and the denial is per-endpoint. A single rejection is never evidence of a killed session — and a *stale* credential must be re-verified too: an operator can delete the account mid-engagement, so a token that passed a namespace hours ago can answer "account does not exist" across the whole API now. Re-run one known-good call before building the next link on any token.
    - **Classify the rejection, do not just record it.** Three verdicts look alike and mean different things: (i) `401 未授权` to a garbage/expired token = <REDACTED> or role check failed; (ii) a **distinct** code to a *validly-signed* token (e.g. `1005 管理员不存在`) proves the **signature verified and the role claim was accepted**, and the only failure was looking the account row up — i.e. an admin token for a since-deleted account; (iii) `200` with your own record = the endpoint re-applies token scope. Class (ii) is a lever, not a dead end: because the claim is checked *before* the account query, that token passes the **role gate**, so a per-endpoint diff ("my low-priv token → 401" vs "stale admin token → 1005") maps every endpoint that only asserts a role claim. And replaying that one token against **every brand backend** and getting the *identical* code is architecture proof that the whole white-label family shares one account table and one backend DB — a report finding in itself. Cap the sweep: if the entire endpoint list returns the generic deny code, write it down and stop re-sweeping.
11. **A write endpoint with real-world blast radius stays un-fired.** When the discovered endpoint dispatches to third parties — mass-send / campaign / queue / dialler APIs on a live platform — do not invoke it to demonstrate exploitability. The side effect lands on real people, not on the target, and an untested endpoint still reports fine. Document the endpoint, the missing check, and exactly what a request would carry; leave the send unfired. This user's engagements draw that line explicitly and expect it stated in the report.
    - **How this rule actually gets broken is by accident, through a probe list.** A batch sweep — "URL-parameter SSRF scan", "missing-parameter discovery loop", "all-methods matrix" — runs dozens of endpoints inside one script, and one send-semantics path dropped into that list fires the side effect with no intent and no warning. Before the sweep, filter the endpoint list by **name** against a blacklist (`send`, `push`, `notify`, `message`, `broadcast`, `chat`, `rebote`, `switch`, `delete`, `clear`, `reset`, `update`). Snapshot a **read-only counter** first (`/statistics/list`-style `sendSize`/`createSize`) and re-read it afterwards, so a mis-fire is proven by diff instead of denied. Whatever the diff shows, pull that endpoint out of the list and state the mis-fire in the report — a silent send is far worse than a disclosed one.
12. **Global-config namespaces are a read primitive, and a realm denial may be YOUR request's fault, not the target's authorization.** On Spring-style platforms the config namespace usually auth-gates only *some* sibling methods: `getByKey` demands admin while `userGetByKey` / `proxyGetByKey` check nothing but "is this any valid session on this platform". Send one with any low-privilege token — the response is platform-wide settings, not your own record. Two mechanics decide whether you find it:
    - **Copy the method and encoding from the app's own call site, not from the method name.** The same endpoint answered a role denial (`scode:2`) to a POST+JSON probe and returned data to the GET-with-query-params the front-end JS actually used (`data:{code:...}` in a jQuery `$.post` default). A realm-shaped denial on a guessed encoding is a **false authorization negative** — the mirror of the false-positive IDOR in Pitfalls, and it is why "no permission" is not a finding until the caller's own JS has been read.
    - **A missing key is its own oracle.** An absent key returns a distinct generic error (`500 系统异常` / "missing parameter") while a present one returns the value — so you can confirm candidates instead of guessing, then harvest the key-name space wholesale from the platform's own JS bundles (grep snake_case tokens out of `js/*.js` and page fragments). This is routinely the highest-yield unauth read on a white-label platform: content-encryption keys, operator chat handles and shift rota, business contacts, and full reseller↔customer ID maps.
    - **Calibrate the oracle with a key you know exists before believing any negative.** On one deployment of this family *every* key — including keys whose values had already been harvested — came back with the same `500 系统异常`, i.e. a generic exception rather than an absent-key signal. A key-name oracle that answers identically for a known-present and a known-absent key carries **zero information**: drop it the moment calibration fails instead of hunting the bundles for more candidates.
    - Do not expect the config table to hold infrastructure secrets (DB passwords). Tens of candidates returning absent is normal — stop and go to connection-string leaks, backups, or error echoes.
13. **Generated credentials must be proven to persist before they count as a takeover.** Endpoints that *return* a fresh secret (`generateSecret`, `generateGoogleSecret`, reset-key, mint-token) are reachable with a low-privilege token on many platforms and will hand you a plaintext secret — that is not yet control of any account.
    - **Test with a before/after state delta, not the return value:** read `status?userId=X`, call the generator, read the same status again. Unchanged (`false` → `false`) = a pure calculator with no write, **not a finding** — do not report it as a 2FA/TOTP reset.
    - **Then test the ID namespace:** call it with an admin row's ID from a user-realm token. A distinct "account does not exist" code proves the tables' ID spaces are separate and the realm cannot cross over.
    - Only "the status changed" or "it returned another identity's *existing* secret" is a real takeover. Reporting the generator as one is exactly the inflation this user rejects.
    - **Fastest calibration, do it before any state-delta test:** call the generator **twice with the same ID**. Two *different* secrets = a pure calculator that never touches the stored record — inert, do not report. The *same* secret both times, or a value that matches a secret the target already had, = it is reading the stored seed, i.e. a real 2FA/secret leak.
    - **The same generator is usually an identity oracle.** QR / `otpauth://totp/<Issuer>:<account>?secret=...` responses embed the target's **plaintext account name in the URI path**, so calling the generator across an incrementing numeric ID space maps `userId` → username without ever touching a user table. Harvest that mapping before calling the namespace opaque; it is also what tells you which IDs are worth attacking.

14. **A write into a tenant-shared store is a *delivery* primitive — find where the value is rendered before hunting a payload.** When an unenforced write lands in a table that the admin console (or every customer) renders, the payoff is not the row, it is code running in someone else's authenticated browser: stored XSS → admin session → the platform's own control endpoints. Both questions are answered by reading the app's own code, never by guessing:
    - **Read the row renderer.** Fetch the authenticated page with the low-privilege token, find the table's `createdRow` / `fmtTableLine` / `.html(` / `innerHTML` / `replace("#slot", data)` path, and read the sanitizer it calls. A blacklist that blocks only a **literal substring** (`script`) is bypassable with a different execution primitive (`<img src=x onerror=...>`, `<svg onload=...>`) — and the render path is only proven by this read, not by the write returning success.
    - **Sibling verbs and sibling fields are not equally guarded.** The namespace's *read* verb may be role-gated while an *add/update* verb is not — test every verb under the module with your lowest-privilege token (`/mod/list` → 401 while `/mod/addTemplate` → `scode:0`); a locked verb is not a locked namespace. The payload field may also have a length cap taken from the server's own error text (`模板名称不能超过50`), while a sibling field (content body, remark, batch payload) has none — that one is the longer-payload exit.
    - **Find the writer for a sink field and prove YOUR realm can reach it — before weaponizing anything.** A render map is only half the chain: map every sink field, then for each one locate the endpoint that writes it and test it with your own token. A profile page that exposes *only* a password-change writer (`/user/updatePass`) means the sinks rendering `account` / `userName` / nickname are **unreachable from your realm** — a whole branch to strike off before spending hours on payloads. Confirm the negative the same way (`/user/updateAccount` → `404` = the writer does not exist for this role at all), then move realms instead of re-reading pages. The plantable fields are exactly the intersection of "your role can write it" and "their console renders it raw"; on this family that was template name/body plus, for a **reseller** token only, the child-account name (the reseller-only writer namespace answers a client token with a blanket generic deny). Grow the intersection by **moving realms**, not by re-reading more pages.
    - **A render map is a snapshot, not a live wiring diagram — re-check that the field's data source is still called.** A page that used to load `/mod/list` into the sink can have that loader **commented out** in the version you are about to test (the dashboard moved to a different endpoint), so the payload never auto-fires where the map said it would. Grep the current page source for the loader call and confirm it is live code before betting a budget on "the admin sees it the moment they open the page".
    - **Operational discipline:** keep a listener on a publicly reachable port, and read back the created row's ID at creation time so you can delete it afterwards. Expect the callback hours later when a human opens the page — a quiet log is not a dead chain. Never delete another test team's marker found in the same shared table; record it as independent corroboration.
    - **Plant the same payload in every sink you can write at once — they are independent draws on the same prize.** An operator's navigation is unpredictable, so hit probability ≈ the sum of each sink's page-visit frequency. On one platform three sinks ran in parallel from one script: the reseller-child **account name** (rendered raw in the admin user list, which fired), the **SMS template body**, and a **mutual-send content pool**. All three are write-once-and-forget; none interferes with the others, and a second admin session arriving from a different source IP proved two of them were being visited.
    - **A row-level keyword blacklist is bypassable — retry with a syntactic variant before writing the sink off.** A template-body filter that rejects any line containing `http` (turning a full-document payload into "cannot contain http") was passed by a **protocol-relative** `//host/path` URL, which browsers still resolve and fetch. Sibling variants worth one attempt each: protocol-relative, scheme-only (`https:example.com`), case-mangled (`hTtP`), `\/\/`, and an already-loaded script's `.src`. Also re-use a `400`-style rejection as a *format* hint, not a verdict: `400 不支持的 Content-Type` means the handler is live and wants a JSON body — resend as JSON rather than concluding the write surface is closed.
    - **Read the row back by ID after every plant.** Only the read-back proves the payload survived the store (some pools trim, escape, dedupe, or run a second filter), and it is what lets you delete your row afterwards. Until then you do not know the payload's stored form — and a payload whose stored form was mangled never fires.
    - **Sinks that filter on the way in are still worth a second sink that filters on the way out.** If one writer sanitizes `<`/`>` on input, the sibling that stores raw text and lets *another page's renderer* escape or not is the one that matters — the render map, not the writer, decides.
    - Recipe and payload-sizing rules: `references/shared-data-stored-xss.md`.

15. **Asset-keyed control endpoints are a separate enforcement axis from role-prefixed realms: if a low-privilege token can *name* any asset ID, it usually *acts* on it.** A control API (`/simswitch/*`, `/device/*`, `/command/*`, `/machine/*`) frequently sits on the same API host as the customer portal and checks only "is there a session", so the asset identifier itself becomes the authorization. Find it by sweeping *every* namespace mined from the front-end JS, not just the realms you can log into: the read verb (`slots?deviceMac=`) and the write verb (`switch {deviceMac, slotsPattern}`) are one family, while the neighbours (`/command/at`, `/machine/list`) answering `401` show a single missed interceptor rather than a design choice — say which in the report.
    - **Prove the handler ran with a zero-effect value, never the live action.** Send an out-of-range parameter (a nonexistent slot/card pattern) so the platform answers its own success envelope (`"...request dispatched"`, `success:true`) having consumed the real field names — evidence of the gap, no hardware touched. Firing the live effect (SIM switch, device command, send) is a write with blast radius on real people (rule 11).
    - **A validated parameter closes injection, not authz.** Push special characters and format breaks to see whether the value reaches the device/upstream protocol, but expect a strict regex (`\d+\.\d+(,\d+\.\d+)*`) and stop there: the finding is "a client-role account commands the platform's assets by ID", not RCE.
