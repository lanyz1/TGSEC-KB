## 一、菜单B 数据判定(简化菜单四功能)

### 部署时间界过滤("部署前项目不要")
- 用户口径:只包含"从报名开始就完整拦截"的项目(公告发布时间 >= v6 部署日 2026-08-31)
- 判定字段:**公告发布时间**(queryBusinessNoticeList 的 pubTime / getProjInfo 的 noticeDate)
- **平台无独立"报名开始时间"字段:公告发布(noticeDate/pubTime)= 报名开始**(getProjInfo 实测字段:noticeDate/sellEnddate/paymentDate/bidStarttime/bidEndtime/createTime)
- 实现:主服维护 `pubtime_map.json`(projId→pubTime,来源=公告流拉取 + 公告_831.json 存量),bot 查询时 `pt[:10] >= "2026-08-31"` 过滤

### 分类判定
- 可拦截项目 = stage ∈ {报名中, 待竞价, 竞价中} AND pubTime >= 部署日
- **未开始报名** = 可拦截 + enterpriseCount == 0(公告刚发,还没人报)
- **已开始报名已拦截** = 可拦截 + enterpriseCount > 0
- 功能2/3 = 同分类,行内显示/隐藏审核状态统计(check_status_summary:遍历 pack_map 企业包件审核状态,计 通过/拒绝/未审批/无)

### 已结束项目三分类(功能4,比对用)
- ✅ **完整拦截** = stage 已结束 + 目录有"包件清单.json"或"包件清单_*.csv"
- ⚠️ **部分数据** = 有目录 + 无包件清单(只有 pack_map 等)
- 🗄️ **历史索引** = index 有条目但无目录 = 8515 快照导入的 2022-2023 老项目占位(status 全 14、编号 OG/OH/OR/OK 旧体系、无 bidStarttime)——不是真拦截缺口,对比对无意义
- 实测:12,797 完整 / 0 部分 / 7,922 历史索引(20,719 已结束)

## 二、数据池"不能实时更新"诊断(用户感觉不实时,实际是供给侧枯竭)

### 诊断方法(三步实锤)
1. **企业记录新鲜度分布**:遍历全部 pack_map.json 企业记录"时间"字段(≈票的 operation_time)按新鲜度分桶——99.6% 是 3 天前 = 数据基本不增长
2. **新票供给统计**:看采集机日志每轮"审计 ST N, 新 X"——夜间/周末 X=2-7,识别 0-1 = 人肉操作节奏决定一切
3. **单轮耗时**:日志"轮询开始→完成"间隔 = 60s sleep + 轮内 3-4 分钟(审计5页+目标发现3通道翻页+15候选票识别+全量比对)→ 实际 4-5 分钟/轮,所有延迟放大

### 审核状态更新机制(2026-08-31 后现状)
| 通道 | 状态 |
|---|---|
| getBuyPackageList(企业票→包件+bidderCheckStatusName) | ✅ **唯一活通道**,依赖企业产生新 ST |
| biddingandsellingsupplier(无鉴权企业名单) | ❌ 8/31 起 total=0(数据平台业务表全受限,auditlog/sysfunc 例外) |
| aggregation_bfwz_bfwzpackage_a(已结束包件表) | ❌ 处理异常 |

| 审计日志解析审核操作 | ❌ 只有资质变更审核(复核审核通过/变更审核拒绝),无报名包件审核记录 |

**"审核状态冻结"根因链**:票识别成功后进 seen 集合永不重拉 → 企业报名后不操作=无新票 → 审核状态停在首次识别时刻;8515 兜底停用后无替代。

**验证机制活着的方法**:看**待竞价项目**(报名截止已过)pack_map 审核状态分布——有"通过/拒绝"=机制闭环(实测:无847/未审批259/通过40/拒绝3);**报名中项目全"未审批"是正常的**(报名截止未到,审核员还没开始审),不是数据池不更新。

**修复方向(已提议未实施)**:保留"企业→ST"映射,对待竞价/竞价中项目已识别企业周期性重拉 getBuyPackageList(票 TTL 30 分钟,过期等新票)。

## 三、部署运维坑(本次实测)

- **paramiko 私钥 fallback 坑**:本机 `~/.ssh/id_ed25519` 存在但不是主服密钥 → 认证失败。连接主服一律**强制指定 v6_master_key**,不要用 exists 判断 fallback。
- **SSH 远程 `-c` 传 Python 代码**:emoji/换行经 json.dumps 转义后远程 shell 解析破坏 → 一律 sftp 上传脚本文件再 `python3 /tmp/x.py` 执行。
- **setsid/nohup 启动后 exec_command read 阻塞**:启动命令里的后台进程持有 channel stdout → `stdout.read()` 挂住超时。**read 超时 ≠ 启动失败**(第一次 nohup 实际成功了,误导又启一次 → 双进程抢 getUpdates)。安全流程:①启动命令带 `</dev/null >>log 2>&1 &`;②sleep 后单独 exec 验证 `ps -eo pid,cmd | grep '[p]ython3 pix_bot_server.py'`;③确认唯一实例,多余 kill。
- **pkill 自杀**:pkill -f 匹配到 exec_command 自身 shell(命令行含字面量)→ 用 `grep '[p]attern'` 防自匹配 + 分两条 exec(先 kill 后启动)。
- **时区判定坑**:主服 UTC、采集机/用户北京时间。看到"index updated 停在 22:33"先换算时区(UTC 22:33 = 北京 06:33,刚刚更新),别误判 merger 卡死。
