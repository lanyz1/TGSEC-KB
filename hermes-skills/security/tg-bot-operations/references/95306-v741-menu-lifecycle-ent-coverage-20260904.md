## 2. ent_coverage 空壳根因链与修复(死数据差集跳过失效)

现象:8 台采集机 + 主服 ent_coverage.json 都只有 1 企业 1 条;6 天 313 个榨干回传文件但跳过机制从未生效 → 对已覆盖已结束项目重复榨干(无用功)。

**根因 1(致命):主服系统时区=UTC**,平台时间全为北京时。gen_ent_coverage 用 `datetime.now()` 与 bidStarttime 比较 → 错位 8h,已结束判定乱。修复:全局 `_bjnow() = datetime.now(timezone(timedelta(hours=8))).replace(tzinfo=None)`,所有与平台时间比较处替换。

**根因 2:safe 判定过严**。原规则=企业记录"时间"(pack_map 内,=首次被抓登录时间,多在报名期)≥bidStarttime 才算覆盖。已结束项目(20719 个,6122 带包件)的覆盖几乎全被拒。修复后的认可规则(任一):
- 记录 tm ≥ bidStarttime(报名截止后抓的=完整)
- 项目竞价结束已 >48h:平台数据定稿,pack_map 存量即终稿(审核在竞价开始前定稿,结束后平台不再变)
- 榨干回传文件 mtime ≥ bidStarttime(见根因 3)

**根因 3:文件证据没被利用**。`/data_raw/<城市>/_ent_full_*.json` 文件 mtime=真实拉取时刻(JSON 内"时间"字段=企业登录时间,不可用)。注意两坑:
- `_ent_full` 内 `bidStarttime` 字段**常为空** → 项目竞价时间须从 index.json 取(文件内取会全挡)
- 782 条文件记录中 781 条是**进行中(未来竞价)项目**——fts<bidStarttime 正确排除(活数据永不跳过);不要因此怀疑文件证据

**验证**:修复前 1 企业/1 条 → 修复后 **3405 企业 / 51502 条**可跳过(总 51678 条里剩 176 条真实缺口)。

**部署细节**:gen_gap main() 每 6h(cov_ts 超 21600s)才重新 gen_ent_coverage+推送;手动改完要手动 push_to_collectors。手动推送 8 台时:超时的 exec_command 远端进程不死会残留并发(阿里云对同源 SSH 并发有限制,3 进程互相卡)→ 用 setsid nohup 后台跑+日志轮询,或接受 6h 兜底自动推送。

## 3. 平台侧验证手法(漯阜案例)

用户指定「漯阜铁路有限责任公司 2026年报废机车公开竞价处置项目」,数据池搜不到精确名 → 实为平台公告名「2026年第3次废移动设备物资处置项目」,且**同一主题拆成两个公告**:
- B: 8/25 公告(ON002026082508284281,7包:韶山6B/东风4/金鹰轨道车/平板车/行李车),报名截止 8/31,竞价 9/8
- A: 8/27 公告(ON002026082716462849,6包),报名截止 9/2,竞价 9/9 — 名册 25 家

B 名册 0 家 → 判定"我们漏采 vs 平台真相":直接调 `biddingandsellingsupplier`(cg.95306.cn/proxy/dataplatform/api/findList,startDate/endDate 窗口)全量拉 + 本地按 proj_code 过滤:
- **接口 proj_code 参数不可信**:带参数时返回 500 行全量且 bidder_name 全 null(参数被忽略或触发汇总模式)——不要用该接口做服务端过滤,全量拉本地筛
- B 仅 1 行公告行(bidder_name/buy_time 全 null)= 平台侧该 code 无任何报名记录 = **平台真相是 0 家报名**,非采集遗漏
- 解读:同一批次物资平台可能 8/25 发 B 后 8/27 又改发 A,B 实际作废/并入 A;真实活项目=A

通用手法:对"采集缺口"疑问先验证平台侧原始数据(名册接口/公告全文),区分 平台真相 vs 管道问题,再决定是否修管道。
