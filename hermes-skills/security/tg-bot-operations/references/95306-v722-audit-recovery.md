## 1. 审计→ST 捕获链路(核心机制)

```
审计日志(auditlog findList)= 系统操作登记簿
每次 business-proxy 操作(报名/查看/审核)记一笔,含 serviceTicket(ST)
ST TTL = 30 分钟(服务端控制,过期作废)
getBuyPackageList(projId) 必须用"报名了该项目企业的有效 ST"才能拉到它的报名包件明细
```

**采集机两个过滤坑(本次修复):**
1. 审计条件只抓 `operation_details like %redirectEnrollUrl%`(报名操作)→ 登录查看/审核操作全漏
   → 修复:`like %`(全部操作)
2. ST 提取正则只认 `bfwz-view/#/auction/manage/allProject?projName=...&serviceTicket=` 格式
   → 修复:通用 `re.search(r'serviceTicket=([0-9a-f]{32})', det)`,projName 单独可选提取

**效果**:审计 ST 每轮 0-1 → 9-10 个;目标项目 38 → 41。
**用户认知要点**:用户登录后"应该被采到"→ 解释时说明:审计有记录但过滤丢了 = bug 可修;若 ST 已过 30min TTL = 接口时效限制,只能等再登录或提供账号密码登录拉取。

## 2. 统计幻觉两层根因(企业查询"已报名/包件/参与项目"与实际不符)

### 第一层:孤儿记录(status 空被算"进行中")
- 08文件(615,267 条,2022-2025 已结束项目全量)导入时**项目没进 index**(只有企业档案带官方 projId)
- 档案记录 projId 在 index 找不到 → `info={}` → `status=""` → 不计入已结束 → **全部虚增为"进行中"**
- 实测:50,636 条记录中 23,776 条孤儿(47%)!
- **修复:08文件项目全量补入 index**:按 projId/projCode/projName 去重(14,056 个)→ 与现有合并(命中 6,101,新增 7,955)→ index 13,182 → 21,137;孤儿 0,命中率 100%
- 补入字段:`status="14"`(已结束),live=False

### 第二层:空账号匹配(误合并无关企业)
- 实时合并条件 `账号 == acct`,档案账号为空("")→ **空==空 匹配所有无账号记录** → 无关企业全部算进来(陕西新瑞凯达虚增 21 个"进行中")
- **修复:严格匹配** — 仅 `(归一化名 u2 == unit)` 或 `(acct 非空且 a2 == acct)`;去掉 `ev2.单位 or ek2 == unit` 宽松匹配
- 项目级记录(无包件编号)显示"项目级"而非虚报"1包";pack_n 只累计有真实包件编号的

### 数据质量修复方法论汇总
- 企业名归一化:供应商主数据(369K)建 `核心名(去后缀)→全称` 映射,`_norm_key` 去"再生资源回收有限公司"等后缀;O(1) 缓存查找(不要每企业遍历 369K 文件!)
- 账号补全:同账号其他记录有名字 → 补全 `resolve_acct_name`(全库扫描缓存 5min)
- CSV 生成三层兜底:`norm_ent_name → resolve_acct_name → 账号/ek`,三处生成器(报名明细/18列/查询工坊)都要改
- **merger 实时汇总写独立文件**(实时项目汇总_18列.csv),绝不覆盖全量历史(221,661 行被覆盖成 42 行事故!)
- 启动预热缓存线程(_warm_caches),防首次查询卡 2-5s
