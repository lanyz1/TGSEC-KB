# TG Bot 手机 UX 模式与运维坑(2026-08-29 会话沉淀)

## 1. 手机自适应项目列表(核心模式)

**问题**:TG inline keyboard 按钮在手机上宽度有限,长项目名(30-45 字)必然截断。

**方案**:"文本行 + 数字直达按钮"
```
📁 实时项目 | 第1/6页 (共29个)
━━━━━━━━━━━━━━
1. 🔥 广西沿海铁路经贸有限公司2026年第17次废钢铁物资处置项目   ← 纯文本,自动换行,长按可复制
   🕘08-31 09:00 | 🎁6包 🏢0家
...
📄 回复数字或点按钮查看详情
[1] [2] [3] [4] [5]      ← 数字按钮(短,手机友好)
[⬅️] [1/6] [➡️]
[🔙 返回]
```

实现要点:
- `render_list(cid, title, items, page=0, per=5, back="main", note="")` 返回 (text, kb)
- 列表状态存内存 `LIST_STATE[cid] = {"items": [pid...], "back": cb, "title": str}`(不占 callback_data 空间)
- 回调:`listopen:{idx}`(数字直达,内部 `list_open(cid, idx)` 读 LIST_STATE + record_browse + 发项目卡片)、`listpage:{page}`(重渲染)
- handle_text 里**数字回复优先于 PENDING_INPUT 判断**:`if t.isdigit() and 1<=int(t)<=9 and LIST_STATE.get(cid): list_open(cid, int(t)-1); return`
- 每页 5 个(全名占 2 行 × 5 = 10 行文本,手机上可读)
- 分页边界:page 超界自动修正 `page = pages - 1`

## 2. TG 按钮宽度真相(用户强迫症实测结论)

- **全角空格填充会被 TG 渲染裁剪/忽略**——wide_center() 方案无效
- 按钮宽度由**真实文本长度**决定,一行 2 按钮按文本比例分配
- 手机一行 2 按钮:**文本 ≤6 字**(emoji 2 + 2-4 字)才能显示全
- 18 字符描述文本(如"📁 数据池(实时项目)")手机上会被截断 → 用户反馈"显示不全"
- 想要更宽 = 每行 1 按钮(全宽),或接受截断
- 结论:短文本 + 描述放文本区,不要放按钮里

## 3. TG 无原生"点击复制"

方案:项目详情加 `copyname:{pid}` 按钮 → `answer_cb("📋 已发送,长按复制")` + 单独发一条消息:

```
📋 **项目名称**(长按复制):

`沈阳铁道工业集团有限公司2026年第82次废钢轨物资处置项目`
```

## 4. 公告推送去重

**问题**:部署脚本重复执行(分两次跑看输出)→ 同一版本公告推两次,用户不满。

**方案**:`push_update(version, changes, stats, manual=False)`:
- 非 manual 时读 `/opt/v6/last_push.json` {v, t}:同版本且 <30 分钟 → 打印 `[公告去重] 跳过`,返回 []
- 推送成功后写入 {v, t}
- manual=True 强制重推

## 5. 正则批量删代码块 = 灾难(已踩两次)

用 `re.sub` 删除回调分支会**误删相邻分支**(accel/settings 回调被删 → 按钮点击无反应,用户发现)。

**纪律**:
- 删除功能 = 精确 patch(带完整上下文 old_string),不用正则跨块删除
- 删除后必须跑"回调对账":提取所有 `callback_data": "xxx"` vs 分支(`elif data == "x"` / `elif data in (...)` / `elif data.startswith("x:")`),找出无对应分支的按钮
- 对账脚本注意 `elif data in ("a","b")` 形式和 startswith 前缀(否则误报)
- 已知无害残留:死函数里的按钮(cat/mysubs)不渲染,不影响;`if data == "main"` 不是 elif,对账脚本会误报

## 6. paramiko heredoc 不可靠(反复踩)

- `exec_command("python3 << 'EOF' ... EOF")` 经常不执行/无输出(引号嵌套、EOF 匹配问题)
- **可靠做法**:本地 write_file 脚本 → sftp.put 到 /tmp/xxx.py → exec_command("python3 /tmp/xxx.py")
- 所有需要多行 python 的诊断/批量操作一律 sftp 上传

## 7. 启动预热缓存(防首次卡顿)

首次调用遍历 13K 文件/369K 文件名的函数(账号→企业名映射、供应商名列表),首次使用会卡 2-5 秒。
**方案**:启动时 `threading.Thread(target=_warm_caches, daemon=True)` 后台预热(`_sup_names()` + `resolve_acct_name("__warm__")`)。

## 8. 企业数据源限制(解释"项目企业 0/幻觉")

- `getBuyPackageList` 只能拉"**该 ST 企业自己的报名包件**",ST 有效期 30 分钟
- 报名截止早的项目(企业 8/23-25 报名)ST 全过期 → 实时拉不到 → 显示企业 0
- 补法:①官方快照文件(8515/08文件)按 proj_code→projId 导入 ②等企业再次登录(审计出现新 ST 自动捕获)③用户提供企业账号密码登录拉取
- 8515 部分项目只有公告行无企业(真没报名数据);重复公告(同编号两个 projId)会导致一个显示 0
- 不同数据源字段差异 = VOKE 说的"不同文件内容不同":dwhz 企业自填名(简称)、官方库全称、接口漏名("?")——三源差异

- 项目名:所有展示处全量显示(不截断),长按可复制;列表用文本行方案
- 企业查询:只统计进行中(已报名未结束),显示"已报名: N(进行中 X | 已结束 Y)",记录显示 项目名+包件编号(不显示时间),加基本信息(账号/信用代码/手机/法人/联系人/地址)
