# v7.24 ST 利用率机制重构:失败重试队列(2026-08-30)

## 背景
用户反馈"st的利用率太低了"——统计实测:bot 搭建至今 4 台 seen_st 各 43(全局≈43),全部尝试过,成功仅 2 家新企业 → 利用率 4.7%。

## 根因:seen_st 一次性标记 = 利用率杀手
老逻辑:`seen.add(st)` 在**第一次尝试时**执行(不管成败)→ 失败票(超时/WAF抖动/接口异常)永久放弃,哪怕 ST 还有 29 分钟有效期。
→ 43 个票里 41 个失败票全部浪费。

## 修复:三层机制(4 台采集机已部署)
```
第1层 新票即试:审计抓到新 ST → 立即 /user/info + 拉包件
第2层 失败重试:失败票进 retry_st 队列 → 30min TTL 内每轮自动重试
第3层 补拉兜底:审计里 30min 内(仍在TTL)的票,含旧 seen 失败票 → 每轮重新入候选
成功 → 永久 seen;过期(>30min 按 st_times 首次发现)→ 才丢弃
```

## state.json 字段(统计口径)
- `seen_st`: **成功利用**的 ST(永久,不是"见过")
- `retry_st`: {st: {acct, tm, tries}} 待重试队列(TTL 内每轮清点)
- `st_times`: {st: 首次发现时间} — TTL 计算依据,过期票从 retry 删除
- 统计回答口径:抓取总数 = len(seen_st)(跨台去重);利用尝试 = seen + retry 历史;成功 = 日志"识别 N"行(格式 `  acct (用户名/单位名)`)

## 关键代码要点
```python
# 候选 = 新 ST + 未过期重试票 + 审计里30分钟内(仍在TTL)的票(含旧 seen 失败票补拉)
cutoff = (now_ts - timedelta(minutes=30)).strftime("%Y-%m-%d %H:%M:%S")
for t in tickets:
    if t["st"] not in candidates and t.get("time", "") >= cutoff:
        candidates[t["st"]] = t
# 成功才 seen.add(st) + retry.pop(st);失败 retry[st] = {tries+1}
# 每轮日志: 轮询完成 ... 识别 N, 重试队列 M  ← 利用率可观测
```

## 附带提升
- 审计翻页 2页(200条)→ 3页(300条):审计 ST 18→22 个/轮
- 日志每轮打印"识别 N, 重试队列 N"——利用率可观测,不再黑盒

## 遗留事实(无法绕过的硬限制)
- 审计里的历史 ST 全过期(30min TTL),**重试也救不了死票**——只能救"TTL 内失败"的活票
- 提升利用率的唯一路径 = 产生新票(用户账号现在登录 / 提供账号密码走官方登录链拉完即弃)
- 审计"新 0"持续 = 系统无新操作,不是采集挂了(与 session15 参考一致)
