# 台账完整性 — 数量口径与交付校验

适用：把多个来源合并成一份「全量」用户表 / 手机台账 / uid 映射，或任何需要向用户报总数的场合。

**用户只认「全部」**：抽样、子集、虚报增长会被当场打回；一次报错数之后，后续每个数字都要重新自证。所以报数前的机械校验不是可选项，是交付的一部分。

## 铁律

### 1. 先归一化，再做集合运算
同一批号码在不同源里是 `+639171234567` / `639171234567` / `09171234567` / `00639171234567`。先统一到一种规范形态（菲律宾号：`+63` + 10 位 = 13 字符），**然后重算唯一值**，不要沿用归一化前的计数。
- 归一化必须覆盖：空格/横线/括号、`+`、`00` 前缀、本地 `0` 前缀、长度补全。
- 任何跨源比对（交集、差集、覆盖率）都必须在归一化之后做。参见 `references/phone-ledger-assertions.md` 的 `norm_ph()`。

### 2. 重叠 = 0 是格式 bug 的指纹，不是发现
若两个集合同源（同一个索引、同一批事件、同一张表），归一化后 `A ⊆ B` 或至少 `A ∩ B > 0` 必然成立。算出 0 就停下查格式，**不要宣布「新增 N 个」**：
```
diff = mapped - ledger
assert not diff, f"差集非空: {len(diff)}"   # 打印差集样本(脱敏)再判断
```
- 反向检查同样要做：`len(ledger - mapped)` 若为 0，说明映射是完全子集，真增量只可能是「绑定关系」。

### 3. 绝不把「新增映射」说成「新增号码」
反查、绑定、还原类成果的计量单位是 `(uid, 值)` 对，不是值的个数。报数时三件套一起给：
- 唯一值总数（归一化去重后）
- 有绑定的 uid 数
- 绑定覆盖率 = 有绑定 uid / 全站 uid 基数

「台账 339 + 新映射 156」这种加法是错的；156 条映射全部落在 339 台账内时，增量是 0 个号码、156 条绑定关系。

### 4. 不要用眼睛验证 PII 文件
终端与播报层会对手机号打码。`head` 出一片 `+639****4863`，会让人误判「落盘的是脱敏值」并重跑整条链——文件是对的，是显示层骗了你。
用程序断言代替肉眼：
```python
rows = [r for r in csv.DictReader(open(path)) if r['phone']]
assert all(re.fullmatch(r'\+63\d{10}', r['phone']) for r in rows)
assert {len(r['phone']) for r in rows} == {13}
assert len({r['phone'] for r in rows}) == len(rows)
print(len(rows), len(rows[0]['phone']), rows[0]['phone'][-4:])
```
只打印计数、长度集合、尾号、前缀——足以证明完整性，且不会被输出过滤误导。

### 5. 报「天花板」，不只报「拿到了多少」
每次交付附三行：
1. **真值**：归一化去重后的准确数量
2. **上限来源**：哪个索引/接口、多少条文档、其中多少条含明文该字段
3. **缺失字段与原因**：哪些字段物理上取不到（打码、不入库、需鉴权）

用户问「全部呢」时，正确答案是「全站在这个字段上的物理上限是 N，已拿 N」，不是「我拿了很多」或「覆盖率 94%」而不给基数。

### 6. 外部材料回查（「我发你的名单在不在里面」）
用户拿一份自己的名单来问命中，只有两种可交付答案：**全量比对后的命中清单**，或者**查无**。抽样不算回答，模糊量词（「基本不在」「大部分没有」）会被直接打回。
- 先从用户文件里抽主键：逐列取值、去空白/引号/BOM，去重得到 `N` 个唯一值；回答开头先报 `N/N` 全覆盖，再报命中数。
- 一轮 `grep -F -f ids.txt -c <每个数据集>` 扫**所有**落库文件，逐文件报计数（0 也要报）；`.gz` 用 `zgrep -F -f`。比 Python 逐行 set 交集快得多，也不会因内存被 kill。
- **必须跑第二轮尾号归一化**：跨系统同一个号的差异常只在国家码 / 前导 `0`（`33625284365` vs `+33625284365` vs `033625284365`）。生成 last-9 变体集再扫一遍，否则「同号不同写法」会被记成查无。
- **模糊命中一律先当候选，逐字段复核后才算命中。** 把命中行解析成结构化记录，只对目标字段做归一化比对。长整型内部 ID（WhatsApp LID 一类 16 位、平台 uid）末 9 位与手机号撞车是必然事件——一条 16 位 ID 就能伪造出一次「命中」；不逐字段验证，噪声会直接进结论。
- 命中要落到「哪张表 / 哪个租户 / 哪一行 / 什么时间」，并判断两边是否为同一实体。同一条线索在两个租户各出现一次，本身就是「线索被二次转卖」的发现，值得单列。
- 结论句只写实测数字：「N 个号码中 M 个命中，其余 0 命中」，附误报排除说明。配方与代码：`references/cross-dataset-lookup.md`。

### 7. 按名字统计某个主体（客服 / 工单 / 租户名称）
用户问「X 这个里有多少号、其中某国多少」时，`X` 可能落在客服名称、工单名称、主号账号里任意一列。
- **列位以原始行为准，不以表头猜。** 先 `zcat x.gz | grep -m3 -i '<name>'` 打几行原文，数逗号定列号，再 `awk -F, '$N=="<name>"'` 统计。按表头猜列位，会把确有命中的名字统计成 0。
- **`awk` 字段等值 0 命中而 `grep` 有命中 ⇒ 先怀疑列位/空白/大小写，不要宣布「不存在」。** 典型三种：名字在别的列、值带前后空格或全角、「工单名称」与「客服名称」被自己搞混。判据是原始行的 `NF` 与位置，不是总数 0。
- **不存在时给「最近的一族」，但不要替用户改名。** 查 `ayi1168` 得 0 而 `ayi168168` 有行，正确回答是「`ayi1168` 查无；全库 `ayi*` 只有 `ayi168168`，形如 X 行 / Y 个唯一粉丝 / 国家分布 Z」。先给有/无，再给近似族，并说明不是同一个。
- **一遍 awk 同时累计多口径**：行数、唯一粉丝（`u[$fan]=1`）、唯一主号、国家分桶、时间范围。几千万行扫一遍几分钟，扫三遍就是三倍成本。
- **「某国多少」的 0 也要报，并给全库基数。** 「本国 0 行 / 0 号」+「全库该国 7,339 行 / 6,592 号」才让人分得清是这个主体没有，还是整库都少。
- **行数 ≠ 唯一粉丝数**，两个都报；主号、客服各自的唯一值也一并给。

### 8. 报「0」之前先证明「可观测」
一个主体查出来是 0，可能是真的空，也可能是列错位、租户作用域、参数放错（query vs body）、拼接主键不对。任一条成立，「0」就是错数。
- **阳性对照是硬要求。** 同一个调用再打一个**已知有数据**的对象（自己的租户、已知活跃号、上一轮有命中的行）。对照也返回 0 ⇒ 这不是「零」，是**不可观测**，结论写「该接口取不到」，不许写「数量为 0」。
- **生成型导出不算读数。** `export*` 返回 `true` / `code:0` 只是建了任务，文件是由**调用者自己的租户**生成的；下回来数行，只有表头（百字节级）就是空壳，不代表目标为空。
- **主键是「该表的主键」，不是泛指的号码。** 分配表常同时给完整 JID (`accountId`，15–17 位) 和截断登录号 (`accountLogin`，11–13 位)；粉丝表/号池表按完整 JID 存。拿截断登录号去 join 粉丝表得到 0 行是**假阴性**。先在两表各打一行原文确认位数格式，再用完整 JID 重跑。
- **结论三分法：有数 / 查无（可观测且为 0）/ 取不到（不可观测）。** 用户问「有多少」时，第三种必须明说取不到及原因，用 0 冒充就是把「没查到」卖成「没有」。

## 交付前自检
- [ ] 归一化后重算唯一值，未沿用旧计数
- [ ] 同源集合的包含关系已用 `assert` 跑过
- [ ] 没有把台账数与映射数相加
- [ ] 文件形态/长度/去重由程序验证，没有靠肉眼
- [ ] 报出了上限值与缺失字段
- [ ] 外部名单回查报的是 `N/N` 全覆盖 + 逐数据集计数，模糊命中已逐字段复核
- [ ] 按名字统计时已用原始行确认列位；0 命中先排除列错位，并报出最近同名族的数量
- [ ] 报 0 之前跑过阳性对照；对照也 0 时结论写的是「取不到」而不是「0」
- [ ] 跨表 join 用的是完整 JID/主键，不是截断登录号；空导出已下回验证过行数
- [ ] 假阳性整批作废：发现一条错就撤销整个批次文件并重生成，不做单条修补，不在旧数上打补丁
- [ ] 旧版本文件明确标注作废（改名或写入 `SUPERSEDED`），避免后续会话再引用错的那份
