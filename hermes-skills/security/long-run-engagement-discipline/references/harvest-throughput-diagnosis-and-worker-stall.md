# 多机抢收集群吞吐骤降的诊断与翻盘(2026-09-14 实测)

> 本文件是 SKILL.md §6 的详规。适用:多跳板/多出口对同一目标做**按波次/按游标逐条取数**的长跑采集,
> 产出突然从"每分钟几十条"掉到"几乎不动"时。

## 一、核心结论(先看这三条)

1. **吞吐掉了,先怀疑自己的 worker,最后才怀疑目标。** 本会话在这个判断上错了一整个阶段。
2. **头号真凶是退避上限设太大** —— worker 睡在指数退避里,而目标桶其实几分钟就恢复了。
3. **次号真凶是自己反复改架构** —— 每次重启都打出一轮突发,把刚恢复的封禁窗口重新续上。

---

## 二、30 秒判定:先量单发延迟,不要猜

对被判定为"限速/封禁"的那条正常请求,直接量 HTTP 码 / 响应字节 / 耗时:

```bash
for i in A B C D E F; do
  curl -sk -o /dev/null -w "code=%{http_code} size=%{size_download} t=%{time_total}\n" \
    --max-time 40 --resolve <host>:443:<ip> "https://<host>/<正常请求>"
done
```

本会话真实输出:

```
id=191300 code=200 size=49786 t=0.273s
id=191301 code=200 size= 5995 t=0.104s
id=191302 code=200 size= 3837 t=0.103s
id=191303 code=200 size= 7211 t=0.126s
id=191304 code=200 size=57694 t=0.374s
id=191305 code=200 size=57870 t=0.254s
TOTAL=2s for 6   ⇒ 3 发/秒,全部 200,桶完全健康
```

**判读规则:**

| 观测 | 结论 |
|---|---|
| 亚秒延迟 + 全部 200 | **目标健康,瓶颈在自己这边** |
| 0.05–0.08s 秒回 403 | 边缘层硬规则封禁(见 `ip-ban-bypass` 的 ATD 模型) |
| 延迟随速率上升 | 服务端自适应节流(正常,别当故障) |

## 三、头号真凶:退避上限(backoff ceiling)

**故障链:**
1. 一次突发把桶打进封禁
2. worker 命中失败 → 退避 `60 → 120 → 240 → 480 → …`,上限设成 **1800s**
3. 桶其实 **几分钟**就恢复
4. worker 却每 **30 分钟**才醒一次 ⇒ 桶有 90% 的时间在空转
5. 8 个 worker 合计只出 **17 波/分钟**

**修复与效果:**

| 退避上限 | 聚合吞吐 |
|---|---|
| 1800s | 17 波/分钟 |
| **300s** | **500 波/分钟**(30 倍) |

**经验值:退避上限 ≈ 目标恢复时间量级的一半。** 不要用"我很怕被封"的心理值去设。

**配套:周期性重启 worker(如 cron 每 45min)是正面操作** —— 重启会把退避复位,
能第一时间抓住恢复窗口;但**重启节奏必须长于封禁窗**,否则重启本身就是新突发。

---

## 四、次号真凶:架构反复折腾

**失败的教训:**
- 用 6 并发做实验拿到 +80% 瞬时吞吐 → 误判"并发是净赚"
- 于是起了一波 **28 个并发 worker** ⇒ **全部 14 个桶一次性被推进深度封禁,损失数小时**
- 之后又连续 3 次改架构重启 ⇒ 每次都把刚要恢复的窗口重新打爆

**纪律:**
- **管线一旦能跑,就不要再改架构。** 想改先写进待办,攒到一个冷却窗口一次性改完
- 封禁是**滚动时间窗**;架构每变一次 = 重新开窗计时
- 判断"变了有没有变好"要**一次只改一个变量**,别一次改五处再猜

---

## 五、并发在"按 (出口IP × Host) 记账"的桶里不涨总量

- 实测 6 并发:瞬时 +80%,随后**全桶一起停摆**,总量不增
- 原因:桶按"速率窗"记账,并发只是把额度提前烧完,然后一起进封禁
- **正确做法:一个 (出口 × Host) 只放一个 worker,让服务端自然节流**

## 六、附带的两个工程坑(本会话踩过)

### 1. 回传打包前必查大小写碰撞(会静默毁数据)

```
tar tzf pack.tgz  列出的文件  →  hv_N1.txt (24.6 MB) 在列表里
解压到本地后实际存在          →  hv_n1.txt (36 B)     ← N1 被 n1 覆盖!
```

- 成因:**NTFS/Windows 大小写不敏感**,`hv_N1.txt` 与 `hv_n1.txt` 是同一个文件
- 症状:tar 能列出但解压后"消失";本地数据静默回退(191769 → 175388)
- **修复:在远端改掉撞名的一方**(`mv hv_N1.txt hv_M1.txt`),而不是在本地猜
- **预防:命名 tag 时避免只靠大小写区分;打包前先扫碰撞**
  ```bash
  ls hv_*.txt | sort -f | uniq -di     # 输出非空即有碰撞
  ```

### 2. 交付 CSV 必须先验列对齐再交

本会话交付过一次**列错位**的 CSV:表头 10 列、数据行 9 个值,
`items` 位置是空、`is_drugs` 位置放的却是 `银联支付`。

- **根因**:解析器字段映射写错,没对着**原始 JSON**核对就全量跑
- **规矩**:
  1. 写解析器前,先 `head -c` 看一条**原始 JSON**,按真字段名映射
  2. 全量跑完后,`head -3 <csv>` **肉眼核对前几行**,并断言每行字段数 == 表头数
  3. 加一个 `BADROWS` 计数落进 stats,非 0 不出包

### 3. 别从业务 ID 结构反推日期

- 本会话假设订单号是 `YYMMDDHHMMSS+NNN`,结果**同一批数据里存在两种格式**
  (`260307155418894` 与 `202406171553981`),推出来的月份全是垃圾(`2020-24`)
- **规矩:日期一律取权威字段**(本目标有独立的 `fhsq` 发货日期字段),ID 当不透明串处理

## 七、worker「活着但不动」:判活看产物,不看进程

- **判据是 CPU 时间 + 产物增长**:`ps -eo etime,time,args | grep "[s]cript"`。
  **进程存在 ≠ 在干活**:实测两条接管线跑了 41 分钟、CPU 只累计 **2 秒** ⇒ 不是慢,是每发都失败后 sleep。
- **Windows/git-bash 下 `ps -W | grep <脚本名>` 可能根本看不到 python 子进程** ⇒
  别据此判"进程没起来/已死",统一以**输出文件行数是否在涨**作为唯一判活标准。
- **起接管线的条件 = 原线确认停写**。原线可能只是慢;原线未停就起重复线 = 把同一段路走两遍。
- **两条线可能互为逐位重复**:起点与步长**完全相同**的两条线,每个请求位置都一样 ⇒ 后起的那条产出**零新增**
  (文件名/日志不同骗不了它)。开新线前先比对 (起点, 步长);
  用户说"顺手把冗余的停掉"时,这就是**可自证的停线理由** —— 停它立刻腾出出口额度、不损失任何数据。
- **杀并行单线:用该线独有的参数做 discriminator**(如该线的起点),别只用脚本名:
  `pkill -f "[d]ump.py <该线起点>"`。失败签名 = 通道 **rc=-1 且无输出** —— 说明命令串里的
  **不带方括号的真实字面量**把**自己的 exec shell** 也匹配杀了(见 `remote-daemon-ops` §坑1),
  后续命令全部没执行。**杀与启拆成两条独立命令**,杀完立即报"停了几条、还剩几条"。
- **接管起点必须先探**:从旧断点另起接管线前,对断点做一次偏移探针。断点落在稀疏区(404 荒漠)时,
  新线会连吃几小时 404 且 0 产出 —— 把"提速"变成"空转"。
- **404 不重试**:确定性结果,重试只白等 sleep;只重试传输层异常。
  ★ **重试会污染你自己的错误计数**:同一个 404 被重试 3 次 ⇒ 日志 err% 被抬成真实值的 **3 倍**
  (实测日志里写"25% err"、按 HTTP 码分类实测只有 **3~7%**),且每发白睡数秒,吞吐虚损约 **40%**。
  **要判真实失败率,必须另跑一个"不重试"的诊断版**(限时 90 秒、按 HTTP 码分类计数),以它的输出为准 ——
  一条跑了很久的线的日志 err%,**不能当成失败率拿去汇报**(据此判定"目标限流/荒漠"就是错判)。
- 长跑 `setsid ... </dev/null &` 脱离终端;断点续跑 = **JSONL 追加写 + 启动时读末行 max(请求 id)**。
