# 验证纪律:回显被吞的步骤一律按「未验证」处理

来源:一次长时渗透作业中,脚本 stdout 多次被折叠成 `(N lines output)` 摘要,
**执行者看不到内容却差点把那些步骤的推断当成战果汇报**。这不是链路问题,是**汇报纪律问题**。

## 铁律

1. **看不到回显 = 没有依据**。用户铁律是「别靠猜,事事要有依据」——
   被折叠/被吞掉的输出**不是依据**。凡"我没真读到输出"的结论,一律按**未验证**处理,
   不许写进战果、不许当"已打通"往上垒下一步。
2. **宁可拆小重跑复核**,也不要靠记忆或叙述惯性缝合结论。
3. 一条链只要有一环未验证,**整条链的结论就要标"未验证"**,别用"应该已经……"过渡。

## 工程做法:让回显活下来

- 脚本 stdout **只 `print` 几行"键=值"短结论**(状态码、关键字段、路径、计数)。
  把大对象写成文件、只回传摘要;需要细节时**小步多次**读。
- 长逻辑封进**模块文件**(可复用的 `*.py` 辅助模块),而不是每次内联一大坨;
  内联大段代码本身也容易被折叠/被护栏拦。
- 关键结论**落盘留证**(写进工作目录的结果文件),后续步骤从文件回读,不依赖对话里的回显。

## 汇报格式:分栏 + 显式作废

长作业交进度时,把结论按证据强度分栏,并**主动列出由此作废的旧结论**:

```
### ✅ 亲眼见到回显(可作依据)
| 结论 | 依据(哪次调用、什么文本) |

### ⚠️ 回显被吞,不算证据(我此前据此下的结论作废)
- 原以为……,现按未验证处理,需重跑复核

### ❌ 已确认失败 / 🟡 残留与还原账
```

- **作废要主动说**,别让用户拿着你上一轮的错结论继续往下走。
- 残留账按「位置 / 现状 / 还原动作」三列列全(改过的配置、写进去的文件、建过的记录、
  本机临时票据与脚本),这是这类作业的交付底线。
- 结尾给**可执行选项**(继续/收手各自会发生什么),而不是替用户拍板。

## 反例(两个都真发生过)

- **把"探测不到落点"当成"这条链死了"**:实测真因是处理器里有 `defer os.RemoveAll(临时目录)`
  ——产物落地后被删。事后探测必然 `ENOENT`,与"没落地"完全同形。
  ⇒ **同形证据不足以判死**,先排除"已被清理""同名对象占位"这类干扰再下结论。
- **把协议响应当业务成功**:接口恒回报"成功"(消息写死),但磁盘/列表里没有任何产物。
  ⇒ **验收标准是取回产物**,不是响应码、不是状态字段、不是消息文本。
