# 自伤事故:状态变更型执行汇打坏了生产状态,同轮回滚

**事故类别**:把"能执行"的接口当成果,直接在**共享/生产**对象上打了一发,
服务端**强制**覆盖了安全开关 → 真实生产状态被改。

## 事故本体(可作为检查清单模板)

- 目标:证书轮换执行器 `POST .../signingCerts/rotations/save` + `/rotations/run`
- 我送:`{"Name": "<穿越/注入串>", "RunAt": <过去时间>, "generateCount": 1, "disablePrevious": false}`
- **服务端响应里 `disablePrevious` 变成了 `true`(我明明送的 false)**
- 执行结果:`{"status":"success","createdCertIds":[13]}` —— 真跑了,并且
  **把平台上三张真实生产签名证书(ID 4/5/6)全部禁用**(`enabled: false`)

**为什么会自伤**:这类"轮换/轮替"执行器普遍有"停用旧的"语义,
而**开关是服务端说的算**,你送 `false` 不代表它听。参数可控 ≠ 副作用可控。

## 处置(当天同轮内完成,不隔轮)

1. **立刻回读受影响集合,不猜**:`GET .../signingCerts` → 逐个看 `enabled`。
   (回读确认 4/5/6 变 false;对照打之前的读数是 true → 就是自己干的)
2. **整条记录原样回写,只改要改的那一位**:`update` 要求「Name + ApplicationID」等必填,
   所以**先把回读到的整条记录 dict 拿回来,只覆盖 `enabled: true`,其余字段原样 POST 回去**
   —— 这样不会把 `keystorePath` / `certSha256` / `certSubjectDn` 等字段清空。
   只送 `{"ID":4,"enabled":true}` 会被必填校验打回,别在那里反复试。
3. **回读验证**:再 `GET` 一次确认 `enabled: true` 已生效 —— **没回读的还原不算还原**。
4. **清掉自己的产物**:测试证书(10–13)、轮换任务(2)逐个 delete,全部确认"删除成功"。
5. **如实交代 + 挂账"清不掉的"**:轮换执行时在目标盘上生成的
   `.../signing-certs/generated/rotation-2-<rand>.jks` —— **DB 记录能删,磁盘文件删不掉**(没有删文件接口),
   必须写进未还原清单,不许含糊成"已全部还原"。

## 事前:该怎么做才对

- **打之前先读全字段**,把可能的副作用面列出来:
  带 `disable* / auto* / replace* / rotate* / mirror* / poll* / sync*` 语义的开关,
  默认假设**它会在生产对象上生效**
- **只在自己名下的对象上打**(自建模板 / 自建账号 / 自建邀请码),并且**先备份可回读的状态**
- **单发**:一发就回读,不要连打几发再看
- **同轮回滚**:不要"先打完再一起收尾",副作用要在**当轮**闭掉

## 变体:没有「回滚」、只有「自愈」的副作用(缓存/派生数据/全量重建)

前一节的处置前提是「旧状态还读得到、能原样回写」。**另一类副作用没有这条路** ——
动作本身把数据**删掉/清空/重算**了,原值不存在,「回滚」在物理上就不成立。

**出事形态(与前一节不同:不需要你主动"打一发",一发空参就够了)**:盲枚举一批**未知语义的 action/端点**时,
名字带 `clear` / `flush` / `purge` / `reset` / `rebuild` / `reload` 的动作**无参即执行全量操作**,
不需要会话、不需要确认。实测:一次盲枚举打中缓存清除动作,**当场清掉全站数十万条缓存行 + 整个 Redis 键空间**,
并触发应用侧全量重建(缓存随后自己重新长回来)。

- **事前(唯一有效的防线是分栏)**:先把候选动作按名字分成「读形状」(`list/status/get/query/info/config/preview/test`)与
  「写/破坏形状」;只有读形状允许空参基线,写/破坏形状一律发**必然不合法**的载荷(缺必填/类型错/不存在的 id)让参数校验先失败。
  详规见 `api-probe-layer-triage` 的《写类/空体探测》两条与 `zero-write-endpoint-proofing` 铁律 5。
  **「无参 = 零写入」是错的直觉**:破坏性动作往往根本没有参数校验。
- **事后(四步,别只做第一步)**:
  1. **判定可自愈性**:这些数据是**派生/可再生**(缓存、索引、聚合、预览)还是**原始/唯一**(订单、资金、用户状态)?
     可再生 ⇒ 影响面收敛;原始 ⇒ **立即停手并通知**。
  2. **回读自愈实证**:判据不是「我觉得会自己恢复」,而是**回读到的读数** —— 缓存计数重新上涨、出现重建后的新行、
     页面重新可用。把这几个读数写进报告(与前一节第 3 步「没回读的还原不算还原」同一个规矩)。
  3. **如实写进「测试影响」,并明确区分三档**:**已回滚** / **已自愈(附回读读数)** / **未还原**。
     禁止写「无影响」;也禁止把「已自愈」含混成「已回滚」—— 前者是我们等它好的,后者是我们动手改回去的,责任形状不同。
  4. 附带:**重建/重算本身是一波生产负载**,即使数据最终自愈也要报(它会影响目标当时的性能与日志)。

## 红线级的接口(永远别碰)

**批量替换/全量刷新族**:`replaceAllPayloads` / `replaceAllInstallers` 这类
会**重新生成并覆盖所有真实邀请码的产物** = 直接影响真实终端。
只打**只作用于自己对象**的那一支(自己的 template / 自己的 invite code / 自己的 cert)。
同理,动作名带 `clear` / `flush` / `purge` / `reset` / `rebuild` / `truncate` / `delete`(-all) 的端点,
**未确认其作用域前不发任何请求**;要探它就用「必然非法」的参数探。
