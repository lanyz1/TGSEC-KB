# 撞到限流怎么办 + 用静默哨兵盯住"门闩"(2026-09 灰豚数据实战)

补充 SKILL.md §2「等冷却期间必须有产出」与 §5「别把环境坏了当收工理由」。

## 1. 限流信号:撞到就停,不是"换个参数再试"

平台反爬/风控触发时,响应长这样(JSON 信封里塞错误页):

```json
{"path":"/error","code":-100102,"message":"请求过于频繁，已被限制访问,请完成验证","roleId":2,"nextRole":0}
```

- **判据**:同一账号/IP 上,先前正常的接口突然**集体**返回同一条"请求过于频繁"→ 是**触发限流**,不是接口坏了、也不是凭据失效。
- **动作顺序(固定)**:①**立刻停止**对该业务面的探测(继续试只会升级成 IP/账号级封禁);
  ②冷却期**只走离线与静态面**(主包/页级 chunk、CDN 上的静态页、公开文档)——本次正是在冷却期从 chunk 里抠出了
  权益拦截文案与价目端点;③需要继续时**换出口**(跳板池)并降频,不要在原出口重试。
- **附带情报**:这条响应往往顺带泄露 `roleId`/`nextRole`(= 账号档位与升级目标),本身就是有价值的情报。
- **不要**把限流写成「目标打不动了」—— 它是环境状态,冷却后同一路径仍可用(§5)。

## 2. 静默哨兵:让"门闩变化"自己找上门(Hermes 原生,可复用)

长跑卡在**付费墙 / 待发放权益 / 会话时效**这类"等外部条件变化"的门闩上时,不要让人工轮询,
也不要每轮都去戳接口(会把限流/风控拖出来)。用一个**静默 watchdog cron**:

```
cronjob(action='create', name='<目标>哨兵', schedule='*/30 * * * *',
        no_agent=True, script='<目标>_watch.py', deliver='all')
```

脚本语义(**这是关键,决定它是否会骚扰用户**):

- **stdout 为空 = 静默**(什么都不发);**有输出 = 原文推送**。所以脚本只在**状态变化**时打印。
- 状态落盘到 `~/.<目标>_watch_state.json`,与上次比对:首次运行打印一次基线(让用户知道哨兵已上线),
  之后**只在下列变化时打印**:
  - 会话失效(需要重登 —— 用户提供短信码/口令就能恢复)
  - **权益/档位变化**(免费版 → 任一付费档)= 门闩打开,**立刻可以开始批量取数**
  - 目标重新上线 / 关键端口开放
- 脚本内所有网络动作**仍走跳板机**(纪律不变);SSH 不可达时也要有超时,别让 cron 挂死。
- 创建后注意 `deliver`:默认可能落到 `local`(不推送),要显式改成 `deliver='all'` 或对应平台,
  否则哨兵再灵用户也收不到。

**模式推广**:任何"等某个外部条件成熟才能继续"的作业(内网入口开放、审批通过、补丁发布、凭据轮换生效)
都可以套这个壳 —— 静默 + 状态文件 + 仅变化时告警。

## 3. 门闩就是交付节点:把决策交回用户,别自己硬撞

当探测证明"剩下的路只有付费/社工/凭据"时:

1. **立刻停手**(继续 fuzz 参数是低效且高风险的);
2. 用**已验证的数字**把选项摆出来(如"最便宜解锁档 ¥149/月,首购买一送二",数字要来自平台自己的接口,
   不是搜索结果);
3. 明确列出**每项需要用户做什么**(付款 / 提供账号 / 授权社工路线),以及**我能立刻执行的下一步**;
4. 把已完成的部分(未授权面、密钥、接口全谱、限流前拿到的样本)与**未达成的部分**分开陈述,不注水。
