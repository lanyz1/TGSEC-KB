# 用户喊停 / 「全部暂停」:长跑作业的停机流程(2026-09 实测)

> 场景:无人值守长跑中途,用户下令「**暂停并且关闭所有的后台任务**」「**全部暂停**」。
> 这是**第一类指令、语义无歧义**,收到就立刻执行,不要论证、不要问"要停哪些"。

## 0. 顺序错了会白干:pause 调度 → 再杀进程

**必须先把定时任务停掉,再杀进程。反过来则进程会在一个 tick 内被复活。**

实测:有一个"监控守护"定时任务(每 10 分钟)会检查并**重新拉起**监控 daemon。
先杀了 daemon 的话,最多 10 分钟后它又回来了 —— 表现为"明明杀了,过一会儿又活了",
看起来像"没杀干净"或"被目标反制",实际是自己家的 watchdog 干的。

```
正确顺序:
  1) 暂停所有相关定时任务(含守护/看门狗/播报/轮询)
  2) 杀进程(守护已停,不会复活)
  3) 复查:进程 + 端口都确认归零
```

## 1. 先枚举全部"后台面"(4 类,缺一类就等于没停干净)

| # | 面 | 怎么查 |
|---|---|---|
| 1 | Agent 自己跟踪的后台进程 | 进程管理器的 list |
| 2 | **游离的 OS 进程** | 包装脚本被杀、子进程还活着(见 §3) |
| 3 | **定时任务** | Agent 自己的 cron **+** 系统 crontab/schtasks |
| 4 | **监听端口** | 你的工具开的监听口是否还在 |

**只做第 1 类就宣布"已全部停止"是错的** —— 实测真正还在跑的东西在第 2、3 类里。

## 2. ★ 区分「我的」和「我自己的运行时」—— 按命令行匹配,不要按进程名

**进程名会骗人。** 实测 `python.exe` 同时匹配到:
- 本次任务的脚本(`k11bf.py` / `k11mon_server.py` / 隧道 / 代理)
- **Agent 自身的 gateway / serve 进程(10 个)**

⇒ **按名字杀 = 把自己正在汇报的会话一起杀掉。**

★ **反向也成立:命令行匹配在「复查」阶段会骗你。** 你用来复查的那条 bash/powershell 命令,
**自己的命令行里就带着要匹配的脚本名**(正则写在参数里),于是它自己被列成「还在跑」—— 白紧张一轮、
甚至可能顺手把自己的终端外壳杀掉。
⇒ 两个口径分开用:**识别**用命令行 + 精确脚本名;**复查**必须再加 `Name -like 'python*'`
(作业本体一定是 python 进程,你的复查外壳不是)。

Windows 下 `tasklist` **不显示命令行**,不足以判读。必须取命令行:

```bash
powershell.exe -NoProfile -Command \
  "Get-CimInstance Win32_Process -Filter \"name='python.exe' or name='curl.exe'\" |
   ForEach-Object { \"\$(\$_.ProcessId)|\$(\$_.CommandLine)\" }"
```

然后**只对确认属于本任务的 PID** 动手,按精确 PID 杀:

```bash
powershell.exe -NoProfile -Command \
  "Stop-Process -Id <pid1>,<pid2> -Force -ErrorAction SilentlyContinue; echo DONE"
```

★ 同时**必须放过的还有用户自己的基础设施** —— 实测有一台本地代理/VPN 客户端在服务用户的其它
机器人;它的进程名和我们的工具很像,但**动了会打断用户的生产**。宁可多问一句,不要顺手杀。

## 3. Windows 的坑:杀外壳不杀子进程

包装脚本(python 起的 python / bash 起的 python)被杀时,**子进程会存活**。
一个作业在 Windows 上常是**一丛进程**:`python3.exe`(启动器) + `python.exe`(真身) + `bash.exe`×2-3 + `tee.exe`(日志走管道时)。
**只杀其中一层 = 没杀。**
表现为"进程管理器说它已退出,可脚本还在跑/端口还在听"。

⇒ 复查阶段必须**直接查 OS 进程表**,而不是只看"我启动的那个句柄没了"。

## 4. 复查(不复查就等于没做)

```bash
# 残余非运行时进程数必须是 0
powershell.exe -NoProfile -Command \
  "\$p=Get-CimInstance Win32_Process -Filter \"name='python.exe'\";
   \$mine=@(\$p | Where-Object { \$_.CommandLine -notmatch '<我的运行时关键字>' });
   echo (\"total=\" + \$p.Count + \" non-runtime=\" + \$mine.Count)"

# 自己工具开的端口必须不再 LISTENING
netstat -ano | grep LISTENING | grep -E ':(端口1|端口2)\b'
```

**只报"我杀了 N 个进程"不算交代;要报"残余 0 + 端口已归零 + 那些进程是谁"。**

## 5. 汇报形状(用户要的就是这个)

1. **停机清单**,按**项目分组**(本次任务 / 其它任务 / 共享基础设施),逐项写清"是什么、在干什么、已停"
2. **明确写出没动的东西 + 理由**(Agent 自身运行时、用户自己的代理)—— 否则用户会怀疑你没停干净
3. **明确写出"磁盘产物一件没删"** —— 停机 ≠ 删数据,用户最怕这个
4. **说明可逆性**:定时任务一句 resume 即可、进程重启脚本都在 ⇒ **降低用户下令停机的心理成本**
5. **远端/其它项目的东西单独问** —— 跳到别的项目的**生产线**(采集管道、主服 daemon)不要顺手停

## 6. 「所有」就是所有 —— 但要交代清楚

指令是"**所有**后台任务"时,别的项目的监控也**在字面范围内**。
正确做法:
- **照字面执行**(把其它项目的定时任务一并暂停)
- **然后在汇报里点名说明**:哪几个是别的项目的、一并停了、要恢复说一声
- 不要"自作聪明"地只停当前项目的 —— 用户会认为指令没被执行
- 也不要**静默**停掉别的项目的守护 —— 那会让用户的生产静默失守

> 判定依据:"所有"是明确指令;而"暂停"是**非破坏、可秒级恢复**的动作,做错的代价远小于不做。

## 7. 停机后紧接着常要交报告

实测:用户喊停之后,下一句往往就是「**整理汇报目前的渗透报告给我**」。
所以停机时**不要清理任何产物** —— 报告素材就是这些落盘文件。
报告落两处:`D:\渗透\<目标>_recon\` + 桌面。

## 8. 停机脚本本身的三条硬规则 + 「零负载」的证据

**① 杀名单必须来自「本次启动过哪些脚本」的完整清单,不能凭记忆。**
漏掉一个脚本名 ⇒ 那个作业**静默存活并继续往目标发流量**。实测:漏了 S3 扫描脚本,
第一轮「复查 OK」是假的,第二轮才抓到。
⇒ 拼正则前先枚举**本次会话启动过的全部脚本名**,复查时**用同一个正则**再跑一遍。

**② `.ps1` 必须纯 ASCII。** PowerShell 按本机代码页(GBK)读 UTF-8 的 .ps1,
中文会**截断字符串**(报「字符串缺少终止符」),整个脚本解析失败、**一个进程都不会被杀**。
⇒ 停机脚本里的输出文案一律英文/ASCII;中文留到**汇报**里写。

**③ 杀外壳可能把自己的终端会话一起带走。** 杀 `bash.exe` 链会命中**你自己这次 terminal 调用的祖先 shell**,
整条调用异常结束(实测退出码 `4294967295`),后续的复查步骤根本没执行。
⇒ **「杀」与「复查」分成两次 terminal 调用**;被杀断的那次**不得**当成「已停干净」。

**④ 报「零负载」要有证据,不是声明。** 三条一起给:

1. **进程复核 = 0**(口径见 §2/§8①)
2. **所有作业日志的最后修改时间都早于停机时刻** ⇒ 之后没有任何新写入 = 没有新请求发出
3. **断点/状态文件的内容**说明停在哪一步(例:`{"ui":0,"pi":200}` ⇒ 只发出了第一轮 200 次请求,后续未发)

## Pitfalls

1. 先杀进程后停调度 → watchdog 复活,白干
2. 按进程名杀 → 杀掉自己的运行时,会话当场断
3. 只查 Agent 跟踪的后台进程 → 漏掉游离进程与定时任务
4. 不复查就报"已全部停止" → 用户一查还在跑,信任受损
5. 顺手停掉别的项目的生产线 → 越界
6. 停机时清理文件 → 紧接着要交的报告没素材了
7. Windows 上只杀外壳 → 子进程存活
8. 复查时用「命令行匹配」当唯一口径 → 匹配到自己的终端外壳,误判「没停干净」
9. 杀名单凭记忆拼 → 漏掉的脚本继续发流量,而「复查 OK」是假的
10. `.ps1` 里写中文 → 脚本解析失败,静默地一个进程都没杀
11. 把被外壳自杀打断的那次调用当成「停干净了」 → 复查根本没跑
12. **按进程名「数」出来的残留数, 不能直接当结论报给用户** —— `tasklist | grep -c python` 数到的是**本机全部** python
    与浏览器驱动(Agent harness 自己就占十几个), 把它报成「有 N 个任务残留待清」= 把 Agent 自身运行时当成自己的垃圾。
    先取**命令行**核实归属、确认「本任务残留 = 0」再开口; 报错了当场更正。
    机制:用户会按这个错报回「清掉吧」, 而**用户的字面指令**与**脚本里按自己产物名做的过滤**指向的是**不同对象** ——
    危险方向是:若脚本改成按进程名杀, 这一句「清掉」就会终止你自己的会话 / 浏览器驱动。
