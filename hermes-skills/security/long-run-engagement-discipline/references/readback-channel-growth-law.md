# 回读通道的增长律:取数作业的「日志」会自己长大

> 本文只补 **一个** 坑,不重复其余内容。并发自毁 / 退避上限 / 空 stdout 误判已分别写在
> `concurrency-self-defeat-and-remote-progress-truth.md` 与
> `harvest-throughput-diagnosis-and-worker-stall.md` —— 读那两篇,别在这里重读一遍。

## 症状(与"目标变慢"极易混淆)

取数循环的形态是「**写侧极端(每发一条注入) → 读侧回读同一份工件(运行日志)**」时:

- 读侧**单批耗时随作业时长单调上升**
- **捕获率断崖式下跌**:本会话实测 **93% → 9%**(每批 62 发只有 5~6 发能取回值)
- 表现成"目标不返回了 / 被限速了",但目标的单发延迟其实没变

## 为什么会掉

工件是**由作业自己灌大**的,每次回读都重新下载**整份**:

1. 下载量 ∝ 已跑时长 ⇒ 批周期越拖越长(自我拖慢的正反馈)
2. 到某个体积后响应被**截断**(或超时),而**最新条目在文件最尾部** ——
   恰好就是这一批要取的那几条 ⇒ 取不到,却看着像"目标没回写"

**判据:捕获率整齐地掉到某一低位并保持不动 ⇒ 先怀疑回读被截断,最后才怀疑目标。**
(真被限速通常伴随单发延迟上升或状态码变化;这里两者都没有。)

## 处置

- **只取尾部**:`Range: bytes=-N`(N 覆盖最近几批即可,如 300–600KB)
- 每次回读都**防缓存**:`?cb=<毫秒>`;工件在 CDN/WAF 后面时尤其必须(缓存会回旧值)
- **标记全局唯一**(把游标/序号编码进标记)⇒ 截断或陈旧只会导致**缺失**,
  不会导致**错值**。缺失可重取,错值不可见 —— 这是整条通道"可信/不可信"的分水岭
- 分批落盘 + `flush()` + 每批打印 `got/n`,**把捕获率当健康指标盯**
- 交付前先确认捕获率回到 ~90%+,再开始校验与出包

## 变体:暂存表整表回读("写进暂存表 → 每批读回整张表")

同一增长律的另一形态,最容易被误读成"目标在限速":写侧把数据打进一张**暂存表**,读侧每批都**读回整张表**
⇒ 响应体积 ∝ 已暂存量,与单发延迟无关。实测:**12MB 挺住 / 27MB 断 / 72MB 断**(失败与累积量严格正相关)。

**处置(比"只取尾部/Range"更彻底):把暂存量做成恒定 —— 每个单元推完立即读回该单元 + 立即删除该单元(按标记打标删除)。**
于是单次响应恒为「1 个单元 + 固定噪声」,与总规模无关。
判据比"捕获率掉落"更早出现:**同一作业里小单元全过、大单元必断**。

并行多实例时,每实例必须用**各自独立的标记前缀**(外加独立产物目录/状态文件),
否则互相擦掉对方暂存的行 ⇒ 无休止的"缺块重试",看起来像目标不稳定。
