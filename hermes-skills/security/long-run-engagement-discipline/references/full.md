## 8. 禁止宣布「打不穿」——交「已闭合矩阵 + 未开发清单」

用户会直接追问「**技术面没有可打穿的地方了吗**」。把「我这条路走完了」讲成「没有可打的地方」= 用自己的路线选择冒充技术结论,
下一轮必被这句话打回来。交付形态固定为三块:

- **已闭合**:逐条「试过什么 × 原始判据 × 为什么这条路死了」(无 FILE 权限 / 堆叠查询 500 且耗时无变化 / 数组绕盾仍被拦 / 无 LFI / 备份类 370 条零命中 / SSH 与 RDP 定向凭据全 fail …)。每条都要能复核(命令或响应片段),不写"试过了不行"。
- **未开发**:按性价比排序,并区分「**已证实存在、尚未利用**」(如可读的第三方会话 SQL、可枚举的越权查询接口、未逆的 WS 协议)与「**完全没碰**」两档,各配下一步动作。
- **判词只到原语层**:说「**现有原语不足以拿到 X**」,不说「X 不可能」;把缺哪个原语写清楚(缺文件读 / 缺落盘写 / 缺主机凭据 / 缺后台入口),
  再给换取该原语的具体路径。用户要的是下一步,不是判决书。
- **「未测」与「已排除」必须分栏记账,不许混写**:批量能力测试里,每个候选的每个能力都要有显式状态。实测踩坑 —— 存活筛选脚本对候选传了 `allow_create=False`(本意只筛存活),
  输出里的「建群成功=无」被顺手读成「建群不可达」,**那其实是未尝试**;补测后同一批里既有成功候选、也有 `UserRestrictedError: spamreported`。
  **写「不可达/阻塞」必须能指到一条失败响应原文,否则一律写「未测」**;结论被新证据推翻时回头改掉档案里那句旧话 —— 留旧句 = 下一轮从错误前提出发。
- **★「已做」与「计划做」必须分栏,不许把计划当战果**(与上一条同一毛病的另一半):宣布某实验/探测**已做**前,
  必须能指到**现场产物或脚本里的真实调用点** —— 该动作的 **URL/端点字面量或调用语句** + **同基名的落盘响应文件**;
  指不出来一律写「**未落地(仅计划)**」。
  **`grep` 关键词命中 ≠ 执行过**:命中可能来自**响应文案常量**(判据字符串里正好带着那个接口名)、注释、或案卷里**别的项目**的产物。
  判定「跑过没有」只认**调用点/URL 字面量**,再核**对应产物文件是否存在**;只凭命中行会把一句文案当成一次调用。
  机制:方案写下时「决定要做 A 且 A 零副作用」极易被后续汇报读成「A 已做」,而用户按字面采信,下一轮追问立刻暴露
  (典型追问形态:「那个测试怎么样了」)。
  自检句:报「已完成」前先问自己「**它的产物文件叫什么?**」—— 答不出就改写成「计划 / 未跑」。
  **纠偏要一次说清**:发现自己把计划当战果报过,当轮先明确纠正(哪一条不成立、为什么),再给本轮真实跑出的结果与产物路径 ——
  不要靠下一轮措辞淡化,也不要只补新结果不提旧话。
- **「已闭合」的准入判据:先核销「已知但未实读」清单。** 手上配置 / 指标 / URL / 报告里出现过的资产
  (桶名、host、端口、端点、路径)只要有**已获得访问权却没有实读过**的,那条面就不许写进「已闭合」。
  核销动作都很便宜:把那个桶名发一发 `?list-type=2`、把那个 `/metrics` 读一次、把那个日志接口查一次,响应落盘为证。
  机制:「我试过的都试了」≠「能试的都试了」;用户说「你肯定有遗漏」时,指的通常正是这类零成本未读项
  (一个被当成「别人的日志桶」而从未列过的桶名、一个从未读过的 `/metrics`),而不是还没碰的新攻击面。
  把这条当成**写入「已闭合」前的前置检查**:每写一条闭合结论,问一句「这背后有没有一个我握着却没读的东西」。

用户说「仔细分析有没有遗漏的可利用的东西 / 整理一下进度 / 整理一遍已挖出的漏洞 / 感觉有细节漏掉了」时,交付 = **漏洞总清单(按严重度、每条附实网证据) + 遗漏面分析(已证实/未触及/已闭合三档)**,独立落盘 + 桌面副本。
副作用段与"未还原清单"照旧单列。

**总清单的固定形状**(缺任何一项都会被当成「有细节漏掉了」打回):

- 每条 finding 五段式:**结论 / 证据(产物文件·行或响应体) / 复现 / 影响 / 状态(`已验证` | `待验证` | `已证否`)**
- **必须单列「已证否」区** —— 否则下一个会话会把判死的路重走一遍,这是最大的时间黑洞
- **跨线交叉结论单独立节**:同一平台的不同部署之间常有**只有一处成立**的结论(一侧有 WAF 一侧无 / 同一端点一侧公开一侧要票 / 账号级限流与配额机制 / 同代码多品牌共用账号库)。这类结论价值高于单条 finding,必须单列并与主攻击链挂钩
- 战果按**层**分开写,不许合并:凭据层 / 权限层 / 数据层 / 全量数据层 / 控制权·shell / 资金 —— 每层写「实际获得 + 证据 + 价值」;**「账号级接管」不得写成「接管」**(用户会按字面理解成系统级)
- 数字(条数/分布/计数)一律用产物重算,不沿用旧文档里先前的数字(中途快照与终值会不同)
- 存量外部报告要**逐条复核再引用**:它自己写了资金 0、死路清单、剩几次尝试,不代表结论都对 —— 常见错法是「同源同质的三条 Critical 各计一次」(计数注水)、「NPE 当成全端点被否」(过度结论)。引用时按本 skill 的判据重估,不照抄定级

## 8.5 别用穷举式笨办法开路 —— 先交按杠杆排序的路径清单

**用户对「逐条盲扫 / 百万级枚举」容忍度极低**。触发句:「**不要这样搞 这样太麻烦了 没别的路径吗**」、
「这样太慢了」、「有没有别的办法」。看到这类句子 = **立即停当前笨扫进程**(停进程先获准,见 §0.6),回答替代路径,不要「跑完这批再说」。

铁律:

1. **缩减优先于枚举**。要枚举才能推进时,先做**空间缩减**:时间轴标定(自增/雪花 ID → 时间,或按递增速率估窗)、
   差分对账、分页边界收敛、状态/类型筛选 —— 把候选压到**可定点验证的窗口**再扫。缩减不掉才谈枚举。
2. **枚举前先问授权**。批量/大字典类动作用户会否;只有**靶向小列表**才直接给。授权后仍须低频限速、可随时停。
3. **「一条链直达」优于「多接口穷举」**。能用一条可信链拿到的(如扫码确权→换票、导出接口、后台查询),
   不要去逐接口试参数名/逐 ID 探路 —— 后者在用户眼里就是「骚扰式盲扫」。
4. **被问「有没有别的路径」时,交 2–4 条按杠杆排序的路径**(每条:入口 / 需要什么 / 代价 / 我立即做什么),
   而不是反讨资源或重述已排除的路径。这与 §8「交已闭合矩阵 + 未开发清单」同一形状。

## 9. 报告交付形态与版本升级(整理/收口类请求)

- 桌面副本**按目标建子目录**(现行惯例 `Desktop\01_渗透报告\<目标名>_<日期>\`):报告 md+html、附录、发现记录都进该子目录,不平铺桌面根
- **中间轮次交增量卷 (delta),里程碑才整合全量**: 主报告 (vN.0) 已交付后,每轮续作产出一卷自包含增量 `_v<N>_delta_<date>.md`(本轮新增/纠错端点、纠错复测、负结果等强度排除、凭证轮汇总、归属变化),链在主报告之后;合格线 = 「只看增量也能接力」。这与「不散交附录」不冲突:附录是支撑材料,delta 卷是正式交付单元
- **里程碑回合再全量整合**(原「升级报告版本号」流程): 旧章节程序化提取保持原样 + 新章节分片写入 + 脚本拼接 → 重新生成 HTML → grep 关键标记(新 finding 编号/新关键词)+ 行数双验证
- **副本落位双核验**: `cp` 到桌面目录后用 `wc -c -l` + `md5sum` 与案卷本体逐位比对,一致才算交付完成
- 旧版移入交付目录 `v1_archive\` 子目录**保留不删**;新版成为主交付,md+html 双格式都给

## Pitfalls

- **进度查询命令本身必须轻量** —— 用 `cat 全部分片 | wc -l` 这类「重扫全部产物」的方式算进度, 单次查询要几分钟,
  会把跳板/SSH 会话窗口占满 ⇒ **查询自己超时**(症状: 重试循环报「重试1」而远程命令其实没报错)。
  进度一律从**增量证据**读(三者都是 O(1)): 状态文件行数(`wc -l < done.tsv`)、日志末行(脚本自己按单元打的累计行数)、`du -sh` 体积。
  查询命令只允许「取回几个小标量」, 不允许在远程做聚合。
- **长跑哨兵用「本地脚本 + 轻量轮询 + 达成就退出」** —— 不要在会话里空转等待、也不要用一条长驻远程命令盯到天亮
  (跳板会掉线, 且会挂住通道)。形态: 本地 `sh watch.sh` 循环里每 5 分钟发一次**轻量**查询, 进度追写本地日志;
  命中阈值(全部完成)或**进程消失**就 `echo` 退出码并 `exit`, 用 `background=true, notify_on_complete=true` 启动 ——
  完成时自动通知唤醒, 中间不占任何工具调用。**进程消失早于完成量 = 异常, 必须报出来而不是继续等。**
- **中段输出保持短句+纯文本,严禁重复字符/装饰性长串**:输出退化(重复字符、失控长文)会被用户当故障直接叫停整场作业(「暂停，先修复」);一旦察觉自己在重复输出,立即收敛为一句状态说明,不解释不辩解
- 把"第一发成功"当成"可以随便连试" → 十几次就把账号锁死
- 长时间静默憋大招 → 用户认为你卡死/跑偏,直接喊停
- 只报"未成功的尝试" → 用户反感;报里程碑与结论
- 收尾只交成果不交残留清单 → 等于把痕迹留在现场
- 改完就宣布"已还原" → 没回读验证的还原都不算数
- 长跑脚本**不加 `-u`** 又把 stdout 重定向到文件 → Python 块缓冲让日志长时间空白,被误判"卡死";
  长跑一律 `python3 -u`,并在启动后 1–2 分钟查一次日志与状态文件 mtime 作为存活判据
- **判活统一看「产物增长 + CPU 时间」,不看进程是否存在**:`ps -eo etime,time` 里进程活着但 CPU≈0 且输出文件不涨 = 空转;
  Windows/git-bash 下 `ps -W | grep <脚本名>` 可能根本看不到 python 子进程。原线未确认停写不要起重复线
  (详规:`references/harvest-throughput-diagnosis-and-worker-stall.md` §七)
- **「被 orphan 掐死」是最容易误判的结论**:同一脚本重跑前惯例 `rm -f <log>` ⇒ **首跑日志被覆盖**,它的真实结局永远说不清。
  实测教训(2026-09-25 `mchleaf2`):首跑被记成「orphan 掐死」并重启,直到批通知到达才发现 **首跑其实 `rc=0` 完整收官**(`TOTAL reqs=1944 hits=0`)——
  日志停在半途 ≠ 死,也可能只是慢(timeout 内跑完)。规则:①后台跑批**日志名带唯一后缀**(`<name>.log.<ts>`)或**跑前先 `cp` 留存**,让每次运行各有其证;
  ②判死前必须看三样 —— **有无异常栈 / 产物 mtime 是否还在涨 / 日志末行有无 `rc=`**;三样都不满足才叫被掐死,否则只是慢。**且完成回执可能在你已判读结论之后才成批到达**(实测连收 5 条)⇒ 逐条核对「这是不是我已读过的那份产物」,**不因回执重跑、也不把旧信号当新线索**;收尾列一张「已启动作业 → 产物 → 判读状态」对账表,清零后才算这一轮结束。
- 并行脚本用**共享计数取模**(`n % 200 == 0`)决定打印/落盘 → 竞态下几乎永不触发:进度不可见、状态文件不更新,
  作业看着像死了、被迫 kill 重启。改成**每 worker 本地计数 + 到量即 flush**,并且**可续跑**(重启前先看状态文件能否接上,
  能接上就别把已跑的量白丢)
- 长跑作业**不要用包装 shell / `nohup … &` 起**(宿主会拦,且包装 shell 一结束就把子进程带走)。
  **本机可靠形态**:在 `execute_code` 里 `subprocess.Popen([...], stdout=open(日志,'w'), stdin=DEVNULL,
  creationflags=0x00000008|0x00000200)`(= `DETACHED_PROCESS|NEW_PROCESS_GROUP`):调用立刻返回、进程活到跑完,靠 tail 日志判活。
  ⚠️ **`terminal(background=true)` 报 `timed out after 420s` 不等于"没起来"** —— 实测那个进程**仍在跑**;
  再发一次就成**多实例并发写同一个日志**(日志出现 NUL 填充、行错乱、同一段重复多遍)。
  **续发前先查重**:`ps -W | grep <脚本名>` / 看日志首行时间戳,确认没有同族实例再动。
  判据:日志停在**某个工作单元中途**且**没有任何异常栈** = 被外部终止,不是崩溃;
  配一个可续跑的状态文件,重启零损失(重启前先读状态文件确认能接上)
- **进度日志粒度 = 工作单元**:一张大表只在跑完才打一行 ⇒ 中途十几分钟无输出,
  你和用户都会误判卡死。按单元/按 N 个单元打一行并带游标,才是可判活的心跳
- 并行多实例必须**四独立**:标记前缀 / 产物目录 / 状态文件 / 表清单(互斥),
  否则共享标记命名空间的两个实例互相擦掉对方暂存的行 ⇒ 无休止"缺块重试",看着像目标不稳定
- 复用旧脚本里的辅助模块(读值/分片/会话引导)前,**先读它当前的签名再写调用**:
  按记忆传了不存在的参数 ⇒ **每项都在几秒内整齐失败**,看着像"目标全表不可读",实际是本地 TypeError。
  判据:失败**快而整齐**(每项耗时几乎相同)= 本地 bug;失败**慢而零散** = 目标侧问题
- **不可逆删除前先出「分级清单 + 档位方案」, 等用户点档位再动手** —— 落盘体积大 ≠ 价值大
  (通用工具安装包与素材能占掉 80%), 且删了就没法再复核。分级口径、跨目录去重、A/B/C 档位与体积自证见
  `references/deliverable-shapes-and-asset-inventory.md` §六
- **中途重启一个「健康但在产废料」的长跑任务, 先做三态分类**(跑错 / 跑慢 / 跑死) ——
  只有「**结果静默错**」值得为正确性掐掉一个健康作业(它进程在、请求 200、进度在涨, 但产出与另一通道对账不符);
  判据只能来自**跨通道对账**(丢列/丢行/整份空), **不能来自「进程还在 / 文件能打开」**;
  系统性错(整列丢失) = 旧产物整体作废, **别打补丁**, 直接重跑。
  重启四步(先改并语法自检 → 杀旧与起新**拆成两次调用** → 确认新实例存活 → 告知用户)见
  `references/restart-orchestration-and-resume-safety.md` §四
