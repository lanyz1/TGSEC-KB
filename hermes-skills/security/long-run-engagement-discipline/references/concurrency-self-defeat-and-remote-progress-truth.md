# 并发自毁 + 远端进度才是真进度

> 本文是 `harvest-throughput-diagnosis-and-worker-stall.md` 的姊妹篇。
> 那篇讲"退避上限 / 架构反复折腾"两个真凶;这篇补第 3 个真凶:**自己起的并发**,
> 以及一个把"活着"误判成"卡死"的 stdout 陷阱。
> 第 3 真凶针对**同一作业内**的 worker;§六 补**跨会话/跨 agent** 那一层的资源切分。

## 一、并发不只"不涨总量",会**倒扣**

同一目标、同一"报错注入取数"任务,先 1 个 worker、后 6 个并发:

| 并发数 | 聚合吞吐 |
|---|---|
| **1** 个 worker | **137–163 行/分钟** |
| **6** 个(主作业 + 3 旧分片 + 2 修复分片) | **合计 ~6 行/分钟** |

⇒ 并发把**总量**打到 1/25。杀掉 5 个、只留 1 个后立刻回到 132–168 行/分钟(**28 倍**)。
5 个 worker 分散在 5 个**不同出口**,总吞吐一样崩 —— 出口只解决"单 IP 被封",
**不解决 worker 之间互相拖**。

## 二、机制:共享"回显侧信道"时,并发是自毁

本目标是"注入报错 → 落 TP3 运行日志 → 另一个请求读日志"的取数通道:

- 每个 worker 每批都要**下载同一份日志**
- N 个 worker ⇒ 日志增长快 N 倍 **且**同时有 N 个下载者
- ⇒ 每个 worker 的批周期都被拉长,全员一起变慢(总产出反而塌)

**判据(下并发决定前必问):**
「我的 worker 是否共享一个**总量随写入方数量增长**的读取对象」
(同一份日志 / 同一个队列 / 同一张表 / 同一个文件)?

- **是** ⇒ 并发上限 **1~2**,不要拿 worker 数量去堆吞吐
- **否**(彼此独立的资源)⇒ 才谈并发

## 三、处置纪律

1. 吞吐掉了,**先看"我起了几个 worker"**,再量化(单发延迟 + 聚合行/分),再瘦身
2. 本会话用户明确选择:**「全部停掉,只留 1 个分片慢慢跑 → 最稳,~90 分钟」**
   ⇒ 记住这条偏好:**宁可 1 个跑 90 分钟,也不要 6 个互相拖到几小时**
3. 杀进程要按用户铁律先报备(哪怕是自己起的作业)。用户会直接给取舍
   ("全部停掉" / "先只停污染的那条"),**给选项比自己替他决定更快**
4. 收尾要**同时**清本地进程与远端残留(`pkill -f <脚本名>`),否则孤儿子进程继续烧目标:

```python
for pat in ["tst26.py", "_mk.py", "_full.py", "_full2.py"]:
    subprocess.run(["bash", "-c", "pkill -f " + pat])   # returncode 0 = 真的杀到了
# 校验：远端 python3 计数 + 残留文件 ls
```

- `pkill -f` 会匹配到自己的命令行 ⇒ **杀脚本别叫被杀的脚本名**(或写成 `[t]st26.py`)
- 本地 kill 只断 SSH 客户端,**远端 python 可能变孤儿** ⇒ 必须单独 pkill 校验一次

## 四、本地 stdout 全程为空 ≠ worker 卡死(SSH exec runner 陷阱)

`rex2.py` 这类 SSH runner 用 `exec_command` + `out.read()`:**命令结束才回吐输出**。
⇒ 长跑作业的本地日志文件**全程 0 字节**,直到作业结束才一次性写入。

本会话因此两次差点误判卡死(盯 75 秒、盯 5 分钟的空日志),**实际作业一直在正常产出**。

**存活/进度判据(按可信度排序):**

1. **远端产物文件的 `size` + `mtime`** —— 唯一可信的进度源。
   挂一个 `_chk.py` 周期跑 `os.listdir('/root/dict')` + `getsize/getmtime`
2. 远端 `ps -ef | grep -c [p]ython3`(`[p]` 避免匹配到 grep 自己)
3. 本地日志**只能**在作业结束后看逐批明细,**不能**用来判活

**推论:任何长跑作业必须把进度写进"远端文件"并 flush**(`f.flush()` + 每批 `print(..., flush=True)`),
**不要把 stdout 当进度通道**。远端每批落盘一次 ⇒ 进度可观测、可断点续跑。

## 五、速率基线(本目标参考值,别照搬到别的目标)

- 单 worker 稳定跑 **2.3 请求/秒**(约 137–168 行/分钟)持续 40+ 分钟**未触发封禁**
- ⇒ 出口的"速率窗"不是字面上的"每出口 ≤6 个请求",而是**按 (出口 × Host) 的时间窗记账**;
  单个匀速 worker 能撑远超 6 发
- 但**并发 fan-out 不会乘总吞吐**(见 §一)⇒ 提速只能靠"每发多带数据"(提高每请求行数),
  不能靠"多起 worker"

## 六、多会话/多 agent 并行的资源切分（跨会话能力边界）

用户会直接问「同时做几个任务,要不要多开会话」。**别笼统答"能"或"不能"** —— 分三层说,
每层结论不同;笼统答会让人以为多开会话是免费的。回答时按 A/B/C 顺序讲,并把 D 当成推荐选项。

### A. 保持的(技能与记忆层) —— 前提是**同一个 profile**

- 技能库、`MEMORY.md`、USER PROFILE 都是**按 profile 隔离**的。
- ⇒ 到**别的 profile** 里开会话,那个分身**没有这套技能库与记忆**,能力直接退化到裸模型。
  "最近变得不好用了"这类反馈,先怀疑是不是开了不同 profile 的会话。
- **多会话统一在同一个 profile 内开。**

### B. 不保持的(判断层)

- 会话之间**互相看不见**对方手头的上下文:做过什么、卡在哪、下一发准备发什么。
  跨会话读取只有一条路 —— 状态**写进文件**,或用会话检索去翻。
- 每个新会话开局是**冷的** ⇒ **开工必须重读该目标的既有产物索引**
  (见 `prior-artifact-inventory-and-dead-end-ledger.md`),否则等于空手重来、重复已排除路径。
- `MEMORY.md` 是**单文件带锁**且接近上限 ⇒ 多会话并发写会互相覆盖。
  **多开会话时停写 memory**,把状态写进各自目标目录的文件。

### C. 会打架的(资源层) —— 真正要调度的东西

| 资源 | 冲突机制 | 切分办法 |
|---|---|---|
| 浏览器调试端口 | 两个会话驱动同一调试端口 ⇒ 抢标签页、互相看到对方的页面 | **一会话一端口 + 各自独立 user-data-dir** |
| 质询/风控会话态 | 会话态绑定**出口 IP + UA** ⇒ 从不同出口过挑战会互相作废 | 同一目标固定同一出口;别在不同出口重复过挑战 |
| 跳板机出口 | 按 (出口 × Host) 记账 ⇒ 两会话共用一个出口会**共用配额桶**,各自刚热身就被一起封 | **一会话一出口**(按跳板机分,不按目标分) |
| 输出文件 | 并发实例写**同一文件名**会静默覆盖(曾一次丢数百条已采集记录) | **一目标一目录** + 脚本输出文件名带目标前缀 |
| 同一目标 | 两会话打同一目标 ⇒ 重复发同一条、锁同一账号、抢同一 token | **同一目标绝不开两个会话** |

### D. 比多开会话更好的形态

主 agent 在**单会话内**用子 agent 并行:出口、端口、输出目录由主 agent 统一分配 ⇒ 不会自撞。
代价:子 agent **不能问问题**,且其结论**必须主 agent 复验**才可采信。

### E. 分工建议(直接给用户这个)

- 长跑 / 可脚本化 / 不需人拍板的 → 子 agent 或后台任务
- 需要人介入的(读验证码、下断点、授权判断) → 留在主会话
- 只有**目标完全独立、且用户要分开对话**时,才多开会话 —— 且都在同一 profile 内
