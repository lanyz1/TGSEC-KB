## 一、镜像陈旧 ≠ 采集停摆(诊断顺序有严格次序)

**症状**:本地数据文件的 mtime 停在 1.5 小时前,波次上界一动不动。
**我的错误**:第一反应是「采集停了」,跑去逐台跳板机核 worker —— worker 全都好得很,
甚至已经推进到远超前镜像的位置。**白烧了一个阶段。**

**正确诊断顺序(自上而下,每层都能独立否定):**

| 层 | 查什么 | 本会话结果 |
|---|---|---|
| **1. 自动化作业本身** | `cronjob list` → 看 `last_status` / `last_run_at` | ★ **`last_status: ERROR`** ← 真凶就在这里 |
| 2. 远端 worker 实况 | 各跳板机上的 `hv_*/hz_*/hs_*` 计数与 LAST 波次 | 全部健康,远超镜像 |
| 3. 回传/解析各步 | 单步重跑看哪一步报错 | 正常 |

**铁律:镜像不动,先看 scheduler 的作业状态,再看 worker。**
把顺序反过来 = 用「目标/采集出问题」的假设去解释一个**你这边**的故障。

**死罪是:在镜像陈旧的情况下继续拿它报数字。** 本会话我基于旧镜像给了用户一整轮
进度与推算,数据比真实值少了约 3 倍。**报数前先看 mtime。**

## 二、cron 脚本的退出码陷阱(静默失败,代价 1.5 小时)

**真凶代码**(我写的,最后一行):

```bash
N=$(cat stats.txt 2>/dev/null)
O=$(cat .laststats 2>/dev/null)
if [ "$N" != "$O" ]; then
  echo "$N" > .laststats
  echo "[进度] $N"          # 只在有变化时输出
fi
# ← 脚本在此结束
```

**机制**:

- 脚本的退出码 = **最后一条命令**的退出码。
- 「无变化」时 `[ "$N" != "$O" ]` 求值为假 ⇒ 整条 if 返回 **1** ⇒ 脚本 **exit 1**。
- 于是:**恰恰在「没有新数据」的那次运行**,被判定为失败。
- 作业被标 `error`,而**数据其实已经成功入库、桌面包也已经刷新** —— 错误状态与真实结果不一致。

**修复**:

```bash
if [ "$N" != "$O" ]; then   # 有变化才推送
  echo "$N" > .laststats
  echo "[进度] $N"
fi
echo "[汇总] $(cat stats.txt 2>/dev/null)"   # 无条件输出,给交付层一个稳定锚点
exit 0                                       # ★ 显式收尾,杜绝隐式退出码
```

**推广到所有无人值守脚本:**

1. **长跑管线的收尾一律显式 `exit 0`。** 管线的成功/失败由文件产物说话,不由最后一条命令的退出码说话。
2. **静默看门狗(no_agent 模式)更要注意**:空 stdout = 静默,非零退出 = 报警。
   如果脚本因为一个无害的尾部测试而常常非零退出,**你会收到一堆假报警,然后开始忽略真报警**。
3. 条件式推送那一段,**不要让它成为最后一条语句**。

## 三、「无变化」的脚本不要用尾部测试表达成功

同源教训,换个说法记住:**「没有变化」是一个正常结果,不是错误。**

把「本次无新增」编码成退出码 1,等于告诉调度器「我失败了」。
正确表达:输出一行恒定的汇总(`[汇总] UNIQ=... RANGE=...`),让**输出**承载状态,让**退出码恒为 0**。
