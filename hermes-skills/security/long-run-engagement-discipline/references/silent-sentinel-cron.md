# 静默哨兵:长跑期间轮询「会话 + 权益档位」的 cron 设计(2026-09 实战)

> 适用:目标数据被**登录态 / 付费档位**门控,当前拿不到,但"档位或活动一旦变化就立刻能拿"。
> 用户授权无人值守长跑、且反感"长时间不反馈"也反感"频繁汇报无进展"时,这是最合适的等待姿势:
> **平时完全静默,条件命中才出声。**

## 1. 为什么要哨兵(而不是人肉轮询)

- 人肉轮询 = 要么静默太久(用户以为你卡死),要么每轮汇报"没变化"(用户嫌吵)
- 权益档位变化(平台发试用/活动会员/用户自行升级)是**唯一能解开付费门闩的自然事件**,
  它随时可能发生,捕捉窗口很窄 → 适合机械轮询
- 代价极低:一次只读请求 / 30 分钟,不触发风控阈值(远低于触发限流的量级)

## 2. 实现要点(已实测)

| 要点 | 做法 |
|---|---|
| 不计 token | cron `no_agent=True` + `script=<本地脚本>`,脚本自己 SSH 到跳板机打一个只读接口 |
| **静默** | `no_agent` 语义:**stdout 为空 = 什么都不发**。所以只在"有变化"时 print |
| 首次运行 | 打一条基线(避免用户以为没生效),之后进入静默 |
| 用户能收到 | 创建时若被判定 `deliver=local`(CLI/桌面会话无常驻投递),**改成 `deliver=all`** 才会推到已连的网关 |
| 状态文件 | `~/.<target>_watch_state.json` 存上一轮结果(档位/会话态/命中计数),用于 diff |
| 会话保真 | 跳板机上固定 cookie jar 路径,哨兵**只读**、绝不重建会话(会踢掉正在用的会话) |

## 3. 关键设计:**必须区分「限流」与「会话失效」**

本次踩到的核心点 —— 长跑期间平台会因探测密集回:

```json
{"code":-100102,"message":"请求过于频繁，已被限制访问,请完成验证","roleId":2,"nextRole":0}
```

若哨兵把它当"会话失效"处理,**每次限流都会误报"需要重新登录"**,用户会被无意义告警淹没并开始忽略告警。

```python
if isinstance(j, dict) and j.get("code") == -100102:
    print("SESSION=RATELIMIT"); raise SystemExit      # 限流:静默,只累计计数
```

判读表:

| 观测 | 定性 | 动作 |
|---|---|---|
| `code == -100102` | 平台**账号/会话级**限流 | 静默;冷却期内只做离线工作 |
| 响应无 `data` / 结构变了 / 要求登录 | 会话真失效 | 告警(一句话说明重登所需材料) |
| 字段齐、档位取值变了 | **权益变化** | 告警 + 立刻转自动取数 |
| 网络/SHH 连不上 | 跳板故障 | 只在上一轮为正常时告警一次(避免连环告警) |

## 4. 告警文案要自带"下一步动作"

```
🔔 <目标>账号等级变化: 免费版(vip2) → 豪华版(vip4) —— 若为付费版,立即开始抓 <目标数据>
```

理由:告警可能落在另一个会话/另一台设备上,读它的人需要**当场知道要不要动手**。

## 5. 与"门控判定"的衔接

哨兵盯的应该是**门控变量本身**(权益档位),不是"数据是否拿到"。
配套分层判定见 `pentest-finding-verification/references/entitlement-gate-vs-auth-gate.md`:
认证层 / 权益层 / 真不存在 三态分开取证 —— 哨兵负责"权益层何时解除",报告负责"当前卡在哪一层"。

## 6. 纪律

- 哨兵上线前**手工跑两遍验证**:第一遍出基线、第二遍必须**完全静默**(否则会变成噪音源)
- 哨兵只读:**不建/不切会话、不发短信、不下单**;任何"能改状态"的动作都必须回到有人值守的轮次
- 用户放弃等待时(例如选择付费或换账号),记得**停掉任务**,别留一个永远在跑的哨兵
