# 缺失字段的重建与独立源交叉验证(2026-09-15 实战)

> 触发:用户问「这份数据里没有 X 吗,能不能把 X 列补全」(金额/价格/数量/日期…),
> 或交付前发现关键字段缺失时。本文件给的是**可复现的五步法 + 必须标注的口径**。

---

## 一、★ 先别急着说「没有」:三步把源头翻干净

### 1. 把原始响应的**全部字段**打出来,不要只看你解析过的那几个

本会话第一反应是「接口没有金额」。做了两步才发现真相:

- 订单对象只有 9 个键:`order / wuliu / name / fhsq / pch / store / items / is_drugs / actual_pay`
- ★ **`actual_pay` 看着像「实付金额」,实际值是「银联支付」= 支付方式**
  ⇒ **差点把它当金额交付**。**同名/近名字段必须先打印值再采信,不能凭字段名下结论。**
- 金额的**组件**其实都在 `items` 里:`num`(数量) + `unit_price`(单价)

**动作:** `python3 -c` 把一条原始 JSON 的**所有键值** dump 出来,逐个念一遍值。

### 2. 枚举同一 dispatcher 的其它动作

同一入口(本例 `api.php?ac=<动作>`)往往有多个只读动作,**其中一个可能直接带你要的字段**:

```bash
for A in xp dd order orders bch bch_list daochu get_order_print_data userlist; do
  n=$(curl -sk --max-time 10 "https://$H/api.php?ac=$A&$sys" | wc -c)
  [ "$n" -gt 60 ] && echo "ac=$A len=$n  <<<"
done
```

本会话借此发现 **`ac=bch` = 单位级商品汇总**(但**仍无价格**)⇒ 确认全站唯一金额来源就是 `items`。

### 3. 确认「确实没有」之后再动手(并留下证据)

翻干净才敢说「接口没有实付金额字段」,并把这句话写进交付说明。**没翻干净就说没有 = 谎言。**

---

## 二、★ 重建公式:组件相乘,但先把组件的语义定死

重建本身是平凡的:`金额 = Σ(num × unit_price)`。**危险在组件的语义歧义。**

### 本会话的真实歧义(不解决会错 30 倍)

| 来源 | SKU `TC3960-08-30` | SKU `ZP0104` |
|---|---|---|
| 订单的 `items[].num` | **30** | **8** |
| 面单的托寄物 `tuojiwu` | `TC3960-08-30(1)` | `ZP0104(8)` |

- SKU 名里 `-08-30` 的 **30 = 包装规格(30 盒装)**;托寄物 `(1)` = **1 包**
- `ZP0104` 是单件 SKU ⇒ `(8)` = 8 件,与 `num=8` **一致**

⇒ **`num` = 可售单位数(盒/件)**:30 盒装的 1 包 = 30 盒 = 30 件 ✓
⇒ **两个 SKU 互相印证了同一个语义,这才敢用。**

**规矩:凡组件字段的"单位"有歧义(件/包/箱/盒),必须找到第二个来源把它钉死,不能选一个看起来合理的解释就往下跑。**

---

## 三、★★ 用**完全独立**的通道交叉验证(交付可信度就是这个数)

**这是本方法论的核心。** 拿与你的解析路径**毫无关系**的另一路数据去撞:

- 本会话独立源 = **快递面单的 `tuojiwu`(托寄物)字段**,它自带 `SKU(件数)`,与订单的 `num` 是两条独立通道
- 配对键 = **运单号**(订单里有 `wuliu`,面单里也有 `wuliu`)⇒ 逐单对齐
- 结果:**一致 28 / 不一致 0 = 100%**

```
一致率: 100.0%
```

**报告里必须写:验证源是什么、配对键是什么、match:mismatch 各多少。**
只说「已验证」不算验证(参见 `recovered-data-acceptance-gates.md` §三)。

**若 mismatch 不为 0:如实写疑似原因,不要为了好看硬报 100%。**

---

## 四、★ 口径标注:标价 ≠ 实付(用户最容易被误导的地方)

重建出来的数是**基于某个口径**的,必须原样标注,不能让它冒充另一个口径:

- 本会话:全站统一标价 **198 元/件**(抽样 7,815 个商品段 100% 都是 198)
- ⇒ 算出总额 **93.96 亿元**,但这是**标价(零售价)口径**,**不是客户实付**
- ⇒ 源接口**没有任何折扣/实付字段** ⇒ 代理折扣后的真实成交额**物理上不可知**

**动作:把口径写进交付的 `数据说明.md`,并在对话里明说「这是标价口径、不是实付、接口没有该字段」。**
并主动给下一步:**「你有统一折扣的话告我,我按折扣重算一版实付口径」**。

**缺这一步 = 用户会拿标价总额当成真实营收做判断。**

---

## 五、把重建接进自动管道(否则下次回传又变回没金额)

1. 把重建脚本做成**通用工具**(接受 `argv[1]=源 CSV`、`argv[2]=输出 CSV`),不要写死路径
2. 把它插进管道的**解析后、交付前**:`parse → 重建 → 交付/统计`
3. 下游交付脚本的数据源改成**重建后的文件**,导出子集里**加上新列**
4. 交付包同步更新:**主 CSV + 金额维度统计(年/月/商品/门店) + 数据说明.md**
5. 旧的、不带该字段的统计文件**删掉或覆盖**,别让用户读到错数字

**验证:跑完后 `csv.DictReader` 打出表头 + 抽一行核对 `件数 × 单价 == 金额`。**

---

## 六、附:重建脚本的性能与写法

- 355 万行流式处理约 **22 秒**(`csv.reader` 逐行 + 写新文件),不需要 pandas
- **先抽样统计格式变体**,确认正则 100% 命中再全量跑:
  本会话抽样 300,001 行 / 593,250 个商品段,**全部匹配 `x<数字> @<数字>`,零异常** ⇒ 才敢全量
- 解析正则:`re.compile(r"x(\d+)\s*@")`
- 输出用 `utf-8-sig`,Excel 打开不乱码
