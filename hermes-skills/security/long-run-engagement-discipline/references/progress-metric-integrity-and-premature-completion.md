## 一、★★ 我在本会话连错两次,都是口径问题

### 第一次:把「有数据单位数」当成「全部单位数」⇒ 宣布了 98.8% 完成

- 实测「有数据波次 119,022」全采到手 ⇒ 我对外宣布「**订单总量 = 修正后总量的 98.8%**」
- **随后回传继续带来新数据:实际到手从 353 万涨到 408 万,超过了我当时宣布的分母**
- ⇒ **那次「98.8%」是错的**,而且我在报告里说得像终值

**教训:数据仍在流入时,不要宣布完成度百分比。** 分母是**移动目标**
(最高 ID 对应当天日期 ⇒ 数据还在长)。宁可说「已到手 X 条,仍在增长」。

### 第二次:worker 进度计数器被自己污染 ⇒ ETA 严重失真

- 监控里 `xp` 波次显示 **162,713**,而我定的名义总波数是 **143,700**
- **计数器 > 名义总数 = 不可能值** ⇒ 立刻说明计数器已经不可信
- 原因:**我做的「全范围重扫」把重跑的波次又累加进去了**
- 基于这个被污染的分母,我又报了 zt「剩余 43,505 波 / 6.3 小时」——**数字本身是垃圾**

**规矩:任何「进度计数器 > 名义总量」都必须在报告里当场作废并换口径,不能继续算。**

## 二、正确的进度口径:业务硬指标优先

**优先级(从最可信到最不可信):**

| 优先 | 口径 | 本会话实例 | 为什么可信 |
|---|---|---|---|
| **1** | **业务关联率**(两张真实表之间的 join 命中率) | 订单 ↔ 面单关联率 `3,642,946 / 4,083,885 = 89.2%` | 直接反映交付物完整度,不受 worker 行为影响 |
| 2 | 落盘产物行数 | 合并后 CSV 行数 | 可复算,但滞后一个回传周期 |
| 3 | 计数器/worker 进度 | `zt=214,728` | **可被重扫污染,只能看趋势不能看绝对值** |

**做法:每次报进度都给出业务关联率 + 缺口绝对数**(「还缺 440,939 单」),
这两个数用户能直接理解,而且不会被措辞掩盖。

**计数器只用来算「速率」(两点差分),不用来算「完成度」。**
算速率时也要确认两点之间没有发生重扫/重启,否则差分也是假的。

## 三、ETA 的规矩(与 dataset-scale-estimation §四 配合)

1. **按流分别报**,并点明瓶颈是哪条流。
2. **先量速率再报**:两点差分(间隔 ≥3 分钟),不要用瞬时值或估算值。
3. **给区间 + 说明口径分歧**,不要给单一乐观数。
   本会话两个口径给出 80 分钟 vs 2.5 小时 ⇒ **取保守值报「1.5–2.5 小时」并说明分歧原因**。
4. **提速声明必须跨一个周期复测**(见 `restart-orchestration-and-resume-safety.md` §一 规矩 3)。
   当轮测出的「提速 4 倍」不可信 —— 本会话就是这么误报的。
5. **宁可事后上调并解释,不要给乐观数然后反复延期。**

## 四、缺口判定的正确做法(别把空单位当漏采)

- 名义 ID 空间里**大量单位是空的**(本目标抽样 23 个「缺口」单位:`total=23 empty=23 withdata=0`)
- ⇒ **缺口 ≠ 漏采**。判定漏采必须**实采几个缺口单位**确认里面有内容,
  再按「有内容的单位」重算分母
- 报「已完整」要有**实采证据**,不能只凭「名义空间跑满了」
