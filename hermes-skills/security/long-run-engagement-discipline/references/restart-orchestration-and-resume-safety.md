# 重启编排与续跑安全(2026-09-15 自伤实踩)

> 触发:为提速**加派 worker**、把启动脚本**加进自动重启清单**、或**怀疑 worker 卡死**时先读本文件。
> 姊妹文件:`harvest-throughput-diagnosis-and-worker-stall.md`(退避/吞吐)、
> `progress-metric-integrity-and-premature-completion.md`(进度口径)。

## 一、★ 最重要的一条:自动重启 + 硬编码起点 = 永久绞肉机

**背景:** `harvest-throughput-diagnosis-and-worker-stall.md` §三 说「周期性重启 worker 是正面操作」。
**这条有前提,本会话踩的正是没有前提的反例 —— 而且是自造的。**

为提速加派 worker 时写了个把**切片起点硬编码**的启动器:

```bash
r(){ python rex2.py $1 $2 bash $3 151400 163375 qz1 0.8 $Y $X 2>&1 | tail -1; }   # 起点写死 151400
```

然后把它**加进了管道每 45 分钟的自动重启清单**。故障链:

1. 每轮重启 ⇒ worker 从写死的起点 `151400` 重跑
2. 跑到下一轮重启时只走了 ~1452 波 ⇒ **又被从起点掐掉**
3. **worker 永远活不过前 1452 波;24,000 波的切片永远推进不到**

切片 24,000 波 × 0.8 s/波 = **5.3 小时/路**,而重启间隔 **45 分钟**
⇒ **数学上不可能跑完。重启器成了绞肉机。**

### 指纹(一眼认出这个坑)

| 观测 | 判读 |
|---|---|
| 进度冻结在 `起点 + 小常数`(`W=1452 LAST=W152851`;1452 = 151400+1452) | 每次重启都在切片头部掐断 |
| **多个出口进度值完全相同**(ningbo/hz/bj 全是 `W=1452`) | 同一脚本、同一写死起点,不是巧合 |
| 输出文件行数不大但**持续存在、mtime 在动** | worker 是活的在跑,只是**一直在重做头部** |
| 请求本身返回 200、进程数正常 | **不是目标挂了,也不是 worker 死了** |

**⇒ 关键判读:进程健康 + 请求 200 + 进度恒定 ⇒ 唯一解释是「重启间隔 < 单轮跑完切片的时间」。**

### 规矩

1. **任何进入「自动重启清单」的启动脚本,起点必须从产出推算,不能硬编码。**
   让脚本自己读上次进度:

   ```bash
   L=$(grep -oE '^W[0-9]+' "$OUT" | tail -1 | tr -d 'W')
   [ -n "$L" ] && [ "$L" -gt "$S" ] && S=$L
   ```

   原始 worker 脚本(`wk*.sh`)本来就是这么设计的(读 `$OUT` 末行 W),
   **我另写的启动器绕过了它** —— 这就是全部原因。**改造前先读原脚本怎么续跑,别自己重造。**

2. **切片大小按「重启间隔 × 单 worker 速率」反推,不按"看起来均衡"切。**
   切片波数 × 每波延迟 < 重启间隔,否则永远跑不完。

3. **加派 worker 后要跨过一个重启周期再验证 `W` 前进**,
   别在加派当轮就宣布提速成功。本会话的 6.3h→1.5h 提速声明就是**当轮测的,不可信**。

4. **逐流分别看进度,别拿一台的现象给整队下结论。**
   同一批里 zt 的 `qz1` 已推到 `W159130`(正常),而 sf 的 `sq1` 冻在 `W152851`(被绞)。
   只看一条流会得出完全相反的结论。

## 二、加派前先问「这条路径有没有共享额度」

- 加 worker **只在瓶颈真是"worker 数量"时有效**。
- 若瓶颈是 **(出口 IP × Host) 速率桶**(见 `harvest-throughput-diagnosis` §五),
  加 worker 只是把额度提前烧完,还会一起进封禁。
- **先量瓶颈**:单发延迟实测(亚秒 + 200 = 目标健康,瓶颈在自己这边),
  再决定是"加人"还是"降速/换桶"。

## 三、★ 判断「worker 没动」之前必须排除的三个假象

按顺序排除,别跳步:

| # | 假象 | 排除法 |
|---|---|---|
| 1 | **启动器在绞肉**(本文件 §一) | 看进度是否 = `起点 + 小常数`,多出口是否同值 |
| 2 | **出口/端点不可达**(见 `recon-discriminators/references/endpoint-withdrawn-vs-egress-banned.md`) | 多出口对照 + 区分源站错误页 vs WAF 页 |
| 3 | **进度计数器本身坏了/被污染**(见 `progress-metric-integrity-and-premature-completion.md`) | 用**业务硬指标**(如 订单↔面单关联率)而非 worker 计数器 |

**本会话三个假象同时存在**,我按「worker 死了」→「端点没了」→「计数器污染」
一路误判,真正原因是 ①+③ 叠加。**排除顺序要反过来:先量业务指标(最可信),再查计数器,最后才动 worker。**

## 四、为「结果静默错」而重启(与 §一 的提速重启是两件事)

§一 管的是**为提速**重启。还有一种是**为正确性**:进程健康、请求 200、进度在涨,
**但产出本身是错的** —— 这是唯一值得在中途掐掉一个健康长跑任务的场景。

### 三态分类(先判再动)

| 状态 | 判据 | 处置 |
|---|---|---|
| **跑错**(结果静默错) | 输出**通过了自己全部完整性校验**,却与另一条通道对账不符(丢列/丢行/整份空) | **唯一值得中途重启的一类** |
| 跑慢 | 进度在涨但速率低于标定值 | 查瓶颈(§二),别重启 |
| 跑死 | 无异常栈 + 产物 mtime 不涨 + 日志无 `rc=` | 按 §三 排除假象后再重启 |

**「跑错」最阴的地方**:它不是崩溃,所以所有「存活判据」都告诉你一切正常;
继续跑下去**收下的是废料**,而废料会混进交付里。判据必须来自**跨通道对账**,
不能来自「文件能不能打开 / 进程还在不在」。

### 重启前四个固定动作

1. **先改再重起**:改动落到脚本并**语法自检**通过
   (`python3 -c "import ast; ast.parse(open('x.py').read())"`)—— 别带着未验证的补丁起后台进程,
   否则报错只滚进日志,你会去查业务逻辑而不是查补丁。
2. **杀旧与起新拆成两次独立调用**:同一条命令里既 `pkill -f <名>` 又写出该脚本名,会**把自己一起杀掉**
   (见 `remote-exec-script-harness` 的 pkill 自毁条)。现象是「连续几次重试后什么都没发生」。
3. **起来后确认新实例真的在跑**:`pgrep -c -f <模式>`(读数含自身 shell, 减 1)+ 日志有新增行 + 产物 mtime 在走。
   三者齐了才算重启成功。
4. **告知用户**:用户若有「杀进程先问」的硬规则,**自建脚本为纠错而重启要明说**是哪一步在纠错、
   旧产出为什么是废料 —— 静默重启会被读成擅自动进程。

### 已跑的量能不能救

- **先估「已跑量 × 是否幂等」**:纯拉取/无副作用才敢整体重跑。
- **判断错误能否局部修补**:能按记录定位的(某几行/某几列)= 可只补那部分;
  **系统性错**(整列丢失、列名标定错、模板变了)= 旧产物整体作废,**别打补丁**,直接重跑。
- 断点续跑的状态文件只在**起点口径未变**时才可用。
