# v9 drain 队列实机验证:调试链与修复实录(2026-09-01)

场景:v9 采集端(主服抓票队列调度/缺口补拉/榨干队列)部署 8 台后,drain 队列全空、日志无处理行。以下为按序排障路径,未来同类"新机制部署后不生效"直接套用。

## 症状
- `/tmp/v6_state.json` 的 `drain` 字段 8 台全空
- 日志只有"审计 ST 61, 新 36 / 轮询完成"汇总行,无 `  账号 (单位)` 处理行、无 `🎯`/`📦` 新机制输出
- 部署后等 6 分钟(约 4 轮)仍空

## 调试链(按序)

1. **确认代码已生效**:远端 `md5sum /opt/v6/collector.py` == 本地新 md5,`systemctl is-active` active。排除部署失败。
2. **查 state 队列字段**:drain 空 = 入队代码(`if _all_ids and _my_acct(...)`)没执行到或条件不满足。
3. **grep 处理行**:
   ```
   journalctl -u v6collector --since "1 hour ago" | grep -E '^.{17}  [a-zA-Z0-9_]'  # 处理行
   ```
   处理行只在 `user/info` 成功后打印。16:07 修复版部署后 8 轮零处理行 → 候选票全被过滤。
4. **根因一:seen 占名额(已修复)**——原 30 分钟窗口逻辑:
   ```python
   for t in tickets:
       if t["st"] in dead_set: continue
       if not _my_ticket(t["st"]): continue
       if t["st"] not in candidates and t.get("time","") >= cutoff:
           candidates[t["st"]] = t
   ```
   已处理票(st in seen)也被加回 candidates → 挤满 `proc_new = sorted(...)[:15]` → 真新票(not in seen)排不进去 → 每轮 0-1 票。修复:
   ```python
   if t["st"] in seen: continue   # 已处理票不再占名额;失败票走 retry 队列
   ```
   注意:new_t 循环(审计新票)不受影响,只有窗口票循环需要加。
5. **根因二:分片环境变量(验证中)**——修复后仍零处理行,下一步查:
   - `systemctl show v6collector -p Environment` 是否含 `V6_SHARD=n`
   - `cat /proc/$(pgrep -f collector.py|head -1)/environ | tr '\0' '\n' | grep V6_SHARD`
   - 算 st_times 票 `int(hashlib.md5(st.encode()).hexdigest(),16) % 8` 分布是否 ~均匀;若全台 SHARD_ID=0(环境变量缺失默认 0),只有 hash%8==0 的票(1/8)被处理,其余台处理行≈0 但有 1 台(0 号)应正常——若 8 台全静默则另有原因。

## 诊断脚本陷阱

- **paramiko 外层 f''' 包裹内层 heredoc 脚本 → f-string 冲突**:内层脚本所有 `{...}` 被外层解析 → `SyntaxError: f-string: empty expression not allowed`,报错行指向 PYEOF。解法:外层普通字符串 + `.replace("@IP@", ip)`。
- **采集机域名**:collector 的 B = `https://cg.95306.cn`,不是 zjgcjypt.com。诊断脚本直连用错域名 → `Name or service not known`。复用 collector 的 B/bfwz_get,别另起炉灶。
- 单测接口 HTTP 500 大概率是 ST 过期或 header 传法问题,别在诊断脚本上耗时间,优先走日志/state 证据。

## 经验结论
- 调度系统验证的标准姿势:**处理行计数 > 汇总行**。汇总行"新企业包件 0"可能是数据已齐全(正常),但处理行缺失 = 链路断了。
- 修复部署后等 3-4 轮再下结论,期间同时收集 state 证据。
- 当前状态:seen 修复已部署(8 台 md5 51529857…),drain 验证仍未通过,分片环境变量是下一步疑点——未验证前不得宣称机制生效。

- 单独 `候选 1-4 → proc N(新N/重试0)` **不是**新票信号,是风控冷却重试环;必须配「识别>0 / 入队 / 榨干 + 账本差分」才算机制信号。
- 深探只读一条命令(12 台一次跑完,经主服 base64 中转,输出 @@LAST12/@@EVT/@@STATE):`profiles/123/scripts/_drain_verify_0911_0055.py`;sh8-11 应用日志在 `/opt/v6/v6_run.log`(journald 空),按时间窗 `grep -aE "\[09-11 00:4[5-9]:"` 取处理行上下文。
- **DRAIN 账本量级已变**:2026-09-02 记的「稳态 1-5」早已过时——2026-09-11 01:00 实测单机 28-55(上海3=55 最高),12 台合计 **420**。账本 = 曾入队账号留存(榨干后不删,持久化),随日累积,**不能按深度判积压**,更不按旧「1-5 正常」口径判异常;判在不在跑只看「事件行 + 两点差分」。
- `识别 N>0 + SEEN +N` = 真新票识别证据(**即使同一轮紧邻 🧊 风控冷却行**)。实例(上海3/sh8,2026-09-11):`00:46:48 处理行 nifhort (王浩宇/辽宁尚昇贸易有限公司)` → `00:47:00 ↳ 风控响应 [/user/info]: code=100 msg=系统服务异常…` + `🧊 触发风控冷却 15min(business 域暂停,审计继续)` → `00:47:01 轮询完成, 目标 96, 新企业包件 0, 识别 1, 重试队列 0, 死票 0`;`/tmp/v6_state.json` SEEN 172→173、DRAIN 55 不变 ⇒ 真识别(处理行 + 账本差分双证),不是 tail 窗口伪影。
- 上轮汇总里的 DRAIN 数字可能有笔误:2026-09-11 上轮自报成都2 37,本轮实测 36,而该机 collector 自 09-10 18:39 未重启、无清理/prune 行、state 实时写入 ⇒ 账本按设计只增,**数字对不上优先怀疑汇总读数错**,别当异常上报(除非同时有 restart/清理日志)。

## 2026-09-10 代码级语义补正(判读口径固化,sh0 collector.py L1306-1322 实读)
- **账本 `tm` ≠ 入队时刻**:入队块为 `_d["tm"] = t["time"]` → tm 是**票自身的 time 字段**(票发布时间),每次入队整条目覆盖。故多台出现同一 tm = 同一张票被多台重复入队(全局广播),**不可**用 tm 反推"首次入队时间",也不可用"tm 很早"判定旧票。
- **入队分支的残留 elif**:`if _all_ids:` → log `drain 入队 {acct} N 项目`;另一支 `elif _all_ids:` → log `drain 跳过(分片)`(旧 `_my_acct` 分片残留路,注释已改为"修复:去掉 _my_acct 二次分片")。实测 2026-09-10 全 12 台「跳过(分片)」命中 **0**,`drain 入队` 当日 18–26 次/台(sh8-11 走 v6_run.log 累计 87–93)→ 无 acct 二次分片 = 全局广播拓扑确认。**验证修复生效的最快判据 = 这两条计数**(比逐机 tail 更快更硬):
  ```bash
  journalctl -u v6collector --no-pager --since today | grep -ac '跳过(分片)'   # 期望 0
  journalctl -u v6collector --no-pager --since today | grep -ac 'drain 入队'   # 期望 >0
  grep -n -B22 'drain 入队' /opt/v6/collector.py   # 看 if _all_ids 是否已无 _my_acct
  ```
- **入队 ≠ 新票**:同一企业 dc12301(票 time 11:33:43)在 sh11(11:42:10)/sh6(11:45:36)/sh9(11:49:15)/sh0(11:50:07)四台各入队一次、各台 DRAIN +1(per-machine 账本)→ 是广播重复,**不是 4 张新票**。报"新机制生效"可以,报"新票"必须满足:该企业当轮账本 `all/done` 真有变化 + `新企业包件 N` 与入队项目数量算术闭合 + `识别 > 0`。
- **榨干可能被业务域风控冷却推迟**:dc12301 本轮 `n_all=4 n_done=0`,入队后 3+ 分钟无 `📦 榨干队列` 行;同期日志有 `🧊 触发风控冷却 15min(business 域暂停,审计继续)` 与 `冷却升级(当日第 N 次): 冻结到次日 00:10(北京)`。入队后榨干缺席时先查这两行再判故障(冻结账号 cohort 实例:bjxcd001 单日 208 次、w<PHONE-REDACTED> 47 次、wangzhaoying 22 次)。
- **hb_age 受采集机时钟影响**:同一轮 sh0-2 = +86~+95s、sh3-11 = -76~-90s(±90s 量级,`stat -c %Y` 取的是采集机本地 mtime);跨机不可比、也不是失活判据——服务活跃性以 journal 秒级新行(轮询完成/候选)为准。
