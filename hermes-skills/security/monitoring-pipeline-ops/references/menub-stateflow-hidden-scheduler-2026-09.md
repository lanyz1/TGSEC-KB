# 菜单B 状态流转 + 隐藏调度定位 + 观察窗口陷阱(2026-09 实录)

95306 v6 系统实录,三组可复用经验。

## 1. 隐藏调度者:"merger 退休"是误判(调度定位法)

现象:用户问某常驻脚本(merger)干嘛用的;crontab 里只有 sync_plat_enroll(30min)+ orch8b(5/35min),**没有 merger** → 早前结论"merger 已退休,orch8b 接替"。但后来 index.json 每 2.5 分钟自动更新(updated 时间戳跳动),且没有任何 crontab/常驻 merger 进程——写者其实是 **pix_bot_server 主进程内部周期 subprocess.run("cd /opt/v6 && timeout 180 python3 merger.py ...")**。

教训:
- **判断"脚本退役"不能只看 crontab**:主进程可能在内部 subprocess 周期调度(搜索 `subprocess.run`/`subprocess_check` + 目标脚本名)。
- **文件被谁写**:看文件内容自述(`updated`/`source` 字段)→ 连续 `stat` 两次确认仍在更新 → `grep 目标脚本名 所有常驻进程的代码`(含 subprocess 字符串)。
- 误判"组件退役"会导致后续所有推理建立在错误前提上(当时以为 gaps.json 断供是 merger 退休导致,实际 merger 还活着、只是输入源变了)。

## 2. 平台状态滞后 → 用本地时间字段推导状态机(不等上游切状态)

现象:项目报名 17:00(平台时间)截止,但平台 selectSelfSellList 2 小时后仍返回 `status=19`(发布中),平台自己没切"待竞价";下游 stage 字段死等平台 → 项目卡在"报名中"分类,不流转。

修复模式(通用):
- **状态机不要只吃上游 status 字段**,手里有权威时间字段(如 `regEndtime=202609031700` 报名截止、`bidStarttime` 竞价开始)就本地推导:`stage=报名中 且 regEndtime < now → 视同"报名结束"`(归待竞价组),不等平台。
- **时区纪律**:平台时间是北京时间(UTC+8),服务器可能是 UTC——所有时间比较先 `datetime.utcnow() + timedelta(hours=8)` 统一到平台时间系;字符串直接比较会因格式(`202609031700` vs `2026-09-03 17:00`)与时区双重出错。
- 截止时间解析支持多格式:`%Y%m%d%H%M` / `%Y-%m-%d %H:%M[:SS]` / `%Y-%m-%d`,逐个 try。
- 注意:平台接口(selectSelfSellList)可能**不返回截止字段**(sellEnddate=None)——权威截止时间在旁路字段(公告流解析出的 regEndtime),查 index 全字段再下结论。
- **"部署日/上线日过滤"类旧约束要定期审视**:DEPLOY_DAY 过滤当初为"部署前公告的项目报名真空期拦不全"而设;等系统有了权威名册 + 差集补漏 + 审计联动兜底(数据完整性不再依赖"从报名开始拦截"),这类一刀切过滤已过时,应放开(否则 8/28 公告的活项目在菜单里永远不可见,用户困惑"项目去哪了")。放开前确认兜底链路(名册/补漏)确实覆盖被放开对象的阶段。
- **状态机改动影响面**:bot 分组逻辑改后,下游消费方(orch8b 补漏条件 `stage=="报名中"`、gen_gap `_is_live` 四态)的 stage 口径要同步——若数据层 index stage 仍写"报名中"(为让 orch8b 继续补),那"时间推导"只放渲染/分组层,两层口径要分清(渲染推导 vs 数据真实值)。

## 3. 观察器/诊断脚本的日志窗口陷阱(误报"还在抖动")

现象:修复部署后,后台观察器每次 check 都打印同一条异常+同几条推送 → 误判"修复无效、异常每轮还在刷"。实际:**观察器 grep 的是日志文件尾部窗口,输出行号每次重新计数**;06:40 重启后新日志主要是用户操作(不匹配 grep 关键词),匹配行全是 06:40 前旧进程的历史记录 → 每次 check 输出几乎不变,看起来像"每轮都在发生"。

教训:
- 观察器先**对齐时间线**:`ps -eo pid,lstart` 进程启动时间 vs 日志中"启动"标记位置;grep 输出的行号排序 = 文件内位置 = 时间顺序,异常行在"启动行"之前 = 旧进程历史,不算新发生。
- 多 check 输出几乎相同 = 无新事件(不是"重复发生")。判断"是否还在发生"看**新增**内容,不是窗口内容。
- setsid 后台脚本 stdout 全缓冲:重定向到文件时 print 不 flush 会一直空到进程退出——调试脚本一律 `flush=True` + 阶段时间戳打印(`t=%.1f import done`),避免"卡死 vs 慢"误判。
- import 大模块(4000 行 + 全量数据初始化)慢≠卡:先加阶段打印再下结论;卡死定位用阶段标记,不要盲等。

## 4. 大名单线性匹配 → 卡死与索引化

现象:新分组函数(每项目×每企业调 norm_ent_name)全库跑 5 分钟+不返回——`norm_ent_name` 每次 `for full in 36.9万条供应商名单: _norm_key(full)==key` 线性扫(91 项目 × N 企业 × 2 遍 ≈ 亿次字符串比较)。

教训:
- 归一化/匹配函数如果内部全量扫大名单,任何"被批量调用"的新场景都会把它从毫秒级打成分钟级。**匹配前先问:这函数在循环里被调多少次 × 名单多大?**
- 修复:建 **norm-key → 全称 索引 dict**(一次遍历 36.9 万 ≈ 1-2s,缓存 10min),主匹配 O(1);包含匹配(低频)保留线性回退。
- 性能诊断:卡住时加阶段打印(见 §3),确认卡在哪个函数;不要靠猜。

## 5. 推送文案名称截断批量修复

用户报"好多项目名称显示不全"(例:`…有限公司202` 被切)。全库 grep 显示多处推送/告警对 projName/企业名做了 `[:18]/[:22]/[:28]/[:30]` 切片,各点截断长度不一。修复:统一放宽到 `[:80]`(项目全名最长 ~60 字,远低于 TG 4096 单条上限);CSV/Excel 导出单元格应全名不截。TG 消息内列表条目少,放宽无超限风险。**检查清单**:`grep -n 'projName.*\[:\|\[:\d\+\].*projName'` 全库扫一遍,逐点评估(展示类放宽,仅防御性截断可留)。
