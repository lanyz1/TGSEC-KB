## 机队实体台账、断供与到期诊断

- **SSH 失败先分类,别判"机器死了"**:`BadAuthenticationType` = 服务端禁用口令认证(与口令对错无关)⇒ 该机已切 publickey-only,换主服私钥 `pkey=` 重试;`AuthenticationException` = 口令错;100% 丢包 + :22 无响应 / `socket.timeout` = 真失联。三类混判会把"认证方式变了"整批报成机队掉线。
- **判"哪台真断供"用回传目录 mtime 横比**:rsync 落点(如 `/data_raw/<台>/`)内最新文件 mtime = 主服最后一次收到该台数据的时刻;某台明显落后其余台 = 该台已断供,该时刻即断供起点(据此算漏采窗口)。**与心跳规则不冲突**:心跳 mtime 恒新鲜只证推送器活着(判活无效),横比才判死。
- **云主机"到期停机/被释放"形态**:单台 ping 全丢 + :22 超时 + 每轮重试全失败,而其余台正常 ⇒ 先按到期停机定性,去控制台续费+启动(停机保留期内数据还在),别先改代码。要让用户在控制台搜得到就给**云实例 ID**:阿里云 hostname 形如 `iZ<instance-id>Z`,去掉首 `iZ`/末 `Z` 即实例 ID;规格/地域/类型从实例元数据取 `curl -s http://100.100.100.200/latest/meta-data/{instance-id,instance-type,region-id,zone-id}`。
  - **★主控(中心机)停机 ≠ 采集机掉线,症状面完全不同**。用户看到的是**托管在主控上的服务**不回话(bot 没反应/面板不更新/推送停),不是"某台机掉线" ⇒ 禁止一头扎进改 bot 源码、怀疑 offset 丢消息或去翻 12 台采集机。判别 = **三视角 + 双 IP,全部要打**:①本机直连 `timeout 12 bash -c 'cat </dev/null >/dev/tcp/<ip>/<port>'`(**超时即无输出——工具掐断,"看不到打印"本身就是不可达的证据**)②经本机代理出口再打一次 `curl -s --socks5-hostname 127.0.0.1:10808 -m 10 -o /dev/null -w '%{http_code}' http://<ip>:<port>/`(paramiko/裸 TCP **不走系统代理**,只能这样拿"境外出口"视角;同命令打 `http://api.telegram.org/` 应回 302 作阳性对照)③从一台国内采集机 `ping` + `curl` 主控。**三处全不通 + 主控主/备两个 IP 同时死 + ICMP 100% 丢 ⇒ 主机级离线**(停机/欠费/硬件/被释放),不是封禁、更不是脚本层——**进程级操作不可能让双 IP 与 ICMP 同时死**,这条推理直接排除"是不是我把它改坏了"。定性后按上条走控制台续费/启动;完整判别矩阵、影响面核算与开机后恢复清单见 `references/master-outage-triage-and-recovery.md`。
- **续费台账纪律**:机内无 AKSK/RAM 角色 ⇒ 读不到 `ExpiredTime`,用 `uptime -s` 开机时刻当账单周年 + 交付实例 ID 供控制台检索;厂商/机房靠外网 IP 归属(AS + org)+ 系统里残留的面板标记(如 `/etc/resolv.conf` 的安装串)反查经销商。**清单文件绝不写口令/私钥**;取证一律经主服跳转,凭据不出主服机。
★★**merger 每轮 ≈11分47秒 才是正常值;"开始合并流程 → 合并完成" 之间的静默不是卡死(2026-10-01 实踩,我误 kill 过一轮)**。实锚三轮连续配对:`[16:26:30]开始 → [16:38:17]合并完成`、`[16:40:46]→[16:52:30]`、`[16:54:59]→[17:06:43]`,每轮都是 **11m47s**,期间**不打日志、不写池**(池文件 mtime 停在上上轮),日志里还夹着 `某台: tar 打包失败` / `某台: 失败 timed out` 这类非致命行 —— 只看"日志 10 分钟没动 + 池子没刷新"必然误判成死循环(我据此 kill 了进程,**那一轮其实是健康的,白跑**)。

  - 该阶段是**全量 roster 重合并**(逐个过 `/data_raw/95306_full/roster_*.jsonl.gz`,实测 90 个文件),属周期性重活,不是每轮都走。

- ★★**拓扑铁律(用户 2026-10-01 亲自纠正)**:本机(Windows 工作台)**从不直连采集机** —— 链路是 **本机 → 主控 → 采集机**,采集机的云安全组/白名单**只对主控 IP 开放** ⇒ 本机 `ping`/`/dev/tcp 22` 测采集机**天生无效**(实踩:本机测在跑的成都也是"断",同一时刻主控侧是通的)⇒ **所有采集机可达性判据一律在主控侧跑**(mrun/ssh、merger 日志、回传目录 mtime)。主控换 IP 后采集机批量失联的真因就是**白名单里还是旧 IP**;要放行的是主控**唯一真实出口 IP**(另一张网卡上的副 IP 不出站,填了也没用)⇒ 给用户的操作指令必须写成"安全组入方向 TCP 22 放行 <真实出口IP>/32"(或直接 0.0.0.0/0,和其余机器保持一致)。**另:用户口述"已修好/另一台也好了"指的是他在云控制台做的动作,但那一下可能点在同族另一台**(成都 `47.108.152.60` vs 成都2 `47.108.173.230`;广州 `8.138.236.124` vs 深圳 `47.107.124.62`;实例 ID 只差一位)⇒ 口述一律**以主控侧实测复核**,矛盾时以实测为准并回告"哪一台真的变了"(实踩:用户说两台都好,主控实测成都通/广州闭)。
- ★**Windows 下脚本内调 mrun.py 必须走 shell(2026-10-01 踩)**:Python 里 `subprocess.run(["python","mrun.py",...], capture_output=True)` 报 `ModuleNotFoundError: No module named 'paramiko'` —— `shell=False` 的 PATH 解析找到的是**另一个 python**(无 paramiko),而 shell(PATH 里的 git-bash)那个是好的 ⇒ 写后台值守类脚本时用 `subprocess.run(cmd, shell=True)` 且把远端命令用双引号拼进去(远端命令里的单引号如 `pgrep -af '[m]erger.py'` 可原样保留);同时把 `stderr` 也并入返回,否则报错被吞成"空输出"。诊断法:先跑一个最小脚本打印 `RC/len(stdout)/stderr` —— 一眼定性。
- ★**采集机云侧封禁(安全组/实例状态)与"断链期数据零损失"判据(2026-10-01)**:两台机(`8.138.236.124` / `47.108.152.60`)**ICMP 通但 22/80/443 从任何来源全闭** ⇒ 主机层排查(hosts.allow/iptables/sshd)对在跑机器逐条看全是**全放** ⇒ 机队**不靠主机白名单工作**,问题一律在云侧**安全组入方向/实例状态**;修法 = 用户在控制台操作(续费/启动/安全组)+重启,恢复后 systemd 自动拉起、无需手工干预。**恢复自证五件**:TCP 22 通 / `hostname`+`uptime -s` 是同一台 / `systemctl is-active`+state mtime 在写 / merger 该台那行不再 `失败 timed out` 且 `/data_raw/<台>/` 最新文件刷新 / 本轮 `完成:` 行照常出现。**断链期是否丢数据**:看该机**自己的**日志 —— 它一直在 `轮询完成`(本地采集正常,只是回传断了)⇒ 缺口是"回传"不是"采集",merger 全量补拉即补齐(实测恢复后一轮只回传 5 文件 3KB,因为那段时间平台本身无新包件)⇒ **判"丢没丢"要区分 采集 vs 回传 两段**。
★**merger 自带的 `rsync_fail` 连续计数是死代码**:它要求两次失败间隔 ≤5min 才累加,而 merger 轮次 ≈11.6min ⇒ count 永远停在 1,它那句"连续≥3 轮告警"永远不触发。**排查机队掉线别依赖它**,用 `/opt/v6/fleet_gc.py`(cron */10):按"失败时间戳是否刷新"自维护 streak ⇒ 冗余机 3 轮自动摘除+TG 主动推送,主机 3 轮只告警,6h 去重;支持 `--dry`/`--selftest`。
- **换机重配 / 冗余采集(2026-09-28 实做)**:下线一台 = 从 `jumpers.json` 摘掉它的条目 + 该机 `systemctl stop/disable v6collector`(保留 state 与 /data_raw, 可一行恢复) + 顺手把 `orch8b.py` 静态兜底 `BOXES` 表一起换掉(否则 jumpers 读失败会去唤醒已下线机)。验收=等一轮 merger 只看得到 12 台 + `gen_gap 12/12`。:换机后**只改 `/opt/v6/jumpers.json`**(唯一舰队源,含 `name/ip/port/pwd/shard`,先备份)——merger/orch8b/gen_gap/bot 全读它。**到期前的老机可当同分片冗余挂回**(merger 按观测时间去重,不脏数据,纯增量),到期删两行即下线。**非 22 端口机(宁波 25175)要求所有主控 SSH 消费方从 jumpers 取 port**,任何写死 22 的代码都要拔。**按“列表位置”当语义的机队代码(如 orch8b 原用 `enumerate(BOXES)` 当 shard)必须改成显式 `shard` 字段**,否则多机/乱序会静默喂错分片。`ent_coverage.json`(6MB)每 6h 才推 ⇒ 新机接入必须手动补推。详见 `references/fleet-reconfig-2026-09-28-inventory-and-sop.md`。
- **`BadAuthenticationType` 的另一半根因**:服务端 `PubkeyAuthentication no` 时,口令能通、密钥恒失败(宁波实踩)⇒ 先 `sshd -T | grep pubkeyauthentication` 复核再判机器死活;修 `yes` + reload + 重写 authorized_keys。同时:paramiko/mrun 通道读超时约 3 分钟,远端长任务(含 sleep 等待)必被扯断 ⇒ `setsid nohup … > /tmp/x.log &` + 短命令读日志。**★远端脚本里拉常驻也别用 `capture_output` 的 `run()`**:`subprocess.run(["bash","-lc","setsid nohup X & sleep 8; echo OK"], capture_output=True, timeout=60)` 会因**后台子进程继承着 stdout 管道**而一直等到超时(报 TimeoutExpired/EXC),但 X **确实起来了** —— 别据此判失败:事后 `ps -eo pid,etimes,args` 核实,`etimes` ≈ 已过秒数即证明是本次拉起的;要干净就 `Popen(..., start_new_session=True, stdout=DEVNULL, stderr=DEVNULL)`。
- **探针脚本要核脚本身份再信输出**:在长期复用的脚本目录里写同名文件可能被写守卫拒绝(旧文件保留),紧接着的执行会跑**旧脚本**并正常 exit 0 —— 输出看着合理却属上一轮的目标名单/逻辑。每个任务新建子目录;跑前核对 md5/首行,写完 `read_file` 验尾。

### ★主控离线后的恢复清单(开机后按序跑,幂等)

- **cron 轨自己会回来**:主控 cron 全是 `* * * * *` 形态、**不依赖 `@reboot`** ⇒ 开机即按表恢复,无需人工。**只有常驻进程要手动拉起**:merger(`setsid nohup bash /opt/v6/merge_daemon_fast.sh`,自身 120s 循环)、`security_watch.py`、`priv_loop.py`(带 `flock -n /tmp/priv_loop.lock` 保单例)、`pix_bot_server.py`(带 `-X utf8`,日志 `/opt/v6/pixbot.log`)。**精确命令行从现役 `ps -eo pid,ppid,etimes,args` 快照里逐条抄,改前重核一遍现役进程表**;`while true … sleep N` 形态的残留循环(如 `/tmp/stage_verify.py`)不计入标准常驻集。
- **补拉一律用幂等守卫**(缺谁补谁,重复执行安全):`pgrep -f X >/dev/null || (cd /opt/v6 && setsid nohup … >> log 2>&1 < /dev/null & echo UP)`。**别无条件起第二条**——bot 双实例会抢 TG polling,现象是两边都不回话。
- **恢复后自证四件**:①进程表 `ps -eo pid,etimes,args | grep -E '[m]erger.py|[p]ix_bot_server|[p]riv_loop|[s]ecurity_watch'` ②池/令牌文件 mtime + 体积(`/data_pool/index.json`、`/opt/v6/bid2_tokens.json`)③merger 首轮日志 `tail /tmp/v6_merge.log`(应见逐台同步)④bot 日志尾 `tail /opt/v6/pixbot.log`。
- **回答"数据会不会丢"前先算缓冲**:采集机 systemd 自启 ⇒ 离线期间照常采集、产出落本地盘(单机 `/tmp/targets` 2.6–26 MB、系统盘 49 G,数周不溢出),主控回来 merger 全量补拉 ⇒ **不丢**。**兜底路径**:机队 SSH 是 publickey-only ⇒ 本机持主控私钥(本地有副本)即可直连全部采集机,**主控真要换机/重建也能把数据捞回,不依赖主控**。

### ★主控换 IP(2026-10-01 实做,换 IP 类操作的标准动作)

- **顺序**:全量替换引用 → 重建通道 → 重判 403,不能反。①本地连接脚本(`mrun.py`/`mpull2.py`)改成**双 IP 列表逐个试**(主机商给两个就都写进去;写死单个 ⇒ 下次换 IP 再全断一次)。②主控自身硬编码旧 IP:实测只有 `pix_bot_server.py` 的"服务器信息"面板 + 两个 v936 变体(`/opt/v6` 下 grep py/sh/json)。③**先判归属再改**:`/root/测绘引擎/tools` 里 grep 到 `128.241.245.` 的 7 处**是别的机器**(`.172/.227/.247` 属工具的保护前缀/部署目标)⇒ 同段 IP ≠ 同一台机,"无脑全量替换"会改坏生产工具。④换 IP 伴随重启 ⇒ **常驻进程全丢**(见上节清单),cron 会自动回来。⑤**旧 IP 的封禁不跟着走**:实测新 IP `cg.95306.cn/=200`(旧 IP 自 09-12 被 CDN 403)⇒ 换 IP 是解封机会,但**别顺手把中继改回直连**(境外 IP 随时再被拉黑,中继已验证可用就留着)。
- **`pgrep -f X` 会匹配到自己**:mrun/ssh 传过去的命令行里含 `X` ⇒ `pgrep -f X` 恒命中(命中的是这条 `bash -lc` 自己)⇒ 幂等守卫永远走"已存在"分支、进程根本没起,还不报错。**守卫一律 `ps -eo args | grep '[X]'`**(方括号法)。
- **远端命令里双引号内的 `$(...)` 会被本地展开**:`ssh root@H "echo svc=$(systemctl is-active x)"` 在**本地**执行 ⇒ 所有机器返回同一个(本机的)值,一行输出看着完全合理 ⇒ 静默错判(本次把 11 台正常采集机报成 inactive)。判据:输出**来得太快**或**每台都一样**。改用 `\$(...)` 或整段单引号。
- **推上去的 `.sh` 先删 CR**:Windows 写文件常带 CRLF ⇒ `OLD1=1.2.3.4\r` 让 `grep -e "$OLD1"` 零命中(脚本照跑完、`bash -n` 也过)⇒ 常量静默失效。上传后 `tr -d '\r' < f > f2 && bash f2`。
- **非 ASCII 路径 + Python `os.walk` 静默漏**:中文目录(`/root/测绘引擎/…`)walk 拿到的路径乱码 ⇒ `open()` 抛异常被 `except: continue` 吞 ⇒ "扫描 0 命中"与"grep 有命中"并存。**批量替换用 shell(`grep -rl` + `while read`)别用 Python walk**;`< <(grep …)` 进程替换在非交互 ssh 里也可能喂不进循环 ⇒ 先落 `/tmp/hits.txt` 再 `done < /tmp/hits.txt`。
- **换 IP 后先验"这台还是原来那台"**:`hostname` + 数据目录/关键文件 md5 与台账对表 —— 同 IP 换了机(重装/重建)会和"IP 变了"表现一样,但数据面结论相反。本次 `hostname=jnjjn` + `/data_pool` 2.2G 完好 ⇒ 确认是同一台机换 IP,数据不用重建。

改手搓树时以下五条是**常驻纪律**（每条都烧过一轮自测或一次排障）：
- **被别的组件消费的产物，键名/嵌套就是外部契约**：健康/缺口/预算/传输台账这类文件，形状对而键名旧 ⇒ 消费端读到空值且不报错。**两侧都要核**：`grep` 消费端**读取点**（如 bot 里的 `machines[机]["status"]`）+ 产出侧写点，两者不一致时以**读取点的访问路径**为准（写侧多余的层级不算契约，读侧要用的层级一个不能少），再在离线自测里按读取路径逐键断言。
- **改文件名/形状/键名后，同批 `grep -rn '<旧键名>' tools/` 改掉假桩与断言**；新层要读的上游文件必须在假桩里真造出来，否则新层静默产出空结果、断言在别的名字上失败（看着像"新代码坏了"）。
- **判"缺口/名单为空"前先验 join 键的上游来源**：核对层恒空多半是**产端没记那个键**（本例报名操作只记时间、没记单位）。补在产端，不补在核对层；自测里放一条"必须被判中"的正样本，否则分支死了看不出来。
- **对拍扫描器报的每条"旧有新无"先 grep 新树核实一次再定性**（正则漏判会把真有的报成缺口）。
- **改函数签名前看清默认值，改完回读 def 行**：模糊匹配的 2 行锚点会把 `def f(a, b=None):` 悄悄改成 `def f(a, b):`（`py_compile` 查不出，运行期才炸）。
- **自测红灯先判“桩错还是码错”，禁止为了让桩变绿改生产代码**：红灯第一动作是回查线上权威口径（产出方写点 + 消费方读取点），再决定改谁；**桩的期望必须能指到老代码的具体行号，指不出行号的期望就是猜测**（常见桩错：把首轮当静默——线上基准为空时首轮本就出事件；把贪婪正则当非贪婪；绝对计数断言被前序断言污染 ⇒ 改比增量）。细节与三例见 `references/handwrite-vs-prod-parity.md` 第三节。
- **离线全绿 ≠ 形状对；手搓链的收尾必修是"上机联调（只读/单台/小样本）"**：离线桩会**迁就你喂的形状**（票池线上是 `list[dict]`、桩喂 `list[str]` ⇒ 离线绿、上机即 `IndexError`）⇒ 桩的 fixture 必须照真产物的**元素形状**造。联调在**主控**侧跑（本机从不直连采集机/目标）：`/tmp/<probe>/` 放两份手搓模块 + **只含通道键的极简 ini** + 探针，借 1 台采集机出口发个位数请求，只核**顶层键/容器路径/条数**；同一次请求 "直连 403 + 中继 200" = 架构红线的活体证据。全程不动进程、不写生产目录；崩溃在真形状上 = 联调的价值（记为对拍差异 → 修树 + 修桩 fixture → 复跑）。配方见 `references/handwrite-vs-prod-parity.md` 第十节，探针骨架 `templates/live-parity-probe.py`（首次用先 grep 本树核方法名/容器路径）。**取票必须取目标机"此刻的活票"**：票 TTL ≈6h，拿隔日票跑联调会全线 `code:100`，极易误读成"端点改了/权限不对"——只读载荷投到持票机上本地跑，票不出机。
- **收尾最后一步是"真产物对拍"，不是"源码对拍"**：`ls` 线上产物目录 + 逐个打印真产物的顶层类型/键风格/键集合（`type(doc)` + `list(doc)[:8]` 一眼定性），跟新树对照。**顶层是 list 还是 dict、键是 snake_case 还是 camelCase、落盘 indent 是多少，都算契约**，错一处该腿**静默全空**（不报错、日志干净、产物空）；源码里两边都能自洽，只有真产物能证伪。**从源码 grep 出的"线上有、我们没有"只是候选：先拿真产物证伪再动手**（真题里没有的键不要往新树加 —— 那是制造差异不是消差异）；反过来，判"有没有更新"的内容签名要容错地排除线上写入口会刷的运维水位键（混跑时会读到）。细节见 `references/handwrite-vs-prod-parity.md` 第十一至十三节。

### 上线这道关：时间尺 / 双级验收 / 分阶段割接

- **判态尺子用平台时间**：凡拿平台时间戳比大小的判据（票新鲜度、窗口、重查闸）一律 `bj_now()`（UTC+8），绝不用宿主本地 `datetime.now()` —— 同一行代码在 CST 采集机上恰好对、搬到 UTC 主控就 8h 偏差（重查闸恒不放行 = 静默漏采）。改完的闸必须**双时区跑**（默认 TZ + `TZ=UTC`），只在本机跑等于没测。细节见 `references/handwrite-vs-prod-parity.md` 第十四节。
- **验收分两级**：本机绿 ≠ 真机绿（解释器 3.10/3.11、时区 UTC/CST 都可能不同）⇒ 打包后必须 scp 到目标机、在**目标机自己的解释器**上复跑同一套关；自证三件 = 逐文件 sha256 清单全对 + 内容树指纹两侧**逐字一致** + 生产目录项数前后不变。汇报里写清“跑在哪台机 / 哪个解释器 / 哪个时区”。
- **动进程的动作留批准口**：割接工具拆 `--stage`（上包 + 解到 release 目录 + **在该机自己的解释器上**复跑全套关，只写 release 目录、不碰生产目录、不重启，默认跑这个）/ `--activate`（须显式 `--yes`，起不来自动回滚）/ `--rollback`；替换、重启、kill、改 systemd/sshd 一律先经用户同意 —— 没人答就停在只写 release 目录那一步，并在汇报里点明“就差你一句话”。
- **割接落点必须自洽：入口 + 版本化树 + 原子切链**（只装入口的割接必炸）：入口（`ExecStart` 指的那个文件）只做三件事——解析“当前树” → `sys.path` 插进去 → import 后跑；代码树放 `<根>/lib/<版本>/`，`<根>/current` 软链指过去，切链用 `ln -sfn <树> current.new && mv -Tf current.new current`（单条 `ln -sfn` 不是原子的）。**上线的那棵树必须是刚在“这台机”上跑过关的那一棵**（把 stage 目录 `cp -a` 过去，不是重新上传），否则“验过的”和“上线的”是两样东西。
  - 入口找不到树时**直接退 1 并打出回滚命令**：不猜路径、不进 systemd 重启循环（否则现场是“装了新代码的机器起不来还反复重启”，比装错更难判）；systemd 单元一个字都不用改（`ExecStart` / `Environment=<分片变量>` 保持原样）＝ 选这个布局的主因。
  - 回滚 = 老入口从 `<入口>.bak_<版本>` 拷回 **+** 旧指针切回（切链前把旧 target 存成 `current.prev`，回滚时 `mv -Tf current.prev current`），再重启自证；只做一条会留下“新入口 + 老树”的半截状态。
  - 工具三阶段、机队跑法/回读、`launcher` 契约、布局关、机队回读四行见 `references/fleet-cutover-entry-tree-symlink.md`；**主控侧变体（平铺老目录 / 无 systemd / crontab 混装受管块）+ 工装离线自证与反控 + 换常驻时 `pgrep -f` 的三层壳**见同文件后半。
- **crontab 割接只动受管块，认不出的条目一律拒绝割接**：只改 `# >>> <标记> >>>` … `# <<< <标记> <<<` 之间，块外一行不碰；开工前 `crontab -l` **全量取回逐行归类**（keep 逐字照抄 / stop / tmpl 供新条目继承 / pending 待拍板 / notes 注释 / foreign 别的项目），**别按记忆里的条数对拍**——实况常比记忆多（本次记忆 11 条、实测 19 条有效 + 1 DISABLED，多出 4 条大表拉取腿 + 反匿名/存档腿 + 运维守护）。keep 类命令行从线上**逐字**提取，`timeout 900`/日志重定向等环境一并继承，漏一项就是行为变更。逐字取回用 `ssh <host> 'crontab -l | base64 -w0'` + 本地 `base64 -d`，避开多行输出的换行/截断差。
- **自动回滚不是默认正确值，按波及面定**：无人值守机队＝起不来自动回滚；**用户可见的主控（动 bot 推送、写库、重启常驻）＝失败停在原地 + 打印人工回滚命令**（用户明确要求“不是 active 自动回滚”）。同一套工装两种语义都合法，差别在谁会吃到回滚的副作用。
- **“完全替换了吗”按层据实核**：每台/每角色**单独**查 `current` 软链指向 + 新树文件是否落地 + 老文件名是否仍被调用；**禁止用已置换的那半边推断另一半**（实况：采集端 12/12 已换、主控侧一个字没换）。
- **换常驻进程：一条角色常对应 2–3 个进程**——`bash -lc … setsid nohup …` 的**启动壳**（后台子进程继承了它的 stdout ⇒ shell 长期挂着不退）、`flock -n <锁> <命令>` 的**锁包装**、真进程。按角色 token 匹配后**全部停掉**，别把启动壳误判成“还有第二个实例”；新常驻启动命令**显式带锁**（新代码的锁名与老锁不同，漏锁＝老新各一份，bot 双实例抢 TG polling 的直接后果是两边都不回话）。
- **硬结构闸拦到自己人就抽模块，不改基线**：文件/函数超限 ⇒ 先抽 `case_x(chk, ...)`（`chk` 当参数，计数仍统一汇总），再抽伴生模块 `tools/<名>_cases.py`，主入口只留一行调用。**且 import 常是 `try/except` 两个分支**（导入失败回退另一路径）：**两个分支都要改**，只改一个 ⇒ 另一分支照旧导入旧名字、报 `NameError`，且只在跑到那条分支时才炸（实况：只改了 except 那半，夹具当场 NameError）。**加闸时不许让被棘轮冻结的入口函数变长**：N 行 `chk(*check_x())` 直接写成 `for c in (check_a, check_b, check_x): chk(*c())`，净增 0 行自然过闸（闸拦的是增长，不是新功能）。
- **闸必须断言“形状”，不能只断言“键存在”**：只查键在、值非空就收工的闸会放过真崩的形状错（例：把线上冷却表按数字播种，用它的代码却按 `{"day","n"}` 取值 ⇒ 取用点 `AttributeError`，闸还全绿）。规矩两条：①断言值的容器/类型/子键（`isinstance(v, dict) and {"day","n"} <= set(v)`）；②**至少一条端到端**——用真类实例跑真入口（真判冷却函数挡人、真取票函数跑一遍），不只调纯函数。
- **批量作业回读用“聚合计数”，不看单条**：N 台跑完看四行——完成分隔符计数 / 内容指纹 `grep -o '<指纹标记> [0-9a-f]*' | sort | uniq -c`（一眼看出哪台没换干净）/ 判定行 `grep -c 可以上` / 失败行 grep。**工具调用被中断、超时、无输出 ≠ 作业失败**：先 `pgrep -af` + 读日志核现场再决定是否重跑——批量上传类作业盲重跑会重复推送（实测工具超时，但读数显示作业早已跑完全队全绿）。
- **lint 结论必须带口径**：`python -m pyflakes <各层>` + `python -m ruff check --isolated --select E9,F <各层>`（`--isolated` 才忽略环境配置、可复现）；环境宽规则报的数百条风格项要明说“不在验收口径内”。
- **★换树后不许说「下一轮起生效」，先验「进程是不是换壳后启动的」**：bash 把脚本读进内存 ⇒ 换盘上文件对已在跑的进程无效（实况：守护 08:31:26 起、壳 11:10:46 才换）⇒ 两级判据 = 盘上壳新版（查**调用点** `$(read_sleep)`，别查函数定义）+ `/proc` 启动时刻晚于壳 mtime；取不到证据一律保守，话术只许「等它下次启动」。
- **`pgrep -f` 自匹配要连工具代码一起治**：部署工具的「停老常驻」段 `pgrep -f <老脚本名>` 会匹配**它自己那条 `bash -lc` 外壳**（症状：每个角色各一个假 PID、彼此差 12；"事后 ps 零残留"即自证）⇒ 修法三件 = 模式首字符包字符类 `[m]erge_…`、命令行里给模式加引号、`still_alive` 的 grep 用 `re.escape()`；取证要「同机同时刻 `OLD_PIDS=<有> → NEW_PIDS=<空>`」+ `--activate` 摘要逐角色 `pids=无`。
- **「全线机制完整吗 / 数据有没有缺失·遗漏·不同步」按腿对账，别拿「守护在跑」当结论**：六层只读巡检 + 逐腿给数字，结论形态是「N 条在跑 / M 条跑着不出活 / K 条断」。三条最容易漏的判据：①**陈旧状态文件指标 ≠ 停采**（12 台 `LAST轮询` 停 20h 前，真机正在跑第 201 轮 ⇒ 用真机轮次 + `/data_raw` 近 1h 落盘数反证）；②**对账不能证明上游 feed 活着**（归档自证最新一条停 9 天，而对账照样「缺 0 落后 0」，因为权威就是归档本身）；③**发布树布局下的相对路径是固定炸点**（`conf` 里 `worker = master/bk_worker.py` + cron `cd /opt/v6` ⇒ 树化后 `/opt/v6/master` 不存在，每轮 12 台报错、`DONE 0`），派发到采集机的绝对路径还必须在**目标机**存在（`/opt/v6/tools/gap_once.py` 是主控专属 ⇒ 机器侧 `can't open file`）。脚本与判据表见 `references/leg-completeness-audit-2026-10-04.md`。
- **★路径断腿的修法与「修复会生效」取证**：修法 = 抽一个公共解析器（`tree_root()` 取**本文件所在树根**、`tree_path(rel)=normpath(join(树根,rel))`），**所有**调用点共用（worker 路径、派发命令、清单/矩阵路径）；判据落在**目标机**（主控有 `/opt/v6/tools/x.py` ≠ 采集机有，采集机是树内 `<树根>/tools/x.py`）。上岗前**不动线上就能拿最强证据**：主控 `cd <树根> && python3 - <<'PY'`（带 heredoc 的 ssh 探针**不能加 `-n`**）import 在役模块，打印「实际会发的命令串 + worker 解析后绝对路径 + `os.path.isfile()` 真假 + 清单条数」，并与**老写法复算的 `False`** 对照 —— 三条一致才算成立，**「文件已落盘/已切链」不算证据**。
- **★同族断腿点先证伪再计数**：树化迁移期常见 `相对路径 → 回退 树根/相对路径` 的**双路径写法**，那种点一直正常；判据 = 在**跑这条腿的日志**里 grep 失败串（如「矩阵读不到」）**0 次 ⇔ 不是 bug**。误报的点只作「收敛统一写法」，在报告里标注**无行为变化**，不占修复项、不写进故障清单（拍胸脯说“又一个潜伏暴雷”会被日志当场推翻）。配方与上岗检查单见 `references/release-swap-and-guard-hardening-2026-10-04.md` 第 6–7 节，补丁骨架 `templates/byte_patch_tree.py`。
- **「缺键/条目形状变化」先做新老同口径抽样再定性**：老基线若只抽「有企业」的条目，会把「老版 100% 缺 `用户`/`ST`」误读成老版更全；实际新版只缺 20%/58% ⇒ 是改善不是回归。判缺口前先查**数据在别的层有没有**（本次 154 条包件缺口 298/298 都能在归档里找到 ⇒ 是入池遗漏、不是采集缺失）。
- **★全部改码定稿后才打包分发**：先 `--stage` 到机队、之后又改本地代码 ⇒ 各机 stage 的是**错版本包**，只能重打包 + 重割接（实况白跑一轮 12 台 stage）。顺序固定：本地全绿（含结构棘轮 + 离线夹具）→ 打包 → stage → activate；**stage 与 activate 之间不许再动树**，动了就重打包，别指望“再补一次 activate”能盖上。
- **离线夹具按段改 ini 的键 ⇒ 新配置键必须同时进 ini 模板**：夹具用 `patch_ini` 把 `[段] 键` 改到临时目录，**模板里没有该键会直接报「段里没有键」并整轮失败**——代码里写了默认值**不算**模板里有；增配置键时三处一起改（代码默认值 / ini 模板 / 夹具里该路径指向 tmp，绝不能落生产绝对路径）。
- **新事件推送类改动的验收位置**：夹具只能证逻辑（首轮不播 / 补一条恰好一推 / 再跑 0），“用户真能收到”要靠**通道层**证：读推送/订阅函数的**首行守卫**（`if not 名单: return 0` 一类早退会让挂在里面的事件永不触发）、查状态/名单文件的 mtime 与条目数（停留很久 + 只有 1 条 = 函数从未被调用）。通道落点判据、诊断顺序、降噪三律与实现骨架见 `95306-data-collection-ops` 的 `references/notify-channel-placement.md`。
- **发布包上台验收链**：`--stage` **必须显式带 `--tar/--sha`**（不带恒报「包不存在」）→ `--plan`（verdict 可割接 / `problems []` / `running_old []`）→ `--activate --yes` → `--verify`（逐文件 sha256）→ **本地 md5 == 远端在役 md5**；**crontab 验收 = activate 前后 `diff` 为 0 行**；常驻不该被顺手重启（`booted []` + `skipped_already_running` + 守护 PID 前后一致，三条同时成立）；**⚠️ 但「跳过重启」= 常驻仍在跑旧代码**：本次要生效的改动若落在常驻里（bot/daemon），割接后必须**显式停起**（停/起分两次通道，停完先核残留 0 + lock 释放），否则软链换了而功能用的还是内存里那份旧模块（实况：新推送代码已落盘上线，bot 进程仍在旧代码上跑，看着“已发布”但新功能永不触发）。取证 = 进程 STARTED 晚于新树切换时刻；取不到就只说「等它下次启动」换树后**等一轮自然收轮**再下结论（拉取→并库→判活三断点 + 日志零 `Traceback`）。deploy 工具在**在役树 `current/`** 里（`/opt/v6/deploy/` 可能是空的）。**`--verify` 取清单要按显式 rel 名，不能 `sorted(glob(...))` 取「最新」**（`z` 排在 `aa` 之后 ⇒ 验 `aa` 时抓到 `z` 的清单，看着像「对不上」）。割接后「修复生效」的取证落在**叶子侧三条**：下一轮调度真用新树跑（派发串里是树根路径、目标机该文件存在）+ 下一次定时任务不再出现旧报错串 + 目标机 `/tmp/*.log` 无 `can't open file` 且 stats/JSON 在刷新；主控侧日志只能当旁证。
- **「JSON 非 dict 就 `.get` 崩」同族要一次清完**（老 `merger.py:1024` 真死于 `AttributeError: 'str' object…`）：`or {}` **只防 None 不防 str/list** ⇒ 逐处 `isinstance` 守卫 + 统一助手 `_d(v)=v if isinstance(v,dict) else {}`，**链式 `(X.get(K) or {}).get(K2)` 要包外层**；整文件被写坏的候选（下游会静默当没有）**带反例自动排除、不硬包**；收口判据 = `grep -c " or {})\.get("` 残余 **0** + 回归锁加「坏数据不许带走整轮」段（宁可报缺，不可静默吞）。
- **本机回归锁两坑**：`subprocess` 里 `"bash"` 会解析成 **WSL `bash.exe`**（吃不了 `C:/…`、stderr UTF-16 告警 ⇒ 断言全红而生产逻辑其实对）⇒ 探测真 bash，探不到**显式 `SKIP`**；`ast` 的 `col_offset` 是 **UTF-8 字节偏移** ⇒ 补丁器全程按 bytes 切串写盘，且**先 compile 通过再写**（中文源码按字符切必错）。
- **补丁工装四条硬闸（每条都烧过一轮）**：①**语法闸走内存 `compile(src, path, "exec")`，不要 `py_compile` 落 `.pyc`** —— 目标名取到 `os.devnull` 时在 Windows 上它是**真实文件名 `nul`** ⇒ PermissionError 假红，代码其实全绿；②**换行风格别让 shell 数 `\r`**（`grep -c $'\r'` 经 shell/传输会把 CR 吞掉，表现为「每行都命中」⇒ 误判 CRLF 混行）—— 让补丁器**从自己读到的 bytes 判定并原样保留**；③**ini/conf 的锚点别按「单空格」猜**（这类文件常是**对齐空格** `worker        = master/xx.py`）：先整行读出原文再 patch，或把锚点落在**键名子串**上；④**断言里比路径字符串必须两侧规范化**（`os.path.join(root,"a/b")` 出正斜杠、树根助手出平台分隔符 ⇒ 直接 `==` 假红）：用 `os.path.normcase(os.path.normpath(...))` 或直接断言 `os.path.isfile`。骨架 `templates/byte_patch_tree.py`（唯一性先验 + 全或无 + 内存编译 + 换行自检 + 回读），**一个文件里任一锚未中 ⇒ 整文件跳过**，不允许「半个文件的补丁」落盘。
