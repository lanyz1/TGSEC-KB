# 多机舰队运维三纪律(2026-09 实踩沉淀)

适用:任何"N 台采集机/跳板机 + 主服编排"的监控系统。三条都是当天实际踩出来的。

## 1. 机器清单以清单文件为唯一权威,禁止硬编码

- 机器 IP/名称/端口集中存一处(`/opt/v6/jumpers.json`),**所有部署/推送/巡检脚本循环读它**。
- 凭记忆硬编码 IP 必错:2026-09 一次部署脚本手写 12 台 IP,错了 3 台(武汉/乌兰察布/河源),
  靠 `cat /opt/v6/jumpers.json` 才纠回。机器扩编(8→12)、SSH 变更等只改清单文件一处,
  消费端(merger/orch/gen_gap)全部自动跟随——**写脚本前先读清单文件,不要相信自己对 IP 的记忆**。
- 验证部署批次时用"文件 md5 全台一致 + systemd active"双条件,别只看命令回显(中继输出会丢)。

## 2. 批量 SSH 加固顺序(禁密码前严格按序)

```
① 所有机器授权运维 key(新机 authorized_keys append 公钥)
② 逐台验证 key 登录成功(不能跳)
③ 才改 PasswordAuthentication no 并重启 sshd
④ 改完立刻:密码登录必须被拒 + key 登录必须通(双向验证)
⑤ 排查所有"用密码连接"的存量脚本改 key 优先 —— 漏一个 = 那台静默失联
   (本次:merger pull_one 密码连接前 4 台,不改就集体断 rsync)
```

- **服务名坑:阿里云镜像是 `ssh` 不是 `sshd`**(`systemctl restart sshd` 报 Unit not found,
  此时配置已改但服务没重载 = 未生效,看起来"改了没用")。
- key 布局:主服持私钥,Windows 本地留副本供 paramiko `key_filename=`;前 N 台安全组只放行主服时,
  本机直连必 `WinError 10060` → 走主服中转 scp/ssh,别在本地重试。

## 3. 冗余 vs 分片:按数据性质决策,不搞一刀切

多机同构部署后,逐项过一遍"这个任务该全冗余还是分片":

| 数据性质 | 决策 | 理由 |
|---|---|---|
| 实时流(审计/日志窗),单次错过就丢 | **全冗余**(N 台都拉) | ①单台停机不丢行 ②限流冷却对冲:N 台错峰重试总有台在窗口外成功(实证:某票 11 台被冷却、第 12 台成功) |
| 幂等小量(报名/确认类) | **全冗余** | 量小,换 100% 到达率 |
| 确定性数据(同 ST 拉同接口,返回值相同) | **分片**(如 hash%k 或 N%4==0 的 k 台轮值) | 全冗余 = 无效冗余 + 同凭证高频触发平台限流 + 白白占用各机主循环时间(实测每台每轮白卡 6 分钟) |
| 大吞吐逐条处理(票/企业/反查) | **hash 分片 %N** | 消除重复劳动;配合全冗余兜底通道覆盖失败 |

- 改频率(如 orch 10min→5min)时与同机其他 cron 错峰(如 `2-59/5` 避开 `0/10/20` 与 `8/18/28`)。
- 深翻页类升级只让 1/k 的台升档(如 `SHARD_ID%3==0`),防 N 台同时打爆上游接口。
