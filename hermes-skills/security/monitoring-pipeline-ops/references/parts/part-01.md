## 主服 IP 被平台拉黑 → 采集机中继(2026-09-13 实踩)

- **症状**:2026-09-12 23:30 UTC 起主服对 findList 全 funcId 返回 **403**(采集机 IP 同调用 200);翻牌哨兵静默瞎跑约 1.5h(XA79 若翻牌将漏收割);watch_xa79(TQ 抓票)同源同挂。
- **判定法**:同一请求①主服直发 403 ②经 `ssh root@<采集机IP> python3 -` 发 200 → **WAF 按来源 IP 封禁,非端点变更**(采集机 12 台出口各异,全通)。审计收割等不同端点不受影响,别扩大化。
- **解法**:relay_post 中继按分钟轮转采集机、失败顺延(已落 xa79_flip_watch.py / watch_xa79.py;模板与换血记录见 references/collector-relay-code-and-rollout-2026-09-13.md、references/master-ip-ban-collector-relay-2026-09-13.md)。
- **盲期"清空覆盖"事故(2026-09-13,12h)**:sync_plat_enroll.py 在 403 时把空结果照常覆盖保存 → plat_enroll_map.json 被清零,bot 全站"平台N家"权威数字消失。**铁律:凡"拉取→覆盖保存"型脚本必须加 got/条目阈值守卫,失败保留上轮快照**(已修 sync_plat_enroll + fetch_8515_inc,均加中继+守卫);排障链 = 报"数据都没了"→ls -la 数据文件(updated/条目数)→找生产者脚本日志(403?)。
- **★中继只覆盖了部分脚本 ⇒ 漏掉的静默死 16 天(2026-09-29 修)**:2026-09-13 那次只把 findList/business 域(`xa79_flip_watch`/`watch_xa79`)改成采集机中继,**`/opt/v6/audit_harvest.py`(审计域抓票 → 产令牌池 `/opt/v6/bid2_tokens.json`)没改** ⇒ 主控直连恒 403:日志 `rows=0` 刷 2364 次,池文件 16 天停在 **23 字节 / `jwt=0 st32=0`**,消费者 `watch_xa79.py` 每天空转(`run: st32=0 filled=0`)。**教训:同一次封禁事件里,凡"主控直连目标"的脚本必须逐个列出改道——只改发起那次排障的两个,其余会静默死;判据 = 脚本自己的 `rows=0` 计数 + 产物文件恒空(cron 一直在正常跑,看进程/看 cron 都查不出来)。**
  修法(已落):①采集机(上海 sh0,CN IP)本地 cron `1,11,21,31,41,51 * * * * cd /opt/v6 && flock -n /tmp/ah_cn.lock python3 -X utf8 audit_harvest_cn.py >> /tmp/ah_cn_cron.log 2>&1`(池写 `/opt/v6/bid2_tokens_cn.json`,实测 `rows=600`);②主控 `4,14,24,34,44,54 * * * * cd /opt/v6 && flock -n /tmp/ah_relay.lock bash audit_harvest_relay.sh`(scp 拉 CN 池 → `tok_merge.py` 并入主控池,按 JWT exp / ST 12h 剪枝;scp 失败自动 ssh 兜底);③**必须注释停掉旧的主控直连 cron**——它每轮拿空结果覆盖池,不停就会把修好的池每 10 分钟清空一次(`crontab -l > /root/ct.bak_$(date +%F_%H%M%S)` 备份,旧行留成注释+原因)。**验收必须看"自动 tick"而不是"手动跑通"**:实证 17:51:09 采集机本地自动跑(pool 380/252)→ 17:54:01 主控自动拉取合并(`[tok_merge] jwt=380 st32=252`)→ 主控池 23 B→248,995 B,消费者日志 `st32=0`→`st32=249`。**别把令牌池与"账号↔企业"映射混为一谈**:映射(`_ent_full_*.json`,6831 个)由采集机榨干队列产出 + 主控 `merge_ent_full()` 每轮合并,本条死时它照常在产(最新就在当天)。
- **★403 判别法(一眼分清"CDN 封 IP"还是"应用拦规则")**:同一时刻双出口对比 + 看响应头——**`x-via: 1.1 PS-XXX (Cdn Cache Server V2.0)` 且无 `Server: wswaf` = 铁总 CDN 边缘就拒了** ⇒ IP/地理级封禁(整站、连首页 `https://cg.95306.cn/` 和 `www.95306.cn/` 一起 403,响应体是 1965 B 自定义 403 页) ⇒ **跟端点/账号/UA 无关,只换出口才能通**;**若带 `Server: wswaf` = 已到应用层** ⇒ 才是端点/会话/规则问题。实测 2026-09-29:主控三个 URL 全 403(CDN 拦)vs 上海采集机同刻 200(`wswaf`)——用户"主控外网 IP 被 403"的判断完全成立,且**自 09-12 23:30 起才发生**(之前主控能拉)⇒ 不是"境外一律封"的先天设定,而是那晚起 CDN 加了境外拦截/拉黑了该 IP 段(两者证据不可分,实践等价:主控此 IP 永远不再直连目标)。
- **★全轨扫描结论(2026-09-29)**:主控 15 条 cron 轨逐条验完——**被 403 打死的只有 `audit_harvest.py` 一条**(已修+自动 tick 自证),其余全健在:4 条已走中继(`sync_plat_enroll` / `fetch_8515_inc` / `watch_xa79` / `xa79_flip_watch`)、本地池操作 6 条(`link8515` / `arch8515` / `roster_check` / `fixfields` / `fleet_gc` / `gen_gap_projects`)、`hf_pull.py` 四任务(`b580`/`roster`/`proj`/`pack`,`*/30`,自带 `RELAYS=[采集机IP]` 轮换,四轨每月都有落盘)。**教训:"在跑+不报错+rows=0"必须区分"真死"与"窗口本身为空"**——`hf_pull` 的 `rows=0` 来自一直排到 2027-06 的未来月份,看 `ck_<task>.json` 尾部与当月 `.jsonl.gz` 的 mtime+体积才能定性,只看日志 tail 会误判成死轨。**另扫出隐患**:`hf_pull.py` 的 `RELAYS` 里挂了 `121.43.97.73`(已下线老机,SSH 不通、也不在 `jumpers.json`)⇒ 靠轮换重试兜住不断,但每 4 次请求白等一轮超时,换现役机即可(1 行)。

- **★bot「添加采集机」必须走 systemd + 密钥认证(2026-09-29 修)**:旧流程 `pkill collect_daemon` + `./collect_daemon.sh` 在现役机队上是**双重错的**:①机队已改 systemd `v6collector.service` + `Environment=V6_SHARD`,旧流程会起成**无分片第二实例**(与 shard0 撞车);②机队 SSH 是 **publickey-only**,只用 `password=...` 连不上(`BadAuthenticationType`)。正确四步:①paramiko 连接**密钥优先**(`key_filename="/root/.ssh/id_ed25519"`,失败才回退口令)②`mkdir -p /opt/v6`(新机无目录则上传失败)③**本机生成 unit 再 SFTP 直推** `/etc/systemd/system/v6collector.service`(避开 shell 引号/heredoc 地狱)——分片号 = 现役 0-11 ⇒ **新机从 12 起**,同名重加沿用原号(分片号必须回写 `jumpers.json`,否则下次重加会漂移)④`daemon-reload` + `enable --now` + 回执自检 `SVC=active / SHARDCFG=V6_SHARD=n / MD5=… / NPROC=1`。**验证配方别拿真采集器试**(会双实例上传重复数据)——改用 `ExecStart=/bin/sleep 30` 的假 unit 自测:起得来 + `disable --now` + `rm` + `daemon-reload` 清得干净 = 配方可用(零副作用)。
- **★补采轨常态化参数(已上 cron)**:`*/30 * * * * cd /opt/v6 && BK_SHARDS=8 BK_ROUNDS=2 BK_WAIT=300 flock -n /tmp/bk_multi.lock timeout 900 python3 -X utf8 /opt/v6/bk_fill_multi.py >> /tmp/bk_multi_cron.log 2>&1`——验收看两条:`HIT <企业> acct=<账号>`(命中)与 `WRITEBACK {"files":..,"new_acct":..,"packs_add":..}`(真落库)。**cron 安装前先 `crontab -l > /root/ct.bak_bk_$(date +%F_%H%M%S)`**。
- **重启坑(2026-09-13 bot 换血实踩)**:`setsid nohup ... &` 后台启动后,paramiko/ssh exec 通道因后台进程持有 fd 会**假超时**(脚本抛 TimeoutError)——命令其实已成功,**严禁盲目重试**(会多实例);一律用 `pgrep -f '[p]ix_bot_server'` 核实。kill 用括号技巧防自匹配,kill/start 分两次 exec。

- 判定采集机 idle/挂掉前先确认 **unit 的日志去向**:`systemctl cat v6collector | grep StandardOutput`。
  - 无 StandardOutput 行 → 应用日志进 journald,`journalctl -u v6collector` 可见。
  - `StandardOutput=append:/opt/v6/v6_run.log` → journald 只有 systemd 的 Started/Stopped 三行,**应用日志全在文件里**。
- 2026-09-10 实踩:新加入的 4 台(sh8-11)用 file 输出,监控脚本只 grep journald → 4 台恒"无事件",差点误判为分片配置错。实际 `v6_run.log` mtime 一直在涨、处理行/入队行齐全。
- **判活三板斧**:`stat -c %y /opt/v6/v6_run.log`(mtime)、`tail -400 /opt/v6/v6_run.log`、`pgrep -af collector.py`。任一活跃即健康;`journalctl` 空不能作为判据。
