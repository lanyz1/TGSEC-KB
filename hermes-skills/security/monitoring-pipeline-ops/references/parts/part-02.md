## 机队实体台账、断供与到期诊断

- **SSH 失败先分类,别判"机器死了"**:`BadAuthenticationType` = 服务端禁用口令认证(与口令对错无关)⇒ 该机已切 publickey-only,换主服私钥 `pkey=` 重试;`AuthenticationException` = 口令错;100% 丢包 + :22 无响应 / `socket.timeout` = 真失联。三类混判会把"认证方式变了"整批报成机队掉线。
- **判"哪台真断供"用回传目录 mtime 横比**:rsync 落点(如 `/data_raw/<台>/`)内最新文件 mtime = 主服最后一次收到该台数据的时刻;某台明显落后其余台 = 该台已断供,该时刻即断供起点(据此算漏采窗口)。**与心跳规则不冲突**:心跳 mtime 恒新鲜只证推送器活着(判活无效),横比才判死。
- **云主机"到期停机/被释放"形态**:单台 ping 全丢 + :22 超时 + 每轮重试全失败,而其余台正常 ⇒ 先按到期停机定性,去控制台续费+启动(停机保留期内数据还在),别先改代码。要让用户在控制台搜得到就给**云实例 ID**:阿里云 hostname 形如 `iZ<instance-id>Z`,去掉首 `iZ`/末 `Z` 即实例 ID;规格/地域/类型从实例元数据取 `curl -s http://100.100.100.200/latest/meta-data/{instance-id,instance-type,region-id,zone-id}`。
  - **★主控(中心机)停机 ≠ 采集机掉线,症状面完全不同**。用户看到的是**托管在主控上的服务**不回话(bot 没反应/面板不更新/推送停),不是"某台机掉线" ⇒ 禁止一头扎进改 bot 源码、怀疑 offset 丢消息或去翻 12 台采集机。判别 = **三视角 + 双 IP,全部要打**:①本机直连 `timeout 12 bash -c 'cat </dev/null >/dev/tcp/<ip>/<port>'`(**超时即无输出——工具掐断,"看不到打印"本身就是不可达的证据**)②经本机代理出口再打一次 `curl -s --socks5-hostname 127.0.0.1:10808 -m 10 -o /dev/null -w '%{http_code}' http://<ip>:<port>/`(paramiko/裸 TCP **不走系统代理**,只能这样拿"境外出口"视角;同命令打 `http://api.telegram.org/` 应回 302 作阳性对照)③从一台国内采集机 `ping` + `curl` 主控。**三处全不通 + 主控主/备两个 IP 同时死 + ICMP 100% 丢 ⇒ 主机级离线**(停机/欠费/硬件/被释放),不是封禁、更不是脚本层——**进程级操作不可能让双 IP 与 ICMP 同时死**,这条推理直接排除"是不是我把它改坏了"。定性后按上条走控制台续费/启动;完整判别矩阵、影响面核算与开机后恢复清单见 `references/master-outage-triage-and-recovery.md`。
- **续费台账纪律**:机内无 AKSK/RAM 角色 ⇒ 读不到 `ExpiredTime`,用 `uptime -s` 开机时刻当账单周年 + 交付实例 ID 供控制台检索;厂商/机房靠外网 IP 归属(AS + org)+ 系统里残留的面板标记(如 `/etc/resolv.conf` 的安装串)反查经销商。**清单文件绝不写口令/私钥**;取证一律经主服跳转,凭据不出主服机。
★★**merger 每轮 ≈11分47秒 才是正常值;"开始合并流程 → 合并完成" 之间的静默不是卡死(2026-10-01 实踩,我误 kill 过一轮)**。实锚三轮连续配对:`[16:26:30]开始 → [16:38:17]合并完成`、`[16:40:46]→[16:52:30]`、`[16:54:59]→[17:06:43]`,每轮都是 **11m47s**,期间**不打日志、不写池**(池文件 mtime 停在上上轮),日志里还夹着 `某台: tar 打包失败` / `某台: 失败 timed out` 这类非致命行 —— 只看"日志 10 分钟没动 + 池子没刷新"必然误判成死循环(我据此 kill 了进程,**那一轮其实是健康的,白跑**)。
  - **判死活三件一起看,缺一不可**:①`ps -o etimes=` 比对本轮开始时刻(>15 分钟才可疑)②**CPU 时间是否累积**(`awk '{print $14, $15}' /proc/PID/stat` 取 utime+stime,隔 15-20s 再取,**增量 ≈ 18 jiffies/s = 满核在算**)③**fd 读位置是否前进**(`grep pos /proc/PID/fdinfo/<fd>` 采样两次,或看 fd 目标文件名是否换到下一个 —— 实锚 `roster_2023-02.jsonl.gz → roster_2023-03.jsonl.gz`)。②涨 + ③走 = 在干活,别动它;②涨 + ③冻住 = 真死循环,才谈 kill(且须先经用户同意)。
  - 该阶段是**全量 roster 重合并**(逐个过 `/data_raw/95306_full/roster_*.jsonl.gz`,实测 90 个文件),属周期性重活,不是每轮都走。
- ★★**采集机 SSH 基线 = 仅密钥 root(2026-10-01 全机队实测 12/12)**:`PermitRootLogin` = `prohibit-password`/`without-password`(8 台)或 `yes`(4 台),`PasswordAuthentication no` + `PubkeyAuthentication yes` + `kbdinteractiveauthentication no`,uid0 只有 root,`authorized_keys` 1–2 把,无 AllowUsers/DenyUsers,无 `sshd_config.d/` 生效项 ⇒ **root 用密钥一直能登,主控 12/12 都进得去**。供应商/云盾“禁止 root 登录”提示 = 指**密码**登录被关(他们 Workbench 没配密钥才进不去),**不是我们的冲突**;真正危险的动作是 `PermitRootLogin no` ⇒ merger/mrun/审计收割整条通道当场全断 ⇒ 供应商要“加固”时允许范围只到 `PasswordAuthentication no` + `PermitRootLogin without-password`,要禁 root 必须先铺非 root 运维账号(同公钥+sudo)并同步改主控侧用户名。**2026-10-02 02:00 广州 sshd_config 被改过一次(AliYunDun/aegis agent 在跑,内容仍是 prohibit-password+PasswordAuthentication no,未伤到我们)**。判“谁改的”:`stat -c %y /etc/ssh/sshd_config` + `ps -eo comm= | grep -iE 'aegis|aliyun|yundun'`;查最近改动文件用 `find /etc/ssh -mmin -600`(**`-newermt -6hours` 在本环境静默返回空,别用**)。
- ★**采集数据对账**(2026-10-02 定型)：落盘形态 = 采集机 `/tmp/targets/<uuid>/<文件>` vs 主控 `/data_raw/<机名>/<uuid>_<文件>`（**扁平**）；
  **一律按内容 hash 集合比**——按路径比全错、`comm` 因两侧 sort locale 不同会误判、主控是历史累积 superset、`bid_status.json` 是活文件（版本差≠缺口，判据=主控 mtime 晚于抽样时刻）；实操见 `references/collection-data-reconciliation.md`
- ★★**拓扑铁律(用户 2026-10-01 亲自纠正)**:本机(Windows 工作台)**从不直连采集机** —— 链路是 **本机 → 主控 → 采集机**,采集机的云安全组/白名单**只对主控 IP 开放** ⇒ 本机 `ping`/`/dev/tcp 22` 测采集机**天生无效**(实踩:本机测在跑的成都也是"断",同一时刻主控侧是通的)⇒ **所有采集机可达性判据一律在主控侧跑**(mrun/ssh、merger 日志、回传目录 mtime)。主控换 IP 后采集机批量失联的真因就是**白名单里还是旧 IP**;要放行的是主控**唯一真实出口 IP**(另一张网卡上的副 IP 不出站,填了也没用)⇒ 给用户的操作指令必须写成"安全组入方向 TCP 22 放行 <真实出口IP>/32"(或直接 0.0.0.0/0,和其余机器保持一致)。**另:用户口述"已修好/另一台也好了"指的是他在云控制台做的动作,但那一下可能点在同族另一台**(成都 `47.108.152.60` vs 成都2 `47.108.173.230`;广州 `8.138.236.124` vs 深圳 `47.107.124.62`;实例 ID 只差一位)⇒ 口述一律**以主控侧实测复核**,矛盾时以实测为准并回告"哪一台真的变了"(实踩:用户说两台都好,主控实测成都通/广州闭)。
- ★**Windows 下脚本内调 mrun.py 必须走 shell(2026-10-01 踩)**:Python 里 `subprocess.run(["python","mrun.py",...], capture_output=True)` 报 `ModuleNotFoundError: No module named 'paramiko'` —— `shell=False` 的 PATH 解析找到的是**另一个 python**(无 paramiko),而 shell(PATH 里的 git-bash)那个是好的 ⇒ 写后台值守类脚本时用 `subprocess.run(cmd, shell=True)` 且把远端命令用双引号拼进去(远端命令里的单引号如 `pgrep -af '[m]erger.py'` 可原样保留);同时把 `stderr` 也并入返回,否则报错被吞成"空输出"。诊断法:先跑一个最小脚本打印 `RC/len(stdout)/stderr` —— 一眼定性。
- ★**采集机云侧封禁(安全组/实例状态)与"断链期数据零损失"判据(2026-10-01)**:两台机(`8.138.236.124` / `47.108.152.60`)**ICMP 通但 22/80/443 从任何来源全闭** ⇒ 主机层排查(hosts.allow/iptables/sshd)对在跑机器逐条看全是**全放** ⇒ 机队**不靠主机白名单工作**,问题一律在云侧**安全组入方向/实例状态**;修法 = 用户在控制台操作(续费/启动/安全组)+重启,恢复后 systemd 自动拉起、无需手工干预。**恢复自证五件**:TCP 22 通 / `hostname`+`uptime -s` 是同一台 / `systemctl is-active`+state mtime 在写 / merger 该台那行不再 `失败 timed out` 且 `/data_raw/<台>/` 最新文件刷新 / 本轮 `完成:` 行照常出现。**断链期是否丢数据**:看该机**自己的**日志 —— 它一直在 `轮询完成`(本地采集正常,只是回传断了)⇒ 缺口是"回传"不是"采集",merger 全量补拉即补齐(实测恢复后一轮只回传 5 文件 3KB,因为那段时间平台本身无新包件)⇒ **判"丢没丢"要区分 采集 vs 回传 两段**。
★**merger 自带的 `rsync_fail` 连续计数是死代码**:它要求两次失败间隔 ≤5min 才累加,而 merger 轮次 ≈11.6min ⇒ count 永远停在 1,它那句"连续≥3 轮告警"永远不触发。**排查机队掉线别依赖它**,用 `/opt/v6/fleet_gc.py`(cron */10):按"失败时间戳是否刷新"自维护 streak ⇒ 冗余机 3 轮自动摘除+TG 主动推送,主机 3 轮只告警,6h 去重;支持 `--dry`/`--selftest`。
- **换机重配 / 冗余采集(2026-09-28 实做)**:下线一台 = 从 `jumpers.json` 摘掉它的条目 + 该机 `systemctl stop/disable v6collector`(保留 state 与 /data_raw, 可一行恢复) + 顺手把 `orch8b.py` 静态兜底 `BOXES` 表一起换掉(否则 jumpers 读失败会去唤醒已下线机)。验收=等一轮 merger 只看得到 12 台 + `gen_gap 12/12`。:换机后**只改 `/opt/v6/jumpers.json`**(唯一舰队源,含 `name/ip/port/pwd/shard`,先备份)——merger/orch8b/gen_gap/bot 全读它。**到期前的老机可当同分片冗余挂回**(merger 按观测时间去重,不脏数据,纯增量),到期删两行即下线。**非 22 端口机(宁波 25175)要求所有主控 SSH 消费方从 jumpers 取 port**,任何写死 22 的代码都要拔。**按“列表位置”当语义的机队代码(如 orch8b 原用 `enumerate(BOXES)` 当 shard)必须改成显式 `shard` 字段**,否则多机/乱序会静默喂错分片。`ent_coverage.json`(6MB)每 6h 才推 ⇒ 新机接入必须手动补推。详见 `references/fleet-reconfig-2026-09-28-inventory-and-sop.md`。
- **`BadAuthenticationType` 的另一半根因**:服务端 `PubkeyAuthentication no` 时,口令能通、密钥恒失败(宁波实踩)⇒ 先 `sshd -T | grep pubkeyauthentication` 复核再判机器死活;修 `yes` + reload + 重写 authorized_keys。同时:paramiko/mrun 通道读超时约 3 分钟,远端长任务(含 sleep 等待)必被扯断 ⇒ `setsid nohup … > /tmp/x.log &` + 短命令读日志。**★远端脚本里拉常驻也别用 `capture_output` 的 `run()`**:`subprocess.run(["bash","-lc","setsid nohup X & sleep 8; echo OK"], capture_output=True, timeout=60)` 会因**后台子进程继承着 stdout 管道**而一直等到超时(报 TimeoutExpired/EXC),但 X **确实起来了** —— 别据此判失败:事后 `ps -eo pid,etimes,args` 核实,`etimes` ≈ 已过秒数即证明是本次拉起的;要干净就 `Popen(..., start_new_session=True, stdout=DEVNULL, stderr=DEVNULL)`。
- **探针脚本要核脚本身份再信输出**:在长期复用的脚本目录里写同名文件可能被写守卫拒绝(旧文件保留),紧接着的执行会跑**旧脚本**并正常 exit 0 —— 输出看着合理却属上一轮的目标名单/逻辑。每个任务新建子目录;跑前核对 md5/首行,写完 `read_file` 验尾。

### ★主控离线后的恢复清单(开机后按序跑,幂等)

- **cron 轨自己会回来**:主控 cron 全是 `* * * * *` 形态、**不依赖 `@reboot`** ⇒ 开机即按表恢复,无需人工。**只有常驻进程要手动拉起**:merger(`setsid nohup bash /opt/v6/merge_daemon_fast.sh`,自身 120s 循环)、`security_watch.py`、`priv_loop.py`(带 `flock -n /tmp/priv_loop.lock` 保单例)、`pix_bot_server.py`(带 `-X utf8`,日志 `/opt/v6/pixbot.log`)。**精确命令行从现役 `ps -eo pid,ppid,etimes,args` 快照里逐条抄,改前重核一遍现役进程表**;`while true … sleep N` 形态的残留循环(如 `/tmp/stage_verify.py`)不计入标准常驻集。
- **补拉一律用幂等守卫**(缺谁补谁,重复执行安全):`pgrep -f X >/dev/null || (cd /opt/v6 && setsid nohup … >> log 2>&1 < /dev/null & echo UP)`。**别无条件起第二条**——bot 双实例会抢 TG polling,现象是两边都不回话。
- **恢复后自证四件**:①进程表 `ps -eo pid,etimes,args | grep -E '[m]erger.py|[p]ix_bot_server|[p]riv_loop|[s]ecurity_watch'` ②池/令牌文件 mtime + 体积(`/data_pool/index.json`、`/opt/v6/bid2_tokens.json`)③merger 首轮日志 `tail /tmp/v6_merge.log`(应见逐台同步)④bot 日志尾 `tail /opt/v6/pixbot.log`。
- **回答"数据会不会丢"前先算缓冲**:采集机 systemd 自启 ⇒ 离线期间照常采集、产出落本地盘(单机 `/tmp/targets` 2.6–26 MB、系统盘 49 G,数周不溢出),主控回来 merger 全量补拉 ⇒ **不丢**。**兜底路径**:机队 SSH 是 publickey-only ⇒ 本机持主控私钥(本地有副本)即可直连全部采集机,**主控真要换机/重建也能把数据捞回,不依赖主控**。

### ★主控换 IP(2026-10-01 实做,换 IP 类操作的标准动作)

- **顺序**:全量替换引用 → 重建通道 → 重判 403,不能反。①本地连接脚本(`mrun.py`/`mpull2.py`)改成**双 IP 列表逐个试**(主机商给两个就都写进去;写死单个 ⇒ 下次换 IP 再全断一次)。②主控自身硬编码旧 IP:实测只有 `pix_bot_server.py` 的"服务器信息"面板 + 两个 v936 变体(`/opt/v6` 下 grep py/sh/json)。③**先判归属再改**:`/root/测绘引擎/tools` 里 grep 到 `128.241.245.` 的 7 处**是别的机器**(`.172/.227/.247` 属工具的保护前缀/部署目标)⇒ 同段 IP ≠ 同一台机,"无脑全量替换"会改坏生产工具。④换 IP 伴随重启 ⇒ **常驻进程全丢**(见上节清单),cron 会自动回来。⑤**旧 IP 的封禁不跟着走**:实测新 IP `cg.95306.cn/=200`(旧 IP 自 09-12 被 CDN 403)⇒ 换 IP 是解封机会,但**别顺手把中继改回直连**(境外 IP 随时再被拉黑,中继已验证可用就留着)。
- **`pgrep -f X` 会匹配到自己**:mrun/ssh 传过去的命令行里含 `X` ⇒ `pgrep -f X` 恒命中(命中的是这条 `bash -lc` 自己)⇒ 幂等守卫永远走"已存在"分支、进程根本没起,还不报错。**守卫一律 `ps -eo args | grep '[X]'`**(方括号法)。
- **远端命令里双引号内的 `$(...)` 会被本地展开**:`ssh root@H "echo svc=$(systemctl is-active x)"` 在**本地**执行 ⇒ 所有机器返回同一个(本机的)值,一行输出看着完全合理 ⇒ 静默错判(本次把 11 台正常采集机报成 inactive)。判据:输出**来得太快**或**每台都一样**。改用 `\$(...)` 或整段单引号。
- **推上去的 `.sh` 先删 CR**:Windows 写文件常带 CRLF ⇒ `OLD1=1.2.3.4\r` 让 `grep -e "$OLD1"` 零命中(脚本照跑完、`bash -n` 也过)⇒ 常量静默失效。上传后 `tr -d '\r' < f > f2 && bash f2`。
- **非 ASCII 路径 + Python `os.walk` 静默漏**:中文目录(`/root/测绘引擎/…`)walk 拿到的路径乱码 ⇒ `open()` 抛异常被 `except: continue` 吞 ⇒ "扫描 0 命中"与"grep 有命中"并存。**批量替换用 shell(`grep -rl` + `while read`)别用 Python walk**;`< <(grep …)` 进程替换在非交互 ssh 里也可能喂不进循环 ⇒ 先落 `/tmp/hits.txt` 再 `done < /tmp/hits.txt`。
- **换 IP 后先验"这台还是原来那台"**:`hostname` + 数据目录/关键文件 md5 与台账对表 —— 同 IP 换了机(重装/重建)会和"IP 变了"表现一样,但数据面结论相反。本次 `hostname=jnjjn` + `/data_pool` 2.2G 完好 ⇒ 确认是同一台机换 IP,数据不用重建。
