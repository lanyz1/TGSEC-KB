# 授权后台表格数据：抓全 → 交付 Excel

## 触发
「把 X 全量给我拉到本地 D 盘」「把落到本地的数据整理成 excel，然后给我打开文件所在文件夹」「对应的注册手机号/微信号怎么没一起落盘」「把 26 年所有的 X 全部导出来」。
目标形态：有登录态的后台管理系统（PHP/layui 服务端渲染、低代码后台、SaaS 运营后台），数据由 列表页 + 导出接口 + 详情页 三层构成。

## 铁律（每次都适用）
1. **全程只读 GET**：不改数据、不投 shell、不留写操作。
2. **出口纪律**：所有目标请求从跳板机/代理发出，**本机不直连目标**；本机只做 SFTP 取回 + CSV→Excel 转换。用户会当面确认这一点 ⇒ 要能举证（本机到目标 IP 的活动连接数应为 0，脚本与产物都在跳板机）。
3. **先摸清数据在哪，再决定导什么**：列表分页 → 导出接口（常有硬上限，如单次 1 万条，需按日期/条件分片）→ 详情页（PII 主源）。别一上来就假定列表页有全部字段。
4. **要「某年」的数据先做 year sweep**（见坑 3），再决定去哪导、能不能导；结论要如实说「给的是现有全量」而不是「某年新增」。
5. **交付前必过对齐验收闸**：逐表比对「每行单元格数 == 表头列数」+ 抽查首行值是否落在语义正确的列。只核行数会漏掉列错位。
   **数字一律用独立解析器在最终交付的那份文件上复算** —— `wc -l` 会因引号折行虚高, 产出脚本自己的计数会带进它内联的筛选条件(见坑 20)。
6. **抓取脚本与中间产物留在跳板机**，可断点续跑（逐行 append + flush）；本机只保存最终 CSV/xlsx。
   **一机几十 MB 的原始 JSONL 不要把多机全拉到本机再联表**：在跳板机上就地 join/过滤，只回传紧凑 TSV，本机再做去重与出表（本机拉取量降一个数量级，断点续跑也留在远端）。

## 步骤
1. **盘点通道**：先从列表页内联 JS 挖导出端点（`$("#xxx_excel").click(... "<path>?" + $("#export_xxx").serialize())`），抓一遍表单看真实参数名与默认值；确认导出格式（常见 CSV/GBK）、单次上限、是否带 PII 列。
2. **列表全量**：`?page=N` 循环，页数上界取页面里的「共 N 页」。每页 20 行属常态 —— `page_size` 类参数通常无效，别指望放大单页。
3. **PII 富化**：列表页 ID 首列 → 详情页并行抓（`ThreadPoolExecutor(max_workers=12)` + `urllib`，带 `Host`/`Cookie` 头，逐条 append 到 CSV）。千级页面 ≈ 秒级完成，别串行也别手动。
4. **解析 + 验收**：用无注释干扰的表格解析器（见坑 1 与 `references/robust-html-table-parser.md`），落 CSV 后跑对齐验收闸。
5. **打包 Excel**：见「交付形态」。
6. **收尾**：创建/更新总索引与 README 的数据时间实况，`explorer.exe` 打开文件夹，汇报带行数表 + 数据口径与缺口。

## 坑（每条都带机制，别重复踩）
1. **`<td[^>]*>(.*?)</td>` 会被 HTML 注释里的 `<td>` 骗到** —— 源站常把「操作」列整段注释掉（`<!-- <td><input ...></td>-->`），naive 正则把它当真实单元格 ⇒ **整行列错位一格**（症状：主键列空、相邻字段串位），且行数看起来完全正常。修法：先 `re.sub(r"<!--.*?-->", "", h, flags=re.S)` 删注释，再逐 `<tr>` 用**深度匹配扫描器**收单元格（同名开标签 +1、闭标签 −1，归零才收尾）。表头行同样会中招。
2. **分页顺序不稳** ⇒ 不要用「无新增行即停」：会出现页 100 空、页 1000 有数据，早期就停手只拿到零头。改成把「共 N 页」**全抓一遍再按主键去重**。
3. **date-string 假阳性**：页面上出现的年份串常不是数据 —— 导出表单的默认区间（「近 30 天」按当天生成）、统计页表头标签（「昨日」）、管理员最后登录时间都会命中。年份结论必须落在**表格行内的日期列**上。
4. **整列为空 ≠ 解析 bug**：列表页的名称/店铺列源端就是空的（要名称走详情页）；某些表的联系方式列（如主播表 `contact_mobile`）源端 0/总数。先比对源 HTML 再下结论，别急着重写解析器。
5. **导出接口未必有 PII**：手机号常只在详情页；微信号可能全站都没有（只有二维码/备份库有）⇒ 被问「微信怎么没有」时给真实来源与覆盖率，不要含糊承诺。
   被问到某个联系方式字段时，把**该字段的全部可能来源列成表**（免票接口 / 受角色门控接口 / 自由文本字段 / CDN 图片路径），逐源给覆盖率与阻塞点
   （如「图片 CDN 路径是顺序数字，可枚举」是一条独立旁路）。阻塞点必须写清是**「源端就没有」**还是**「有但拿不到、卡在哪一扇门」** —— 后者是下一轮的作业面，不许混写成前者。
6. **Excel 名规则**：`xlsxwriter` 的 sheet 名不能含 `[]:*?/\`（如「推广员(手机号/微信号/二维码)」直接抛 `InvalidWorksheetName`）⇒ 统一 `re.sub(r"[\[\]:*?/\\]", "-", name)[:31]`。
7. **`{"strings_to_urls": False}`**：否则 URL 单元格被转成超链接，写几万行就刷满警告且明显变慢。
8. **两套 API 别混**：`xlsxwriter` 用 `write_row`；`openpyxl` 改已存在文件用 **`ws.cell(row=, column=, value=)`**（`Worksheet` 没有 `.write()`）。
9. **大表单独成文件**：单表 >5 万行拆出去（否则 Excel 打开卡死）；小表按分类合并，每 sheet 首行冻结 + `autofilter`。
10. **分页参数放错位置 = 整库变复制品（最贵的坑）** —— POST 分页接口常把 `pageNum/pageSize` 只从 **query string** 读，放 JSON body 里被**静默忽略**：2889 页每页都返回同一批 20 条。脚本会老老实实报「700/2889 pages」、文件涨到几万行，**看不出任何异常**。
    - 判定：抓完必算 **唯一主键数 / 重复率**（`0.00%` 才算过；本次是 `22 唯一 / 15380 行 = 99.86% 重复`）。
    - 定位：同一 body 换 `?pageNum=2` / `?current=2` / `?offset=20` 各打一页，比首末主键是否变化；body 版恒不动、query 版变 ⇒ 分页在 query。
    - 加固：循环里**跨页去重**（`seen` 集合，断点续传也从文件重建），别只 append。
11. **交付前先跑「结构自检」再跑解析**：`json.loads(每行)` 后打印顶层键 + 主键样例 + 日期分布，确认「一行 = 一条记录」而不是「一行 = 一页响应（`data` 是 list）」。本次前者（每行一条通告），若按后者写解析器则得到 0 条。

12. **导出文件本身可能就是坏的 —— 先定责, 再抢救, 别默认是自己下载错了** —— 服务端生成的 xlsx 会出现 ZIP 结构损坏(局部文件头是乱字节、中央目录偏移错位、成员 CRC 对不上), 症状 `Bad magic number` / `Bad CRC-32` / `invalid distance too far back`。**四步排除法定责**(少一步就会误判成自己的 bug 并反复重下):
    a. `Content-Length` 与实际收到字节数是否一致 → 一致 = 不是截断;
    b. 抽样重下, 新旧文件**字节数/哈希是否相同** → 相同 = 不是下载竞态;
    c. 加随机 query、`Cache-Control: no-cache` 各取一份 → 三份同 hash = 不是 CDN 缓存了上传中间态;
    d. **对同一条记录连续重新导出 6 次** → 6/6 全坏且大小恒定 = 服务端**确定性**损坏(per-record), 重试无用。
    得到 (d) 结论 ⇒ **不要再重试导出, 直接换通道**: 同一条记录的 JSON 列表端点没有文件生成环节, 天然不坏。
    残余可抢救: 绕 CRC 直读解析器, 实测能救回约 1/6(见 `references/corrupt-xlsx-recovery.md`)。
    **先抽样算损坏率**(20~30 条)再决定策略, 别用「几个坏了」推断「全坏」或「全好」。
13. **下载完整性校验必须用 zipfile 全量校验, 不能用首字节** —— `body[:2] == b'PK'` 会把**截断/坏体**文件判为完好(PK 头在、数据不全) ⇒ 坏文件进目录后被「已存在且够大就跳过」的条件**永久跳过, 再也修不回来**。用 `zipfile.ZipFile(fp).testzip() is None` 才算通过; 跳过条件写「**校验通过才跳过**」。并发下载再配 `Accept-Encoding: identity` + `Content-Length` 比对 + 最多 5 次退避重试。
14. **合并多来源表格: 列并集爆炸 + 内存爆炸** —— 各记录带自定义字段(表单列)时, 25 份表的并集能从 22 列炸到 358 列, 绝大多数列只有个位数填充。**按填充率切两份**: 核心列版(填充率 ≥5%)+ 全列版留档; 交付主用核心列版。别把 358 列的表直接交给用户。
    规模上到百万行级时**合并必须流式写出**(逐行 `csv.writerow` + 每 N 行 `flush()`), 不要先把全量行读进内存再聚合;
    同时**每份文件的行数单独落一份 `<记录id>→rows` 的 TSV** —— 它是坑 18 的强制前置(没有它就查不出空表)。
    裁列前**必须先做表头并集**(见坑 19), 不能凭第一份样本写死列名。
    - **百万行级去重不能用字符串集合**: `set("记录id|主键")` 到 600 万 key 就吃 ~600MB, 小内存作业机(3.5GB)直接 OOM。
      用**两遍式**: PASS1 只把 `blake2b(键, digest_size=8)` 的整数 append 进 `array('Q')`(600 万 ≈ 48MB), `sorted()` 后扫相邻判重;
      PASS2 流式重读直接写盘, 全程不持有原始行。两遍必须用**同一段切片逻辑**抽键, 否则判的不是同一批(空格/转义差异会让判重失效)。
15. **多线程批处理 worker 的锁必须可重入** —— `threading.Lock` 非重入, 若 `log()` 在 `with lock:` 块内被调用 ⇒ **自我死锁**。唯一症状: 进度停在某个整数不动 + 失败表 0 条 + 手动单发同类请求 200 且耗时正常。**极易误判成服务端限流**。用 `threading.RLock`。

16. **列表端点的「默认视图」不是全量 —— 隐式过滤会静默吞掉大半数据** —— 同一列表接口常写死一个默认筛选
    (「只返回待处理」),`total` 显示 96 而实际全量 1293, 前端自己传了筛选参数才拿到全量。
    挖参数的手法(响应数值字段当 oracle)见 `references/hidden-list-filters-and-pagination-oracle.md`。
    **抓完必须拿接口自己报的 `total` 与落盘行数对账**(不是与「我以为的总数」对账): 不等 ⇒ 还有没解锁的筛选维度或分页没翻完。
17. **吞吐按「行/秒」标定, 不按「延迟」** —— 同一端点不同 `page_size` 单请求延迟差 5 倍(`1`→0.24s, `200`→2.44s),
    但目标函数是**行/秒**: 实测甜点在 `page_size=50`(~90 行/s), 反而 `100`/`200` 更低(85/82)。
    并发也有服务端天花板: 8→16 线程只涨 14% 且延迟翻倍 ⇒ **加线程不再涨 = 服务端饱和, 到此为止, 别继续堆线程**
    (堆下去只会把对方风控触发概率抬高)。标定法: 固定一个小任务集, 逐个 `page_size` 各跑一轮算 行数/耗时;
    再试 2~3 档线程数找拐点。参数一旦定下来就**别在跑的中间改**。

18. **能正常打开的导出文件可能是「表头-only 空表」—— 所有文件完整性校验都查不出来, 只有跨通道行数对账能查** ★
    服务端按记录生成文件时, 部分记录会**静默产出 0 行数据**: 文件 ZIP 完好、`testzip()` 通过、Excel 正常打开、
    表头列名齐全、体积看着也正常(几 KB) ⇒ **`PK` 首字节 / CRC / 中央目录 / 能打开** 这一整套校验全部放行,
    坑 12/13 那套「定责四步」也全部通过。这是比坏文件更危险的一类:**它不报错, 只是没有数据**。
    - **同一条记录不可信一次结论**: 实测同批里有的记录 814 条报名导出 0 行、有的 241 条只出 45 条、有的 586 条出 581 条、
      有的完全相同 ⇒ 不是「全好/全坏」, 是**逐记录随机**。抽几个样本判「这通道没问题」必错。
    - **先证伪「下载太早/异步没写完」这个天然嫌疑, 再下结论**: 空表/少行最像写入竞态, 但两者判据完全不同、处置也相反。
      **对同一条记录重新导出 → 取新 URL 重下 → 比字节**: 字节完全相同 = 服务端按记录**确定性**产出空表, 重导出/重试/换
      cache-buster 一律无效 ⇒ 直接弃用这条通道、别再花时间抢救;字节不同才是竞态, 才值得重下。
      (与坑 12(d) 同一手法 —— 坑 12 判坏文件, 这里判空文件。)
    - **合并汇总里单独打一行覆盖率**: `有效行 / 空表数 / 不可读数` —— 它是这条通道的真实下限。
      实测:24,660 份文件里空表 26.3%、不可读 15.6%, 有效行 2.43M vs 另一通道 6.39M(**只有 38%**);
      总量看着几十万行很体面, 缺的是**整条记录整段**, 只报总数会把缺口藏起来。
    - **唯一可靠的判定 = 每记录行数对账**: 用**同数据的另一条通道**(JSON 列表端点)拿 `total`, 与导出文件实际行数逐条比,
      落一份「记录id / 通道A行数 / 文件行数 / 差值」的**完整性对照表**。行数对不上就以另一通道为准。
    - **交付时附这张对照表**, 让缺数可追溯 —— 只报总数会把缺口藏起来(总量看起来正常, 缺的是某些记录整段)。
    - 战略上同坑 12: **主通道选不生成文件的 JSON 列表端点**; 导出文件降为「尽力而为的富集层」,
      只说它独有、JSON 没有的列, 且**绝不把它当交付主体**。

19. **多平台/多模板的列名变体会静默丢掉整列** —— 后台服务多个平台时, 同位置列的表头名不同(如 `小红书id` / `抖音id`,
    链接列同理), 合并时若核心列名写死 ⇒ **该平台的整列被静默丢弃**, 0 报错, 只有人工比对表头才能发现。
    - **定列名要先扫表头并集**: 把所有文件的**第一行**读一遍做表头并集, 再定核心列; 不要凭一份样本写死。
    - 核心列写成**变体超集**(各平台的 id 列、链接列都列上), 或用并集动态生成列;
      合并时把「表头里出现、核心列没覆盖」的列名单独打一行告警, 别静默吞。
    - **与坑 14 是一对**: 14 是「列太多要按填充率裁」, 19 是「列名不同不能裁错」。正确顺序 = **先表头并集, 再按填充率裁**。

20. **交付文件里的数字必须用独立解析器重算, 不能读产出脚本自己打的计数** ★
    产出脚本的计数会带进它自己的**内联筛选/清洗条件**, 与「交付文件里真实有多少」不是一回事,
    而用户拿到的是后者。实测合并脚本按「手机号长度 ≥7」过滤后报 70,427,
    独立全量复算交付 CSV 得 **75,183**(差 6.7%)—— 两个数字都往外报必然被追问, 只报错误那个就是失实。
    - **`wc -l` 不是 CSV 行数**: 字段内含换行的引号折行(名片说明/附言/评论几乎必然有)会让它**大幅虚高**
      —— 实测 4,099,094 vs 真实 2,430,488(**虚高 69%**)。行数一律用 `csv.reader` 逐行数。
    - 验收脚本固定四件套, 全部跑在**最终交付的那份文件**上(不是中间产物):
      ① `csv.reader` 行数 ② 「每行单元格数 == 表头列数」的异常行计数(应为 0)
      ③ 关键列的非空计数与唯一值计数 ④ 覆盖的实体数(覆盖了多少条记录/商品/通告)。
    - 汇报给**复算值**, 并与产出脚本的计数显式对账:不一致要查出差在哪(内联筛选 / strip / 编码),
      并把口径写进交付 README —— 否则下一轮会拿旧口径的数字与新数字打架。

21. **双边平台：先定口径再导，别把「另一侧」交给用户** ★
    平台把「供给侧」与「需求侧」两类账号混在同一张用户表里时，用户说的业务词（品牌方 / 商家 / 放单方 vs 达人 / 接单方）
    必须先在数据里**找到平台自己的角色码或分类码**把它映射成一个可执行条件，再决定导什么。
    实测代价：用户要「放单方（品牌/商家）」，而交付的是「接单方（达人）」全量 —— 数据一条没错，**整个交付作废**。
    - **平台自己的 `category`/`type`/角色码就是分侧器**，远比按昵称/头像/描述猜准。实测某订单表 `category` 把两侧切得极干净：
      供给侧付费码（商家会员卡 / 加急过审券 / 额外报名额度）vs 需求侧会员码。
    - **开场先出一张按分类码分组的计数表**（唯一实体数 / 单数 / 金额），据此判定用户指的是哪一侧，并把判据写进 README —— **别为口径去反复问用户**，口径错了用户会立刻说。
    - **口径写进文件名与表头**（`…_<侧别>付费名录.csv`），并检查交付目录里**不要有两侧混装的文件**。
    - 顺带白得一个**付费子集**（带金额、单数、首末时间），往往比全量名单更值钱。

22. **让脚本报「命中 N 条」之前，先按来源字段自证这个数** ★
    与坑 20 同族（数字必须独立复算），这里是它的正则版：宽松关键词正则会大量命中**结构噪音**。
    实测一次大小写不敏感的关键词匹配报出**数十万条**「微信号」命中，其中绝大多数来自 `view_users` 的 id 串与头像 CDN URL（域名里就含 `wx`），
    真信号只有几百条 —— 直接报数就是失实。
    - 计数时**同时打 `<字段名>:<命中数>` 的 Counter**，先看分布：某个 URL / token / id 字段独占绝大多数 ⇒ 模式在匹配结构噪音，**该批作废**；
    - 关键词加**边界锚点**（前后非字母数字），并把 URL / 头像 / 编码串字段**排除在扫描范围外**；
    - 扫描范围要**点名**：只有人类输入的字段（昵称 / 真名 / 简介 / 正文 / 地址）才可能含联系方式。

23. **在发请求拿 PII 之前，先把已落盘的产物榨一遍** ★
    全量语料是第二个来源：实测对数万条详情产物里的**自由文本字段**做一轮正则，零请求就拿到数十条自主披露的手机号 / 微信号，
    而当时正在为**同一个字段**去攻一个受角色门控的接口。顺序应当是 **先榨本地产物 → 再决定要不要发新请求**。
    - 结果落成「实体 → 联系方式」表（按实体 id 聚合）并**并进交付目录**，别只留在临时输出里。

24. **交付值的「完整性」必须用代码断言, 不能信终端里看到的形态** ★
    终端/工具输出会把**长或高熵值的中间一段省略**(JWT / 卡密 / 密钥 / 长 hash 最先被省), 打印成
    `eyJ0eX...vI4E` 这种「前 6 位 + 省略号 + 末 4 位」的样子 —— **看起来和数据被平台截断一模一样**。
    实测回读文件断言: `len(value)==152`、`"..." in value == False` ⇒ 值完整, 省略只发生在显示层。
    据此写成「平台截断/数据损坏」会把错误结论带进交付报告。
    - 正确动作: 对**最终交付文件**跑一条断言脚本 —— 逐条 `len()` 分布 + 「是否含省略号」计数 + 抽样全值 `repr`;
      形态可疑时**先回读文件**(`read_file` / `json.load`)再下结论, 不要拿屏幕上的一行当证据。
    - 与坑 20 同族(数字/取值都要独立复算), 区别是这一条针对**值本身**而非计数。

## 交付形态（本用户偏好，照做）
- 目录形如 `D:\渗透\<目标>_recon\excel\`：
  - `01_总索引.xlsx` = 说明 / 索引（逐表行数列数） / 分类统计 / 联系方式汇总；后续新增交付时**在它前面加一页**说明新文件。
  - `02`+ 按分类（商户客户 / 达人主播 / 协议合作 / 现网实时 / 后台导出 …）分文件；大表单独文件。
  - 手机号/联系方式单独一份「对照表」，并在分类表里**直接加一列**「★手机号（现网今日）」，别让用户自己去 join。
  - **同一条铁律适用于一切「原文型」数据的交付（卡密/激活码/凭据/密钥/单号清单）**：一串裸值用户看不懂 —— 必须联成
    「业务主键 ↔ 原文 ↔ 商品/时间/状态/金额」的多 sheet 表（① 单据清单 ② 逐条明细 ③ 去重表），另附同内容 TSV 供 grep。
    只交裸清单会被退回（用户会说「不然我看不懂」）。联表键取平台自己的单据号，别自造。
  - `README.md` 必带「★数据时间实况」一节：每个数据源的真实时间口径 + 「哪些年没有数据」+ 为什么。
- 收尾一律 `explorer.exe "<目录>"` 打开文件夹。
- 汇报：文件/行数表格 + 联系方式覆盖口径 + **如实交代缺口**（哪些字段源端没有、哪年没有数据、原始 CSV 落在哪里）。
