# 损坏导出文件: 定责 → 抢救 → 换通道

## 症状分类(先看报错落在哪一层)

| 报错 | 含义 | 可救性 |
|---|---|---|
| `Bad magic number for file header` | 局部文件头签名不是 `PK\x03\x04`(乱字节) | 低(需按中点目录定位原始 deflate 流) |
| `Bad CRC-32 for file 'xl/...'` | 数据解压正常, 只是 CRC 字段对不上 | **高(跳过 CRC 校验即可读)** |
| `invalid distance too far back` / `invalid block type` | DEFLATE 流真被截断 | 低 |
| `File is not a zip file` | 首字节就不是 PK | 无 |
| **(无报错)** | **表头-only 空表**: ZIP 完好、`testzip()` 通过、Excel 正常打开、列名齐全、体积正常、**0 行数据** | 不可救(服务端就没写数) |

## 定责四步(缺一步就会误判成自己的 bug)

```
1) Content-Length  == 实收字节数 ?          → 不等 = 截断(我方/链路)
2) 重下若干次, 新旧 字节数/哈希 相同 ?       → 不同 = 下载竞态
3) 加随机 query 与 no-cache 各取一份同 hash ? → 不同 = CDN 缓存了上传中间态
4) 同一记录连续重新导出 6 次:               → 6/6 全坏且大小恒定
                                              = 服务端确定性损坏, 重试无用 ⇒ 换通道
```

第 2 步的旁证很有用: 旧脚本(无校验、高并发)下过一批坏文件, 但重下后字节**完全相同** ⇒ 与自己无关。
注意 `X-Cache: HIT` 只说明走了 CDN, **不说明缓存是坏因** —— 必须用第 3 步的哈希比对来定。

## 抢救: 绕 CRC 直读解析器

核心两点:
1. **跳过 CRC 校验**: `zipfile.ZipFile(f)` 打开后, 对成员对象把 `_expected_crc` 置 `None` 再 `read()`,
   DEFLATE 数据完好时即可拿到完整内容(实测 1185 个坏文件里救回 196 个 / 20 万行)。
2. **不依赖 openpyxl 的严格性**: 直接解析 `xl/worksheets/sheet1.xml` + `xl/sharedStrings.xml`
   (用 `xml.etree` 遍历 `row`/`c`/`v`/`is` 节点, `t="s"` 的单元格按 sharedStrings 下标取值)。

**局部头损坏时**: 用中点目录的 `ZipInfo.header_offset` + `header_offset+30+len(filename)+len(extra)`
定位数据起点, 再 `zlib.decompressobj(-15).decompress(raw)` 手工解 deflate。
**注意**: 头一坏, 偏移就不可信 —— 实测按此法读出的「成员」长度荒谬(几百字节的 `.rels` 读出 69 万字节)
即为错位证据, 这类**不要硬修, 直接判不可救并回退到 JSON 通道**。

## 第三类: 完好但空 —— 比坏文件更危险

导出文件还有第三种失败形态, 它在上面整张表和「定责四步」里**全部看不出异常**:

```
文件有 PK 头, zipfile.testzip() 返回 None, openpyxl 打得开,
表头列名齐全且正确, 体积几 KB 看着正常, 但是 0 行数据。
```

- **为什么会查不出来**: 前面所有校验回答的都是「文件完整吗」, 而它**确实完整** —— 缺的是数据。
  服务端按记录生成时, 某些记录的取数步骤静默失败, 却仍然写出了一个合法但只有表头的文件。
- **逐记录随机, 不是全好/全坏**(实测同一批内): 有的记录 814 条报名导出 0 行、有的 241 条只出 45 条、
  有的 586 条出 581 条、有的完全相同 ⇒ **抽几个样本判「这通道没问题」必错**。
- **唯一可靠的判定 = 跨通道逐记录行数对账**:
  ```
  记录id | 通道A(JSON列表端点的 total) | 导出文件实际行数 | 差值
  ```
  数据由脚本自动出, 交付时附上。只在总量层面看会漏 —— 总量可能看着正常, 缺的是某些记录整段被吞。
- **前置条件**: 合并阶段就要**每份文件单独落一行 `记录id→行数`** 的 TSV。没有它, 事后无法对账, 只能重读全量文件。

## 战略结论(比代码更重要)

- 损坏率过高的通道**不能当作主通道**: 先抽查算率, 再决定要不要把主通道换成同数据的 JSON 列表端点。
- JSON 列表端点没有「服务端生成文件」环节 ⇒ 天然不坏, 应作为可靠兜底;
  代价是字段可能与 xlsx 不同(要逐字段比对覆盖度, 别假定 JSON 是超集)。
- 两通道并存时: JSON 拿可靠全量, xlsx 只用来补它独有的列(如真实姓名/微信号/自定义表单列)。
- **导出文件通道不能当交付主体**: 它同时会「损坏」「部分丢」「整份空」三种病, 且后两种不报错。
  把它降为**尽力而为的富集层**(只说它独有、JSON 没有的列), 主通道始终是 JSON 列表端点; 并附行数对照表。
