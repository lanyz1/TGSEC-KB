# 列表接口的隐藏筛选与真分页参数: 用响应数值字段当 oracle

## 适用症状

- 列表接口默认只能拿到很少一部分数据(「待处理 96 条」), 但业务量明明是几万条
- 前端页面里明明有筛选/翻页, 但扒下来的请求里没有明显的筛选参数
- 自己朿参数名发过去, 服务端 **200 + 一份看着正常的数据**, 看不出到底筛上了没有

## 铁律: 参数名错了不会报错, 只会被静默忽略

所以「没报错」不能当判据。**必须找一个能反映数据集大小的 oracle, 做差分。**

## 第一步: 选 oracle

不带任何筛选参数发一次, 拿响应里**一个随数据集大小变化的数值字段**:

| 优先级 | 字段 | 说明 |
|---|---|---|
| 高 | `meta.total` / `pagination.total` / `count` | 服务端自报的总数 |
| **最高** | **伴生计数** `coop_cnt`/`pending_cnt`/`done_cnt` + `filtered_cnt` | **与 total 的算术关系能直接反推筛选取了哪个子集** |
| 中 | `has_more` / `next_cursor` | 只能证明「还有」 |
| 低 | `list.length` | 受 `page_size` 干扰, 单看无意义 |

**实测价值**: 基线 `total=96` + `filtered_cnt=-1197`, 同页又给出 `coop_cnt=1197`
⇒ 96 + 1197 = 1293 = 被隐藏的全量。**伴生计数一放一收就把真相交代了**, 比只盯 total 强得多。

## 第二步: 跑候选名矩阵

每个候选名各发一次, 值先用**最简单的一个**(`1` / `true` / `0`), 只比 oracle 数值变不变。

候选词表(按命中率降序):

```
<对象>_status   (如 process_status / audit_status / signup_status / task_status)
status  ·  state  ·  statuses  ·  coop_status
tab  ·  filter  ·  type  ·  kind
is_all  ·  all  ·  include_<x>  ·  scope
```

实测: 19 个候选里**只有 `process_status` 命中**, 其余 18 个全被忽略 —— 
名字带对象前缀的那一个往往就是答案。

## 第三步: 先测「有/无」, 再测取值语义

命中的参数**先只测存在与否**。实测踩坑: `process_status` 传 `0/1/2/3/4` **任意值返回完全相同(都是全量)**
⇒ 服务端只判「该参数是否出现」, 是 **fail-open 的显式筛选**; 这种接口下值怎么传都无所谓。
一上来就用取值猜语义 = 白跑一遍矩阵。

顺序: **无 → 有** 定位参数 → **逐值枚举** 定义语义 → 再谈组合。

## 第四步: 翻页参数单独探、单独证伪

**`start_index` / `offset` / `current` 被忽略 ≠ 分页不可用** —— 真参数可能是 `page`
(服务端自己换算成 `start_index = page × size`)。

- **判据不看回显、看数据**: 逐页取回, 统计**新增主键数**; 每页都有全新主键才算真翻页。
  实测 `page=1..5` → 500 条零重复 ⇒ 真翻页。
- 只看 `start_index` 回显递增会被「回显了但没生效」骗过。
- `page_size` 上限**必须实测**(100 / 200 都见过, 超限报 422), 不要沿用别处的结论。
- 分页参数**放错位置**(该放 query 放了 body)同样会全页返回同一批数据 —— 见本 skill 坑 10 的重复率验收闸。

## 收尾对账

抓完拿**接口自己报的 `total`** 与**落盘行数**对账(不是与「我以为的总数」对账):
不等 ⇒ 还有没解锁的筛选维度、或分页没翻完。对不上就别宣布「全量已拉」。
