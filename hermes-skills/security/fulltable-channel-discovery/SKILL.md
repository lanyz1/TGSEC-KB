# 全表取数通道:发现 + 完整性对账

手上只有「带条件的查询接口 / 分页列表接口」而要拿全量时,**先花几次请求确认能不能一次问出全表**,
再决定采集方案;找不到全表通道才退回逐条件枚举。

## 1. 数组参数旁路(最常见、收益最大)

PHP 站点的过滤参数常直接来自 `$_GET/$_POST`;把**标量过滤参数改成数组**会让拼条件那一步失效
(条件变空 ⇒ 返回全表):

```
POST act=query  qq=123456   → total:104      正常条件过滤
POST act=query  qq[]=1      → total:69385    ★ 条件崩掉:全表 + 直接吐 data
变体: qq[0]=1 / qq[1]=1 / qq[]=            多数同样生效
反例: a[]=1 / page=1        → total:0        参数名不对时不生效,别把 0 当「旁路失败」
```

- **判定看 `total` 的跳变,不看单页记录**:单页条数被写死时,只有 total 从条件量跳到全表量才算证明。
- 同时试 `param[]=1`、`param[0]=1`、`param[]=` 空值,以及把该参数**整个删掉**
  (部分实现在缺参时干脆不加条件)。
- 旁路成功后立刻记下这个 total —— 它就是后面证明完整性的**服务端自报基准**。

## 2. 每页条数探测(决定请求预算)

遍历 `limit / pagesize / pageSize / size / rows / per_page / num / count / show`。
全部无效说明服务端写死(实测恒 10 条/页)⇒ 预算 = `ceil(total / 每页条数)`,
据此判断前台跑还是后台跑、要不要分片并行。

## 3. 活表 offset 翻页必然漂移

对**正在写入**的表(订单/流水)按 offset 翻页会漏:每翻一页,新行插入把窗口整体后移,
相邻页出现重叠(实测相邻页 7 条交集),同时老行被跳过。规则:

- 去重键用**业务唯一键**(订单号/支付单号),不要用 `id+时间` 这类会漂的组合键。
- 采集器**可续跑**:产物已存在就追加续写 + 另写 progress 文件每 N 页刷一次;中断后不要从头重扫。
- `total` 采集期间会变(实测 69384 → 69385)⇒ **收尾重新取一次 total 再对账**,
  「实取 ≥ 首轮 total」是活站增长的正常结果,报告要写明是增长而非抓取缺陷。
- 收尾若「唯一键去重后行数」明显少于 total ⇒ 用**分片条件**(状态位/时间窗/首字母)重扫缺口区间补打,
  不要重跑全量。

## 4. 结果字段先看清再落盘

条件崩掉的返回里常带**未脱敏字段**(明文卡密/密钥/手机号)。落盘前把字段全集打印一遍,
确认敏感列没被截断、也没只留索引列 —— 「拿到全表」和「拿到有价值的列」是两件事。

## 5. 纪律

- 全程只读:探测阶段不要触发写操作(下单/支付/提交/注册)。
- 批量循环请求仍受用户的批量动作授权约束:靶向小列表可直接跑;大字典/全量长跑先问,
  并保证可随时中断、可续跑。
- 交付必须带完整性对账,不要只说「跑完了」。
