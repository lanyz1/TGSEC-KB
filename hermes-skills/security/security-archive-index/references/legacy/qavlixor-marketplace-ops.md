## 环境坑
- Bash 每次调用 cwd 重置到 `C:\Users\Administrator`,必须链式 `cd "/d/跨境商城/qavlixor-marketplace" && ...`(**中文路径必须加引号**;MSYS 下 `/d/跨境商城/...` 可解析)。
- **search_files(rg)对中文路径失效(2026-08-05 实测)**:`search_files` 在 `/d/跨境商城/...` 上报 `rg: ... IO error for operation on ... The system cannot find the path specified`,且 `target='files'` 直接返回空——**本仓库内搜文件/搜内容一律用 terminal + `grep`/`find`(中文路径加引号),别用 search_files**;路径定位用 terminal `ls` 确认。
- **patch 工具可能把整文件行尾符 LF→CRLF(2026-08-05 实测)**:patch 编辑个别 .tsx 时会把**整个文件**重写成 CRLF(同批次其他文件却保持 LF),git diff 显示全文件每行带 `\r` 变化(实际只改 1 行却 diff 71 行)。**检测**:`git diff --stat` 改动行数异常大 + `grep -c $'\r' <file>` > 0 的判定已废弃(2026-08-06 实测修正旧记录:本仓库 HEAD 的 components/admin/*.tsx、lib/translations.ts 等大量文件本来就是 CRLF,正确标准 = `git show HEAD:<file>` 与工作区的回车计数一致,别按绝对 0 判断;patch 工具本次把 AdminMerchantManager 从 CRLF 改成 LF,方向可与旧记录相反,别只防 LF→CRLF 一种;`git diff` 报 "LF will be replaced by CRLF" 在本仓库常态出现,别当故障信号);`file <file>` 显示 `with CRLF line terminators`。**修复**:`python -c "p='<file>';d=open(p,'rb').read();open(p,'wb').write(d.replace(b'\r\n',b'\n'))"`(按字节替换,**保留 BOM**——本仓库部分文件带 UTF-8 BOM,别用文本模式读写)。**规矩:每次 patch 完跑 `git diff --stat`,改动行数必须与预期一致(小改动应只有几行);不一致先查行尾符,修完再继续,别带着整文件 diff 提交**。
- **dev 运行中禁 `pnpm build`**(会冲突),类型验证用 `npx tsc --noEmit`,须 EXIT 0。
- 本地 `schema.prisma` provider=postgresql(生产真源) 但 dev.db 是 sqlite(双轨)。
- **双轨 generate(2026-08-06 已改新方案,旧 sed 方法废弃)**:旧方法 `sed` 临时把 schema provider 改成 sqlite → generate → 还原,有**致命坑**:dev 在跑时 generate 必 EPERM(DLL 被占用);杀掉 dev 后 generate 成功,但 client 变成 postgresql provider → dev.db(sqlite)连不上(`PrismaClientInitializationError: URL must start with postgresql://`),dev 重启即全崩,且问题要等重启才暴露(会话进行到一半 dev 挂,难排查)。**正确做法(commit df7baad 落地)**:用 `scripts/make-dev-schema.mjs`(读主 schema.prisma → 替换 provider=sqlite → 写 prisma/schema.dev.prisma,模型自动与主 schema 同步)→ `pnpm db:gen:dev`(generate --schema schema.dev.prisma) / `pnpm db:push:dev`(db push --schema schema.dev.prisma)。**dev 流程固定:`pnpm db:gen:dev && pnpm dev`;生产构建才用主 schema 的 `prisma generate`。加新模型时:改主 schema.prisma → `pnpm db:push:dev`(自动重新派生 dev schema 建表)→ 重启 dev(改表后旧进程不认新模型,报错先重启)**。验证 client 是 sqlite:node 直查 `prisma.store.count()` 成功即可。完整流程见 `references/pnpm-migration-windows.md`。
- **停 dev 的坑**:Hermes `process kill` 只杀 shell 包装,`next dev` 子进程常残留占着 3000 端口(新 dev 会静默换到 3001!)。停 dev 必须:① 先 `netstat -ano | grep ":3000.*LISTEN"` 找真实监听 PID → ② `MSYS_NO_PATHCONV=1 taskkill /F /PID <pid>`(MSYS 下 `taskkill //F //PID` 会被路径转换吞掉报 "Invalid argument",必须加 `MSYS_NO_PATHCONV=1` 或用 `cmd //c "taskkill /F /PID <pid>"`)→ ③ 确认端口释放再重启。
- **dev 静默崩死(2026-08-05 实测)**:Next.js 15 dev 首次编译新路由(如首次访问 /products/[id])可能抛 `Jest worker encountered 2 child process exceptions, exceeding retry limit` → **整个 dev 进程退出**(`process poll` 显示 status=exited),所有页面开始 500。**排查顺序:页面 500 → 先 `process poll` 看 dev 进程是否还活着(别只盯浏览器) → 死了就按上条重启**。非代码 bug,重启即恢复。重启后首次编译该路由仍可能再崩一次,再重启一次即稳。
- **dev 日志分级(2026-08-05 实测)**:dev 输出里 `getProductCatalog: prisma failed, serving stale catalog cache` = **设计内降级**(prisma 短暂抖动用缓存兜底,非故障);`prisma failed with no cache, falling back to local db` = **较严重**(真数据源不可用,买家页会显示 local-db 假数据,此时查 P2023/连接问题)。旧 dev 进程被 kill 后其 watch 通知会延迟推送(可能混在活跃进程通知里),收到 `Error` 匹配先 `netstat` 确认是哪个进程、看是否已 kill,别慌。
- **tronscan 401 诊断(2026-08-05 实测)**:dev 定时刷 `chain-watcher tronscan failed Error: Tronscan 401`(lib/chain-watcher.ts)。**链路:有 `TRONGRID_API_KEY` 走 TronGrid,否则 fallback Tronscan 公开接口(无 key)——Tronscan 公开接口现在对无 key 请求返 401**。**结论:生产 `.env.production.example` 配了 TRONGRID_API_KEY → 走 TronGrid 不受影响;本地 `.env.local` 只配了收款地址没配 key → 每轮刷 401**。影响:仅本地 USDT 入账自动确认监控失效,不影响页面/下单/开发;线上正常。处理:本地可不管(治标=失败日志降级低频),要本地监控通就申请免费 TronGrid key 填 `.env.local`。**诊断套路:`grep -oE "^(TRONGRID_API_KEY|PLATFORM_USDT_TRC20_ADDRESS|USDT_TRC20_RECEIVE_ADDRESS)" .env .env.local .env.production.example` 看各环境配了哪些键,再对照代码 key→fallback 分支判断影响面,别直接动代码**。

## 管理端批量 i18n 落地模式(2026-08-06 第三轮,6 页 102 键 zh/en 双区,可复用)
**data-i18n 是整元素 textContent 替换**(LanguageSync `element.textContent = value`),不是只翻中文部分——**混合节点必须拆,否则变量被翻译值吞掉**:
- 前缀/后缀拼接:`合计 {n} USDT` → `<span data-i18n="key">合计</span> {n} USDT`;`{count} 笔` → `{count} <span data-i18n="key">笔</span>`;`SKU：{sku} · 数量 x{qty}` 拆三段,` · ` 分隔符留原文。data-currency-lock 只加属性不改文本,混合节点可直接挂。
- **三元假分支**:`{cond ? ... : "未填写"}` → `{cond ? ... : <span data-i18n="key">未填写</span>}`(字符串字面量换 JSX span,条件/逻辑不变)。
- **内联模板串**:`{isGuest ? `${buyer} · 游客` : buyer}` → `{isGuest ? <>{buyer} · <span data-i18n="key">游客</span></> : buyer}`(fragment 包内联 span)。
- **全角括号独立成键(2026-08-06 组件轮实测)**:混合节点里的 `（`/`）` 拆成独立 span 键——parenOpen zh「（」/en「(」、parenClose zh「）」/en「)」,英文态才出半角(`目标店铺（已选 {n} / 共 {m}）` → `<span>目标店铺（已选</span> {n} / <span>共</span> {m}<span>）</span>`,en 渲染 "Target stores (selected 3 / of 5)";全选按钮的 `（{n}）` 同理)。全角引号「」在 zh/en 值里都安全,不用拆。
- **相邻 span 的空格塞进 en 值(2026-08-06 实测)**:`全选{cond?"筛选结果":""}（{n}）` 拆 span 后 en 会拼成 "Select allfiltered(12)"——**zh 值必须与原文字节一致,空格只能放 en 值**:selectAll zh「全选」/en「Select all」+ selectFiltered zh「筛选结果」/en「 filtered」(前导空格)。数量单位同理:`{n}<span> 个</span>`(空格进 zh 值「 个」)+ countUnit en 值「」空串 → en 只显示数字,zh 保持「3 个」。
- **en 值里的 ASCII 双引号(2026-08-06 实测)**:`No store matches "` / `".` / `"After-sales Active"` 是**要转义的合法内容**——构建 TS 行时统一 `v.replace("\\","\\\\").replace('"','\\"')` 再拼 `"key": "value",`,**别在 python 里断言 `'"' not in v`**(值可以含引号,断言会在写盘前误报);zh 值用全角「」（）天然安全。
- **data-currency-lock 与 i18n 同加**:含 USDT 字样的金额 strong 与说明 em(如 `{order.total} USDT`、`USDT 待释放`、`USDT 实际打款金额`、`USDT / PayPal / Wise`)一律挂 `data-currency-lock` 防货币换算——currencyAdjust 先查 `[data-currency-lock]` 再查 `[data-currency-fixed]`,deposits 页虽已 `data-currency-fixed="USD"` 区内金额仍加 lock 保持精确 USDT。
- **中文 aria-label 用 `data-i18n-aria-label`**:LanguageSync translatedAttributeSelector 支持 `[data-i18n-aria-label]`;词级翻译只碰 Text 节点不碰属性,不标的话英文态 aria 永远是中文(本批 3 处:商品类目筛选/分页/保证金类型筛选)。

**一键部署（2026-08-09 起，98 秒全自动，替代手动多步）**：`python scripts/deploy.py "改动说明"`——自动完成：①本地 `npx tsc --noEmit --incremental`（tsconfig 已有 incremental → 2 秒）②git commit ③`git archive | gzip` ④paramiko SFTP 上传 ⑤服务器 `tar xzf` + `pnpm exec next build --no-lint` ⑥`pm2 restart ×2` + curl 200 探测。**提速前提**：`next.config.ts` 已加 `typescript: { ignoreBuildErrors: true }`（本地 tsc 把关后 build 跳过重复 typecheck，build ~3min → ~1.5min）。**注意**：`next build` 默认跑 typecheck+lint，跳过必须显式配置。
**部署四步清单（每轮部署照做）**：
1. **验证 tar 包内容**：`git archive --format=tar HEAD -o qav-deploy.tar` 后必 `tar tf qav-deploy.tar | grep <本次改的文件>`——**gitignore 误伤会让目标文件不进包，生产永远旧版**（本轮实坑：`.gitignore` 第 29 行 `uploads/` 匹配了 `app/api/uploads/` 目录 → 上传 API 从不进 git → 生产一直 7/30 旧文件 → 修复 3 次部署都不生效）。**修复模式：gitignore 规则加根锚 `/uploads/`（只挡根目录存储），`git add -f` 强制跟踪被误伤的路由**。

## 部署中断 → crash loop 恢复流程（2026-08-10 实录）
**现象**：部署命令被中断（deploy.py 被杀）→ 服务器 tar 解压半程代码损坏 → PM2 4 实例全部 `waiting restart`（restarts 100+，crash loop）→ Cloudflare 502。**任何"部署进行中被掐断"后用户报 502 = 先查 pm2 jlist 的 status/restarts，别猜攻击**。
**恢复（手动重部署，deploy.py 可能因"nothing to commit"卡住时用）**：
```python
# ① 打包（Windows Python 子进程无 gzip！用 gzip 模块）
raw = subprocess.run("git archive --format=tar HEAD", shell=True, capture_output=True, check=True).stdout
with open("qav-deploy.tar.gz","wb") as f:
    with gzip.GzipFile(fileobj=f, mode="wb", compresslevel=6) as gz: gz.write(raw)
# ② paramiko 上传 → ③ 服务器：tar xzf 覆盖解压 + db push + next build --no-lint（看日志确认 87/87 页面完成）
# ④ pm2 restart ×2 + curl 200 探测 + 外网 https://qavlixor.com 200 确认
```
**教训**：①部署命令跑完前（~100s）不可中断；②deploy.py git commit 步骤已加容错（nothing to commit 不再 exit 1 卡部署）；③deploy.py 的 db push 已去掉 `--skip-generate`（**schema 加新字段后服务器 Prisma Client 必须重新 generate，否则新字段的 update/findUnique 静默失败**——本会话忘记密码 token 落库 NO 就是这个原因，手动 `pnpm prisma generate` + `pm2 restart` 解决）。

## PM2 多实例进程内缓存不同步 → "改了刷新不变"(2026-08-12 实测,重大)
**症状**:卖家端改库存(行内/批量)或改价,PATCH 返回 ok 且前端提示成功,刷新/重进页面仍显示旧值。**本地单实例 dev 复现正常,生产必现/概率复现**——用户报"改了不变/还是不对"先看本节再怀疑代码。
**根因**:生产 PM2 fork **4 实例**(端口 3000-3003,nginx 轮询),`lib/product-repository.ts` 的 `catalogCache`(60s TTL)+`catalogInflight` 是**模块级进程内变量,每实例独立一份**;`invalidateProductCatalog()` 只清**当前进程**缓存。PATCH 命中实例 A(更新 DB+清 A 缓存)→ 前端 router.refresh()/后续请求轮询到 B/C/D → B/C/D 在 60s TTL 内返回旧 catalog → 显示旧库存(如 19998=9999×2 双 SKU 商品)。
**排查顺序(先证真源再疑缓存)**:① paramiko 直查生产 DB 该商品 variants.stockQuantity 是否已变(变了=写入成功,问题在缓存层);② 本地端到端 PATCH 复现(见 `references/stock-change-multi-instance-cache-2026-08-12.md`);③ `pm2 jlist` 确认 fork 多实例 + grep catalogCache 确认进程内缓存;④ 生产 `$transaction`+末尾 throw 回滚模拟 syncProductToPrisma 的 upsert,验证 DB 层写入不报错(零副作用)。
**修复(已实施 ✅ commit edb07f3,2026-08-12,用户拍板方案 A 版本号广播)**:① schema 加 `CatalogVersion` 表(固定单行 id=1,`version Int` 递增);② `invalidateProductCatalog()` 改 async:清本地缓存 + `bumpCatalogVersion()`(`upsert where id=1, version increment 1`——所有实例共享同一 DB,写后全实例感知);③ `loadPrismaCatalogCached()` 读时比对 DB 版本:变了即使 TTL 未到也重建;**版本读失败返回 null → 降级纯 TTL 判断**(防 prisma 抖动时每次请求全表重建雪崩);④ **调用点必须 `await`**(PATCH/DELETE/POST 路由 + lib 内部 syncProductToPrisma/deleteProductFromPrisma 全改)——不 await 则响应先返回、前端 refresh 到达时版本还没递增,问题依旧。**验证(本地模拟多实例)**:外部 node 进程直接 UPDATE 变体库存 + bump 版本号 → 60s TTL 窗口内立即 GET 页面必须读到新值;无变更时连续 GET 缓存仍命中(不退化)。副作用:sync 内部+路由各 bump 一次版本跳 2(无害,Int 上限 21 亿)。部署时 deploy.py 自动 db push 建表。生产 27 个 19998 库存商品为拓竹铺货正常数据(9999×2),无需改数据。完整实录/复现配方见 `references/stock-change-multi-instance-cache-2026-08-12.md`。
**⚠️ 版本号广播上线后暴露的第二个坑:写路径禁全量 catalog(2026-08-12,commit a101ee3)**——批量改库存/改价(55 项)点应用后按钮变灰 5-10 分钟"卡死":每个 PATCH 结尾 bump 版本 → 下一个 PATCH 开头 `getProductCatalog()` 发现版本变 → **全量重建 7086 商品 catalog(实测 4.4s/次)** × 55 个串行 = 卡死。修复 = 新增 `getProductRowById(id)`(prisma findUnique 单商品 + operationMetric,实测 ~40ms/次),PATCH/DELETE 路由改用它校验商品存在/归属,写路径不再碰全量 catalog;读路径(买家页/列表页)仍走缓存。**教训:写操作路由永远用单商品查询,别用全量 catalog(哪怕有 60s TTL 缓存,批量写场景每写一次重建一次 = O(n²))**。批量 PATCH 后本地实测 3 连 PATCH 从 0.96s/0.14s/0.11s,生产验证 chunk 时间戳=本次构建。
**⚠️ 第三个坑:下单扣库存/取消回补库存漏广播 → "库存乱跳"(2026-08-12,commit 88eb093)**。症状:**买家端/店铺商品库存一会正常一会缺货,刷新来回跳**。根因:库存写路径不止卖家 PATCH——**`reserveProductStock`(下单扣库存,productVariant.updateMany decrement)和 `releaseProductStock`(取消/退款回补,increment)两个高频写路径漏调 `invalidateProductCatalog()`** → DB 库存变了但 4 实例缓存不知道(版本号没递增) → 有的请求命中缓存(旧库存=有货)、有的 TTL 过期重建(新库存=扣后/缺货)、交替显示。**规则:所有改库存的写路径(卖家 PATCH/批量改/下单扣/取消回补/销量增减)结尾都必须 `await invalidateProductCatalog()`——漏任何一条 = 多实例缓存不一致**。排查顺序:先 paramiko 直查 DB variants.stockQuantity 是否已变(变了=缓存层问题)→ 全局 grep 所有 `stockQuantity: { decrement|increment }` 写点逐个核对是否带广播。验证(本地):tsx 直调 `reserveProductStock`/`releaseProductStock` → 断言 CatalogVersion 递增(14→15→16)+ 库存数值正确回补。

**现象**：部署后 h1/h2 探测 500，pm2 日志刷 `Error: You cannot use different slug names for the same dynamic path ('id' !== 'orderNo')`。根因：**新建 API 路由时用了与同路径段现有路由不同的参数名**——`app/api/orders/[orderNo]/pay-balance` 与既有 `app/api/orders/[id]/*`（aftersale/cancel/confirm/fulfillment）冲突，Next.js 全应用同一动态路径段参数名必须一致，**直接全站 500（不是该路由 500）**。
**恢复三步（缺一不可）**：① 本地改名统一参数名（`git mv` 到 `[id]`，改 `{ params }: { params: Promise<{ id: string }> }` 解构）；② **删服务器残留目录**——deploy 是 tar 解压覆盖，**不清理多余目录**，旧 `app/api/orders/[orderNo]/` 会留在服务器继续冲突（`ls /www/tiktok/app/api/orders/` 确认）；③ **`rm -rf /www/tiktok/.next` + 重新部署全量构建**——增量 build 会保留坏路由 manifest，只 restart 不重建 500 依旧。
**新建路由前置检查**：`find app/api -type d -path "*[参数名]*"` 看同路径段已有参数名，或直接复用同目录现有段名（orders 全用 `[id]`、payments 用 `[orderNo]`）。
**注意**：`find -name '*[orderNo]*'` 里 `[]` 是字符类通配（会匹配 o/r/d/e/r/N 任一字符），别用它验证残留，用 `ls` 直接看目录名。
