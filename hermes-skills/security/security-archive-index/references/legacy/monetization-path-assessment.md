# 变现可达性评估（可盈利点）

**何时用**: 用户问「现在可盈利点在哪里 / 能变现吗 / 这站值多少钱」，或渗透交付要写资金面影响。
分工: 手法本身看 `business-logic-payment` / `fund-edge-ops` / `payment-callback-forgery`; 钱包类验证看 `wallet-exchange-fund-verification`; **本卡只管「可达性判定 + 交付口径」**——不重复利用链写法。

## 铁律
1. **先算钱在哪，再谈能不能拿走**：没拿到资金坐标就先扒数据（余额列、结算表、订单量/额/时间跨度、手续费差额）。表里的钱 ≠ 能拿的钱。
2. **分级表必须区分「得钱型」与「破坏型」**：绝大多数「未授权退款/任意作废」类漏洞只把钱退回**原付款方**并扣商户余额 ⇒ 属破坏/勒索面，**不得**写成「攻击者可获利/套现」。退款只会原路返回，除非攻击者本人就是买家。
3. **未执行的动作一律标 `❌ 未执行`**；「端点在线可达」≠「已到账」。禁止为了凑结论去跑真实资金动作（授权另说，且须书面指定对象）。
4. 每条变现点必须带**机制（文件:行）+ 前提 + 我方验证状态**三件套，缺一件不进表。

## 步骤
1. **资金坐标盘点**（SQLi / 接口 / 配置任一路径均可）: 商户余额、结算表（金额/状态/`auto` 标记）、订单 `count(*)` + 金额合计 + 时间跨度、`realmoney` 与 `money` 差额（= 平台手续费）、注册费/测试开关指向哪个 uid（惯常 = 站长主账号 ⇒ 影响对象就一个）。
2. **五道闸门逐段判定，缺一段即降级为「不可变现」**:

   | 闸门 | 判什么 | 断链症状 |
   |---|---|---|
   | 入口 | 端点是否 `nosession` / 未授权可达 | 要登录 ⇒ 先去拿票 |
   | 鉴权 | 唯一凭据是什么、能否**算得出**（弱签、固定盐、可枚举） | 凭据不可得 = 死 |
   | 上限 | 单次 **与累计** 金额校验（按整行读完整 if 分支） | 只有单次校验 ⇒ 才去试累计 |
   | 动作能力 | 通道/插件是否**实现了该动作**（`method_exists($cls,'refund')`、`plugins/<ch>/<ch>_plugin.php` 有无 `refund`） | 插件没实现 ⇒ 调用即返「不支持」，链在最后一跳断 |
   | 出款 | 提现/代付开关 + 商户权限列 + 是否**管理员审核** | 出款被 admin 闸门挡 ⇒ 钱进来也拿不走 |

3. **身份类闸门要问「谁可以设置这个值」**: 设备号/终端号/商户号这类「看起来需要真实设备」的门槛，若后台表单可自填且零校验 ⇒ 等于没有闸门。本类最常见的误判就是把它当硬门槛而写「潜伏面」。
4. **输出**（直接落报告附录）: ① 资金坐标表 ② 变现点排名表（# / 变现点 / 机制 / 前提 / 所得 / 验证状态 / ★等级）③ 已判死清单 ④ 需委托方决策的动作（真实资金验证须书面指定对象）。
5. **规模诚实评估**: 把可见资金量级写出来（几万级 ≠ 大鱼），别把测试/主账号的钱说成平台大盘。

## Pitfalls
- **截断打印会凭空造漏洞**: 判定金额上限/权限分支时输出**整行原文**，禁用 `[:160]` 式截断 —— 截断片段会把 `... ) retur` 读成「空 if / 缺 return」，据此写出的「可累计超额退款」是假的。发现依据是截断片段就立刻撤回，并在报告与口头结论里显式纠错。
- **部分转储要标注**: 按**可解析行数**核对完整性，不看字节数（400KB 的产物可能只装着 330/2297 行）；产物名和报告都标「部分转储」。
- **镜像双前缀**: `.env DB_PREFIX` 指向真身表族时，旧前缀表族常原样保留并镜像同数据，只查一族会低估影响面（详见 `staged-bulk-exfil-sqli`）。
- **零写入取证边界**: 资金类端点只用错误凭据 / 缺字段 / 不存在的标识探存在性，绝不带正确凭据或真实金额；把「只报告不执行」写进交付。
- **第三方凭据不外用**: 通道商户 RSA 私钥等属第三方，只做离线能力评估，绝不发任何回调。
- **别把「不可变现」写成「无风险」**: 破坏型（退款作废、余额扣减、资金错配）对站长是实打实的损失，勒索/竞争打击价值要单独列出。
