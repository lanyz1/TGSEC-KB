# account-enumeration-oracles

打认证面时，**最优起手不是爆破，是先找 oracle**：同一端点对不同账号/字段返回不同 message 或不同耗时，每个差异都是存在性判据。拿到确认名单后再定向撞弱口令 ⇒ 命中率高一个量级，且省配额（配额才是被封 IP 环境下的真瓶颈）。

## 工作顺序

1. **摸契约**：把注册/找回/校验/发码端点（`register`、`forget`、`findUsername`、`checkUser*`、`send`、`captchaStart`）逐个空体或半体 POST，读第一句报错；每轮只加一个字段，走完「字段阶梯」直到报错从「缺参」切成「业务」。
2. **固化两态基线**：先打一次「必然存在」和一个「必然不存在」的账号，把两种文案记下来——之后所有判定都拿这两条比，别凭记忆。
3. **挖 oracle**：找免鉴权、免验证码、判据粗粒度的那个端点（见下节）。
4. **反查字段名**：从 SPA 懒加载 chunk 读，不猜（见下节）。
5. **定向打**：确认名单 × 按命中概率降序的弱口令表，走 `references/brute-harness-ops.md` 的 harness。
6. **回灌**：确认出的账号名通常就是该平台的租户/店铺标识（如 `/shop/<名>`），拿去开其他面（取数端点、跨租户判据）。

## oracle 去哪找（按性价比排序）

- ★ **密码找回**：`POST /user/forget` 只传 `{username}`、不传密码 → 存在返「密码不能少于6位」、不存在返「用户名不存在」。免鉴权免验证码，一招枚举全平台账号表。
- ★★ **空必填字段会【短路校验】, 使 oracle 消失 —— 探针必须把每个必填位填上「语法合法的假值」再读判据**。
  实测: 带谷歌/短信码位的登录端点, **空码** ⇒ 所有人同一句「XX不能为空」(纯字段必填层, 与账号无关);
  同一端点送一个**非空假码**(`code=111111`) 立刻分化成三态: **存在 → 「验证码错误, 还剩N次机会」**(★连剩余配额都回显) / 不存在 → 「账号不存在」/ 其它。
  ⇒ 铁律: **凡「空值/缺字段回统一文案」的认证面, 一律再送一轮「语法合法的假值」** —— 必填层与业务判定层是两层, 只有后者带 oracle。
  ⇒ 同一条也解释了「校验顺序」类旧结论: 当初把「TOTP 校验在账密之前, 无法枚举」写死, 实际只是**空码被必填层拦住**, 根本没有顺序问题(实测同一端点按账号分化的文案证明了这一点)。**没做过假值轮就不要对认证面下"无 oracle"的结论。**
- ★★ **「与口令无关的成功文案」不是命中 —— 任何 oracle 都要换口令复测 2–3 次再下结论**：实测同一账号换三个不同口令都回
  `Request successful`（而其它账号一律「User is not registered」）⇒ 它只说明**账号存在且该账号走发码/免密登录路径**，
  不代表口令撞对。判据：**响应随口令变化 = 真进了凭据判定；不随口令变化 = 该字段根本没参与判定**。
  把「口令无关的成功」写成「口令命中」会污染其后所有结论（并让人去等一个永远不会出现的会话票）。
- **登录三态**（若未统一文案）：`用户不存在` / `密码不正确` / `账户与平台不匹配`。统一文案时退化，改用锁定态或找回端点。
- ★★ **「凭据正确性 oracle」：验证先于授权时，`403 权限不足` 就是「密码对了」的判据** —— 管理端登录的常见顺序是「查账号 → 验密码 → 查角色」，于是三态可分：密码错 = `400 密码错误`；**密码对但无管理角色 = `403 insufficient authority` / `403 权限不足`**；有角色 = `200`。
  ⇒ **这类端点不必等 200 才算命中：`403` 即「凭据对」**，可用来确认候选手机号/口令对真存在（再据「403 而非 200」判定「该账号存在且口令对，只是没有管理身份」）。
  ⇒ 反过来：若**所有候选（含 `admin` / `administrator` 这类必然存在的名字）都回同一句** `INVALID_PASSWORD` ⇒ 才是真无 oracle —— **「无 oracle」必须先跑「已知存在 + 编造不存在」两态基线，基线不分化才许下结论**，别把「没试基线」写成「没有 oracle」。
- ★ **「请求体里有 captcha 字段」不等于「captcha 真校验」** —— 管理端登录带 `captchaId`/`captchaCode`、且另有 `/captcha` 发图端点，但**传空值或直接省略字段仍然进到凭据判定**（回 `INVALID_PASSWORD` 而不是验证码错）⇒ 该 captcha 只是前端装饰，**节流实际只剩 IP 风控**。
  **开爆前先用空 captcha 打一发确认它到底挡不挡**：挡，就要先解决读码/复用；不挡，就别把「要过验证码」当假设写进计划（实测若按「要验证码」规划会直接把可行性判死）。
- **邀请码/邀请人校验**：`checkUserInviteCode` / `checkUserInviteToken`——语义差异就是判据（「该邀请码不存在」=无效，**其它任何文案 = 命中**）。
- **零鉴权写接口的唯一性校验**：真写库但报「已存在」的接口 = 读不到的数据集也能枚举；文案统一时看**响应耗时差异**（唯一键冲突早退，0.3s vs 0.02s）。
- **耗时/回显**：报错回显请求值时让脚本按「回显是否等于预期」自动判，别人工读。

## 字段名必须从前端 chunk 反查，不要猜

- ★ **先看框架给不给「字段字典」，白拿一轮**：ASP.NET Core 的 ProblemDetails / Pydantic / DRF 会把模型字段
  **逐条列全**（`The <FieldName> field is required.`），一个空体/半体 POST 就拿到完整字段表。
  自研中文报错（「XX不能为空」）不给字段名 —— 那种才必须回前端包反查。
- **报错只告诉你「缺什么」，不告诉你「字段叫什么」**。做法：拉 SPA 主包（如 `/package/merchant/assets/index.*.js`）→ 从中提取懒加载 chunk 名（`assets/register.*.js`）→ 抓该 chunk，直接读出表单 schema 与提交字段名。
- 实测代价：确认密码真名是 `repeat_password`，而 `password_confirm` / `confirm_password` / `repassword` / `password2` / `confirmPassword` 等 10 种猜测全不中——**每个猜错的变体都是一次白烧配额**。先读包，再开打。
- 拿到 schema 再走字段阶梯，才能分清「硬门槛」和「可绕项」：如注册强制真实手机短信码（`mobile_code`），而发码端点把码发到**账号本人手机** ⇒ 无收码资源时该链封死，**及时收线换面，别硬耗**；同链的邮件发码同样要人机验证 ticket。

## 验证码链（图文码）

```
POST /common/captchaStart {} → {img_url, check_url, ip}
GET  <img_url>   (captchaImg.html?key=…)              → PNG
GET  <check_url> (captchaCheck.html?key=…)&code=<答案> → 参数名常为 code
```

- 判据：错码返「验证码不正确」而不是被忽略 ⇒ 参数名对了。若同一 key 错码后仍返「不正确」（而非「已失效」）可换读法重试，但每次重试都是一次命中风险，不是无限次。
- **读图用模型自己的视觉**：图 base64 拉回本机 → 先看全图、再用 region 裁剪放大逐字确认。加固噪声码上 ddddocr 会系统性全灭（颜色掩膜/形态学预处理也救不回），那是「系统性 100% 失败」，别当精度问题调参。
- key/票多为一次性绑定：**读错一次即废一张**，提交前必须放大复核易混字形（`>` vs `7`、`1/l/I`、`B/8`）。

## 假阴性与配额（铁律）

- **限速期的 502/空响应 = 「未验证」，不是「否定」**：CDN(EdgeOne 等) CC 规则触发后首页与 API 一起 502，此刻的打点根本没被判定；把 502 计入口令错误 = 整批假阴性、命中被埋。harness 必须把 502/空响应重新入队重试（`retry<2`）。
- **判「目标限我」还是「出口坏」**：同一出口请求 `https://www.gstatic.com/generate_204` 得 204、请求目标首页/API 得 502 ⇒ 目标侧限流；两者都失败 ⇒ 出口坏（换口）。
- **并发上限要认审计账**：4 出口 × 8 线程（≈5 发/秒）足以触发 CDN CC 并让**所有出口同时 502**；稳到单口 3 线程 + ~0.12s 间隔（≈1 发/秒/口）。
- **先估值空间 ÷ 实测可靠速率再开跑**：几百次就封 IP 时，大刀典不是「多打几次」而是「把出口烤焦」。宁可先小表确认命中率，再决定是否放量。
- ★★ **锁定/配额计数器的【记账键】决定 OTP 爆破是否结构性可行 —— 开跑前先用「换来源标记」实测它按什么记账**：
  换 `X-Forwarded-For` / 换代理出口后**剩余次数继续递减** ⇒ 按**账号**记账 ⇒ 每轮 N 次机会 + M 分钟冷却 ⇒ 6 位空间结构性不可达,
  **当场判死 OTP 爆破并转其它因子**(别用"轮换 IP"去规划百万级爆破 —— 那是白烧一晚上);反之换了来源即重置 ⇒ 按 IP 记账 ⇒ 才值得规划。
  ★ 同一端点上的**剩余次数回显本身就是 oracle**: 逐发递减即可读出"每轮几次机会"与"按谁记账"两个参数, 不必先爆破一遍才知道预算。
  ★ **反向也成立**: 既然计数按账号共享, 同一账号上任何**字段名猜错/载荷形状错**的尝试都会消耗这份预算(实测按错误字段名跑完整轮矩阵后才发现计数早锁死) ⇒ **先回 bundle 拿准字段名(见上节), 再动第一个字**;
  白名单/来源头那类绕过只解"IP 被封", **解不了按账号记账的配额**。
