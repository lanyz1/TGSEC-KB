# 加密信封 / 签名闸门：可达性判定与收线

适用：目标前端有自研加密信封（AES/RSA 信封、sign/nonce/HMAC 签名），服务端有解密/验签闸门，你无法伪造，纠结「再调调就能过」还是「此路已死」。
WAF 侧绕过手法见 `acw-js-challenge-waf-bypass`；本卡只管**闸门侧判决**。

## 0. 铁律（先读，省整轮白发）
1. **不要用自己的实现去猜闭环**（公钥/分组模式/AAD/时间窗/签名头/字段顺序，每一项都能耗掉一整轮）。改用**目标自己刚生成的产物**当 oracle。
2. **恒定响应不是 oracle**：任何通道先跑对照（缺头/空 body/乱码）；与对照**同字**即零信息量 ⇒ 立刻换通道，不要再调参。
3. **先排除「旧包」再谈失配**，且对账要落到**常量本身**(公钥串/加密开关/前缀字面量)而不只是整包 md5：
   线上可能是**另一个构建**(入口 hash 不同)而关键常量逐字相同 ⇒ "包不同"零信息量，别据此重写 crypto；
   常量逐字相同 ⇒ 密钥/算法轮换假设直接作废。
4. **闸门是「每应用」的，不是「每平台」的**：同平台姊妹主机常是不同年代代码栈，逐台探（见 references）。
5. **换通道后，旧枚举结论一律重跑**：被 WAF/闸门拦下的请求与真实 404 在输出里长得一样，旧通道上跑的路径表没有效力。
6. **★★加密封信多半「一请求一密」——这是最容易骗死自己的机制**：`RSA 包 AES key + AEAD nonce + 时间戳` 这种信封**通常一次性有效（防重放）**。
   - 同一份信封第二次使用 ⇒ 服务端回**恒定**的解密失败码（如 `400 Invalid encrypted request`）；它与「路径不对 / 缺头 / 算法错 / padding 错」**同字**。
   - ⇒ 在一个脚本里跨多个路径或对照组**复用同一信封**，会把「一次性」误读成「闸门按路径分流」，整轮推理作废。
   - ⇒ **每个测试用例重新生成全新信封**；验证「是不是重放」用单变量对照：新信封打**同一路径** ⇒ 从 400 变 401/业务响应，则根因是重放。
7. **★拒绝码先读成三态语义，再谈路径与权限**（实测）：
   - `401 需认证 / 需登录` = **解密成功、信封被接受** ⇒ 闸门已打穿，这才是作下去的槽点，**别把它当「又被拒了」**。
   - `400 Invalid encrypted request` = 解密失败：重放 > 过期 > 算法/字段错，按此顺序排除。
   - `405 + errors.aliyun.com / spm=a3c0e` = 云 WAF 层拒的非应用响应。
   - **`403` + 框架默认体（`{"timestamp","status":403,"error":"Forbidden","path":…}`）= 票已被接受、授权被拒** ⇒ 缺口从「取票/调信封」变成「提权」。★ 同一张票跳主机打同一路径做差分：`403` = 该台认得这张票（令牌库共享）；`401` = 不认（令牌库不同 / 前缀不对）。**403 不是 WAF**（挑战页恒 200，勿混读）。
   - **`500` 绑定/类型错/`Content type '…' not supported` = 已抵达控制器** ⇒ 这是「进去」的证据，不是失败；且**空 body 打 permitAll 端点常直接吐控制器全限定签名 + 入参 BO 类名**（一次拿到模块名与参数结构，比读源码快），是零成本拿契约的最快一手。
   - ★ **发 JSON 体必须显式 `Content-Type: application/json;charset=UTF-8`**：XHR/fetch 发 string 体默认 `text/plain`，Spring `@RequestBody` 立即回 500 ⇒ 这个 500 极易被误读成「信封/凭据不对」，把整轮带回 crypto 岔路（§0.1 的浪费就是这么发生的）。
   - ⇒ 出现「同一形状跨路径结果不一致」时，**第一动作是重跑单变量（全新信封 × 同路径）**，而不是去 grep 闸门源码找路径分流规则。
8. **★★ 解密失败先怀疑自己截了数据，再怀疑密钥/算法**：
   - `Invalid padding bytes` / `length of provided data is not a multiple of 16` 这类报错，在**自己中转/解密的响应体**上一大半是**日志切片**（`respText.slice(0,2400)`）把 base64 砍断 —— 拓扑上等同于密钥错。
   - 判据：同一端点放大到**全量取体（≥64KB）**后立刻能解 = 定案，纯自我伤害。
   - 纪律：**dump/解密一律全量取体，切片只用于打印**；否则会把「其实可解的端点」写成「另一套加密/解不开」，白白换面。
9. **★★ 自家代理通道「无票」的判据是看请求头，不是看 401**：
   - 用目标自己的 bundle/wrapper 当代理（`import()` 主包调它的通用 GET/POST）时，若它的票取自带 TTL 的存储包装器（`localStorage["userinfo"+id].token` 之类），**你注入的裸 token 不满足其字段/单位语义 ⇒ 取到 null ⇒ 请求根本不带 `authorization` 头**（不是带错票）。
   - ⇒ 先看**有没有认证头**：无头 = 存储层语义未满足（补 `expireTime`、猴子补 `Storage.prototype.getItem` 常都无效）；有头仍 401 = 票本身无效/过期。两者处置相反。
   - ⇒ 该通道的收益上限只是「省造信封」；**一旦卡在票上就果断回退自接信封的通道**（自造 key + RSA/签名，通常已验证可用），别在“让目标自己拿自己的票”上烧轮次。

10. **★★ 自家 crypto helper 的文档/注释是二手契约，会集体污染整轮推理**：写给自己用的 `xw8crypt.py` 之类模块，其 docstring 与自检断言一旦记错 key 形状（把「UUID 去横线后的 32 字符」记成 36 字节），后续**所有**探针都带着错形状去打，而失败码与「公钥错 / 算法错」**同字** ⇒ 整轮被带回 crypto 岔路。
    - ⇒ 信封契约**只认 bundle 原文**：`grep -ohE "(mode:[a-zA-Z._]+|padding:[a-zA-Z._]+|setPublicKey|setPrivateKey|encryptParams|encrypt-key)" <chunk>` 取真实实现，逐字抄进探针（实测 `mode: ECB` + `padding: Pkcs` + 无 IV 这类关键项就在一行里）。
    - ⇒ 自检断言必须在**每次运行**的主路径上执行（模块顶层或被调用点），只写在 `if __name__ == "__main__"` 里等于没写。
    - ⇒ 历史脚本给出的「已证实契约」结论，复用前一律按此复核。

11. **★★ 重建信封前先做「钥匙账本」**：把所有本地 key 文件与所有 bundle 里的 RSA 字面量**全部 import**，逐个列 `bit 数 + modulus 前 20 位`，按 **modulus 相等**配对公私钥。
    - **文件名不是身份**：五个不同名字的公钥文件常是同一把钥匙（modulus 相同）；同一 bundle 里的两个常量常是**互不配对**的同位钥匙（一把的公钥用于请求头，另一把私钥用于解回包头）。
    - 某私钥的公钥不在本地 ⇒ 该私钥**不能**生成请求信封，只能解回包；别拿它去调请求侧。
    - 公钥位数决定头长度（512-bit ⇒ base64 88 字符；2048-bit ⇒ 344）⇒ **先与真包长度对齐**，长度不符即钥匙选错，不用再打。

12. **★ 变体探针必须自证「到达了被测层」**：改后缀 / 编码 / 折叠的变体一旦改变了**路由命中行为**，它就不再是同一个面。
    - 判据：**同一路径**发「带信封」与「无信封对照」两发，两者**同字** ⇒ 该路径根本没进被测逻辑，在上面堆多少载荷形状都是零信息量（实测 20 种形状同字）。
    - 静态后缀（`.jsp/.html/…`）能过 WAF 但框架无该映射 ⇒ 两条约束**结构性互斥**，该变体族整体作废，别逐个后缀试。
    - ⇒ **404 响应体本身就是栈指纹**：`Whitelabel Error Page` = Spring Boot（无 `.jsp` 映射）；裸 JSON `{"state":"fail","msg":"404 Not Found"}` = 另一层（前置网关 / nginx）；闸门壳自己的根路径回自定义拒码（如 `{"msg":"参数异常","status":"1000"}`）= **纯网关壳**，路径与算法都要另找。

13. **★★ 闸门不只有密文闸：应用级「入口闸」同样只看上下文、不看头**。
    - 形态：一批业务端点整齐回同一句**客户端入口文案**（`请用<客户端>通道入口进入平台` / 要求 `initData` / 要求 WebApp 环境 / 要求 app 内打开），而同站其他端点裸 `?suid=` / 裸票就能读到数据。
    - 判据：**换遍请求头零差异**（Referer / 伪 initData / `Authorization: tma` / 各类定制头 / XFF 逐字回同一句）⇒ 该闸读的是**会话来源上下文**（initData / 客户端通道 / TMA 壳），不是头。
    - ⇒ 正解 = **走目标自己的运行环境**（真 TG WebApp 入口、现铸 initData 秒内投递、headed 真浏览器），而不是自造头；自造头在这一类闸上**永远零信息量**。
    - ⇒ 收线时写明「已换 N 种头逐字同码」作为证据，连同台账判负区一起登记 —— 否则下一轮会把同一批头再烧一遍。

14. **★ 全候选参数名 + 全值零差异 ⇒ 换层（调用者属性），不要加长候选表**。
    - 实测形态：11 个参数名候选 + 不同值打同一端点，逐字回同一句业务错误（`代理不存在` / `非代理不可操作`）。
    - 根因：该端点**先看调用者自身属性**（角色 / 身份 / 开关：如 `isagent:0`），前置不满足时无论传什么都走同一条早退分支。
    - ⇒ 与 §0.2「恒定响应不是 oracle」同源：**变体全同文案是「层错了」的信号，不是「再试一个」的信号**；换层顺序 = 载体（form/json/query）→ 调用者身份 → 会话态 → 客户端上下文。
    - ⇒ 同源兄弟：测试载体的选错也会押出全区恒定同字（JSON 发 form 端点、multipart 端点发 JSON）—— **先跑三载体对照，再进入字段级探测**。

15. **★★★ 客户端源码证明「明文透传」而服务端行为像在解密 ⇒ 这是「契约矛盾」判决，不是「我还没复刻」**：
    - 判据链：① 分片全量 grep 后字段定义**零变换**（无拦截器、无字段级加密、平行「加密版」方法都调用不到，且有 N 为数百量级的产出作硬度，见 `spa-request-contract-extraction`）；
      ② 服务端对**同一字段**分两级报错 —— 「非合法 base64 / 格式错」= 格式层、「已解密但值不符」= 比对层。
    - 两者不可能同时为真 ⇒ **服务端存的值 ≠ 客户端发出去的值** ⇒ 该账号（及同机制下的全部自建号）在口令层**结构性不可达**。
    - ⇒ 处置 = **收线换面**。把它读成「客户端加密还没复刻」去写加密器，是 §0.1 / §0.10 的变体：拿自己的猜测去补一个**客户端根本不存在的环节**，白烧整轮。
    - ⇒ 泛化：客户端**从不明文发送**某字段而服务端只收明文（或反之）⇒ 该字段的写入路径同样死锁（注册接口回「成功」但存的值不是你发的，日后永远登不上）。

16. **★★★ 过闸门之前先算「过了能拿到什么」—— 闸门通过 ≠ 有收益，否则等于给空壳磨钥匙**（前置收益闸，任一条为真即判该面 ROI≈0，先换面）：
    - **白名单在闸门后面**：登录/鉴权成功后第一个业务/权限接口回 `IP未授权访问` 类文案（或错误体回显你送的 XFF = 那个头被信任）
      ⇒ 白名单之外即便拿到**有效票**也用不了；且白名单的**值查不到** ⇒ 不枚举 IPv4 段、不为它继续磨口令。
    - **票背后没有角色**：权限模型为「超管在后台分配角色」时，**自助注册得到的账号是空壳**（登录成功也零菜单零权限）。
      先读 bundle 的角色映射表/菜单接口把模型定下来，再决定要不要投登录攻坚。
    - **收信渠道不在你手里**：计划走邮件码登录/重置前先 `dig +short MX <目标域>`：Google Workspace / M365 ⇒ 信进别人的托管邮箱，**永远读不到**；
      **无 MX 记录** ⇒ 信根本发不出。两者都判死；只有**自建邮箱**能收码 ⇒ 该路线只能建自控号，接管不了目标超管号。
    - **注册接口的 200 不是建号证据**：注册类端点常是**空壳桩** —— 对已存在邮箱与全新邮箱返回**完全相同**的响应；
      账号是否存在必须用**登录端的账号 oracle**（未注册 vs 口令不符两种文案）独立确认，别拿注册的 200 去推「该邮箱有账号」。
    - **`POST {}` 的必填表只说字段「存在」，不说字段被「消费」**：非必填字段常被服务端整段忽略（实测 `email`/`pwd` 均非必填 ⇒ 该接口压根不写口令）。
    - **500 + 空 body = 端点自身缺陷**：重置/注册一类端点恒 500 空体 ⇒ 别再调字段名/信封参数，记为「该端点不可用」换面 —— 与「参数不对」是两回事。

## 1. 三条硬证据（按序做，任一条即可结案）
1. **平台自身新鲜产物回放**：CDP 被动抓包拿客户端当场生成的密文/令牌/头，原样投进已打通的通道，并同时投一份乱码当对照。
2. **线上产物一致性**：线上 chunk md5 vs 本地分析副本（排除轮换）。
3. **缺头对照**：同路径**不带**加密/签名头发一次 ⇒ 200/业务响应 = 闸门确实被跳过，那个 400 是闸门给的，不是通用错误页。
4. **★全新信封跨路径矩阵（判定「有无路径分流」的唯一干净实验）**：同一明文形状、**每个用例全新**信封，打 3~5 个不同真实路径
   ⇒ 全部同码（如整齐 401 需认证）= **闸门无路径分流且信封契约正确**，可以正式往下打。
   若出现一个 400 ⇒ 先按 §0.6 排查重放，**不要写「该路径特例」**。

## 1.5 恒定被拒时的第一嫌疑：base/域，而不是算法

信封**逐字复刻后仍恒回同一句拒绝**(如 `400 Invalid encrypted request`)时，省下改 crypto 的轮次 ——
下一个怀疑对象是**你把它发到哪儿去了**：

- **真客户端受同源/CORS 约束 ⇒ 跨域 base 必错**：在**真实页面上下文**(同源)发一次同形请求，
  若打向从旧 bundle 抽出的 base 被浏览器报 `Failed to fetch`(无 ACAO)⇒ 那个 base **不是**活客户端用的；
  在它上面继续调信封永远是同一个 400。
- **静态桶/CDN 域不代理 API**：该域对 `<prefix>/...` 回**对象存储 XML**(`<Code>NoSuchKey</Code>` 一类)⇒
  这个域是静态部署，API 在别处。
- **读页面自己发出的 URL 定 base(权威)**：在真实页面里取 `performance.getEntriesByType('resource')` 中
  非静态资源的条目，或直接看页面自身的 XHR ⇒ 一次拿到**真实 base + 真实前缀**，不要向 bundle 索要。
- **前缀可能"被替换"而非缺失**：旧构建抽出的 base 与真实 base 常只差中间一个路径层，
  表现为**整批整齐的 401/404**而不是"报错文案变化" ⇒ 遇到整齐 401 先怀疑 base，别先怀疑权限。
- **★同一业务端点常在"明文前缀"下另挂一份**：加密前缀拒你时，拿**同一个业务端点**到同站的明文网关前缀再试一发
  (实测同一动作：加密前缀回 `Invalid encrypted request`、明文前缀回 `200`)⇒ **先走明文那套**，
  不要因为加密闸门打不动就判该业务面不可达。与第 3 条「缺头对照」互为补充：那条证明闸门存在，这条整道绕过它。

## 2. 终局判决
- 「平台自身新鲜产物」与「乱码 / 篡改 / 空 body」得到**同字恒定拒绝** ⇒ 服务端与该产物不匹配（私钥失配或闸门自身已坏）⇒
  **此路对所有人（含它自家客户端）都是死的** ⇒ 立即收线换面，别再调字段/时间窗/签名头。
- 返回**业务级**错误（token 无效 / 参数非法 / 需要登录）⇒ 闸门真解开了 ⇒ 该通道是**活 oracle**，继续往下打。
- 客户端自己报「网络连接失败」**不等于**后端坏：闸门/挑战响应若**没有 ACAO**，跨源 XHR 读不到响应，前端只会显示网络错误 ⇒ 先核 ACAO 再下结论。
- **闸门「对自家客户端也死」的第三种成因是契约矛盾**（§0.15）：服务端按密文解、客户端发明文 ⇒ 与私钥失配同属「此路对所有人都是死的」，处置相同：收线，别再调参。

## 3. 收线判据 & 换面顺序
两条同时成立即判该资金面外部不可达：① WAF/网关对一切**带 body 的真路径请求**挑战（唯一过法是静态后缀形态，而静态后缀又被闸门当静态资源处理）；② 闸门连**平台自身新鲜产物**都恒定拒绝。
换面优先级：**同平台姊妹主机/环境**（常无闸门）→ 移动端/APK → 开放平台/回调面 → TG bot/客户端面。
TG bot 侧低成本侦察（无需 MTProto 用户会话）：`curl --socks5-hostname <socks> https://t.me/<bot>` 读 `og:title`/`og:description` 拿品牌与业务定位；要拿 `menu_button`/TMA 地址才需要用户会话。
CT+DNS 只翻出三五个子域 ⇒ 资产面窄，别在 DNS 爆破上继续耗。

## 4. 抓包与探针片段
```python
# 被动抓「目标自己刚生成的密文/令牌」——不拦截、不要求请求成功
cdp("Network.enable")
req = wait_event("Network.requestWillBeSent")["params"]["request"]
save({"url": req["url"], "method": req["method"],
      "headers": req.get("headers"),     # 含全部自定义加密/指纹头
      "postData": req.get("postData")})  # 加密后的最终 body
```
- 抓包用 `Network.*` 被动事件，**不要** `Fetch.enable`（会阻塞/改写请求，污染证据）。
- **注入自定义加密头只有 `Network.setExtraHTTPHeaders` 这一条路**：它对**导航请求生效**（实测被 `Network.requestWillBeSent` 抓到 `encrypt-key` 真发出），而 `Fetch.continueRequest` 改自定义头 Chrome 不生效。
  ⇒ 挑战型 WAF 下 in-page `fetch()` 的 POST 仍被拦（挑战页恒 200）⇒ **能穿的只有 GET 导航**：密文放 `?encryptParams=`，密钥头走 `setExtraHTTPHeaders`。
- 让前端自己发起调用：伪造它依赖的宿主环境（宿主对象 + URL 参数）比手写签名省事。
- 抓到后**分钟级内**投递，避免把「时间窗过期」与「服务端失配」混为一谈。
- 探测姊妹主机有无闸门：`curl -H 'Content-Type: application/json' -d '{"a":1}' "https://<host>/<ctx>/abc;x=.js"` ⇒ 原生 404（框架 404 页，长度随路径变）= **无闸门、可直打**；`400 Invalid encrypted request` = 同款闸门。
- 老应用根路径常留 IDE 默认脚手架页（`My JSP 'index.jsp' starting page`）+ `<base href>` ⇒ 直接读出真实 context-path。
