# ID 计数器步长采样拖库(绕过分页的批量取数)

**适用**:目标 API 的详情接口形如 `GET /api/item/<id>`,且:
- `id` 是**全局递增计数器**的编码(常见 base36/base62,**定宽**、同前缀)
- 服务端**不做精确匹配**,而是返回**距请求 id 最近的那条记录**,且**永不 404/400**

⇒ 常规"没有分页参数/游标无效"的结论**只对列表接口成立**,详情接口反而是**无上限出口**。

## 判据(先证伪,别急着开拖)

1. **同一 id ±1 / ±10 / ±1000 是否返回同一条记录** → 是 = **回落半径存在**(服务端模糊匹配)
2. **加大步长**:±1e4 → ±1e5 → ±1e6,看何时**跳出一条不同的记录** → 该量级即**有效步长**
3. **有效步长的富余度 = 抗重复能力**:步长 ≥ 相邻记录平均间距时,每次请求必命中新记录
4. **对照实验**:同一组请求分别用 1e4 / 2e4 / 1e5 步长跑 10-30 点,**统计唯一记录数**
   (1e5 得 10/10 唯一、2e4 只得 5/10 ⇒ 真实间距在 2e4~1e5 之间)
5. **确认响应体里带真实 id**:若回落严重,响应 `id` 可能与请求 id 不同 —— 这是**正常现象**,按响应 id 去重

## 采样与去重(直接给能跑的形状)

```python
alpha = "0123456789abcdefghijklmnopqrstuvwxyz"
dec = lambda s: functools.reduce(lambda n, c: n*36 + alpha.index(c), s, 0)
enc = lambda n, w: ... # int → 定宽 base36

base, STEP, W = dec("<已知id>"), 100000, len("<已知id>")
seen = {}
for i in range(1, 121):
    d = api_get("/api/item/" + enc(base + i*STEP, W))
    seen.setdefault(d["id"], d)          # ★ 按响应 id 去重,不按请求 id
```

**步长选择**:从 1e5 起;若 30 点里唯一率 < 90% ⇒ 步长翻倍;若唯一率 100% 且**响应 id 间距远小于步长** ⇒ 可缩小步长提高产出密度(但会开始重复,需实测权衡)。

## 时间窗映射(判断能回溯多深)

计数器**按时间线性增长**,可反推单位:

1. 取两个已知 id 及其 `create_time` → `日均 counter 增速 ≈ (Δcounter)/(Δ天)`
2. 用「回退 N × 日均增速 → 命中日期」实测若干点,验证线性
3. 由「平台已知时间窗」(列表接口的 `create_time` 范围、公告/App 版本日期)推全库可回溯深度

实战(crabindex):日均 ≈ **1.2e7**;回退 1e7→当天、1e8→3 天前、4e8→10 天前、**1e9→27 天前**;
步长 1e5 × 120 发 → **118 条唯一、0 重复、2.14 req/s**。

## 速率与成本口径(汇报用,必须实测别估)

- 记录 `req/s`(经跳板机通常 1–3;直连可 10+)
- 每条记录携带的**关联数据量**(报名数/子对象数/头像数)= 真实泄露规模,别只报条数
- 例:118 条记录 = 22,490 条报名 + 15,071 个微信头像 ⇒ 外推「1 小时 ≈ 147 万条」才算量化

## 止步条件

- 唯一率跌到 0(全库扫完)或到达平台时间窗边界
- 出现 429/403/挑战页 ⇒ **停手换节奏**(见 `ip-ban-bypass`),别硬打
- **批量拖库属高风险动作**:先做 30–120 发的**可行性采样**并汇报规模,拿到授权再放量

## Pitfalls

- ❌ 看到"无分页/游标无效"就写"不可全量获取" —— 必须单独测**详情接口的 id 语义**
- ❌ 按**请求 id** 去重 —— 回落会让大量请求返回同一条,必须按**响应 id** 去重
- ❌ 用固定小步长(±1/±10)下结论"服务端只返回同一条" —— 那是回落半径内,不是没数据
- ❌ 本地 SOCKS 代理跑长任务(常几十发僵死)→ 用 `ip-ban-bypass` 的 `scripts/jump_http.py` 进程内直连
- ⚠️ 身份证/手机号等 PII 只作为**危害证据**记录条数与校验结果,**不要把原文抄进报告**
