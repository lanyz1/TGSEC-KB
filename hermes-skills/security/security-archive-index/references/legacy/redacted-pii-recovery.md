# 脱敏 PII 还原(掩码真号 / 隐私号逆转)

**定位**:拿到一批被脱敏/虚拟化的用户数据(电商订单、快递面单、WMS 导出、泄露库),
目标是**还原完整真号(或其他被掩码的 PII)**。

2026-09 K11(赛乐赛医药 WMS,353 万单 / 408 万行)实战定型:从 **88 万条虚拟转接号 + 140 万条掩码**
里精确还原出 **3,873 个确认真号 + 967 条虚拟号→真号映射**。

---

## 1. 先分类形态 —— 别急着动手

同名字段可能是 5 种完全不同的东西,**处置互斥**。跑 `scripts/tel_shape_classify.py shape` 一次出全表:

| 形态 | 样例 | 信息量 | 可否还原 |
|---|---|---|---|
| 完整明文 | `<PHONE-REDACTED>` | 全 | ✓ 直接可用 |
| 掩码(前 3 后 3) | `136*****720` | 6 位 | ★★ 可交叉还原 |
| 掩码(前 3 后 4) | `136****7200` | 7 位 | ★★ 更好 |
| 虚拟转接号 | `<PHONE-REDACTED>-261` / `<PHONE-REDACTED>转647` | 0 | ✗ 必须查表 |
| 全星号 / 空 | `********` | 0 | ✗ |

**★ 坑 1:某些数据集把"11 位虚拟主号"统计成"明文手机号"。**
K11 采集进度表写"明文手机号 883,928",实测 **883,416 是虚拟转接号**。
**接手任何"明文手机号"统计,先自己重算形态,不要采信上游口径。**

**★ 坑 2:字段非空 ≠ 明文。** 统计前必须用正则过滤 `*` 和 `-`/`转`,否则形态分布全错
(本次第一版脚本正则写错一位,把 140 万条掩码全归进"其他",差点误判)。

## 2. 虚拟转接号 = 隐私号,先判它是不是号池

`<11位主号>-<分机号>` 是运营商「号码保护/隐私号」的 **AXN 分机号模式**
(华为云隐私保护通话、阿里云号码保护 PLS、联通号码保护同款实现)。

**判定它是"号池"还是"真号被当主号用"** —— 跑 `scripts/tel_shape_classify.py pool`:

```python
主号集合 = {记录.split('-')[0] for 记录 in 虚拟号列表}
复用率   = len(虚拟号列表) / len(主号集合)
```

- **复用率 ≫ 1 ⇒ 是号池,不可逆**。实战:299 个主号背 883,416 条 ⇒ 平均 **2,954 分机/主号**,
  单号最高 `<PHONE-REDACTED>` 挂 **15,509 个分机**。
- 复用率 ≈ 1 且主号落在普通号段 ⇒ 才可能是"真号当主号",值得逐个复核。

**主号号段分布是运营商指纹**:全是同一运营商段(实战 167/171/186/131/130/132/170/156/166 = 全联通)
⇒ 企业向该运营商租的**一个**号池。

**★ 关键性质**:分机号是平台**随机分配的路由 key**,与真号**无任何数学关系** ——
`<PHONE-REDACTED>-261` 和 `-771` 背后是毫不相关的两个人。**只能查绑定表,不能算。**

**时效**:按阿里云 PLS 官方规则,隐私号绑定 **"订单完成后 7 天内有效"**,过期自动解绑回收。
⇒ **历史订单拨号验证是死路,不要去试**;只有极近期订单才可能还活着。

**绑定表只存在于 4 处**:运营商号码保护平台 / 快递公司系统 / 业务系统(调用方) / 驿站。

## 3. ★ 核心还原法:掩码前3后3 × 地址内嵌真号 双校验

**这是唯一真正打通的还原路径,可靠度 100%(双端校验)。**

用户下单时经常把手机号**写进收货地址栏**,而系统原样存了地址:

```
s_tel     = 173*****909
s_address = 北京北京市平谷区马坊镇早立庄村村委会<PHONE-REDACTED>蓝曦晨
                                         ↑ 内嵌真号
```

**掩码自带校验位**:前 3 位 + 后 3 位。内嵌号与掩码**两端都吻合** ⇒ 确认本人真号。

```python
for 候选 in re.findall(r'1[3-9]\d{9}', 地址):
    if 候选[1:3] == 掩码前3 and 候选[-3:] == 掩码后3:
        → 确认还原
```

**必须两端都验**。实战反例:掩码 `166*****567` vs 内嵌 `<PHONE-REDACTED>` —— 不匹配,
那是"鑫淼缘服务社"的号,不是本人。只验单端会把人搞错。

## 4. 自关联扩散:(姓名, 地址) 做 key

同一人在同一数据集里多次下单,而**不同订单的电话形态可能不同**(有的明文、有的掩码、有的虚拟号)
—— 说明该字段是**混合来源**写入的。建索引后用已确认真号回填:

```python
key = (姓名, 地址归一化去空格/中英文逗号)
idx[key] = {'明文': set(), '掩码': set(), '虚拟号': set()}
```

实战收益:虚拟号记录中 **28.11%(135,892 条)** 能关联到掩码真号;
**967 条**虚拟号直接关联到已确认真号。

## 5. 真号实际存在于哪(5 层)—— 决定要打哪里

| # | 位置 | 说明 |
|---|---|---|
| 1 | **业务系统自己的库(订单表)** | 它是调用隐私号接口的**调用方**,真号在此 ← 最值钱 |
| 2 | 运营商号码保护平台 | 企业控制台可导出绑定明细 |
| 3 | 快递公司系统 | 商家/网点账号可查收件人 |
| 4 | 驿站/快递柜入库系统 | 发取件码短信**必须**真号 |
| 5 | 电商平台订单解密接口 | 商家 token + 额度限制 |

**★ 判据:先找"调用方"。** 谁把真号传给运营商/快递,谁库里就有真号 —— 通常就是发件商家/WMS,
**不是承运商**。用快递单号绕去反查是绕远路。

---

## 6. 快递单号能做什么(诚实边界 — 别承诺做不到的事)

- 顺丰 `EXP_RECE_SEARCH_ROUTES` 入参是「单号 + **真号后四位**」⇒ **要求你已知真号**,且只回轨迹。
  ⇒ **不能用来反查真号**。这是隐私面单时代的刻意设计,不是配置问题。
- 单号真正的价值是**定位**(承运商 → 网点 → 驿站 → 快递员),从而打开第 3/4 层。
- 各家快递客服要身份核验,走不通。

---

## 7. 其他可用杠杆

- **掩码前 3 后 3 + 完整地址 ⇒ 归属地收敛**:手机号第 4-7 位是 HLR 归属地码,地址已知时
  中间 5 位候选可从 10 万压到百位级,再配空号检测收敛(需接口)。
- **明文姓名 + 完整地址 → 外部库反查**:地址+姓名近乎唯一,命中率高。
- **★ 找"脱敏失效的裂缝"**:若同一数据集里少数记录是完整明文,统计它们的**日期/批次/来源**聚集性
  —— 实战中 1,000 条明文**全部**集中在某一天某个波次 ⇒ 定位脱敏未生效的出口 ⇒ 可能拿到全量明文。
  这比任何外部反查路径都高效,**优先做**。

## Pitfalls

1. **别把虚拟号当明文号统计**(§1)——上游口径会骗你,自己重算。
2. **别指望从虚拟号"算出"真号** —— 分机是随机路由 key,必须查表(§2)。
3. **别去拨号验证历史订单** —— 绑定 7 天失效(§2)。
4. **双校验必须两端都验**(§3),否则会把驿站/家人的电话当成本人。
5. **地址字符串细微差异会导致关联失败** —— 务必归一化(去空格/中英文逗号/换行),
   必要时退回地址前缀匹配。
6. **地址里嵌的号未必是本人** —— 一律用掩码双校验筛,不要直接采信。
7. **不要向用户承诺"用快递单号反查真号"**(§6),那是死路。诚实交代边界。
8. **口径要分清**:常规脱敏(掩码)**可部分还原**;运营商隐私号(虚拟转接号)**不可还原**。
   不要在汇报里把两者混成一个数字。
