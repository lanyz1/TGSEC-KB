# 实时流导出转发（Realtime Stream Forwarding）

把目标系统的实时事件流（告警/消息/数据）可靠导出并零值守推送给委托方（通常经 TG bot）。适用于「实时导出 / 监控推送 / 一有新的就发给我」类任务。

## 工作流

1. **确认数据通道与事件载荷**：找出实时流端点（常见 `wss://host/ws` + 订阅事件，如 `{"event":"admin_subscribe"}`），确认单条事件是否携带完整业务数据（缺字段则需二次拉取，先确认有没有读接口）。前端 JS 常暴露订阅事件名与参数。
2. **受控注入验证链路**：自然流量稀疏时，用系统自身能力注入一条**中性文本**测试事件（混入日常流不扎眼），记录返回 id，确认端到端时延与载荷结构。
3. **⚠️ 判定单播 vs 广播（先于一切采集设计）**：服务端可能「单播分配」——每条事件只投递给订阅连接中的**一个**，单连接会静默漏收约一半。判定：开两条连接并行采集，对比各自收到的事件 id 集合——无交集且并集连续=单播；两集合基本相同=广播。**单播必须多连接合并采集**：N 路订阅汇入同一去重管道。
4. **连接数从 2 路起步**：服务端常有并发连接上限，超限会被互踢（连上即断的无限重连风暴，比少连接更糟，且向目标暴露异常）。4 路互踢、2 路实测稳定且覆盖 100%——需要更多时逐路加、观察是否被踢，被踢立即回退。外部订阅者（如目标自己的管理页面）在线时，单播会在全部连接间分配——我们的连接数是覆盖份额的杠杆，审计是唯一真相。
5. **合并去重管道**：N 路连接 → 同一 seen 集合去重 → 推送队列。seen 持久化（set + max）+ 状态文件原子写，跨重启恢复；队列设上限防洪。
6. **缺口审计（可靠性核心指标）**：事件 id 全局连续自增时，缺口数=漏收数。`scripts/audit_alert_gaps.py <state.json> [since_id]` 输出缺口+覆盖率，稳定期目标 0 缺口。同时在收件路径加 **GAP 实时侦测**（新 id 与 seen_max 差 >1 即写日志告警）——错过快照窗口的漏收无来源可补。
7. **补漏兜底**：重连时拉「最近事件快照」对比补推（多数系统快照窗口仅 ~5 条）；连接 8-12 分钟随机轮换顺带触发补漏。快照窗口有限——重启/换班空窗的漏收大多补不回：换版要快、错峰 phase 用小值、尽量避开高峰。
8. **TG 推送通道**：
   - chat 学习：`getUpdates` 长轮询，任何与该 bot 对话者自动入列（「不设白名单」=不加过滤）；offset 前推防重复消费
   - 限速：单 chat ~1 msg/s——逐条发、每条间隔 ≥1.15s；超限 429（retry_after 秒数）
   - `sendMessage` ok:true 反证该对话已建立（对方发过消息）；未 /start 用户首条会 403 can't initiate
   - 消息用 HTML parse_mode + 转义（业务文本含任意字符）；超长截断 <4000
9. **常驻部署**：systemd（Restart=always + 开机自启）+ state.json + append 日志；加 `/status` 类自检命令（借 bot 回运行状态）；定期跑审计。

## Pitfalls
- **别假设 WS 事件是广播**：多连接并存时先做双连接对照实验；误判=长期静默漏收（实测 ~50%）。
- 并发连接不是「越多越稳」：超限互踢比少连接更糟——先 2 路验证基线，再逐路加。
- 快照补漏只是兜底：窗口 ~5 条，高频流按它补几乎无效。
- 换版前设计好空窗：连接就位要数秒~数十秒；空窗漏收不可追补。
- 推送日志全 OK 只说明「已激活对话」都送达：未激活目标的首条消息会 403，不要据此误判系统故障。
- id 审计依赖「id 连续自增」前提：先抽样验证无明显跳跃再启用审计结论。

## 交付与验收
- 交付形态：常驻服务 + state + 审计工具 + 自检命令；向用户说明用法（看哪个对话、发什么命令）、当前推送频率、可选模式（全量/聚合/关键词过滤）。
- 端到端验证：用任务侧 TG 账号（单副本纪律）真实收信核对，并在汇报中说明测试号在推送名单中的去留。
- 汇报口径：给量化覆盖数据（审计缺口/覆盖率）；漏收如实披露，并区分「稳定期设计保证」与「升级窗口损失」。
