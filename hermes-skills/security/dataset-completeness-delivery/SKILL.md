# 数据集完整性 — 报「全部」之前必须拿得出的证据

适用：把目标用户面枚举完、要向老板/客户报「已拿全量」的任何场合。

用户只认「全部」，而且一定会追问一句「**这是全部吗 / 我注册的号在里面吗**」。这一问有两种死法：
数字口径错（报了虚高的数，下一轮自己打脸），或者只有一句「覆盖率 99.8%」（没有基数、没有归因、没法复现）。
下面每一条都是实测踩过的。

## 一、口径先核实：`total=` 几乎总是错的

脚本里的汇总数未必是实体数。实测踩坑：`total = MAX_ID - len(done)` 是**待扫 id 数**，被当成
「用户总量」报出去，虚高 3%–40%；发现时已经交付了一版错数。

- **实体数 = 去重后的行数**，只此一个定义。
- id 池大小、分页 `total`、`meta.total`、平台自报的后台「用户总量」（实测虚报 10 倍，纯招商话术）
  **都不是**用户数。
- 上报前能指出这个数出自哪个字段/哪次计算。说不出 = 不许报。

## 二、缺口必须逐类归因，不能一句百分比带过

`缺口 = max_id - 实体数`。逐个定性，三类写清楚：

| 类别 | 特征 | 结论 |
|---|---|---|
| 根账号本身 | id 1/2/3 这种顶级 | 结构上不会出现在任何人的下级列表 → **天然不可达**，不是漏拉 |
| 中间 id | 连号缺口（如 14003–14015） | 物理删除 / 风控批量清洗，同一批注册被杀 |
| 未知树根 | 第三棵顶级树 | 手机号未知 → 拿 config 里的客服/运营号逐个当 `node` 试 |

**证明「读不到」要用参数变体矩阵**，不能只看一次空返回：
`status` / `ban` / `isOpen` / `del` / `deleted` / `all` / `isBan` / `isFilter` 各取 0/1，
再看 `total` 是否变化。全部返回同一 total ⇒ 确认被过滤或已删除，可以写进报告当结论。

## 三、实时性 + 越权双自证（最硬的一条链）

老板问「你注册的号在不在里面」时，不要翻 CSV 回答，做一次现场实验：

1. 注册一个新号（拿到 uid + fullPath）
2. **立刻用另一个毫不相干的账号的 token** 回读它（`getChirld(node=<树根>)` 之类）
3. 两个数字同时对上：
   - 返回记录里出现刚注册的号 ⇒ 数据实时、跨账号可读、没漏最新数据
   - 树根 `total` 恰好 +1 ⇒ 分页参数正确、服务端无隐藏过滤

一条链同时证明 IDOR + 数据新鲜度 + 完整性，比任何推断都硬。

**分页参数陷阱**：参数名写错时 `total` 仍正常返回、`rows` 为 0（`code=-1` 容易被忽略）。
看到「total 对但 rows=0」先怀疑参数名（`page` vs `pageNum` vs `pageNo`），不要当成服务端过滤。

## 四、枚举残留不是空，补扫完才能报「全部」

主循环跑完、`done` 文件覆盖全区间，仍有几百个 id 缺失（全重试失败）。这批里约 **7 成是真数据**
（实录 180 个 err id → 补回 133 个用户）。

- 12 线程、代理/直连交替、6 次重试，几百个 id 几分钟补完。
- 跳过这步 = 交了一个计数器显示「完成」但内容残缺的盘子。
- 吞吐/代理/并发细节见 `rate-limit-throughput-engineering` 的 Step 5–7。

## 五、跨库重合度：用显著性判「同一批人 / 同一运营方」

两个库求交集，只报「重叠 61 个」等于把铁证降级成一句凑巧。给期望基数：

```
期望 = N1 × N2 / 值空间          中国在用手机号 ≈ 1.7 × 10⁹
实际 / 期望 > 100 倍  ⇒  同一批人，巧合不成立
```

实录：14,534 × 13,797 两库交集 **61 人**，期望 0.12 人 = **508 倍**。

交集再切开看构成，往往直接指向运营方同一性：

- 交集里 60/61 在 A 站有实名身份证、30/61 有绑定银行卡 → A 站负责收身份
- 同一批人在 B 站累计交易 120.8 万 → B 站负责收钱
- 两边网关同 `/24` 段 → 同一机房、同一运营方

**分身存放是这类盘的标准做法**：一个站收身份证，一个站收钱，字段结构天然互补，所以
「A 站没有交易数据、B 站没有实名字段」不是巧合，是设计。

## 六、一个报告只许有一个「总流水」——多口径必须对账

支付/博彩/资金盘后台至少有三套互不相等的「总额」，混着用必被打脸：

| 口径 | 典型来源 | 性质 |
|---|---|---|
| 订单底表（`paymenttime>0`） | 订单列表/导出 | **唯一可交付口径**，逐笔可复算 |
| 应用/商户计数器 `total_revenue` / `success_price` | 用户表、应用列表 | 缓存计数器，只统计现存应用/账号；删号删通道后旧值仍留着 |
| 通道计数器 `total_success_price` | 通道配置列表 | 只统计现存通道，通常最小 |

实测（<目标> 第四方支付）：底表 ¥13,619,251.83 / 应用计数器 ¥6,879,422.43 / 通道计数器 ¥5,738,975.41。
差额不是 bug，是「已删通道 56,480 笔 ¥1.32M + 已删商户 725 笔 ¥3.23M」从计数器里蒸发了。
**报告里两个总数并排出现且不解释 = 老板一句「你他妈是不是搞错了」的直接来源。**

对账步骤：
1. 先按底表算：`sum(amount) where paymenttime>0`、笔数、去重付款人，再出按日/按商户/按通道三张汇总。
2. 再抓平台计数器（用户表 `success_price`、应用 `total_revenue`、通道 `total_success_price`），与底表并排一列。
3. 差额逐项归因到「已删账号 / 已删通道 / 结算口径」；能对上几分写几分，对不上的明写「未解释差额 X」，不许糊过去。
4. 报告里只拿底表当「流水」，计数器一律标注「平台计数器口径」。

三个连带坑：
- **已删账号从用户表消失，订单还在**：按订单 `admin.nickname` 聚合，不等于用户表列表。实测漏掉一个已删商户 725 笔 / ¥3.23M（均笔 ¥4,458，与散户 ¥13–63 完全两个物种，是自营大额单）。用户表 4 个账号 ≠ 订单里 5 个昵称。
- **去重键要写清楚**：`buyer_id` 去重 99,061；`buyer_id or openid` 兜底才是 100,089。把兜底键的数目标成「按 buyer_id 去重」就是错标。
- **设备指纹 ≠ 订单笔数**：指纹去重 104,631，其中 Apple 指纹只有 48,538，而 Apple 订单 89,061 笔。把笔数写进「设备指纹 iPhone 占比」是数量级错。
- **`total` 与 `rows` 长度不是一回事（父子账号）**：`/admin/alipay/config?limit=2000` 现场返回 `rows=290`、`total=194` —— `total` 只数主账号，`rows` 连子账号一起返回（290 = 194 主 + 96 子）。报「290 个通道」要写成「290 条记录（194 主 + 96 子）」；只报 194 像漏抓，只报 290 又与面板对不上。
- **计数器是活的，缺的是「已删实体」那段历史，不是计数器不准**：同一批应用 `total_revenue` 两小时内从 6,879,422.43 涨到 6,883,051.79，增量 ¥3,629 与当日 `today` 增量分毫对应 —— 它按成功单实时累加。6.88M 与底表 13.6M 的差，全部来自已删应用/账号随实体一起消失的历史。结论要写成「计数器口径 = 现存实体」，不能写成「面板数字是假的」。

## 七、交付三件套 + 自检

每次报「全部」时一并给出：
1. **真值**（去重后行数）+ **上限来源**（扫了哪个 id 区间/哪个接口）
2. **缺口清单 + 逐类归因 + 证明读不到的证据**
3. **可复跑脚本**（导出脚本 + 自证脚本），别人能重算出同样的数

三件一起落在案卷目录里（`REPORT.md` + `summary.json` + `recon_v2.py`）。长跑作业的会话/上下文随时会丢，丢的时候唯一能救你的就是这三个文件 —— 新会话 `ls -lt` 找到报告，跑一遍脚本，所有数字重新长出来，不用回头猜。

自检：
- [ ] 每个上报数字都说得出出处，没把 id 池/分页 total 当实体数
- [ ] 缺口逐类归因，附参数变体证据
- [ ] 做过「注册新号 + 他人 token 回读」的现场自证
- [ ] err 残留已补扫
- [ ] 跨库交集给了期望基数与倍数
- [ ] 报告里写的是「天花板 + 不可达原因」，不是「覆盖率 99.8%」
- [ ] 报告内所有「总额」同口径，或已并排列出并解释差额（底表/应用计数器/通道计数器）
- [ ] 商户、账号按订单表 `admin` 聚合核对过用户表，已删账号的单已计入并单列
- [ ] 去重键写明是 buyer_id 还是 buyer_id+openid；设备指纹与订单笔数没有混用
- [ ] 报告里的 `total` 与 `rows` 已分清父子（主账号 / 子账号），没有把行数当实体数
- [ ] 资产归属自证：报告里每个域名/IP 都说得清「哪条证据把它绑到这个目标上」，未证实的已剔除
- [ ] 用户说「搞错了」时，从底表重算全部头号数字再回话，不要先问「哪里错了」

## 八、目标归属自证：老板问「你给我打的是不是这个目标」

只要前台是商城/门户皮、而报告讲的是后台支付/会员系统，这一问必来（实测原话：「我给你的不是这个目标吗？」）。
它和数字错是两件事，但触发条件常常是同一条：报告里混了自己都不认识的资产。

三条硬证据，按顺序给，不要用推断代替：

1. **现场重登，同一域名下打三个接口**，贴 `total` + 时间戳。推断再漂亮也打不过一个带时间的真实响应。
2. **与几小时前的 dump 对比，报增量**：341,365 → 341,681（+316 单 / 2 小时）⇒ 站还在收单、dump 是当次真拉的，不是三天前的旧包。
3. **解释双皮同域**：`/` 302 → `/h5/`（商城皮）；`/admin/index/login` 与 `/hm888.php/index/login` 共用 `backend.min.css`、同 `__token__` + `google_code` 字段、同库名 `kg002_sql` ⇒ 前台商城只是皮，钱在 `/admin` 那套系统里。

去噪规则（交付前必过一遍）：

- 顺手扫到的旁站/兄弟域（本案 `afkjie CrossAllPay` 五品牌 `/m/` 全 ACCESS DENIED）→ 与主目标无关，**从主报告删掉**，别留在资金数字旁边。
- 只凭端口/指纹猜的 IP（`8.136.101.171` 只回 Hyperf 默认页）→ 删，或单独一节标「归属未证实」。
- 带 Host 头能回同站页面的 IP（`47.96.16.32` 回 remotePay 页）→ 可留，写「疑似源站」。
- 判据一句话：报告里出现的每个资产，都要能回答「哪条证据把它绑到这个域名上」。答不出就别放。
