## 一、业务逻辑漏洞系统化方法论

### 1.1 OWASP BLA Top 10 2025 框架

| 类别 | 核心思想 | 典型例子 |
|------|---------|---------|
| BLA1 Action Limit Overrun | 幂等操作限额超限（并发绕过单次使用检查） | 并发兑换同一优惠券/重复退款 |
| BLA2 工作流步骤跳过 | 未按顺序执行或跳过验证步骤 | 跳过验证码直接重置密码 |
| BLA3 对象级授权破坏 | 未验证对象属主/权限即操作 | 改 order_id 操作他人订单 |
| BLA4 业务约束绕过 | 业务规则（限额/频次/资格）可被绕过 | 超出提现限额、越权领取会员权益 |
| BLA5 状态转换错误 | 允许非法/未定义状态转移 | 已取消订单再发货 |
| BLA6 竞态与时序缺陷 | 检查与使用之间非原子 | TOCTOU、Double-Spend |
| BLA7 参数篡改信任 | 服务端信任客户端提交的关键参数 | 前端传价格/折扣/角色 |
| BLA8 数据完整性缺失 | 关键字段缺少签名/防篡改 | 篡改回调金额/回调状态 |
| BLA9 滥用敏感业务流 | 不受限访问敏感业务流程 | 无限投票/刷注册/批量提交 |
| BLA10 依赖链滥用 | 组合多个弱校验形成高危链 | IDOR+支付确认+竞态 |

### 1.2 业务流程状态机分析（核心方法）

**步骤：**
```
1. 梳理状态全集：枚举业务对象的全部状态（订单/审批/工单/退款单/优惠券）
2. 绘制状态转移图：合法转移有哪些？（订单：待支付→已支付；禁止 待支付→已完成）
3. 标注每个转移的前置条件与后置条件
4. 寻找"缺失的边"：状态 A→C 是否被代码放行？（跳步）
5. 寻找"反向的边"：C→B 是否被允许？（回退）
6. 对每个转移做并发化：前置检查与后置写入之间是否有窗口？
```

**订单状态机攻击面示例：**
```
合法：待支付 --支付--> 已支付 --发货--> 已发货 --确认--> 已完成
             |                 |                 |
             +--取消-----------+                 +--退货--> 退款中 --> 已退款
攻击面：
  - 待支付 --直接改状态--> 已完成        （状态字段可篡改）
  - 已取消 --改回--> 待支付/已发货      （回退转移未禁止）
  - 已发货/已完成 --并发--> 退款多次     （退款无状态幂等）
  - 待支付 --并发支付--> 扣款N次/发货N次 （Double-Spend）
  - 退款中 --跳步--> 已退款但货物未退回  （跳过"收到退货"前置）
```

### 1.3 资金流与数据流追踪

**资金流追踪**（支付/退款/转账/提现/佣金/积分）：
```
1. 识别所有资金入口：充值、支付、退款、转账、提现、佣金、积分兑换、红包、返利
2. 识别所有资金出口：余额扣减、冻结、解冻、入账
3. 关键问题：
   - 金额从哪里来？服务端计算还是客户端提交？
   - 金额精度用什么类型？（float/double vs BigDecimal/分）
   - 入账和扣账是否在同一事务？扣款失败是否回滚？
   - 退款是否可超过实付？是否可重复？
   - 负数金额/零金额是否被允许？
   - 汇率/税率/手续费是否可篡改？（跨境支付、代金券折算）
   - 转账是否校验余额非负？（并发转出余额可能为负）
4. 资金守恒检验：模拟"充值→消费→退款→提现"闭环，验证账目是否守恒
```

**数据流追踪**：
```
1. 找出所有"身份/归属"参数：user_id、order_id、coupon_id、address_id、file_id、team_id
2. 每个参数追踪到 SQL/ORM 查询：WHERE 子句是否带 owner 条件？
3. 找出所有"状态/金额"参数：status、amount、discount、quantity、level、role
4. 追踪其来源：服务端计算 / 客户端提交 / 可被中间人篡改
5. 找出所有"一次性"令牌：验证码、重置 token、兑换码、优惠券码——是否绑定使用者？是否可并发复用？
```

### 1.4 信任边界与攻击面建模

```
不可信输入来源（全部要测）：
  1. URL/Query/Path 参数        → IDOR、状态篡改、HPP
  2. Body/JSON/XML/Form 参数    → 价格/数量/角色/折扣篡改、批量分配
  3. Header（Cookie/XFF/Host/Referer/Origin）→ 认证绕过、IP 限流绕过、Host 头注入
  4. 本地存储（localStorage/Cookie）→ 余额/积分/会员状态篡改
  5. 文件内容（上传的 CSV/JSON/图片）→ 解析后影响业务（批量导入金额/批量转账）
  6. 第三方回调（支付/短信/物流/IM webhook）→ 回调伪造、签名绕过
  7. 前端 JS（加密密钥/签名逻辑）→ 提取密钥伪造请求
  8. 消息队列/定时任务触发 → 延迟执行导致的时序问题
```

### 1.5 业务逻辑测试五步法（实战流程）

```
Step 1 业务梳理：抓取并梳理完整业务流（注册→登录→下单→支付→发货→收货→退款），
        用思维导图/时序图画出所有状态与转移（可用 AI 辅助，见第十二章）
Step 2 攻击面枚举：对每个业务动作列出"可篡改参数 + 可跳过前置 + 可并发化 + 可越权对象"
Step 3 单点测试：参数篡改（价格/数量/状态/身份）、跳步、回退、越权、精度
Step 4 时序测试：竞态条件（单包攻击）、TOCTOU、Double-Spend、多端点竞态
Step 5 组合链测试：把多个低危逻辑缺陷组合成高影响链（IDOR+支付确认+竞态→0元购）

每个发现按"前置条件→攻击步骤→影响→修复建议"四要素记录，便于写报告。
```
