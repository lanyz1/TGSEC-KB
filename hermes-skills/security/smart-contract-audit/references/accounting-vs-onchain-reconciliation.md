# 账实对账：担保/托管合约的最高价值一击

权限矩阵跑完（结论无越权）、参数扫描跑完（只有中低危）之后，**别就此收尾写"风险在治理"**。
切到账实对账 —— 本会话靠它拿到唯一一个真正"影响运营"的严重级 finding。

## 一、方法：账面 ↔ 事件级实收

```
账面 = 合约自己的 view 返回（getEscrow/getRefund/getFeeTerms…）= 它"答应付多少"
实收 = 链上事件级全量入金           = 它"真的有几分钱"
```

**两件事都做完，再相减。** 只看账面会被记账数字骗；只看余额看不出记账是假的。

### 取实收（TRON / TronGrid，实测可用）
```bash
curl -s --noproxy '*' -H 'Accept: application/json' \
  "https://api.trongrid.io/v1/accounts/<合约地址>/transactions/trc20?limit=200&only_confirmed=true"
```
- 逐条看 `from` / `to` / `value` / `token_info.address`
- `to == 合约` ⇒ 入金；`from == 合约` ⇒ 出金
- ⚠️ **响应里混着 Approval 事件**：`value` 在 1e77 量级（≈2^256）的都是 Approval，**必须剔除**，
  否则 `Σ流入` 直接变天文数字（本案 8 条里 4 条是 Approval）
- 按 `block_timestamp` 排序，做成时间线（对齐每笔 party 的入金顺序）

### 算术证明（报告里最能打的一段）
```
若  Σ(入金) == 当前余额   且  Σ(出金) == 0
⇒ 合约一生只收过这么多钱，一分钱都没出去过
⇒ 账面凡是超过这个数的部分 = 没有资金背书的记账
另外：若某笔托管(status=0)的 party 地址
      在【全部入金事件】里根本找不到 ⇒ 该笔是零资金空头记账
```

### 兑付可行性（把结论钉死）
拿 `previewRefund(id, mode, amount)` 类 view 的返回值（= 合约自己承诺的应付额）
跟合约实有余额比 ⇒ **应付 > 实有 ⇒ 结算必然失败 ⇒ 平台核心承诺被证伪**。
这是**纯算术**，不需要广播、不需要状态变更，无争议。

## 二、案件实测数字（未开源担保合约，TRON）

| 托管 | 合约账面 | 该笔 partyA 实际转入 | 虚增 |
|---|---|---|---|
| escrow1 | `[5]=6.000000` | 3.060000 | 2.940000 |
| escrow2 | `[4]=8.300000` | 0.113000 | 8.187000 |
| escrow3 | `[4]=10.000000` | 2.000000 | 8.000000 |
| escrow4 | `[4]=10.000000` | 2.000000 | 8.000000 |
| **escrow6（唯一 status=0 活跃）** | `[4]=5 [5]=5 [6]=10` | **0.000000（零入金）** | **10.000000** |
| 合计 | **44.300000** | **7.173000** | **37.127000（6.18×）** |

- 合约一生入金 = 4 笔真金 `3.06 + 0.113 + 2 + 2 = 7.173`，**流出 0 笔**，与当前余额**完全相等**（双源一致）
- escrow6 的 partyA/partyB 在**全部入金事件里根本不存在** ⇒ 零资金背书
- `previewRefund(6, 0, 0) → [5.000000, 5.000000, 0]` ⇒ 按账面承诺付 10 USDT，池子只有 7.173 ⇒ **兑付必失败**

## 三、记账注入面：energy 差分定位"谁能凭空写账面"

```
主运营 depositFor(6, partyB, 1U)   → energy=112,029  ★ 通过全部校验，走完记账逻辑
主运营 depositFor(6, partyA, *)    → energy=8,571    → InvalidParticipants
主运营 depositFor(6, 陌生人, *)     → energy=8,571    → InvalidParticipants
运营A / partyB / partyA / owner / 陌生人 → energy=8,437 → Unauthorized
对照: partyB deposit(6, 1U)        → energy=19,068，随后裸 REVERT（无具名错误）
```
⇒ 运营员分支能量是拒绝路径的 **13 倍** ⇒ 走了独立代码路径，可指定任意 `party`/任意 `amount` 写账面。
⇒ 同时说明：**`deposit` 与 `depositFor` 是两条不同的记账入口**，权限/校验必须分别测。

## 四、报告写法（本用户偏好）

- 结论一句话先给：`账面 44.30 USDT / 实有 7.173 USDT，兑付缺口 37.127 USDT（6.18 倍）`
- 紧跟"事件级硬证据"：列出全部入金（时间 + 地址 + 金额）+ 声明流出为 0
- 再给逐笔对账表（账面 / 实收 / 虚增）
- 最后给危害推演：`previewRefund` 承诺 → 池子不够 → 结算失败 → 平台核心承诺失效
- **修复必须落到 P0 可执行动作**：记账与本次实际到账额强绑定（`balanceOf` 前后差值 == 记账额，
  不等则 revert）、结算前断言池子充足、撤销废合约授权、owner 上多签+timelock

## 五、纪律

- 账面数字与实收数字**都必须是实测**；跨源交叉（explorer 索引 + RPC + 事件求和）一致才采信
- `balanceOf` 与索引打架时**先跑无参 view 自检 + 换源复核**，别单方面宣布"索引滞后"
  （本案曾据 `balanceOf`=0 误判"钱已跑光"，真相是自己的参数编码 bug，索引是对的）
- 全程只读，报告里显式声明"未广播任何交易"
- 定性克制："账实不符 + 兑付必然失败"是硬结论；"这就是诈骗"需要受害人侧证据，不下
