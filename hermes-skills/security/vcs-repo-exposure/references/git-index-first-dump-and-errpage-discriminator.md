# 索引直取 / `.gitignore` 神谕 / 探测误判 — `.git` 暴露后的三条实战增量

2026-09-14 实战(ThinkPHP 3.1.3 应用,`.git` 全裸露)。补 SKILL.md §2、§5 与 Pitfalls。

## 1. 索引直取:当 `.git/index` 可读时,别走对象图

SKILL.md §2 给的 `scripts/git_walk_dump.py` 走的是
`commit → tree → 递归子树 → blob`。**如果 `.git/index` 本身可读,这条路是多余的** ——
索引里已经有每个文件的 `(path, size, sha)`,直接取对象即可:

```
GET /.git/index           → 解析 DIRC 条目 → [(path, size, sha1), ...]
GET /.git/objects/<sha[:2]>/<sha[2:]>  → zlib.decompress(raw)
                                        → 掐掉 b"<type> <size>\0" 头 → 落盘
```

**为什么更好:**

| | 树遍历 | 索引直取 |
|---|---|---|
| 请求数 | commit + 每个 tree + 每个 blob | **每个 blob 一次** |
| 拿得到 size | 否 | **是**(可按体积筛掉大媒体文件) |
| 拿到完整清单 | 需走完所有 tree | **索引即清单**,一次就有 |

**实测**:3984 条索引里筛出 65 个自研文件(`App/` + 根目录),**65/65 命中、0 失败**,212 KB tar 回本地。
索引解析的坑(必读,SKILL.md 已记):`total = 62 + len(name)`,`pad = 8 - total % 8`,
**整除时补 8 而不是 0**;错位后只能解析出零头。

**索引还是"清单权威来源"**:即使部分 blob 已 404,你也能立刻说出
"仓库声明 N 个文件、实际取回 M 个" —— 这正是交付环节要的一句。
**别为了"全量"去拉 vendor/框架目录**(ThinkPHP/、node_modules/),对拿凭据无帮助且慢。

## 2. `.gitignore` 是配置路径神谕(读完源码先读它)

`.gitignore` 常常**精确点名凭据文件在哪**,并且同时宣告"它们不在仓库里"。
实测原文:

```
.idea
App/Conf/config.php     ← 数据库/应用配置(口令就这里)
App/Conf/db.php         ← 数据库配置
App/Runtime             ← 日志/缓存(可能有 SQL 明文)
App/Upload              ← 上传落地目录
./test_log
```

**一步得到两个结论**:
1. **目标路径**:以后做路径穿越 / LFI / 上传利用,直接照这个清单打,不用猜。
2. **期望管理**(更重要):`config.php` / `db.php` 被 ignore ⇒ **不在 `.git` 仓库内,源码泄露不会给你 DB 口令**。
   同批要试的 IntelliJ 侧信道也常一起落空:
   - `.idea/workspace.xml`、`modules.xml`(可读,泄露**开发机绝对路径**如 `D:\wamp\wamp64\www\myhfm`、运行配置)
   - `.idea/dataSources.xml` / `dataSources.local.xml`(**存库口令的地方**,通常未部署 ⇒ 返回错误页)

⇒ **报告口径**:写清"`.git` 全裸露 → 源码全量到手,但 `App/Conf/config.php`(DB 口令)被 gitignore
不在仓库,故未取得数据库凭据"。**不写这句就等于把"源码全裸"夸大成"整库已拖"。**

## 3. ★坑:定长错误页导致"备份文件遍地都是"

在 TP/框架类应用上探测备份名(`/backup.sql`、`/myhfm.zip`、`/db.sql`、`/App/Conf/config.php.bak` …)时:

**不存在的路径也返回 `200`,体是框架的定长错误页**(该目标 1524–1652 B)。
于是清单会显示"找到 30 个备份文件",**其中只有 1 个是真的**。

| 路径 | 响应 | 真相 |
|---|---|---|
| `/myhfm.sql` | 200, **35605 B** | ✅ 真 Navicat 转储 |
| `/myhfm2.sql`、`/db.sql`、`/myhfm.zip` … 各 30 个 | 200, **1524–1534 B** | ❌ 全是同一个错误页 |

**判据**:批量探测**必须比字节数**,不能只看状态码。做法:
先取一条**已知不存在的路径**作为"错误页基线尺寸",再把**同尺寸(±几十字节)**的结果全部划为假阳性。
另外要把列表**按体积降序**看 —— 真文件几乎总在最前面。

同源教训:**`LIMIT`/分页类页面返回"正常尺寸页面"也一样骗人** ——
本轮请求返回 13487 B(和基线分页页一模一样),看着像"成功",实际注入参数根本没进 SQL。
**判"参数进没进 SQL"永远读后端日志里的真实 SQL,不要靠状态码、响应长度或页面长得像不像。**
