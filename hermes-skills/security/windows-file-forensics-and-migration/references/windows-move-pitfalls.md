# 跨盘移动 / 只读 / 占用 —— 实测行为与失败样本

本文件是 `windows-file-forensics-and-migration` 的实测细节附录。场景：把 213 项 / 12 GB 桌面归档到另一个盘（181 项移动 / 39 项留桌面），期间出现只读致失败与第三方删除。

## 1 shutil.move 跨盘的真实语义

```
shutil.move(src, dst)
  ├─ 同卷:  os.rename()            → 原子、瞬时
  └─ 跨卷:  copytree() + rmtree()   ← 本例的失败点
```

跨卷分支意味着：

- 复制成功但 `rmtree` 失败 → **抛异常，但目标是完整的、源是残缺的**。异常信息指向**源路径**，很容易被误读成"复制失败"。
- `rmtree` 删不掉 **只读文件**：Windows 上 `os.remove` 对只读文件抛 `WinError 5`。
- git 仓库是天然雷区：`.git/objects/**` 一律 444 只读。

实测失败样本（4/181）：

| 项 | 报错点 | 真因 |
|---|---|---|
| `touliu/` | `.git/objects/00/1035b0...` | 1927 个只读 object |
| `破甲全套/` | `全破.zip` | 2 个只读文件 |
| `便携软件/` | `新v2包.zip` | 1 个只读文件 |
| `喊麦军火库/` | `商业` 目录 | 目录内残留只读项 |

**这四个的目标副本其实都已完整**，证据：

```
touliu   源(残留) 25034 文件 / 1153.8 MB   ← 比目标少
         目标     25110 文件 / 1155.1 MB   ← 多出来的正是已被 rmtree 删掉的部分
         "仅目标有: .claude | .deploy | .env | .env.example"  ← 源里这些目录已被整体删除
         逐文件比对: 缺失 0
```

判据：**目标文件数 > 源残留文件数**，说明 copytree 早于 rmtree 全部完成；源只是删不掉的尾巴。

## 2 正确收尾顺序（不要跳步）

1. `verify_subset_then_clean.py SRC DST` —— 逐文件比对相对路径 + 字节数，输出缺失数；
2. 缺失为 0 ⇒ 复制完整；
3. 清只读属性（`os.chmod(f, stat.S_IWRITE)` 遍历）再 `rmtree`；
4. 只有这时才允许删源。**验证前删任何东西都可能真丢文件。**

反面做法：看到 `WinError 5` 就重跑一遍复制（浪费数分钟且不改结果）、或直接 `rm -rf` 源（真丢）。

## 3 数量对账别用 ls

`ls -1 | wc -l` **漏隐藏文件**（`desktop.ini` 等），本例对账时出现 213 vs 220 的偏差，一度被误判成"少了 7 项"。

改用 `os.listdir()` 复核。最终对账关系：

```
dry-run 读到 220 项 = 归档 181 项 + 桌面保留 39 项     ✔ 完全闭合
```

## 4 任务开始前必须做的依赖预检

三条硬依赖，任一条漏查都会砸掉用户在用的东西：

1. **活进程从待移动目录启动** —— 本例 `v2rayN.exe` + `xray.exe` 的 `CommandLine` 指向桌面 `新v2包\...`，移动即断代理（实测：移动后必须复核代理仍通，HTTP 200 才算安全）。
   查法：`Get-CimInstance Win32_Process | Where CommandLine -like '*目标路径*'`
2. **`%~dp0` 相对依赖组** —— `启动上品工具.bat` 内 `cd /d %~dp0` 再调同目录 `qavlixor_shelf_ui.py`，整组必须同处一地。
3. **`.lnk` 指向** —— `WScript.Shell.CreateShortcut($p).TargetPath`；本例 27 个快捷方式全部指向 D/E 盘，可安全保留，其中 `v2rayN.exe - 快捷方式.lnk` 指向桌面内目录（同第 1 条）。

## 5 并发写入者：本类的最大不确定性

归档执行期间，6 个留在桌面的文件被第三方删进回收站：

```
$I 删除时间(UTC)  2026-09-12 04:36:53 → 本地 12:36:53   (4 个同秒)
                            04:36:57 → 12:36:57
                            04:36:58 → 12:36:58
```

**这两个时间戳不是一回事，别搞混**：

| 来源 | 字段 | 含义 |
|---|---|---|
| `$R` 文件的 mtime | LastWriteTime | 文件**原始修改时间**（本例显示 9/7–9/10，与删除无关） |
| `Shell.Application` 的 `ModifyDate` | 同上 | 同上，仍是原始修改时间 |
| `$I` 偏移 16 | FILETIME | **唯一可信的删除时刻**（本例显示就是刚才） |

只看 `$R`/`Shell.Application` 会得出"这些文件是三天前删的"的错误结论，从而彻底放弃追查。

归因结果：脚本日志无记录（`move`/`rmtree` 不走回收站）；窗口内 3 个活跃 agent 会话的完整工具调用逐条查过，都在跑各自任务，排除；5 秒内连删 6 个不同类文件 = 批量删除特征 ⇒ 判定为 Hermes 之外（Explorer/同步客户端/清理工具一类），现有日志无法进一步指认。**结论要如实写成"未闭环"，不要把推测写成定论。**

## 6 多 agent 并发的连带症状

同机多个会话共享环境时会出现一组看似无关的现象，识别出来能少走弯路：

- 共享目录里的文件被第三方删除/改写
- 移动时偶发 `WinError 5`（另一进程短暂持有句柄）
- 一个新文件"凭空出现"（另一个会话的产物落到同一目录）
- **连 memory 都会被并发改写**：本例记忆写入因条目被另一会话修改而 batch 失败，报错内容与自己的记录完全不符

动手前先确认没有别的会话在同域作业；写共享状态（memory / 共享路径）要有"可能被别人改过"的预期。
