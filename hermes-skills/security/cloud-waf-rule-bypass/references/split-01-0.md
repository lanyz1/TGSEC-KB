## 0. 先给响应分类,不要只看状态码

| 类别 | 识别特征 | 含义 |
|---|---|---|
| WAF 拦截 | 小段厂商 HTML,中文文案提到安全威胁 / 请求已被阻断 | 规则集命中,需绕过 |
| 源站 4xx | Spring Boot JSON 带 `timestamp`/`status`/`path` | 请求已到应用 ⇒ 这一发已被放行 |
| 502 Bad Gateway | 厂商/Apache 错误页 | WAF 转给了不存在的默认上游 —— Host 不在已配置域名表里 |
| 400 + 应用自定义文案(如 `Invalid encrypted request`) | JSON `{code,msg}`,与厂商无关 | ★**文案判不了层,判层只看响应头**:带 `access-control-allow-origin: <前端域>` 才是应用层;只有 `Server: nginx` + 无 CORS/框架头 ⇒ **网关层(加密闸)**,请求**没到应用**。见下方 ★★ |
| 400 Bad Request | 框架解析错误 | 畸形归一化到了应用,不是绕过 |
| **500 Whitelabel**(Spring `{timestamp,status,error,path}`) | 应用抛未捕获异常 | 已到应用层,且**未被要求加密**(过滤器白名单命中);异常来自框架对畸形路径的处理 ⇒ 用它判「该路径属过滤器白名单」 |
| **200 + JS 质询页**(最易漏判) | **200**,HTML 含 `renderData` 表单/大段混淆 JS、厂商标记(阿里云 `aliyun_waf_bb`),Set-Cookie `acw_tc`/`aliyungf_tc`/`ssxmod_itna` | **反机器人质询层,与规则集无关** —— 补 header/XFF/换 UA/换出口全无效 ⇒ 走 §3b |

**WAF 403 与源站 403 是两个问题,解法完全不同**。源站自己拒的(JSON 错误体)用鉴权/路径绕过;
WAF 拒的(拦截页)用本卡。判错会白烧一整轮。用响应体文案做程序化判定 ——
路径绕过常回 302、Host 变形常回 200,都不是 403。

### 0b. ★ 先定位 WAF 在匹配哪个“词”——别默认它是显而易见的那个

**拦截页只告诉你“被拦了”,不告诉你“被哪个字拦的”。判错关键词 = 在同一根因上换 payload 空转一整轮。**

- **判据(最省请求的定关键词法):若 N 个语义完全不同的入口同时被拦,而它们只共享一个子串,
  那 WAF 匹配的就是那个子串,而不是你选的那个 payload。**
  实测:5 个互不相干的框架入口(输入过滤/模板引擎/文件写/会话/异常处理)全回拦截页,
  唯一共同点 = URI 里的**框架命名空间前缀** ⇒ **关键词是命名空间,不是那个公网流传的函数名**。
  ⇒ 此时“换 gadget 家族”是无效动作(它们都含命名空间),不要再逐个试。
- **匹配面不只有查询串**:同一厂商既可只查查询串,也可**连 URI 路径一起查**。所以“把关键词搬进 body”只在
  **body 不被查**时成立 —— 这本身就是个必须先测的未知量。
- **关键词隔离(定位到具体词)**:一条 URI 只含词 A、一条只含词 B、一条干净 URI 而把词放 body,各发一发(每发换出口)。
  **“body 是否也被查”是分水岭**:不查 ⇒ 关键词搬 body 路还通;也查 ⇒ 转 Host 归一化(§2)或换面。
- ★ **实测锚点（自研/宝塔式 WAF，可直接引用）**:保持 URI 干净、仅 body 携带 `system`/`__construct`/`think\app`
  ⇒ **全部正常放行**（回应用页）⇒ 该实例**不查 body**，「关键词搬 body」路线成立。
  对照一旦成立就不要重复测这层，直接进入下面的「烧出口记账」。
- ★★ **反例锚点：同一厂商的另一个实例会查 body**（宝塔「网站防火墙」：URI 干净、仅 JSON 体带
  `gopher://`/`dict://`/`file://`/`127.0.0.1` ⇒ 403 拦截页）⇒ **「查不查 body」是逐部署的事实，不是厂商属性**；
  已测过 body 不被查的实例，不能拿来推另一个实例。
- ★★ **给 body token 拦住时，先换编码形态，不要换措辞**：同一份 JSON 改用 `Transfer-Encoding: chunked` 分片发
  ⇒ 200 且值真落地（**读回确认字节**）—— WAF 的体解析器不覆盖 chunked 形态。
  ⚠ **chunked 只救 POST body，不救查询串**（实测同实例：chunked 体放行，而带 `%2f` 的 GET 查询串仍回 403 拦截页）
  ⇒ 它不是"哪一发都能过"的万能键：**凡能搬进 body 的载荷就搬进 body**，留在查询串里的载荷等于没绕 ——
  别把"我用了 chunked"当成已绕过。另：应用层可能对已放行的字段再做字符过滤（实测 `code` 参里的 `<?php` 被清空）
  ⇒ 绕过了 WAF ≠ 值完整到达 sink，仍要回读落地字节。
  ⇒ 换 IP 等价写法（`127.1`/十进制 `2130706433`/八进制/IPv6-mapped）在同实例上**全 403**，那是无效动作，别逐个试。
- ⚠ **这类 WAF 的拦截是自适应/burst 触发的**：同一 token 低速率曾放行（实测 `127.0.0.1:888/8888/3306` 通）、
  突发十几发后整体拉黑 ⇒ **「这一发被拦」不等于「这个词被拦」**：先降速/换出口重发一发对照再判。
  ⇒ 同理，「某个 payload 过了」也可能只是 burst 未触发，不是真的绕过了 —— 结论必须可重复复现。
- ⚠ **「请求被放行」≠「值已生效」**：写配置/写库类载荷发完立刻回读，比对落地字节，否则会把
  「WAF 放行」写成「写入成功」。
- ★ **烧出口按发数记账，并预设停手判据**:撞关键词类 WAF **每出口只值 5–13 发**（实测多个出口均在此区间被硬封）。
  **一旦该出口连站点首页都回 `000`，它就是死的** —— 立即换出口，**不要在同一出口继续做对照实验**
  （之后的每一发都无信号，却会写进你的结论）。curl 与 Python 双双 `000`/RST 且首页也 `000` = 真 IP 层封锁，
  不是 TLS 指纹问题，重试无意义。
- ★ **成本裁决（决定继续还是转面）**:每出口只值 5–13 发时，「换 payload 撞关键词拿 RCE」的期望成本
  远高于「改用**零 WAF 特征的正常业务 URI** 打数据面」。**RCE 未通即转数据面是默认次序**，
  不要把跳板池继续烧在关键词上；转面后请求不再含任何检测特征，可低成本大批跑。
- ★ **不要把最典型的那个公网 payload 拿去当首轮探测**:在特征匹配型 WAF 上它既是拦截诱因、
  也可能**直接拉黑源 IP**(实测本机 IP 由此被硬封:curl 回 `000`、Python 回 `RemoteDisconnected`,
  而跳板出口同秒回首页 200 = 站是活的,只是这个 IP 没了)。首轮就用不含关键词的形态,或换干净出口再发。
- 完整判别矩阵、URI 编码实测负结果、以及关键词确实在 URI 路径时的下一步,见
  `references/waf-keyword-identification.md`。

★ **同一个 JSON 错误体可由不同层分别产生 ⇒ 先比响应头指纹,再决定打哪一层**。
实测同站同一句 `{"code":400,"msg":"Invalid encrypted request"}` 有两种来源:
`Server: nginx` + **无** `access-control-allow-origin` + 无框架头 ⇒ **网关/反代层**(WAF 之后的加密闸);
带 `access-control-allow-origin` ⇒ 应用栈(CORS 过滤器已执行)。
把网关层当应用层 ⇒ 会一直在调加密实现(OAEP 参数、iv 长度、payload 字段名、公钥轮换),永远调不通。
反之 `{timestamp,status,error,path}` 形状的 404 是 **DispatcherServlet** 产出 ⇒ 该请求已穿过 WAF+网关+Security,
是「打到最里面了」的标志。

★★ **加密闸是"真解密"还是"只看路径形状":一发垃圾密钥判定(最省时的 A/B)**。
把 `X-Encrypt-Key` 换成明显非法的值(如 `AA`),其余原样重发:
- 与完整合法信封**响应逐字节相同** ⇒ 该层**不做解密** ⇒ **立刻停手**:不调 OAEP hash/MGF、不查 iv/nonce 长度、
  不查 payload 字段名、不怀疑公钥轮换,并**放弃"我的加密实现有偏差"这条假设** —— 问题不在加密;
- 响应**不同** ⇒ 它真在解密 ⇒ 这时才值得跑算法对齐矩阵(见下)。
- ★ **更省的一发:裸请求对照**(不带 `X-Encrypt-*` 头、不带体,只给路径)。裸发与完整合法信封**回同一句固定文案、长度逐字节相同**
  (实测同一 46B 错误体,且 `/app/**` 与 `/prod-api/**` 两个不同前缀都一样) ⇒ 该层**按请求形状(URI 形态)判定**,与密文无关
  ⇒ 不要继续调 OAEP hash/iv/nonce/payload 字段名,改去测**路径形态**(原路径 vs 分号后缀 vs 大小写)
  或改用客户端自发请求(浏览器钩子法)取合法签文后重放。

★ **第二次对照能一次消灭一整类假设**:在目标页面的**同源上下文**里用页面自己的 `crypto.subtle` 按 bundle 参数
生成信封发出(CDP `Runtime.evaluate` + `awaitPromise`)。与本地实现结果相同 ⇒ 字节序/base64 变体/字段包装名/
iv 长度/nonce 参与派生 这一整类偏差全部作废,别再逐个对参。

**算法对齐矩阵(仅在上一节判为"真解密"时才跑)**:前端 `RSA-OAEP`+`SHA-256` 而 Java 后端默认常是 **SHA-1**
(`RSA/ECB/OAEPWithSHA-1AndMGF1Padding`)⇒ 依序各发一发,以"**响应类别是否变**"为唯一命中判据:
① OAEP SHA-256/MGF1-SHA-256(基线) ② OAEP SHA-1/MGF1-SHA-1 ③ SHA-256/MGF1-SHA-1 ④ SHA-1/MGF1-SHA-256 ⑤ PKCS1v15。
**全败 + 垃圾密钥同响应 ⇒ 结论是"不是加密问题",不是"再换一个组合"。** 矩阵与定层表见
`references/encrypted-gate-layer-triage.md`。
