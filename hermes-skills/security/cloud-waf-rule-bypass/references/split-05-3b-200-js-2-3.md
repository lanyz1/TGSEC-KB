## 3b. ★ 第二层:200 + JS 质询页(反机器人层)——别用 §2/§3 打

云 WAF 至少两层,**打错层 = 白烧一整轮**:§1–§3 是**规则集层**(403 拦截页,按 Host/payload 记账);
另有一层是**质询层**(200 + JS 质询页,要你执行它的 JS 换 cookie)。规则集的招式(Host 归一化、
路径单字符编码)对质询页一律无效,反之亦然。

- **识别**:状态码 200 + `renderData` + 大段混淆 JS + `acw_tc`/`ssxmod_itna` Cookie ⇒ **不是放行,是质询**。
  只看状态码会把质询页判成"正常"。
- ⚠ **永不 print 质询页正文** —— 实测单页约 66 万字符,冲爆上下文后后面几轮都只剩"1 行输出"可猜。
  判定只输出:状态码、`Content-Length`、是否含 `renderData`、cookie 名;要拆 JS 就落盘后按偏移读。
- ★ **先做一条 A/B,再谈换出口**:同一出口、同一秒、同一 URL,**文档导航放行 / 同页 XHR 被质询**
  ⇒ 拦截挂在**请求形态**(navigation vs subresource)上,**不是 IP 信誉、不是 header 指纹**。
  实测无效(全 100% 仍质询):`Origin`/`Referer` 指真实前端、`Sec-Fetch-Dest/Mode/Site`、`X-Requested-With`、
  UA 轮换、**XFF 轮换**、HTTP/1.0、`Accept-Encoding: identity`。
  ★★ **多出口确证法(一次定死"这是 IP 维度"这条错误假设)**:把同一探针矩阵(原路径 POST / `;x=.js` POST / 原路径 HEAD)
  在多台**互不相干的出口**(不同云/不同城市/全新未用过的 IP)各跑一遍。实测 4/4 逐格一致
  ⇒ **换出口 0 收益**,此后不再消耗代理池与冷却时间。
  ⚠ 探针只记 `Content-Length` + 是否含 `renderData` + 首 40 字节:同一尺寸重复出现即可定性为质询页,不要 print 正文。
- ⚠ **页内 fetch 能不能用取决于页面的「信任态」，不要一句判死**:未获信任态的页面上页内 `fetch` 同样被质询;
  但**目标自家真前端页**（它自己就在打同一 WAF 实例时）里，页内 XHR **会被质询脚本接住**：脚本 hook 了 XHR/fetch,
  会为**每个受保护 URI 现场铸造令牌**写进查询串，并把被质询的请求**原样重放**（method/body 逐字保留）。
  判定“重放发生过”的方法：注入 hook 记录 `open/send` 的 `{method,url,含令牌?,body}`，
  会看到**同一请求两条 URL** —— 第一条裸路径（响应=挑战页），第二条带令牌且 body 相同。
  ⇒ **真页面内的 XHR 是一个可用运输层，不要用 curl 的失败结论或“页内也被质询”的旧结论直接否掉它。**
- ★★ **跨源重放：JS 读不到响应 ≠ 请求失败，用 CDP 取回 response body**（本层绕 CORS 的标准手法）：
  跨源重放时 JS 侧只会得到 `onerror` / `TypeError: Failed to fetch` / axios `status: 0`，而请求**已发出且响应已返回**。
  做法：`Network.enable` → 事件循环里收 `Network.responseReceived`（按 `response.url` 命中目标，取 `params.requestId`）
  → `Network.getResponseBody(requestId)` 读回。**它不受 CORS 约束**。
  ⇒ 命中目标后先看 `body`：含 `renderData`/`_waf_` 是挑战页，否则才是真响应。
  ⇒ 有了这一步就不用再靠 `OPTIONS` 预检去猜“该 API 能不能从页内打”——直接发、直接读回。
  完整配方（hook + 读回代码 + 逐字实测证据形态）：`references/page-context-auto-replay.md`。
- ⚠ **历史产物里的"大体积命中"不算证据**:质询页本体就在 ~110KB 量级,只记长度的脚本会把质询页记成"真页面"
  (实测某路径曾以 65,137B 记为命中,重取后是框架 404)。**复核判据 = 重取一次看 title/正文**,不是看字节数。
  ★ **质询页有多个长度变体**(同一站实测 65,137 / 48,753 / 110,310 三种同现)⇒ 判据不能用单一阈值或"约等于某个数":
  **主判据 = 是否含 `renderData`**,长度只用于去重；无 `renderData` 时再谈响应类别。
  ⚠ 唯一有效的例外是质询页自己签发的 URL token,但**必须连同它绑定的那条 URL 一起回放**;
  把 token 挂到别的路径/查询串上仍被质询(见下方 ★ token 铸造)。
- ★ **方法白名单 = `HEAD` / `OPTIONS`**(别信"方法切换无效"这类粗结论):质询层按 HTTP 方法记账。
  同一路径逐方法打一遍即可确认:`HEAD`/`OPTIONS` **无后缀直达源站**;
  `GET/POST/PUT/DELETE/PATCH/PROPFIND/MKCOL/LOCK/UNLOCK/COPY/MOVE/SEARCH/REPORT/VIEW/CONNECT` 全被质询
  (`TRACE` 更早一步被 Tengine 405)。两个用途:**(a) 通用绕过** —— 不改路径、不加后缀就能摸源站;
  **(b) 路由/白名单 oracle** —— 批量 `OPTIONS` 扫候选路径,谁回应用层响应谁就存在,比逐后缀试快一个量级。
  ⚠ 局限:该发法**到不了业务 handler** —— `OPTIONS` 被 Spring 默认处理器吃掉(200 空体),`X-Http-Method-Override` 实测不生效。
- ★ **浏览器侧永远先查 CORS 预检,再怀疑自己的信封/指纹**:跨域页面向目标发**带自定义头**的请求先走 `OPTIONS` 预检,
  源站不认就回 **`403 Invalid CORS request`**,浏览器侧只表现为 `TypeError: Failed to fetch` / axios **`status: 0`**。
  一发判死:`curl -i -X OPTIONS <url> -H 'Origin: <前端域>' -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: <你的自定义头>'`。
  回 403 ⇒ 该 API **不可能**从页内打,转命令行;同时这也解释了「前端自己的 XHR status 0」。
  **把 `status: 0` 读成"我们的头/加密不对"是本类目标最贵的误判。**
- **后缀白名单**(.css/.js/.txt/.xml/.json/.svg/.ico/.jpeg…)可直穿源站(`.zip/.rar/.bak/.jar/.java` 被 Tengine 405),
  但它**同时改写了路径 ⇒ 绕开 Spring Security 的 `permitAll`**:`/login`、`/captchaImage` 变 401/404,
  **永远到不了业务 handler**。后缀法只用来读源站错误体/指纹。
  矩阵参数 `;` 分两种命运,别混:
  - `/login;.css`(分号后无 `=`):Spring `StrictHttpFirewall` 拦成 **500 Whitelabel** ⇒ 不能承载真实调用,见 500 就停
  - `<真实路径>;x=.js`:WAF 按后缀放行 + 容器剥离分号后**后端收到的是真实路径**。
    它能不能承载真实调用**取决于路径由谁映射**:Spring Security 按原路径匹配 `permitAll`
    ⇒ 白名单路径统一 500(**不能**发业务请求);而 Servlet/JFinal/Struts 栈没有 `StrictHttpFirewall`
    ⇒ 请求落到 DefaultServlet/JspServlet,**静态文件真服务、`.jsp` 真执行**。
    无论哪一栈,**它的响应类别本身就是免费的分层 oracle**:源站 400(要求加密)= 路径存在且需信封;
    500 Whitelabel = 命中过滤器白名单;容器原生 404 = 不存在(并泄露内部真实路径);200 含正文 = 该文件/JSP 真实存在。
    ⇒ **Spring 栈上只用来判层,非 Spring 栈上它就是可用的读取通道**(见 `references/anti-bot-challenge-layer.md` §3.1)。
  ★★**网关白名单 ≠ 应用 `permitAll`,是两份独立清单,必须分别实测**:实测把网关放行的 `/common/download/**`
  当成应用白名单,据此预测"免认证任意文件读",结果每个变体都回 **401**(应用侧还要认证),
  而真正免认证的是另一个前缀 ⇒ 整轮白烧。**判定应用白名单只能用应用层响应类别(200/401/404/500)反推,
  绝不用网关放行清单外推**。同理,穿越类变形(`..`、绝对路径、`/etc/` 字样)在网关/风控层就有规则,
  大矩阵硬撞只会换来拦截页或限流 ⇒ **每个想法只试少量代表变体,先确认哪一层拦,再决定是否值得铺开**。
- ★★ **有效通道 = 浏览器当 token 铸造机,Python 当炮台**(本层最省事的正解):
  真浏览器**导航**到目标 URL → 质询 JS 跑完会把 URL 改写为 `<原URL>?timestamp__<rand>=<token>`
  (参数名与 rand 随厂商/会话而变,也见 `refer__<rand>`)。**读 `location.href` 取回它**,
  然后用**裸 `requests` 原样回放这条带 token 的 URL** —— 实测**不需要任何 cookie、连 UA 换掉也不影响**,
  且**数分钟内持续有效**(无短 TTL),回来的就是源站真实业务响应。
  代价是**每个 URL 要一次浏览器导航**(约 5s)铸 token;铸完一轮就能用 Python 高速打同一批 URL。
  ★ **令牌参数名形态**（不要 match 字面量，每次部署会变）：`refer__<数字>`、`md5__<数字>`（XHR 用）、`type__<rand>`、`timestamp__<rand>`;
  **导航令牌与 XHR 令牌共用同一段盐前缀**（如 `2790552d-`）⇒ 可据此判断“多个主机是不是同一个 WAF 实例”，同一实例的页面能互铸令牌。
  ★ **别在业务 bundle 里 grep 令牌名**:令牌由 WAF 脚本铸造，**不在前端业务 JS 里**，0 命中是正常的，
  不代表机制判断错（据此否掉整条路线是浪费）。
- ⚠ **token 与完整 URL 绑定**(路径 + 查询串都要一致):`/` 的 token 打到 `/zzz` 或 `/?a=1` 一律重回质询页。
  ⇒ 批量枚举只能**逐 URL 铸一次**;也**别把「回放 token 无效」写成结论** —— 那几乎总是回放到了另一个 URL 上。
- 质询页 cookie(`acw_tc`/`ssxmod_itna`)**单独搬进 Python 不能直连**;直连的凭据是上面那个 URL token。
- **文档导航本身是最简通道**:`new_tab(url)` + `wait_for_load()` + 读 `document.body.innerText`
  (源站 JSON 被当文档渲染)。**GET 面够用;POST 面在本层打不通(见下条,已实测成型)。**
- ★★ **“质询层只为 GET 签 token”要按配置实测，别当普适定论**:
  默认形态确实是挑战重放永远写成 `location.replace('<原URL>?alchlgref=…%3Frefer__<rand>=<token>')`（一条纯 GET），
  用 CDP `Fetch.continueRequest` 把被挑战的**导航**改写成 POST/自定义头会被降级回 GET（改写循环实测多轮零进展）。
  但**页内 XHR 的 POST 是另一回事**：实测观察到挑战脚本把页内发出的 POST **带着原 body 重放**，
  URL 形如 `POST <原URL>?refer__<rand>=<token>`，CDP 侧看到该 URL 回 200。
  ⚠ **“看到带 token 的 POST URL + 200”不等于通道已通** —— 那 200 可能是挑战页。
  必须用 §3b 首条的 CDP 读回核实 body（含 `renderData` = 仍是挑战页）。
  两个方向都别过头：**既不要因旧结论“POST 不存在”提前收手，也不要因看到一个 200 就宣布打穿。**
  ⇒ 打法固定为：页内发 POST → CDP 读回 body → `renderData` 缺失才是真通道，否则换面。

完整矩阵与代码见 `references/anti-bot-challenge-layer.md`。
