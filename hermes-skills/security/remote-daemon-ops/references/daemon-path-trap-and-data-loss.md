# Daemon 部署路径陷阱 + 数据灾难实录(2026-08 PixBot v7/v8)

## 部署不生效的隐形根因:daemon 实际运行路径 ≠ 上传路径
- `merge_daemon.sh` 写死 `python3 /opt/v6/merger.py`;历次迭代上传到 `/opt/v6/t95306_v6_merger.py` → **daemon 跑旧文件,修复从未生效**。
- 症状:改完代码部署后,行为无变化(旧文件继续每轮覆盖数据);文件 mtime 持续更新但内容逻辑是旧的。
- 排查:①`cat <daemon脚本>` 看真实文件名 ②`ps aux | grep -E '[m]erger'` 看进程命令行 ③确认后上传到正确路径。
- 杀进程:`pkill -9 -f 'merge_daemon'` 只杀 bash 脚本,**杀不到 python 子进程** → 用 `pkill -9 -f '[m]erger.py'` 按 python 文件名杀;杀完 `ps aux | grep -c` 确认归零再重启。
- 验证生效:重启后等一轮,检查新输出文件/新日志特征(`grep -c '新路径' <运行文件>`)。

## 数据灾难:实时汇总覆盖历史全量
- merger 的 write_all_summary 每 5 分钟用 29 个 live 项目重写"全量_企业包件_18列.csv" → 221,661 行历史全量被覆盖成 42 行(81MB→15KB),历史数据只剩 42 行!
- 教训:**实时汇总必须写独立文件名**(实时项目汇总_18列.csv),全量文件单独命名(全量_历史_...),任何按轮次重写的逻辑绝不能碰全量文件。
- 检查:汇总目录 `ls -la`,全量文件 mtime 若持续更新且行数骤降 = 被覆盖;恢复:全量文件改名保留(历史版本还在原文件里时立即改名隔离)。

## 验证脚本自身也可能误导
- 验证时匹配项目名撞上同名重复公告(沈阳82次 08:30 vs 09:30,前者企业 15 家后者 0 家)→ 验证"CSV 生成失败"。用精确 projId 验证,不要用名称匹配。

## 防御加固流程(SSH 强化,防锁死顺序)
密钥登录测试通过 → 才禁密码登录(PermitRootLogin prohibit-password)→ 防火墙(采集机只放主服 IP)→ iptables recent 限速。加固后本机直连采集机被 DROP(设计如此),所有采集机操作改走主服跳板。
