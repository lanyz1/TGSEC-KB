# 硬化管理登录的 oracle 化三诊（admin-auth-oracle-triage）

**一句话**：登录失败文案是**信道**，不是结论。每一次拒绝都在告诉你一件确定的事，把它变成判据再动手。

**触发**：该IP已被封禁 / 账号已锁定请X分钟后再试 / 请输入谷歌验证码 / 登录体要 googleCode /
管理端 401 与 403 混着出 / 代理一半通一半 403 / 后台进不去但接口明显存在。

## 何时用

- 管理端登录面可达，但账号密码 + 2FA 顶着，弱口令短字典打不进
- 同一路径在不同出口上 401/403 乱跳，分不清真封 IP 还是假封禁
- 登录体强制 `googleCode` / `otp` / `captcha`，想知道**口令对不对**而不用真的拿 TOTP
- 想在不惊动锁定的前提下，把后台路由表先摸清

**不要走本卡**（先专卡）：凭据产地扫描走 `admin-credential-hunt`；找后台走 `admin-console-discovery`；
未授权管理 API 整面走 `unauthenticated-admin-api`；纯爆破走 `auth-brute` / `password-spray-lockout-bypass`；
JWT 伪造走 `jwt-bypass-pentest`；验证码识别走 `captcha-ocr`。

## 三诊顺序（阴性才换下一刀）

```text
⓪ 基线     未知路由 ×1 + 必错凭据 ×1（记状态码与原文，后面全靠这两条差分）
① 路由面   404 原生页 vs 401/403 ⇒ 无票枚举后台全部路由
② 封禁面   同路径换出口重放 ⇒ 真 IP 白名单 还是 路由级统一拒绝
③ 口令面   2FA 前置报错顺序 ⇒ 免 TOTP 的口令 oracle
④ 锁定面   故意撞到锁，读倒计时 ⇒ 账号存在性 + 精确解锁时刻 + 每轮配额
⑤ 全阴性   交接泄露面 / 持票人 / 社工内线；禁止写「后台进不去」结案
```

## ① 路由存在性 oracle（Go / gin / echo）

未知路由吐框架原生 `404 page not found`（纯文本、无 JSON 包装），受保护的真实路由吐 `401 {"msg":"未登录"}` 或 `403`。
⇒ **无票也能枚举后台路由表**。做法：

1. 先抓 `/admin/` 外壳（几百字节的 SPA 也算命中）→ 拉 bundle → 正则出 `/admin/xxx` 段 → 得候选集合
2. 逐个 `GET`（不要 POST，避免写副作用），按 `404 page not found` / `401` / `403` 三档分类
3. 401 档 = 有门禁的真接口 ⇒ 后续有票时优先打这批；403 档进入 ② 判定

> 反例警戒：若**所有**路径都回同一个 JSON 或同一块 WAF 挑战页，那是 catch-all，本 oracle 失效，
> 回 `http-signal-false-positive-triage`。**但先做 ①.1 —— 失效时可以反着用，别直接跳过。**

### ①.1 前缀级 401 硬拦截：把 oracle 翻过来用（白名单反推）

有些后台把拦截器挂在**前缀级、路由之前**，于是**连随手编的路径**都回同一句 401：

```
GET /api/admin/user/list             → 401 未能读取到有效 token
GET /api/admin/zzzz_nonexistent_9127 → 401 同上（一字不差）
```

⇒ **零存在性区分度**，按 ① 的正常做法枚举纯属烧量。但**拦截器自己就是 oracle**：
**非 401** 的路径只可能落在**放行白名单**上，而那里躺着的正是**登录 / 回调 / 健康检查**这类必然真实存在的特权端点。

1. 三条基线先分开「未映射」与「被拦截」：
   - 前缀内**假路径** → `401` ⇒ 整个前缀被拦
   - **前缀外**假路径（`/api/zzzz_nonexistent`）→ `400 + 0B` ⇒ **400 = 路径未映射**（网关层）
   - 一个已知公开端点 → `200` ⇒ 传输正常
2. 前缀内外各铺一圈认证类候选（`auth/login`、`login`、`logout`、`token`、`admin/login`、`passport/login`、`signin`），**只记非 401**。
3. 命中后逐条验方法：
   - 同路径 `GET` → `400` 而 `POST` 有响应 ⇒ **映射只注册了 POST**，GET 的 400 是方法不对，**不是不存在**
   - 同族 `auth/logout` / `auth/zzzz` 回 `401` ⇒ 白名单是**精确路径匹配**，不是前缀通配

实测 2026-10：`/api/admin/**` 全域 401，`/api/zzzz` → 400；一圈候选里**只有 `POST /api/admin/auth/login` 穿过**
⇒ 白名单 = `{auth/login}` **一条**。**一个精确路径，就靠「非 401」这一发捞出来的。**

## ② 假封禁辨伪（换出口差分）

「该IP已被封禁」这类文案常是**认证失败共用的兜底**，不是真封了你的 IP。判据只有差分：

| 现象（同一错误凭据、换干净出口） | 判定 |
|---|---|
| `403 该IP已被封禁` → `401 账号或密码错误` | 真有一层 **IP 白名单**，文案可信 |
| 干净出口上：不存在路由 `404`、真实路由仍 `403` | 403 是**路由级中间件统一拒绝**，文案纯装饰；别再烧预算换 IP |
| 所有路径（含随机串）都 403 | 边缘 WAF/封禁页，不是应用层 ⇒ 换层再看 |

**出口分类法（实测有效）**：拿**一个已知错误**的凭据在每个出口上打一发——回 `401` 的记为「干净口」
（已进密码校验），回 `403` 的记为「封禁口」。结果落盘成 `clean_px.json` / `banned_px.json`，
之后一凭据一出口，既摊薄 IP 级限流，也不会把 403 误读成密码错。

## ③ 2FA 前置 = 口令 oracle

登录体要 `googleCode` 时，先看**校验顺序**（这一步是白送的）：

| 提交 | 返回 | 结论 |
|---|---|---|
| 不传 googleCode | `请输入谷歌验证码` | 2FA 校验排在口令校验**之前** |
| 任意 6 位 + 错口令 | `账号或密码错误` | 口令先被判死，TOTP 还没轮到 |
| 任意 6 位 + 对口令 | `验证码错误` | ← **口令已确认**，不需要真 TOTP |

所以「有 2FA」不等于「不能验口令」。但每次尝试都在给锁定计数器 +1 ⇒ 必须接 ④。
真正的 TOTP 拿不到就转：管理员手机号/邮箱泄露面、客服工单骗重置、内线、备份里的 `otp_secret`；
不要试图猜 6 位码（1e6 × 锁定 = 必死）。

### ③.1 三个十秒判据（先做，再决定要不要投入）

1. **空码门 ≠ 用户名 oracle。** 不传 `googleCode` 回「请输入谷歌验证码」时，**换成乱码用户名也得同一句**（实测 `admin'-- -`、随机串全一样）⇒ 这是表单非空校验，跑在查库之前，**不能用来枚举账号**。
2. **类型混淆一枪否掉一整支。** `googleCode` 传 `null` / `0` / `[]` / `{}`：回 `400 参数错误` ⇒ 强类型绑定（Go/gin），这类绕过整支死，不用铺 payload。
3. **持票重放判独立密钥。** 拿一个**合法签发**的低权 JWT（不是伪造的）去打全部 admin 路由：
   - 全部回 `401 登录已失效` ⇒ admin 与业务端**签名密钥不同** ⇒ `role:"admin"` 伪造整条路报废，别再碰 JWT
   - 出现 `403 无权限` ⇒ **同密钥**，只差 role ⇒ 转而找能改 role 的签发点（注册/登录请求体、profile 更新）
   ⚠ 扫后台路由要打**两轮**：空票一轮（查未授权）、持低权票一轮（查鉴权不对称），只打一轮会漏。

### ③.2 密钥可破性 15 分钟判死

别凭手感说「密钥是随机的」。固定流程：

- 纯 Python `multiprocessing` + `hmac` 在 8 核上约 **1M cand/s** ⇒ rockyou 全量 1430 万约 **14 秒**。先跑完再说。
- 再跑一组**目标词变异**（品牌/域名/运营方拼音/框架名 × 大小写 × 2018-2026 × 0-99 × `!@#$`），几千条，秒出。
- 两组全灭 ⇒ 随机密钥，收手。**别再用 `-a 3` 暴力掩码烧几个小时。**

### ③.3 ★字段名未核对前，401 不算结论（本卡最容易翻车的地方）

「账号或密码错误」是最常被误读的一句。实测 2026-10：某 App 登录接口要的字段是 `loginPassword`，
我们发 `password`，服务端按空密码处理 → 稳定 401「账号或密码错误」→ 据此判「回传账号已被冻结」，
**整轮 App 侧测试全建在假阴性上**；换成正确字段，两个账号立刻 200 发 token。

⇒ 打任何登录面前，先从 SPA bundle 抄**调用点的完整 body**（字段名、类型、必填项、以及 `loginType` /
   `deviceCode` / `deviceFingerprint` 这类伴随字段），逐字照抄；只有与浏览器抓包逐字段一致时，401 才能读成「凭据错」。
⇒ 下「账号被冻结 / 已注销 / 被清号」结论前，必须先排除**字段缺失或改名**——这两件事的返回文案常常一模一样。
⇒ `password` / `pwd` / `passwd` / `loginPassword` / `userPwd` 都试一轮；别猜客户端是否先哈希，
   直接读 bundle 里的登录函数（本案 `Login-*.js` 确认是**明文**提交，所以 200+ 次尝试的失败都是真失败）。

### ③.4 口令之后的角色门 = 凭证有效性 oracle（面板不收你 ≠ 密码错）

有些面板**先验口令、再验角色**，两道门回不同文案（实测 2026-10，`daili.*` 代理后台）：

| 提交 | 返回 | 结论 |
|---|---|---|
| 已知好账号 + 对口令 | `500 {"message":"请使用代理号登录"}` | **口令是对的**，卡在角色/账号形态 |
| 同一账号 + 错口令 | `401 账号、密码或验证码错误` | 口令错 |
| 邀请码 / userId 当账号 | `401 同上` | 该形态不是登录账号 |

⇒ 见到「请使用X号登录 / 无权限登录」这类**角色门文案**，先当作「口令已验证」，转去找**正确的账号形态**，
不要回头爆破密码。文案往往直接点名形态（代理号 ≠ 手机号 ≠ 邀请码 ≠ userId），三种各打一发即可定性。

**验证码与口令共用一句文案时（`账号、密码或验证码错误`），先校准 OCR 管道**：
拿一个**已知口令正确**的账号打一发——回角色门文案 ⇒ OCR 正常，后续 401 才算「口令错」；
回同一句 401 ⇒ 分不清是 OCR 还是口令，此时任何「密 码错 / 账号不存在」结论都是假阴性。

### ③.5 校验顺序决定 oracle 能不能用（注册/申请类端点）

想用「已存在标识 + 待测字段」做**无副作用 oracle** 时，先测顺序（两发即可）：

- 已存在手机号 + **有效**邀请码 → `账号已存在`
- 已存在手机号 + **无效**邀请码 → 若**同一句** `账号已存在` ⇒ 存在性检查在前，邀请码 oracle 死
- 若第二发回 `邀请码不存在` ⇒ oracle 成立，可用零写入方式枚举邀请码

⇒ 顺序在前的是「便宜的库查询」时，这类 oracle 基本全灭，别再铺 1e6 枚举（每次都要真建号）。

## ④ 锁定窗口读数

- 国产后台锁号文案常自带倒计时：「登录失败次数过多，账号已锁定，请**18**分钟后再试」
  ⇒ 一次同时拿到 **账号存在性（用户枚举）** 和 **精确解锁时刻**
- 先测配额：常见 5 次 / 30 分钟；命中锁立刻停，把解锁时间写进案卷，按点再战
- 多账号候选（`admin` / `superadmin` / 业务名）**各自独立计数**，可并行，但每号 5 发为上限
- **不存在的用户名永远不会被锁**（连打 3 发仍只回 `账号或密码错误`，无倒计时）⇒ 「没锁」不等于「账号存在」，「被锁」才是存在性的**确认**。代价是把真实账号锁满整个窗口（本案 `admin` 被锁两次、各 23 分钟）⇒ **只用于已怀疑的账号，禁止拿它批量枚举**

### ④.1 429「登录尝试过多」的归属判定（IP 级 vs 账号级）

同一句限流文案，作用域不同打法完全不同。两个差分就能定死：

| 实验 | 结果 | 判定 |
|---|---|---|
| 同 IP、**换账号**重放 | 仍 429 | 不是纯账号级（多半 IP 级或叠加） |
| **换出口**（WARP `socks5h://127.0.0.1:40000`）、同账号重放 | 恢复 200 | **IP 级** ⇒ 每口一份配额，可轮换 |
| 换出口仍 429 | 账号级 | 只能等窗口/换账号，别烧出口 |

实测 2026-10：`登录尝试过多，请 900 秒后重试` 直连 IP 数发即锁，换 WARP 出口立刻恢复正常 ⇒ 代理后台可无限次尝试。

⚠ 先确认**登录路径本身存在**：旧案卷里记的 `/v1/login/account` 实测 404，真实口是 `/v1/login`；
把 404 读成「被限流」会让整轮排查跑偏。路径一律以**当前 bundle 的调用点**为准。

## ⑤ 全阴性时交接（不是结案）

按顺序换面：泄露面（`.env` / 日志 / heapdump / JS 硬编码）→ 持票人（客服/代理/测试号）→
写入面（上传保留扩展名的同源 XSS，等管理员点开）→ 兄弟端点鉴权不对称（`/api/v1` vs `/api/internal`）。

## ⑥ 恒 500 且与入参无关 = 后端模块没上线（不是口令问题，停手）

白名单登录口对**任何** body 都回同一句 `{"code":500,"msg":"服务暂时不可用，请稍后重试"}`：
表单 / 空 body / 纯垃圾字符 / 合法 AES 密文 **一字不差**；而 `Content-Type: application/json` → `400`。

⇒ 异常发生在**读完 body 内容之前**，与凭据、加密密钥、包络格式**全都无关**。

**判据：三种不同形态的 body 回同一句 500 ⇒ 停止换包络、换密钥、爆破凭据。**
正经的登录失败必然区分「用户不存在 / 密码错误 / 验证码错误」（本卡 ③.3 就是靠这个读口令对错的）；
**一字不差 = 依赖的 Bean/服务没部署 = 模块未完整上线，不是策略层能绕的。**
记作「入口存在、后端未上线」,直接进 ⑤ 换面,不要在这里加字典。

**多品牌矩阵同症状 ⇒ 别再逐品牌重复投包**。实测 2026-10:同平台 10 品牌,6 个挂了 admin
(`91dy/91kb/91pk/mfcg/pzcm/qw`) 登录全返同一句 500,另 4 个 (`91md/91tx/dycm/gdsp`) admin 路径直接 404。
一个品牌定性即可推定同版本集群全灭;把品牌名 × 路径跑成矩阵只是为了**确认配额边界**,不是为了多试几次口令。

**边缘 400 与应用 400 分开记**:`400 + 0B` 且响应头带 `Server: ESA` / `Set-Cookie: acw_tc=...` /
`EagleId` ⇒ 边缘 WAF 在读完 body 前就掉了,**不代表路径不存在**,也不代表参数错;
同路径撕掉多余头(如 `X-Encrypt`)再发一次才能拿到应用层真实读数。

### ⑥.1 Content-Type 本身是判层信号

同一路径换 Content-Type 读数分档，**别把 CT-400 当成「路径不存在」**：

| 形态 | 读数 | 判读 |
|---|---|---|
| `application/json` | `400 + 0B` | **应用只收 form/raw**，不是不存在 |
| form / raw / octet-stream | `200 + 应用 JSON` | 正常口径 |
| 空 body | 部分应用 `400` | 单独记第三态，别当阴性 |

⇒ 批量扫这类应用**统一用 form 编码发**；JSON 一发就把整批探针变成假阴性。

## 红线

- 发现 oracle 不等于可以放大字典：仍在锁定配额内，**低频可停**，命中锁立即写复工条件
- 上传/写入类验证只证明行为（重命名、扩展名保留），不落持久化后门
- 失败文案里出现的手机号/邮箱/内网地址只记不追；跨用户改密只用平台自带测试号
