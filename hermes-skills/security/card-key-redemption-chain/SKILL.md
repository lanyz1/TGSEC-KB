# 卡密下游兑换链（卡密 → 兑换站 → JSON/母号 → 面板）

发卡平台（云猫寄售 / jingsoft 系、独角数卡、Toka、号商商城…）的商家只是**卡密零售端**。同一张卡密的真实价值发生在**商家自有的兑换站/激活站**：

`卡密 → 兑换站 → 余额/额度 · 母号账号 · 账号 auth JSON → 导入自己的面板`

用户问「库存卡密在哪里兑换 / 这个怎么兑 / 帮我操作一下」时，答案永远不是发卡平台本身。**交付卡密时必须同时给出对照表：哪类卡密 → 去哪个站 → 换到的是什么。**只给码不给站 = 没交付完。

## 1. 定位兑换站（成本从低到高，按序做）
1. **批量 grep 全平台商品/店铺描述**：对已拖回的店铺/商品 JSON·JSONL 全量跑 `兑换地址|兑换网站|兑换入口|中转站|卡密兑换|卡网`，正则抽 `https?://...`，**按出现次数聚合** → 一次拿到全站兑换站清单；被多店引用的 URL = 上游主站。
2. **读商品描述全文，不要截断**：末句常一句定音（「直接卡网卡密兑换，给json」「默认发sub的json」「兑换地址：<url>」「可下载 sub2/cpa 格式 json」）。截断恰好丢掉这一句，直接决定能不能答上用户。
3. **抓商家自有文档子域**：`docx.<merchant-domain>` / `doc.<merchant-domain>` 常挂着「零基础图文教程」，把 注册→登录→兑换→建密钥→导入 的官方步骤写全，是权威流程来源；搜 `"<merchant-domain>" 兑换` 常直接命中。
4. **扫兑换站 HTML+JS 取码格式**：抓根页 + 同源 script，正则找 placeholder 与校验文案（`XXXX-XXXX-XXXX-XXXX`、「格式不对」、「前缀」/`prefix`）。**先确认码格式再输码**。

## 2. 按码前缀判归属（选站前必做）
- `TEAM-XXXXXXXX` / `PLUS-XXXXXXXX` / `TEAM5X-XXXXXXXX` → 只认母号站，输到别处报「格式不对」。
- `XXXX-XXXX-XXXX-XXXX`（32 位 hex 四组）= sub2api 面板原生兑换码。
- 其他自定前缀（如 `CPA-`+5 组 hex）= **上游卡网的激活码**，必须回上游激活站兑。

三族站点与行为对照见 `references/redemption-site-families.md`。

## 3. 铁律
- **兑换码一码一用、不可恢复**：演示只从自己已掌握的库存取 **1** 张；有「已兑换回查 / 质保查询」入口就先回查，不盲兑。
- **对兑换站只做只读侦察**（首页 / 同源 JS / placeholder / 官方教程），不当渗透对象、不拿别家码试错。
- **硬卡点如实交底，不烧时间**：注册白名单、必须真实邮箱、必须手机绑定这类服务端强校验，试 1-2 个变体确认是服务端判定后立即停手，直接告知用户「需要 <具体东西> 才能继续」，不要堆伪装域/临时邮箱轮换。
- **演示要给出可粘贴级步骤**：带 URL、带码格式、带导入工具的落点（sub2api/CPA/Cockpit/CC Switch 等），不写「大致如此」。
- 拿不出真实可兑的码时，明确说明卡在哪一环、缺什么，不用推测当结论。

## 4. 导入面板（链条后半段）
- 兑换站常同时给 **sub** 与 **cpa** 两种格式 JSON；格式不匹配时先过格式转换器（本地浏览器解析、不上传 token），再导入目标面板。
- 导入成功后验证点是面板里的窗口：常见 **5h 窗口 + 7d（周限）窗口**，额度按码档位随机。
- 额度网关型兑换站（New API / Sub2API 系）只给余额或订阅，**不发 JSON** → 要 auth JSON 只能回上游激活站。
