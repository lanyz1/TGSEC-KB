# 兑换站家族 / 码格式 / 行为对照

## 家族表
| 家族 | 行为 | 码格式样例 | 备注 |
|---|---|---|---|
| 母号 / 邀请站 | 填邮箱+码 → 发母号账号，或把该邮箱拉进 Team 空间（发邀请邮件） | `TEAM-XXXXXXXX` / `PLUS-XXXXXXXX` / `TEAM5X-XXXXXXXX` / `XXXX-XXXX-XXXX-XXXX` | 通常无需登录、一码一用；常带「取号数量」「库存」「质保/换号」「合并兑换码→额度卡」子功能 |
| JSON 下载站 | 卡密 → 下载 sub / cpa 格式 auth JSON | 各家自定前缀 | 商品描述里的「下载 sub2/cpa 格式 json」指的就是这类 |
| 额度网关（New API / Sub2API 系） | 卡密 → 充余额 / 开订阅（**不发 JSON**） | sub2api 原生 = 32 位 hex 四组 | 数量最多；面板类目标本身也是渗透面 |

## 判站套路
- 同一 URL 被**多家店**的商品描述引用 → 上游主站，优先级最高。
- 描述里出现「卡网」二字 = 交易链上游那张卡网，不是当前发卡平台。
- 三个不同前缀的码分属三个站时，逐一用 1 张码验证格式，**不要一码多站试**（一码一用，试错即报废）。
- 兑换站的码校验通常在服务端：placeholder 只提示格式，不代表前端能拦；格式对但码无效会返回「兑换码不存在/已使用」。

## 与发卡平台的接口关系
发卡平台自身通常**没有兑换路由**（挖遍买家端 / 商家端 JS 也找不到）——这是判据，不是失败信号：兑换功能在商家自有站。
