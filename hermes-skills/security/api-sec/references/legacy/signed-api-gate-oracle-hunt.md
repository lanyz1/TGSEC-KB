# 签名闸 / 参数闸 API:预言机优先法

适用:目标 API 强制携带你算不出的 `sign` / `signature` / `nonce` / `timestamp`(密钥在 native/加固包、服务端 HMAC、或根本不下发)。目标是**拿会话/实例数据**,不是还原算法本身。

## §0 预检:先校服务端时钟(★在判「签名失效/nonce 已消费/TTL 过期」之前)
本机钟偏会让**正确的算法与密钥**恒被判失败,和「签名被作用域绑定」「nonce 一次性」表现得一模一样。
一分钟做掉:`Date` 响应头必须用**出网 HTTP 库**读(页内 fetch 因 CORS 只暴露 safelisted 头,`Date` 恒 `null`;被 WAF 挑战/403 的响应也一样带 `Date`)。
```python
skew = email.utils.parsedate_to_datetime(r.headers["date"]).timestamp() - time.time()  # 本机快为正
# 生成/校验时间戳统一用 time.time() + skew; 先扫 delta ∈ {-1,0,1,2}
# 30s/秒级窗口下「时区」不是有效假设 => 不要一上来扫 ±960
```
多打几台主机(含一个无关大站)比 `Date`,才能判定是本机偏还是目标偏。
> 完整诊断序(TOTP/OTP 同步、字段名以 bundle 为准、两步 bind→enable、尝试计数器纪律)见 `time-sensitive-credential-diagnostics`。

## 决策顺序(严格按序,别跳步)
1. **存在性绕过 > 算法还原** — 闸门只校验字段是否存在是最常见的实现缺陷。
2. **签名预言机 > 爆破 HMAC** — 服务端有「替你签名」的端点时,签名不再是障碍。
3. **兄弟前端 > 死磕签名** — 同一业务往往有多套前端(H5 / 小程序 / App / v2),其中一套的闸更松。同产品的**平行部署栈**(其他 TLD / 子域 / 旧环境)也可能跑旧版代码,签名档位与校验更松 ⇒ 逐栈差分验证,别只钉在主栈上。
4. **缺口收敛后只做值枚举** — 所有可写面返回同一句鉴权错时,缺口是「一个实例 ID」,横向扩面是浪费。

## 1. 先判闸类型(一次请求定路线)
| 响应 | 含义 | 立刻做 |
|---|---|---|
| `101020 未获得签名，拒绝处理` / `验签参数不可为空` | 只查字段存在性 | JSON body 或表单加 `sign=1` 即进业务层 |
| `101010 验签失败` | **真值校验** | 转第 3、4 节,不打字典 |
| `缺少参数，名称：X，类型：Y`(常 `code 100011`) | 参数预言机 | 逐参喂,见第 2 节 |
| `{com.<厂>.<模块>.validation.<字段>.NotBlank.message}`(常 `code 300400`) | Bean Validation 预言机,**泄全限定字段名** | 逐参喂,比 swagger 权威 |
| `211057 token不存在!` / `未登录` / `登录已过期` | 闸已过,**只剩会话** | 停手扩面,转第 5 节的值枚举 |

**铸票类闸(JWT 自签)先做三发差分,判「验不验签 + 有没有登记簿」**(省下一整轮无效爆破):
- A=结构完备 claims+真钥;B=同 claims+错钥;C=空/残缺 claims —— 同一端点各一发。
- A、B 回同一句话(如都回 `token已失效`)而 C 回另一句(如 `解析失败`)⇒ 签名根本不验,闸门 = claims 结构 + 服务端**有状态登记簿** ⇒ **该主体**自铸票必败(掌握密钥也无用),爆破/还原签名密钥是纯无效功;方向改:找**登记在册的真实 (主体id, secret) 对**(刷新流 / 配置载体 / 泄漏库)或借活票(审计日志 / 浏览器会话)。
- A、B 文案不同 ⇒ 签名真在验,再走密钥路线 —— **但「验签 + 有登记簿」不等于伪造路已死:登记簿比对常被特权身份短路**(见下条)。
- **★★ 已验出「验签 + 在册登记簿」时,改判据为「换身份」而不是「换密钥」**:同一把**已验证正确**的签名钥,签**普通主体**被登记簿挡(「不在册」档,如 `TokenNotExistError`),签**特权主体**却直接放行(实测 `errCode:0`)。⇒ **「自铸票必败」只对普通主体成立,严禁写成「该服务不可伪造」**;把结论降级为「非特权主体不可伪造」,下一步是拿**出厂默认特权名的小列表**(如 `imAdmin` / `admin` / `chatAdmin`,**不是大字典**)逐个试签,一个命中即完全接管。机制:特权判定写在在册比对**之前**。
  **★ 错误码阶梯就是校验顺序剖面**:`signature is invalid`(钥错)→ `TokenNotExistError`(验签过、票不在册)→ `… is not admin userID`(真票、非特权)。**码停在「不在册」而特权名返成功 ⇒ 特权判定在在册比对之前**;看清这条顺序,比再爆一轮密钥便宜一个数量级。
- **★ 扫描命中判定严禁用「响应里不含已知错误串」**:该写法把**每一档不同错误**都计成命中(实测一次「80 命中」里绝大多数是 `TokenNotExistError`,真命中仅 1 条,整轮判读作废)。正确做法 = 先**枚举该服务的完整错误码阶梯**(含成功码,如 `errCode:0`),命中只认**成功码或明确的下一档业务码**,其余按档归位并**分档计数** —— 分档计数本身就是闸门结构的证据。
- **★ 判「签名覆盖 payload 还是只覆盖固定串」必须用『保签名改载荷』,不能用『换错密钥』**:错密钥在任何实现下都失败,证明不了验签存在。正确的一对 = (i) **改 payload 里某个 claim、原样保留 signature** + (ii) **保留 payload、改 signature 一个字符**;外加 (iii) `alg:none`/算法降级。三发都拒且错码同档 ⇒ 签名真在验且**覆盖 payload**(伪造票路线关闭,只剩取真票或取签发密钥);只有 (ii) 拒而 (i) 放行 ⇒ 签名只覆盖 header/固定串 ⇒ **载荷可自由改 = 越权面**。
- **★ 闸门文案在目标二进制里 0 命中 ⇒ 该文案来自 DB/i18n 配置,不是漏挖**:先确认是否为原生串(邻域是 TLS/crypto/MySQL 模板即噪音),0 命中就停止在 strings 里找产出者,改搜**判定键名**(`minVersion` / `xxxDisabled` 这类配置键)并回线上实测。**「文案不在二进制」≠「判定逻辑不在二进制」**,两者要分开找。
- 文案分档:`解析失败`=结构层、`已失效/不存在`=状态层、`签名验证失败`=签名层;**同族错误的后缀数字(-1/-2)变化 = 到了不同校验档位**,作为分层信号采集,别当同一错误忽略。
- 有服务端二进制(如未剥离 Go 服务)时,把分层从文案猜测升级为**分支级证据**:错误串 xref 找到发射函数、反汇编读分支条件与中间件调用图(中间件含 Redis/DAO 调用 = 有状态登记簿),配方见 `go-service-binary-dissection`。

**同主机多路由的中间件排序不一致——用「全路由 × 三档凭据」矩阵扫「签名在前」的口**:
- 同一 host 上并存:有的路由先查签名(无签名回 `签名验证失败-N`),有的直接查 token(回 `token解析失败-N`)。
- **仅凭 App/平台级签名即返业务数据(ErrCode:0 且带字段)的路由 = 最高价值裂缝**:高级别凭据可能替代用户凭据直入业务层 ⇒ 逐参数试用户标识(uid / userId / memberId / 第三方 uid 等),并用响应字段核对拿到的是谁的数据。
- 签名在前且报「必填参数缺失」= 闸已过(错误从『签名失败 / 裸 403』推进到『业务字段错』就是进业务层的最强正证据,别再回头怀疑签名),补参即入;按报错字段名迭代,方法见 `api-param-name-discovery`。
- **403 墙判「端点族级」还是「App 级」必须带对照路由**:同一套有效凭据再打一条墙外的普通业务路由——它进业务逻辑(回字段校验错)⇒ `access denied` 只是**那一个端点族**(如第三方集成族)的授权墙,不是 App/IP 级;全部路由同 403 才是 App 级。无对照就写「IP 白名单」=凭空假设,会让整轮烧在换源 IP 上。
- **X-Api-Key 类应用凭据的两种拒态分读**(先在同 harness 拿「已知可用 key vs 乱造 key」对照再采信):`签名验证失败` = 服务端查不到该 key 对应 secret(app 认不出,换 key 才有意义);`access denied`/仅单端点族 403 = app 已认出但无该族授权(换 key 是无效功,换端点族或趁该 app 有权限的面)。

## 2. 逐参喂参配方(报错即下一个参数名)
一个参数一次,读报错里的 `名称：X，类型：Y` 再补 X,直到进业务层。类型是 `long/String/枚举` 时按报错里的类型给真值。
```bash
for q in '' '?timestamp=1790000000000' '?timestamp=1790000000000&nonce=1'; do
  curl -sk --path-as-is -o /tmp/b -w "%{http_code}|%{size_download} " "https://<host><path>$q"; cat /tmp/b; echo
done
# 枚举型参数穷举合法字面量:?type=1..8 / ?channel=<平台代号> / ?fundCode=<大写代号>
```
- **参数命名风格会互相泄漏**:同一厂商混用 `orderNo` / `order-no` / `order_no`,报错给的才是真的。
- 报错里的**顺序就是校验顺序**,也是服务端 DTO 字段顺序 → 据此推断还有哪些未暴露参数。

## 3. 找签名预言机(★ 最高杠杆)
命名族:`re-route` / `pre-sign` / `clientQsPreSign` / `signature` / `getSign` / `signUrl` / `unionUrl` 类「给你个链接」的端点。
- 判据:`GET <端点>` 返回体里带 `?timestamp=<ms>&nonce=<hex>&signature=<hex>` 的**完整 URL**。
- **改请求参数看签名值是否变化**:变 ⇒ 签名覆盖该参数 ⇒ 载荷由你控制(可换实例 ID 生成任意用户的签名链接);不变 ⇒ 签名只覆盖时间/nonce。
- `GET` 该端点报 `缺少参数，名称：timestamp，类型：long` = 活预言机入口,补参后即可取签名。
- 取到后**按返回的路径直接请求**,别改路径:签名通常**路径绑定**,换端点必 `链接已失效/签名失败`,但**同路径换实例 ID 有效**。
- **nonce 是一次性还是可复用必须实测,别预设**:同一实现可能只消费一次,也可能在 TTL 内**可跳端点反复用**(实测某族一枚三元组连打 34 个不同端点全部被接受)⇒ 判「nonce 已消费/签名失效」前先重取一枚对照;长扫描循环一律**每 N 次重铸**,否则 TTL 到期后整批假阴性、整轮误判。
- **对照实验必做(用来区分「签名过期」与「作用域不符」)**:每铸一个三元组,先拿**它本来的消费端**(签名 URL 里那条路径,如 `render/order/<id>`)打一发——返回 302/200 证明该三元组当下有效;再用**同一**三元组打目标端点。对照通过而目标回 `链接已失效` ⇒ **是路径/流程作用域绑定,不是过期,也不是预言机坏了** ⇒ 立刻停手,不再跨端点复用同一个三元组(一端点一铸一用);若仍不通,缺口就不是签名,是**实例 ID**,转 §5。没有对照就下「预言机无效」的结论会白丢整条链。
- **别被端点名骗**:`pre-sign` / `signature` 这类名字的端点**自己也要 nonce + signature**(回 `缺少参数，名称：nonce`)⇒ 它们是**验签方/流程中间站,不是铸造器**。判据只有一条:返回体里带完整 `?timestamp=..&nonce=..&signature=..` URL 的才是铸造器(`re-route` 类)。同一个名字族里既有铸造器也有验签方,逐个实测,别按名字归类。
- **同主机上第二套命名空间常带更松的闸**:同一 IP 上出现不同错误信封(英文 `Method [GET] not allowed, allowed methods [POST]` / `Missing parameter, name: x, type: Long`,而非中文 `缺少参数`)即**另一个上游**,其 POST 路由往往**完全免鉴权**;新的顶级前缀(如 `/uranus-api/**`)要从兄弟 SPA 的 `app.js` 里抽,别只抽 `^/api/`。

- **★ 先确认凭据的「载体」,再判作用域**:同一个闸可能从 **JSON body** 读 `timestamp/nonce/signature`(独立命名空间常见),只放 query 会回「不能为空」,或直接回 `链接已失效`被你读成作用域不符 ⇒ **一处放错,整轮作用域结论作废**。三种载体(query / form / JSON body)各投一次:回「不能为空」= 载体错,回「失效」= 真无效。
  **★ 同一必填报错在全部候选键名 × 该载体下都不消失 ⇒ 判载体/键名族错,别再扩键名**:键名三系(camel `userId` / snake `user_id` / 缩写 `uid`)全投后仍无变化即为信号;反之 `<字段>不能为空` 是**正向 oracle** —— 它同时证明①该路由已注册②该字段名权威(required 校验在 handler 前),别当噪音过滤。且**相邻端点采纳的键名可能相反**(实测 A 端认 `userId` 忽略 `uid`、同族 B 端认 `uid`)⇒ 键名命中只能逐端点判,不能按族推。
- **★ 作用域地图用「一枚有三元组全量投递」一次拿到**:拿一枚已验证有效的三元组,按正确载体投给该命名空间**全部端点**,三元分类:`业务不存在/进件不存在/试算流水号不存在` = **闸已过(同作用域)**、`链接已失效` = 另一作用域、`不能为空` = 参数名/载体不对。比逐个猜快一个数量级,而且**吃签清单本身就是「只差一个实例 ID」的可用面清单**(实测 100 条中 34 条吃签)。
- **★ 铸造器改不了作用域**:给它塞 `path`/`route`/`type` 类参数想换作用域——**被忽略**(回 URL 里的路径不变);把目标路径塞进它会插值的 ID(穿越)→ 报错/500。⇒ 作用域只由铸造器自身决定,换作用域只能去找**另一个**铸造器。
- **★ 网关的类型绑定会挡在业务层之前**:`Parameter type mismatch, name: template-id, required type: Long`(常 `code 100012`)⇒ SSTI/穿越串(`{{7*7}}`、`../`)根本到不了 sink,**看到这类报错就换面,不要继续调 payload**;这也解释了「明明有服务端渲染器却没有 SSTI」。
- **★ 自己签不出来时,先用「建一张最小额未支付单」拿一对 (明文参数串, sign) 作离线起点**:支付/下单跳转页常把完整参数与签名一起回吐(`action` 真实网关域名、`pid`、`sign_type`、`money/out_trade_no/notify_url/return_url/type` 明文 + `sign`)⇒ 有已知明文样本才能离线验证密钥假设与编码细节(**中文参数是否 urlencode 会整体改变签名串**)。**建单属可接受的写操作**(未支付待付单、零资金变动、绝不付款);其余破坏性写一律不做。
- **★ 真实网关域名以「资金流出点」为准,不以品牌域名/兄弟域名为准**:同一厂商常有多个网关实例,`action` 指向的那个才是钱的去处;拿同厂其他域名当家开会白打一整轮。⇒ **从已授权站的资金流里新发现的网关域名,属于新目标,需单独确认一次授权**。

### ★ 上游供应商 HMAC API(密钥在下游客户手里时)

**第一步永远是把契约拿全,不是去猜算法**:这类「分销/供货 API」主机上通常同时挂着框架自描述文件 —— `GET /openapi.json`(path × method 全表 + 参数名)、`GET /docs`(**人可读文档常直接写出签名字典序拼接公式、时间戳/nonce 窗口、限流额度、产物保留天数**)。文档写着「API 客户由运营总后台人工开通」也照样拉:它是权威契约来源,比逆向省一轮。⚠ 同一主机可能对**客户端指纹**敏感:`curl` 默认 UA 吃到挑战页(1xx 字节 HTML)而 `python urllib`/浏览器 UA 直接 200 ⇒ 拿到小体积 HTML 先换 UA 重发,别写成「文档受保护」。
- **文档里的 callback 验签规范是「它对你的出站调用」**(校验它推给你的通知),**不是入站鉴权**;别把它当攻击面。
- **格式层 oracle 先于密钥层**:短键/乱写键回 `X-Api-Sign format is invalid` / `key format is invalid` = 服务端**先校验签名格式、再查密钥表**。要拿「密钥是否存在」的 oracle,必须先按文档算出**格式合法**的签(定长 hex)—— 否则你测的永远是格式层。分档:`format invalid` = 格式层、`sign invalid` = 密钥/签名层、`app key not found` = 键不存在 ⇒ 键名存在性可枚举,但**拿到存在性也进不去**(无 secret 造不出合法签)。
- **键名可枚举 ⇒ 仅当键名是人工命名的短串时才值得跑靶向小列表**;随机长串直接止损。
- **★ 免密钥触达上游的唯一读面 = 下游付费客户自己的后端**:客户服务端会用自己的 key 调上游,且常把你给的路径参数**原样拼进上游 URL**。判据(一条对照即可):**发一个肯定不存在的 id,回的是上游的错误体格式**(如 FastAPI `{"detail":"..."}`)而非本应用文案 ⇒ 参数透传 + 客户就是签名代理 ⇒ 可借它反推上游契约/错误语义、并试 `../` 穿越触达上游其它端点(含下载类)。
  ⚠ **穿越在 Spring 目标上从入口就死**:`StrictHttpFirewall` 拒 `%2f`/`%5c`/双重编码(400,body 回显**未解码** path),浏览器又会把 `%2e%2e/` 归一化 ⇒ 别烧编码变体。此形态的价值在**透传证明与契约**,不在接管。
- **★ 终局判据(该收线时收线)**:契约+公式+格式 oracle 全拿到,而密钥「在下游服务端 / 总后台人工签发」⇒ 纯技术面的密钥路已封;再往上只剩 ① 打穿下游客户自己的后端(拿它的 key)② 真下单一笔(资金写操作,须用户点头)。把这两条写清即可,**不要回头再枚举键名或换编码**。

## 4. 兄弟前端改判(签名打不动时的战略转向)
- 一套前端的登录链在 API 主机上**全 404** ⇒ 该前端有独立后端,**是另一台主机**,不是路径写错。用候选域名族探测定位(前缀方向:`al-`、`api-`、`mobile-`、`-h5`、`h5-`、`wap-`、`applet-`)。
- 找到后先重跑登录链:若同业务的另一套 API(`/api/oauth/*`、`/api/v2/*`)免签,直接在该面上拿会话,回头再用会话打原来的签名面。
- **多套 SPA 并存**(`/h5/` 与 `/h5-v2/` 是两套不同应用,各有自己的 app.js)。权威契约 = 各自 `js/app.*.js` 里的 route 表 + **API 常量对象**;从里面能一次抽出几百条路径(含 `?` 后的参数名)。
- **302 的 Location 会暴露新应用**:某端点把你 302 到 `/h5-v2/<route>?<参数>` ⇒ 该 base 是新前端,立刻拉它的 `index.html` → app.js → 重抽 API 常量。
- 抽取命令(先落盘再 grep,别 inline):
```bash
curl -sk -o /root/t/app.js "https://<host>/<base>/js/app.<hash>.js"
grep -o 'prototype\.[A-Za-z0-9_]*=function([^)]*)' /root/t/app.js | head -60   # 方法签名=契约
grep -o '"/[a-zA-Z0-9/_{}.-]*"' /root/t/app.js | sort -u | head -200        # API 常量
```

## 5. 缺口收敛:同一句鉴权错 = 只剩一个实例 ID
- 所有写面(上传/落盘/提交)都回同一句鉴权错 ⇒ **不要再找新端点**,改为枚举那个能解锁一切的实例值。
- **免费存在性预言机**(无鉴权、无签名、响应区分存在与否):`orders?orderNo=X → 进件不存在`、`verify{userId} → 会员N不存在`、`getcontract?order-no=X`、`getXxxByCustId`。响应带格式化数字(`会员1,000不存在`)= 服务端真读了你给的值。
- 值从哪来(并行三路):① 未鉴权的 CRUD 表端点直接读;② 签名预言机生成带真实实例 ID 的链接;③ 短信/验证码链中的手机号或用户 ID 字段。
- 短信链的字段名与顺序全靠报错驱动:`{phoneNo}` → 再要 `{orderNo|applyNo}` → 再要 `{smsCode}`;**先试固定测试码(123456/888888/000000)再谈爆破**。
- **★ 缺凭据时的「ID 池测绘」形态**:同一端点只补唯一必填 ID 而不给密钥,服务端回**两句不同文案**即构成零凭据存在性 oracle —— 例:`api.php?act=query&pid=N` 回 `商户ID不存在`(无) vs `商户密钥错误`(**存在**,只差密钥)。此类 oracle 可**全量测绘 ID 池**(连续段往往密集命中),先拿到真实 ID 列表再谈任何爆破与靶向,否则爆破没有靶。
- **★ 权限封顶的判据**:同一端点换多个取值(如 `x.php?mod=user|site|order|...`)回**完全相同字节数的同一个页面** ⇒ 该参数无效 / 该身份无此权限,**不是「还有没探到的取值」**;停止枚举该参数,改换身份或换面。
- **★ 读『他人数据』的身份参数:全零/默认载荷 ≠「目标余额为 0」**。判据 = 补一组**随机/不存在 ID 对照**:目标ID 与随机ID 载荷逐字节一致 ⇒ ID 参数被忽略(handler 只认会话身份)——带自身会话时它返回的其实是**你自己**的账号数据;不带会话的 app 上下文则可能恒全零。⇒ 先补对照、再用响应字段核对结果归属,别把「参数没生效」写成「目标为 0」(与 `*ForThirdParty` 标定同一机制的常规端点版)。

- **★ `*ForThirdParty` 端点族 = 免用户 token 的神谕候选**:规格/命名里含 `ForThirdParty` 的口常为第三方集成面,其中部分**不校验用户 token**、按标识参数直接查库。**先标定再采信**:拿**已知真实标本**与**确不存在标本**各打一发——真标本返真实行、假标本返全零/默认 ⇒ 判别神谕成立,可枚举、可校验;**两者同返同一默认** ⇒ 两种解释先分清:① 该实例是桩/测试部署;② **ID 参数被忽略、只按会话身份作答**(带自身会话时载荷 = 你自己账号的数据)⇒ 换栈/换 ID 皆无效功,改换能代表目标身份的凭据或换读链族。
- **★★ 同族内必须逐端点做三值差分,严禁按族推广结论**:同一命名族(资产族 / `*ForThirdParty` / `getUser*`)里,**端点 A 丢弃 `uid` 而端点 B 认 `uid` 并返回目标数据**是常见的共存形态。做法 = 每个端点各取三发(**不带参数 / 目标值 / 随机垃圾值**),并核对响应体里**回述的对象标识字段**(`uid`/`userID`/`thirdPartyUserId`)是否等于你投进去的值。⇒「族内某个端点丢弃参数」只能写「**该端点**无越权读路径」,写成「该族无越权」会被同族兄弟端点整体推翻。
- **★ 免鉴权配置响应 = 标本库**:`getConfig` 族常泄露真实账号 id / 审核账号 / 样例主键——拿到就登记,后面一切神谕标定与差分实验都用它们当「已知存在」正样本。

## 6. 挑战值/随机数往往在 cookie,不在响应体
- 端点索要 `requestNo` / `nonce` / `captchaId` 而响应体里找不到该字段 ⇒ 读 `set-cookie`。
- 常见形态:`X-nonce=<uuid>` + `X-nonce.sig=<HMAC>` 签名 cookie 对(例:`sig-captcha-nonce` / `.sig`)。把值原样回填为请求参数即通过 —— 这是服务端签发的,无需你计算。

## 7. 客户端签名还原(App/native 侧)—— 静态优先
前面几节假设密钥拿不到。**若手上有 APK,先花 10 分钟确认「能不能纯静态拿」,再决定要不要上运行时**:
1. `readelf -sW lib*.so | grep Java_` —— `Java_<pkg>_<Class>_<method>` **明文导出**就基本赢了(加固壳常只保护 dex,不动 `.so` 符号)。
2. `objdump -d --start-address=..-stop-address=..` 看返回路径:认 `NewStringUTF`(JNIEnv 表 offset **1336 = index 167**)+ 其前的 `adrp/add` 串引用。
3. 串在 `.rodata` ⇒ **该段 VA == 文件偏移**,直接 `python3 -c "print(open(f,'rb').read()[A:B].hex())"` dump;多段短串的**拼接顺序 = append 调用顺序**。
4. 第二盐常是 **APK 签名证书 RSA 模数**(防重打包):`.so` 里常藏整份 X.509 DER 的 hex 串,或从 `META-INF/*.RSA` 用 `openssl pkcs7 -inform DER -print_certs` 取。
5. jadx 侧找签名函数:**注解名被压成单字母**(`@GET→@f` `@POST→@o` `@Headers→@k` `@Body→@y`),`grep '@GET('` 恒空;用 `grep -rhno '@f("/[^"]*"'` 拉全部路径。

典型形态:`sign = md5( md5(按 key 排序拼接的参数值 + 密钥源) + 证书模数hex )` —— **盐在哪一层很重要**:native/SP 密钥常在内层,APK 证书模数在外层(搞反则全错)。服务端只用**你发来的参数**重算 ⇒ 设备真实值(OS 版本/渠道)不重要,自造一组自洽值即可。

⚠ 未登录签名还原后,还差**一个路由该族的活宿主**才算打通;两者都拿到才是「可伪造」。**没在活 handler 上做过 A/B 对照就不要声称签名可用。**

**★ dex / Retrofit 侧(Android 原生壳)**:`.so` 静态优先之外,签名与请求契约常在 dex。① 按**类名族 grep** 锁定签名层(`*SignatureHelper` / `*Signature` / `*Interceptor` / `*ApiClient` / `*Signer`),dump 它的 `const-string` 得**头名与签名消息模板**(实测形态:`X-Timestamp`/`X-Nonce`/`X-Signature`;另有 `ACCESS-KEY`/`ACCESS-SIGN`/`ACCESS-TIMESTAMP`/`ACCESS-NONCE` 的 ts+method+path+body 族);请求头名一律以**拦截器类**为准,不扫。② Retrofit 接口方法 `code_off == 0`(无字节码)⇒ 真路径只在**注解**里,`@Body` 参数多为 `Lokhttp3/N;`(手工 RequestBody)⇒ 字段名必须 xref 调用方的 `const-string`,枚举字段名必全败(踩过一整轮)。③ 无 jadx 时用纯 Python struct 解析 DEX:见 `apk-reverse` 第 2.5 步与其 `scripts/dex_struct_extract.py`(串表是 MUTF-8 长度前缀,`strings`/行正则不可用)。

**★★ 密钥源若是「客户端自带票据里的一个声明」⇒ 伪造票据就等于自带密钥(优先于一切公式爆破)**:实测签名类从所携 token 的 **JWT claim** 读 HMAC 密钥(如 `user_secret` / `userSecret`,请求头 `Authorization: Bearer ` 里的 Bearer 亦取自该 claim),并有 `... parse fail` 风格解析文案。⇒ 一旦已握有该 token 的**签发密钥**,无需还原任何应用级公式:自铸一张 claims 里带**你自己指定的 secret** 的票,服务端便拿这个 secret 去验签,签名闸自行消失。**判据 = 同一签名类的 const-string 里同时出现 `Bearer `、claim 名与解析失败文案**。此形态下「N 种公式爆破 + 密钥字典」必然全灭(实测 144 公式全 401),别再烧轮次。

**★★ 「签的是参数值序」的签名器:GET 必须把 query 当 body 签 —— 否则整片 GET 恒失败,会被误判成「GET 面无权限」**:
客户端签名器呈 `buildSignature(map)` + `queryParamsToSignBody(query)` 形态(jadx grep `*SignatureHelper` / `queryParamsToSignBody` / `applySignatureHeaders`)时,签串 = **按 key 排序后的各参数值**以 `&` 连接,再拼 `&<秒级ts>&<小写UUID nonce>`,HMAC-SHA256(userSecret) 出 hex。GET 无 body ⇒ `queryParamsToSignBody` 把 query 转成同构 map 再签,即 **query 的值序就是签名对象**。
- **典型症状与误判**:POST 通道正常(走签名器),而**同族的全部 GET 恒回同一个 `签名验证失败-1`** ⇒ 极易被写成「GET 面无权限 / 端点未注册 / 该族封了」。真因只是把签串算成了空串。**判据 = 同一套头下 POST 通、全量 GET 同码失败 ⇒ 先改 GET 的签串构造,别判死 GET 面。**
- **空 query 的 GET 签串 ≠ 空**(仍是 `&<ts>&<nonce>` 形态),按「无参 ⇒ 空签串」想当然会命中上面那个坑。修正后同一批 GET 立即返业务数据(实测一次解锁整片资产/代理/返佣族)。
- **★ 签名对象随载体变,公式只有一套(别为加密体另创一套)**:同一签名器(`buildSignature(map)` + `applySignatureHeaders(..., encryptedFields, ...)`)下 —— GET = query 参数值;POST 明文体 = body 值;**POST 加密体 = wire 上那两个密文字段值(`{aes_key,data}`),且按它们在线上的形态(URL 编码后)取值**。差分判据:签明文值或签空体 → `签名验证失败-1`;签 urlenc 后的密文两值 → **过签名闸**。⇒ 遇到「签名恒失败」先问「我签的是哪一层载体」,再谈改算法。

> 完整配方/命令/坑位见 `references/client-sign-recovery-static.md`

**★ 服务端二进制在手 ⇒ 签名消息直接读(服务端侧还原)**:反汇编中间件的 `GenerateSignature`/`VerifySignature` —— 参数排序(`sort.Strings`+`mapIter*`)、拼接模板(`fmt.Sprintf` 格式串如 `%v&`)、算法(`hmac.New`)、输出编码(hex/base64)逐条落实,外部逐字复刻,别猜格式。同时读**密钥源函数**(如 `GetUserSecretKey`/`GetAppSecretKey` 并列出现)= 验证方支持多档密钥 ⇒ **先拿自己票据里已有的用户密钥实测,放行就整条跳过找应用密钥**。**哪档密钥生效由鉴权载体决定(实测矩阵)**:带 `Authorization: Bearer` ⇒ 验**用户密钥**;仅 `X-Api-Key`(无 Bearer)⇒ 验**应用密钥**;错配(带 Bearer 却拿应用密钥签)⇒ `签名验证失败-1`。判档 = 同端点『带票 / 不带票』各投一发;应用密钥一旦在某载体放行,即证服务端认可该 key 对。穿透判据:错误从裸 403/`access denied` 推进到下一层文案 = 上一道闸已过,**新文案即下一闸名**(缺什么头/什么载荷由它命名,逐层补)。⚠ **层序按路由而异,别拿 `Invalid AES key or data` 当签名通过证据**:要求加密信封的路由里它是**解密码头层**的直接拒态(明文体死在该层、签名层未被评审)⇒ 判签名层须用『同密文体、正确签 vs 错签』对照。配方见 `go-service-binary-dissection`「请求契约反查」。
- **★ 头名族必须从「该路由自己的验签函数」反汇编读出,不能按同服务里另一族外推**:同一服务可并存两套头名族(实测 `X-Timestamp/X-Nonce/X-Signature` 与 `clientTimestamp/clientNonce/clientSignature`),而**用错族与签错值回的是同一个错误文案** ⇒ 光看错误文本区分不了,矩阵盲扫头名还会互相污染。用法:反汇编目标 verifier(`go tool objdump -s "<pkg>.<Verifier>"`),读它自己的头名常量与取参调用;头名一律以该 verifier 为准。
- **★ 验签器读的是 `GetQueryMap()` ⇒ 业务身份参数必须放 query**:被签名/被鉴权的参数塞进加密信封体内时中间件看不到 ⇒ 恒回「参数缺失(-1)」而非签名不匹配(实测 `uid` 放加密体恒 -1,移进 query 参与签名后才推进)。**「参数缺失」先怀疑载体,不是怀疑算法**;IDOR 的身份参数同理只在 query 被采用。
- **★ 带有效票却报签名不匹配时,先枚举「票放哪个头」,再动算法**:服务端从某个特定头解析出 per-user 签名密钥,放错头 ⇒ 密钥解析失败 ⇒ 报的仍是「签名验证失败」,与「密钥/公式错」同文案(实测同一张有效票用 `token:` 头恒 -2,换 `Authorization: Bearer` 即过签名闸,而 `token:` 是 chat/OpenIM 面的正解)。判据 = 头位枚举 2–3 种 × 同一张票对照。
- **★ 「用户票打不通」先分清「用户路由」还是「App 路由」**:真票仍回 `403 access denied for user`(jwt 中间件层)⇒ 该端点族要的是 **App/应用级凭据**(ACCESS-KEY 或 app 密钥对),不是用户票 ⇒ 改投应用凭据,别继续修用户签名。
- **★ 回归排查:已知可用脚本就是基线,先逐字节 diff 自己的请求,再怀疑服务端/密钥**:同端点前一轮能读、后一轮恒拒,真因多次是**我方本轮改了请求构造**(换了头族、挪了票的头位、换了出口代理)。流程 = 原样跑一发基线脚本 → 与现脚本 diff 头集合/票头位/代理 → 只改一个变量再比。「我方构造改动」被写成「密钥错/服务端变了」会白扩整轮密钥字典。
- **★ 配方修正后,此前所有「该参数被忽略 / 该面无越权」的差分结论一律作废并重跑**:闸配方不对时(签名错、漏一个必需头、带着被判旧的版本头、body 没过信封层),中间件或软闸会用**同一响应**盖掉一切入参差异 —— 统一错误码,或**按会话身份回的默认载荷** ⇒ 目标 ID 与随机不存在 ID 逐字节一致。**那个一致性是请求被挡出来的,不是 handler 忽略参数的证据。** 实测踩过:整轮「该族 uid 一律被忽略、本平台无越权读路径」的定案,是在配方还差两个必需头时下的;配方锁定后同一 uid 差分立刻出现按 ID 分化的真实数据。⇒ 任何「参数被忽略 / 该面无越权」的判决都要写明**它是在哪个配方版本下取得的**;配方一改,旧判决降级为待复证,**别在新会话里当既成事实引用**(这类旧判决最容易被后手照着写「已排除」)。
- **★ 双原语同时错会互相掩盖(自己踩过)**:信封形态与签名基串**同时**错时,只修其中一个结果字节不变 ⇒ 极易被读成「该族无路 / 凭据不对 / 参数被忽略」并据此收线。⇒ 判「不可达」前先确认**签名基串、信封形态、头族、参数载体**四项都已按客户端源码修正,再跑一次对照;结论里写清依赖的是哪几个原语版本。
- **★ 凭据字段「存在但为空」≠ 这条路不存在**:登录/注册响应里的应用凭据成套下发(实测 `otcAppKey/otcAppSecret` 与 `kbitAppKey/kbitAppSecret` 并存),而本账号只在其一注册过 ⇒ 另一对**字段在、长度 0**。取用前先 `len()` 量一次,并去本地其他产物(代理端 bundle、落盘配置、历史响应)找同族字段真值 —— 别拿空串去签名再判「凭据无效」。

## 8. Web/H5 前端签名还原 —— 密钥通常是**明牌**,先找再算
App/native 之外,同一网关的 H5/网页端常把整套签名体面地写在 bundle 里。**顺序:先抠 bundle 找密钥与签法,再考虑任何爆破/枚举。**
1. **定位业务包** — 读 `index.html` 拿 `main.<hash>.js`;`runtime.<hash>.js` 里的分片清单才是权威。3MB 级 `scripts.*.js` / `vendors.js` 是第三方库(plotly/mapbox/ckeditor),其字符串里带 `/activiti-explorer/`、`/warning` 这类看似真路由的**诱饵**,拿去探测会白烧一轮 —— **只信业务 `main.*.js`**。同一 SPA 可能有多份构建(`:11443` 与 `:13443` 上的 `main.*.js` 不同 hash),以当前实际加载的那份为准。
2. **找签名函数** — 搜 `sign-data` / `signKey` / `appKey` / `app-key` / `MD5` / `hmac` / `signature` 的**调用点**,以及被多处引用的常量对象(密钥表通常就是一个 `{环境: {appKey, signKey}}` 字面量)。
3. **典型形态(门户网关族)**:
   ```js
   要签串 = accessToken + url + JSON.stringify(body) + signKey
   headers = { "sign-version":"1.0.0", "app-key":appKey, "timestamp":<ms>,
               "access-token":accessToken, "sign-data": MD5(要签串).toUpperCase() }
   ```
   **复现必须用 JavaScript 原生的 `JSON.stringify` 语义**(成员间逗号后无空格、转义规则一致)。用 Python `json.dumps` 默认参数(带空格)算出来的签串**永远不对** —— 这是自签失败最常见的原因。
4. **★ 看签串里有没有「可空字段」** — `accessToken` 取自身份 cookie(`APIGW-ACCESS-TOKEN` 一类),**缺失即为空串 ⇒ 签串前缀为空 ⇒ 无 token 也能造成服务端认可的签名**。这条比脱壳/解密取 token 便宜一个数量级,应当**先测**。
5. **密钥是矩阵不是单值** — 租户(品牌/机构代号) × 环境(test1/test2/prod)各一套 `appKey`/`signKey`,外加一个 `Basic`(常见 id=secret 弱模式,同一个 Basic 也用于 `/oauth/token` 的 client 认证)⇒ 视为「密钥已握有,N 组候选」,**不要再去枚举头名/字段名组合**:字段名是固定的(`sign-data`,不是 `sign`)、值就在包里,这类枚举是纯无效功。
6. **与章节 3 互补** — 预言机拿不到时自签是同一闸的另一条路;两条都不通,缺口就不是签名,转章节 5(缺实例 ID)。资源名同样从 bundle 里抠(如 `/api-gw-asset/{nwd-loan,nwd-loan-wap,loan-picture,open-gateway}`),别靠猜。
7. **★ 抠 bundle 要抠「请求拦截器」,不是只抠签名函数** — 决定闸门开不开的常是拦截器产物而非算法:① 默认头(如 `{api-version:"1", sign:"false"}` = 一个版本轴开关 + 客户端可主动声明免签);② **认证头注入规则**(`Authorization: "Bearer "+token`、自定义 `Token:` / `Kbit-Token:`,以及 localStorage 键名如 `token` / `user_secret_key`);③ 构造配置(baseUrl / walletUrl / **urlPrefix**,如 `urlPrefix:"/api/v1"` ⇒ 真前缀与 `^/v1/` 不同)。
   **实测价值:按拦截器逐字复刻后,恒回「请升级客户端」的路由立刻返业务数据(ErrCode:0)⇒ 那句文案是「你没按我的头来」,不是版本不够。**
   **★ 版本类闸先做「头消融」A/B,别升版本号**:这类「请升级客户端 / 版本过低」闸常由**客户端自报版本的那个头**(如 `Terminal-Version`)触发 —— 实测**整条头去掉后闸消失、同一路由直达业务层**,而升版本值/扫版本头名全部无效。判决序 = ① 逐头隔离(一次去掉一个头)找出触发头 ② 去掉它 ③ 才谈版本值。**「客户端版本太低」几乎从不是服务端的真判定,而是你自己带上去的自证。**
   **头名/字段名一律以客户端源码为准,不扫**:只有客户端也留空的**值**(版本号、AppType 取值)才值得枚举;一整轮 header 名/值矩阵(十几个 AppType 值 + 十来个版本头名 + sign 开关 + Origin + body/query 的 apiVersion)零变化是无效功的典型。
8. **★ 同 host「已知可用路由」做对照,先定性「按路由」还是「按连接」** — 同一套头、同一加密体下 A 路 `ErrCode:0`、B 路回神秘闸门文案 ⇒ 闸门**按路由**:同一 api-version 值下 A 已通过即证**版本值轴不是闸门**,立刻停止版本扫射(实测 17 个版本值全无效)。之后只剩:找 B 路由自己的真实调用形态(必填参数 / 加密开关 / 它其实属于另一个服务),或换读链族。

## 信封闸(请求体加密):三档错误码判据 + 自实现坑

管理后台/资金后端常见「请求体整体 AES 加密、AES key 再用服务端公钥 RSA 包一层」。这类闸的正确性判据**不是响应体像不像，而是错误码停在哪一档**:

| 档 | 响应形态 | 含义 |
|---|---|---|
| 闸层 | 框架/网关**统一码**(如 `4044`) | 明文体死在这层，**信封根本没被解** |
| **模型绑定层** | `.NET 400` / `Unexpected character encountered while parsing value: P` / `The <Field> field is required.` | **信封已解开**，服务端把解密后的 JSON 交给了模型绑定器 ⇒ 加密闸专属过渡态 |
| 业务层 | 业务错误码(如 `4009 User is not registered`) | 全链通，进 oracle 阶段 |

- **吃到模型绑定层 = 信封格式对的直接证据**，而且它**免费给出内层字段名与类型**(比回 bundle 反查快一轮)⇒ 先用空体/半体把绑定错误读全，再去 bundle 复核嵌套结构。
- **层序按路由而异，别外推**:要求加密信封的路由里，明文/错签都先死在信封层的 `Invalid AES key or data` —— 那是**解密码头层的直接拒态**，签名层根本没被评审 ⇒ 判签名层必须用「同密文体 + 正确签 vs 错签」对照。
- **自实现信封的两个本机坑(不是算法猜错，别回去重逆 bundle)**:① Python `cryptography` 的 CBC **不自动补 PKCS7**，不补就报 `The length of the provided data is not a multiple of the block length`；② 解响应时**先剥 padding 再 `json.loads`**，残留控制字符会报 `JSONDecodeError: Extra data`，看着像「信封不对」。
- **公钥从免鉴权端点现取**:`GetRsaPublicKey` / `getConfig` 类回 `{KeyId, PublicKey}` ⇒ 信封构造器就在**自己的 bundle 里**(搜该端点名的调用点，紧跟的 2–3 个短函数 = 生成 key/iv、组装信封、解响应)，不要盲扫头矩阵；`X-Skip-Encrypt: 1` 类**调试旁路头先试一发**，命中就省掉整条实现。
- **IP 白名单类闸与信封闸的分读**:`IP未授权访问：<ip>` 里 `<ip>` **等于你送的头值** ⇒ 该头被信任已成立，但「被信任」≠「能过白名单」(环回/内网段常不在名单)⇒ 结论写「需猜白名单内容」+ 按 ELB/NAT 出口与同机房段枚举，**不要写成「信任头无效」**；且 IP 闸常只罩部分路由(同 API 下有路由回 IP 未授权、有路由回登录失败)⇒ 先按路由分类再决定 oracle 读哪个码。

> ⚙ 信封/解密自实现（RSA 包 AES，含 padding 与响应解码坑）可直接跑验证：`scripts/envelope_rsa_aes.py`（`python3 envelope_rsa_aes.py --selftest` 先离线自证，再 `get_pubkey()` → `build_envelope()` → `strip_meta()` → `decode_response()`）。新建信封族时**先跑 selftest**，把本机实现排除掉，剩下的差异才可能是算法。

## Pitfalls
- **★ hybrid App(Flutter/uni-app/xapk)的协议不在 dex —— 但判壳只对当前这个 APK 成立,别按家族/版本外推**:`grep` dex 找不到 API 串 ≠ 没有 API 逻辑(业务在 `libapp.so` 或 H5 bundle);**同族另一个版本的 APK 可能是纯原生、契约就在 dex 里**(实测同产品旧版是 Flutter 壳、现役版是原生聊天端且 dex 静态引用钱包登录方法)⇒ 每拿到一个 APK 都重新判壳(有无 `libapp.so` / `assets/apps/__UNI__*` / 业务包 smali),把「本家 dex 无协议」当永久结论会白丢整条链。(`.xapk` 是 zip,内层 `base.apk` 要再解一层。)
- **判「签名过期/nonce 已消费」前先校时钟(§0)**:密钥/算法都对却恒失败的场景里,时钟偏差是最常见真因;跳过这一步会把时钟问题写成「预言机无效/密钥错」的假结论,白丢整条链。
- **批量扫不许把 500 视图错误、400 缺参当噪音过滤**:Spring MVC 下 `500 Could not resolve view with name '<path>'` = 控制器已执行(校验通过、SQL 已跑),`400 Required String parameter 'x' is not present` = 参数预言机。把这两类筛掉会连**真命中**一起丢掉;正确信号是「补参后该端点由报错转为静默/切换错误」。(机制:MyBatis 生成式 CRUD 控制器返视图名,数据层已执行但视图不存在。)
- **跳板机长扫必须落盘再筛**:`| head -N` 会截掉真正命中的那一段,先写 `/root/<任务>/hits.txt`,再用 `grep -v '<噪音特征>' + cut -c1-165` 打紧凑投影读。
- **同一路径 GET/POST 响应形态不同不等于接口不存在**:GET 返 nginx `<h1>404</h1>`、POST 返 Spring `{"status":404,"path":...}` 说明后端存在,只是方法/前缀不对;`405 Method Not Allowed` 提示该端点是另一种方法。
- **★ 扫描矩阵里必须有「完全不带该认证头」这一档,不能只测「带空值」**:空 `Authorization` 头(或空凭据字段)会被网关先拦成 `token解析失败-N`,把真实响应盖掉 ⇒ 会把「本可进入业务层」的端点批量误分类成「需鉴权」,也会把「免签」结论系统性带偏。先去掉空头重扫,再谈分类。
- **★ 从落盘配置/战利品里取到的签名密钥,先核环境标签再采信**:配置里的 `env: test` / `testapi.*` 域名指纹说明它属于测试环境,用它验生产活体票必然失败 —— **这是预期行为,不是「密钥找错了」**。核完标签再决定是否值得扩候选集;把环境错配读成密钥错会白扩一整轮字典。
- **★ 中间件先于路由匹配 ⇒ 中间件错误码不是「路由存在」的证据**:`签名验证失败-N` / `token解析失败-N` 由全局中间件在最前面产出,**与路径是否注册无关**(路径不存在时也可能先吃中间件);只有**带合法签名的请求**返 `404` / `ErrCode 65 Not Found` 才证路由层在答。⇒ 路由存在性一律以**服务端路由表**(二进制元数据 / bundle / 未签名的路由清单)为准,别拿中间件响应做推论 —— 「靠中间件错误码数出 N 条路径存在」会被路由表整体推翻。
- **★ 权威路由清单(spec)只权威「路径拼写」,不证明「该构建已注册」**:框架自生成的 `GET /openapi.json` / 自绘 spec 是路径名的权威来源(一次暴露从未试过的路由族,别再靠臆测路径名),**但同一产品的不同构建/不同域注册集可能相差很大**(实测生产域只注册资产族、同一批新路由全回框架兜底 `user not found`;测试域全注册、但回 `token已失效`)。⇒ ① 从 spec 列全路径,**逐条在目标构建上实测注册状态**再谈鉴权面;② 判「该路由未注册」要**跨构建/跨域 A/B**(同路径 A 域回兜底文案、B 域回中间件/票错 ⇒ 路由是存在的),单域错误串不足以定性,更不能把兜底文案当「产品里没这个路由」;③ **边缘/WAF 规则常按主机名挂载** ⇒ 整域统一 403/`access denied` 时,拿同族非生产域(配置泄露的域名池里常有)做一发对照,可能完全无规则直达应用层。
- **★ 无原生文案的 403 也要分层**:响应体 `access denied` 在二进制里 0 命中,不代表判定逻辑不在二进制 —— handler 分支(读哪个头、查哪张表)照样能从反汇编读出,**状态码由 handler 分支产出、文案由框架层补齐**是常见组合。**★ 已定性的闸不得据弱证据改写归因**:一轮已把该 403 定位到具体 handler 分支(读哪个头 → 查哪张表,反汇编级证据),且多条出口同码已排除网络侧 ⇒ 后续会话**禁止**因为「二进制里存在 `sys_filter_ip` 一类配置键名字符串」就把它改写成 IP 白名单、转去刷 `X-Forwarded-For`/`X-Real-IP`。**归因证据阶梯:多出口/多请求对照 & handler 反汇编 > 双请求差分 > 错误文案或错误信封形态(如换成小写 `{"code","msg"}`)> 产物里某个字符串存在**;低档不能推翻高档,改写只在拿到新的高档证据时成立(配置键名只是**存在**,不证明该路由启用了它)。
- **不要用长度猜签名算法**:`signature` 是 64 hex 只能说明 SHA-256/HMAC-SHA256,推不出密钥;有预言机就别碰算法。
- **`render/{name}` 类 SSR 路由未命中常回 SPA catch-all 200** ⇒ 别拿 200 HTML 当「路由存在」证据;先拿一条**确定不存在**的路径取基线(体积/是否含 SPA 外壳),再对候选做差分。
- **响应里的 `sign` 是响应完整性签名**:同一 rspCode 下恒定,不泄密钥,别浪费时间。
- **★ 判「闸已被强制」之前先做矩阵,单次 4xx 不构成证伪**:同一个闸(如「完成 N 段验证才可提交」)一次尝试回 `400/会话已失效`、另一次却**放行并产生真实业务记录**,唯一变量是**会话年龄**(实测 `open→提交 ≈40s` 放行、`≈80s` 拒绝,TTL 约 60–73s)⇒ 判据必须带**每发时间戳 + 关键动作间隔秒数**并跨尝试对照;拿单次拒绝写「服务端硬闸」= 假阴性。判决矩阵(零步/部分步/显式放弃/全完成四档,最后一档是必进的阳性对照)缺一档整轮结果无效。
- **★ 状态变更的归属只认服务端产物,不认本地日志**:本地日志会被下一次运行覆盖、后态字段也常未序列化 ⇒ 用**服务端侧三件套**(业务记录数组 `{seq,amount,user_id}` + **账单流水/流水号的分钟级时间戳** + 余额)对齐时间线,才能定位「哪一次会话造成了这笔变更」。
- **★ 判决实验必须在「新鲜且可回收」的对象上做**:对象被消耗完后就无法再验闸门 ⇒ 另建**最小额**对象(自有账号间流转、到期原路退回);**建对象的金额受当前余额硬限**,先于任何「最小额」声明触发。
- **★ 驱动脚本的 env 开关名常与语义相反**:`MINT_SKIP=1` 这类名字可能表示「复用现有凭据」而非「跳过校验」⇒ 复用过期凭据只回握手失败/TTL 码,表象像协议错。执行前 `grep` 该 env 在驱动里的读法;凭据铸新与使用必须落在**同一次运行内**,跨调用必过期。
- **★ 「链接无效」类业务码先当「我方载具/前缀形态错」查**:同一对象往往有五套载具(裸载荷 / 动作前缀 A / 动作前缀 B / 列表前缀 / URL 深链),各自只贴在特定入口上;而前缀**几乎只出现在客户端渲染物里** ⇒ 去读渲染出来的按钮 URL 与其 query 拿真前缀,**不要枚举前缀猜**(实测猜前缀一律回「链接无效」,读到真前缀后一击命中)。此类「URL 按钮」通常无 click API,等价复刻 = 把 URL 里的参数**原样取出、原样送回**给对应的深链接口。
- **★ oracle 本身会「时变」,单次观测不得当真相**:同一 `(路径+方法)` 可在不同时间窗口给出互斥结果(存在/不存在),根因多为**多副本**(部分副本没部署该路由)或**灰度**。⇒ ① 每发**带时间戳落盘**;② 同发**重复采样**;③ 扫描**头尾各放 CTL 块**(已知端点 + 两方法)自诊断窗口,CTL 异常则该轮**整批作废**;④ 负结论只写「**该窗口内 404**」。
- **★ 别把被证伪的自造机制当结论(自己踩过)**:「缺必需参数 ⇒ 服务端伪装 404」曾看似被数据支持,实为**跨窗口采样造成的伪相关** —— 同一分钟内裸路径与带参数结果完全相同。⇒ **任何「某参数决定路由匹配」的结论必须同窗口 A/B 对照**。
- **★ 探针 helper 不传方法 = 整轮方法结论作废**:inline helper 若忽略 method 一律发 POST,会把「GET 未注册」读成「GET 已注册」。⇒ 同一路径的 GET/POST **必须在同一分钟内背靠背各打一次**,并拿已知单方法路由(如只注册 POST 的端点)做正控。
- **★ 拿不到密钥时的有界爆破止损线(离线)**:候选集只从**站点派生 + 编码变体**构造(10⁴ 量级),**零命中即结论「密钥是随机串」**,立刻转读配置载体;**不要把候选扩到 10⁷** —— 那已是大字典,按纪律须先请示,且大概率仍然零命中。试过的编码变体(中文参数是否 urlencode)要写进结论,它整体改变签名串。
- **★ 别把每条记录里的随机 32hex 列当成站点主密钥**:一列 32hex 若几乎「一记录一值」,那是**每单独立密钥**;可以拿它试一次,但不能作为主攻假设,更不要在失败后围绕它扩建候选集。
- **★ 签名盐/挑战值常在报错体里明牌**:构造验证前先读一次错误响应正文 —— `hashsalt`/`nonce`/`challenge` 可能由同一个 act 或另一条免鉴权 act 明文吐回,别默认要去前端 JS 里挖。
- **★ 闸门打不动时先找「配置载体文件」,而不是继续怼闸**:同目录里**返回 `[200]` 且 `len=0`** 的 `.php`,而兄弟文件(`config.php`/`db.php`/`xxx_config.php`)全是真 404 ⇒ 这个空体文件就是 `<?php return [...]>` 风格的配置载体,**存在性已被证实**。判据 = 「同目录兄弟全 404 + 它 200 空体」;确认后转 LFI / 备份名变体 / 源码包路径,**不要在 `.bak`/`~`/`.git` 上耗**。
- **★ 验证码先判「服务端是否真校验」再决定投入**:取号端点回 `{success,version}` —— `success:0` = 离线模式(才有绕过空间);`version:0`=v3(字段 `geetest_challenge/validate/seccode`)、`version:1`=v4(字段 `lot_number/captcha_output/pass_token/gen_time`)。登录报错措辞区分:「验证加载失败」= 缺字段/瞬时(补字段或重试),「验证失败,请重新验证」= **服务端真校验** ⇒ 后者下字段绕过矩阵(`|jordan`/`md5(challenge)`/全 1/空字段/改名变体)全灭,别耗,直接上真浏览器解题或改走无验证码的 API 面。**页面里的 `captcha_open=0` 只表示 DOM 无 `#captcha`,不代表服务端不校验。**
