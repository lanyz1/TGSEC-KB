# buyer-facing-api-unauth-chain

**触发**：卡密商城 / 寄售 / 自动发货 / 白标站，商家或管理后台（`/merchantApi/*`、`/adminApi/*`）几乎全 401，但买家前台（`/shopApi/*`、`/api/*`）公开。目标通常是「拿到全量卡密 / 订单 / 货源」。

## 铁律

1. **别停在 401 上，先把公开那一侧全量枚举**。前台 bundle 里常藏着「本该要登录」的读接口（订单详情、资源详情）。先提全部路径再逐个打，**非 401 的（200 / 500）都是面**。
2. **契约靠 bundle 反推，不靠猜字段名**。猜字段只会拿到一句无信息量的校验错误（如「请输入安全密码」），看不出是字段名问题，能白烧十几轮。★ 抓前台 bundle 必须 `curl --compressed`：bundle 常是 gzip，直接落盘再 grep 会 0 命中（文件头 `1f 8b`），会被误判成「bundle 里没有 API」。
3. **枚举值先用字符串再试数字**。数字 `0` 常回空集（`total:0, list:[]`），会误判成「店铺没货 / 没数据」；同族枚举多是字符串字面量（`"card"` / `"article"` / `"resource"` / `"equity"`）。数字返空 ≠ 无数据。
4. **错误文案要做正向 oracle**。别只记否定句：同一接口对不同输入回两种文案时，**另一种文案就是存在性 / 状态的正向信号**（「用户名不存在」= 否；「密码不能少于6位」= 该用户**存在**）。拿它做枚举，比撞库省一个数量级。
5. **节流记账键先做对照实验，再决定要不要烧 IP 池**。应用层「操作频繁请10分钟后重试」常按 `X-Forwarded-For` / `Client-IP` 记账 ⇒ 逐请求轮换该头即相当于无限次；而 `X-Real-IP` / `True-Client-IP` / `Forwarded` / `X-Originating-IP` 常不被信任。**三组同出口对照钉死**：A 不带伪造头 → 全节流；B 每发唯一值 → 全真实业务应答；C 固定一个**全新**值 → 真实应答（新桶 = 满配额）。招牌判据：**连不存在的账号也返「操作频繁」⇒ 键不是账号**。判错会把可无限打的登录面当成「每 IP 5 次」而放弃；实测轮换 XFF + 20 线程 = **62 次/秒（较受限速 0.9/s 提速 69 倍）**。★ 若节流在**边缘/CDN 层按真实 TCP IP 记账**（换了伪造头仍被拦），见「陷阱」的源站直连。
6. **写动作留边界**。下单 / 注册会落库，用最小量（`quantity:1`）验证契约；改密类（`user/forget`）会清 2FA 且不可逆，先确认是否强制验证码，排在只读路径之后。
7. **一个租户令牌就能横推全平台清单**。拿任一有效 `Merchant-Token` 去打「我的下级 / 上级 / 货池」类接口，常一次拿到全站商户表（含 link / `agent_id`）、货池、他店商品；`order/list {agent_id:<n>}` 还能跨店读订单列表。★ 但**交付物（卡密本体）几乎总是本店作用域**：跨店详情端点返空（或抛框架错误页）、导出接口忽略 `agent_id` ⇒ 能用清单锁定目标店，卡密仍要逐店拿令牌。
8. **「缺参数回空」不是「无数据」**。导出 / 列表接口的参数必填项要照实摸全：参数名错或漏传 `status` / `days` 这类筛选字段会回空集，看起来像「无洞」。先对同一接口做参数差分（全参 → 逐个删）再下结论。

## 交付（卡密类目标）

- **必须附「卡密 → 兑换地址」对照表**：卡密本体常只是 hex 兑换码，用户拿到也不知道去哪用。兑换站写在**商品描述 HTML** 里 —— 免鉴权 `POST /shopApi/Shop/goodsInfo {token, goods_key}` 取 `description`，去标签后正则抽 `https?://`，逐商品建 `secret / 商品名 / 兑换地址 / goods_id` 对照表（用户原话：「不然我看不懂」）。兑换站常对机房出口返 CF 403 —— 打不开 ≠ 站点挂。
- **报告默认脱敏，用户说「未脱敏」时出全明文版**：凭据 / 令牌 / 卡密样本 / 联系方式全原文，报告头标「敏感件勿外发」，并单列「边界与纪律」节（卡密仅作证据、未兑换未外发、未做破坏性操作）。

## 流程

### 1 摸公开面
- 入口：`/shop/<token>`、`/item/<key>`、`/package/shop/assets/index.*.js`（`curl --compressed`）
- 从 bundle 提 `/<x>Api/...` 路径 + 每个请求的 body 字段名，顺带看 `localStorage` 里 token 的键名（往往就是鉴权头名）
- 逐个探测：**200 / 500 都记下来**；500 + `<title>系统发生错误</title>` = handler 存在但参数不合法 ⇒ 继续摸参数

### 2 读面优先（只读，先把泄露榨干）
- 订单 / 资源详情接口先打一遍 —— 未付款也吐数据的情况很常见
- 详情里**回吐的嵌套对象常是最大泄露**：上游 / 供货商对象（含上游 `user_id`、上游资源 key、成本价、销量）⇒ 反推该店是转售货源，并给横向找上游的入口
- 判据：数量 / 金额 / 状态字段只在业务完成后才出现（如 `sendout:0` + 空内容）⇒ **未完成态读不出交付物，别在这条路上耗**；要出交付物必须先把状态推进到完成

### 3 拿账号（需要侧门时）
- 用户名枚举 oracle（铁律 4）
- 登录面先确认：是否需要验证码、是否有安全模式 / 锁定
- 节流绕行（铁律 5）后再跑定向口令表；**优先只读 + 可恢复的凭据路径**，改密类排最后

### 4 支付面
- 下单响应里的 `payurl` 多半是站内中转 ⇒ `GET` 它并看 302 `Location`：`/payApi/<Plugin>/pay.html` ⇒ **回调端点 = `/payApi/<Plugin>/notify`**，插件名由此确定，不用猜
- 枚举插件名：404 = 无此插件；**500 PHP 致命错误 = handler 存在**，可达 → 继续摸签名
- 官方渠道插件（支付宝 / 微信）走 RSA 验签，伪造门槛高；彩虹易支付族走 md5/sign，优先打

## 陷阱

- 交付物编号多是「前缀 + 日期 + 随机串」，**不可枚举** ⇒ 别指望遍历订单号拿他人已发货内容，走后台 / 回调
- 金额 = 价签 ×（1 + 手续费率）。**据金额差异判定「有优惠 / 被篡改」前先算手续费**
- 同一接口换个出口 / 会话后可能回「请用联系方式重新查询」这类身份约束提示 —— 换 `contact` 重下单即可，不是被封
- 后台路径可能被改：整片 `/adminApi/*` 回「请使用正确的后台路径访问」= **路径被改过，不是 401/403**，别判定成「接口不存在」而收线
- 管理登录的 WAF 弱口令规则是「用户名 + 口令」**组合式**字面黑名单：换用户名 / 加尾空格即可绕过被点名的那一对；但换用户名会连带改变业务结果，先确认应用是否 trim
- **吞吐被边缘层掐住时直连源站**：如果拦你的是 CDN 域名的 CC / 防护层（换伪造头也拦、连 GET 都 502 / 挑战页），拿源站 IP 后 `curl -sk --compressed https://<源站IP>/<path> -H "Host: <站点域名>"` → HTTP/2 200，绕开边缘记账；源站仍按 XFF 记账 ⇒ 轮换照旧。直连「域名」作废 ≠ 直连「源站 IP」作废。
- **弱口令喷洒不是主路径**：全站店铺口径不同源，几百店 × 几十条经典口令可能一发不中；先把吞吐解放了，也要提前算 ROI。命中往往是巧合，不是普遍规律。
